# Part 1 — Fundamentals & JavaScript for Backend

## Node.js architecture at a glance

Node.js is a stack of layers: your code calls the JavaScript core library, which calls C++ bindings, which hand work to V8 (to run JS) or libuv (to wait on I/O).

&#91;embedded content: Node.js architecture · 6 layers\]

When an interviewer says "explain what happens when you call `fs.readFile`", walk this picture top to bottom: core library, binding, libuv thread pool, OS read, then back up through a callback queued on the event loop. Part 2 (Q7a, below) draws that return trip step by step.

## Core questions: what Node.js is

### Q1 \[I\] What is Node.js, in one minute?

**Say this first:** Node.js is a JavaScript runtime built on V8 (which executes JavaScript) and libuv (which provides the event loop, async I/O and a thread pool). It runs one JavaScript thread per process and handles concurrency by never waiting on I/O: it starts the I/O, registers a callback, and keeps running other work.

**Then go deeper:**

- **V8** compiles and runs JS, manages the heap and garbage collection. It knows nothing about files, sockets or timers.
- **libuv** is a C library that wraps OS async primitives (epoll on Linux, kqueue on macOS, IOCP on Windows) and runs the event loop. Work the OS cannot do asynchronously (most file system calls, `dns.lookup`, some crypto, zlib) goes to its thread pool (default 4 threads).
- **Node bindings** (C++) connect JS APIs like `fs.readFile` to libuv and V8.
- **Node core library** (JS) is what you import: `node:fs`, `node:http`, `node:stream`.

**Common mistake:** saying "Node.js is single-threaded." Your JavaScript runs on one thread, but the process has several: the libuv pool, V8's GC and compiler threads, and any worker threads you start.

**Follow-ups:** \[A\] Which operations use the thread pool and which do not? (Network I/O does not; it uses OS readiness notification.) \[E\] What happens to latency if you run 50 concurrent `crypto.pbkdf2` calls with the default pool size?

### Q2 \[I\] Node.js vs JavaScript vs the browser

JavaScript is the language (ECMAScript spec). Node.js and browsers are two host environments that embed a JS engine and add their own APIs.

| Aspect | Node.js | Browser |
| --- | --- | --- |
| Host APIs | fs, net, http, child\_process, worker\_threads | DOM, fetch, localStorage, Web Workers |
| Global object | `globalThis` (also `global`) | `globalThis` (also `window`) |
| Modules | CommonJS and ES Modules | ES Modules |
| Event loop | libuv phases + nextTick + microtasks | HTML spec: tasks, microtasks, rendering |
| Security model | Full OS access by default (permission model is opt-in) | Sandboxed, same-origin policy |
| Shared since Node 18+ | `fetch`, `URL`, `AbortController`, `TextEncoder`, `structuredClone`, Web Streams | same |

**Interview trap:** "Node has no `fetch`." It has had a global `fetch` (built on undici) since Node 18, stable since Node 21.

### Q3 \[A\] Why is Node good for I/O-bound work and poor for CPU-bound work?

A request that spends 95% of its time waiting on a database costs almost nothing while waiting, so one thread can hold thousands of them. A request that spends 200 ms computing a hash in JS blocks the only JS thread, so every other request waits 200 ms too.

```js
// Blocks every request for the full loop
app.get('/report', (req, res) => {
  let sum = 0;
  for (let i = 0; i < 5e9; i++) sum += i; // CPU-bound on the main thread
  res.json({ sum });
});
```

**Production answer:** move CPU work to `worker_threads` (a pool such as Piscina), a separate service, or a queue worker; keep the request thread for I/O orchestration. Covered in Part 7.

### Q4 \[I\] What does the Node.js CLI give you that interviewers ask about?

```bash
node --watch server.js            # restart on change (stable since 22)
node --env-file=.env server.js    # load env vars without dotenv (20.6+)
node --test                       # built-in test runner
node --inspect server.js          # Chrome DevTools debugger on :9229
node --cpu-prof app.js            # write a .cpuprofile on exit
node --heapsnapshot-signal=SIGUSR2 app.js
node --max-old-space-size=2048 app.js   # heap limit in MB
node --enable-source-maps dist/app.js
node --permission --allow-fs-read=./data app.js  # permission model
```

**The REPL** (`node` with no arguments) evaluates each line and prints the result. Useful features: top-level `await`, `_` (last result) and `_error` (last error), `.editor` for multi-line input, `.load` / `.save` for files, Tab completion, and `node -p "expr"` to print one expression from the shell. Debug a running REPL with `node --inspect` and DevTools.

The `node:repl` module lets you embed a REPL in your own app, which some teams use as an admin console. **Production warning:** a REPL exposed on a socket is remote code execution for whoever can connect. If you build one, bind it to a Unix socket with file permissions, never to a TCP port, and prefer one-off job scripts that are reviewed and logged.

### Q5 \[I\] How would you structure a Node.js service?

A layout that survives growth separates transport, business logic and data access, so each can be tested and replaced on its own:

```text
src/
  app.ts            # build the app (no listen) -> testable
  server.ts         # listen, signals, graceful shutdown
  config/           # validated env config, one place
  modules/
    orders/
      orders.routes.ts      # HTTP: parse, validate, map errors
      orders.service.ts     # business rules, no req/res
      orders.repository.ts  # SQL / ORM calls
      orders.schema.ts      # zod / JSON schema
  lib/              # logger, db pool, http client
test/
```

**Senior signal:** split `app` from `server` so integration tests can start the app on an ephemeral port, and group by feature (modules/orders) rather than by layer (controllers/, services/) once the codebase passes a few modules.

## Packages: npm, package.json, lockfiles, semver, LTS

### Q6 \[I\] Walk me through the important fields in package.json

```json
{
  "name": "orders-service",
  "version": "1.4.2",
  "type": "module",
  "engines": { "node": ">=22" },
  "main": "./dist/index.cjs",
  "exports": {
    ".": { "import": "./dist/index.js", "require": "./dist/index.cjs" }
  },
  "scripts": { "start": "node dist/server.js", "test": "node --test" },
  "dependencies": { "pg": "^8.13.0" },
  "devDependencies": { "typescript": "~5.6.0" },
  "peerDependencies": { "react": ">=18" },
  "files": ["dist"],
  "private": true
}
```

- `type: "module"` makes `.js` files ESM; without it they are CommonJS. `.mjs` / `.cjs` override per file.
- `exports` is the public API of a package; anything not listed cannot be imported (Part 4 covers conditional exports).
- `engines` documents the supported Node range; npm only warns unless `engine-strict` is set.
- `private: true` blocks accidental `npm publish`.
- `peerDependencies` say "the host app must provide this" (plugins, framework adapters).

**Common mistakes:** using `main` alone in a library that also needs ESM consumers (they get the CommonJS build and a dual-package hazard, Part 4); forgetting `files`, so tests, fixtures and `.env.example` ship to npm; running anything important in `postinstall`, which consumers may disable with `--ignore-scripts`.

**Theory vs production:** theory is knowing each field. Production is treating `package.json` as a contract: `engines` checked in CI, `exports` reviewed like a public API, and lifecycle scripts audited because install scripts are the main supply-chain attack path.

**Follow-ups:** \[A\] What happens if `exports` and `main` disagree? (`exports` wins on Node 12.7+; `main` is the fallback for old tools.) \[S\] How would you stop a new transitive dependency from running install scripts in CI? (`npm ci --ignore-scripts`, then explicitly allow the few packages that need native builds.)

### Q7 \[I\] What do ^ and \~ mean in semver ranges?

Semver is MAJOR.MINOR.PATCH: breaking, feature, fix.

| Range | Allows | Example `1.4.2` matches |
| --- | --- | --- |
| `^1.4.2` | same major | 1.4.2 to <2.0.0 |
| `~1.4.2` | same minor | 1.4.2 to <1.5.0 |
| `1.4.2` | exact | 1.4.2 only |
| `^0.4.2` | same minor when major is 0 | 0.4.2 to <0.5.0 |

**Trap:** `^0.x` behaves like `~`. Pre-1.0 packages treat minor bumps as breaking.

**What semver actually guarantees:** nothing. It is a promise from the maintainer, not a check by npm. A patch release can still break you, which is why the lockfile pins exact versions and why upgrades go through CI.

**Follow-ups:** \[A\] How do you force one version of a vulnerable transitive package? (`overrides` in npm, `resolutions` in Yarn, `pnpm.overrides` in pnpm, then verify with `npm ls <pkg>`.) \[S\] Your service broke after a fresh install with no code change. How do you find the culprit? (Diff the lockfile between the two builds, then bisect the changed packages.)

### Q8 \[A\] Why commit the lockfile, and what is the difference between npm install and npm ci?

Ranges in `package.json` describe what is *acceptable*; the lockfile records what was *actually installed*, including every transitive dependency and its integrity hash. Without it, two builds a week apart can install different code.

|  | `npm install` | `npm ci` |
| --- | --- | --- |
| Reads | package.json, updates lockfile if needed | lockfile only, fails if out of sync |
| node\_modules | reuses | deletes and reinstalls |
| Use in | local development | CI and Docker builds |

**Senior signal:** `npm ci --omit=dev` in production images, `npm audit` / `osv-scanner` in CI, and review lockfile diffs in pull requests because that is where supply-chain changes appear (Part 9).

**Common mistake:** adding `package-lock.json` to `.gitignore` in an application "because it causes merge conflicts." Resolve conflicts by regenerating from `package.json` (`npm install --package-lock-only`) instead. Libraries may skip publishing a lockfile, because consumers ignore it anyway; applications never should.

**Follow-ups:** \[A\] Why does `npm ci` fail when `package.json` and the lockfile disagree? (It refuses to guess; a mismatch means someone edited one without the other.) \[E\] Is a lockfile enough to reproduce a build? (Not fully: the Node version, OS, CPU architecture and native builds also matter, which is why the Docker base image is pinned too.)

### Q9 \[I\] dependencies vs devDependencies vs peerDependencies vs optionalDependencies

- **dependencies**: needed at runtime.
- **devDependencies**: build, test, lint only; not installed with `--omit=dev`.
- **peerDependencies**: the consumer provides it; npm 7+ installs them automatically and errors on conflicts.
- **optionalDependencies**: install failure does not fail the install (native addons with fallbacks).

**Mistake:** putting TypeScript type packages your published library exposes into devDependencies. If your public `.d.ts` files reference `@types/express`, consumers need it.

**Production angle:** your Docker image size, install time and attack surface all depend on keeping devDependencies out of the runtime image. Use a multi-stage build: install everything to compile, then `npm ci --omit=dev` in the final stage (Part 12).

**Follow-ups:** \[A\] When should a framework adapter use a peer dependency instead of a dependency? (When the host app must share one instance, such as a single React or a single ORM, so two copies would break `instanceof` checks or shared state.)

### Q10 \[I\] What are Node.js release lines and LTS?

**Say this first:** the schedule just changed. Up to Node 26, Node shipped two majors a year (April and October) and only even-numbered majors became LTS. From Node 27 onward there is **one major per year**: alpha from October, release in April, LTS promotion the following October, and **every release becomes LTS**. Node 26 is the last line under the old model. ([Node.js announcement, March 2026, via InfoQ](https://infoq.com/news/2026/06/nodejs-release-changes))

| Line | Status, November 2026 | End of life |
| --- | --- | --- |
| Node 26 | Active LTS since 28 Oct 2026 | April 2029 |
| Node 24 | Maintenance LTS | April 2028 |
| Node 22 | Maintenance LTS, critical fixes only | 30 April 2027 |
| Node 27 | Alpha channel from October 2026; release April 2027; LTS October 2027 | April 2030 |

Sources: [fireup.pro on Node 26 LTS](https://fireup.pro/news/nodejs-26-lts-whats-new-upgrade), [DEV Community summary of the new schedule](https://dev.to/mr_manushukla/one-nodejs-release-a-year-from-2027-what-the-node-27-lts-change-means-for-your-upgrade-cadence-2fo3). The authoritative record is `schedule.json` in the [nodejs/Release](https://github.com/nodejs/Release) repository.

**Why it changed (good follow-up material):** most organisations only ran LTS anyway, odd releases mostly went untested in production, and a volunteer-maintained project carries less backporting work with one line a year. The new alpha channel is where library authors are expected to test early.

**Common mistake:** "odd versions are never LTS" is now only true up to Node 25.

**Follow-ups:** \[S\] How do you plan an upgrade? (Run the next LTS in CI next to the current one for a sprint, check native addons rebuild against the new V8, read the removed-API list, roll out per service.) \[E\] A dependency only supports the old line: what do you do? (Pin, isolate the service, contribute the fix, or replace it; never block the whole fleet on one package.)

**Production rule:** run an Active or Maintenance LTS line, pin the major in Docker (`node:26-alpine` or an image digest) so a rebuild never silently jumps a major, and schedule the upgrade before end of life, not after. Check the live schedule rather than memorising dates.

### Q11 \[A\] npm vs pnpm vs Yarn

- **npm**: default, flat `node_modules`, workspaces since v7.
- **pnpm**: content-addressed store with hard links; strict layout prevents using undeclared ("phantom") dependencies; fast and disk-efficient; strong for monorepos.
- **Yarn Berry**: Plug'n'Play (no `node_modules`), zero-installs; strictest, with some tool-compatibility cost.

**Interview point:** a phantom dependency is a package you `require` that is not in your package.json but happens to be hoisted. It works until the hoisting changes. pnpm makes this a hard error.

**How to answer "which would you pick?":** for a single service, npm is fine and has the least friction. For a monorepo with many packages, pnpm's strictness and disk savings usually win. Name the trade-off you accept (tool compatibility, team familiarity) rather than declaring a winner.

**Follow-ups:** \[A\] What is `corepack`, and why was it controversial? (A shim that installs the package manager version pinned in the `packageManager` field; Node stopped bundling it from Node 25, so teams now install it explicitly.) \[S\] How do you enforce one package manager across a team? (`packageManager` field, `engines`, and a CI check that the right lockfile is the only one present.)

## Configuration: environment variables, dev vs prod

### Q12 \[I\] How should a Node service read configuration?

**Short answer:** read `process.env` once at startup, validate and coerce it into a typed, frozen object, and fail fast if anything is missing. Never scatter `process.env.X` through the codebase.

```ts
// config.ts
import { z } from 'zod';

const Env = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.string().url(),
  DB_POOL_MAX: z.coerce.number().int().positive().default(10),
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
});

const parsed = Env.safeParse(process.env);
if (!parsed.success) {
  console.error('Invalid configuration', parsed.error.flatten().fieldErrors);
  process.exit(1); // crash at boot, not on the first request
}
export const config = Object.freeze(parsed.data);
```

**Why:** every `process.env` value is a string (or `undefined`). `process.env.DB_POOL_MAX + 1` is `"101"`, not 11. `process.env.FEATURE === true` is always false.

### Q13 \[A\] .env files: dotenv vs --env-file, and what not to do

- Node 20.6+ supports `node --env-file=.env app.js` and `process.loadEnvFile()` (21.7+), so dotenv is optional for simple cases.
- `.env` is for local development. Commit `.env.example`, never `.env`.
- In production, inject variables from the platform (Kubernetes Secrets, AWS SSM / Secrets Manager, Vault). Files on disk and environment variables both leak through crash dumps, `/proc/<pid>/environ` and careless logging.

**Mistake:** logging `process.env` or the whole config object at startup. Redact secrets explicitly (Part 9, Part 11).

### Q14 \[I\] What does NODE\_ENV=production actually change?

Node core itself barely looks at it. Libraries do:

- Express turns off stack traces in error responses and caches view templates.
- Many libraries skip dev-only checks and warnings.
- `npm install` with `NODE_ENV=production` skips devDependencies (prefer explicit `--omit=dev`).

**Trap:** using `NODE_ENV` for environment names like `staging`. Keep `NODE_ENV` as a build mode (`production` in every deployed environment) and use a separate `APP_ENV` or `DEPLOY_ENV` for staging vs production, otherwise staging runs dev-mode code that production never runs.

### Q15 \[S\] Twelve-factor config: what changes at senior level?

- **Config is not code, but its schema is.** Version the schema, review changes to defaults.
- **Secrets rotate.** A process that reads a secret once at boot needs a restart or a reload path when it rotates; short-lived credentials (IAM roles, Vault leases) are better than long-lived keys.
- **Feature flags are not env vars.** Env vars need a deploy to change; use a flag service for runtime toggles with audit history.
- **Same image, every environment.** Build once, promote the identical artifact; only config differs.

## JavaScript for backend: types, coercion, scope, closures

### Q16 \[I\] What are the JavaScript types, and which ones bite backend code?

Seven primitives (`string`, `number`, `bigint`, `boolean`, `undefined`, `null`, `symbol`) plus `object` (arrays, functions, dates, maps are all objects).

The ones that cause production bugs:

- **number** is a 64-bit float. Integers are exact only up to `Number.MAX_SAFE_INTEGER` (2^53 − 1). A PostgreSQL `bigint` id like `9007199254740993` silently becomes `...992`. That is why `pg` returns `int8` as a string by default.
- **Money:** `0.1 + 0.2 !== 0.3`. Store minor units as integers or `bigint`, or use a decimal library. Never floats for balances (Part 15, wallet design).
- **JSON** has no `bigint`, `Date`, `undefined`, `Map` or `NaN`. `JSON.stringify({ n: 1n })` throws; `JSON.stringify({ a: undefined })` drops the key; dates become strings and do not come back as dates.
- **null vs undefined:** `typeof null === 'object'` (a historic bug). Use `??` for defaults so `0` and `''` survive.

```js
const limit = Number(req.query.limit) || 20;   // 0 becomes 20 (bug if 0 is valid)
const limit2 = Number(req.query.limit ?? 20);  // keeps 0, but NaN for 'abc'
// production: validate with a schema and reject bad input with 400
```

### Q17 \[I\] == vs ===, and coercion traps that matter on a server

`===` compares without conversion. `==` applies coercion rules that almost nobody remembers. Use `===` everywhere; the one accepted idiom is `x == null` to test for both null and undefined.

```js
'0' == false        // true
[] == false         // true
null == 0           // false
null >= 0           // true  (relational ops coerce null to 0)
'10' < '9'          // true  (string comparison)
[1, 10, 2].sort()   // [1, 10, 2]  (default sort compares strings)
```

**Backend consequence:** query strings and headers are strings. `if (req.query.admin)` is true for `'false'`. Parse and validate at the edge.

### Q18 \[I\] var, let, const, scope and hoisting

- `var` is function-scoped and hoisted with value `undefined`.
- `let` / `const` are block-scoped and hoisted into the **temporal dead zone**: accessing them before the declaration throws `ReferenceError`.
- Function declarations are hoisted with their body; function expressions are not.
- `const` prevents rebinding, not mutation: `const cfg = {}; cfg.a = 1` is fine. Use `Object.freeze` (shallow) for immutability.

```js
console.log(a); // undefined
var a = 1;
console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 2;
```

### Q19 \[I\] What is a closure, and where do closures show up in Node code?

A closure is a function that keeps access to the variables of the scope where it was created, even after that scope has returned. V8 implements this by keeping the captured variables in a heap-allocated **context** object instead of on the stack.

```js
function makeCounter() {
  let count = 0;            // lives in a context object on the heap
  return () => ++count;     // the arrow holds a reference to that context
}
const next = makeCounter();
next(); next(); // 2
```

In Node: every callback, every middleware factory (`(opts) => (req, res, next) => ...`), module-level private state, and memoisation.

**Senior angle, memory:** a closure keeps its whole context alive. If a long-lived callback (a timer, an event listener, a cache entry) closes over a large object, that object cannot be collected. V8 shares one context per scope among all closures created there, so a small closure can retain a big variable that a sibling closure used.

```js
function handler(req) {
  const big = Buffer.alloc(50 * 1024 * 1024);
  const size = () => big.length;          // captures big -> big goes into the shared context
  size();
  emitter.on('tick', () => console.log(req.url)); // same context, so it keeps big alive too
  // listener is never removed -> one leaked listener and 50 MB per request
}
```

Fix: remove listeners (`once`, `off`, or `AbortSignal`), and do not capture what you do not need. Part 3 covers finding this in a heap snapshot.

### Q20 \[A\] The classic loop-closure question

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);
// 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j), 0);
// 0 1 2
```

`var` creates one binding shared by all iterations; by the time the timers fire, it is 3. `let` creates a fresh binding per iteration, so each callback closes over its own value.

## JavaScript for backend: prototypes, this, execution context

### Q21 \[I\] How does prototypal inheritance work, and what does class compile to?

Every object has an internal `[[Prototype]]` link. Property lookup walks that chain until it finds the key or reaches `null`. `class` is syntax over the same mechanism: methods live on `Class.prototype`, shared by every instance.

```js
class Repo {
  constructor(db) { this.db = db; }       // own property, per instance
  find(id) { return this.db.get(id); }     // on Repo.prototype, shared
}
const r = new Repo(db);
Object.getPrototypeOf(r) === Repo.prototype;  // true
Object.hasOwn(r, 'find');                      // false
```

**Why it matters on the backend:** prototype pollution (Part 9). If attacker-controlled JSON can set `__proto__.isAdmin = true` through an unsafe deep merge, every object that inherits from `Object.prototype` now has `isAdmin`. Defences: `Object.create(null)` for dictionaries, `Map` for user-keyed data, schema validation, and rejecting `__proto__`, `constructor`, `prototype` keys.

### Q22 \[I\] How is `this` decided?

By how the function is *called*, not where it is defined (except arrow functions):

| Call form | `this` |
| --- | --- |
| `obj.method()` | `obj` |
| `fn()` in strict mode / ESM / class body | `undefined` |
| `fn()` in sloppy CommonJS | `globalThis` |
| `new Fn()` | the new object |
| `fn.call(x)` / `fn.bind(x)` | `x` |
| arrow function | `this` of the enclosing scope, fixed |

**The backend bug everyone hits:**

```js
class UserService {
  constructor(repo) { this.repo = repo; }
  async get(req, res) { res.json(await this.repo.find(req.params.id)); }
}
const svc = new UserService(repo);
app.get('/users/:id', svc.get);  // TypeError: Cannot read properties of undefined (reading 'repo')
```

Passing `svc.get` detaches it from `svc`. Fix with `svc.get.bind(svc)`, a wrapper `(req, res) => svc.get(req, res)`, or a class field arrow `get = async (req, res) => { ... }` (one function per instance, a fine trade-off for a few singletons).

**Module-level `this`:** in CommonJS it is `module.exports`; in ESM it is `undefined`.

### Q23 \[A\] What is an execution context, and how does it relate to the call stack?

Each function call creates an execution context holding its variable environment, lexical environment (scope chain) and `this` binding, and pushes it on the call stack. When the function returns, the context is popped. Closures survive because their scope lives on the heap, not in the popped frame.

The call stack is synchronous and finite. Deep recursion throws `RangeError: Maximum call stack size exceeded` (about 10,000 frames by default, depending on frame size). Async callbacks start on a fresh, empty stack, which is why a thrown error inside a `setTimeout` callback cannot be caught by a `try` around the `setTimeout` call (Part 2, Part 8).

### Q24 \[I\] Higher-order functions in production code

Functions that take or return functions: middleware, retry wrappers, decorators, `withTransaction(fn)`.

```ts
function withTiming<A extends unknown[], R>(name: string, fn: (...a: A) => Promise<R>) {
  return async (...args: A): Promise<R> => {
    const start = performance.now();
    try {
      return await fn(...args);  // `return await` keeps this frame in the stack trace and the finally correct
    } finally {
      metrics.histogram(name, performance.now() - start);
    }
  };
}
```

**Trap:** `return fn(...args)` without `await` inside `try/finally` would record the duration before the promise settles, and a rejection would skip this function's `catch`.

## JavaScript for backend: iterators, generators, collections, GC basics

### Q25 \[A\] Iterators, generators and async iterators: where do they matter in Node?

An iterator is any object with `next()` returning `{ value, done }`. A generator (`function*`) produces one lazily and pauses at each `yield`. An async generator (`async function*`) yields promises and is consumed with `for await`.

Node uses async iteration everywhere: readable streams, `readline`, `events.on()`, `fs.promises.opendir()`, paginated APIs.

```js
// Process millions of rows with constant memory
async function* paginate(client, pageSize = 1000) {
  let lastId = 0;
  while (true) {
    const { rows } = await client.query(
      'SELECT id, email FROM users WHERE id > $1 ORDER BY id LIMIT $2', [lastId, pageSize]);
    if (rows.length === 0) return;
    yield* rows;
    lastId = rows.at(-1).id;     // keyset pagination, not OFFSET
  }
}

for await (const user of paginate(client)) {
  await sendEmail(user);          // natural backpressure: next page waits
}
```

**Why it is good:** the consumer pulls, so the producer never runs ahead. That is backpressure for free (Part 5).

**Trap:** `break` out of `for await` calls the generator's `return()`, which runs its `finally` blocks. Put cleanup (release a DB client, close a file) in `finally` so early exit does not leak.

### Q26 \[I\] Map/Set vs plain objects/arrays

| Need | Use | Why |
| --- | --- | --- |
| User-supplied keys | `Map` | no prototype keys, no `__proto__` pollution |
| Non-string keys | `Map` | objects coerce keys to strings |
| Frequent add/delete | `Map` | optimised for it; `delete obj.x` can de-optimise objects |
| Insertion-ordered LRU | `Map` | iteration order is insertion order (Part 14) |
| Membership test | `Set` | O(1) vs `array.includes` O(n) |
| Fixed-shape records, JSON | object | serialises directly, fast property access |

### Q27 \[A\] WeakMap, WeakSet, WeakRef and FinalizationRegistry

A `WeakMap` holds keys weakly: if nothing else references the key object, both the entry and its value can be collected. Keys must be objects (or non-registered symbols). It is not iterable and has no `size`, because its contents depend on when GC runs.

```js
const meta = new WeakMap();           // per-request metadata without leaks
function track(req) { meta.set(req, { start: Date.now() }); }
// When req is gone, the entry is gone. A Map here would leak every request.
```

`WeakRef` and `FinalizationRegistry` exist, but GC timing is non-deterministic. **Never use a finalizer to release a resource** (a file handle, a DB connection). Use explicit `close()`, `try/finally`, or `using` with `Symbol.dispose` / `Symbol.asyncDispose` (explicit resource management: native in Node 24, down-levelled by TypeScript 5.2+).

### Q28 \[A\] Immutability: what does it buy you on a server?

Shared mutable state across concurrent requests is the source of most Node race conditions, because every `await` is a point where another request can run.

```js
const defaults = { retries: 3, headers: {} };
function buildOpts(user) {
  const opts = defaults;            // same object for every request
  opts.headers.authorization = user.token;  // request A's token leaks into request B
  return opts;
}
// Fix: return { ...defaults, headers: { ...defaults.headers, authorization: user.token } };
// or structuredClone(defaults) for deep copies
```

`Object.freeze` is shallow and silently ignores writes in sloppy mode (throws in strict mode / ESM). Freezing config at boot turns accidental mutation into a loud error.

### Q29 \[I\] Garbage collection fundamentals

V8 frees memory that is **unreachable** from roots (the stack, globals, active handles). It is generational:

- **Young generation** ("scavenge"): new objects; most die young; collected often and quickly by copying survivors.
- **Old generation** (mark-sweep-compact): objects that survived; collected less often, mostly concurrently and incrementally to keep pauses short.

What keeps memory alive in Node: module-level caches without limits, listeners never removed, timers never cleared, closures over large objects, unbounded queues, and `Buffer`s (their bytes live outside the V8 heap as **external memory**). Part 3 covers heap snapshots, `--max-old-space-size`, and container memory limits.

### Q30 \[A\] Symbols: what are they for in backend code?

A `Symbol` is a unique, non-string property key. `Symbol('id') !== Symbol('id')`, symbol keys never collide with string keys, and they are skipped by `JSON.stringify`, `Object.keys` and `for...in`.

Where they matter:

- **Well-known symbols** hook into language behaviour: `Symbol.iterator` and `Symbol.asyncIterator` (make an object usable with `for` / `for await`), `Symbol.dispose` and `Symbol.asyncDispose` (`using`), `Symbol.toPrimitive`, `Symbol.hasInstance`.
- **Node-specific hooks:** `util.inspect.custom` controls how an object prints in `console.log`, which is a clean way to hide secrets from logs.
- **Hidden-ish metadata** on objects you do not own, without clashing with their properties.
- **Cross-module identity:** `Symbol.for('app.requestId')` returns the same symbol from a global registry, so two copies of a package can agree on a key.

```js
class DbCredentials {
  #password;                                     // truly private (# field)
  constructor(user, password) { this.user = user; this.#password = password; }
  [Symbol.for('nodejs.util.inspect.custom')]() { // same as util.inspect.custom
    return `DbCredentials { user: '${this.user}', password: '[redacted]' }`;
  }
  toJSON() { return { user: this.user }; }       // never serialise the secret
}
console.log(new DbCredentials('app', 's3cret'));
// DbCredentials { user: 'app', password: '[redacted]' }
```

**Common mistake:** treating symbol keys as private. `Object.getOwnPropertySymbols(obj)` and `Reflect.ownKeys(obj)` list them. For real privacy use `#private` fields or a `WeakMap`.

**Follow-ups:** \[A\] Why is `Symbol.for` different from `Symbol()`? (Global registry vs always-unique.) \[E\] How would you make a paginated API client usable with `for await`? (Implement `[Symbol.asyncIterator]` as an async generator that fetches the next page lazily; see Q25.)

## Tricky & trap questions (Part 1)

Each trap: the snippet, the correct answer, the step-by-step reason, and why the tempting answer is wrong.

### T1 \[I\] "Node.js is single-threaded, so it can't use more than one CPU core."

**Correct:** JavaScript execution is single-threaded per isolate, but a Node process uses several threads (libuv pool, V8 GC and compiler threads), and you can use every core with `worker_threads`, `cluster`, or multiple processes behind a load balancer.

**Why the tempting answer is wrong:** it confuses the JS execution model with the process. A better phrasing: "one event loop and one JS thread per process or worker."

### T2 \[I\] What does this print?

```js
const id = 9007199254740993;
console.log(id, id === 9007199254740992);
```

**Answer:** `9007199254740992 true`.

**Why:** the literal exceeds 2^53 − 1 and rounds to the nearest representable double. Two different database ids now compare equal. Use strings or `BigInt` for 64-bit ids; `JSON.parse` has the same problem with large numbers in API responses.

### T3 \[I\] Does this protect the defaults?

```js
const DEFAULTS = Object.freeze({ timeout: 5000, retry: { attempts: 3 } });
DEFAULTS.retry.attempts = 10;
console.log(DEFAULTS.retry.attempts);
```

**Answer:** `10`. `Object.freeze` is shallow; the nested object is still mutable. Deep-freeze recursively or treat config as read-only by convention plus tests.

### T4 \[A\] What does this print in CommonJS vs ESM?

```js
function whoAmI() { return this; }
console.log(whoAmI() === globalThis);
```

**Answer:** `true` in a sloppy-mode CommonJS file; `false` (it is `undefined`) in an ES module or with `'use strict'`. Same code, different module system, different result. This is why migrating CJS to ESM can surface latent `this` bugs.

### T5 \[A\] Is this cache safe?

```js
const cache = {};
function get(key) { return cache[key] ?? (cache[key] = load(key)); }
get(req.query.key);
```

**Answer:** no, for three reasons:

1. `key = '__proto__'` or `'constructor'` returns inherited values (`cache.constructor` is `Object`), so `??` never loads.
2. It is unbounded: an attacker sending random keys grows memory until the process dies.
3. It caches forever with no TTL or invalidation.

**Fix:** a `Map` with a size bound and TTL (an LRU, Part 14), and validate `key` against an allow-list or schema.

### T6 \[A\] typeof traps

```js
typeof null          // 'object'
typeof []            // 'object'   -> use Array.isArray
typeof NaN           // 'number'   -> use Number.isNaN, not isNaN('abc') (true!)
typeof class {}      // 'function'
typeof undeclaredVar // 'undefined' (no ReferenceError)
typeof letInTDZ      // ReferenceError if declared later in the same block with let
```

### T7 \[S\] "We'll just use NODE\_ENV=staging for the staging cluster."

**Problem:** many libraries check `NODE_ENV === 'production'`. Staging then runs development code paths (verbose errors, no template caching, dev warnings) and is no longer a rehearsal of production. Set `NODE_ENV=production` in every deployed environment and name environments with a separate variable.

### T8 \[A\] Spot the bug in the semver range

```json
{ "dependencies": { "some-sdk": "^0.9.1" } }
```

The team expects `^` to allow 0.10.0 with new features. It does not: for 0.x versions, caret allows only patch updates (0.9.x). Conversely, `"*"` or `"latest"` in a manifest means any release, including a hijacked one, can enter the next fresh install without a lockfile.

### D1 \[I\] Debugging: the counter that is always wrong

```js
// Broken
let total = 0;
app.post('/add', async (req, res) => {
  const current = total;
  await db.insert(req.body);   // yields to other requests
  total = current + 1;
  res.json({ total });
});
```

**Symptom:** under load, `total` is lower than the number of inserts.

**Root cause:** a read-modify-write split by `await`. Two requests read the same `current`, both write `current + 1`: a lost update. Single-threaded does not mean free of race conditions.

**Fix:**

```js
app.post('/add', async (req, res) => {
  await db.insert(req.body);
  total += 1;                  // read and write in one synchronous step
  res.json({ total });
});
```

**Production fix:** in-process counters are per process and lost on restart, so with 4 replicas each has its own `total`. Use the database (`SELECT count(*)`, or `UPDATE counters SET n = n + 1 RETURNING n`) or Redis `INCR` for anything shared.

**Test:** fire 100 concurrent requests with `Promise.all` and assert the final count is 100.

### D2 \[A\] Debugging: a config value that is never applied

```js
// Broken
const retries = process.env.RETRIES || 3;
for (let i = 0; i < retries + 1; i++) { /* ... */ }
```

**Symptom:** with `RETRIES=2` the loop runs 21 times instead of 3. With `RETRIES=` (set but empty) it silently uses 3 and nobody notices the misconfiguration.

**Root cause:** env values are strings. `'2' + 1` is the string `'21'`, and the comparison `i < '21'` coerces it to the number 21. An empty string is falsy, so `'' || 3` hides the bad value instead of failing.

**Fix:** parse once with validation (`z.coerce.number().int().min(0)`), as in Q12, and fail at boot on bad values.

### D3 \[S\] Debugging: memory grows by about 1 MB per thousand requests

```js
const seen = new Map();
app.use((req, res, next) => {
  seen.set(req.headers['x-request-id'] ?? crypto.randomUUID(), { url: req.url, at: Date.now() });
  next();
});
```

**Root cause:** an unbounded module-level `Map`. Every request adds an entry; nothing removes it. In Q27 terms, the map is a GC root via the module scope.

**Fix options:** bound it (LRU with max size and TTL), delete the entry on `res.on('finish')`, or, if the goal is per-request context, use `AsyncLocalStorage` (Part 2), which ends with the request. Confirm with two heap snapshots taken a few thousand requests apart (Part 3).

# Part 2 — Event Loop & Asynchronous Programming

Question numbers restart here. A reference such as "Q9" or "T2" inside Part 2 points to Part 2's own questions.

## The event loop in one picture

The loop visits five phases in a fixed order, and after every single callback in any phase it empties the nextTick queue and then the promise microtask queue.

&#91;embedded content: Event loop · 5 phases and the microtask checkpoint\]

If you remember one thing for interviews: phases decide which *macrotask* runs next; the checkpoint decides that promise work always jumps the line.

## Call stack, event loop, macrotasks and microtasks

### Q1 \[I\] Explain the event loop to me.

**Say this first:** JavaScript runs one piece of code at a time on the call stack. When the stack is empty, the event loop picks the next ready callback (a timer that expired, a socket that has data, an `setImmediate`) and runs it. After **every** callback, Node drains two high-priority queues: the `process.nextTick` queue, then the promise microtask queue. Only then does the loop move on.

**The four things to name:**

| Piece | Owned by | What goes in it |
| --- | --- | --- |
| Call stack | V8 | the function currently running |
| nextTick queue | Node | `process.nextTick` callbacks |
| Microtask queue | V8 | promise reactions (`.then`, `await` continuations), `queueMicrotask` |
| Phase queues (macrotasks) | libuv | timers, I/O callbacks, `setImmediate`, close callbacks |

**Key rule:** a callback always runs to completion. Nothing interrupts synchronous JS: no timer, no I/O, no signal handler. That is why a 2-second loop delays every other request by 2 seconds.

### Q2 \[I\] What is the difference between a macrotask and a microtask?

- A **macrotask** (task) is one callback scheduled by libuv: one timer, one I/O completion, one `setImmediate`. The loop runs them phase by phase.
- A **microtask** is a promise job or a `queueMicrotask` callback. Microtasks run as soon as the current callback finishes, before the next macrotask, and the queue is drained **completely**, including microtasks added while draining.

```js
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('promise'));
console.log('sync');
// sync, promise, timeout
```

**Common mistake:** saying "microtasks run between event loop phases." Since Node 11 they run after **each** callback, not once per phase. Node 10 and earlier drained them only between phases, which is why older blog posts show different output for nested timers.

### Q3 \[A\] Browser event loop vs Node event loop

|  | Browser | Node.js |
| --- | --- | --- |
| Spec | HTML Living Standard | libuv implementation + Node rules |
| Task sources | one task per turn from several queues, chosen by the browser | fixed phases: timers, pending, poll, check, close |
| Extra queue | none | `process.nextTick` (runs before promise microtasks) |
| Rendering | between tasks (requestAnimationFrame, paint) | none |
| `setImmediate` | not standard | check phase |
| Microtasks | after each task | after each callback (Node 11+) |

**Interview point:** code that relies on exact ordering between timers and I/O callbacks is not portable between the two, and sometimes not between Node versions. Write code that depends on *data dependencies* (await what you need), not on scheduling order.

## Event loop phases in detail

### Q4 \[A\] Name the phases and what runs in each.

| # | Phase | Runs | Notes |
| --- | --- | --- | --- |
| 1 | **timers** | `setTimeout` / `setInterval` callbacks whose threshold has passed | a delay is a minimum, never a guarantee; `0` is clamped to 1 ms |
| 2 | **pending callbacks** | some system-level callbacks deferred from the previous iteration | e.g. certain TCP errors such as `ECONNREFUSED` on some systems |
| – | idle, prepare | internal to libuv | not visible to you |
| 3 | **poll** | I/O callbacks: socket data, completed fs operations, incoming connections | the loop **blocks here** waiting for I/O when nothing else is scheduled |
| 4 | **check** | `setImmediate` callbacks | always right after poll |
| 5 | **close callbacks** | `'close'` events, e.g. `socket.on('close')` after `destroy()` |  |

Between every callback in every phase: drain `process.nextTick`, then drain promise microtasks.

### Q5 \[A\] How long does the poll phase wait?

libuv computes a timeout before polling:

- **0** (do not block) if there are pending `setImmediate` callbacks, or the loop is stopping.
- **until the nearest timer** if timers are scheduled.
- **indefinitely** if there are active handles (a listening server) and nothing else to do.

The loop exits when there are no active, referenced handles or requests. That is why a script with only `setTimeout(fn, 1000).unref()` exits immediately: `unref()` tells the loop "do not stay alive for me."

### Q6 \[S\] What keeps a Node process alive, and why does it sometimes refuse to exit?

Any **referenced** handle: a listening server, an open socket (including keep-alive connections in an HTTP agent), a `setInterval`, a child process, a file watcher, an open database pool. Graceful shutdown (Part 7, Part 8) is mostly about closing these in order.

```js
// Find what is keeping the process alive (diagnostics, not production logic)
console.log(process.getActiveResourcesInfo());
// [ 'TCPServerWrap', 'TCPSocketWrap', 'Timeout' ]
```

**Trap:** calling `process.exit()` to "fix" a hanging shutdown. It kills in-flight requests and skips flushing logs. Find the handle and close it, or `unref()` timers that should not block exit (metrics flush intervals).

### Q7 \[E\] Does the order of timers vs I/O depend on the Node version?

Yes, in edge cases. The documented change is Node 11, which moved microtask draining from "between phases" to "after every callback" to match browsers. Beyond that, the docs split ordering into two kinds. **Guaranteed:** nextTick before promise microtasks (in CommonJS), and `setImmediate` before `setTimeout(0)` when both are scheduled from an I/O callback. **Not guaranteed:** `setTimeout(0)` vs `setImmediate` from the main module, or the exact order of timers relative to I/O completions; that can vary with machine load, platform and libuv version. The senior answer: never build correctness on unguaranteed ordering, and if a test depends on it, the test is wrong.

### Q7a \[A\] Walk me through what happens when you call fs.readFile.

**Say this first:** the call returns immediately. The file work runs on a libuv pool thread using ordinary blocking system calls, and when it finishes the event loop runs your callback in the poll phase.

&#91;embedded content: fs.readFile round trip · 6 steps across 4 lanes\]

**Step by step:** (1) `fs.readFile` validates arguments and the C++ binding submits a request to libuv; (2) control returns to your code at once, so the main thread keeps serving other requests; (3) a pool thread performs the blocking `open` / `fstat` / `read` / `close` calls (Node reads in chunks, so a large file takes several round trips); (4) the pool thread posts a completion and wakes the loop; (5) in the poll phase the loop runs your callback with `(err, data)`; (6) nextTick and microtasks drain before the next callback. With `fs/promises` the only difference is step 5: the promise resolves and your `await` resumes as a microtask.

**Contrast with a socket read:** network I/O skips the pool entirely. The socket is non-blocking, libuv registers it with epoll / kqueue / IOCP, and the kernel tells the loop when data is ready. That is why 10,000 idle connections cost almost nothing, while 10,000 concurrent file reads queue behind 4 pool threads.

**Follow-ups:** \[A\] Which other APIs use the pool? (`dns.lookup`, zlib, `crypto.pbkdf2`, `scrypt`, `randomBytes` and most `fs` calls.) \[S\] Why can slow DNS make file reads slow? (`dns.lookup` and `fs` share the same 4 threads; a slow resolver occupies them. Part 3 covers sizing the pool and `dns.resolve` as the alternative.)

## nextTick, queueMicrotask, setImmediate, setTimeout

### Q8 \[I\] Order these four and explain why.

```js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('sync');
```

**Output:**

```text
sync
nextTick
promise
timeout      <- these two may swap
immediate    <-
```

**Step by step:**

1. The main module runs synchronously: schedules a timer, an immediate, a promise job, a tick; prints `sync`.
2. Main script finishes. Node drains the nextTick queue (`nextTick`), then the microtask queue (`promise`).
3. The loop starts. Timers phase: has 1 ms elapsed since the timer was scheduled? Usually yes, so `timeout` prints. If the process started fast enough that less than 1 ms passed, the timer is not due yet.
4. Poll has nothing; check phase runs `immediate`.

**Deterministic part:** `sync`, `nextTick`, `promise` always come first in that order. **Non-deterministic part:** `timeout` vs `immediate` from the main module depends on process timing.

**\[E\] The ESM twist:** the output above is for a CommonJS file. Run the same code as an ES module (`.mjs` or `"type": "module"`) and you get `sync, promise, nextTick`. ESM module evaluation itself runs inside a promise job, so the microtask queue is drained before Node gets back to the nextTick queue. This is one of the best "do you really know it" follow-ups, and a reason not to rely on nextTick-before-promise ordering in application code.

### Q9 \[A\] When is setImmediate guaranteed to run before setTimeout(0)?

Inside an I/O callback:

```js
import { readFile } from 'node:fs';
readFile(import.meta.filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// immediate, timeout  (always)
```

We are in the poll phase. The next phase is check, so the immediate runs before the loop wraps around to timers.

### Q10 \[A\] process.nextTick vs queueMicrotask: which and when?

|  | `process.nextTick` | `queueMicrotask` / promise `.then` |
| --- | --- | --- |
| Queue | Node's own nextTick queue | V8 microtask queue |
| Runs | before promise microtasks | after the nextTick queue is empty |
| Portable | Node only | browsers, Deno, Bun |
| Errors | thrown synchronously into the loop (uncaughtException) | same for `queueMicrotask`; a rejection for `.then` |

**When nextTick is right:** making an API consistently asynchronous, e.g. emitting an event after the constructor returns so callers can attach listeners first. Node core does exactly this.

```js
class Connection extends EventEmitter {
  constructor() {
    super();
    process.nextTick(() => this.emit('ready')); // listeners attached after `new` still get it
  }
}
const c = new Connection();
c.on('ready', () => console.log('ready'));
```

**Otherwise prefer `queueMicrotask`** or plain promises; the Node docs themselves recommend it for most cases.

### Q11 \[A\] Why is setTimeout(fn, 0) never really 0?

- Delay below 1 ms is clamped to 1 ms.
- The callback runs in the timers phase of a **later** iteration, after the current callback, all its microtasks, and anything blocking the loop.
- Under load, timers drift: a 100 ms timer can fire at 400 ms if the loop is busy. Never use timers as a clock; compare `performance.now()` or `process.hrtime.bigint()` timestamps instead.

`setInterval` does not compensate for drift and can overlap with slow async work. For periodic async jobs use a self-rescheduling loop:

```js
import { setTimeout as sleep } from 'node:timers/promises';

async function every(ms, task, signal) {
  while (!signal.aborted) {
    const started = performance.now();
    try { await task(); } catch (err) { log.error({ err }, 'periodic task failed'); }
    const wait = Math.max(0, ms - (performance.now() - started));
    await sleep(wait, undefined, { signal }).catch(() => {}); // resolves early on abort
  }
}
```

## Promises and async/await: execution order

### Q12 \[I\] What does await actually do?

`await x` converts `x` to a promise, suspends the async function, and returns control to the caller. When the promise settles, the rest of the function is scheduled as a **microtask**. The code before the first `await` runs synchronously.

```js
async function f() {
  console.log('f start');   // synchronous, runs when f() is called
  await null;               // suspends even for a non-promise
  console.log('f resumed'); // microtask
}
console.log('before');
f();
console.log('after');
// before, f start, after, f resumed
```

**Common mistake:** "an async function runs in the background." It runs on the same thread; it only gives up the thread at each `await`.

### Q13 \[A\] What does an async function return, and what does `return await` change?

An async function always returns a promise. Returning a value resolves it; throwing rejects it; returning a promise adopts that promise's state.

```js
async function a() { return fetchUser(); }          // fine, but...
async function b() { return await fetchUser(); }    // differs in two places
async function c() {
  try { return fetchUser(); }        // rejection is NOT caught here
  catch { return null; }
}
async function d() {
  try { return await fetchUser(); }  // rejection IS caught here
  catch { return null; }
}
```

- Inside `try/catch` or `try/finally`, `return await` is required for the catch or finally to see the settled result.
- `return await` also keeps the async frame in V8's async stack traces, which makes production errors easier to trace.
- Outside `try`, the performance difference is a tick or two and not worth arguing about (V8 7.2, Node 12, cut `await` on a native promise from 3 ticks to 1). Lint rule: `@typescript-eslint/return-await` with `in-try-catch`.

### Q14 \[A\] Thenables and the extra ticks

Resolving a promise with another promise (or any object with a `then` method) takes extra microtask ticks, because the engine must call `then` on it as a separate job.

```js
const p1 = new Promise(r => r(Promise.resolve()));
const p2 = Promise.resolve();
p1.then(() => console.log('p1'));
p2.then(() => console.log('p2'));
// p2, p1   (p1 needs two extra ticks to adopt the inner promise)
```

**Security note:** any object with a `then` property is treated as a thenable. Returning attacker-shaped data from an async function, e.g. a parsed JSON object with a `then` key, can hang or hijack the resolution. Validate shapes before resolving with external data.

### Q15 \[I\] The executor runs synchronously

```js
console.log(1);
new Promise(resolve => { console.log(2); resolve(); console.log(3); })
  .then(() => console.log(4));
console.log(5);
// 1 2 3 5 4
```

The executor runs immediately inside the constructor. `resolve()` does not stop the executor; it only fixes the promise's state. `.then` callbacks always run asynchronously, even on an already-resolved promise.

### Q15a \[I\] Error-first callbacks, and converting them to promises

Before promises, Node's convention was the **error-first callback**: the last argument is a function called once as `cb(err)` on failure or `cb(null, result)` on success.

```js
import { readFile } from 'node:fs';
readFile('config.json', 'utf8', (err, text) => {
  if (err) return handleError(err);   // `return` so success code never runs after an error
  use(JSON.parse(text));              // a throw here is NOT passed to cb: it is uncaught
});
```

**Rules interviewers check:** call the callback exactly once; always asynchronously (never sometimes sync, sometimes async, the "Zalgo" problem, which `process.nextTick` fixes); never throw from inside an async callback API, pass the error instead.

**Converting:** use the promise APIs (`node:fs/promises`, `node:timers/promises`, `node:stream/promises`, `node:dns/promises`) or `util.promisify` for callback-only libraries.

```js
import { promisify } from 'node:util';
import { execFile } from 'node:child_process';
const execFileAsync = promisify(execFile);
const { stdout } = await execFileAsync('git', ['rev-parse', 'HEAD']);
```

**Trap:** promisifying a method loses `this`; use `promisify(obj.method).bind(obj)`. A function whose callback has extra arguments or no error argument needs a hand-written wrapper, or `util.promisify.custom` if you own the function.

**Follow-ups:** \[A\] What happens if a callback is called twice? (Double responses, "headers already sent" errors, double-counted metrics; guard with a `called` flag in library code.) \[A\] How do you go the other way, promise to callback? (`util.callbackify`, mainly for legacy plugin APIs.)

## Combinators, error propagation, unhandled rejections

### Q16 \[I\] Promise.all vs allSettled vs race vs any

| Combinator | Resolves when | Rejects when | Use for |
| --- | --- | --- | --- |
| `all` | every input fulfils (array of values) | **first** rejection | parallel steps that all must succeed |
| `allSettled` | every input settles (array of `{status, value/reason}`) | never | batch jobs where partial failure is fine |
| `race` | first input settles, either way | first settles as rejected | timeouts (with care, see the timeouts section) |
| `any` | first input fulfils | all reject (`AggregateError`) | redundant mirrors, hedged requests |

**Trap:** `Promise.all` rejecting does **not** cancel the other operations. They keep running, consume connections, and their later rejections are handled (all attached a handler) but their side effects still happen. To stop them, pass an `AbortSignal` (see the cancellation section).

```js
const controller = new AbortController();
try {
  const [user, orders] = await Promise.all([
    getUser(id, { signal: controller.signal }),
    getOrders(id, { signal: controller.signal }),
  ]);
} catch (err) {
  controller.abort(err); // stop the sibling that is still running
  throw err;
}
```

### Q17 \[I\] How do errors propagate through a promise chain?

A rejection skips every `.then` fulfilment handler until it reaches a `.catch` (or a `.then(_, onRejected)`). A `.catch` that returns normally **recovers** the chain: the next `.then` runs with its return value.

```js
Promise.reject(new Error('boom'))
  .then(() => console.log('skipped'))
  .catch(err => { console.log('caught', err.message); return 'fallback'; })
  .then(v => console.log('continues with', v));
// caught boom, continues with fallback
```

**Mistake:** `.catch(err => console.error(err))` in a service function. It logs and resolves with `undefined`, so the caller thinks it succeeded and uses `undefined`. Either rethrow, or return an explicit result type.

### Q18 \[A\] What happens on an unhandled rejection?

Since **Node 15**, the default `--unhandled-rejections=throw` turns an unhandled rejection into an uncaught exception: the process emits `'unhandledRejection'`; if nothing handles that event, it crashes with exit code 1. Before Node 15 it only printed a warning.

A rejection is "unhandled" if no handler is attached by the time the microtask queue drains after it rejects.

```js
const p = Promise.reject(new Error('late'));
setTimeout(() => p.catch(() => {}), 0);
// Crashes on Node 15+: no handler existed when microtasks drained.
```

**Production pattern:**

```js
process.on('unhandledRejection', (reason) => {
  logger.fatal({ err: reason }, 'unhandled rejection');
  throw reason; // let it become uncaughtException -> crash -> restart
});
process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaught exception');
  // flush logs, stop accepting traffic, then exit; state may be corrupt
  shutdown().finally(() => process.exit(1));
});
```

**Senior point:** catching `uncaughtException` and continuing is unsafe. A callback threw halfway through, so locks, counters or transactions may be in an unknown state. Log, drain, exit, and let the orchestrator restart the process (Part 8).

### Q19 \[A\] Floating promises

A promise you neither `await` nor return nor `.catch` is "floating." Its errors become unhandled rejections, and its work outlives the request.

```js
app.post('/signup', async (req, res) => {
  const user = await createUser(req.body);
  sendWelcomeEmail(user);       // floating: crash on failure, no retry, lost on restart
  res.status(201).json(user);
});
```

**Fix:** if it must not block the response, enqueue it to a durable job queue (Part 10). If fire-and-forget is acceptable, make it explicit: `void sendWelcomeEmail(user).catch(err => log.warn({ err }))`. Enforce with `@typescript-eslint/no-floating-promises`.

## Concurrency: sequential, parallel, limits, races, request context

### Q20 \[I\] Concurrency vs parallelism in Node

**Concurrency** is many tasks in progress at once (interleaved at `await` points) on one thread. **Parallelism** is many tasks executing at the same instant on different cores. Node's main thread gives you concurrency; worker threads, child processes and the libuv pool give you parallelism.

### Q21 \[I\] Sequential vs parallel awaits

```js
// Sequential: 300 ms if each call is 100 ms. Only correct if each step needs the previous result.
for (const id of ids) results.push(await fetchItem(id));

// Parallel: about 100 ms, but unbounded. 10,000 ids = 10,000 sockets at once.
const results2 = await Promise.all(ids.map(fetchItem));

// Bounded: at most 10 in flight.
const results3 = await mapWithLimit(ids, 10, fetchItem);
```

**Common mistake in reviews:** `ids.forEach(async id => await save(id))`. `forEach` ignores the returned promises, so nothing waits and errors are unhandled. Use `for...of` (sequential) or `Promise.all` with `map` (parallel).

### Q22 \[A\] Implement a concurrency limit

```ts
export async function mapWithLimit<T, R>(
  items: readonly T[], limit: number, fn: (item: T, i: number) => Promise<R>,
): Promise<R[]> {
  if (!Number.isInteger(limit) || limit < 1) throw new RangeError('limit must be >= 1');
  const results = new Array<R>(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;                 // safe: no await between read and increment
      results[i] = await fn(items[i], i); // keep input order
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

**Why it works:** N worker loops pull from a shared index. Because JS is single-threaded, `next++` cannot interleave with another worker. Results keep input order.

**The flaw an interviewer will probe:** on the first error the returned promise rejects (like `Promise.all`), but the other workers keep pulling and processing items. Add a `stopped` flag checked in the `while`, or an `AbortSignal` passed to `fn`. Part 14 builds that version with `allSettled` semantics and tests. In production, `p-limit` or `p-map` do the same job.

**Why limits matter:** an unbounded fan-out can exhaust the DB pool, hit downstream rate limits, run out of file descriptors (`EMFILE`), or blow memory with buffered responses.

### Q23 \[A\] Race conditions on a single thread

Any read-check-write sequence with an `await` in the middle can interleave with another request.

```js
// Broken: two concurrent withdrawals both see balance 100 and both succeed
async function withdraw(accountId, amount) {
  const { balance } = await db.getAccount(accountId);
  if (balance < amount) throw new Error('Insufficient funds');
  await db.setBalance(accountId, balance - amount);
}
```

**Fixes, from weakest to strongest:**

1. An in-process mutex per key: only protects one process; useless with 2+ replicas.
2. An atomic conditional write in the database (correct across replicas):

```sql
UPDATE accounts SET balance = balance - $2
WHERE id = $1 AND balance >= $2
RETURNING balance;   -- 0 rows = insufficient funds
```

3. `SELECT ... FOR UPDATE` inside a transaction, or optimistic concurrency with a version column (Part 10).

**Senior signal:** move the invariant to the place that serialises writes (the database row), not to application memory.

### Q24 \[A\] AsyncLocalStorage: per-request context without passing it everywhere

`AsyncLocalStorage` (from `node:async_hooks`) stores a value that follows the async call chain: every callback, promise continuation and timer created inside `run()` sees the same store.

```js
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';

export const requestContext = new AsyncLocalStorage();

app.use((req, res, next) => {
  const ctx = { requestId: req.get('x-request-id') ?? randomUUID(), userId: req.user?.id };
  requestContext.run(ctx, next);
});

// anywhere deeper, no parameter threading
export function log(msg, extra) {
  const ctx = requestContext.getStore();
  logger.info({ ...extra, requestId: ctx?.requestId }, msg);
}
```

Used by OpenTelemetry, Pino helpers and most tracing libraries. Since Node 24 it is implemented on V8's `AsyncContextFrame` and is cheaper than the older `async_hooks`-based version.

**Pitfalls:** context is lost across some callback-based libraries that pool callbacks (older DB drivers, custom queues); keep stores small (they live as long as any async work started in them); never use it for authorisation decisions without also validating at the boundary.

## Cancellation and timeouts

### Q25 \[A\] How do you cancel async work in Node?

Promises cannot be cancelled; the **operation** behind them can, if it accepts an `AbortSignal`. `fetch`, `fs.promises.readFile`, `stream.pipeline`, `events.once`, `timers/promises`, `child_process` and most modern libraries do.

```js
const controller = new AbortController();
const { signal } = controller;

const res = fetch(url, { signal });
controller.abort(new Error('client went away'));  // res rejects with that reason

// Ready-made signals
AbortSignal.timeout(2000);                 // aborts with a TimeoutError after 2 s
AbortSignal.any([clientGone.signal, AbortSignal.timeout(2000)]); // whichever first (Node 20.3+)
// clientGone: an AbortController you abort on res.on('close') when the response was not finished (Part 6)
```

**Making your own function cancellable:**

```js
async function processBatch(items, { signal } = {}) {
  signal?.throwIfAborted();
  for (const item of items) {
    signal?.throwIfAborted();          // check between units of work
    await handle(item, { signal });    // pass it down
  }
}
```

**Key insight:** cancellation is cooperative. CPU-bound code that never checks the signal cannot be cancelled; that is a reason to chunk it or move it to a worker you can terminate.

### Q26 \[A\] What is wrong with this timeout helper?

```js
// Broken
function withTimeout(promise, ms) {
  return Promise.race([
    promise,
    new Promise((_, reject) => setTimeout(() => reject(new Error('Timeout')), ms)),
  ]);
}
```

Three problems:

1. **The timer is never cleared.** On success it still fires later and keeps the process alive for `ms` (and at scale, thousands of pending timers).
2. **The underlying work continues.** The race rejects, but the HTTP request or query keeps running and holding a socket or pool connection.
3. **The error is anonymous.** Callers cannot distinguish a timeout from a real failure.

```js
export class TimeoutError extends Error { name = 'TimeoutError'; }

export async function withTimeout(task, ms, { signal: outer } = {}) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(new TimeoutError(`timed out after ${ms} ms`)), ms);
  const signal = outer ? AbortSignal.any([outer, controller.signal]) : controller.signal;
  try {
    return await task(signal);         // task must honour the signal
  } finally {
    clearTimeout(timer);
  }
}

// usage
const user = await withTimeout(sig => fetch(`${API}/users/${id}`, { signal: sig }).then(r => r.json()), 2000);
```

**Production nuance:** pick timeouts from latency data (p99 of the dependency plus margin), keep a total budget per request (a deadline propagated down, not fresh timeouts at every hop), and remember a timeout does not mean the remote side did not act: a timed-out payment may have succeeded. That is why writes need idempotency keys (Part 15).

### Q26a \[A\] Retries: what goes wrong with a naive retry loop?

```js
// Broken
async function getWithRetry(url) {
  for (let i = 0; i < 5; i++) {
    try { return await fetch(url).then(r => r.json()); }
    catch { await sleep(1000); }
  }
}
```

Five problems:

1. **Retries everything,** including 400s and validation errors that will never succeed. Retry only transient failures: network errors, timeouts, 429, 502, 503, 504.
2. **Treats HTTP errors as success:** `fetch` only rejects on network failure, so a 503 is "returned" as JSON (or a parse error). Check `res.ok`.
3. **Fixed delay, no jitter.** Every client that failed at the same moment retries at the same moment, hitting the recovering service in synchronised waves (thundering herd).
4. **Silent exhaustion:** after 5 failures it returns `undefined` instead of throwing the last error.
5. **No budget or cancellation:** 5 attempts with no per-attempt timeout can hang for minutes; a caller that gave up cannot stop it.

```js
import { setTimeout as sleep } from 'node:timers/promises';

const RETRYABLE = new Set([429, 502, 503, 504]);

export async function fetchJsonWithRetry(url, { attempts = 4, baseMs = 200, maxMs = 5_000, signal } = {}) {
  let lastErr;
  for (let attempt = 0; attempt < attempts; attempt++) {
    try {
      const perAttempt = AbortSignal.timeout(2_000);              // each attempt gets its own timeout
      const res = await fetch(url, { signal: signal ? AbortSignal.any([signal, perAttempt]) : perAttempt });
      if (res.ok) return await res.json();
      lastErr = Object.assign(new Error(`HTTP ${res.status}`), { status: res.status });
      if (!RETRYABLE.has(res.status)) throw lastErr;            // permanent: stop now
    } catch (err) {
      if (signal?.aborted || (err.status && !RETRYABLE.has(err.status))) throw err;
      lastErr = err;                                             // network error or timeout
    }
    if (attempt < attempts - 1) {
      const cap = Math.min(maxMs, baseMs * 2 ** attempt);
      await sleep(Math.random() * cap, undefined, { signal });  // exponential backoff, full jitter
    }
  }
  throw lastErr;
}
```

**Senior points:**

- **Only retry idempotent operations,** or send an idempotency key so the server can de-duplicate a retried write (Part 15).
- **Retries multiply load.** Three layers each retrying 3 times turn one user request into up to 27 calls on the bottom service during an outage. Retry at one layer, use a retry budget (for example, retries may add at most 10% extra traffic), and pair retries with a circuit breaker (Part 8).
- **Honour `Retry-After`** on 429 and 503 when present.
- Part 14 builds this as a tested, generic utility.

## Blocking, starvation and measuring the loop

### Q27 \[I\] What blocks the event loop?

Anything synchronous that takes long: CPU loops, `JSON.parse`/`stringify` of multi-megabyte payloads, synchronous crypto (`crypto.pbkdf2Sync`, `scryptSync`), `zlib.*Sync`, `fs.*Sync` calls after startup, catastrophic regex backtracking (ReDoS, Part 9), sorting huge arrays, and synchronous template rendering of large pages.

**Rule of thumb:** keep any single callback under about 10 ms on a latency-sensitive server. `fs.readFileSync` at boot is fine; inside a request handler it is not.

### Q28 \[A\] What is microtask starvation, and how is it different from nextTick starvation?

The loop cannot advance while the microtask or nextTick queue is non-empty. Code that keeps adding to them never lets I/O run.

```js
// Starves the loop: the server stops responding, timers never fire
function spin() { process.nextTick(spin); }      // same with Promise.resolve().then(spin)
spin();
setTimeout(() => console.log('never'), 0);
```

`setImmediate(spin)` does **not** starve the loop: each immediate is queued for the next check phase, so timers and I/O run in between. That is the standard way to yield during long work:

```js
import { setImmediate as yieldToLoop } from 'node:timers/promises';

async function hashAll(rows) {
  for (let i = 0; i < rows.length; i++) {
    rows[i].digest = cheapHash(rows[i]);
    if (i % 1000 === 0) await yieldToLoop();   // let I/O and timers through
  }
}
```

Chunking keeps the server responsive but does not make the work faster, and it adds latency to this job. For heavy CPU, use worker threads (Part 7).

### Q29 \[S\] How do you measure event loop health in production?

**Event loop delay** (lag): how late a timer fires compared to when it should. **Event loop utilization (ELU)**: the fraction of time the loop was busy running callbacks rather than idle in poll.

```js
import { monitorEventLoopDelay, performance } from 'node:perf_hooks';

const delay = monitorEventLoopDelay({ resolution: 20 });
delay.enable();
let previous = performance.eventLoopUtilization();

setInterval(() => {
  const current = performance.eventLoopUtilization();          // read once
  const elu = performance.eventLoopUtilization(current, previous); // delta between the two readings
  previous = current;
  metrics.gauge('nodejs_eventloop_delay_p99_ms', delay.percentile(99) / 1e6); // ns -> ms
  metrics.gauge('nodejs_eventloop_utilization', elu.utilization);
  delay.reset();
}, 10_000).unref();
```

Reading the counter once and diffing against the previous reading keeps every window exactly contiguous; calling it twice per tick leaves small gaps that skew short intervals.

**How to read them:**

| Signal | Meaning | Typical action |
| --- | --- | --- |
| ELU high (above 0.8) and delay high | CPU-saturated loop | profile (Part 11), offload CPU, scale out |
| ELU low, latency high | waiting on downstream (DB, APIs) or pool exhaustion | check pools, timeouts, dependency latency |
| Delay spikes, ELU moderate | occasional long synchronous task or GC pause | find the long task with a CPU profile; check GC logs |

**Senior signal:** use ELU, not CPU percent, for autoscaling and load-shedding decisions. CPU percent includes GC and pool threads and can look fine while the JS thread is saturated. Shed load (return 503) when delay passes a threshold, rather than queueing requests that will time out anyway.

## Tricky & trap questions (Part 2)

Outputs assume a **CommonJS** file on Node 24 or 26 unless stated. Where ESM differs, it says so.

### T1 \[A\] Nested ticks and promises

```js
Promise.resolve().then(() => {
  console.log('p1');
  process.nextTick(() => console.log('tick inside p1'));
}).then(() => console.log('p2'));
process.nextTick(() => console.log('tick1'));
```

**Output:** `tick1, p1, p2, tick inside p1`.

**Why:** after the main script, the nextTick queue drains (`tick1`), then the microtask queue drains **completely**: `p1` runs and queues a tick and `p2`'s reaction; `p2` is a microtask so it runs before Node returns to the nextTick queue. Only then `tick inside p1`.

**Tempting wrong answer:** `tick1, p1, tick inside p1, p2`, which assumes nextTick preempts the microtask queue mid-drain. It does not; the check happens between queue drains.

### T2 \[A\] async/await ordering

```js
async function a() { console.log('a1'); await b(); console.log('a2'); }
async function b() { console.log('b'); }
console.log('start');
setTimeout(() => console.log('timeout'), 0);
a();
Promise.resolve().then(() => console.log('then'));
console.log('end');
```

**Output:** `start, a1, b, end, a2, then, timeout`.

**Step by step:** `a()` runs synchronously until its `await`; `b()` runs synchronously and returns a resolved promise; the continuation of `a` is queued as a microtask **before** the `.then` callback because `await` was reached first. `end` prints, microtasks run in FIFO order (`a2`, `then`), then the timers phase prints `timeout`.

### T3 \[A\] setTimeout inside setImmediate and vice versa

```js
setImmediate(() => {
  console.log('immediate');
  setTimeout(() => console.log('timeout from immediate'), 0);
  setImmediate(() => console.log('immediate from immediate'));
});
```

**Output:** `immediate` first, always. The other two can come in **either order**.

An immediate scheduled during the check phase goes to the **next** iteration's check phase, so the loop passes through timers first. Whether the 1 ms timer is due by then depends on how much wall time the rest of that iteration took. The correct interview answer is "`immediate` first; the remaining two are timing-dependent, so code must not rely on their order." Contrast Q9, where scheduling from an I/O callback makes the order deterministic.

### T4 \[I\] "try/catch catches errors from callbacks"

```js
try {
  setTimeout(() => { throw new Error('boom'); }, 0);
} catch (e) {
  console.log('caught');
}
```

**Output:** nothing is caught; the process crashes with an uncaught exception. The `try` block finished long before the callback ran on a new, empty stack. The same applies to errors in event listeners and in non-awaited promises. Wrap the inside of the callback, or use promise APIs with `await` inside the `try`.

### T5 \[A\] Does async make this non-blocking?

```js
app.get('/hash', async (req, res) => {
  const out = crypto.pbkdf2Sync(req.query.pw, salt, 600_000, 64, 'sha512');
  res.send(out.toString('hex'));
});
```

**No.** `async` only changes the return type. The synchronous call still blocks the loop for hundreds of milliseconds. Use `crypto.pbkdf2` (callback, runs on the libuv pool) or `util.promisify` it. And remember the pool has 4 threads by default: 50 concurrent hashes queue behind each other (Part 3).

### T6 \[S\] Promise.all with a shared connection

```js
const client = await pool.connect();
await client.query('BEGIN');
await Promise.all(items.map(i => client.query('INSERT ...', [i])));
await client.query('COMMIT');
```

**Question:** is this parallel? **Answer:** no, and it has a worse bug.

1. **Not parallel.** One PostgreSQL connection executes one query at a time; `pg` queues them. You get the complexity of `Promise.all` with sequential execution. On the first failure, the remaining queued inserts still run and each fails with "current transaction is aborted."
2. **It leaks the connection.** If any insert fails, `COMMIT` is never reached, nothing runs `ROLLBACK`, and `client.release()` is never called. A few failures exhaust the pool and every request then hangs waiting for a connection.

```js
const client = await pool.connect();
try {
  await client.query('BEGIN');
  await client.query(
    'INSERT INTO items (sku, qty) SELECT * FROM unnest($1::text[], $2::int[])',
    [items.map(i => i.sku), items.map(i => i.qty)],   // one round trip, one statement
  );
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK').catch(() => {});      // connection may already be broken
  throw err;
} finally {
  client.release();                                     // always return it to the pool
}
```

For very large batches use `COPY` via `pg-copy-streams`. Part 10 wraps this into a reusable `withTransaction(fn)` helper.

### T7 \[E\] Why can a tight loop of awaits still starve I/O?

```js
while (queue.length) await processInMemory(queue.shift()); // processInMemory is async but never does I/O
```

Each `await` of an already-resolved promise resumes in a **microtask**, and microtasks drain before the loop can reach the poll phase. If no step ever waits on real I/O or a timer, this behaves like a synchronous loop. Insert `await setImmediate()` from `node:timers/promises` periodically to yield to the event loop.

### C1 \[A\] EventEmitter is synchronous

```js
import { EventEmitter } from 'node:events';
const e = new EventEmitter();
e.on('x', () => console.log('listener 1'));
e.on('x', () => console.log('listener 2'));
console.log('before');

console.log('after');
```

**Output:** `before, listener 1, listener 2, after`. `emit` calls listeners synchronously in registration order. A slow listener blocks the emitter and everything after it. An async listener's rejection is not caught by `emit` unless the emitter was created with `captureRejections: true`. A thrown error from a listener propagates out of `emit`, and an `'error'` event with no listener throws.

### C2 \[A\] Error propagation through async functions

```js
async function inner() { throw new Error('inner'); }
async function outer() { inner(); return 'done'; }
outer().then(console.log).catch(e => console.log('caught', e.message));
```

**Output:** `done`, then the process **crashes** with an unhandled rejection from `inner` (Node 15+). `outer` never awaited `inner`, so its rejection has no handler. Fix: `await inner()`.

### C3 \[A\] Promise.race and the leftover timer

```js
const slow = new Promise(r => setTimeout(() => r('slow'), 5000));
const fast = Promise.resolve('fast');
console.log(await Promise.race([slow, fast]));   // ESM, top-level await
```

**Output:** `fast`, but the process keeps running for another 5 seconds. The 5-second timer is still referenced. In a server this is invisible; in a CLI or a test it causes the "Jest did not exit" / hanging test symptom.

### D1 \[S\] Debugging: the API that gets slower under load and then times out

```js
// Broken
app.post('/login', async (req, res) => {
  const user = await users.findByEmail(req.body.email);
  const ok = user && bcrypt.compareSync(req.body.password, user.hash); // cost 12, ~250 ms
  res.json({ ok: Boolean(ok) });
});
```

**Symptoms:** p50 fine at 1 rps, p99 several seconds at 20 rps; health checks fail and the orchestrator restarts healthy pods; event loop delay metric spikes.

**Root cause:** `compareSync` blocks the loop for about 250 ms per login. At 20 rps that is 5 seconds of CPU per second on one thread: queueing grows without bound.

**Fix:**

```js
const ok = user ? await bcrypt.compare(req.body.password, user.hash) : await fakeCompare();
```

- The async version runs on the libuv pool, so the loop stays responsive. Raise `UV_THREADPOOL_SIZE` (set before startup, max 1024) only with load-test evidence, and rate-limit login (Part 9).
- `fakeCompare()` hashes against a dummy hash when the user does not exist, so response time does not reveal which emails are registered (timing attack).
- **Test:** a load test asserting event loop delay p99 stays under a threshold at target throughput.

### D2 \[S\] Debugging: duplicate emails after a deploy

```js
// Broken
process.on('SIGTERM', () => process.exit(0));
queue.on('job', async (job) => {
  await sendEmail(job.data);
  await job.ack();
});
```

**Root cause:** on deploy, SIGTERM exits immediately. Jobs where `sendEmail` finished but `ack` did not are redelivered by the broker and sent again.

**Fix:**

```js
import { setTimeout as sleep } from 'node:timers/promises';

let shuttingDown = false;
const inFlight = new Set();

queue.on('job', (job) => {
  if (shuttingDown) return void job.nack({ requeue: true });
  const p = handle(job)
    .catch((err) => {                         // never let a job failure become an unhandled rejection
      logger.error({ err, jobId: job.id }, 'job failed');
      return job.nack({ requeue: true }).catch(() => {});
    })
    .finally(() => inFlight.delete(p));
  inFlight.add(p);
});

async function handle(job) {
  if (await sentLog.has(job.id)) return job.ack();         // idempotent consumer
  await sendEmail(job.data, { idempotencyKey: job.id });  // provider de-duplicates too
  await sentLog.add(job.id);
  await job.ack();
}

process.once('SIGTERM', async () => {
  shuttingDown = true;
  await queue.pause();                                     // stop taking new jobs
  await Promise.race([Promise.allSettled([...inFlight]), sleep(25_000)]); // under the 30 s grace period
  await queue.close();
  process.exit(0);
});
```

**Why both parts are needed:** graceful shutdown reduces duplicates; idempotency makes the remaining duplicates (crashes, network failures) harmless. At-least-once delivery means duplicates *will* happen (Part 10).

## Cheat sheet & interviewer follow-ups (Part 2)

**Ordering rules you can state with confidence:**

1. Synchronous code runs to completion first; nothing interrupts it.
2. After each callback: drain nextTick, then drain microtasks, repeat until both are empty (CommonJS; ESM main module flips the first pair).
3. Phases in order: timers, pending callbacks, poll, check (`setImmediate`), close.
4. Inside an I/O callback, `setImmediate` runs before `setTimeout(0)`. In the main module, their order is not guaranteed.
5. `await` resumes in a microtask; code before the first `await` is synchronous.
6. A promise executor runs synchronously; `.then` callbacks never do.
7. Unhandled rejections crash the process by default (Node 15+).
8. `Promise.all` rejection does not cancel siblings; `AbortSignal` does, if the operation supports it.
9. Recursive nextTick or microtasks starve I/O; recursive `setImmediate` does not.
10. Measure loop health with event loop delay and ELU, not CPU percent.

**Follow-ups interviewers chain from Part 2:**

| If you said... | Expect next | Where answered |
| --- | --- | --- |
| "Microtasks run after each callback" | What changed in Node 11, and why? | Q2 |
| "Use setImmediate to yield" | Why not nextTick? What does chunking cost? | Q28 |
| "Use Promise.all" | What about 10,000 items? Partial failure? Cancellation? | Q16, Q22, Q25 |
| "Wrap with a timeout" | What happens to the underlying request? The timer? | Q26 |
| "Just retry it" | Which errors? How many layers? What about writes? | Q26a |
| "AsyncLocalStorage for request IDs" | Performance cost? Where is context lost? | Q24 |
| "The event loop is blocked" | How would you find the blocking function in production? | Part 11 (CPU profiles) |

**Theory vs production:** theory is knowing the phase order. Production is knowing that ordering puzzles rarely matter in real code, and that what does matter is never blocking the loop, never leaving promises floating, always bounding concurrency, and always making async work cancellable and observable.

# Part 3 — Runtime Internals, Memory & GC

Question numbers restart here. This part is where interviewers separate people who use Node from people who can debug it at 3 a.m.

## Who does what: V8, Node, libuv, the OS

### Q1 \[A\] Draw the line between V8, Node.js, libuv and the operating system.

**Say this first:** V8 runs JavaScript and manages its heap. libuv runs the event loop and does asynchronous I/O. Node.js glues them together and provides the APIs. The operating system does the actual reading, writing, networking and scheduling of threads.

| Concern | Owner | Examples |
| --- | --- | --- |
| Parse, compile, execute JS | V8 | JIT tiers, inline caches, `eval` |
| JS heap, garbage collection | V8 | scavenger, mark-compact, `--max-old-space-size` |
| Promises, microtask queue | V8 (Node drains it) | `.then`, `await`, `queueMicrotask` |
| `process.nextTick` queue | Node | runs before microtasks in CJS |
| Event loop phases, timers | libuv | `setTimeout`, `setImmediate` |
| Async network I/O | libuv + OS (epoll / kqueue / IOCP) | sockets, `net`, `http` |
| Blocking work made async | libuv thread pool | most `fs`, `dns.lookup`, zlib, `crypto.pbkdf2` |
| APIs you import | Node core (JS + C++ bindings) | `node:fs`, `node:http`, `Buffer` |
| Thread scheduling, page cache, TCP stack | OS | which core runs which thread, TCP retransmits |

**Common mistake:** saying "V8 has an event loop." V8 has a microtask queue and a task API but no I/O loop; embedders (Chrome, Node, Deno) bring their own. Deno and Bun use different loops, which is why ordering puzzles do not port between runtimes.

**Follow-up:** \[E\] Where does a `Buffer`'s memory live? (Outside the V8 heap, in memory allocated by Node and tracked by V8 as *external* memory. It counts toward RSS and `external`, not `heapUsed`. See Q10.)

## V8 execution: JIT tiers, hidden classes, deoptimisation

### Q2 \[A\] How does V8 turn your JavaScript into machine code?

**Say this first:** V8 starts by interpreting bytecode, watches which functions are hot and what types they see, and progressively compiles hot code with faster, more speculative compilers. If a speculation turns out wrong, it throws the optimised code away and falls back (deoptimises).

The tiers in current V8 (Node 22 and later):

| Tier | What it does | Trade-off |
| --- | --- | --- |
| **Ignition** | parses to bytecode and interprets it; collects type feedback | starts instantly, slowest to run |
| **Sparkplug** | baseline compiler: bytecode straight to machine code, no optimisation | cheap to compile, removes interpreter overhead |
| **Maglev** | mid-tier optimising compiler using type feedback | fast compile, good code for warm functions |
| **TurboFan** | top-tier optimising compiler (inlining, escape analysis) | slow to compile, fastest code for hot paths |

**Why interviewers ask:** it explains why benchmarks need warm-up, why the first requests after a deploy are slower, and why "micro-optimisations" measured in a cold loop are often wrong.

### Q3 \[A\] What are hidden classes and inline caches, and how can code defeat them?

V8 gives every object a hidden class (a "shape" or "map") describing its property layout. Objects created the same way share a shape, so a property access site that always sees one shape can be cached as "read offset 16" (an **inline cache**). A site that sees 2–4 shapes is polymorphic (slower); more than that is megamorphic (a generic, much slower lookup).

```js
// Same shape: fast
function makePoint(x, y) { return { x, y }; }

// Shapes diverge: property order and late additions create new hidden classes
const a = { x: 1, y: 2 };
const b = { y: 2, x: 1 };      // different order -> different shape
const c = { x: 1 }; c.y = 2;   // added later -> shape transition
delete a.x;                     // often drops the object into slow "dictionary mode"
```

**Practical rules that matter in backend code:**

- Initialise all fields in the constructor, in the same order; use `null` rather than adding properties later.
- Do not `delete` properties on hot objects; set them to `undefined`, or build a new object.
- Keep functions monomorphic on hot paths: one function handling five unrelated object shapes is slower than five small functions.
- Use `Map` for dynamic keys instead of turning objects into dictionaries.

**Common mistake:** applying these rules everywhere. In most services the time goes to I/O, serialisation and database calls. Shape hygiene matters in genuinely hot loops (parsers, serialisers, per-message processing at high throughput); prove it with a profile first.

### Q4 \[S\] What is deoptimisation, and how would you notice it in production?

Optimised code is built on assumptions ("`x` is always a small integer"). When an assumption breaks (a string arrives, an array gets a hole), V8 deoptimises: it discards the optimised code and returns to a lower tier. Repeated deopt-reopt cycles show up as a function that is unexpectedly expensive in a CPU profile.

```bash
node --trace-deopt --trace-opt app.js 2>&1 | grep -i 'processOrder'   # development only: very noisy
```

**Production approach:** you rarely trace deopts in production. You take a CPU profile (Part 11), find the hot function, reproduce locally with representative data, then check for type instability (mixed number/string ids, sparse arrays, changing object shapes).

**Follow-ups:** \[E\] Why can `arguments` or `try/catch` hurt performance? (Historically they blocked optimisation in Crankshaft; in modern TurboFan they are mostly fine. Saying "try/catch is slow" in 2026 is an outdated answer.) \[A\] Why are arrays with holes slower? (They move from packed to holey element kinds, which needs extra checks, and they never transition back.)

## Memory: what the numbers mean, GC, and heap limits

### Q5 \[I\] Explain every field of process.memoryUsage().

```js
console.log(process.memoryUsage());
// {
//   rss: 182452224,        // resident set size: all RAM the process occupies
//   heapTotal: 61341696,   // V8 heap reserved
//   heapUsed: 48211784,    // V8 heap actually used by live + not-yet-collected objects
//   external: 9142813,     // memory owned by C++ objects bound to JS (includes arrayBuffers)
//   arrayBuffers: 7364802  // Buffer / ArrayBuffer / SharedArrayBuffer bytes
// }
```

Also useful: `process.memoryUsage.rss()` (cheaper, RSS only), `v8.getHeapStatistics()` (`heap_size_limit`, `used_heap_size`) and `v8.getHeapSpaceStatistics()` (per space).

**How to read them:** `heapUsed` growing across GCs suggests a JS object leak; `external` / `arrayBuffers` growing suggests retained Buffers; RSS growing while heap and external stay flat points to native memory (a native addon, memory fragmentation in the allocator, or many threads).

**Common mistake:** alerting on `heapUsed` alone. The container is killed on RSS, and Buffers are not in `heapUsed`.

### Q6 \[A\] How is the V8 heap organised?

&#91;embedded content: Node.js process memory · V8 heap vs external vs RSS\]

- **Young generation** (new space): two semi-spaces. Allocation is a pointer bump, so it is very fast. The **scavenger** copies live objects to the other semi-space; anything that survives twice is **promoted** to old space. Cost is proportional to *survivors*, not garbage, which is why short-lived request objects are cheap.
- **Old space**: collected by **mark-sweep-compact** ("major GC"). Marking runs mostly concurrently on helper threads and incrementally on the main thread; compaction moves objects to fight fragmentation.
- **Large object space**: objects above a size threshold are never moved.
- **Code space**: JIT-compiled machine code.
- **Outside the heap**: Buffer bytes and native allocations, which GC frees indirectly when the owning JS object dies.

### Q7 \[A\] What does a GC pause cost, and when does GC hurt latency?

Scavenges are short (typically sub-millisecond to a few milliseconds) and frequent. Major GCs are rarer and mostly concurrent, but still have stop-the-world phases. GC hurts when:

- **Allocation rate is very high** (building huge intermediate arrays, `JSON.parse` of large payloads, string concatenation in loops): more scavenges, more promotions.
- **The heap is near its limit**: V8 runs major GCs back to back trying to free memory, and throughput collapses before the process finally crashes with "JavaScript heap out of memory." This GC death spiral shows up as rising latency and CPU long before the crash.
- **Many objects survive just long enough to be promoted** (medium-lived caches, request batching), which makes major GCs bigger.

**Tuning knobs, used rarely:** `--max-semi-space-size` (larger young generation, fewer promotions for high-allocation services; measure first) and `--max-old-space-size`.

### Q8 \[S\] How do heap limits interact with containers?

V8 sets a default old-space limit based on available memory; recent Node versions take a container's cgroup memory limit into account when sizing it. Two things still go wrong:

1. **The heap limit is not the process limit.** RSS = heap + external + native + thread stacks. A 1 GB container with a heap allowed to grow toward 1 GB gets OOM-killed by the kernel (exit code 137, no JS stack trace) instead of throwing a JS heap error.
2. **Old images, odd defaults.** Behaviour has changed across versions, so do not rely on the default.

**Production rule:** set it explicitly, leaving headroom for non-heap memory.

```dockerfile
# 1 GiB container: about 70-75% for the JS heap
ENV NODE_OPTIONS="--max-old-space-size=768"
```

And monitor RSS against the container limit, not just heap.

**Follow-ups:** \[S\] Exit code 137 vs "FATAL ERROR: Reached heap limit": what is the difference? (137 = SIGKILL from the kernel OOM killer or the orchestrator, usually RSS over the container limit; the V8 message = JS heap limit reached inside the process.) \[E\] Would you raise `--max-old-space-size` to fix a leak? (No; it only delays the crash and makes each major GC slower. Find the leak.)

## Memory leaks, Buffers and heap snapshots

### Q9 \[I\] What is a memory leak in a garbage-collected runtime?

**Say this first:** memory that is still reachable from a GC root but that the program will never use again. GC frees unreachable objects; a leak is a reference you forgot to drop.

The usual suspects in Node services, roughly in order of how often they appear:

| Leak source | Example | Fix |
| --- | --- | --- |
| Unbounded module-level cache or map | `const cache = new Map()` keyed by user input | LRU with max size and TTL |
| Listeners added per request, never removed | `emitter.on('x', ...)` inside a handler | `once`, or `off` when the owner closes |
| Timers never cleared | `setInterval` per connection | `clearInterval` on close; `unref()` |
| Closures capturing large scope | callback keeps a 50 MB buffer alive (Part 1, Q19) | narrow what the closure captures |
| Growing arrays used as queues or logs | `pending.push(job)` with no consumer | bounded queue, backpressure |
| Promises that never settle | awaiting an event that never fires | timeouts, `AbortSignal` |
| Retained Buffers or slices | a small slice keeps a large parent alive | `Buffer.from(slice)` to copy (Q10) |
| Global state from libraries | per-request metrics labels with unbounded cardinality | bounded label sets |

**Node will even warn you:** `MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 listeners added.` The fix is almost never `setMaxListeners(0)`; it is finding why listeners accumulate.

### Q10 \[A\] How do Buffers use memory, and what is the slice trap?

- Buffer bytes live **outside** the V8 heap (external memory). The JS `Buffer` object is small; its bytes can be huge.
- `Buffer.allocUnsafe(n)` and `Buffer.from(string)` for small sizes (under 4 KB) are carved out of a shared **8 KB pool**, which is faster but means one tiny buffer can keep that pool slab alive. `Buffer.alloc(n)` is zero-filled and never pooled.
- `buf.subarray()` (and the deprecated `buf.slice()`) return a **view** on the same memory, not a copy.

```js
// Retains the full 200 MB file for as long as `header` lives
const file = await fs.promises.readFile('dump.bin');
const header = file.subarray(0, 64);
cache.set(id, header);

// Copy the bytes you need so the large buffer can be freed
cache.set(id, Buffer.from(file.subarray(0, 64)));
```

**Security note:** `allocUnsafe` memory is not zeroed and may contain old data (tokens, other users' payloads). Only use it when you overwrite every byte before reading or sending it.

### Q11 \[S\] Walk me through finding a memory leak in production.

1. **Confirm it is a leak.** RSS and `heapUsed` keep rising across many major GCs under steady load, rather than levelling off. A rising sawtooth that returns to a stable baseline is normal.
2. **Decide which memory.** `heapUsed` rising: JS objects. `external`/`arrayBuffers` rising: Buffers. Only RSS rising: native memory (addon, allocator fragmentation).
3. **Capture heap snapshots** without killing the service:

```js
import { writeHeapSnapshot } from 'node:v8';
process.on('SIGUSR2', () => {
  const file = writeHeapSnapshot();   // blocks the loop and needs about 2x heap size in memory
  logger.warn({ file }, 'heap snapshot written');
});
```

or start with `--heapsnapshot-signal=SIGUSR2`, or `--heapsnapshot-near-heap-limit=2` to capture automatically just before an OOM.

4. **Use the three-snapshot technique.** Snapshot at baseline, after N requests, after another N requests. In Chrome DevTools (Memory tab), compare: objects allocated between 1 and 2 that still exist in 3 are the suspects.
5. **Read the retainer chain.** Pick a suspicious object (a large count of the same class or closure), open its *Retainers*, and follow the path to a GC root. The first object in that chain that you own (a module-level `Map`, an emitter's listener array) is the bug.
6. **Fix, then prove it:** a load test that runs long enough to show flat memory, plus a regression test where possible.

**Production cautions:** taking a snapshot pauses the process for seconds on large heaps and roughly doubles memory, so take it on one instance pulled out of the load balancer, never on all replicas at once. Snapshots contain user data and secrets: treat them as sensitive files.

**Follow-ups:** \[S\] How would you catch leaks before production? (Soak tests with memory assertions; tracking `heapUsed` after forced GC in an integration test with `--expose-gc`; alerts on RSS slope, not just a threshold.) \[E\] What does `--heap-prof` give you that a snapshot does not? (Allocation sampling over time: *where* memory was allocated, cheaper to run, but it does not show retainers.)

## The libuv thread pool and DNS

### Q12 \[A\] What runs on the libuv thread pool, and what happens when it is saturated?

**Uses the pool:** most `fs` operations, `dns.lookup` (and anything that resolves hostnames through it, such as `http.request` and `net.connect` by default), `crypto.pbkdf2`, `scrypt`, `randomBytes`/`randomFill` (async forms), `generateKeyPair`, and async `zlib`.

**Does not use the pool:** network sockets (OS readiness notification), timers, `dns.resolve*` (uses c-ares over the network), and anything synchronous (which blocks the main thread instead).

**Saturation:** the pool is a fixed set of threads (4 by default) with one shared queue. Five slow tasks mean the fifth waits for a free thread, and unrelated work waits with it:

```js
// 8 password hashes saturate a 4-thread pool for hundreds of milliseconds...
for (let i = 0; i < 8; i++) crypto.pbkdf2(pw, salt, 600_000, 64, 'sha512', done);
// ...so this file read, which should take 1 ms, waits in the same queue
fs.readFile('config.json', onConfig);
```

**Symptom in production:** event loop delay is fine, CPU is moderate, but file reads, outbound HTTP connection setup and hashing are all slow at once. That combination points at the pool.

### Q13 \[S\] How do you size UV\_THREADPOOL\_SIZE?

- Default 4, maximum 1024. It is read **once**, when the pool is first used. Set it in the environment (`UV_THREADPOOL_SIZE=16 node app.js`). Setting `process.env.UV_THREADPOOL_SIZE` inside your code only works if it runs before anything touches the pool, and does not work on Windows; avoid it.
- More threads help when pool tasks **wait** (slow disks, network file systems, slow DNS). They help less for CPU-bound pool work (`pbkdf2`, `scrypt`, zlib) beyond the number of cores, because the threads compete for the same CPUs as your main thread.
- Each thread costs a stack (typically 8 MB of address space, less resident) and scheduling overhead.

**Senior answer:** start from the default, measure pool queueing (latency of `fs`/`crypto` calls under load), raise it to roughly core count or a bit above for mixed workloads, and move heavy CPU (hashing at scale, image processing) to dedicated worker threads or a separate service (Part 7) rather than growing the pool forever.

### Q14 \[A\] dns.lookup vs dns.resolve: why does it matter?

|  | `dns.lookup` | `dns.resolve4` / `resolve*` |
| --- | --- | --- |
| Mechanism | OS `getaddrinfo` | c-ares, direct DNS queries |
| Runs on | libuv thread pool (blocking call) | event loop, async sockets |
| Honours `/etc/hosts`, nsswitch, OS caching (e.g. nscd, systemd-resolved) | yes | no |
| Used by `http`, `net`, `fetch` by default | yes | no (unless you pass a custom `lookup`) |

**Consequences:**

- Node has **no built-in DNS cache**. Every new outbound connection does a lookup. Under load, slow or failing DNS occupies pool threads and slows `fs` and `crypto` too (Part 2, Q7a).
- Keep-alive connection reuse (an `http.Agent` with `keepAlive: true`, the default in undici's `fetch`) reduces lookups dramatically, and is the first fix.
- Caching options: OS-level caching (systemd-resolved, nscd, NodeLocal DNSCache in Kubernetes) or a library such as `cacheable-lookup` passed as the agent's `lookup`. Respect TTLs; caching forever breaks failover.

**Version trap:** since Node 17, `dns.lookup` returns addresses in the order the resolver gives them (`verbatim`) instead of preferring IPv4. Code that connected to `localhost` suddenly hit `::1` and got `ECONNREFUSED ::1:5432` when the server only listened on IPv4. Fixes: listen on both, connect to `127.0.0.1` explicitly, or `dns.setDefaultResultOrder('ipv4first')`. Node 20 also enabled Happy Eyeballs (`autoSelectFamily`) by default, which tries both families.

**Follow-ups:** \[S\] Your service calls an API whose IP changes during a failover, but your pods keep hitting the old IP. Why? (Long-lived keep-alive connections never re-resolve; set a max socket lifetime or idle timeout so connections are recycled.) \[E\] Why would `dns.lookup` be slow in Kubernetes? (`ndots:5` makes short names try several search-domain suffixes first; use fully qualified names with a trailing dot or lower `ndots`.)

## Runtime diagnostics

### Q15 \[A\] What is in Node's built-in diagnostics toolbox?

| Question you are answering | Tool | Cost |
| --- | --- | --- |
| Where is CPU time going? | `--cpu-prof` (writes `.cpuprofile`), `--inspect` + DevTools Performance, `perf` + `--perf-basic-prof` on Linux | low to moderate; sampling |
| What is retaining memory? | heap snapshots (`v8.writeHeapSnapshot`, `--heapsnapshot-signal`, `--heapsnapshot-near-heap-limit`) | high: pause + about 2x memory |
| Where is memory being allocated? | `--heap-prof` (sampling heap profiler) | low |

| What did the process look like when it crashed? | diagnostic report (`--report-on-fatalerror`, `--report-uncaught-exception`, `process.report.writeReport()`) | negligible until written |
| How long did my operation take? | `performance.mark` / `measure`, `PerformanceObserver` | negligible |
| Which library calls happen, without patching them? | `node:diagnostics_channel` | negligible when no subscriber |

Third-party tools build on these: Clinic.js (Doctor, Flame, Bubbleprof), 0x flame graphs, and APM agents built on OpenTelemetry.

### Q16 \[A\] How do you observe garbage collection?

```js
import { PerformanceObserver, constants } from 'node:perf_hooks';

const obs = new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    const kind = e.detail?.kind === constants.NODE_PERFORMANCE_GC_MAJOR ? 'major' : 'minor';
    metrics.histogram('nodejs_gc_duration_ms', e.duration, { kind });
  }
});
obs.observe({ entryTypes: ['gc'] });
```

For a local investigation: `node --trace-gc app.js` prints one line per collection (type, heap before and after, pause time). Healthy services show frequent short scavenges and occasional mark-compacts that free a lot; a struggling one shows back-to-back mark-compacts freeing little, which is the death spiral from Q7.

### Q17 \[S\] What is a diagnostic report, and what is diagnostics\_channel for?

**Diagnostic report:** a JSON snapshot of the process: JS and native stacks, heap statistics, libuv handles (open sockets, timers), environment, resource usage, loaded shared libraries. Enable `--report-on-fatalerror --report-uncaught-exception --report-directory=/var/log/node` in production so a crash leaves evidence behind. Reports include environment variables, so redact or restrict access (`--report-exclude-env` on recent versions).

**diagnostics\_channel:** a publish/subscribe API for instrumentation. Libraries publish named events (`undici:request:create`, `http.server.request.start`, database drivers' query events); tracing agents subscribe without monkey-patching. Publishing is nearly free when nobody subscribes.

```js
import diagnostics_channel from 'node:diagnostics_channel';

diagnostics_channel.subscribe('undici:request:create', ({ request }) => {
  logger.debug({ origin: request.origin, path: request.path }, 'outbound request');
});
```

**Senior signal:** decide before an incident what you will collect (metrics for loop delay, GC, heap, RSS; reports on crash; an on-demand path for snapshots and CPU profiles on one instance). During an incident is the wrong time to discover that profiling requires a redeploy.

## Tricky & trap questions (Part 3)

### T1 \[A\] "heapUsed is 80 MB, so the service uses 80 MB."

**Wrong.** RSS can be several times larger: Buffers (external), native allocations, JIT code, thread stacks, and allocator fragmentation are all outside `heapUsed`. A service streaming files can show 80 MB heap and 900 MB RSS. Containers are killed on RSS, so that is the number to alert on.

### T2 \[A\] Does this cap the pool at 16 threads?

```js
// server.js, line 40, after imports that read config files
process.env.UV_THREADPOOL_SIZE = '16';
```

**Usually not.** The pool is created on first use, and the imports above already did file system work, so the pool exists with 4 threads and the variable is ignored. On Windows it is ignored regardless. Set it in the process environment before Node starts.

### T3 \[A\] Is this cache leak-proof because it uses WeakMap?

```js
const cache = new WeakMap();
function getUserProfile(userId) {               // userId is a string
  if (!cache.has(userId)) cache.set(userId, loadProfile(userId));
  return cache.get(userId);
}
```

**It throws.** WeakMap keys must be objects (or non-registered symbols); `cache.set('u1', ...)` is a `TypeError`. And even with object keys, a WeakMap is not a cache: entries vanish when the key object is collected, not on a TTL or size limit, and you cannot iterate or bound it. Use an LRU for caching; use WeakMap for metadata attached to objects you do not own.

### T4 \[S\] "Just call global.gc() after each request to keep memory low."

**Bad idea.** `global.gc` only exists with `--expose-gc`; forcing a full GC per request pauses the main thread every time, destroys throughput and does not fix a leak (leaked objects are still reachable). V8's heuristics are better than manual collection in production. `--expose-gc` belongs in tests that assert memory returns to baseline.

### T5 \[A\] Why is the second loop much slower?

```js
const items = Array.from({ length: 1e6 }, (_, i) => ({ id: i, price: i * 2 }));
for (const it of items) total += it.price;                 // fast

items.forEach((it, i) => { if (i % 2) it.discount = 0.1; }); // half the objects change shape
for (const it of items) total += it.price;                 // now polymorphic access
```

**Answer:** adding `discount` to only some objects gives the array two hidden classes, so the `it.price` access site becomes polymorphic. The fix is to initialise `discount: 0` for every object at creation. Note this is real but small; the interview point is understanding *why*, not that you should hand-tune every loop.

### T6 \[S\] "Our pods keep restarting with exit code 137 but there is no error in the logs."

**Answer:** 137 = 128 + 9 (SIGKILL). The kernel OOM killer or the orchestrator killed the process for exceeding its memory limit; JavaScript never got a chance to log. Check container memory metrics (RSS against the limit), the orchestrator events (`OOMKilled`), and whether `--max-old-space-size` leaves headroom for non-heap memory (Q8). A V8 heap OOM instead prints `FATAL ERROR: ... JavaScript heap out of memory` and exits with a different code.

### T7 \[E\] Same code, Node 22 vs Node 26: why might memory or latency differ with no code change?

Different V8 versions change JIT tiers, GC heuristics and default heap sizing; new libuv versions change I/O internals; undici upgrades change `fetch` connection behaviour. That is why runtime upgrades go through load tests, and why benchmark results should always state the Node version.

## Debugging challenges (Part 3)

### D1 \[S\] The leak hunt: memory grows about 40 MB per hour

```js
// Broken: a WebSocket gateway
import { EventEmitter } from 'node:events';
export const bus = new EventEmitter();

wss.on('connection', (ws, req) => {
  const user = authenticate(req);
  const onNotify = (msg) => { if (msg.userId === user.id) ws.send(JSON.stringify(msg)); };
  bus.on('notify', onNotify);
  ws.on('message', (data) => handle(user, data));
});
```

**Evidence:** `heapUsed` climbs steadily across major GCs; logs show `MaxListenersExceededWarning` on `notify`; a heap snapshot comparison shows thousands of `onNotify` closures, each retaining a `WebSocket` and its buffers, retained via `bus._events.notify`.

**Root cause:** a listener is added per connection and never removed when the client disconnects. Every closed socket stays reachable through the module-level emitter.

**Fix:**

```js
wss.on('connection', (ws, req) => {
  const user = authenticate(req);
  const onNotify = (msg) => { if (msg.userId === user.id) ws.send(JSON.stringify(msg)); };
  bus.on('notify', onNotify);
  ws.once('close', () => bus.off('notify', onNotify));  // removal tied to the socket's lifetime
  ws.on('message', (data) => handle(user, data));
});
```

**The principle:** every `on` needs a matching `off` tied to the lifetime of the thing it serves. `EventEmitter.prototype.on` takes no options, so there is no `{ signal }` shortcut here; the `{ signal }` option exists on `events.on()` / `events.once()` (the promise and async-iterator helpers) and on `EventTarget.addEventListener`.

**Better design:** keep a `Map<userId, Set<ws>>` and deliver directly, instead of one listener per connection filtering every message (O(connections) work per notification).

**Test:** open and close 10,000 connections in an integration test, force GC (`--expose-gc`), and assert `bus.listenerCount('notify') === 0` and that `heapUsed` returns near baseline.

### D2 \[S\] OOM-killed in a 512 MB container while the heap looks small

**Situation:** an export service streams CSVs from the database to S3. Pods are killed with exit code 137; heap metrics peak at about 180 MB.

**Investigation:** RSS reaches about 510 MB at the moment of death; `external`/`arrayBuffers` grows with each concurrent export. The code reads each export into a single string, converts it to a Buffer for upload, and allows unlimited concurrent exports.

**Root causes:** (1) whole-file buffering instead of streaming: each 100 MB export lives as a string (heap) *and* a Buffer (external) at the same time; (2) no concurrency limit; (3) monitoring watched heap, not RSS.

**Fix:** stream end to end (`pipeline(dbCursorStream, csvTransform, gzip, uploadStream)`, Part 5) so memory per export is bounded by stream buffers (`highWaterMark`), cap concurrent exports with a queue, set `--max-old-space-size` to leave headroom for external memory, and alert on RSS as a percentage of the container limit.

### D3 \[A\] Everything is slow, but CPU and event loop delay are fine

**Symptoms:** p99 latency jumps from 80 ms to 2 s for all endpoints; event loop delay p99 is 5 ms; CPU 30%. Outbound calls show most time spent before the TCP connection opens.

**Root cause:** a cluster DNS outage made `dns.lookup` calls hang for seconds. They occupy all 4 pool threads, so new outbound connections queue for DNS and every `fs` call queues behind them. Keep-alive was disabled on the HTTP client, so every request needed a fresh lookup.

**Fix:** enable keep-alive connection reuse, add DNS caching at the node or OS level with TTL respect, set connect timeouts so lookups cannot hang requests, and add a metric for outbound connection setup time so this is visible next time.

## Cheat sheet & interviewer follow-ups (Part 3)

**Ten sentences to have ready:**

1. V8 runs JS and owns the heap; libuv runs the loop, async I/O and the thread pool; Node binds them; the OS does the real work.
2. V8 tiers: Ignition interprets, Sparkplug and Maglev compile quickly, TurboFan optimises hot code; wrong assumptions cause deopts.
3. Stable object shapes keep property access monomorphic; prove a hot path with a profile before tuning it.
4. RSS = heap + external (Buffers) + native + stacks; containers are killed on RSS.
5. Young generation is scavenged cheaply; survivors are promoted; old space is mark-compacted mostly concurrently.
6. Near the heap limit, back-to-back GCs crush throughput before the crash.
7. Set `--max-old-space-size` to about 70–75% of the container limit and alert on RSS.
8. Leaks are forgotten references: unbounded maps, unremoved listeners, timers, closures, retained slices.
9. The pool (4 threads) serves fs, `dns.lookup`, zlib and some crypto; saturation slows all of them together.
10. Node does not cache DNS; reuse connections and cache at the OS or cluster level.

# Part 4 — Modules & Package Systems

## CommonJS vs ES Modules

### Q1 \[I\] What are the real differences between CommonJS and ES Modules?

|  | CommonJS (`require`) | ES Modules (`import`) |
| --- | --- | --- |
| Loading | synchronous, at the line it runs | parsed and linked before any code runs; evaluation can be async |
| Bindings | `module.exports` is a value copy at require time | live bindings: importers see later changes to an exported `let` |
| Static analysis | dynamic, hard to tree-shake | static `import` / `export`, tree-shakable |
| Top-level `await` | no | yes |
| `this` at top level | `module.exports` | `undefined` |
| File paths | extension optional, `index.js` resolution | full relative paths with extensions in Node (`./db.js`) |
| Helpers | `__dirname`, `__filename`, `require.resolve` | `import.meta.dirname`, `import.meta.filename` (Node 20.11+), `import.meta.resolve` |
| How Node decides | `.cjs`, or `.js` without `"type": "module"` | `.mjs`, or `.js` with `"type": "module"` |

**Interop:** ESM can `import` CommonJS (you get `module.exports` as the default export, plus named exports Node can detect statically). CommonJS can `require()` an ES module synchronously since Node 22.12 / 20.19 (`require(esm)`), as long as that module graph has **no top-level await**; otherwise use `await import()`.

**Common mistake:** "ESM is just new syntax for require." The loading model is different: imports are hoisted and resolved before your code runs, so conditional imports need `await import()`.

### Q2 \[I\] How does require() resolve and cache modules?

1. Core module? (`node:fs` or `fs`) return it.
2. Path (`./`, `../`, `/`)? Try the exact file, then `.js`, `.json`, `.node`, then a directory's `package.json` `main` or `index.js`.
3. Bare name? Walk up `node_modules` folders from the current directory, honouring the package's `exports` field.
4. Wrap the file in a function `(exports, require, module, __filename, __dirname) => {...}`, run it once, store `module.exports` in `require.cache` keyed by **resolved absolute path**.

Every later `require` of the same resolved path returns the cached object. That is why modules behave like singletons, and why two copies of a package (different versions, or one via a symlink) are two different singletons.

### Q3 \[A\] What happens with circular dependencies?

```js
// a.js
exports.name = 'a';
const b = require('./b');
console.log('in a, b.name =', b.name);
// b.js
const a = require('./a');
console.log('in b, a.name =', a.name);
exports.name = 'b';
// node a.js -> in b, a.name = a ; in a, b.name = b
```

CommonJS returns the **partially filled** `exports` of a module that is still loading. In `b.js`, `a.name` happens to be set because `a.js` assigned it before requiring `b`; anything assigned later would be `undefined`. A classic bug is `module.exports = { ... }` at the bottom of `a.js`: `b` keeps a reference to the old, empty object forever.

In ESM, cycles resolve through live bindings, but reading an imported binding before its module has evaluated throws a `ReferenceError` (temporal dead zone).

**Fix:** break the cycle by extracting shared code into a third module, or inject the dependency at call time. Cycles usually signal a layering problem.

### Q4 \[A\] Module initialisation side effects and the singleton assumption

Code at module top level runs once, at first import: opening DB pools, reading env vars, registering routes. Problems:

- **Tests:** importing a module connects to a real database. Fix: export a factory (`createDb(config)`) and wire it in one composition root.
- **Order dependence:** a module reads `process.env.X` at import time, before `dotenv` (or `--env-file`) loaded it.
- **Duplicate singletons:** a monorepo with two copies of a package gives two "singletons" (two loggers, two metric registries). `instanceof` checks fail across them.
- **Workers:** each worker thread loads its own copy of every module; module state is never shared between threads.

## Packages: exports, conditions, dual packages

### Q5 \[A\] What does the exports field do, and how do conditional exports work?

```json
{
  "name": "@acme/sdk",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./errors": "./dist/errors.js",
    "./package.json": "./package.json"
  }
}
```

- It is the **only** public surface: `import '@acme/sdk/dist/internal.js'` fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`. That lets maintainers refactor internals safely.
- Conditions are matched in object order: put `types` first, then `import` / `require`, then `default`. Custom conditions (`--conditions=development`) are possible.
- `main` is only the fallback for tools that do not understand `exports`; `module` is a bundler convention that Node ignores.

### Q6 \[S\] What is the dual-package hazard?

A package that ships both CJS and ESM builds can be loaded **twice** in one app: once through `require` and once through `import`. Two copies means two module states: two caches, two registries, `instanceof` failing on errors created by the other copy.

**Mitigations:** ship ESM only (now practical because `require(esm)` works on supported Node lines); or keep state in one CJS core and make the ESM entry a thin wrapper that re-exports it; or ship CJS only with an ESM wrapper. Test both entry points.

### Q7 \[A\] Dynamic import and top-level await

```js
// lazy-load a heavy dependency only when needed
export async function renderPdf(data) {
  const { default: PDFDocument } = await import('pdfkit');
  // ...
}

// top-level await in ESM: fine for startup config
const config = await loadConfig();
export default config;
```

**Trap:** top-level await **blocks evaluation of every module that imports this one** until it resolves. A slow network call at the top of a shared module delays the whole app's startup, and a hanging one hangs it. It also prevents `require(esm)` of that graph.

## Monorepos and dependency management

### Q8 \[S\] How would you structure a Node monorepo?

- **Workspaces** (npm, pnpm, Yarn) link local packages; pnpm's strict `node_modules` catches undeclared dependencies.
- **Task runners** (Turborepo, Nx) cache builds and tests and run only what changed.
- **Boundaries:** apps depend on packages, packages never depend on apps; enforce with lint rules (`eslint-plugin-boundaries`, Nx module boundaries).
- **Versioning:** internal packages at `workspace:*`; publishable ones versioned with Changesets.
- **One TypeScript config base**, project references for incremental builds.

**Trade-off to name:** a monorepo makes atomic cross-package changes and shared tooling easy, but needs build caching and ownership rules, or CI time and coupling grow without limit.

### Q9 \[S\] How do you keep dependencies healthy and safe?

- Lockfile committed; `npm ci` in CI; reviewers read lockfile diffs.
- Automated updates (Renovate, Dependabot) grouped and scheduled, with CI as the gate.
- `npm audit` / `osv-scanner` in CI, triaged rather than blindly "fixed" with `--force`.
- Fewer dependencies: check maintenance, install scripts, transitive count, and whether a 10-line function would do.
- `npm ci --ignore-scripts` where possible; provenance (`npm publish --provenance`) and signature verification (`npm audit signatures`) for supply-chain trust. Part 9 covers attacks.

### Q10 \[I\] Tree-shaking: does it matter on the server?

Less than in browsers, because there is no download cost. It matters for serverless cold starts and container size, where bundling (esbuild, Rollup) with tree-shaking can cut startup time. ESM's static imports make tree-shaking possible; `sideEffects: false` in `package.json` tells bundlers a package's modules can be dropped if unused.

## Tricky & trap questions (Part 4)

### T1 \[A\] Why is the logger configured twice?

```text
node_modules/@acme/logger            (v2.1.0)
node_modules/@acme/http/node_modules/@acme/logger   (v1.9.0)
```

Two versions resolve to two paths, so two module instances with separate state. `npm ls @acme/logger` shows the duplication; fix with aligned version ranges, a peer dependency, or `overrides`.

### T2 \[I\] `__dirname is not defined in ES module scope`

ESM has no module wrapper, so no `__dirname`. Use `import.meta.dirname` (Node 20.11+), or `path.dirname(fileURLToPath(import.meta.url))` on older lines.

### T3 \[A\] What does this print?

```js
// counter.mjs
export let count = 0;
export function inc() { count++; }
// main.mjs
import { count, inc } from './counter.mjs';
inc(); inc();
console.log(count);
```

**Output:** `2`. ESM exports are live bindings. The CommonJS equivalent (`const { count, inc } = require('./counter')`) prints `0`, because destructuring copied the value at require time. You cannot assign `count = 5` from `main.mjs`, though: imported bindings are read-only.

### T4 \[A\] "I'll clear require.cache to hot-reload config."

It reloads that module, but every module that already holds a reference to the old exports keeps it, and listeners or timers created by the old instance keep running. Hot reload this way leaks and produces split-brain state. Reload configuration through an explicit API, or restart the process.

## Debugging challenge (Part 4)

### D1 \[S\] `TypeError: Cannot read properties of undefined (reading 'findById')` only in production

**Root cause:** a circular import between `user.service.js` and `order.service.js`. In development, a different import order (tests import `order.service` first) made it work; the production entry point imports `user.service` first, so `order.service` received a half-initialised `user.service` export.

## Cheat sheet (Part 4)

1. CJS loads synchronously and copies values; ESM links first and exports live bindings.
2. `require` caches by resolved path; two paths, two singletons.
3. Cycles in CJS return half-built exports; in ESM they can throw TDZ errors.
4. `exports` is the public API; put `types` first in conditions.
5. `require(esm)` works on supported LTS lines unless the graph uses top-level await.
6. Dual packages risk two module states; prefer ESM-only or a shared CJS core.
7. Top-level await delays every importer.
8. Module top-level side effects make testing and ordering fragile; use factories.

### More trap questions

#### T5 \[A\] Environment variable read at import time

```js
// config.js
export const PORT = Number(process.env.PORT ?? 3000);
// server.js
import { PORT } from './config.js';
```

`PORT` is always 3000 locally: ESM evaluates `config.js` (in import order) before `dotenv/config` runs. Imports are hoisted. Load env first (`node --env-file=.env`), or import `dotenv/config` before `config.js`.

### Code output questions

#### O1 \[A\] Module initialisation order

```js
// a.mjs
console.log('a');
import './b.mjs';
console.log('a end');
// b.mjs
console.log('b');
```

**Output (`node a.mjs`):** `b`, `a`, `a end`. Imports are linked and evaluated before the importing module's body runs, regardless of where the `import` line appears. In CommonJS with `require`, the order would be `a`, `b`, `a end`.

#### O3 \[E\] ESM cycle with a function declaration

```js
// x.mjs

console.log(y());
// y.mjs
import { x } from './x.mjs';
```

**Output (`node x.mjs`):** `y sees x`. Function declarations are hoisted and initialised during linking, so `x` is callable even though `x.mjs` has not finished evaluating. Had `x` been `export const x = () => 'x'`, calling it from `y` during evaluation would throw a `ReferenceError` (TDZ); here `y()` is only called after both modules evaluated, so it works either way. # Part 5 — Buffers, Streams & File Systems

## Buffers and encodings

### Q1 \[I\] What is a Buffer, and what are the encoding traps?

A `Buffer` is a fixed-length sequence of bytes (a `Uint8Array` subclass) for binary data: file contents, network packets, hashes. Strings are text; Buffers are bytes. Converting between them needs an encoding (`utf8` by default; also `base64`, `base64url`, `hex`, `latin1`, `utf16le`).

```js
Buffer.byteLength('€');            // 3 (bytes), while '€'.length === 1 (UTF-16 code units)
Buffer.from('€').subarray(0, 2).toString(); // '\uFFFD' replacement char: a split multi-byte sequence
```

**The streaming trap:** decoding each chunk separately breaks multi-byte characters that straddle a chunk boundary. Use `stream.setEncoding('utf8')`, `string_decoder.StringDecoder`, or `TextDecoder` with `{ stream: true }`, which carry partial bytes over to the next chunk.

**Other traps:** body size limits must count **bytes** (`Buffer.byteLength`), not `string.length`; comparing secrets needs `crypto.timingSafeEqual` on equal-length Buffers (Part 9); `Buffer.allocUnsafe` is not zeroed (Part 3, Q10).

## Streams

### Q2 \[I\] What are the four stream types?

| Type | Direction | Examples |
| --- | --- | --- |
| Readable | source | `fs.createReadStream`, `http.IncomingMessage` (request on the server), `process.stdin` |
| Writable | sink | `fs.createWriteStream`, `http.ServerResponse`, `process.stdout` |
| Duplex | both, independent | TCP `net.Socket`, WebSocket streams |
| Transform | duplex where output is computed from input | `zlib.createGzip()`, `crypto.createHash` (as stream), CSV parsers |

Why streams: constant memory regardless of data size, data starts flowing before it is all available (lower time-to-first-byte), and composition (`read → parse → transform → compress → upload`).

### Q3 \[A\] Explain backpressure.

&#91;embedded content: Stream backpressure · write() return value and 'drain'\]

`writable.write(chunk)` returns `false` when the writable's internal buffer has reached `highWaterMark`. A well-behaved producer stops writing and waits for the `'drain'` event. Ignore the return value and the buffer grows without limit: a fast disk read piped by hand into a slow client can buffer gigabytes in memory.

```js
// Broken: ignores backpressure
readable.on('data', (chunk) => res.write(chunk));

// Manual but correct
readable.on('data', (chunk) => {
  if (!res.write(chunk)) {
    readable.pause();
    res.once('drain', () => readable.resume());
  }
});

// What you should actually write
await pipeline(readable, res);
```

**Common mistake:** thinking `highWaterMark` is a hard limit. It is a threshold: `write()` still accepts the chunk and returns `false`; only the producer's cooperation keeps memory bounded.

### Q4 \[A\] pipe() vs pipeline()

|  | `src.pipe(dest)` | `pipeline(src, ...transforms, dest)` |
| --- | --- | --- |
| Backpressure | yes | yes |
| Error forwarding | **no**: an error in `src` does not close `dest` | yes: any error destroys every stream |
| Cleanup | manual; leaks file descriptors on error | automatic |
| Completion | listen to `finish` / `close` yourself | returns a promise (`node:stream/promises`) |
| Async generators as stages | no | yes |
| Cancellation | manual | `{ signal }` option |

```js
import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';

await pipeline(
  createReadStream('access.log'),
  createGzip(),
  createWriteStream('access.log.gz'),
  { signal: AbortSignal.timeout(60_000) },
);
```

Use `stream.finished(stream)` (promise version) when you only need to know a single stream is done or failed.

### Q5 \[A\] Async iteration over streams, and generator transforms

Readable streams are async iterables, and `pipeline` accepts async generator functions as transform stages. Backpressure is automatic because the consumer pulls.

```js
import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';
import readline from 'node:readline';

await pipeline(
  createReadStream('events.ndjson'),
  async function* (source) {
    const lines = readline.createInterface({ input: source, crlfDelay: Infinity });
    for await (const line of lines) {
      if (!line) continue;
      const event = JSON.parse(line);
      if (event.type === 'purchase') yield JSON.stringify(event) + '\n';
    }
  },
  createWriteStream('purchases.ndjson'),
);
```

### Q6 \[I\] Object mode and highWaterMark

In **object mode** a stream carries JS values instead of bytes, and `highWaterMark` counts **objects** (default 16) rather than bytes (default 64 KiB since Node 22; 16 KiB before). A transform from bytes to rows usually has `readableObjectMode: true` and `writableObjectMode: false`.

**Tuning:** a larger `highWaterMark` means fewer, larger chunks and more throughput, at the cost of memory per stream multiplied by concurrent streams. 1,000 concurrent downloads with 1 MB buffers is 1 GB before anything else.

## Processing large files

### Q7 \[S\] Process a 20 GB CSV and load valid rows into PostgreSQL without running out of memory.

**Requirements:** constant memory, backpressure from the database, bad rows reported not fatal, resumable or at least idempotent, observable progress.

```js
import { pipeline } from 'node:stream/promises';
import { createReadStream } from 'node:fs';
import { parse } from 'csv-parse';

async function* toBatches(rows, size = 1000) {
  let batch = [];
  for await (const row of rows) {
    batch.push(row);
    if (batch.length === size) { yield batch; batch = []; }
  }
  if (batch.length) yield batch;
}

async function importCsv(path, db, { signal } = {}) {
  let ok = 0, bad = 0;
  await pipeline(
    createReadStream(path),
    parse({ columns: true, skip_empty_lines: true, relax_column_count: true }),
    async function* (rows) {
      for await (const row of rows) {
        const v = OrderRow.safeParse(row);
        if (v.success) yield v.data;
        else { bad++; badRowLog.write(JSON.stringify({ row, issues: v.error.issues }) + '\n'); }
      }
    },
    (rows) => toBatches(rows),
    async function (batches) {
      for await (const batch of batches) {
        await db.insertOrdersBatch(batch);   // ON CONFLICT (external_id) DO NOTHING -> idempotent re-runs
        ok += batch.length;
        if (ok % 100_000 === 0) logger.info({ ok, bad }, 'import progress');
      }
    },
    { signal },
  );
  return { ok, bad };
}
```

**Why it works:** each stage pulls only when the next is ready, so a slow database slows the file read instead of filling memory. Batching amortises round trips. `ON CONFLICT DO NOTHING` on a natural key makes re-running after a crash safe.

**Faster alternative:** PostgreSQL `COPY ... FROM STDIN` via `pg-copy-streams` into a staging table, then one `INSERT ... SELECT` with validation in SQL. **Run it where?** Not in an API process: in a job worker (Part 10) so a 20-minute import cannot starve request handling.

### Q8 \[S\] Streaming uploads and downloads

- **Download:** `await pipeline(createReadStream(path), res)`; set `Content-Length` from `stat`, support `Range` requests for large media, and handle client aborts (pipeline destroys the file stream when the socket closes).
- **Upload:** stream the request body to its destination (`busboy` for multipart, or straight to S3 with a multipart upload) instead of buffering. Enforce a **byte limit while streaming** (a transform that counts bytes and errors past the limit), validate content type by sniffing magic bytes rather than trusting the header, and write to a temporary name, renaming only on success.
- **Proxying:** a reverse proxy in front (Nginx) may buffer whole requests by default (`proxy_request_buffering`); know where buffering happens end to end.

## Files: descriptors, temp files, paths, permissions

### Q9 \[A\] How do file descriptor leaks happen, and how do you prevent them?

Every open file or socket uses a descriptor; the process limit (`ulimit -n`, often 1024 by default outside containers) runs out and you get `EMFILE: too many open files`.

```js
// Leaks the handle if parse throws
const fh = await fs.promises.open(path);
const data = parse(await fh.readFile('utf8'));
await fh.close();

// Correct
const fh2 = await fs.promises.open(path);
try { return parse(await fh2.readFile('utf8')); }
finally { await fh2.close(); }
// Node 24+: await using fh3 = await fs.promises.open(path);  // closes automatically via Symbol.asyncDispose
```

Also: streams created but never consumed or destroyed, `pipe()` chains that error without cleanup, and unbounded concurrency (`Promise.all` over 50,000 files). Limit concurrency (Part 2, Q22) and prefer `pipeline`.

### Q10 \[S\] Safe path handling: how do you prevent path traversal?

```js
import path from 'node:path';
const ROOT = path.resolve('/srv/uploads');

function safeJoin(root, userPath) {
  const target = path.resolve(root, userPath);               // normalises ../ and absolute paths
  if (target !== root && !target.startsWith(root + path.sep)) {
    throw Object.assign(new Error('Invalid path'), { status: 400 });
  }
  return target;
}
```

- `path.join(ROOT, '../../etc/passwd')` escapes the root; `startsWith(ROOT)` without the separator lets `/srv/uploads-old` through.
- Symlinks inside the root can still point outside: resolve with `fs.realpath` and check again, or disallow symlinks.
- Better: never use user input as a path. Store files under generated IDs and keep the original name as metadata.
- Permissions: create files with restrictive modes (`0o600`), run as a non-root user, and mount upload directories without execute rights. Node's permission model (`--permission --allow-fs-read=...`) adds a runtime guard.

**Temp files:** use `fs.mkdtemp(path.join(os.tmpdir(), 'job-'))` for a unique directory, clean up in `finally`, and also on startup (crashed runs leave files behind).

## Tricky & trap questions (Part 5)

### T1 \[A\] Does this handle errors?

```js
fs.createReadStream('in.txt').pipe(zlib.createGzip()).pipe(fs.createWriteStream('out.gz'))
  .on('error', (e) => console.error(e));
```

**Only for the last stream.** The `error` handler is on the write stream. A missing `in.txt` emits an unhandled `'error'` on the read stream, which crashes the process; the gzip and write streams stay open. Use `pipeline`.

### T2 \[A\] Why does memory still grow with streams?

```js
const chunks = [];
req.on('data', (c) => chunks.push(c));
req.on('end', () => process(Buffer.concat(chunks)));
```

This buffers the whole body: streaming API, buffering behaviour. Add a size limit, or process incrementally.

### T3 \[I\] What is wrong with `fs.readFileSync` in a handler that serves a 5 KB template?

It blocks the event loop for every request (disk latency under load can be milliseconds). Read it once at startup and keep it in memory, or use the async API.

### T4 \[S\] "We set highWaterMark to 1 GB so the stream never pauses."

You have disabled backpressure and promised up to 1 GB of memory per stream. With concurrency, that is an OOM waiting to happen.

## Debugging challenge (Part 5)

### D1 \[S\] Download endpoint leaks file descriptors under load

```js
// Broken
app.get('/files/:id', async (req, res) => {
  const file = await files.get(req.params.id);
  const stream = fs.createReadStream(file.path);
  stream.pipe(res);
});
```

**Symptoms:** after a few days, `EMFILE` errors; `lsof -p <pid>` shows thousands of open files.

**Root cause:** when a client disconnects mid-download, `pipe` stops writing but does **not** destroy the source; the read stream stays open forever. Read errors also go unhandled.

**Fix:**

```js
app.get('/files/:id', async (req, res, next) => {
  try {
    const file = await files.get(req.params.id);
    const { size } = await fs.promises.stat(file.path);
    res.setHeader('Content-Length', size);
    res.setHeader('Content-Type', file.mimeType);
    await pipeline(fs.createReadStream(file.path), res);  // destroys both on error or client abort
  } catch (err) {
    if (err.code === 'ERR_STREAM_PREMATURE_CLOSE') return;   // client went away: not a server error
    if (!res.headersSent) return next(err);
    res.destroy(err);
  }
});
```

**Test:** start a download, abort the client after 1 KB, and assert `process.getActiveResourcesInfo()` shows no lingering `FileHandle` / read stream after a tick.

## Cheat sheet (Part 5)

1. Strings are text, Buffers are bytes; count bytes for limits; decode streams with a decoder that carries partial characters.
2. Respect `write()` returning `false`; wait for `'drain'`.
3. Use `pipeline` (promise version) over `pipe`: errors, cleanup, cancellation.
4. Streams are async iterables; async generators make readable transforms.
5. `highWaterMark` is a threshold, not a cap; memory = buffer size x concurrency.
6. Large files: stream, validate per row, batch writes, idempotent keys, run in a worker.
7. Always close handles in `finally` or with `await using`.
8. Never trust paths from users: resolve, check the prefix with a separator, beware symlinks, prefer generated IDs.

### More trap questions

#### T5 \[A\] Partial reads

```js
const fh = await fs.promises.open('data.bin');
const buf = Buffer.alloc(1024);
const { bytesRead } = await fh.read(buf, 0, 1024, 0);
process(buf);           // bug
```

`read` may return fewer bytes than requested (end of file, pipes, network file systems). Use `buf.subarray(0, bytesRead)` and loop until you have what you need.

#### T6 \[A\] Does `stream.destroy()` flush buffered writes?

No. `destroy()` discards pending data; `end()` flushes and then finishes. Use `end()` for normal completion and `destroy(err)` for aborts.

#### T7 \[S\] Cancelling a `pipe()` chain on client disconnect

With `src.pipe(res)`, when the client disconnects `res` is destroyed but `src` keeps reading (and with `pipe`, unpiping stops flow but does not close the file). The fix is `pipeline`, which destroys every stream in the chain when any one closes early (Part 5, D1).

### Code output questions

#### O1 \[A\] Event order for a small file

```js
const s = fs.createReadStream('small.txt');
s.on('open', () => console.log('open'));
s.on('data', () => console.log('data'));
s.on('end', () => console.log('end'));
s.on('close', () => console.log('close'));
```

**Output:** `open`, `data` (once per chunk; once for a small file), `end`, `close`. `end` means no more data; `close` means the file descriptor was released. Deterministic order.

#### O2 \[A\] What does this log?

```js
const w = new Writable({ highWaterMark: 4, write(chunk, enc, cb) { setTimeout(cb, 10); } });
console.log(w.write('ab'), w.write('cd'), w.write('ef'));
```

**Output:** `true false false`. After the first write, 2 bytes are buffered (below 4); the second makes 4 (at the threshold), so `write` returns `false`; further writes still return `false` until `'drain'`. Deterministic.

#### O3 \[A\] Memory behaviour

```js
const big = fs.createReadStream('10GB.log');
big.on('data', (chunk) => slowSocket.write(chunk));
```

**Behaviour:** memory grows toward the file size if the socket is slower than disk, because `write()` return values are ignored. With `pipeline(big, slowSocket)` memory stays near `highWaterMark` for each stream.

# Part 6 — HTTP, Networking & APIs

## The request lifecycle

### Q1 \[A\] Walk me through one HTTPS request to a Node service behind a load balancer.

```text
Client                LB / reverse proxy              Node process
  | DNS lookup           |                                |
  | TCP handshake ------>|  (SYN, SYN-ACK, ACK)           |
  | TLS handshake ------>|  TLS usually terminates here   |
  | HTTP request ------->|-- new or reused TCP conn ----->| libuv: socket readable (poll phase)
  |                      |                                | llhttp parses headers -> 'request' event
  |                      |                                | your handler runs; body arrives as a stream
  |                      |<---- response headers + body --| res.write / res.end (backpressure applies)
  |<---- response -------|                                |
  | keep-alive: connection stays open for the next request|
```

Key points to say: Node's `http` server parses with **llhttp**; the request body is a **Readable stream** you must consume or discard; the response is a **Writable**; one TCP connection can carry many sequential requests (HTTP/1.1 keep-alive) or many concurrent streams (HTTP/2).

### Q2 \[I\] TCP vs HTTP, and HTTP/1.1 vs HTTP/2 vs HTTP/3

- **TCP** gives an ordered, reliable byte stream. **HTTP** is a request/response protocol on top of it (TLS in between for HTTPS).
- **HTTP/1.1:** one in-flight request per connection; browsers open about 6 connections per origin; keep-alive reuses connections.
- **HTTP/2:** binary framing, many concurrent streams over one TCP connection, header compression (HPACK). TCP head-of-line blocking remains: one lost packet stalls all streams.
- **HTTP/3:** HTTP over QUIC (UDP), with per-stream loss recovery and faster handshakes. Usually terminated at the CDN or load balancer.

**In practice:** Node services often speak HTTP/1.1 to a proxy that speaks HTTP/2 or HTTP/3 to clients. Node has `node:http2`; gRPC uses HTTP/2.

### Q3 \[A\] Build a minimal HTTP server with built-in modules, done properly.

```js
import http from 'node:http';

const MAX_BODY = 1_000_000; // bytes

async function readJson(req) {
  let size = 0; const chunks = [];
  for await (const chunk of req) {
    size += chunk.length;
    if (size > MAX_BODY) throw Object.assign(new Error('Payload too large'), { status: 413 });
    chunks.push(chunk);
  }
  try { return JSON.parse(Buffer.concat(chunks).toString('utf8')); }
  catch { throw Object.assign(new Error('Invalid JSON'), { status: 400 }); }
}

const server = http.createServer(async (req, res) => {
  try {
    if (req.method === 'POST' && req.url === '/echo') {
      if (!req.headers['content-type']?.startsWith('application/json')) {
        res.writeHead(415).end(); return;
      }
      const body = await readJson(req);
      res.writeHead(200, { 'content-type': 'application/json' }).end(JSON.stringify(body));
      return;
    }
    res.writeHead(404).end();
  } catch (err) {
    const status = err.status ?? 500;
    if (status === 500) console.error(err);
    if (!res.headersSent) res.writeHead(status, { 'content-type': 'application/json' });
    res.end(JSON.stringify({ error: status === 500 ? 'Internal error' : err.message }));
  }
});

server.requestTimeout = 30_000;      // whole request must arrive within 30 s
server.headersTimeout = 10_000;      // headers within 10 s (slowloris defence)
server.keepAliveTimeout = 65_000;    // longer than the load balancer's idle timeout
server.listen(3000);
```

**What the interviewer looks for:** body size limit counted in bytes, content-type check, never leaking error details on 500, server timeouts set deliberately.

## Timeouts, keep-alive, connection reuse

### Q4 \[S\] Which timeouts exist on a Node HTTP server, and how do they interact with a load balancer?

| Setting | Meaning | Typical default |
| --- | --- | --- |
| `server.headersTimeout` | max time to receive headers | 60 s |
| `server.requestTimeout` | max time to receive the whole request | 300 s (Node 18+) |
| `server.keepAliveTimeout` | idle time before closing a kept-alive socket | 5 s |
| `server.timeout` / `socket.setTimeout` | inactivity on the socket | 0 (off) |

**The classic 502 bug:** an AWS ALB keeps idle connections for 60 s; Node closes idle ones after 5 s. The LB sends a request on a socket Node just closed and returns 502. **Fix:** `keepAliveTimeout` greater than the LB idle timeout (for example 65 s), and `headersTimeout` greater than `keepAliveTimeout` on older Node lines.

**Application timeouts are separate:** a handler waiting on a slow database is not stopped by any server timeout. Give each request a deadline and pass an `AbortSignal` down (Part 2).

### Q5 \[A\] HTTP client keep-alive and connection pooling

Opening a TCP + TLS connection costs one to three round trips. Reusing connections removes that from every request.

- **`fetch` / undici:** pools and keeps connections alive by default per origin. Tune with an `Agent` (`connections`, `keepAliveTimeout`, `pipelining`).
- **`http.request`:** Node 19+ enables keep-alive on the global agent; create your own `http.Agent({ keepAlive: true, maxSockets: 50 })` per upstream to bound concurrency.

```js
import { Agent, setGlobalDispatcher } from 'undici';
setGlobalDispatcher(new Agent({ connections: 100, keepAliveTimeout: 10_000, connectTimeout: 2_000 }));
```

**Pitfalls:** unbounded sockets to a slow upstream (each waiting request holds one); stale pooled connections that the server already closed (retry idempotent requests once on `ECONNRESET`); long-lived connections that never re-resolve DNS (Part 3, Q14).

### Q6 \[S\] Handling client disconnects safely

If the client goes away, keep work you must finish (a payment you already started) but stop work that only served this response (a 30-second report query).

```js
app.get('/report', async (req, res, next) => {
  const ac = new AbortController();
  res.on('close', () => { if (!res.writableFinished) ac.abort(new Error('client disconnected')); });
  try {
    const rows = await db.query(reportSql, { signal: ac.signal });  // driver must support cancellation
    res.json(rows);
  } catch (err) {
    if (ac.signal.aborted) return;   // nothing to send; not a server error
    next(err);
  }
});
```

Use `res.on('close')` (fires on both completion and abort; check `writableFinished`), not `req.on('close')`, whose semantics changed across versions. For PostgreSQL, cancellation means `pg_cancel_backend` or a `statement_timeout`.

## Proxies, CORS, compression, streaming

### Q7 \[A\] What changes when you run behind a reverse proxy?

- `req.socket.remoteAddress` is the proxy's IP. The client IP is in `X-Forwarded-For` (or `Forwarded`), which **anyone can forge** unless you only trust headers added by your own proxies. In Express: `app.set('trust proxy', 1)` (number of hops), never `true` blindly. Rate limiting by a spoofable IP is a bypass.
- `X-Forwarded-Proto` tells you the original scheme for redirects and secure cookies.
- The proxy may buffer request and response bodies, add its own timeouts and body limits, and terminate TLS.

### Q8 \[I\] CORS misconceptions

- CORS is enforced by **browsers**, not servers. It does not protect your API from curl, scripts or other servers; it only controls which web origins' JavaScript may read responses.
- It is **not** a CSRF defence on its own: simple requests (form posts) are sent without preflight; the browser just hides the response.
- `Access-Control-Allow-Origin: *` cannot be combined with credentials. Reflecting the request's `Origin` header back with `Allow-Credentials: true` lets any site read authenticated responses. Use an explicit allow-list.
- Preflight (`OPTIONS`) happens for non-simple methods, headers or content types; cache it with `Access-Control-Max-Age`.

### Q9 \[A\] Compression trade-offs

Gzip or Brotli cuts JSON and HTML size by 70–90%, but costs CPU. In Node, `zlib` compression runs on the thread pool when async, but middleware compression of every response still burns CPU per request.

**Production answer:** compress at the reverse proxy or CDN, not in Node; skip tiny responses (under about 1 KB) and already-compressed formats (images, video, zip); precompress static assets at build time. **Security:** compressing secrets alongside attacker-controlled input over TLS enables BREACH-style attacks; avoid reflecting user input in pages that contain tokens.

### Q10 \[A\] Streaming responses and Server-Sent Events

Stream large results instead of building one huge JSON string: NDJSON (one JSON object per line) or a cursor piped through a transform, with backpressure via `pipeline`. **SSE** (`text/event-stream`) is a simple one-way push channel over plain HTTP, auto-reconnecting in browsers, good for notifications and progress. WebSockets (Part 13) are for two-way, high-frequency messaging.

```js
app.get('/events', (req, res) => {
  res.writeHead(200, { 'content-type': 'text/event-stream', 'cache-control': 'no-cache', connection: 'keep-alive' });
  const send = (e) => res.write(`id: ${e.id}\nevent: ${e.type}\ndata: ${JSON.stringify(e.data)}\n\n`);
  const unsubscribe = notifications.subscribe(req.user.id, send);
  const ping = setInterval(() => res.write(': ping\n\n'), 25_000);   // keeps proxies from timing out
  res.on('close', () => { clearInterval(ping); unsubscribe(); });
});
```

## API design

### Q11 \[S\] What makes a good REST API in production?

- **Resources and methods:** nouns, correct verbs, correct status codes (201 with `Location`, 204, 400 vs 422, 401 vs 403, 404, 409 for conflicts, 429 with `Retry-After`).
- **Validation at the edge:** schemas (Zod, TypeBox/Ajv) for params, query and body; reject unknown fields on writes; one consistent error format (RFC 9457 problem details).
- **Pagination:** cursor (keyset) pagination for large or changing data (`?after=<opaque cursor>&limit=50`); offset pagination gets slow and skips or duplicates rows as data changes.
- **Versioning:** additive changes by default; a new version (`/v2` or a header) only for breaking changes, with a deprecation timeline (`Deprecation` and `Sunset` headers).
- **Idempotency:** `PUT` and `DELETE` are idempotent by definition; make `POST` safe to retry with an `Idempotency-Key` header (Part 14, Part 15).
- **Rate limits, auth, request IDs, and documentation** (OpenAPI generated from the same schemas you validate with).

**Common mistake:** returning 200 with `{ "error": ... }`. Clients, proxies, retries and monitoring all rely on status codes.

## Tricky & trap questions (Part 6)

### T1 \[A\] `Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent`

Two code paths responded: usually a missing `return` after `res.json()`, a callback and a promise both handling the same request, or an error handler running after a streamed response started. Always `return` after responding; in error handlers check `res.headersSent` and destroy the socket instead of writing.

### T2 \[S\] Why do we see random 502s only under low traffic?

Idle connections between LB and Node hit Node's 5 s `keepAliveTimeout` before the LB's 60 s idle timeout (Q4). High traffic keeps connections busy, which hides it.

### T3 \[A\] Does `Promise.all` of 1,000 `fetch` calls send 1,000 requests at once?

No: undici's pool caps connections per origin, so most requests queue inside the client, holding memory and timing out in the queue rather than at the server. Bound concurrency yourself so queueing is visible and controlled.

### T4 \[I\] "We enabled CORS, so our API is protected from other sites."

CORS only restricts reading responses in browsers. Authorisation, CSRF protection and rate limiting are still your job.

## Debugging challenge (Part 6)

### D1 \[S\] Outbound calls to a partner API time out under load, but the partner says they are fast

**Evidence:** client-side latency is mostly time waiting for a socket; `undici` pool stats show all connections busy; each partner call has a 30 s timeout.

**Root cause:** a pool of 10 connections per origin, slow partner responses during their peak, and long timeouts: requests queue in the client. The partner's server-side latency looks fine because queued requests have not reached it yet.

**Fix:** size the pool for real concurrency, set a connect timeout and a total deadline shorter than your own SLO, add a concurrency limit with fast rejection when the queue is full, a circuit breaker (Part 8), and a metric for client-side queue time.

## Cheat sheet (Part 6)

1. Request bodies are streams: limit bytes, validate content type, handle aborts.
2. Set `headersTimeout`, `requestTimeout`, and `keepAliveTimeout` above the LB idle timeout.
3. Reuse outbound connections; bound pools; set connect timeouts and deadlines.
4. Trust `X-Forwarded-For` only from known proxy hops.
5. CORS is a browser read policy, not authentication or CSRF protection.
6. Compress at the edge; stream big responses; SSE for one-way push.
7. Correct status codes, schema validation, cursor pagination, idempotency keys, problem-details errors.

**Theory vs production:** theory is knowing HTTP semantics; production is aligning timeouts across hops, bounding every pool, trusting only your own proxies' headers, and making retries safe with idempotency.

### More trap questions

#### T5 \[A\] What happens here?

```js
http.createServer((req, res) => {
  const data = JSON.parse(undefinedVariable);   // throws synchronously
  res.end(data);
}).listen(3000);
```

**Answer:** a `ReferenceError` thrown synchronously inside the request handler is an **uncaught exception**: the whole process crashes and every in-flight request on it fails. Frameworks wrap handlers in try/catch; with the raw `http` module you must do it yourself (Q3).

#### T6 \[A\] "Our body parser protects us from big uploads."

Express's `express.json()` defaults to a 100 KB limit, but `express.raw()` / custom parsers and multipart libraries have their own limits, and a proxy may already have buffered the whole body. Check every layer: proxy `client_max_body_size`, parser limits, multipart `fileSize`, and streaming byte counters.

#### T7 \[S\] Why did moving the API to HTTP/2 between LB and Node not reduce p99?

The p99 was dominated by handler time (database and CPU), not connection setup or head-of-line blocking on the wire. Protocol upgrades fix transport problems only; measure where time is spent first (Part 11, Q7).

#### T8 \[A\] Does `res.end()` mean the client received the response?

No. It means Node handed the data to the socket; the kernel and network may still be sending it, and the client may disconnect before it arrives. `res.on('finish')` fires when Node finished writing; there is no end-to-end delivery acknowledgement in HTTP.

# Part 7 — Processes, Threads & Parallelism

## The four kinds of parallelism

### Q1 \[A\] Worker threads vs child processes vs cluster vs the libuv thread pool

&#91;embedded content: cluster vs worker\_threads · processes vs threads\]

|  | libuv thread pool | `worker_threads` | `child_process` | `cluster` |
| --- | --- | --- | --- | --- |
| What runs | Node's internal C++ tasks (fs, dns.lookup, zlib, crypto) | your JS, in a new V8 isolate | any program (or Node via `fork`) | copies of your Node app |
| You control it? | only its size | yes | yes | yes |
| Memory | shared process | one process; each thread its own heap; can share `SharedArrayBuffer` | separate process | separate processes |
| Communication | none (callbacks) | `postMessage` (structured clone), transferables, shared memory | stdio, IPC channel | IPC; connections handed out by the primary |
| Startup cost | none | tens of ms and some MB per worker | higher | higher |
| Crash isolation | n/a | an uncaught error ends the worker; the process survives | yes | yes |
| Best for | built-in async APIs | CPU-heavy JS (hashing, image work, parsing, compression) | running other binaries, isolating untrusted or leaky code | using every core for an HTTP server on one machine |

**Common mistake:** "use cluster for CPU-heavy work." Cluster spreads *requests* across processes; one CPU-heavy request still blocks its own worker. Offload the heavy work to worker threads.

## Worker threads

### Q2 \[A\] Build a worker-thread task processor.

```js
// hash-worker.js
import { parentPort } from 'node:worker_threads';
import { scryptSync } from 'node:crypto';
parentPort.on('message', ({ id, password, salt }) => {
  try { parentPort.postMessage({ id, hash: scryptSync(password, salt, 64).toString('hex') }); }
  catch (err) { parentPort.postMessage({ id, error: err.message }); }
});
```

```js
// pool.js: a small fixed pool with a queue
import { Worker } from 'node:worker_threads';
import os from 'node:os';

export class WorkerPool {
  #idle = []; #queue = []; #pending = new Map(); #nextId = 0;
  constructor(file, size = Math.max(1, os.availableParallelism() - 1), maxQueue = 1000) {
    this.maxQueue = maxQueue;
    for (let i = 0; i < size; i++) this.#spawn(file);
  }
  #spawn(file) {
    const w = new Worker(new URL(file, import.meta.url));
    w.on('message', ({ id, error, ...result }) => {
      const p = this.#pending.get(id); this.#pending.delete(id);
      error ? p.reject(new Error(error)) : p.resolve(result);
      this.#release(w);
    });
    w.on('error', (err) => {                      // the worker died: fail its task, replace it
      for (const [id, p] of this.#pending) if (p.worker === w) { p.reject(err); this.#pending.delete(id); }
      this.#spawn(file);
    });
    this.#release(w);
  }
  #release(w) {
    const next = this.#queue.shift();
    next ? this.#dispatch(w, next) : this.#idle.push(w);
  }
  #dispatch(w, task) { this.#pending.set(task.msg.id, { ...task, worker: w }); w.postMessage(task.msg); }
  run(data) {
    return new Promise((resolve, reject) => {
      const task = { msg: { id: this.#nextId++, ...data }, resolve, reject };
      const w = this.#idle.pop();
      if (w) return this.#dispatch(w, task);
      if (this.#queue.length >= this.maxQueue) return reject(new Error('pool saturated')); // load shedding
      this.#queue.push(task);
    });
  }
}
```

**Production version:** use **Piscina**, which adds task cancellation, timeouts, resource limits, idle shutdown and metrics. The interview value is showing you understand the moving parts: fixed pool, bounded queue, failure replacement, correlation IDs.

### Q3 \[A\] What does postMessage cost, and how do you avoid copying?

`postMessage` uses the **structured clone** algorithm: data is serialised and copied. Sending a 50 MB object to a worker for 2 ms of work can cost more than the work.

- **Transfer** an `ArrayBuffer` instead of copying it: `worker.postMessage(buf, [buf.buffer])` moves ownership (the sender's view becomes empty).
- **Share** memory with `SharedArrayBuffer` plus `Atomics` for coordination (counters, ring buffers). Correct concurrent code is hard; use it only when profiling shows copying is the bottleneck.
- Functions, class instances' prototypes and sockets cannot be cloned.

```js
const shared = new SharedArrayBuffer(4);
const counter = new Int32Array(shared);
// in any thread:
Atomics.add(counter, 0, 1);          // atomic increment, no lost updates
Atomics.wait(counter, 0, 0);          // block until value changes (never on the main thread of a server)
```

## Child processes

### Q4 \[S\] spawn vs exec vs execFile vs fork

| API | Shell? | Output | Use for |
| --- | --- | --- | --- |
| `spawn(cmd, args)` | no (unless `shell: true`) | streams | long-running processes, large output |
| `execFile(file, args)` | no | buffered (`maxBuffer`, default 1 MB) | short commands with arguments |
| `exec(commandString)` | **yes** | buffered | almost never with user input |
| `fork(modulePath)` | no | IPC channel to a Node child | isolating Node code |

**Security:** `exec` passes one string to `/bin/sh`, so building that string from user input, such as `exec('convert ' + userFile + ' out.png')`, is command injection: a file named `x.png; rm -rf ~` runs the second command. Use `execFile` / `spawn` with an argument array, validate inputs, and never set `shell: true` with user data (Part 9).

**Reliability:** always handle `error` (binary missing) and `close` (exit code); kill children on timeout (`{ timeout, killSignal }` or an `AbortSignal`); consume or ignore stdout and stderr, or a full pipe buffer will hang the child.

## Cluster and multi-core servers

### Q5 \[S\] Cluster, PM2, or multiple containers?

- `node:cluster` forks N workers that share a listening port; the primary distributes connections (round-robin by default on Linux).
- **PM2** wraps cluster mode with restarts, log management and zero-downtime reloads on a VM.
- **Containers:** the common modern answer is *one process per container* and let the orchestrator run N replicas behind a load balancer. Simpler health checks, per-replica resource limits, crash isolation, and scaling across machines, not just cores.

**Senior signal:** choose cluster/PM2 when you own a VM and want all its cores; choose one process per container in Kubernetes or ECS. Do not run cluster *inside* a container that already has a CPU limit of 1.

**Shared-state trap:** with any of these, in-memory state (sessions, rate-limit counters, caches, WebSocket subscriptions) is per process. Move shared state to Redis or the database.

## Signals, exit codes, graceful shutdown

### Q6 \[A\] Process lifecycle: signals and exit codes you must know

- `SIGTERM`: polite stop request (Kubernetes, Docker, systemd). Handle it with graceful shutdown.
- `SIGINT`: Ctrl-C. Handle the same way in development.
- `SIGKILL` (exit 137) and `SIGSTOP`: cannot be caught.
- Exit codes: `0` success; `1` uncaught exception; `130` after SIGINT; `137` killed (often OOM); `143` after SIGTERM if you did not handle it.
- **PID 1 in containers:** a Node process running as PID 1 does not get default signal handling from an init system; `CMD ["node", "server.js"]` (exec form) is needed so signals reach Node, and `npm start` as PID 1 may not forward them. Use `--init` / tini or handle signals explicitly.

### Q7 \[S\] Implement graceful shutdown.

```js
import { setTimeout as sleep } from 'node:timers/promises';

let shuttingDown = false;

app.get('/healthz/ready', (req, res) => res.status(shuttingDown ? 503 : 200).end());

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  logger.info({ signal }, 'shutting down');
  const force = setTimeout(() => { logger.error('forced exit'); process.exit(1); }, 25_000);
  force.unref();

  await sleep(5_000);                     // let the LB see readiness fail and stop routing here
  await new Promise((r) => server.close(r)); // stop accepting; wait for in-flight requests
  server.closeIdleConnections?.();        // drop idle keep-alive sockets (Node 18.2+)
  await queueWorker.close();              // finish current jobs, take no new ones
  await db.end();                         // close pools last: in-flight work may still need them
  await logger.flush?.();
  process.exit(0);
}
process.once('SIGTERM', shutdown);
process.once('SIGINT', shutdown);
```

**Order matters:** fail readiness, wait for the load balancer, stop accepting, drain in-flight work, close resources, exit. Keep the total under the orchestrator's grace period (Kubernetes default 30 s). Part 12 covers zero-downtime deploys.

## Tricky & trap questions (Part 7)

### T1 \[A\] "Worker threads share memory, so module-level caches are shared."

No. Each worker loads its own copy of every module with its own heap. Only `SharedArrayBuffer` memory (and OS-level resources) is shared. A cache in the main thread is invisible to workers.

### T2 \[S\] Two cluster workers each allow 100 requests per minute per IP. What is the real limit?

200 (or N x 100 with N workers), and it varies with how connections are distributed. Rate limiting must use shared state (Redis) or happen at the gateway.

### T3 \[A\] Why does this child process hang forever?

```js
const child = spawn('generate-report', ['--all']);
child.on('close', (code) => console.log('done', code));
```

The child writes a lot to stdout, nobody reads it, the pipe buffer fills (about 64 KB on Linux) and the child blocks on write. Consume `child.stdout` (or pass `stdio: 'ignore'` / `'inherit'`).

## Debugging challenge (Part 7)

### D1 \[S\] Image resizing makes the whole API slow

**Symptoms:** when users upload photos, every endpoint's p99 jumps to seconds; event loop delay spikes match uploads.

**Root cause:** resizing with a pure-JS library on the main thread (CPU-bound for 300 ms per image).

**Fix options, by effort:** use `sharp` (native libvips, runs off the main thread); or a worker pool (Q2) with a bounded queue that returns 503 when full; or move resizing to an async job processed by a separate worker service (Part 10), returning `202 Accepted` with a status URL. Measure event loop delay before and after.

## Cheat sheet (Part 7)

1. Pool = Node's internal threads; worker\_threads = your JS in parallel; child\_process = other programs; cluster = copies of your server.
2. Workers do not share module state; messages are copied unless transferred or shared.
3. Use a fixed worker pool with a bounded queue (Piscina in production).
4. Never `exec` user input; use `execFile` / `spawn` with argument arrays.
5. In containers: one process per container, scale replicas; on VMs: cluster or PM2.
6. In-memory state is per process; share through Redis or the database.
7. Graceful shutdown: fail readiness, wait, stop accepting, drain, close pools, exit within the grace period.

# Part 8 — Error Handling & Reliability

## Errors in Node

### Q1 \[I\] Synchronous, callback, promise and event errors: how is each caught?

| Source | How it surfaces | How you catch it |
| --- | --- | --- |
| Synchronous code | thrown exception | `try/catch` around the call |
| Error-first callback | `cb(err)` | check `err` first (Part 2, Q15a) |
| Promise / async function | rejection | `await` inside `try/catch`, or `.catch` |
| EventEmitter / stream | `'error'` event | `on('error')`, or `pipeline` / `events.once` |
| Thrown inside a callback or timer | uncaught exception | only inside that callback; the outer `try` is gone (Part 2, T4) |

**Rule:** an `'error'` event with no listener throws and crashes the process. Every stream, socket, child process and emitter you create needs an error path.

### Q2 \[A\] Operational errors vs programmer errors

- **Operational errors** are expected failures of a correct program: network timeouts, a missing file, invalid user input, a full disk, a 503 from a dependency. Handle them: retry, fall back, return 4xx/5xx, alert.
- **Programmer errors** are bugs: `undefined is not a function`, a wrong argument type, a broken invariant. You cannot handle a bug into correctness. Log it with full context, fail the request, and if state may be corrupt, crash and restart.

**Why it matters:** catching everything and continuing turns programmer errors into silent data corruption. Catching nothing turns every timeout into a crash.

### Q3 \[A\] Design custom errors that are useful in production.

```ts
export class AppError extends Error {
  constructor(message: string, readonly opts: {
    code: string;              // stable, machine-readable: 'ORDER_NOT_FOUND'
    status?: number;           // HTTP mapping at the edge
    expose?: boolean;          // safe to show the client?
    cause?: unknown;           // the original error (ES2022 error cause)
    details?: Record<string, unknown>;
  }) {
    super(message, { cause: opts.cause });
    this.name = new.target.name;
  }
}
export class NotFoundError extends AppError {
  constructor(what: string, id: string) {
    super(`${what} ${id} not found`, { code: `${what.toUpperCase()}_NOT_FOUND`, status: 404, expose: true });
  }
}

// wrapping keeps the root cause for logs
try { await payments.charge(order); }
catch (err) { throw new AppError('Payment failed', { code: 'PAYMENT_FAILED', status: 502, cause: err }); }
```

**Edge mapping:** one error middleware turns `AppError` into a problem-details response; anything that is not an `AppError` becomes a generic 500 with a request ID, and the full error (with `cause` chain) goes to logs only.

**Common mistakes:** throwing strings (no stack); matching on `err.message` (breaks on rewording; use `code`); losing the original error when wrapping; leaking stack traces or SQL to clients.

### Q4 \[S\] Why is catching an error not the same as recovering safely?

```js
async function transfer(from, to, amount) {
  await accounts.debit(from, amount);
  try {
    await accounts.credit(to, amount);
  } catch (err) {
    logger.error({ err }, 'credit failed');   // "handled"
  }
}
```

The error was caught, but money left one account and never arrived. Recovery means restoring an invariant: a database transaction around both writes, a compensating action (refund the debit), or a durable record that a reconciler will finish. Ask of every `catch`: **what state is the system in now, and who fixes it?**

### Q5 \[S\] uncaughtException and unhandledRejection: what should a server do?

Log with full context, stop accepting traffic, try to finish in-flight requests briefly, flush logs, exit non-zero, and let the supervisor restart you (Part 2, Q18). Do not continue serving: the error escaped every boundary, so you do not know what it left half-done. For Express 4, async handler rejections are not forwarded to the error middleware automatically (Express 5 does this); wrap handlers or upgrade.

## Resilience patterns

### Q6 \[A\] Timeouts, retries, backoff and jitter: how do they fit together?

- **Timeout** every remote call; derive from latency data; propagate a **deadline** so inner calls get the remaining budget, not a fresh 30 s each.
- **Retry** only transient failures and only idempotent operations (or with idempotency keys), a small number of times, at **one** layer (Part 2, Q26a).
- **Exponential backoff with full jitter** (`random(0, min(cap, base x 2^attempt))`) spreads retries so recovering services are not hit in waves.
- **Retry budget:** cap retries as a fraction of normal traffic so an outage does not triple load.

### Q7 \[S\] Implement a circuit breaker, and explain its states.

A circuit breaker stops calling a dependency that is clearly failing, so you fail fast instead of piling up timeouts, and gives the dependency room to recover.

```ts
type State = 'closed' | 'open' | 'half-open';

export class CircuitBreaker {
  private state: State = 'closed';
  private failures = 0;
  private openedAt = 0;
  private probing = false;
  constructor(private opts = { failureThreshold: 5, resetAfterMs: 10_000 }) {}

  async exec<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === 'open') {
      if (Date.now() - this.openedAt < this.opts.resetAfterMs) throw new AppError('Circuit open', { code: 'CIRCUIT_OPEN', status: 503 });
      this.state = 'half-open';
    }
    if (this.state === 'half-open') {
      if (this.probing) throw new AppError('Circuit half-open', { code: 'CIRCUIT_OPEN', status: 503 });
      this.probing = true;                      // allow exactly one trial call
    }
    try {
      const result = await fn();
      this.state = 'closed'; this.failures = 0;
      return result;
    } catch (err) {
      if (this.state === 'half-open' || ++this.failures >= this.opts.failureThreshold) {
        this.state = 'open'; this.openedAt = Date.now();
      }
      throw err;
    } finally {
      this.probing = false;
    }
  }
}
```

**States:** **closed** (calls flow, failures counted) → **open** after a threshold (calls rejected immediately) → **half-open** after a cool-down (one trial call) → closed on success, open again on failure.

**Production version:** `opossum`, or a service mesh (Envoy outlier detection). Count failures over a rolling window and as an error *rate*, not a raw count; decide which errors count (timeouts and 5xx yes, 4xx no); expose breaker state as a metric; and keep a fallback (cached data, degraded response) for when it is open. Part 14 adds tests.

### Q8 \[S\] Bulkheads, load shedding and graceful degradation

- **Bulkhead:** isolate resources so one slow dependency cannot exhaust everything. Separate connection pools or concurrency limits per downstream; a reporting query cannot take every DB connection that checkout needs.
- **Load shedding:** when overloaded, reject early (503 with `Retry-After`) rather than accepting work you will time out on. Signal: event loop delay, queue length, or pool wait time.
- **Graceful degradation:** serve a reduced experience: cached recommendations, "prices may be stale", search without personalisation. Decide in advance which features are critical.

### Q9 \[S\] Dead-letter queues and failure recovery for background work

A job that fails repeatedly (bad data, a permanent error) must not block or loop forever. After N attempts with backoff, move it to a **dead-letter queue** with the error and attempt history; alert on DLQ growth; provide tooling to inspect, fix and replay. Combine with idempotent consumers so replays are safe (Part 10).

## Tricky & trap questions (Part 8)

### T1 \[A\] What does the caller see?

```js
async function load() {
  try { return fetchConfig(); }
  catch { return DEFAULTS; }
  finally { console.log('done'); }
}
```

If `fetchConfig()` rejects, `load()` rejects too: the promise was returned, not awaited, so `catch` never saw it. And `done` logs before the fetch settles. `return await` fixes both (Part 2, Q13).

### T2 \[A\] Is `err instanceof MyError` reliable?

Not across module copies (two versions of the package, Part 4, T1), worker threads or realms. Prefer a `code` property or a type-guard function (`isAppError(err) => err?.code !== undefined && 'status' in err`).

### T3 \[S\] "We retry every failed request 3 times at the gateway, the service, and the client SDK."

One user action becomes up to 64 calls on the bottom service (4 x 4 x 4) during an outage: a self-inflicted DDoS. Retry at one layer with a budget.

## Debugging challenge (Part 8)

### D1 \[S\] A downstream outage takes the whole API down

**Situation:** the recommendations service starts timing out (30 s). Within minutes, checkout and login (which do not need recommendations) also fail.

**Root cause:** product pages call recommendations with a 30 s timeout and 3 retries; requests pile up holding DB connections opened earlier in the handler; the shared pool is exhausted; every endpoint that needs the DB now waits. A cascading failure through shared resources.

**Fix:** a 300 ms timeout and no retries for a non-critical call; a circuit breaker with a cached fallback; release DB connections before calling downstream services; a separate concurrency limit (bulkhead) for recommendation calls; load shedding on pool wait time. Then a game day that injects latency into recommendations to prove the fix.

## Cheat sheet (Part 8)

1. Every emitter and stream needs an error path; unhandled `'error'` crashes.
2. Handle operational errors; crash and restart on programmer errors.
3. Custom errors carry `code`, `status`, `expose` and `cause`; map them at one edge.
4. Catching is not recovering: restore the invariant (transaction, compensation, reconciler).
5. Timeout everything, propagate deadlines, retry once at one layer with jitter.
6. Circuit breakers fail fast; bulkheads contain; load shedding protects; degradation keeps core flows alive.
7. Repeatedly failing jobs go to a DLQ; consumers must be idempotent.

| Q2 | Give an error that could be either kind | `TypeError: cannot read 'id' of null` from an API that sometimes returns null: a bug in your handling of an operational case | crashing on every 4xx from a dependency |
| Q3 | How do you serialise `cause` chains in logs? | pino/serializers walk `err.cause`; include `code` at each level | logging `err.message` only |
| Q4 | Who reconciles after a partial failure? | an outbox/saga or a scheduled reconciler with alerts on drift | a `console.error` and hope |
| Q5 | Why not keep serving after `uncaughtException`? | unknown state: half-written caches, held locks, broken invariants | `process.on('uncaughtException', log)` and continue |
| Q6 | How do you set the timeout value? | from the dependency's p99 under load plus margin, within the caller's remaining deadline | the same 30 s everywhere |
| Q7 | What counts as a failure for the breaker? | timeouts, connection errors, 5xx, 429; not 4xx client errors | opening the breaker on 404s |
| Q8 | How do you pick what to shed? | by priority: health checks and critical paths last; cheap rejections before expensive work | shedding after doing the expensive part |
| Q9 | How do you replay from a DLQ safely? | idempotent consumers, small batches, after fixing the root cause | bulk replay before the bug is fixed |

**Theory vs production:** theory is knowing the patterns' names. Production is choosing numbers from data (timeouts, thresholds, budgets), deciding which errors count, exposing state as metrics, and testing the failure paths with fault injection.

### More trap questions

#### T4 \[A\] Does this error reach the Express error handler (Express 4)?

```js
app.get('/u/:id', async (req, res) => {
  const user = await users.get(req.params.id);   // rejects
  res.json(user);
});
```

**No** in Express 4: the rejected promise is not passed to `next`, so it becomes an unhandled rejection (crash on Node 15+) and the request hangs until the client times out. Express 5 forwards rejections to error middleware. On Express 4, wrap: `const wrap = (fn) => (req, res, next) => fn(req, res, next).catch(next);`.

#### T5 \[A\] What does `finally` do to a returned value?

```js
function f() { try { return 'try'; } finally { return 'finally'; } }
function g() { try { throw new Error('x'); } finally { return 'swallowed'; } }
```

`f()` returns `'finally'`; `g()` returns `'swallowed'` and the error disappears. A `return` in `finally` overrides both returns and throws. Never return from `finally`.

#### T6 \[S\] "We catch errors in each microservice and return 200 with `{ ok: false }` so the gateway doesn't retry."

That breaks monitoring (error rates look like zero), caching (proxies may cache the 200), client retries and circuit breakers. Return proper status codes and control retries with idempotency and retry policies.

### Code output questions

#### O1 \[A\] Predict the output

```js
async function a() { throw new Error('A'); }
async function b() { try { await a(); } catch (e) { throw new Error('B', { cause: e }); } }
b().catch((e) => console.log(e.message, '<-', e.cause.message));
```

**Output:** `B <- A`. The cause chain is preserved; deterministic.

#### O2 \[A\] Predict the output

```js
const results = await Promise.allSettled([
  Promise.resolve(1),
  Promise.reject(new Error('no')),
  new Promise((r) => setTimeout(() => r(3), 10)),
]);
console.log(results.map((r) => r.status));
```

**Output:** `[ 'fulfilled', 'rejected', 'fulfilled' ]`. `allSettled` never rejects; the rejection is not unhandled because `allSettled` attached a handler.

#### O3 \[A\] Predict the behaviour

```js

```

**Behaviour:** `emit('error')` with no listener throws the error synchronously; `after` never prints and the process crashes (uncaught). Add `e.on('error', handler)` or use `captureRejections` for async listeners.

# Part 9 — Security

Exploit scenarios below are described at the level needed to recognise and prevent them.

## Authentication and sessions

### Q1 \[I\] Authentication vs authorisation, and where each check belongs

**Authentication** proves who the caller is (password, token, mTLS). **Authorisation** decides what they may do. Most real breaches are authorisation bugs: an endpoint checks that you are logged in but not that the order belongs to you (IDOR / broken object-level authorisation, OWASP API #1).

```js
// Vulnerable: any logged-in user can read any order
const order = await orders.findById(req.params.id);
// Fixed: scope the query to the caller (and the tenant)
const order2 = await orders.findOne({ id: req.params.id, userId: req.user.id, tenantId: req.user.tenantId });
if (!order2) throw new NotFoundError('order', req.params.id); // 404, not 403: do not confirm existence
```

Enforce authorisation in the service layer (or the query), not only in route middleware, and test it with a second user's credentials.

### Q2 \[A\] How should passwords be stored?

Never encrypted, never with a fast hash (SHA-256, MD5). Use a slow, salted, memory-hard **password hash**: **Argon2id** (preferred), scrypt, or bcrypt (cost 12 or more; note bcrypt truncates input at 72 bytes).

```js
import argon2 from 'argon2';
const hash = await argon2.hash(password, { type: argon2.argon2id });   // salt included in the output
const ok = await argon2.verify(hash, attempt);
```

Hashing runs off the main thread in these libraries, but at login peaks it saturates the thread pool or CPU (Part 3, Q12): rate-limit login and size capacity for it. Also: rehash on login when parameters change; check passwords against breached-password lists; never log request bodies on auth routes.

### Q3 \[S\] JWT: what goes wrong?

- **Algorithm confusion:** accepting `alg: none`, or verifying an RS256 token with the public key as an HS256 secret. Always pin the expected algorithm: `jwt.verify(token, key, { algorithms: ['RS256'], issuer, audience })`.
- **No revocation:** a stateless JWT is valid until it expires. Keep access tokens short (5–15 minutes) and use rotating refresh tokens stored server-side so you can revoke them.
- **Storing JWTs in `localStorage`:** readable by any XSS. Prefer `HttpOnly` cookies for browser apps (then you need CSRF protection).
- **Putting secrets or PII in the payload:** it is only base64-encoded, not encrypted.
- **Skipping `exp`, `aud`, `iss` checks**, or accepting tokens issued for another service.

**Senior answer:** for a browser app on one domain, server-side sessions in `HttpOnly` cookies are often simpler and more revocable than JWTs. Use JWTs where you need stateless verification across services, and keep them short-lived.

### Q4 \[A\] Cookie security and session management

```js
res.cookie('sid', sessionId, {
  httpOnly: true,          // not readable by JavaScript (limits XSS impact)
  secure: true,            // HTTPS only
  sameSite: 'lax',         // blocks most cross-site sends (CSRF defence); 'strict' for sensitive apps
  path: '/',
  maxAge: 8 * 60 * 60 * 1000,
});
```

Regenerate the session ID on login (prevents session fixation), invalidate it on logout and password change, store sessions server-side (Redis) with idle and absolute timeouts, and use the `__Host-` cookie prefix to prevent subdomain overrides.

### Q5 \[A\] CSRF and XSS: what are they and how do you prevent them?

- **CSRF:** another site makes the victim's browser send an authenticated request (cookies attach automatically). Defences: `SameSite` cookies, CSRF tokens (synchronizer or double-submit) for state-changing requests, checking `Origin`/`Sec-Fetch-Site`, never changing state on `GET`. Token-in-header APIs (no cookies) are not CSRF-prone.
- **XSS:** attacker-controlled data executes as script in your pages. Defences: context-aware output encoding (template engines escape by default; never build HTML with string concatenation), sanitise HTML you must allow (DOMPurify), a strict **Content-Security-Policy**, and `HttpOnly` cookies to limit the damage.

## Injection

### Q6 \[I\] SQL and NoSQL injection

```js
// SQL injection: never interpolate
await db.query(`SELECT * FROM users WHERE email = '${email}'`);
// Parameterised: the driver sends data separately from the query text
await db.query('SELECT * FROM users WHERE email = $1', [email]);
```

ORMs are safe for normal queries but have raw-query escape hatches (`sequelize.query`, `knex.raw`, `$queryRawUnsafe`) where the same rule applies. Dynamic identifiers (sort columns) cannot be parameters: map them through an allow-list.

**NoSQL injection (MongoDB):** a JSON body `{ "email": "a@b.com", "password": { "$ne": null } }` turns an equality check into "password is not null" and bypasses login. Validate types with a schema (password must be a string) and strip `$`-prefixed keys (`express-mongo-sanitize`, or Mongoose `sanitizeFilter`).

### Q7 \[A\] Prototype pollution

```js
// Vulnerable deep merge of user JSON
function merge(target, src) {
  for (const key in src) {
    if (typeof src[key] === 'object') merge(target[key] ??= {}, src[key]);
    else target[key] = src[key];
  }
}
merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
console.log({}.isAdmin); // true for every object in the process
```

**Impact:** authorisation bypasses (`if (user.isAdmin)`), and in some libraries remote code execution through polluted options. **Fixes:** reject `__proto__`, `constructor`, `prototype` keys; use `Object.create(null)` or `Map` for user-keyed data; validate input against a schema with `additionalProperties: false`; keep merge/query-string libraries patched; `node --disable-proto=delete` removes the `__proto__` accessor.

### Q8 \[A\] Command injection and path traversal

Covered in Part 7 (Q4: use `execFile`/`spawn` with argument arrays, never `exec` with user data) and Part 5 (Q10: resolve paths and check the root prefix with a separator; prefer generated file IDs).

### Q9 \[S\] SSRF: what is it and how do you defend against it?

Server-side request forgery: your server fetches a URL the user controls (webhooks, image-by-URL, PDF renderers), and the attacker points it at internal targets: `http://169.254.169.254/` (cloud metadata with credentials), `http://localhost:6379` (Redis), internal admin APIs.

**Defences, together:**

1. Allow-list destinations where possible (known webhook hosts).
2. Resolve the hostname yourself and block private, loopback, link-local and metadata ranges (IPv4 and IPv6) — then connect to **that resolved IP** so DNS rebinding cannot swap it between check and use.
3. Disable or re-validate redirects (a public URL can 302 to an internal one).
4. Enforce timeouts and response size limits.
5. Network controls: egress firewall, IMDSv2 on AWS (requires a session token), run fetchers in an isolated network segment.

### Q10 \[E\] HTTP request smuggling, conceptually

When a front-end proxy and the back-end server disagree about where one request ends (conflicting `Content-Length` and `Transfer-Encoding` headers), an attacker can hide a second request inside the first and have it executed with another user's connection. Defences: keep Node and proxies patched (llhttp is strict by default; avoid `insecureHTTPParser`), normalise or reject ambiguous requests at the edge, and prefer HTTP/2 end to end where possible.

## Denial of service, ReDoS, rate limiting

### Q11 \[A\] What is ReDoS?

A regular expression with nested or overlapping quantifiers backtracks exponentially on crafted input, blocking the event loop for seconds or minutes.

```js
const EMAIL = /^([a-zA-Z0-9]+)*@example\.com$/;     // nested quantifier: catastrophic backtracking
EMAIL.test('a'.repeat(30) + '!');                   // takes a very long time on one thread
```

**Defences:** avoid nested quantifiers; cap input length before matching; use vetted validators; lint with `eslint-plugin-regexp` / `safe-regex`; for user-supplied patterns, use a linear-time engine (RE2 via `re2`).

### Q12 \[S\] Rate limiting and brute-force protection

- Limit by user/account **and** IP (credential stuffing uses many IPs; one IP may be a company NAT).
- Store counters centrally (Redis) so limits hold across replicas; algorithms: fixed window (simple, bursty at boundaries), sliding window, or token bucket (allows controlled bursts). Part 14 implements one.
- Login: progressive delays and lockout with care (lockouts can be abused to deny service), CAPTCHA after failures, MFA.
- Return 429 with `Retry-After`; do it at the gateway for coarse limits and in the app for business limits.

### Q13 \[A\] Other DoS vectors in Node

Large or deeply nested JSON bodies (limit size; `JSON.parse` of 50 MB blocks the loop), huge multipart uploads, slowloris connections (`headersTimeout`, `requestTimeout`), zip bombs (limit decompressed size), unbounded queries (`limit` caps), expensive GraphQL queries (depth and cost limits), and algorithmic hot spots (sorting or regex on user-sized input).

## Secrets, supply chain, logging, headers

### Q14 \[A\] Timing attacks

```js
if (req.headers['x-signature'] === expected) { /* ... */ }   // leaks how many leading chars matched

import { timingSafeEqual, createHmac } from 'node:crypto';
const a = Buffer.from(req.headers['x-signature'] ?? '', 'hex');
const b = createHmac('sha256', secret).update(rawBody).digest();
const valid = a.length === b.length && timingSafeEqual(a, b);
```

Also hash a dummy password when the user does not exist so login time does not reveal valid emails (Part 2, D1).

### Q15 \[S\] Secrets management and secure logging

- Secrets come from a secret manager (AWS Secrets Manager, Vault, Kubernetes Secrets with encryption at rest), never from the repository or Docker image layers; rotate them, prefer short-lived credentials (IAM roles, workload identity).
- **Log redaction:** configure the logger to remove `authorization`, `cookie`, `password`, tokens and card data (`pino` `redact` paths); never log full request bodies on auth or payment routes; treat heap snapshots and diagnostic reports as secret-bearing.
- **PII:** log user IDs, not emails or names; define retention; support deletion requests.

### Q16 \[S\] Dependency and supply-chain risk

Attacks include typosquatting, compromised maintainer accounts publishing malicious versions, malicious `postinstall` scripts, and dependency confusion (a public package with your private package's name). Defences: lockfiles and `npm ci`; `--ignore-scripts` with an allow-list; scoped private packages with registry configuration that pins the scope; automated advisories (`npm audit`, OSV, Socket, Snyk); verifying provenance (`npm audit signatures`); minimal dependencies; and a fast patch-and-deploy path.

### Q17 \[I\] Security headers and TLS

`helmet` sets sensible defaults: `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `frame-ancestors` (clickjacking). Remove `X-Powered-By`. Terminate TLS with modern versions (TLS 1.2+, prefer 1.3) at the proxy, and use TLS (or mTLS) for internal traffic in zero-trust networks.

## Tricky & trap questions (Part 9)

### T1 \[A\] "We validate input on the frontend."

Attackers do not use your frontend. Validate on the server; frontend validation is for user experience.

### T2 \[A\] Is `JSON.parse` of user input safe?

It does not execute code, but the result can carry `__proto__` keys (prototype pollution once merged), `$` operators (NoSQL injection), huge sizes (DoS) and wrong types. Parse, then validate against a schema before use.

### T3 \[S\] Why is `res.redirect(req.query.next)` a problem?

Open redirect: `?next=https://evil.example/login` lends your domain's trust to a phishing page, and can leak OAuth codes. Only allow relative paths or an allow-list of hosts.

### T4 \[S\] "Our internal service has no auth; it is only reachable inside the VPC."

SSRF, a compromised pod or a misconfigured security group makes it reachable. Use service-to-service authentication (mTLS, signed tokens) and least privilege.

## Debugging challenge (Part 9): security incident handling

### D1 \[S\] An API key appears in a public GitHub commit

1. **Revoke and rotate** the key immediately; deleting the commit is not enough (it is already scraped).
2. **Assess:** audit logs for the key's usage since the commit time; check for data access or resource creation.
3. **Contain:** block suspicious IPs or accounts, revoke sessions if user data was exposed.
4. **Fix the cause:** pre-commit secret scanning (gitleaks), push protection, secrets only from a manager.
5. **Communicate** per policy and law if personal data was affected; write a blameless postmortem.

## Cheat sheet (Part 9)

1. Most breaches are authorisation bugs: scope every query to the caller and tenant.
2. Argon2id/bcrypt for passwords; never log auth bodies.
3. Pin JWT algorithms; short-lived access tokens; revocable refresh tokens; consider cookies + sessions.
4. `HttpOnly`, `Secure`, `SameSite` cookies; CSRF tokens for cookie-based state changes.
5. Parameterise SQL; validate types to stop NoSQL operators; reject `__proto__` keys.
6. SSRF: allow-list, block private ranges on the resolved IP, no blind redirects.
7. Cap input sizes; avoid catastrophic regex; rate-limit with shared state.
8. Constant-time comparisons for secrets and signatures.
9. Secrets from a manager, rotated; redact logs; lock down the supply chain.

### More trap questions

#### T5 \[A\] Is this safe?

```js
const token = crypto.randomBytes(16).toString('hex');   // password reset token
await db.query('INSERT INTO resets (user_id, token) VALUES ($1, $2)', [user.id, token]);
```

The randomness is fine, but the token is stored in plain text: anyone with database read access can reset any account. Store a **hash** of the token (SHA-256 is fine for high-entropy tokens), expire it (15–60 minutes), make it single-use, and invalidate it on password change.

# Part 10 — Databases, Caching & Distributed Systems

## Data access from Node

### Q1 \[A\] How does database access interact with Node's concurrency model?

Thousands of requests can be in flight on one thread, but a PostgreSQL connection runs **one query at a time**, and the database has a hard connection limit (often 100–500). The pool is therefore the real concurrency limit for anything that touches the database.

```js
import pg from 'pg';
export const pool = new pg.Pool({
  max: 10,                          // per process; total = max x replicas x processes
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 2_000,   // fail fast instead of queueing forever
  statement_timeout: 5_000,         // server-side cap per statement
});
pool.on('error', (err) => logger.error({ err }, 'idle client error'));  // otherwise it crashes the process
```

**Sizing:** 20 pods x 10 connections = 200 connections; add a deploy surge and you exceed the database limit. Use a pooler (PgBouncer in transaction mode, RDS Proxy) when replicas are many. Bigger pools are not faster: past roughly a few times the database's CPU cores, extra connections just add contention.

### Q2 \[A\] Write a reusable transaction helper.

```js
export async function withTransaction(pool, fn, { isolation = 'READ COMMITTED' } = {}) {
  const client = await pool.connect();
  try {
    await client.query(`BEGIN ISOLATION LEVEL ${isolation}`);   // isolation comes from code, never user input
    const result = await fn(client);                             // every query inside uses this client
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK').catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}
```

**Rules:** keep transactions short; never call slow external services inside one (it holds locks and a connection for the whole call); every query must use the transaction's client, not the pool (a classic bug: `pool.query` inside the callback runs outside the transaction).

### Q3 \[S\] Isolation levels and the anomalies they prevent

| Level (PostgreSQL) | Prevents | Still allows |
| --- | --- | --- |
| Read Committed (default) | dirty reads | non-repeatable reads, lost updates with read-modify-write, write skew |
| Repeatable Read (snapshot) | non-repeatable reads, phantom reads in PG | write skew; may abort with serialization errors |
| Serializable | all of the above | nothing, but transactions can fail and must be **retried** |

**Practical guidance:** most apps run Read Committed and protect invariants with atomic updates (`UPDATE ... SET balance = balance - $1 WHERE id = $2 AND balance >= $1`), row locks (`SELECT ... FOR UPDATE`), unique constraints, or optimistic concurrency. Use Serializable for complex invariants and wrap it in a retry loop for serialization failures (SQLSTATE `40001`).

### Q4 \[A\] Optimistic vs pessimistic concurrency

```sql
-- Optimistic: a version column; 0 rows updated means someone else changed it
UPDATE documents SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;
```

- **Optimistic:** no locks; detect conflicts at write time; return 409 or retry. Good when conflicts are rare (user edits, admin screens).
- **Pessimistic:** `SELECT ... FOR UPDATE` locks the row until commit. Good for hot, high-contention rows (inventory, wallet balance) but watch lock waits and deadlocks; lock rows in a consistent order and set `lock_timeout`.

### Q5 \[A\] N+1 queries, indexing and pagination

```js
// N+1: one query for orders, then one per order for its customer
const orders = await db.query('SELECT * FROM orders LIMIT 50');
for (const o of orders.rows) o.customer = (await db.query('SELECT * FROM customers WHERE id = $1', [o.customer_id])).rows[0];

// Fix: one join, or one batched IN query (DataLoader batches this in GraphQL)
const rows = await db.query(`SELECT o.*, c.name AS customer_name FROM orders o JOIN customers c ON c.id = o.customer_id LIMIT 50`);
```

- **Indexes** support your `WHERE`, `JOIN` and `ORDER BY` patterns; composite index column order matters (equality columns first, then range/sort). Check plans with `EXPLAIN (ANALYZE, BUFFERS)`. Every index slows writes and uses memory.
- **Pagination:** keyset (`WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 50`) stays fast at any depth; `OFFSET 100000` scans and discards 100,000 rows.

### Q6 \[S\] SQL vs NoSQL, ORM vs query builder

- **PostgreSQL** by default: transactions, constraints, joins, JSONB for flexible fields. **MongoDB** when the data is naturally document-shaped, accessed by key, and schema evolves quickly; you give up some cross-document guarantees (multi-document transactions exist but cost more). Pick by access patterns and consistency needs, not hype.
- **ORM (Prisma, TypeORM, Sequelize):** productivity, migrations, types; risks of hidden N+1 and inefficient SQL. **Query builder (Kysely, Knex):** explicit SQL with type safety. **Raw SQL:** full control. Many teams use an ORM for CRUD and raw SQL for hot or complex queries.

### Q7 \[S\] Migrations without downtime

Use **expand and contract**: (1) add the new column or table (nullable, no locking rewrite); (2) deploy code that writes both old and new; (3) backfill in batches; (4) switch reads to new; (5) stop writing old; (6) drop old in a later release. Avoid long locks: `CREATE INDEX CONCURRENTLY`, add constraints `NOT VALID` then `VALIDATE`, set `lock_timeout` on migrations. Run migrations as a separate deploy step, not on every app start across 20 replicas.

### Q8 \[S\] Read replicas, connection exhaustion and database failures

- **Replicas** lag: a user who just wrote may not see their write on a replica (read-your-writes). Route reads that follow writes to the primary, or use a session-level "recently wrote" flag.
- **Connection exhaustion** symptoms: requests waiting on `pool.connect`, timeouts across all endpoints, DB showing many idle-in-transaction connections (a leaked client or long transaction). Alert on pool wait time and idle-in-transaction count.
- **Failover:** connections break; the pool must discard broken clients; retry idempotent reads once; writes need idempotency keys.

## Caching

### Q9 \[A\] Cache-aside, write-through, TTLs and invalidation

```js
async function getProduct(id) {
  const key = `product:v2:${id}`;                    // version keys to invalidate by deploy
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);
  const product = await db.products.find(id);
  if (product) await redis.set(key, JSON.stringify(product), 'EX', 300 + Math.floor(Math.random() * 60)); // jittered TTL
  return product;
}
// on update: write the DB, then delete the key (not update it) to avoid racing writers
```

- **Cache-aside** (above): simple, the cache can be stale until TTL or deletion.
- **Write-through:** write cache and DB together; fresher reads, more write latency.
- **Write-behind:** write cache, flush later; fast, risks data loss.
- **Invalidation:** delete on write, short TTLs, versioned keys. Cache only what you can tolerate being stale, and never cache authorisation decisions longer than you can tolerate a revoked user keeping access.

### Q10 \[S\] Cache stampede: what is it and how do you prevent it?

A hot key expires and 5,000 concurrent requests all miss and hit the database at once. Prevention: **request coalescing** (one in-flight load per key per process, Part 14), a distributed lock so one process recomputes, **stale-while-revalidate** (serve the old value while one request refreshes), probabilistic early refresh, and jittered TTLs so keys do not expire together.

### Q11 \[S\] Distributed locks: when and how?

A Redis lock (`SET key token NX PX 30000`, release with a compare-and-delete Lua script) prevents two workers doing the same job at the same time. It is **not** a correctness guarantee: a process can pause (GC, network) past the lock's TTL while still believing it holds the lock. For correctness, add a **fencing token** (a monotonically increasing number checked by the resource being written), or rely on database constraints and transactions. Redlock is debated for exactly this reason.

## Messaging and distributed systems

### Q12 \[A\] BullMQ vs RabbitMQ vs Kafka

|  | BullMQ (Redis) | RabbitMQ | Kafka |
| --- | --- | --- | --- |
| Model | job queue | message broker (queues, exchanges, routing) | distributed append-only log |
| Ordering | per queue, mostly | per queue | per partition |
| Replay | no (jobs complete) | no (messages consumed) | yes (consumers track offsets) |
| Strengths | delays, retries, priorities, cron, simple ops in Node | flexible routing, acks, mature | huge throughput, event sourcing, stream processing, many consumers of one stream |
| Typical use | background jobs for one app | service-to-service commands and work queues | event backbone, analytics, CDC |

### Q13 \[S\] Delivery guarantees and idempotent consumers

Real systems give **at-least-once** delivery: a consumer can crash after doing the work but before acking, so the message is redelivered. "Exactly-once" end to end is achieved by at-least-once delivery **plus idempotent processing**.

```js
async function handlePaymentCaptured(msg) {
  await withTransaction(pool, async (tx) => {
    const { rowCount } = await tx.query(
      'INSERT INTO processed_messages (message_id) VALUES ($1) ON CONFLICT DO NOTHING', [msg.id]);
    if (rowCount === 0) return;                         // already processed: skip, then ack
    await tx.query('UPDATE orders SET status = $1 WHERE id = $2', ['paid', msg.orderId]);
  });
}
```

The dedupe record and the side effect commit in the **same transaction**, so either both happen or neither does.

### Q14 \[S\] The outbox pattern

Problem: you update the database and publish an event; if the publish fails (or the process dies between the two), consumers never hear about it. Or the publish succeeds and the DB commit fails, and consumers act on something that did not happen.

**Outbox:** in the same transaction as the business write, insert the event into an `outbox` table. A relay (polling, or change data capture with Debezium) publishes outbox rows to the broker and marks them sent. Delivery is at-least-once, so consumers stay idempotent.

### Q15 \[S\] Sagas and eventual consistency

Across services there is no shared transaction (two-phase commit is rarely practical). A **saga** is a sequence of local transactions with **compensating actions**: reserve inventory → charge card → create shipment; if charging fails, release the reservation. **Orchestration** (a coordinator drives steps, easier to follow) vs **choreography** (services react to each other's events, looser coupling, harder to trace). Design the user experience for intermediate states ("payment pending").

**Which guarantees you get for free and which you build:** brokers give durable storage and at-least-once delivery; Kafka gives per-partition ordering. You build idempotency, deduplication, ordering across partitions, compensations, and reconciliation jobs that find and fix stuck states.

### Q16 \[A\] Distributed tracing and service discovery

Propagate trace context (W3C `traceparent` header) on every outbound call and message; OpenTelemetry auto-instrumentation does this for HTTP, gRPC, `pg`, Redis and many queues (Part 11). Service discovery is handled by the platform (Kubernetes DNS, Consul, cloud load balancers); Node clients should use DNS names and respect TTLs.

## Tricky & trap questions (Part 10)

### T1 \[S\] "We use a transaction, so double-charging is impossible."

Only if the external charge call is inside the guarantee, which it cannot be. A retry after a timeout can charge twice even though your DB transaction rolled back. Use an idempotency key with the payment provider and a unique constraint on your side.

### T2 \[A\] Does Redis `INCR` make a rate limiter correct across replicas?

Yes for the counter (it is atomic). But `INCR` then `EXPIRE` in two calls can leave a key without TTL if the process dies in between; use a Lua script or `SET ... NX EX` then `INCR`, or a library that does this atomically.

### T3 \[S\] Kafka guarantees ordering, so our consumers will see events in order.

Only within a partition, and only if producers use the same key for related events and you process each partition sequentially. Retries to a separate retry topic, or parallel processing within a partition, break ordering.

## Debugging challenge (Part 10)

### D1 \[S\] Every endpoint times out every few hours, then recovers

**Evidence:** pool wait time spikes to the connection timeout; PostgreSQL shows connections `idle in transaction` for minutes.

**Root cause:** a code path calls `BEGIN`, then awaits an external HTTP call, which sometimes hangs; on error, a missing `finally` never releases the client. Leaked and stalled clients drain the pool.

**Fix:** `withTransaction` helper (Q2) everywhere; no network calls inside transactions; `idle_in_transaction_session_timeout` on the database; HTTP timeouts; alerts on pool wait time and idle-in-transaction count.

## Cheat sheet (Part 10)

1. The pool is the real concurrency limit; total connections = per-process max x processes.
2. Transactions: one client, short, no external calls, always release.
3. Read Committed + atomic updates/locks/constraints for most invariants; Serializable needs retries.
4. Kill N+1 with joins or batching; keyset pagination; check `EXPLAIN ANALYZE`.
5. Expand-and-contract migrations; concurrent index builds.
6. Cache-aside with delete-on-write, jittered TTLs, stampede protection.
7. Locks need fencing for correctness.
8. At-least-once + idempotent consumers; outbox for reliable publishing; sagas with compensations.

### More trap questions

#### T4 \[A\] Is this safe under concurrency?

```js
const exists = await db.query('SELECT 1 FROM users WHERE email = $1', [email]);
if (!exists.rowCount) await db.query('INSERT INTO users (email) VALUES ($1)', [email]);
```

No: two requests can both see "not exists" and both insert. Add a `UNIQUE` constraint and handle the violation (`23505`) as "already registered", or `INSERT ... ON CONFLICT DO NOTHING RETURNING id`.

#### T5 \[S\] "Redis is our source of truth for user balances."

Redis persistence (RDB snapshots, AOF with `everysec`) can lose recent writes on failover, and replication is asynchronous. Keep money in a durable, transactional store; use Redis for derived or reconstructable data.

#### T6 \[A\] Why does this MongoDB update lose increments?

```js
const doc = await col.findOne({ _id: id });
await col.updateOne({ _id: id }, { $set: { views: doc.views + 1 } });
```

Read-modify-write race. Use the atomic operator: `updateOne({ _id: id }, { $inc: { views: 1 } })`.

### Code output and concurrency outcome questions

#### O1 \[A\] Two concurrent requests run this with balance 100 and amount 80. What happens?

```sql
UPDATE accounts SET balance = balance - 80 WHERE id = 1 AND balance >= 80 RETURNING balance;
```

**Outcome:** exactly one returns a row (`balance = 20`); the other waits for the first's row lock, re-evaluates the `WHERE` against the new balance (20), and updates 0 rows. Deterministic in PostgreSQL Read Committed.

#### O2 \[A\] What does this print with a pool of `max: 2`?

```js
const t0 = Date.now();
await Promise.all([1, 2, 3, 4].map(() => pool.query('SELECT pg_sleep(1)')));
console.log(Math.round((Date.now() - t0) / 1000));
```

**Output:** about `2`. Two queries run at a time; the other two wait for a free connection. With `connectionTimeoutMillis: 500` the last two would fail instead. Timing approximate.

#### O3 \[S\] A consumer processes message M, commits its DB transaction, then crashes before acking. What happens next?

The broker redelivers M (at-least-once). Without a dedupe record in the same transaction, the side effect runs twice. With the `processed_messages` insert from Q13, the second attempt finds the ID, skips the work, and acks.

# Part 11 — Testing, Performance & Observability

## Testing

### Q1 \[A\] What is your testing strategy for a Node service?

- **Unit tests** for pure logic (pricing rules, validators, state machines): fast, many, no I/O.
- **Integration tests** for the service against **real** dependencies in containers (PostgreSQL, Redis via Testcontainers or Docker Compose): routes, SQL, transactions, migrations. These catch most real bugs in backend code.
- **Contract tests** (Pact, or schema checks against the OpenAPI spec) between services, so a provider change cannot silently break a consumer.
- **End-to-end tests:** a few critical journeys (sign up, checkout) against a deployed environment.
- **Load and soak tests** (k6, autocannon, Artillery) before launches and runtime upgrades: throughput, latency percentiles, memory over hours.

**Senior view:** coverage is a signal, not a goal. Prioritise tests where bugs are expensive (money, auth, data integrity) and where code changes often.

### Q2 \[I\] Node's built-in test runner vs Jest vs Vitest

```js
// order.test.js — node --test
import { test, mock } from 'node:test';
import assert from 'node:assert/strict';
import { applyDiscount } from './pricing.js';

test('applies a percentage discount and never goes negative', () => {
  assert.equal(applyDiscount(1000, { percent: 10 }), 900);
  assert.equal(applyDiscount(100, { fixed: 500 }), 0);
});

test('retries once on a transient error', async () => {
  const fn = mock.fn(async () => { if (fn.mock.callCount() === 0) throw Object.assign(new Error('x'), { code: 'ECONNRESET' }); return 'ok'; });
  assert.equal(await withRetry(fn, { attempts: 2, baseMs: 0 }), 'ok');
  assert.equal(fn.mock.callCount(), 2);
});
```

`node:test` is stable, fast, has mocking, fake timers, coverage (`--experimental-test-coverage`) and watch mode with no dependencies. Jest has the largest ecosystem but its module mocking and ESM support add friction; Vitest is fast and ESM-native. Any is fine; consistency matters more.

### Q3 \[A\] Mocks, stubs, fakes, and fake timers — and their pitfalls

- **Stub:** returns canned answers. **Mock:** also records calls to assert on. **Fake:** a working lightweight implementation (in-memory repository).
- Prefer fakes and real dependencies at boundaries you own (your database), mocks at boundaries you do not (a payment provider's HTTP API, via `nock` or `undici`'s `MockAgent`).
- Over-mocking tests the mocks: a test that mocks the repository, the service and the clock proves almost nothing.
- **Fake timers** (`mock.timers.enable()`, `jest.useFakeTimers()`) make retry/backoff/timeout tests instant; remember to advance timers *and* flush promises, or awaited code never resumes.

### Q4 \[A\] Async test pitfalls

- Forgetting to `await` an assertion on a promise: the test passes before the assertion runs. Use `await assert.rejects(promise, /message/)`.
- Leaked handles (open servers, pools, timers) keep the runner alive or bleed state between tests: close everything in `after` hooks; `--detect-open-handles` in Jest helps.
- Shared database state: wrap each test in a transaction and roll back, or truncate tables between tests; run test files in parallel only with isolated schemas or databases.
- Time and randomness: inject a clock and a random source so tests are deterministic.

### Q5 \[A\] Testing HTTP, queues and workers

```js
import { test, before, after } from 'node:test';
import assert from 'node:assert/strict';
import { buildApp } from '../src/app.js';     // app without listen (Part 1, Q5)

let server, base;
before(async () => {
  server = buildApp({ db: testDb }).listen(0);   // ephemeral port
  await new Promise((r) => server.once('listening', r));
  base = `http://127.0.0.1:${server.address().port}`;
});
after(() => new Promise((r) => server.close(r)));

test('POST /orders is idempotent with the same key', async () => {
  const body = JSON.stringify({ sku: 'A1', qty: 1 });
  const headers = { 'content-type': 'application/json', 'idempotency-key': 'k-123' };
  const r1 = await fetch(`${base}/orders`, { method: 'POST', headers, body });
  const r2 = await fetch(`${base}/orders`, { method: 'POST', headers, body });
  assert.equal(r1.status, 201);
  assert.deepEqual(await r2.json(), await r1.json());
});
```

Queues: run the worker's handler function directly with fixture jobs, plus one integration test through the real broker. Worker threads: test the task function directly, then one test through the pool.

### Q6 \[I\] CI/CD, static analysis and TypeScript

CI runs: install with `npm ci`, typecheck (`tsc --noEmit`), lint (ESLint with `no-floating-promises`, security plugins), unit + integration tests against service containers, dependency audit, build the image, and scan it. TypeScript in strict mode removes whole classes of `undefined` bugs, but types vanish at runtime: still validate external input with schemas (and derive types from them with Zod or TypeBox).

## Performance

### Q7 \[S\] How do you investigate a performance problem systematically?

1. **Define the symptom with numbers:** which endpoint, which percentile (p50 vs p99), since when, at what load.
2. **Check the USE/RED basics:** request rate, errors, duration; CPU, memory, event loop delay and utilisation, GC, pool wait times, dependency latency (Part 2, Q29).
3. **Classify:** CPU-bound in Node (high ELU), waiting on something (low ELU, high latency), memory/GC pressure, or contention (pool queues).
4. **Profile the right thing:** CPU profile for CPU; traces for waiting; heap profiling for memory.
5. **Form one hypothesis, change one thing, measure again** under the same load.

**Common mistake:** optimising code before looking at a trace that shows 90% of time in one N+1 query.

### Q8 \[A\] How do you read a flame graph?

Generate with `node --cpu-prof` (open in DevTools), `0x`, or Clinic Flame. The x-axis is **share of samples** (not time order); the y-axis is the call stack. Look for **wide plateaus at the top** of stacks: functions that themselves burn CPU. Common culprits: `JSON.stringify`/`parse` of large objects, regex, synchronous crypto or compression, logging with expensive serialisation, deep cloning, and template rendering.

### Q9 \[A\] Throughput, latency and tail latency

- **Throughput:** requests per second at an acceptable latency. **Latency:** time per request; report percentiles, never averages.
- **Tail latency (p99, p99.9)** dominates user experience in fan-out systems: a page calling 20 services hits each one's p99 often. Causes: GC pauses, event loop blocking by occasional large payloads, pool queueing, cold caches, noisy neighbours.
- **Coordinated omission:** load tools that wait for each response before sending the next under-report tail latency; use open-model tools (k6 with arrival-rate executors, wrk2).

### Q10 \[A\] Common Node performance wins

- Serialisation: avoid stringifying huge objects; use schema-based serialisers (`fast-json-stringify`, Fastify's response schemas); stream large responses.
- Logging: a fast structured logger (pino) writing to stdout asynchronously; no `console.log` of large objects in hot paths; sample debug logs.
- Database: fix N+1, add indexes, batch writes, cache hot reads, right-size pools.
- Connections: keep-alive to upstreams.
- CPU: move heavy work to workers or native libraries; avoid synchronous APIs after startup.
- Benchmark correctly: warm up, run long enough, isolate the machine, compare distributions (`autocannon`, `mitata`/`tinybench` for micro-benchmarks), and state the Node version.

## Observability and production operations

### Q11 \[A\] Structured logging with request and correlation IDs

```js
import pino from 'pino';
export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  redact: { paths: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.token'], censor: '[redacted]' },
});

app.use((req, res, next) => {
  const requestId = req.get('x-request-id') ?? crypto.randomUUID();
  res.setHeader('x-request-id', requestId);
  requestContext.run({ requestId, log: logger.child({ requestId }) }, next);   // AsyncLocalStorage, Part 2
});
```

Log JSON to stdout; let the platform ship it. A **request ID** identifies one request in one service; a **correlation ID / trace ID** follows the whole user action across services and queues. Levels mean something: `error` pages someone or feeds an error budget; `warn` is unusual but handled; `info` is business events; `debug` is off in production.

### Q12 \[S\] Metrics, tracing, and OpenTelemetry

- **Metrics** (Prometheus, OpenTelemetry metrics): RED per endpoint (rate, errors, duration histograms), runtime (event loop delay, ELU, heap, RSS, GC), pools (in use, waiting), queues (depth, age of oldest job), business KPIs. Watch label cardinality: never use user IDs or raw URLs as labels.
- **Tracing** (OpenTelemetry SDK + auto-instrumentations, exported to Jaeger, Tempo, Honeycomb, Datadog): spans per request, DB query, outbound call, queue publish/consume, with context propagated across services. Sample (head or tail-based) to control cost.
- **Error monitoring** (Sentry and similar): grouped exceptions with stack traces and release tags.
- Dashboards (Grafana) per service: golden signals first, runtime second, dependencies third.

### Q13 \[S\] Health checks, SLOs, alerting and incident response

- **Liveness:** "the process is not wedged" (cheap; do not check dependencies, or a DB outage restarts every pod). **Readiness:** "send me traffic" (fails during startup, shutdown, or when a critical dependency is unusable). **Startup** probes for slow boots.
- **SLIs and SLOs:** pick user-facing indicators (availability of checkout, p99 latency of search) and targets (99.9% over 30 days). The **error budget** decides when to slow feature work.
- **Alert on symptoms** (SLO burn rate) not causes (CPU 80%); every alert must be actionable and owned.
- **Incident response:** declare, assign an incident commander, mitigate first (rollback, scale, disable a feature flag), then diagnose; communicate on a cadence; write a blameless postmortem with action items.
- **Container memory limits:** alert on RSS approaching the limit and on OOM kills (Part 3).

## Tricky & trap questions (Part 11)

### T1 \[A\] "Our average latency is 80 ms, so we are fine."

Averages hide tails. p99 could be 3 s for 1% of requests, which in a fan-out page means most users see it. Track percentiles from histograms, not averages of averages.

### T2 \[A\] Why did the test pass even though the code throws?

```js
test('rejects bad input', () => {
  assert.rejects(createOrder({ qty: -1 }));   // missing await
});
```

The test function returned before the assertion settled. `await assert.rejects(...)` (and make the test `async`).

### T3 \[S\] "The liveness probe checks the database."

When the database blips, every pod fails liveness and restarts at once, turning a short outage into a long one with a thundering herd of reconnections. Check dependencies in readiness (carefully), not liveness.

## Debugging challenge (Part 11): performance investigation

### D1 \[S\] p99 latency doubled after a release; p50 unchanged

**Investigation:** traces show slow requests spend their time in the handler itself, not in DB calls; event loop delay p99 rose from 10 ms to 120 ms; CPU profile shows `JSON.stringify` and a new `deepClone` utility wide at the top.

**Root cause:** the release added an audit log that deep-cloned and stringified the full response payload on every request; large customers' responses (2–5 MB) now block the loop for 100 ms, delaying every other request on that process.

**Fix:** log a compact summary (IDs, sizes, changed fields), not the payload; send audit events asynchronously through a queue; add a performance budget test for the largest fixture; alert on event loop delay p99.

## Cheat sheet (Part 11)

1. Many unit tests, real-dependency integration tests, contract tests, few E2E, regular load/soak tests.
2. Await every async assertion; close every handle; isolate DB state; inject clocks.
3. Investigate with numbers: percentiles, ELU, pool waits, traces, then profiles.
4. Flame graphs: wide frames at the top burn CPU.
5. Percentiles, not averages; beware coordinated omission.
6. JSON logs to stdout with request/trace IDs and redaction.
7. RED + runtime metrics with bounded cardinality; OpenTelemetry traces across services.
8. Liveness simple, readiness honest; alert on SLO burn, not CPU.

## Deployment

### Q1 \[A\] What does a production deployment of a Node API look like?

```dockerfile
USER node                                    # never run as root
EXPOSE 3000
CMD ["node", "--enable-source-maps", "dist/server.js"]   # exec form: Node receives SIGTERM directly
```

- Multi-stage keeps compilers and dev dependencies out of the final image. Copy lockfiles before source so dependency layers are cached.
- Pin the major (`node:26-slim`, or a digest for full reproducibility). `slim` (Debian) avoids musl surprises with native modules; Alpine is smaller but uses musl. Distroless shrinks the attack surface further.
- `.dockerignore` excludes `node_modules`, `.git`, `.env`, test fixtures.
- Add `--init` (or `tini`) if the app spawns children, so zombies are reaped.
- Scan the image (Trivy, Grype) in CI.

### Q3 \[S\] PM2, plain containers, or Kubernetes: when does each make sense?

| Situation | Choice | Why |
| --- | --- | --- |
| One or two VMs, small team | PM2 (cluster mode) + Nginx, or systemd | restarts, logs, multi-core, zero-downtime reload with little machinery |
| A few services, want containers without running a cluster | managed containers (ECS/Fargate, Cloud Run, App Runner, Fly.io) | health checks, rolling deploys, autoscaling, no control plane to operate |
| Many services, platform team, complex networking | Kubernetes (EKS, GKE, AKS) | scheduling, service discovery, HPA, policies, ecosystem; real operational cost |
| Spiky, event-driven workloads | serverless functions | pay per use; cold starts and connection pooling need care (RDS Proxy) |

**Senior answer:** choose the simplest platform your team can operate reliably; Kubernetes is not a default.

### Q4 \[A\] Nginx as a reverse proxy in front of Node

Nginx (or an ALB/Envoy) terminates TLS, serves static files, compresses, buffers slow clients so Node sockets are freed quickly, limits body size and request rate, and load-balances across processes. Set `proxy_set_header X-Forwarded-For` / `X-Forwarded-Proto`, match keep-alive and timeouts with Node's (Part 6, Q4), and enable `proxy_http_version 1.1` with upstream keep-alive.

### Q5 \[S\] Zero-downtime deployment: what has to be true?

1. **Rolling or blue-green deploys** with `maxUnavailable: 0` so capacity never drops.
2. **Readiness probes** so new pods only get traffic when ready (DB connected, warm caches if needed).
3. **Graceful termination** in old pods: fail readiness, wait for the LB to deregister (`preStop` sleep of a few seconds), drain in-flight requests, close pools, exit within `terminationGracePeriodSeconds` (Part 7, Q7).
4. **Backward-compatible changes:** old and new versions run side by side during a rollout, so APIs, message formats and DB schemas must work with both (expand and contract, Part 10, Q7).
5. **Fast rollback:** keep the previous image; feature flags to turn off new behaviour without a deploy; canary releases watched by SLO metrics.

### Q6 \[A\] Autoscaling, health checks and resource limits in Kubernetes

- **Requests and limits:** set memory request = limit (memory is not compressible; exceeding the limit is an OOM kill); set CPU requests, and be careful with CPU limits (throttling hurts latency; many teams set none).
- **HPA** on CPU is a poor fit for I/O-bound Node services; scale on request rate, ELU or queue depth (KEDA for queue-driven workers).
- **Probes:** liveness simple, readiness honest, startup probe for slow boots (Part 11, Q13).
- `--max-old-space-size` below the memory limit; `UV_THREADPOOL_SIZE` deliberate.

### Q7 \[S\] Migrations, backups, disaster recovery and rollback

- Migrations run as a separate, single job before (or as part of) a deploy, are backward compatible, and are tested on a production-like copy.
- **Backups:** automated, encrypted, in another region/account; **restores tested** on a schedule (an untested backup is a hope). Point-in-time recovery for the database.
- **RPO / RTO:** how much data you can lose and how long you can be down; they drive replication and multi-region choices and cost.
- **Rollback:** app rollback is easy if schemas are compatible; data rollback is hard, so prefer roll-forward fixes and design reversible migrations.

### Q8 \[A\] Cost optimisation

Right-size replicas from real usage (most Node services are over-provisioned on CPU); scale workers on queue depth and to zero when idle; use spot instances for stateless workers; cache aggressively at the CDN; reduce log volume (sampling, shorter retention for debug logs) and metric cardinality, which are often the surprise bills; and watch cross-AZ / egress traffic.

## Senior architecture

### Q9 \[S\] Modular monolith vs microservices

**Start with a modular monolith** for most products: one deployable, clear module boundaries (each module owns its tables and exposes an interface), in-process calls, one transaction when needed. Move a module out into a service when there is a concrete reason: independent scaling, a different release cadence owned by another team, isolation of a risky dependency, or a different technology need.

**Microservices cost:** network failures between every call, distributed transactions (sagas), versioned contracts, distributed tracing, more infrastructure and on-call surface. They solve organisational scaling problems more than technical ones.

### Q10 \[S\] Clean / Hexagonal Architecture and dependency inversion in Node

The idea: business logic in the centre does not import Express, Prisma or Kafka. It defines **ports** (interfaces such as `OrderRepository`, `PaymentGateway`), and **adapters** at the edges implement them. A composition root wires them together.

```ts
// domain/service — no framework imports
export interface OrderRepository { findById(id: string): Promise<Order | null>; save(o: Order): Promise<void>; }
export interface PaymentGateway { charge(input: ChargeInput, idempotencyKey: string): Promise<ChargeResult>; }

export class PlaceOrder {
  constructor(private orders: OrderRepository, private payments: PaymentGateway, private clock: () => Date) {}
  async execute(cmd: PlaceOrderCommand) { /* rules only; easy to unit test with fakes */ }
}

// composition root
const placeOrder = new PlaceOrder(new PgOrderRepository(pool), new StripeGateway(stripe), () => new Date());
```

**Trade-off:** it pays off where business rules are rich and long-lived; for thin CRUD services it can be ceremony. Apply it pragmatically.

### Q11 \[S\] Domain-Driven Design, domain events and service boundaries

- **Bounded contexts:** the same word ("customer") means different things in billing and support; draw boundaries where models and language change. These are the natural seams for modules or services.
- **Aggregates** enforce invariants in one transaction (an `Order` with its lines); reference other aggregates by ID.
- **Domain events** ("OrderPlaced") decouple modules: publish via an outbox, consume idempotently.
- **API contracts** between contexts are versioned, documented (OpenAPI, AsyncAPI, protobuf), and contract-tested.

### Q12 \[S\] Multi-tenant architecture

| Model | Isolation | Cost | When |
| --- | --- | --- | --- |
| Shared tables with `tenant_id` | lowest; relies on every query being scoped | lowest | many small tenants (most SaaS) |
| Schema per tenant | medium | medium; migrations x N | moderate counts, some isolation needs |
| Database per tenant | highest; easy per-tenant backup and residency | highest | enterprise, regulated, noisy tenants |

With shared tables: tenant ID resolved once per request (from the token, not a header the client can set), carried in request context, applied by the repository layer or **PostgreSQL row-level security** as a backstop; per-tenant rate limits and quotas to contain noisy neighbours; tenant ID in logs, metrics and traces. Part 15 designs one.

### Q13 \[S\] Technical leadership topics interviewers raise

- **Architecture Decision Records:** short documents capturing context, decision, alternatives and consequences, so future engineers know why.
- **Code reviews:** review for correctness, failure modes and operability, not style (automate style); small PRs; reviewers ask "what happens when this dependency is slow?"
- **Team standards:** templates for services (logging, metrics, health checks, shutdown built in), paved roads rather than rules.
- **Technical debt:** make it visible, tie it to business risk or delivery speed, pay it down continuously within feature work, not in a mythical rewrite.
- **Incident analysis and capacity planning:** blameless postmortems with owned action items; load tests and growth forecasts that say when you hit the next limit (DB connections, partition throughput, cost).

## Tricky & trap questions (Part 12)

### T1 \[S\] "We'll run migrations on app startup."

With 20 replicas starting at once, 20 processes race to migrate; long migrations delay readiness and fail deploys; a failed migration crash-loops every pod. Run migrations as one job with a lock, before the rollout.

### T2 \[A\] "Our container uses `npm start`, so SIGTERM works."

npm may not forward signals to Node, so the process is killed after the grace period instead of shutting down gracefully. Use `CMD ["node", "dist/server.js"]` (Part 7, Q6).

### T3 \[S\] "Microservices will make us faster."

Only if team boundaries, ownership and platform tooling are in place. Otherwise you get a distributed monolith: services that must be deployed together, with network calls where function calls used to be.

## Debugging challenge (Part 12)

### D1 \[S\] Every deploy causes a burst of 502s and a few duplicate orders

**Root causes:** pods exit immediately on SIGTERM (no graceful shutdown), the load balancer still routes to them for a few seconds (no `preStop` delay, readiness not failed first), and clients retry `POST /orders` on 502 without idempotency keys.

**Fix:** graceful shutdown sequence (Part 7, Q7) with a `preStop` sleep, `maxUnavailable: 0` rolling updates, idempotency keys on order creation, and a deploy-time SLO check that pauses the rollout on error spikes.

## Cheat sheet (Part 12)

1. Stateless pods, immutable images, config at runtime, workers from the same codebase.
2. Multi-stage Docker, `npm ci --omit=dev`, non-root, exec-form CMD, pinned base, scanned image.
3. Pick the simplest platform you can operate: PM2/VM, managed containers, then Kubernetes.
4. Zero downtime = readiness + graceful termination + backward-compatible changes + fast rollback.
5. Memory limit = request; heap below it; scale I/O-bound Node on rate/ELU, workers on queue depth.
6. Test restores; know RPO/RTO; prefer roll-forward.
7. Modular monolith first; services for organisational and scaling reasons.
8. Ports and adapters where domain logic is rich; bounded contexts guide boundaries.
9. Multi-tenancy: tenant from the token, scoped everywhere, RLS backstop, per-tenant quotas.

### Follow-ups and common mistakes per question

| Q | Likely follow-up | Strong answer | Common mistake |
| --- | --- | --- | --- |
| Q1 | Where do uploaded files go? | object storage (S3, GCS) via pre-signed URLs; never the container filesystem | local disk on a pod that may be replaced at any time |
| Q2 | Alpine or Debian slim? | slim by default (glibc, fewer native-module surprises); Alpine if size matters and dependencies are tested on musl | Alpine plus native addons built for glibc |
| Q3 | When would you move from ECS to Kubernetes? | many services, need for its ecosystem (operators, policies), a team to run it | "because everyone uses it" |
| Q4 | Why buffer slow clients at the proxy? | Nginx absorbs slow uploads/downloads so Node sockets and memory are freed quickly | letting thousands of slow clients hold Node connections |
| Q5 | Blue-green vs canary vs rolling? | rolling: simple, gradual; blue-green: instant switch and rollback, double capacity; canary: small traffic slice judged by metrics | canaries without automated metric checks |
| Q6 | Why can CPU limits hurt Node latency? | CFS throttling pauses the process when the quota is used within a period, producing latency spikes even at low average CPU | setting CPU limit = request on latency-sensitive services without measuring |
| Q7 | What is your RPO with daily backups? | up to 24 hours of data loss; add WAL archiving / PITR for minutes | claiming zero data loss with nightly dumps |
| Q9 | How do you enforce module boundaries in a monolith? | separate folders with public index files, lint rules, no cross-module DB table access, contract tests between modules | a "modular" monolith where every module imports every other |
| Q10 | Does hexagonal architecture slow teams down? | for CRUD, yes; apply it to the domain core, keep simple features simple | interfaces for everything, one implementation each, forever |
| Q12 | How do you prevent cross-tenant cache leaks? | tenant ID in every cache key, tested; RLS for DB; tenant-aware rate limits | global cache keys like `product:123` in a multi-tenant app |

**Theory vs production:** theory is the deployment vocabulary; production is boring, rehearsed releases: small changes, automated canary analysis, fast rollback, backward-compatible schemas, and restores that have actually been tested.

# Part 13 — Senior Real-World Scenarios

These are open-ended "how would you" questions. Interviewers grade the **process** as much as the answer, so every scenario follows the same structure:

1. **Clarify** requirements and constraints (scale, latency, consistency, budget, team).
2. **Propose** the simplest design that meets them, and say why.
3. **Walk the request or event flow** end to end.
4. **Name failure modes** and how the design survives them.
5. **Cover security, performance, testing**, then **trade-offs and alternatives**.

Where a building block is explained earlier, the scenario points to it instead of repeating it.

## S1 \[S\] Design a scalable Node.js backend for a new product

**Clarify:** expected traffic (say 500 rps peak, growing 5x in a year), read/write mix, latency target (p99 < 300 ms), team size (6 engineers).

**Recommendation:** a modular monolith (Part 12, Q9) in TypeScript on Fastify or Express; PostgreSQL as the system of record; Redis for cache, rate limits and BullMQ jobs; stateless containers behind a load balancer (Part 12 diagram); OpenTelemetry from day one.

**Flow:** client → CDN/WAF → LB → API pod (validate → authorise → service → repository → PostgreSQL) → response; slow side effects (email, webhooks, reports) enqueued to workers.

**Failure modes:** DB primary failover (pool reconnects, idempotent retries), Redis loss (cache misses tolerated; rate limiter fails open or closed by decision), a pod crash (LB health checks), a bad deploy (canary + rollback).

**Scale path:** vertical DB first, read replicas, caching, then partition the hottest module into its own service only when data shows it.

**Follow-ups:** What would make you choose microservices on day one? Where is your first bottleneck at 5x? (Usually DB connections and the hottest queries.)

## S2 \[S\] Handle high concurrent traffic and build a high-throughput API

- Keep handlers I/O-bound and short: no synchronous CPU work (Part 2, Q27), offload CPU (Part 7).
- Bound everything: connection pools, outbound concurrency, queue sizes, body sizes; shed load with 503 when event loop delay or pool wait crosses a threshold (Part 8, Q8).
- Reduce work per request: caching (Part 10, Q9), schema-based serialisation, pagination, compression at the edge.
- Horizontal scale: stateless pods, autoscaling on request rate or ELU (Part 12, Q6).
- **Measure:** load test with an open-model tool to find the knee of the latency curve; capacity = replicas x per-pod throughput at target p99, with 30–50% headroom.

## S3 \[S\] Prevent event loop blocking in a growing codebase

Guardrails, not heroics: lint against `*Sync` APIs outside startup; event loop delay and ELU metrics with alerts; CPU profiles available on demand (Part 3, Q15); performance budget tests for the largest payloads; a worker pool or job queue as the documented place for CPU work; code review question "is this proportional to user input size?"

## S4 \[S\] Process large files and build streaming APIs

Stream end to end (Part 5): upload straight to object storage with a byte limit; process from storage in a worker with `pipeline`, per-row validation, batching and idempotent writes (Part 5, Q7); expose status via a job resource (`202 Accepted` + `GET /jobs/:id`); stream large downloads and exports as NDJSON or CSV with backpressure; handle client disconnects (Part 6, Q6).

**Failure modes:** worker crash mid-file (checkpoint offsets or re-run idempotently), poison rows (report, do not fail the job), huge files (limits, timeouts), malicious files (type sniffing, zip bomb limits, malware scanning).

## S5 \[S\] Design a notification system (email, SMS, push)

**Requirements:** many channels and providers, user preferences, templating, retries, rate limits per provider, no duplicates, auditability.

**Design:** producers publish `NotificationRequested` events (via outbox, Part 10, Q14) → a notification service resolves preferences and templates → per-channel queues → channel workers call providers with idempotency keys, per-provider rate limiting and circuit breakers, fail over to a secondary provider → status stored per message; provider webhooks update delivery status.

**Key points:** priority queues (OTP before marketing), quiet hours, unsubscribe compliance, deduplication key per (user, template, entity), DLQ for permanent failures. Part 15 designs this fully.

## S6 \[S\] Reliable background jobs and queue workers

- Durable queue (BullMQ on Redis with persistence, RabbitMQ, SQS); jobs carry IDs and minimal data (IDs, not whole records).
- Workers: bounded concurrency, timeouts per job, retries with exponential backoff and jitter, DLQ after N attempts (Part 8, Q9), idempotent handlers (Part 10, Q13).
- Graceful shutdown that finishes current jobs (Part 2, D2).
- Observability: queue depth, age of oldest job, processing time, failure rate per job type; alert on age, not just depth.
- Scheduled jobs: one scheduler (repeatable jobs or a leader-elected cron), never cron in every replica.

## S7 \[S\] Manage database connection pools at scale

Total connections = pool size x processes x replicas (+ deploy surge + workers + migrations). Keep it under the DB limit with headroom; use PgBouncer/RDS Proxy for many replicas or serverless; set connection and statement timeouts; alert on pool wait time and idle-in-transaction; release connections before calling external services (Part 10, Q1, D1).

## S8 \[S\] Handle slow downstream services and prevent cascading failures

Timeouts and deadlines, retries at one layer with budgets, circuit breakers with fallbacks, bulkheads per dependency, load shedding, and degrading non-critical features (Part 8, Q6–Q8, D1). **Test it:** inject latency and errors (Toxiproxy, chaos experiments) in staging and confirm critical paths stay up.

## S9 \[S\] Optimise CPU-intensive workloads

Profile first (Part 11, Q8). Then: better algorithm or data structure; native libraries (sharp, argon2) that run off the main thread; worker thread pool sized to cores (Part 7, Q2); move batch work to separate worker services; cache results; for heavy numeric work consider WebAssembly or a service in another language.

## S10 \[S\] Design a WebSocket system

**Requirements:** 200,000 concurrent connections, fan-out of user and room events, reconnects, auth.

**Design:** dedicated gateway service (ws or uWebSockets.js) separate from the HTTP API; authenticate at upgrade with a short-lived token; per-connection heartbeats; sticky sessions are not required if every gateway subscribes to a **pub/sub backbone** (Redis Pub/Sub or Streams, NATS, Kafka) and delivers to its local sockets via a `Map<userId, Set<socket>>` (Part 3, D1); backpressure per socket (drop or disconnect slow consumers when `bufferedAmount` grows); resume with a last-event ID so clients catch up after reconnect.

**Scale and failure:** about 50k–100k connections per Node process depending on message rates; graceful drain on deploy (tell clients to reconnect elsewhere with jitter to avoid a reconnect storm); limit message size and rate per connection.

## S11 \[S\] Multi-tenant services

Tenant from the token, scoped repositories, PostgreSQL RLS backstop, per-tenant quotas and rate limits, noisy-neighbour isolation (separate queues or pools for large tenants), tenant-aware observability, and per-tenant data export/deletion (Part 12, Q12; Part 15, D10).

## S12 \[S\] Implement idempotent APIs

```text
POST /payments  Idempotency-Key: 7f3c...
  1. INSERT INTO idempotency_keys (key, user_id, request_hash, status='in_progress') ON CONFLICT DO NOTHING
  2. Conflict? -> same request_hash: return stored response (or 409 "in progress"); different hash: 422
  3. Do the work (with the provider's own idempotency key = our key)
  4. UPDATE idempotency_keys SET status='done', response=... in the same transaction as the business write
  5. Expire keys after 24-72 h
```

Key scoped to the user; request hash prevents key reuse with a different body; in-progress state handles concurrent duplicates. Part 14 implements it.

## S13 \[S\] Distributed transactions

Avoid them where possible by keeping an invariant inside one service's database. Otherwise: sagas with compensations (Part 10, Q15), outbox for reliable events, idempotent steps, a state machine per business process stored durably, and reconciliation jobs that detect and fix stuck or mismatched states (for example, nightly comparison with the payment provider).

## S14 \[S\] Graceful shutdown, zero-downtime deploys, horizontal scaling

Covered in Part 7 (Q7) and Part 12 (Q5–Q6). The senior summary: readiness off → LB drain delay → stop accepting → drain requests and jobs → close pools → exit within the grace period; backward-compatible changes so two versions can run together; scale stateless pods horizontally and move all shared state out of process.

## S15 \[S\] Manage a memory leak in production

Confirm with RSS and heap trends over many GCs; mitigate (restart policy, scale out, roll back the release that introduced it); capture evidence on one drained instance (heap snapshots, three-snapshot comparison); find the retainer; fix; prove with a soak test (Part 3, Q11, D1, D2).

## S16 \[S\] Observability and incident response

Golden-signal dashboards per service, SLO burn-rate alerts, traces across services, structured logs with trace IDs, runbooks per alert, an incident process (commander, comms, timeline), and blameless postmortems (Part 11, Q11–Q13).

## S17 \[S\] Security incident handling

Contain first (revoke credentials, block, isolate), preserve evidence (logs, snapshots), assess blast radius from audit logs, eradicate the cause, recover, notify as required, and fix the class of bug (Part 9, D1).

## S18 \[S\] Cost and infrastructure optimisation

Right-size from utilisation data, autoscale on the right signal, scale workers to zero, spot instances for stateless work, CDN caching, reduce log and metric volume, watch data transfer, and compare reserved capacity against steady baseload (Part 12, Q8). Present savings as a trade-off against reliability, not free money.

### Full structure for S3, S7, S8, S9, S11, S13–S18

**S3 Prevent event loop blocking** — *Requirements:* p99 under 200 ms as payload sizes grow. *Solution:* lint bans on sync APIs, size limits, worker pool for CPU, schema serialisation. *Failure:* one large customer payload blocks a process; mitigate with per-request size caps and load shedding. *Security:* ReDoS and JSON bombs are blocking attacks; cap input sizes. *Performance:* alert on loop delay p99 and ELU. *Testing:* benchmark the largest fixture in CI with a time budget. *Follow-up:* how do you find the offender in production? (CPU profile on one instance.)

**S7 Database connection pools** — *Requirements:* 30 replicas, 8 workers, DB limit 500. *Solution:* pool of 10 per API process, 5 per worker, PgBouncer in transaction mode in front. *Failure:* deploy surge doubles connections; pooler absorbs it. *Security:* least-privilege DB roles per service. *Performance:* watch pool wait time p99 and DB active connections. *Testing:* load test at 2x traffic during a rolling deploy. *Follow-up:* what breaks with PgBouncer transaction mode? (session features: prepared statements in some drivers, advisory locks, `SET` without `LOCAL`.)

**S8 Slow downstream services** — *Requirements:* checkout must stay up when recommendations or tax APIs degrade. *Solution:* deadlines, one retry layer with budget, breakers with fallbacks (cached or default tax table with reconciliation), bulkheads per dependency. *Failure:* breaker flapping; use rate-based thresholds and half-open probes. *Security:* do not fall back to skipping fraud checks silently. *Performance:* shed non-critical calls under load. *Testing:* Toxiproxy latency and error injection in staging; game days. *Follow-up:* which dependencies are allowed to fail open?

**S9 CPU-intensive workloads** — *Requirements:* PDF generation takes 800 ms of CPU each. *Solution:* separate worker service with a bounded queue; API returns 202 and a job URL. *Failure:* worker crash mid-render; idempotent job keyed by document ID. *Security:* sandbox renderers; limit template features. *Performance:* scale workers on queue age. *Testing:* load test the queue path; assert API latency unaffected. *Follow-up:* when would you rewrite the hot part in Rust or Go? (only after profiling shows JS is the bottleneck and offloading is not enough.)

**S11 Multi-tenant services** — *Requirements:* 5,000 tenants, two enterprise tenants with residency needs. *Solution:* shared schema + RLS, enterprise tenants in dedicated cells. *Failure:* noisy tenant saturates the DB; per-tenant quotas and separate pools. *Security:* tenant from the verified token only; tenant-prefixed cache keys. *Performance:* per-tenant metrics to spot hot tenants. *Testing:* cross-tenant access tests for every endpoint. *Follow-up:* how do you migrate a tenant between cells? (dual-write or export/import during a maintenance window, then switch routing.)

**S13 Distributed transactions** — *Requirements:* order, payment and inventory in separate services. *Solution:* orchestrated saga with a persisted state machine, outbox events, idempotent steps, compensations. *Failure:* compensation fails; retry, then human queue. *Security:* sign inter-service messages; authorise saga commands. *Performance:* async steps keep the user path short. *Testing:* simulate failures at each step and assert final consistent state. *Follow-up:* why not two-phase commit? (blocking coordinator, poor fit for HTTP services and many brokers.)

**S14 Graceful shutdown and zero-downtime deploys** — *Requirements:* no 502s or lost jobs during deploys. *Solution:* the Part 7 sequence + rolling updates with `maxUnavailable: 0`, `preStop`, backward-compatible changes. *Failure:* long requests exceed the grace period; make them jobs. *Security:* do not expose readiness toggles publicly. *Performance:* surge capacity during rollout. *Testing:* deploy under load in staging and assert zero 5xx. *Follow-up:* how do WebSocket servers deploy without a reconnect storm? (drain gradually with jittered reconnect hints.)

**S15 Memory leak in production** — *Requirements:* service restarts every 6 hours with OOM. *Solution:* mitigate (roll back or scale out), then evidence on one drained pod (snapshots), find the retainer, fix, soak test. *Failure:* snapshot itself OOMs the pod; use `--heapsnapshot-near-heap-limit` and spare memory, or reproduce in staging. *Security:* snapshots contain secrets; restrict and delete. *Performance:* GC pressure precedes OOM; watch it. *Testing:* leak regression test (Part 14, C18). *Follow-up:* RSS grows but heap does not; now what? (external/native memory: Buffers, addons, allocator; check `arrayBuffers`, try jemalloc.)

## C1 Concurrency limiter

**Requirements:** run an async function over many items with at most N in flight; keep result order; stop starting new work after the first failure; support cancellation.

```ts
export async function mapLimit<T, R>(items: readonly T[], limit: number,
  fn: (item: T, i: number, signal: AbortSignal) => Promise<R>, { signal }: { signal?: AbortSignal } = {}): Promise<R[]> {
  if (!Number.isInteger(limit) || limit < 1) throw new RangeError('limit must be a positive integer');
  const ac = new AbortController();
  signal?.addEventListener('abort', () => ac.abort(signal.reason), { once: true });
  const results = new Array<R>(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length && !ac.signal.aborted) {
      const i = next++;
      try { results[i] = await fn(items[i], i, ac.signal); }
      catch (err) { ac.abort(err); throw err; }        // stop the other workers picking new items
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  ac.signal.throwIfAborted();
  return results;
}
```

**Complexity:** O(n) scheduling, O(n) results. **Edge cases:** empty input, limit larger than input, a rejection mid-way, external abort.

## C2 Retry with exponential backoff and jitter

Implemented in Part 2, Q26a (`fetchJsonWithRetry`). A generic version for interviews:

```ts
export async function retry<T>(fn: (attempt: number) => Promise<T>, {
  attempts = 3, baseMs = 100, maxMs = 5_000, isRetryable = (_e: unknown) => true, signal,
}: { attempts?: number; baseMs?: number; maxMs?: number; isRetryable?: (e: unknown) => boolean; signal?: AbortSignal } = {}): Promise<T> {
  let lastErr: unknown;
  for (let attempt = 0; attempt < attempts; attempt++) {
    signal?.throwIfAborted();
    try { return await fn(attempt); }
    catch (err) {
      lastErr = err;
      if (!isRetryable(err) || attempt === attempts - 1) break;
      const delay = Math.random() * Math.min(maxMs, baseMs * 2 ** attempt);   // full jitter
      await sleep(delay, undefined, { signal });
    }
  }
  throw lastErr;
}
```

**Tests:** succeeds on the 3rd attempt; does not retry non-retryable errors; rethrows the last error; delays are within the cap (inject `Math.random` or a `random` option to make it deterministic); abort stops waiting.

## C4 A basic event emitter

```ts
type Listener = (...args: any[]) => void;
export class Emitter {
  #map = new Map<string, Listener[]>();
  on(event: string, fn: Listener) { (this.#map.get(event) ?? this.#map.set(event, []).get(event)!).push(fn); return () => this.off(event, fn); }
  once(event: string, fn: Listener) {
    const wrapper: Listener = (...args) => { this.off(event, wrapper); fn(...args); };
    return this.on(event, wrapper);
  }
  off(event: string, fn: Listener) {
    const list = this.#map.get(event); if (!list) return;
    const i = list.indexOf(fn); if (i !== -1) list.splice(i, 1);
    if (list.length === 0) this.#map.delete(event);
  }
  emit(event: string, ...args: unknown[]): boolean {
    const list = this.#map.get(event);
    if (!list?.length) { if (event === 'error') throw args[0] instanceof Error ? args[0] : new Error('Unhandled error'); return false; }
    for (const fn of [...list]) fn(...args);         // copy: listeners may remove themselves while emitting
    return true;
  }
}
```

**Points the interviewer checks:** synchronous, ordered delivery; copying the listener array before iterating (so `once` works); `'error'` with no listener throws like Node's; `on` returns an unsubscribe function. O(1) add, O(k) remove and emit.

## C5 LRU cache

```ts
export class LRUCache<K, V> {
  #map = new Map<K, V>();
  constructor(private max: number) { if (max < 1) throw new RangeError('max must be >= 1'); }
  get(key: K): V | undefined {
    if (!this.#map.has(key)) return undefined;
    const value = this.#map.get(key)!;
    this.#map.delete(key); this.#map.set(key, value);   // move to most-recent
    return value;
  }
  set(key: K, value: V) {
    if (this.#map.has(key)) this.#map.delete(key);
    this.#map.set(key, value);
    if (this.#map.size > this.max) this.#map.delete(this.#map.keys().next().value!); // evict least-recent
  }
  get size() { return this.#map.size; }
}
```

**Why it works:** `Map` iterates in insertion order, so re-inserting on access keeps the least recently used key first. O(1) get and set. The classic alternative (hash map + doubly linked list) shows the same idea explicitly; mention it.

**Tests:** evicts the least recently used; `get` refreshes recency; updating an existing key does not grow size; `undefined` values are distinguishable from misses (`has`).

## C6 A rate limiter (token bucket)

```ts
export class TokenBucket {
  #buckets = new Map<string, { tokens: number; updated: number }>();
  constructor(private capacity: number, private refillPerSec: number, private now = () => performance.now()) {}
  take(key: string, cost = 1): { allowed: boolean; retryAfterMs: number } {
    const t = this.now();
    const b = this.#buckets.get(key) ?? { tokens: this.capacity, updated: t };
    b.tokens = Math.min(this.capacity, b.tokens + ((t - b.updated) / 1000) * this.refillPerSec);
    b.updated = t;
    this.#buckets.set(key, b);
    if (b.tokens >= cost) { b.tokens -= cost; return { allowed: true, retryAfterMs: 0 }; }
    return { allowed: false, retryAfterMs: Math.ceil(((cost - b.tokens) / this.refillPerSec) * 1000) };
  }
}
```

Allows bursts up to `capacity`, a steady rate of `refillPerSec`. **Production gaps to mention:** per-process state (use Redis with a Lua script for atomic refill-and-take across replicas, Part 10, T2); unbounded map of keys (evict idle buckets with an LRU); clock injection for deterministic tests.

## C12 Job queue with controlled concurrency

```ts
type Job<T> = { id: string; run: (signal: AbortSignal) => Promise<T>; attempts?: number };

export class JobQueue {
  #queue: Job<unknown>[] = []; #active = 0; #closed = false; #idle?: () => void;
  constructor(private concurrency = 4, private maxAttempts = 3, private onDead = (_j: Job<unknown>, _e: unknown) => {}) {}
  add(job: Job<unknown>) {
    if (this.#closed) throw new Error('queue closed');
    this.#queue.push({ attempts: 0, ...job });
    this.#drain();
  }
  #drain() {
    while (this.#active < this.concurrency && this.#queue.length) {
      const job = this.#queue.shift()!;
      this.#active++;
      const ac = new AbortController();
      job.run(ac.signal)
        .catch((err) => {
          job.attempts! += 1;
          if (job.attempts! < this.maxAttempts) setTimeout(() => { this.#queue.push(job); this.#drain(); }, 100 * 2 ** job.attempts!).unref();
          else this.onDead(job, err);                         // dead-letter
        })
        .finally(() => { this.#active--; this.#drain(); if (!this.#active && !this.#queue.length) this.#idle?.(); });
    }
  }
  async close() { this.#closed = true; if (this.#active || this.#queue.length) await new Promise<void>((r) => (this.#idle = r)); }
}
```

**Mention its limits:** in-memory, so jobs are lost on crash; use BullMQ or a broker for durability (Part 10, Q12). The interview value is the scheduling loop, retry with backoff, dead-lettering and drain-on-close.

**Edge case to point out:** `close()` can resolve while a retry is waiting in a timer; a production version tracks pending retries too.

## C13 Request deduplication (single flight)

```ts
export class SingleFlight<T> {
```

## C14 Idempotency mechanism

```ts
export function idempotent(store: IdempotencyStore) {
  return async (req, res, next) => {
    const key = req.get('idempotency-key');
    if (!key || req.method !== 'POST') return next();
    const scope = `${req.user.id}:${key}`;                         // keys are per user
    const hash = sha256(JSON.stringify(req.body));
    const claim = await store.claim(scope, hash, { ttlSec: 86_400 }); // INSERT ... ON CONFLICT DO NOTHING RETURNING
    if (claim.status === 'done') {
      if (claim.hash !== hash) return res.status(422).json({ error: 'Idempotency key reused with a different body' });
      return res.status(claim.response.status).set('idempotent-replayed', 'true').json(claim.response.body);
    }
    if (claim.status === 'in_progress' && !claim.ownedByUs) return res.status(409).json({ error: 'Request in progress' });
    const json = res.json.bind(res);
    res.json = (body) => {                                            // capture the response to store it
      store.complete(scope, { status: res.statusCode, body }).catch((err) => req.log.error({ err }));
      return json(body);
    };
    res.on('close', () => { if (!res.writableFinished) store.release(scope).catch(() => {}); }); // allow retry if we crashed mid-way
    next();
  };
}
```

**Senior points:** the business write and `complete` should ideally commit in one transaction (store the key in the same DB); only cache deterministic outcomes (store 2xx and 4xx, not 5xx, so retries can succeed); expire keys; pass the same key to downstream providers. **Tests:** same key twice returns the same body and creates one row; concurrent duplicates yield one success and one 409; same key with a different body returns 422.

## C17 Bounded in-memory cache with TTL

```ts
export class TTLCache<K, V> {
  #map = new Map<K, { value: V; expires: number }>();
  constructor(private max: number, private ttlMs: number, private now = () => Date.now()) {}
  get(key: K): V | undefined {
    const e = this.#map.get(key);
    if (!e) return undefined;
    if (e.expires <= this.now()) { this.#map.delete(key); return undefined; }   // lazy expiry
    this.#map.delete(key); this.#map.set(key, e);                              // LRU refresh
    return e.value;
  }
  set(key: K, value: V, ttlMs = this.ttlMs) {
    this.#map.delete(key);
    this.#map.set(key, { value, expires: this.now() + ttlMs });
    while (this.#map.size > this.max) this.#map.delete(this.#map.keys().next().value!);
  }
}
```

Bounded by size (no unbounded growth, Part 3, Q9), expired entries removed lazily (optionally sweep with an `unref()`ed interval). Per-process only: invalidations do not reach other replicas, so keep TTLs short or use Redis.

# Part 15 — System Design Interview Preparation

## How to run a 45-minute design interview

| Minutes | Do | Avoid |
| --- | --- | --- |
| 0–5 | Clarify users, core features, scale, latency, consistency, compliance | drawing boxes before you know the problem |
| 5–10 | Estimate traffic and storage with stated assumptions | false precision |
| 10–25 | High-level architecture, API, data model | naming every AWS service |
| 25–40 | Deep dive on the hardest part (consistency, hot spots, failure) | spreading thin across everything |
| 40–45 | Failure modes, observability, evolution, trade-offs | claiming the design has no weaknesses |

**Estimation template:** daily active users x actions per user / 86,400 = average rps; x 3–10 for peak; payload size x writes per day x retention = storage. Round aggressively and say so.

## D1 \[S\] Design a scalable REST API (product catalogue, 50M reads/day)

&#91;embedded content: Catalogue API architecture · D1\]

- **Requirements:** read-heavy (100:1), p99 < 200 ms, eventual consistency acceptable for listings, strong for price at checkout.
- **Estimates:** 50M / 86,400 ≈ 580 rps average, about 3,000 rps peak.
- **Architecture:** CDN for public GETs (`Cache-Control`, `ETag`), stateless Node API, Redis cache-aside, PostgreSQL primary with read replicas, search in OpenSearch fed by change events.
- **API:** `GET /products?category=&after=&limit=` (cursor pagination), `GET /products/:id`, admin `PUT /products/:id` with `If-Match` (optimistic concurrency).
- **Failures:** cache down (DB must survive the miss load: rate-limit, serve stale), replica lag (read price from the primary at checkout).
- **Trap:** caching personalised responses at the CDN; forgetting `Vary` headers.

## D2 \[S\] Design an authentication and session management service

&#91;embedded content: Authentication service architecture · D2\]

- **Requirements:** email/password, social login (OIDC), MFA, sessions across web and mobile, revocation, audit.
- **Design:** auth service owns `users`, `credentials` (Argon2id hashes), `sessions` / `refresh_tokens` (hashed, rotating, family IDs to detect reuse), `mfa_factors`, `audit_events`. Web: `HttpOnly` session cookie; mobile and service APIs: short-lived access JWT (5–15 min, asymmetric keys, published JWKS) + rotating refresh token.
- **Flows:** login → rate-limit by IP and account → verify hash → MFA challenge → issue session → audit. Refresh → validate and rotate; reuse of an old refresh token revokes the whole family (theft signal).
- **Security:** breached-password checks, constant-time comparisons, generic error messages, CSRF protection for cookie flows, key rotation for JWT signing, account recovery that cannot be socially engineered.
- **Trap:** "JWTs are stateless so we don't need a database" — then you cannot log anyone out.

## D3 \[S\] Design a digital wallet with a reliable transaction ledger

- **Requirements:** balances in multiple currencies, top-up, P2P transfer, withdrawal; never lose or create money; full audit trail; idempotent APIs; regulators will ask for history.
- **Core idea:** **double-entry ledger**. Balances are derived from immutable entries; every transaction has entries that sum to zero.

```sql
CREATE TABLE accounts (
  id uuid PRIMARY KEY, owner_id uuid NOT NULL, currency char(3) NOT NULL,
  balance_minor bigint NOT NULL DEFAULT 0,          -- cached, updated in the same transaction
  version bigint NOT NULL DEFAULT 0,
  CHECK (balance_minor >= 0)                         -- for user accounts that cannot go negative
);
CREATE TABLE transactions (
  id uuid PRIMARY KEY, idempotency_key text NOT NULL, type text NOT NULL, status text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (idempotency_key)
);
CREATE TABLE entries (
  id bigserial PRIMARY KEY, transaction_id uuid NOT NULL REFERENCES transactions(id),
  account_id uuid NOT NULL REFERENCES accounts(id),
  amount_minor bigint NOT NULL,                      -- negative = debit, positive = credit
  created_at timestamptz NOT NULL DEFAULT now()
);
-- invariant: SUM(amount_minor) per transaction_id = 0 (enforced in code + nightly check)
```

- **Transfer (one DB transaction):** insert transaction with the idempotency key (conflict → return the existing result); lock both accounts `FOR UPDATE` **in ID order** (avoid deadlocks); check funds; insert two entries; update cached balances; commit; publish `TransferCompleted` via outbox.
- **External money movement** (card top-ups, bank withdrawals): a state machine (`pending → succeeded | failed`) with provider idempotency keys, webhooks verified by signature, and daily **reconciliation** against provider statements.
- **Money:** integers in minor units (`bigint`), never floats (Part 1, Q16); currency on every account; FX as its own transaction with explicit rates.
- **Scale:** one PostgreSQL primary handles thousands of transfers per second; hot accounts (a merchant receiving many payments) can be split into sub-accounts and swept.
- **Traps:** updating a balance column without entries (no audit trail); read-then-write balance checks without locks (Part 2, Q23); retries without idempotency (double transfers).

## D4 \[S\] Design a payment processing system

&#91;embedded content: Payment processing architecture · D4\]

- **Requirements:** accept card and wallet payments (for example bKash or Nagad in Bangladesh alongside cards) through several providers; authorise, capture, refund; webhooks; PCI scope minimised.
- **Design:** a payments service with a `payment_intents` state machine (`created → requires_action → authorised → captured → refunded/failed`); provider adapters behind one interface (ports and adapters, Part 12, Q10); tokenisation by the provider (card data never touches your servers, keeping PCI scope small); idempotency keys on every provider call; webhook endpoint that verifies signatures, stores raw events, deduplicates by event ID and processes asynchronously.
- **Consistency:** the provider is the source of truth for money movement; your state converges through webhooks plus periodic polling for stuck intents plus daily reconciliation.
- **Failures:** timeouts after the provider charged (retry with the same idempotency key, or query status); duplicate webhooks (dedupe); out-of-order webhooks (state machine ignores invalid transitions); provider outage (failover only for new payments, never mid-payment).
- **Trap:** treating the redirect back from the payment page as proof of payment; only the verified webhook or a server-side status check is.

## D5 \[S\] Design an email and SMS notification platform

- **Requirements:** 20M notifications/day, templates, user preferences, priorities (OTP within seconds, marketing within hours), multiple providers, delivery tracking.
- **Estimates:** about 230/s average, peaks of several thousand/s during campaigns.
- **Design:** `POST /notifications` (or events) → validate, dedupe key, persist → per-channel, per-priority queues (Kafka topics or BullMQ queues) → channel workers render templates, check preferences and quiet hours, call providers with per-provider token-bucket rate limits and circuit breakers, fail over between providers → store attempts and status; provider callbacks update delivery status.
- **Data:** `notifications (id, user_id, channel, template, dedupe_key UNIQUE, status, priority)`, `attempts`, `preferences`, `suppressions` (bounces, unsubscribes).
- **Failures:** provider outage (breaker + secondary), campaign floods starving OTPs (separate high-priority queue and workers), duplicate sends (dedupe key + provider idempotency), poison messages (DLQ).
- **Trap:** sending synchronously from the API request path.

## D6 \[S\] Design a high-traffic voting or contest platform

&#91;embedded content: Voting platform architecture · D6\]

- **Requirements:** a live TV contest; 2M users vote in a 10-minute window; one vote per user per round; results shown live; must be fair and auditable.
- **Estimates:** peak could be 20,000–50,000 votes/s in the first minute.
- **Design:** CDN-served static voting page; auth token issued before the window opens (do not hit the auth service during the spike); vote API validates the token and round, then writes to a fast path: Redis `SET round:{r}:voter:{userId} NX` (dedupe) + `INCR` per option, or append to Kafka partitioned by round; asynchronous persistence of every vote to durable storage for audit; live results read from Redis counters and pushed via SSE/WebSocket at a fixed interval (not per vote).
- **Fairness and abuse:** rate limiting, bot detection, device and account checks, signed vote receipts; final official count recomputed from the durable log, not the cache.
- **Failures:** Redis loss (rebuild counts from the log), regional failover, queue backlog (results lag, votes are never dropped).
- **Trap:** a relational `UPDATE options SET votes = votes + 1` per vote creates a hot-row bottleneck.

## D7 \[S\] Design a file upload and media processing service

&#91;embedded content: Media upload and processing architecture · D7\]

- **Requirements:** images and videos up to 2 GB, thumbnails and transcodes, private by default, resumable uploads.
- **Design:** client asks the API for a **pre-signed upload URL** (S3 multipart for large files) so bytes never pass through Node; storage emits an event on completion → queue → processing workers (sharp for images, FFmpeg via `execFile` for video, in isolated containers) → outputs stored under generated keys → metadata row updated (`pending → processing → ready | failed`) → client notified (webhook, SSE or polling). Downloads via short-lived signed URLs or a CDN with signed cookies.
- **Security:** validate type by magic bytes in the worker, size limits in the pre-signed policy, malware scanning before publishing, no user-controlled paths (Part 5, Q10), strip EXIF location data.
- **Failures:** incomplete multipart uploads (lifecycle rule aborts them), worker crash (idempotent job keyed by file ID), poison files (DLQ).
- **Trap:** proxying 2 GB uploads through Node with `multer` memory storage.

## D8 \[S\] Design a real-time notification system

&#91;embedded content: Real-time notification architecture · D8\]

WebSocket or SSE gateway tier (Part 13, S10) subscribed to a pub/sub backbone; a notification service persists notifications (`notifications` table with `read_at`) and publishes to user channels; on reconnect the client sends its last seen ID and receives missed items from the database; presence via heartbeats in Redis with TTLs; fan-out for large groups done by workers, not by the gateway; push notifications (APNs/FCM) for offline users. **Trap:** using the WebSocket as the only store (offline users lose notifications).

## D9 \[S\] Design a background job processing platform

&#91;embedded content: Background job platform architecture · D9\]

- **Requirements:** many teams submit jobs (reports, exports, emails), scheduling (cron and delays), priorities, retries, visibility, fairness between tenants.
- **Design:** API to submit jobs with an idempotency key → jobs persisted (PostgreSQL `jobs` table, or BullMQ/SQS for the queue with Postgres for metadata) → per-type queues with priorities → worker pools autoscaled on queue depth and age (KEDA) → retries with backoff, timeouts, heartbeats so stuck jobs are reclaimed (visibility timeout / lease) → DLQ with replay tooling → status API and dashboard.
- **Fairness:** per-tenant concurrency limits so one tenant's 1M-job backfill does not starve others.
- **Scheduling:** a single leader (or the queue's repeatable jobs) creates scheduled jobs; at-least-once execution, so handlers are idempotent.
- **Postgres as a queue:** `SELECT ... FOR UPDATE SKIP LOCKED` works well up to moderate throughput and keeps jobs transactional with business data.

## D10 \[S\] Design a multi-tenant SaaS backend

&#91;embedded content: Multi-tenant SaaS architecture · D10\]

- **Requirements:** thousands of small tenants and a few large enterprise tenants; data isolation; per-tenant configuration, limits and billing; some tenants need data residency.
- **Design:** shared PostgreSQL with `tenant_id` on every table and **row-level security** policies (`USING (tenant_id = current_setting('app.tenant_id')::uuid)`) set per transaction from the authenticated token; tenant context carried in `AsyncLocalStorage`; per-tenant rate limits and quotas; large or regulated tenants moved to dedicated databases (cell-based architecture) behind a tenant-to-cell routing table; tenant-aware logs, metrics and traces; per-tenant export and deletion jobs.
- **Migrations:** run per cell; backward compatible.
- **Traps:** trusting an `X-Tenant-Id` header from clients; cache keys without tenant prefixes (cross-tenant data leaks); background jobs that forget to set tenant context.

## D11 \[S\] Design an audit logging platform

&#91;embedded content: Audit logging architecture · D11\]

- **Requirements:** record who did what, when, to which resource, from where; tamper-evident; searchable by compliance teams; retained for years; must not slow the main request path.
- **Design:** services emit structured audit events (actor, action, resource, before/after diff or hash, request ID, IP, timestamp) through the outbox → Kafka topic → consumer writes to an append-only store (partitioned PostgreSQL table or object storage in Parquet with an index in OpenSearch) → hash chaining or periodic signed digests make tampering detectable; WORM storage (S3 Object Lock) for compliance retention.
- **Privacy:** no secrets; PII minimised or tokenised; access to the audit log is itself audited.
- **Failures:** the outbox guarantees events are not lost if Kafka is down; consumers are idempotent by event ID.
- **Trap:** writing audit rows synchronously in the request transaction to a separate database (two-phase problem) or logging audit events only to application logs with short retention.

## D12 \[S\] Design a reporting and analytics system

&#91;embedded content: Reporting and analytics architecture · D12\]

- **Requirements:** dashboards over months of transactional data; ad-hoc filters; reports must not slow the production database.
- **Design:** never run heavy analytics on the OLTP primary. Stream changes (CDC with Debezium, or outbox events) into a warehouse or OLAP store (ClickHouse, BigQuery, Snowflake, or PostgreSQL replicas with pre-aggregated tables for smaller scale); scheduled transformations (dbt) build aggregates; the report API queries aggregates with caching; large exports run as background jobs that stream CSV to object storage and email a signed link.
- **Freshness:** decide per report (real time, minutes, daily) and label it in the UI.
- **Trap:** a "quick" report endpoint doing `SELECT ... GROUP BY` over 200M rows on the primary during business hours.

## Common system design traps (all designs)

1. Not stating assumptions and estimates.
2. No idempotency on writes that can be retried.
3. Assuming exactly-once delivery from a queue.
4. A single relational hot row for counters.
5. Synchronous calls to slow third parties in the request path.
6. No plan for reconciliation between your state and an external system's.
7. Ignoring observability and failure modes until asked.
8. Over-engineering: microservices, Kafka and Kubernetes for 50 requests per second.

**Evaluated:** correctness, clarity, tests, handling of async edge cases. **Red flags:** silent typing for 30 minutes; ignoring errors and rejections; no tests.

## M5 Debugging round (45 min)

You get a broken service and logs. Practise: the leaked listener (Part 3, D1), the blocking hash (Part 2, D1), the duplicate jobs on deploy (Part 2, D2), the leaked pool connection (Part 10, D1), the unclosed file streams (Part 5, D1).

**Method to narrate:** reproduce → read the evidence (logs, metrics) → form a hypothesis → confirm with a targeted experiment → fix the root cause → add a test and an alert. **Red flags:** changing code at random; fixing the symptom (restart cron, bigger heap) and stopping there.

## M6 Performance investigation round (45 min)

Prompt: "p99 latency tripled at peak, p50 is fine, CPU is 40%." Expected flow: clarify scope → RED and runtime metrics → ELU vs latency to classify (CPU vs waiting) → traces to find where time goes → pool waits and dependency latency → CPU profile if ELU is high → one change at a time under the same load (Part 11, Q7–Q10, D1; Part 2, Q29).

**Evaluated:** systematic, evidence-driven reasoning. **Red flags:** jumping to "add more servers" or "rewrite in Go" without data.

## M7 System design round (45–60 min)

Practise D3 (wallet ledger), D5 (notifications), D6 (voting spike) and D10 (multi-tenant SaaS) from Part 15 with the timing table at the top of Part 15.

**Evaluated:** requirement clarification, reasonable estimates, a coherent simple design, a deep dive on the hardest part, failure handling, and honest trade-offs. **Red flags:** no numbers; no data model; ignoring consistency for money.

## M8 Behavioural and technical leadership round (45 min)

Prepare 6–8 stories in **STAR** form (situation, task, action, result) with numbers:

- An incident you led: what broke, how you mitigated, what changed afterwards.
- A technical decision you made and later regretted, and what you learned.
- Disagreeing with a senior engineer or manager, and how it was resolved.
- Mentoring someone, or raising a team's standard (reviews, testing, on-call).
- Delivering under a deadline while managing technical debt.
- A cross-team project with conflicting priorities.

**Evaluated:** ownership, judgement, communication, learning from failure, impact beyond your own code. **Red flags:** blaming others; "we" with no clear personal contribution; no measurable outcome.
