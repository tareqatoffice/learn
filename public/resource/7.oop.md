## 1. Core OOP concepts

The four pillars are tools for one goal: keeping change local. Encapsulation protects state, abstraction hides decisions, inheritance shares contracts, and polymorphism lets callers ignore which implementation they hold.

### 1.1 Encapsulation

**Definition.** Encapsulation bundles state with the behaviour that changes it, and lets only that behaviour change it. The point is protecting **invariants** — rules that must always hold, such as "balance never goes negative".

**The common mistake.** Private fields plus a getter and setter for each one is *not* encapsulation. A public setter lets any caller break the invariant; you have only renamed the field.

```ts
// Weak: "encapsulated" but every rule lives in callers
class Account {
  private _balance = 0;
  get balance() { return this._balance; }
  set balance(v: number) { this._balance = v; } // anyone can set -500
}

// Strong: the object owns its rules
class Account {
  #balance = 0;                       // [JS-runtime] truly private
  get balance() { return this.#balance; }

  deposit(amount: number): void {
    if (amount <= 0) throw new RangeError("Deposit must be positive");
    this.#balance += amount;
  }

  withdraw(amount: number): void {
    if (amount <= 0) throw new RangeError("Withdrawal must be positive");
    if (amount > this.#balance) throw new Error("Insufficient funds");
    this.#balance -= amount;
  }
}
```

**What happens internally.** `#balance` is stored in a per-object private slot. Code outside the class body cannot even name it; `acc.#balance` is a *syntax error*. TypeScript's `private` keyword, by contrast, is erased: `(acc as any)._balance` works at runtime.

**Immutability as encapsulation.** An immutable value object cannot break its invariant after construction, so you validate once.

```ts
class Money {
  private constructor(readonly amount: number, readonly currency: string) {}
  static of(amount: number, currency: string): Money {
    if (!Number.isInteger(amount)) throw new Error("Use minor units (cents)");
    return new Money(amount, currency);
  }
  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("Currency mismatch");
    return new Money(this.amount + other.amount, this.currency);
  }
}
```

**When not to bother.** Plain data crossing a boundary (DTOs, JSON payloads, config) has no behaviour to protect. Wrapping it in setters adds ceremony and no safety.

**Follow-ups interviewers ask**

- "Is a class with only getters encapsulated?" — Only if it also returns copies or immutable values. Returning an internal array lets callers mutate it.
- "Where should validation live?" — In the object whose invariant it protects, plus at system boundaries for input shape.

### 1.2 Abstraction

**Definition.** Abstraction exposes what an object does and hides how. Encapsulation is about *protecting state*; abstraction is about *hiding decisions* (which database, which algorithm, which vendor).

```ts
interface PaymentGateway {
  charge(orderId: string, amount: Money, idempotencyKey?: string): Promise<ChargeResult>;
}
// Callers never learn whether this is Stripe, bKash, or a fake.
```

**A good abstraction** is named after the caller's need, is small, and stays stable when implementations change.

**A leaky abstraction** forces callers to know implementation details anyway. Examples: a `Repository` that returns ORM entities with lazy-loading proxies; a `Cache` whose callers must handle Redis-specific errors; a `FileStore` that only works if paths use `/`.

**Interfaces vs. abstract classes**

|  | Interface (TS) | Abstract class |
| --- | --- | --- |
| Exists at runtime | No \[TS-compile\] | Yes |
| Can hold state / shared code | No | Yes |
| Multiple per class | Yes (`implements A, B`) | One (`extends`) |
| Usable with `instanceof` | No | Yes |
| Best for | Contracts between modules | Sharing a skeleton among a closed family |

**Mistake:** creating an interface for every class "for testability". One implementation and no second consumer usually means the interface is premature. Extract it when the second implementation or a real seam appears.

### 1.3 Inheritance

**Definition.** A subclass reuses and specialises a base class. It brings two things that are often confused: **interface inheritance** (subtype can stand in for base) and **implementation inheritance** (subtype reuses base code).

```ts
abstract class Shape {
  abstract area(): number;
  describe(): string { return `${this.constructor.name} with area ${this.area().toFixed(2)}`; }
}
class Circle extends Shape {
  constructor(private readonly r: number) { super(); }
  area() { return Math.PI * this.r ** 2; }
}
```

**Constructor chaining.** A derived constructor must call `super()` before touching `this` \[JS-runtime: ReferenceError otherwise\]. The base constructor runs first.

**Fragile base class problem.** A subclass that depends on *how* its base class calls its own methods breaks when that internal call pattern changes. The classic case, from Bloch's *Effective Java*:

```java
class CountingSet<E> extends HashSet<E> {
  int added = 0;
  @Override public boolean add(E e) { added++; return super.add(e); }
  @Override public boolean addAll(Collection<? extends E> c) { added += c.size(); return super.addAll(c); }
}
var s = new CountingSet<String>();
s.addAll(List.of("a", "b", "c"));
System.out.println(s.added);   // 6, not 3 — the inherited addAll calls add() once per element
```

Nothing in `HashSet`'s documented contract promises that `addAll` uses `add`; the subclass silently depends on an implementation detail. Remove the `addAll` override and it works today, but would break if a future version stopped calling `add`. The fix is composition: wrap a `Set` and forward calls. Trap T3 shows the JavaScript version, where the `Set` constructor calls `add`.

**Use inheritance when** the subtype is truly substitutable (passes the LSP test), the hierarchy is shallow (≤ 2 levels), and you control both base and subclasses.

**Prefer composition when** you want to reuse behaviour but not the type, behaviour varies on more than one axis, or behaviour must change at runtime.

### 1.4 Polymorphism

**Definition.** One interface, many implementations; the caller does not change when the implementation does.

| Kind | Mechanism | TS/JS example | Resolved at |
| --- | --- | --- | --- |
| Subtype | Overriding + dynamic dispatch | `shape.area()` | Runtime |
| Parametric | Generics | `Repository<T>` | Compile time (erased in TS/Java) |
| Ad hoc | Overloading | TS overload signatures | Compile time |
| Duck / structural | Shape match | Any object with `area()` | TS: compile; JS: runtime |

**Dynamic dispatch in JS.** `obj.method()` looks up `method` on the object, then up its prototype chain; the first match wins, and `this` is bound to `obj`. That is how overriding works — there is no vtable in the language spec.

&#91;embedded content: Method lookup for class Dog extends Animal · 4 objects in the chain\]

Overriding is simply a nearer match on the chain; `super.speak()` starts the search one link further along.

**Overloading in TS** is only signatures; there is one implementation that must branch:

```ts
function area(r: number): number;
function area(w: number, h: number): number;
function area(a: number, b?: number): number {
  return b === undefined ? Math.PI * a * a : a * b;
}
```

In Java and C#, overloads are separate methods chosen at **compile time** from the *static* argument types. Overriding is chosen at **runtime** from the *dynamic* receiver type. Mixing the two is a favourite trap (section 9).

**Replacing conditionals with polymorphism** — the canonical refactor:

```ts
// Before
function fee(type: string, amt: number) {
  if (type === "card") return amt * 0.029;
  if (type === "bkash") return amt * 0.0185;
  throw new Error("unknown");
}
// After
interface FeePolicy { fee(amt: number): number }
const card: FeePolicy = { fee: a => a * 0.029 };
const bkash: FeePolicy = { fee: a => a * 0.0185 };
```

**When not to:** two stable cases that never grow. A `switch` with exhaustiveness checking on a discriminated union is often clearer in TypeScript, and the compiler flags a missing case.

**Textbook vs. practice.** Textbooks list four pillars. Practitioners mostly talk about **cohesion, coupling, and substitutability** — the pillars are mechanisms for getting those right.

## 2. Classes, objects and object relationships

A class is a blueprint plus a namespace for shared behaviour; an object is a runtime instance with its own identity and state. In JavaScript, a class is syntax over a constructor function and a prototype object.

### 2.1 What `new` actually does in JavaScript

```ts
class User {
  static count = 0;            // lives on User (the constructor)
  role = "member";             // own property, set per instance
  constructor(public name: string) { User.count++; }
  greet() { return `Hi, ${this.name}`; } // lives on User.prototype
}
const u = new User("Rina");
```

1. A new empty object is created whose `[[Prototype]]` is `User.prototype`.
2. For a base class, class fields (`role`) are defined on it, then the constructor body runs with `this` bound to it.
3. For a derived class, `this` does not exist until `super()` returns; fields are defined right after `super()` returns.
4. The object is returned (unless the constructor explicitly returns another object).

Result: `u` owns `name` and `role`. `greet` is shared via the prototype. `count` is on `User`, not on `u` — `u.count` is `undefined`.

### 2.2 Instance vs. static members

|  | Instance member | Static member |
| --- | --- | --- |
| Lives on | Each object (fields) or prototype (methods) | The class/constructor itself |
| `this` refers to | The instance | The class it was called on |
| Inherited by subclasses | Yes, via prototype chain | Yes in JS/TS (`Sub.__proto__ === Base`); in Java static methods are *hidden*, not overridden |
| Good for | Behaviour tied to state | Factories, constants, pure helpers |

**Trap:** a static mutable field is global state. It leaks across tests and requests.

### 2.3 Identity vs. equality

- **Identity**: same object in memory. JS: `a === b` or `Object.is(a, b)` for objects.
- **Equality**: same *value* by a domain rule. JS has no built-in structural equality for objects; you write `equals()`.
- Java: `==` is identity for references, `.equals()` is value equality, and overriding `equals` requires overriding `hashCode`.
- C#: `record` types get value equality generated; classes default to reference equality.

```ts
// Money from "Shared types": an immutable value object with equals()
const a = Money.of(500, "BDT"), b = Money.of(500, "BDT");
a === b;               // false — two different objects
a.equals(b);           // true — same value
new Set([a, b]).size;  // 2 — Set compares objects by identity (SameValueZero)
```

**Entities vs. value objects** (DDD): entities are equal by identity (an `id`), value objects by their attributes.

### 2.4 Reference vs. value semantics

In JS, primitives (`number`, `string`, `boolean`, `bigint`, `symbol`, `undefined`, `null`) are copied by value. Objects, arrays and functions are passed as **a copy of the reference** ("call by sharing"). Mutating through the parameter changes the caller's object; reassigning the parameter does not.

```js
function f(o) { o.x = 1; o = { x: 2 }; }
const a = { x: 0 }; f(a); a.x; // 1
```

C# `struct` and Java primitives (and Java value classes in preview) have value semantics; C# `ref`/`out` parameters pass the variable itself.

### 2.5 Shallow vs. deep copy

| Technique | Depth | Keeps class prototype? | Notes |
| --- | --- | --- | --- |
| `{...obj}` / `Object.assign` | Shallow | No (plain object) | Copies own enumerable props only; getters are invoked, not copied |
| `structuredClone(obj)` | Deep | No | Handles Map, Set, Date, cycles; throws on functions; drops `#private` and prototype |
| `JSON.parse(JSON.stringify(obj))` | Deep | No | Dates become strings; drops `undefined`, functions, Map/Set; throws on cycles |
| Custom `clone()` method | You decide | Yes | The only option that preserves invariants and type |

**Senior answer:** for domain objects, prefer immutability so copying is rarely needed; when needed, give the class its own `clone()` or `with(...)` method so it controls its invariants.

### 2.6 Mutable vs. immutable objects

- `readonly` \[TS-compile\] prevents reassignment in TypeScript only.
- `Object.freeze` \[JS-runtime\] prevents changes but is **shallow** — nested objects stay mutable; in strict mode writes throw `TypeError`, in sloppy mode they fail silently.
- `ReadonlyArray<T>` / `readonly T[]` \[TS-compile\] removes mutating methods from the type.
- Immutable objects are thread-safe, cacheable and safe to share; the cost is allocation on every change.

### 2.7 Object lifecycle and initialization order

Order for `new Derived()` in TS/JS (ES2022 class fields):

1. `Derived` constructor starts; any code before `super()` cannot use `this`.
2. `super()` → base field initializers → base constructor body.
3. Back in `Derived`: derived field initializers → rest of derived constructor body.
4. Static fields and `static {}` blocks run once, when the class definition is evaluated.

Java is the same shape (fields after `super()`). **C# differs:** derived field initializers run *before* the base constructor. Destruction: JS and Java are garbage-collected with no deterministic destructor; use `try/finally`, `using` (TS 5.2 explicit resource management with `Symbol.dispose`), Java try-with-resources, or C# `IDisposable` / `using`.

### 2.8 Object relationships

| Relationship | Meaning | Lifetime | Code shape | UML |
| --- | --- | --- | --- | --- |
| Dependency | A *uses* B briefly | Unrelated | B as parameter or local | dashed arrow |
| Association | A *knows* B | Independent | B held as a field | solid line |
| Aggregation | A *has* B, B shared | B outlives A | B passed in from outside | hollow diamond |
| Composition | A *owns* B | B dies with A | A creates B internally | filled diamond |
| Inheritance | A *is a* B | — | `extends` | hollow triangle |
| Realization | A *implements* B | — | `implements` | dashed hollow triangle |

&#91;embedded content: UML relationships around Order · inheritance, aggregation, composition, dependency\]

Read the diamond end as the owner: a hollow diamond means Order shares Customer; a filled one means Order creates and deletes its lines.

```ts
class Order {
  #lines: OrderLine[] = [];                 // composition: Order creates and owns lines
  constructor(readonly customer: Customer) {} // association/aggregation: customer exists independently
  addLine(p: Product, qty: number) { this.#lines.push(new OrderLine(p, qty)); }
  total(calc: TaxCalculator) {              // dependency: used, not stored
    return calc.apply(this.#lines.reduce((s, l) => s + l.subtotal(), 0));
  }
}
```

**Practical note.** In garbage-collected languages, aggregation vs. composition is about *ownership and who controls the lifecycle* (who creates, who deletes, who may share), not about memory. Interviewers want you to say which object is responsible for creating and deleting the part.

**Bidirectional relationships** (Order ↔ Customer) double the places that must stay consistent. Make one side the owner and derive the other through a query, or keep both updates inside one method.

**Circular dependencies** between modules show up in JS as `undefined` imports at load time (ESM live bindings in TDZ, CommonJS partial exports). Fix by extracting a shared abstraction or inverting one dependency.

## 3. SOLID principles

SOLID is five heuristics for managing change in object-oriented code. They are not laws: applied everywhere, they produce interface explosions; ignored, they produce God classes. The senior skill is knowing where change is likely.

### 3.1 Single Responsibility Principle (SRP)

**Definition.** A module should have one reason to change — more precisely, it should answer to one *actor* (one group of stakeholders), per Robert C. Martin's later formulation. It does **not** mean "a class does one thing" or "one method per class".

**Bad**

```ts
class InvoiceService {
  calculateTotal(inv: Invoice): number { /* tax + discount rules — Finance */ }
  renderPdf(inv: Invoice): Buffer { /* layout — Design/Ops */ }
  save(inv: Invoice): Promise<void> { /* SQL — DBA */ }
  emailToCustomer(inv: Invoice): Promise<void> { /* SMTP — Support */ }
}
```

**Why it violates SRP.** Four actors can request changes. A tax rule change forces retesting of PDF and email code, and two teams edit the same file and merge-conflict.

**Refactor step by step**

1. List each method's actor.
2. Move each actor's code into its own class: `InvoicePricing`, `InvoicePdfRenderer`, `InvoiceRepository`, `InvoiceMailer`.
3. Keep a thin coordinator if a workflow needs all four.

```ts
class InvoicePricing { total(inv: Invoice): Money { /* ... */ } }
class InvoicePdfRenderer { render(inv: Invoice): Buffer { /* ... */ } }
interface InvoiceRepository { save(inv: Invoice): Promise<void> }
class InvoiceMailer { constructor(private mail: MailSender) {} send(inv: Invoice, pdf: Buffer) { /* ... */ } }

class IssueInvoice {               // use case: orchestrates, holds no rules
  constructor(private pricing: InvoicePricing, private pdf: InvoicePdfRenderer,
              private repo: InvoiceRepository, private mailer: InvoiceMailer) {}
  async execute(inv: Invoice) {
    inv.finalize(this.pricing.total(inv));
    await this.repo.save(inv);
    await this.mailer.send(inv, this.pdf.render(inv));
  }
}
```

**Trade-offs.** Over-splitting scatters one concept across ten files. Split when actors or change rates actually differ, not by method count.

**Tricky question:** "Does a `UserRepository` with `findById`, `findByEmail`, `save`, `delete` violate SRP?" — No. One actor (persistence of users), one reason to change (storage schema).

### 3.2 Open/Closed Principle (OCP)

**Definition.** Software entities should be open for extension and closed for modification: add new behaviour by adding code, not by editing tested code.

**Bad**

```ts
class ShippingCost {
  calculate(method: string, kg: number): number {
    switch (method) {
      case "standard": return 60 + kg * 10;
      case "express":  return 120 + kg * 20;
      // every new courier = edit this class, retest all cases
      default: throw new Error("Unknown method");
    }
  }
}
```

**Better (Strategy + registry)**

```ts
interface ShippingRate { readonly code: string; cost(kg: number): number }

class ShippingCost {
  #rates = new Map<string, ShippingRate>();
  register(rate: ShippingRate) { this.#rates.set(rate.code, rate); return this; }
  calculate(code: string, kg: number) {
    const rate = this.#rates.get(code);
    if (!rate) throw new Error(`Unknown method ${code}`);
    return rate.cost(kg);
  }
}
const shipping = new ShippingCost()
  .register({ code: "standard", cost: kg => 60 + kg * 10 })
  .register({ code: "express",  cost: kg => 120 + kg * 20 });
```

**Misconceptions**

- OCP does not forbid editing code; bug fixes and refactors are modifications. It targets *predictable variation*.
- You cannot be closed against every change. Choose the axis that actually varies (couriers, payment providers, report formats).
- In TypeScript, a discriminated union + exhaustive `switch` is *closed for extension* but gives compile-time safety. Pick it when the set of cases is owned by you and changes rarely; pick Strategy when third parties or plugins add cases.

### 3.3 Liskov Substitution Principle (LSP)

**Definition.** If S is a subtype of T, any code that works with T must keep working when given an S — without knowing it. This is *behavioural* subtyping, not just matching method signatures.

**The contract rules**

- Preconditions cannot be **strengthened** in the subtype (it must accept everything the base accepts).
- Postconditions cannot be **weakened** (it must guarantee everything the base guarantees).
- Invariants of the base must be preserved.
- No new exceptions the caller was not prepared for.
- History constraint: a subtype must not allow state changes the base forbids (e.g. a mutable subclass of an immutable base).

**Bad — the classic**

```ts
class Rectangle {
  constructor(protected w: number, protected h: number) {}
  setWidth(w: number) { this.w = w; }
  setHeight(h: number) { this.h = h; }
  area() { return this.w * this.h; }
}
class Square extends Rectangle {
  setWidth(w: number) { this.w = w; this.h = w; }
  setHeight(h: number) { this.w = h; this.h = h; }
}
function stretch(r: Rectangle) { r.setWidth(5); r.setHeight(4); console.assert(r.area() === 20); }
stretch(new Square(1, 1)); // area is 16 — the caller's assumption broke
```

**Why.** `Rectangle` promises that width and height vary independently (a postcondition of `setHeight`). `Square` weakens it.

**Fixes**

1. Make shapes immutable: `withWidth(w)` returns a new shape; `Square.withWidth` returns a `Rectangle`. No broken promise.
2. Drop the inheritance: both implement `Shape { area(): number }`.

**Real-world LSP violations**

- A `ReadOnlyRepository extends Repository` that throws on `save()`.
- A payment provider subclass that throws `NotSupported` for refunds.
- Java's `Collections.unmodifiableList` returning a `List` whose `add` throws `UnsupportedOperationException` — a well-known, deliberate trade-off in the JDK.
- A subclass that requires `init()` to be called before use when the base did not.

**Detection test.** If client code contains `if (x instanceof Subclass)` to avoid misbehaviour, LSP is probably broken.

### 3.4 Interface Segregation Principle (ISP)

**Definition.** Clients should not be forced to depend on methods they do not use.

**Bad**

```ts
interface Printer {
  print(doc: Doc): void;
  scan(): Image;
  fax(to: string, doc: Doc): void;
}
class BasicPrinter implements Printer {
  print(doc: Doc) { /* ok */ }
  scan(): Image { throw new Error("Not supported"); }   // also an LSP smell
  fax() { throw new Error("Not supported"); }
}
```

**Better — role interfaces**

```ts
interface Printer { print(doc: Doc): void }
interface Scanner { scan(): Image }
interface Fax { fax(to: string, doc: Doc): void }
class OfficeMachine implements Printer, Scanner, Fax { /* ... */ }
class BasicPrinter implements Printer { /* ... */ }
function printAll(p: Printer, docs: Doc[]) { docs.forEach(d => p.print(d)); }
```

**Trade-offs.** Over-segregating creates one-method interfaces everywhere and hard-to-discover APIs. Segregate by **client role**, not by method. In TypeScript, structural typing gives you ISP almost for free: a function can declare `Pick<Repo, "findById">` and accept the full repository.

### 3.5 Dependency Inversion Principle (DIP)

**Definition.** High-level policy should not depend on low-level detail; both should depend on abstractions, and the abstraction should be **owned by the high-level side**.

**Bad**

```ts
import { Pool } from "pg";
class SignupService {
  #db = new Pool();                     // policy creates detail
  #smtp = new SmtpClient("smtp.host");  // hard to test, hard to swap
  async signup(email: string) {
    await this.#db.query("INSERT INTO users(email) VALUES($1)", [email]);
    await this.#smtp.send(email, "Welcome!");
  }
}
```

**Better**

```ts
// Owned by the domain/application layer
export interface UserStore { add(email: string): Promise<void> }
export interface Notifier { welcome(email: string): Promise<void> }

export class SignupService {
  constructor(private users: UserStore, private notify: Notifier) {}
  async signup(email: string) {
    await this.users.add(email);
    await this.notify.welcome(email);
  }
}

// Infrastructure layer implements the domain's interfaces
class PgUserStore implements UserStore { constructor(private pool: Pool) {} async add(e: string) { /* SQL */ } }
class EmailNotifier implements Notifier { async welcome(e: string) { /* SMTP */ } }

// Composition root (main.ts) wires them
const service = new SignupService(new PgUserStore(new Pool()), new EmailNotifier());
```

The arrows from infrastructure now point up into the domain: Postgres and SMTP can change without touching `SignupService`.

**DIP vs. DI vs. IoC**

| Term | What it is |
| --- | --- |
| Dependency Inversion (principle) | Direction of source-code dependencies points toward policy |
| Dependency Injection (technique) | Dependencies are passed in rather than created |
| Inversion of Control (broader idea) | A framework calls your code, not the reverse; DI containers are one form |

You can do DI without DIP (injecting a concrete `PgPool`), and DIP without a container (manual wiring in `main.ts`).

**Trade-offs.** Every abstraction is indirection. Invert at real boundaries — I/O, third-party services, volatile policy — not between two stable in-process classes.

### 3.6 SOLID trick questions

- **"Which SOLID principle does a `NotImplementedError` violate?"** Usually LSP (subtype breaks contract) and often ISP (the interface was too fat).
- **"Is OCP achievable in a TS discriminated union?"** Not for new cases, but you gain exhaustiveness checking. It's a deliberate trade.
- **"Can you follow SRP and still have a God object?"** Yes, if the "one responsibility" is defined too broadly, like "manages orders".
- **"Does DIP mean every class needs an interface?"** No. It means volatile details sit behind abstractions owned by stable policy.

## 4. Design patterns — creational

Creational patterns control *who decides which concrete class to build and how*. In TypeScript, many of them shrink to a function or a module, and saying so in an interview signals seniority.

Each pattern below follows the same order: problem → naive code → pattern → trade-offs → testing → misuse.

### 4.1 Singleton

**Problem.** Exactly one instance must exist and be globally reachable (a config, a connection pool, a logger).

**Naive:** `export let config = loadConfig();` mutated from everywhere.

**Pattern**

```ts
class AppConfig {
  static #instance?: AppConfig;
  private constructor(readonly values: Readonly<Record<string, string>>) {}
  static get(): AppConfig {
    return (this.#instance ??= new AppConfig(Object.freeze({ ...process.env } as Record<string,string>)));
  }
}
```

**The JS reality.** An ES module is evaluated once per module graph, so `export const config = new AppConfig(...)` is already a singleton — per process, or per bundle copy (duplicated packages in `node_modules` can produce two).

**Why it is criticised.** It is hidden global state: hard to replace in tests, creates invisible coupling, and breaks under parallel test runners that share the module cache.

**Better alternative.** Create one instance in the composition root and *inject* it. You get "one instance" without global access. DI containers call this "singleton lifetime".

**Interview trap:** "Is a Java singleton thread-safe?" Lazy initialisation without synchronisation is not. Idiomatic answers: an `enum` singleton, or the holder-class idiom; double-checked locking requires a `volatile` field.

### 4.2 Factory Method

**Problem.** A base workflow needs to create an object, but subclasses decide which concrete class.

```ts
abstract class ReportExporter {
  export(rows: Row[]): Buffer {
    const writer = this.createWriter();     // the factory method
    rows.forEach(r => writer.write(r));
    return writer.finish();
  }
  protected abstract createWriter(): RowWriter;
}
class CsvExporter extends ReportExporter { protected createWriter() { return new CsvWriter(); } }
class XlsxExporter extends ReportExporter { protected createWriter() { return new XlsxWriter(); } }
```

**Often confused with** a *simple factory* (a function with a `switch` that returns instances). Simple factories are fine and more common; Factory Method specifically uses inheritance to defer the choice.

**When not to use:** if you only vary the created object, pass a factory function instead: `new ReportExporter(() => new CsvWriter())`. That is composition and avoids a subclass per format.

### 4.3 Abstract Factory

**Problem.** Create *families* of related objects that must match (a UI theme's Button + Dialog; a cloud provider's Storage + Queue + Secrets).

```ts
interface CloudKit { storage(): BlobStore; queue(): MessageQueue; secrets(): SecretStore }
class AwsKit implements CloudKit { storage() { return new S3Store(); } queue() { return new SqsQueue(); } secrets() { return new AwsSecrets(); } }
class LocalKit implements CloudKit { storage() { return new FsStore(); } queue() { return new InMemoryQueue(); } secrets() { return new EnvSecrets(); } }

function bootstrap(kit: CloudKit) { return new UploadService(kit.storage(), kit.queue()); }
```

**Trade-off.** Adding a new *family* is easy (new kit). Adding a new *product type* (e.g. `cache()`) changes every kit — the factory interface itself is not closed for that axis.

### 4.4 Builder

**Problem.** Constructing an object needs many optional parameters, ordered steps, or validation of the combination (the "telescoping constructor").

```ts
class HttpRequest {
  private constructor(readonly method: string, readonly url: string,
                      readonly headers: ReadonlyMap<string, string>, readonly body?: string,
                      readonly timeoutMs = 5000) {}
  static builder(url: string) { return new HttpRequestBuilder(url); }
  /** @internal */ static _create(b: HttpRequestBuilder) { return new HttpRequest(b.method, b.url, new Map(b.headers), b.body, b.timeoutMs); }
}
class HttpRequestBuilder {
  method = "GET"; headers = new Map<string, string>(); body?: string; timeoutMs = 5000;
  constructor(readonly url: string) {}
  post(body: string) { this.method = "POST"; this.body = body; return this; }
  header(k: string, v: string) { this.headers.set(k, v); return this; }
  timeout(ms: number) { this.timeoutMs = ms; return this; }
  build(): HttpRequest {
    if (this.method === "GET" && this.body) throw new Error("GET cannot have a body");
    return HttpRequest._create(this);
  }
}
const req = HttpRequest.builder("/orders").post("{}").header("Content-Type", "application/json").build();
```

**TS alternative.** An options object with defaults usually replaces Builder: `new HttpRequest({ url, method: "POST", body })`. Use a Builder when construction has *steps*, cross-field validation, or produces an immutable result from a mutable staging area (test data builders are the most common legitimate use).

### 4.5 Prototype

**Problem.** Create new objects by copying a configured instance, when construction is expensive or the concrete class is unknown to the caller.

```ts
interface Cloneable<T> { clone(): T }
class DocumentTemplate implements Cloneable<DocumentTemplate> {
  constructor(public title: string, public sections: string[], public styles: Map<string, string>) {}
  clone() { return new DocumentTemplate(this.title, [...this.sections], new Map(this.styles)); } // deep enough
}
const invoiceTpl = new DocumentTemplate("Invoice", ["Header", "Lines", "Total"], new Map([["font", "Inter"]]));
const copy = invoiceTpl.clone(); copy.sections.push("Notes"); // template unaffected
```

**Do not confuse** the Prototype *pattern* with JavaScript's prototype *chain*. `Object.create(proto)` shares behaviour by delegation; it does not copy state.

**Pitfall.** Shallow clones that share nested mutable state — the bug the pattern was meant to prevent.

### 4.6 Choosing a creational approach

| Need | Simplest TS choice | Pattern if it outgrows that |
| --- | --- | --- |
| One shared instance | Create once in `main.ts`, inject | Singleton (rarely) |
| Choose class by input | Map of constructors / simple factory | Factory Method, Registry |
| Matching families | Object of factory functions | Abstract Factory |
| Many optional params | Options object with defaults | Builder |
| Copy a configured object | `clone()` method | Prototype + registry |

## 5. Design patterns — structural

Structural patterns arrange objects so that interfaces fit together. Four of them (Adapter, Decorator, Proxy, Facade) look almost identical in code — a class wrapping another — and differ only in **intent**. Interviewers test exactly that.

| Pattern | Wraps | Interface exposed | Intent |
| --- | --- | --- | --- |
| Adapter | One object | A *different* interface the client expects | Make incompatible things fit |
| Decorator | One object | The *same* interface | Add behaviour, stackable |
| Proxy | One object | The *same* interface | Control access (lazy, cache, auth, remote) |
| Facade | A subsystem of many objects | A *new, simpler* interface | Hide complexity |
| Bridge | — (two hierarchies) | Abstraction holds implementor | Vary two axes independently |
| Composite | Children of the same type | Same as leaves | Treat trees uniformly |
| Flyweight | Shared intrinsic state | Same | Save memory across many instances |

### 5.1 Adapter — payment providers

**Problem.** Your domain expects `PaymentGateway`; each provider SDK has its own shape.

```ts
// PaymentGateway and ChargeResult: see Shared types
interface PaymentGateway { charge(orderId: string, amount: Money, idempotencyKey?: string): Promise<ChargeResult> }

// Third-party shape you cannot change
declare class BkashSdk { createPayment(p: { amount: string; merchantInvoiceNumber: string }): Promise<{ paymentID: string; statusCode: string }> }

class BkashAdapter implements PaymentGateway {
  constructor(private sdk: BkashSdk) {}
  async charge(orderId: string, amount: Money) {
    const r = await this.sdk.createPayment({ amount: (amount.amount / 100).toFixed(2), merchantInvoiceNumber: orderId });
    return { ref: r.paymentID, ok: r.statusCode === "0000" };
  }
}
```

The adapter is also an **anti-corruption layer**: provider vocabulary stops at its boundary. (The bKash field names here are illustrative; check the provider's current API docs.)

### 5.2 Bridge

**Problem.** Two independent axes of variation would cause a class explosion: `EmailAlert`, `SmsAlert`, `EmailReport`, `SmsReport`…

```ts
interface Channel { send(to: string, body: string): Promise<void> }     // implementor
abstract class Message {                                                // abstraction
  constructor(protected channel: Channel) {}
  abstract deliver(to: string): Promise<void>;
}
class Alert extends Message { deliver(to: string) { return this.channel.send(to, "[ALERT] Disk full"); } }
class WeeklyReport extends Message { deliver(to: string) { return this.channel.send(to, "Your weekly summary..."); } }
// 2 messages × 3 channels = 5 classes, not 6; scales as M + N instead of M × N
```

### 5.3 Composite

**Problem.** Treat individual items and groups the same way (files/folders, menu items/submenus, permission/permission groups, bundle pricing).

```ts
interface PriceComponent { price(): number }
class Product implements PriceComponent { constructor(private p: number) {} price() { return this.p; } }
class Bundle implements PriceComponent {
  #items: PriceComponent[] = [];
  constructor(private discount = 0) {}
  add(c: PriceComponent) { this.#items.push(c); return this; }
  price() { return this.#items.reduce((s, c) => s + c.price(), 0) * (1 - this.discount); }
}
const combo = new Bundle(0.1).add(new Product(500)).add(new Bundle().add(new Product(200)));
combo.price(); // 630
```

**Design question:** should `add` be on the shared interface? Putting it there ("transparency") lets clients treat all nodes alike but forces leaves to throw. Keeping it on `Bundle` ("safety") is the usual TS choice.

### 5.4 Decorator — caching, retries, logging

```ts
interface RateProvider { rate(from: string, to: string): Promise<number> }

class CachedRates implements RateProvider {
  #cache = new Map<string, { v: number; at: number }>();
  constructor(private inner: RateProvider, private ttlMs = 60_000, private now = Date.now) {}
  async rate(from: string, to: string) {
    const k = `${from}:${to}`, hit = this.#cache.get(k);
    if (hit && this.now() - hit.at < this.ttlMs) return hit.v;
    const v = await this.inner.rate(from, to);
    this.#cache.set(k, { v, at: this.now() });
    return v;
  }
}
class RetryingRates implements RateProvider {
  constructor(private inner: RateProvider, private attempts = 3) {}
  async rate(f: string, t: string) {
    let last: unknown;
    for (let i = 0; i < this.attempts; i++) { try { return await this.inner.rate(f, t); } catch (e) { last = e; } }
    throw last;
  }
}
const rates = new CachedRates(new RetryingRates(new HttpRates()));  // order matters
```

**Interview follow-up:** "Why not subclass `HttpRates`?" Subclassing fixes one combination at compile time; decorators compose any combination at runtime. **Pitfalls:** identity checks fail (`rates instanceof HttpRates` is false), and deep stacks are hard to debug.

TypeScript *decorators* (`@log`, TS 5.0 standard decorators) are a language feature for annotating classes/members; they can implement the pattern but are not the same thing.

### 5.5 Facade

```ts
class CheckoutFacade {
  constructor(private cart: CartService, private stock: InventoryService,
              private pay: PaymentGateway, private orders: OrderRepository, private mail: Mailer) {}
  async checkout(userId: string) {
    const cart = await this.cart.get(userId);
    await this.stock.reserve(cart.items);
    const charge = await this.pay.charge(cart.id, cart.total);
    if (!charge.ok) { await this.stock.release(cart.items); throw new Error("Payment failed"); }
    const order = await this.orders.create(cart, charge.ref);
    await this.mail.orderConfirmed(order);
    return order;
  }
}
```

**Risk:** a facade that grows logic becomes a God object. Keep it as coordination only; business rules belong in domain objects.

### 5.6 Flyweight

**Problem.** Millions of similar objects (map tiles, text glyphs, game particles) waste memory duplicating shared state.

```ts
class TreeType { constructor(readonly species: string, readonly texture: Uint8Array) {} } // intrinsic, shared
class TreeTypeFactory {
  static #pool = new Map<string, TreeType>();
  static get(species: string, load: () => Uint8Array) {
    let t = this.#pool.get(species);
    if (!t) this.#pool.set(species, (t = new TreeType(species, load())));
    return t;
  }
}
type Tree = { x: number; y: number; type: TreeType }; // extrinsic per instance
```

Flyweights must be **immutable**, or one change affects every user. JS string interning and V8 hidden classes are engine-level flyweights.

### 5.7 Proxy

**Kinds:** virtual (lazy load), protection (authorisation), remote (RPC stub), caching, logging.

```ts
class AuthorizedReportService implements ReportService {
  constructor(private inner: ReportService, private user: CurrentUser) {}
  async salaryReport(deptId: string) {
    if (!this.user.can("reports:salary", deptId)) throw new ForbiddenError();
    return this.inner.salaryReport(deptId);
  }
}
```

JavaScript also has a built-in `Proxy` object that intercepts property access at runtime (used by Vue reactivity, MobX, Immer). It is a metaprogramming tool that *can* implement the pattern.

**Proxy vs. Decorator answer:** same structure; Proxy controls *whether/when* the real call happens and usually manages the real object's lifecycle; Decorator *adds* behaviour and is meant to be stacked by the client.

## 6. Design patterns — behavioral

Behavioral patterns decide *who does what and who talks to whom*. In JavaScript, functions are first-class objects, so Strategy, Command and Observer often collapse to a callback — know both forms.

### 6.1 Strategy

**Problem.** An algorithm varies (discounts, pricing, routing, sorting) and you don't want a growing `if/else`.

```ts
interface DiscountStrategy { apply(subtotal: number, ctx: { isMember: boolean }): number }
const none: DiscountStrategy = { apply: s => s };
const percent = (p: number): DiscountStrategy => ({ apply: s => s * (1 - p / 100) });
const memberOnly = (inner: DiscountStrategy): DiscountStrategy =>
  ({ apply: (s, c) => (c.isMember ? inner.apply(s, c) : s) });

class Checkout { constructor(private discount: DiscountStrategy = none) {}
  total(sub: number, ctx: { isMember: boolean }) { return Math.round(this.discount.apply(sub, ctx)); } }
new Checkout(memberOnly(percent(10))).total(1000, { isMember: true }); // 900
```

**Strategy vs. State:** both swap an object behind an interface. In Strategy, the *client* picks the algorithm; in State, the *object itself* switches as its state changes.

### 6.2 Observer

**Problem.** When one object changes, unknown others must react, without the subject depending on them.

```ts
type Listener<E> = (event: E) => void;
class EventBus<Events extends Record<string, unknown>> {
  #listeners = new Map<keyof Events, Set<Listener<any>>>();
  on<K extends keyof Events>(type: K, fn: Listener<Events[K]>) {
    if (!this.#listeners.has(type)) this.#listeners.set(type, new Set());
    this.#listeners.get(type)!.add(fn);
    return () => this.#listeners.get(type)!.delete(fn);   // unsubscribe handle
  }
  emit<K extends keyof Events>(type: K, event: Events[K]) {
    for (const fn of [...(this.#listeners.get(type) ?? [])]) fn(event); // copy: listeners may unsubscribe mid-loop
  }
}
const bus = new EventBus<{ orderPlaced: { orderId: string } }>();
const off = bus.on("orderPlaced", e => console.log("email for", e.orderId));
```

**Pitfalls interviewers probe:** memory leaks from never unsubscribing (lapsed listener); one listener throwing stops the rest; ordering assumptions; synchronous cascades that re-enter the subject. **Pub/Sub** differs by putting a broker between publisher and subscriber, often across processes.

### 6.3 Command (with undo)

```ts
interface Command { execute(): void; undo(): void }
class TextDoc { text = ""; }
class InsertText implements Command {
  constructor(private doc: TextDoc, private at: number, private s: string) {}
  execute() { this.doc.text = this.doc.text.slice(0, this.at) + this.s + this.doc.text.slice(this.at); }
  undo() { this.doc.text = this.doc.text.slice(0, this.at) + this.doc.text.slice(this.at + this.s.length); }
}
class Editor {
  #done: Command[] = []; #undone: Command[] = [];
  run(c: Command) { c.execute(); this.#done.push(c); this.#undone = []; } // new action clears redo
  undo() { const c = this.#done.pop(); if (c) { c.undo(); this.#undone.push(c); } }
  redo() { const c = this.#undone.pop(); if (c) { c.execute(); this.#done.push(c); } }
}
```

Uses: undo/redo, job queues, macros, audit logs, transactional outboxes. Commands are data, so they can be serialised and replayed.

### 6.4 State

```ts
interface OrderState { pay(o: Order): void; ship(o: Order): void; cancel(o: Order): void; readonly name: string }
class Order { state: OrderState = new Pending();
  pay() { this.state.pay(this); } ship() { this.state.ship(this); } cancel() { this.state.cancel(this); } }
const illegal = (s: string, a: string) => { throw new Error(`Cannot ${a} when ${s}`); };
class Pending implements OrderState { name = "pending";
  pay(o: Order) { o.state = new Paid(); } ship() { illegal(this.name, "ship"); } cancel(o: Order) { o.state = new Cancelled(); } }
class Paid implements OrderState { name = "paid";
  pay() { illegal(this.name, "pay"); } ship(o: Order) { o.state = new Shipped(); } cancel(o: Order) { o.state = new Cancelled(); /* + refund */ } }
class Shipped implements OrderState { name = "shipped";
  pay() { illegal(this.name, "pay"); } ship() { illegal(this.name, "ship"); } cancel() { illegal(this.name, "cancel"); } }
class Cancelled implements OrderState { name = "cancelled";
  pay() { illegal(this.name, "pay"); } ship() { illegal(this.name, "ship"); } cancel() {} }
```

**Trade-off.** For 3–5 states, a transition table (`Record<State, Partial<Record<Event, State>>>`) is shorter, data-driven and easy to persist. Use State classes when each state carries substantial *behaviour*, not just allowed transitions.

### 6.5 Template Method

```ts
abstract class DataImport {
  async run(file: Buffer) {                 // invariant skeleton — don't override
    const rows = this.parse(file);
    const valid = rows.filter(r => this.validate(r));
    await this.save(valid);
    this.afterImport?.(valid.length);       // optional hook
  }
  protected abstract parse(f: Buffer): Row[];
  protected abstract validate(r: Row): boolean;
  protected abstract save(rows: Row[]): Promise<void>;
  protected afterImport?(n: number): void;
}
```

The inheritance-based sibling of Strategy. Its weakness: subclasses depend on the base's internal call order (fragile base class). The composition alternative passes `parse`, `validate`, `save` as strategies into one `DataImport` class.

### 6.6 Chain of Responsibility

```ts
type Handler = (req: Request, next: () => Promise<Response>) => Promise<Response>;
function chain(handlers: Handler[], final: (r: Request) => Promise<Response>) {
  return (req: Request) => {
    const dispatch = (i: number): Promise<Response> =>
      i === handlers.length ? final(req) : handlers[i](req, () => dispatch(i + 1));
    return dispatch(0);
  };
}
// Express/Koa middleware, approval workflows (manager → director → CFO), validation pipelines
```

Each handler either handles, passes on, or both. Risk: a request falls off the end silently — always define a terminal handler.

### 6.7 Iterator

JavaScript builds this into the language via `Symbol.iterator` and generators:

```ts
class Paginated<T> implements AsyncIterable<T> {
  constructor(private fetchPage: (cursor?: string) => Promise<{ items: T[]; next?: string }>) {}
  async *[Symbol.asyncIterator]() {
    let cursor: string | undefined;
    do { const p = await this.fetchPage(cursor); yield* p.items; cursor = p.next; } while (cursor);
  }
}
for await (const order of new Paginated(api.listOrders)) { /* hides paging */ }
```

### 6.8 Mediator

Objects talk through a mediator instead of to each other, turning an N×N web into a star. Examples: a chat room, an air-traffic controller, form fields whose enabled state depends on each other, and in-process command buses (MediatR in .NET). **Risk:** the mediator becomes a God object.

```ts
class CheckoutForm {   // mediator
  constructor(private country: Field, private state: Field, private submit: Button) {
    country.onChange(() => this.changed(country));
    state.onChange(() => this.changed(state));
  }
  private changed(_: Field) {
    this.state.setEnabled(this.country.value === "US");
    this.submit.setEnabled(Boolean(this.country.value) && (this.country.value !== "US" || Boolean(this.state.value)));
  }
}
```

### 6.9 Memento

Capture an object's internal state so it can be restored, without exposing that state.

```ts
class Editor {
  #text = ""; #cursor = 0;
  type(s: string) { this.#text += s; this.#cursor = this.#text.length; }
  save() { const t = this.#text, c = this.#cursor; return Object.freeze({ restore: (e: Editor) => { e.#text = t; e.#cursor = c; } }); }
}
```

The memento is opaque to the caretaker (the history list). Memory cost is the main trade-off; Command-based undo stores diffs instead of snapshots.

### 6.10 Visitor

**Problem.** Add new operations over a *stable* class hierarchy without editing each class. It uses **double dispatch**: the element picks the visitor method by its own type.

```ts
interface ShapeVisitor<R> { circle(c: Circle): R; rect(r: Rect): R }
interface Shape { accept<R>(v: ShapeVisitor<R>): R }
class Circle implements Shape { constructor(readonly r: number) {} accept<R>(v: ShapeVisitor<R>) { return v.circle(this); } }
class Rect implements Shape { constructor(readonly w: number, readonly h: number) {} accept<R>(v: ShapeVisitor<R>) { return v.rect(this); } }
const area: ShapeVisitor<number> = { circle: c => Math.PI * c.r ** 2, rect: r => r.w * r.h };
const toSvg: ShapeVisitor<string> = { circle: c => `<circle r="${c.r}"/>`, rect: r => `<rect width="${r.w}" height="${r.h}"/>` };
```

**Trade-off (the expression problem).** Visitor makes new *operations* cheap and new *types* expensive (every visitor changes). Polymorphic methods are the reverse. In TypeScript, a discriminated union with exhaustive `switch` is the idiomatic Visitor; Java 21's sealed interfaces + pattern-matching `switch` play the same role.

### 6.11 Interpreter

Represent a small grammar as a class per rule, with `evaluate(context)`. Useful for rule engines and filter DSLs (`price > 1000 AND category = "electronics"`).

```ts
interface Expr { eval(ctx: Record<string, unknown>): boolean }
class Gt implements Expr { constructor(private f: string, private v: number) {} eval(c: Record<string, unknown>) { return Number(c[this.f]) > this.v; } }
class Eq implements Expr { constructor(private f: string, private v: unknown) {} eval(c: Record<string, unknown>) { return c[this.f] === this.v; } }
class And implements Expr { constructor(private a: Expr, private b: Expr) {} eval(c: Record<string, unknown>) { return this.a.eval(c) && this.b.eval(c); } }
const rule = new And(new Gt("price", 1000), new Eq("category", "electronics"));
```

Appropriate only for simple grammars. For anything larger, use a parser generator or an existing expression language; never `eval` user input.

### 6.12 Quick selection guide

| Symptom in code | Pattern to consider |
| --- | --- |
| `switch` on a type code, repeated in many places | Strategy or polymorphism |
| Boolean flags like `isPaid`, `isShipped` with illegal combinations | State (or a transition table) |
| "Notify X, Y and Z when this changes" | Observer / domain events |
| Need undo, queueing, or audit of actions | Command |
| Same algorithm skeleton, steps differ | Template Method, or Strategy for composition |
| Ordered checks where any step may stop the request | Chain of Responsibility |
| Many objects tightly wired to each other | Mediator |

## 7. Enterprise and application patterns

GoF patterns organise a handful of collaborating objects. Enterprise patterns (Fowler's *Patterns of Enterprise Application Architecture*, Evans's DDD) organise an application around a domain and its persistence. Architectural patterns (layers, Clean/Hexagonal, CQRS, event sourcing) shape the whole system. Name the level when you answer.

| Level | Examples | Scope |
| --- | --- | --- |
| GoF design pattern | Strategy, Adapter, Observer | A few classes |
| Enterprise / DDD pattern | Repository, Unit of Work, Domain Event, Specification | A module or bounded context |
| Architectural pattern | Layered, Clean, Hexagonal, CQRS, Event Sourcing | The application or service |

### 7.1 Dependency Injection

Dependencies arrive through the constructor (preferred), a method parameter, or a property. Constructor injection makes required dependencies explicit and objects valid on creation.

```ts
// Manual DI in a composition root — no container needed
const pool = new Pool({ connectionString: env.DATABASE_URL });
const orders = new PgOrderRepository(pool);
const gateway = new BkashAdapter(new BkashSdk(env.BKASH_KEY));
const placeOrder = new PlaceOrder(new PgUnitOfWork(pool), gateway, new OutboxEventPublisher(pool));
```

Containers (NestJS, InversifyJS, tsyringe; Spring in Java; Microsoft.Extensions.DependencyInjection in C#) automate wiring and lifetimes (singleton, scoped per request, transient). **Anti-pattern:** a *service locator* (`Container.get("orders")` inside business code) hides dependencies and makes tests depend on global setup.

### 7.2 Repository

A collection-like interface for aggregates, defined in domain terms; it hides the database.

```ts
interface OrderRepository {
  byId(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;
  nextId(): OrderId;
}
```

**Senior notes.** One repository per **aggregate root**, not per table. Return domain objects, not ORM rows. Avoid generic `Repository<T>` with `findAll(filter: any)` — it leaks query concerns back into callers. A repository over an ORM that already is a repository (e.g. Prisma, EF Core `DbSet`) is justified only if you want domain-shaped methods or to keep the ORM out of the domain layer.

### 7.3 Unit of Work

Tracks changes made during a business transaction and commits them atomically.

```ts
interface UnitOfWork { run<T>(work: (repos: { orders: OrderRepository; stock: StockRepository }) => Promise<T>): Promise<T> }
class PgUnitOfWork implements UnitOfWork {
  constructor(private pool: Pool) {}
  async run<T>(work: (r: any) => Promise<T>) {
    const client = await this.pool.connect();
    try {
      await client.query("BEGIN");
      const result = await work({ orders: new PgOrderRepository(client), stock: new PgStockRepository(client) });
      await client.query("COMMIT");
      return result;
    } catch (e) { await client.query("ROLLBACK"); throw e; }
    finally { client.release(); }
  }
}
```

ORMs implement this for you (Hibernate session, EF Core `DbContext.SaveChanges`, TypeORM `EntityManager.transaction`).

### 7.4 Specification

A business rule as a composable object, usable both in memory and translated to queries.

```ts
abstract class Spec<T> {
  abstract isSatisfiedBy(c: T): boolean;
  and(o: Spec<T>): Spec<T> { const a = this; return new (class extends Spec<T> { isSatisfiedBy(c: T) { return a.isSatisfiedBy(c) && o.isSatisfiedBy(c); } })(); }
}
class OverdueInvoice extends Spec<Invoice> { constructor(private today: Date) { super(); } isSatisfiedBy(i: Invoice) { return !i.paid && i.dueDate < this.today; } }
class LargeInvoice extends Spec<Invoice> { isSatisfiedBy(i: Invoice) { return i.total > 100_000; } }
const escalate = new OverdueInvoice(new Date()).and(new LargeInvoice());
```

### 7.5 DTO (Data Transfer Object)

A behaviour-free shape for crossing a boundary (HTTP, queue, process). DTOs decouple the API contract from the domain model so you can refactor one without breaking the other. Validate DTOs at the edge (zod, class-validator), then map to domain objects. Do not add business logic to DTOs, and do not return domain entities directly from controllers.

### 7.6 Service Layer / Application Services (use cases)

A thin layer that defines the application's operations: load aggregates, call domain behaviour, save, publish events. It owns transactions and authorisation, not business rules.

```ts
class PlaceOrder {
  constructor(private uow: UnitOfWork, private pay: PaymentGateway, private events: EventPublisher) {}
  async execute(cmd: PlaceOrderCommand): Promise<string> {
    return this.uow.run(async ({ orders, stock }) => {
      const order = Order.place(orders.nextId(), cmd.customerId, cmd.lines);   // rules live in Order
      await stock.reserve(order.lines);
      const charge = await this.pay.charge(order.id, order.total(), "order:" + order.id);
      if (!charge.ok) throw new Error("Payment failed");                       // UoW rolls back the reservation
      order.markPaid(charge.ref);
      await orders.save(order);
      await this.events.publishAll(order.pullEvents());
      return order.id;
    });
  }
}
```

**Trade-off to mention:** this charges inside a database transaction, so locks are held during a network call. Production systems usually reserve and commit first, then charge, then confirm (a saga). It is kept in one transaction here so the example stays short.

**Smell:** services full of `if` statements over entity fields, while entities are bags of getters — the *anemic domain model*.

### 7.7 Domain Services

Domain logic that does not naturally belong to one entity, usually because it spans several (e.g. `TransferService.transfer(from: Account, to: Account, amount)`, or a pricing calculation using customer tier + product + promotion). Stateless, named in the domain's language, no infrastructure.

### 7.8 Domain Events

A record of something that happened in the domain, named in past tense (`OrderPlaced`, `PaymentCaptured`). Aggregates record events; the application layer publishes them after commit.

```ts
abstract class AggregateRoot { #events: DomainEvent[] = [];
  protected record(e: DomainEvent) { this.#events.push(e); }
  pullEvents() { const e = this.#events; this.#events = []; return e; } }
```

**Reliability:** publishing after commit can still lose events if the process crashes in between. The **transactional outbox** pattern writes events to an outbox table in the same transaction, and a relay publishes them.

### 7.9 Factory (DDD sense)

Encapsulates creation of a complex aggregate with its invariants: `Order.place(...)`, `LoanApplicationFactory.fromForm(...)`. Unlike GoF factories, the motivation is *valid construction*, not *choosing a subclass*.

### 7.10 CQRS

Command Query Responsibility Segregation: separate models for writes (commands that enforce invariants) and reads (queries shaped for screens). Can be as simple as two sets of classes over one database, or as complex as separate read stores fed by events.

- **Use when** reads and writes have very different shapes or load (dashboards over a transactional core).
- **Avoid when** the app is CRUD; you double the code and add eventual consistency for nothing.

### 7.11 Event Sourcing

State is stored as an append-only sequence of events; current state is a fold over them.

```ts
type WalletEvent = { type: "Credited"; amount: number } | { type: "Debited"; amount: number };
class Wallet {
  balance = 0;
  static from(history: WalletEvent[]) { const w = new Wallet(); history.forEach(e => w.apply(e)); return w; }
  apply(e: WalletEvent) { this.balance += e.type === "Credited" ? e.amount : -e.amount; }
  debit(amount: number): WalletEvent {
    if (amount > this.balance) throw new Error("Insufficient funds");
    const e: WalletEvent = { type: "Debited", amount }; this.apply(e); return e;
  }
}
```

**Gains:** full audit trail, time travel, rebuilding projections. **Costs:** event schema versioning, snapshots for long streams, eventual consistency, harder queries, GDPR deletion. It is usually paired with CQRS. Recommend it for ledgers and audit-heavy domains, not by default.

## 8. Language comparison: what is enforced, where

TypeScript is a compile-time type layer over JavaScript; almost every TS-only OOP feature disappears in the emitted JS. Java and C# enforce the same features in the runtime (JVM / CLR). Say which layer enforces a rule and you will avoid most language traps.

### 8.1 Feature matrix

| Feature | TypeScript (compile) | JavaScript (runtime) | Java 21 | C# 12 |
| --- | --- | --- | --- | --- |
| Classes | Yes | Yes (ES2015 syntax over prototypes) | Yes | Yes |
| Interfaces | Yes, erased | None | Yes, real types | Yes, real types |
| Abstract classes | `abstract` checked; erased | No keyword; emulate with `new.target` check | Yes | Yes |
| `private` | Checked only; accessible at runtime | `#field` is truly private | Enforced (reflection can bypass) | Enforced (reflection can bypass) |
| `protected` | Checked only | No equivalent | Package + subclasses | Subclasses (`protected internal` etc.) |
| `readonly` / `final` | `readonly` checked only | `Object.freeze`, getters without setters | `final` fields enforced | `readonly`, `init` accessors |
| Method overloading | Signatures only, one implementation | None (last definition wins) | True overloads, compile-time | True overloads, compile-time |
| Overriding | Implicit; `override` keyword with `noImplicitOverride` | Prototype lookup | Implicit for non-final; `@Override` optional check | Must be `virtual` + `override` |
| Multiple inheritance | Interfaces only; mixins via functions | Single prototype chain; mixins | Interfaces with `default` methods | Interfaces with default methods |
| Generics | Structural, erased | None | Erased (type erasure) | Reified (kept at runtime) |
| Typing | Structural | Dynamic (duck) | Nominal | Nominal |
| Runtime type info | None for TS types | `typeof`, `instanceof`, `constructor` | Reflection, `instanceof`, pattern matching | Reflection, `is`, pattern matching |
| Value equality types | — | — | `record` | `record`, `struct` |
| Sealed hierarchies | Discriminated unions | — | `sealed` + `permits` | `sealed` |

### 8.2 Structural vs. nominal typing

```ts
class Usd { constructor(public amount: number) {} }
class Bdt { constructor(public amount: number) {} }
const a: Usd = new Bdt(100);   // OK in TS — same shape
```

Java and C# reject this: types are equal by *name and declaration*. To get nominal behaviour in TS, add a private member or a brand:

```ts
type Bdt = number & { readonly __brand: "BDT" };
const bdt = (n: number) => n as Bdt;
class Usd2 { private readonly currency = "USD"; constructor(public amount: number) {} } // a private member makes the class nominal in TS
```

### 8.3 Interfaces vs. abstract classes in TS

- Use an **interface** for a contract between modules; zero runtime cost; a class can implement many.
- Use an **abstract class** when you need shared code or state, a runtime `instanceof` check, or a template method.
- Note: in TS a class can `implements` another *class* (its public shape) — useful for test fakes.

### 8.4 Inheritance mechanics in JS

```js
class Animal { speak() { return "..."; } }
class Dog extends Animal { speak() { return "Woof " + super.speak(); } }
// Under the hood:
Object.getPrototypeOf(Dog.prototype) === Animal.prototype; // true — instance methods chain
Object.getPrototypeOf(Dog) === Animal;                     // true — static members chain
```

`super.method()` uses the method's *home object* (fixed at definition), not `this`, to find the parent — which is why copying a method to another object keeps its original `super`.

### 8.5 Multiple inheritance alternatives

```ts
type Ctor<T = {}> = new (...args: any[]) => T;
const Timestamped = <B extends Ctor>(Base: B) => class extends Base { createdAt = new Date(); };
const SoftDeletable = <B extends Ctor>(Base: B) => class extends Base { deletedAt?: Date; softDelete() { this.deletedAt = new Date(); } };
class Entity { constructor(public id: string) {} }
class Customer extends SoftDeletable(Timestamped(Entity)) {}
```

Mixins linearise into a single chain, so the "diamond" is resolved by order. Prefer composition (`customer.audit = new AuditInfo()`) unless the behaviour really is the type's.

### 8.6 Runtime type checks

- `instanceof` walks the prototype chain. It fails across realms (iframes, `vm` contexts) and for duplicated package copies.
- TS interfaces cannot be checked at runtime; write a **type guard** (`function isOrder(x: unknown): x is Order`) or validate with a schema (zod).
- Java generics are erased: `List<String>` and `List<Integer>` are the same class at runtime. C# generics are reified: `typeof(List<int>) != typeof(List<string>)`.

### 8.7 Equality and immutability summary

|  | TS/JS | Java | C# |
| --- | --- | --- | --- |
| Reference equality | `===` | `==` | `ReferenceEquals` / `==` default for classes |
| Value equality | Hand-written `equals` | `equals` + `hashCode` | `Equals` + `GetHashCode`; automatic for `record` |
| Deep immutability | Manual (freeze recursively, or immutable libraries) | `record` is shallowly final | `record` with `init`; shallow |

### 8.8 Paradigm trade-offs

| Approach | Strength | Weakness | Fits |
| --- | --- | --- | --- |
| Object-oriented | Encapsulated state, polymorphic extension | Ceremony, hidden mutation | Rich domains with invariants, long-lived state |
| Functional | Pure functions, easy testing, composition | Modelling stateful entities, performance of copying | Data transformation, pipelines, UI state |
| Procedural | Direct and simple | Scales poorly as rules grow | Scripts, glue code, small utilities |

Modern TypeScript code mixes all three: immutable value types and pure functions inside, objects at the boundaries for state and polymorphism. Saying so is a senior signal.

### 8.9 Reflection and runtime metadata

Reflection lets code inspect and invoke members at runtime. Frameworks (DI containers, ORMs, serializers, test runners) depend on it; application code rarely should, because it bypasses encapsulation and defeats rename refactoring.

| Capability | TS / JS | Java 21 | C# 12 |
| --- | --- | --- | --- |
| List members | `Reflect.ownKeys(obj)`, `Object.getOwnPropertyNames(Proto.prototype)` | `getDeclaredMethods()`, `getDeclaredFields()` | `GetMethods()`, `GetProperties()` |
| Type at runtime | Prototype chain and `constructor.name` only; TS types are gone | Full class metadata; generic arguments erased | Full metadata, including generic arguments |
| Annotations | TS 5.0 standard decorators; legacy `experimentalDecorators` + `emitDecoratorMetadata` (with `reflect-metadata`) still power NestJS and TypeORM | Annotations with `RUNTIME` retention | Attributes |
| Invoke by name | `Reflect.apply(fn, obj, args)`, `obj[name](...)` | `Method.invoke` | `MethodInfo.Invoke` |
| Reach private state | `#field`: impossible; TS `private`: trivial | `setAccessible(true)`, limited by module encapsulation | `BindingFlags.NonPublic` |

**Interview point.** TypeScript constructor-injection containers need parameter types at runtime, which only the legacy decorator metadata emits; TS 5.0 standard decorators do not emit it. That is why NestJS still requires `experimentalDecorators`. Without metadata, containers fall back to explicit tokens (`@Inject(TOKEN)`) or manual wiring.

## 9. Tricky and trap questions

Every trap here comes from one of three gaps: TS types vs. JS runtime, construction order, or static vs. dynamic dispatch. Format for each: **Q** → **Answer** → **Why** → **Common wrong answer**.

### 9.1 Classes, objects and construction

**T1. Base constructor calls an overridden method**

```ts
class Base { constructor() { this.init(); } init() {} }
class Derived extends Base {
  items: string[] = [];
  init() { this.items.push("x"); }
}
new Derived();
```

- **Answer:** `TypeError: Cannot read properties of undefined (reading 'push')`.
- **Why:** dispatch is dynamic, so `Derived.init` runs *during* `super()`. Derived fields are initialised only after `super()` returns, so `items` is still `undefined`.
- **Wrong answer:** "It works and items is \['x'\]" (true in **C#**, where derived field initializers run before the base constructor; in **Java** the same code throws `NullPointerException`).
- **Rule:** never call overridable methods from a constructor.

**T2. Field redeclaration wipes a base-assigned value**

```ts
class Base { name: string; constructor() { this.name = "base"; } }
class Derived extends Base { name!: string; }   // just narrowing the type?
console.log(new Derived().name);
```

- **Answer:** `undefined` when `useDefineForClassFields` is true (the default for `target` ES2022+); `"base"` with older settings.
- **Why:** ES class fields use define semantics: the field declaration in `Derived` re-defines `name` as `undefined` after `super()` returns.
- **Fix:** `declare name: string;` — a type-only redeclaration that emits nothing.

**T3. Overriding `add` in a `Set` subclass**

```ts
class CountingSet<T> extends Set<T> {
  added = 0;
  add(v: T) { this.added++; return super.add(v); }
}
const s = new CountingSet([1, 2, 3]);
console.log(s.size, s.added);
```

- **Answer:** `3 0`.
- **Why:** the `Set` constructor calls `this.add` for each element *inside* `super()`. `this.added` is `undefined`, so `++` gives `NaN`; then the field initializer runs and sets `added = 0`.
- **Lesson:** a combined construction-order + fragile-base-class bug. Prefer wrapping (`class CountingSet { #inner = new Set() }`).

**T4. Static counters and inheritance**

```ts
class A { static count = 0; static inc() { this.count++; } }
class B extends A {}
B.inc(); B.inc(); A.inc();
console.log(A.count, B.count);
```

- **Answer:** `1 2`.
- **Why:** `this` in a static method is the class it was called on. `B.inc()` reads `B.count` (found on `A` via the constructor's prototype chain) and *writes* a new own property `B.count`. After that, B and A count separately.
- **Wrong answer:** `3 3` (assuming one shared static slot, as in Java, where statics are not inherited per subclass).

**T5. `new this()` in a static factory**

```ts
class Shape { static create() { return new this(); } name() { return "shape"; } }
class Circle extends Shape { name() { return "circle"; } }
console.log(Circle.create().name());
```

- **Answer:** `circle`. `this` is `Circle`. Typing tip: `static create<T extends Shape>(this: new () => T): T`.

**T6. Identity vs. equality**

```ts
const m = new Map<object, string>();
m.set({ id: 1 }, "one");
console.log(m.get({ id: 1 }), [1] === [1], Object.is(m, m));
```

- **Answer:** `undefined false true`. Map keys and `===` compare object identity. Use a primitive key (`"1"`) or a canonical instance.

**T7. Spread copies only one level**

```ts
const a = { n: 1, tags: ["x"] };
const b = { ...a };
b.n = 2; b.tags.push("y");
console.log(a.n, a.tags);
```

- **Answer:** `1 ["x", "y"]`. `tags` is a shared reference.

**T8. Spreading a class instance**

```ts
class Point { constructor(public x: number) {} double() { return this.x * 2; } }
const p = { ...new Point(2) };
p.double();
```

- **Answer:** TS compile error (`Property 'double' does not exist`); at runtime `TypeError: p.double is not a function`.
- **Why:** spread copies *own enumerable* properties. Methods live on the prototype. Same for `structuredClone` and `JSON` round trips — you get a plain object.

**T9. `Object.freeze` is shallow; `readonly` is compile-time**

```ts
class Team { readonly members: string[] = []; }
const t = Object.freeze(new Team());
t.members.push("Ana");      // allowed
(t as any).members = [];    // TypeError in strict mode (class code and ESM are strict)
```

- **Answer:** the push succeeds; the reassignment throws. Use `readonly string[]` for the type and return copies for runtime safety.

### 9.2 Encapsulation and access modifiers

**T10. TS `private` at runtime**

```ts
class Vault { private pin = 1234; #key = "k"; }
const v = new Vault();
console.log((v as any).pin, (v as any)["#key"], JSON.stringify(v));
```

- **Answer:** `1234 undefined {"pin":1234}`.
- **Why:** `private` is erased; `pin` is a normal own property and is serialised. `#key` lives in a private slot — it is not a property named `"#key"` and is not serialised.
- **Follow-up:** "Then why use TS `private`?" It is cheaper to debug, works with older targets, and has a `protected` sibling that subclasses can use — `#` fields have no equivalent (subclasses cannot see a parent's `#fields`).

**T11. Getters returning internal state**

```ts
class Cart { #items: string[] = []; get items() { return this.#items; } }
const c = new Cart(); c.items.push("hack");
```

- **Answer:** the private array is mutated. Return `[...this.#items]` or a `ReadonlyArray`, or expose behaviour (`add`, `count`) instead of data.

**T12. "Encapsulation and abstraction are the same thing."**

- **Answer:** No. Encapsulation protects state and invariants (a *boundary*). Abstraction exposes a simplified model and hides decisions (a *view*). A class can be well encapsulated with a poor abstraction (a perfect private-field class named `DataManager`) and vice versa.

### 9.3 `this`, arrow functions and methods

**T13. Detached method**

```ts
class Counter { count = 0; inc() { this.count++; } }
const c = new Counter();
[1, 2].forEach(c.inc);
```

- **Answer:** `TypeError: Cannot read properties of undefined (reading 'count')`.
- **Why:** `this` is decided by the *call site*. `forEach` calls the function with `this === undefined`, and class bodies are always strict mode.
- **Fixes:** `forEach(() => c.inc())`, `c.inc.bind(c)`, or define `inc = () => { this.count++; }` as an arrow field.

**T14. Arrow fields and `super`**

```ts
class A { greet = () => "A"; }
class B extends A { greet = () => "B+" + super.greet(); }
new B().greet();
```

- **Answer:** runtime `TypeError: (intermediate value).greet is not a function`; TypeScript also reports compile error TS2855 (a class field defined by the parent is not accessible in the child via `super`.
- **Why:** arrow fields are *own properties per instance*, not prototype methods. `super.greet` looks on `A.prototype`, where nothing exists.
- **Trade-off of arrow fields:** auto-bound `this`, but one function per instance (memory), not overridable through `super`, invisible to prototype spies (`jest.spyOn(A.prototype, "greet")` fails).

**T15. `this` inside a nested regular function**

```ts
class Timer { s = 0; start() { setInterval(function () { this.s++; }, 1000); } }
```

- **Answer:** TS error (`'this' implicitly has type 'any'` under `noImplicitThis`); at runtime the callback's `this` is not the `Timer`. Use an arrow function, which captures lexical `this`.

### 9.4 Type system traps (TypeScript)

**T16. Structural typing**

```ts
class Cat { name = ""; }
class Robot { name = ""; }
const pet: Cat = new Robot();   // compiles?
console.log(pet instanceof Cat);
```

- **Answer:** compiles; prints `false`. TS compares shapes; `instanceof` checks the prototype chain. A narrowing like `if (x instanceof Cat)` can therefore disagree with what the type checker allowed.

**T17. Method parameter bivariance**

```ts
interface Animal { name: string } interface Dog extends Animal { bark(): void }
interface Handler { handle(a: Animal): void }          // method syntax
const h: Handler = { handle(d: Dog) { d.bark(); } };  // compiles!
h.handle({ name: "cat" });                           // runtime TypeError
```

- **Why:** even with `strictFunctionTypes`, parameters declared with *method syntax* are checked bivariantly (a deliberate unsoundness for compatibility, e.g. with DOM types). Declare `handle: (a: Animal) => void` (property syntax) to get contravariant, sound checking.

**T18. Array covariance**

```ts
const dogs: Dog[] = [];
const animals: Animal[] = dogs;   // allowed
animals.push({ name: "cat" });
dogs[0].bark();                   // TypeError at runtime
```

- **Why:** TS arrays are covariant (unsound for writes). Java arrays are covariant too but throw `ArrayStoreException` at runtime; Java generics (`List<Dog>` → `List<Animal>`) are invariant and the assignment does not compile. Use `readonly Animal[]` when you only read.

**T19. `instanceof` an interface**

```ts
interface Payable { pay(): void }
if (x instanceof Payable) {}
```

- **Answer:** compile error: `'Payable' only refers to a type, but is being used as a value here`. Interfaces do not exist at runtime. Use a type guard: `const isPayable = (x: any): x is Payable => typeof x?.pay === "function";`.

**T20. Abstract classes after compilation**

- **Q:** Can JS code instantiate a TS abstract class? **Answer:** Yes — `abstract` is erased. If it matters, guard at runtime: `constructor() { if (new.target === Shape) throw new TypeError("abstract"); }`.

**T21. Excess property checks only apply to fresh literals**

```ts
interface Opts { retries: number }
const a: Opts = { retries: 3, retires: 5 };  // error: object literal may only specify known properties
const raw = { retries: 3, retires: 5 };
const b: Opts = raw;                          // OK — not a fresh literal
```

## 10. Code output and debugging questions

Predict first, then read the answer. Each output answer says whether the failure is a **compile-time error** (tsc/javac), a **runtime error**, or **silent wrong behaviour** — interviewers grade that distinction.

### 10.1 Predict the output

**O1. Class declarations and the TDZ**

```ts
const u = new User();
class User {}
```

Runtime `ReferenceError: Cannot access 'User' before initialization`. Classes are hoisted but not initialised (temporal dead zone), unlike function declarations. TS also reports "used before its declaration".

**O2. Patching a prototype after creation**

```js
class Dog { speak() { return "woof"; } }
const d = new Dog();
Dog.prototype.speak = () => "meow";
console.log(d.speak(), Object.hasOwn(d, "speak"));
```

`meow false`. Lookup happens at call time through the prototype chain, so every existing instance sees the change. This is why monkey-patching is dangerous and also how `jest.spyOn(Dog.prototype, "speak")` works.

**O3. Default parameters are evaluated per call (unlike Python)**

```js
function add(item, list = []) { list.push(item); return list; }
console.log(add(1), add(2));
```

`[1] [2]`. Each call gets a fresh array. In Python, a mutable default is shared — a common cross-language confusion.

**O4. `toString` and template literals**

```ts
class Taka { constructor(private c: number) {} toString() { return (this.c / 100).toFixed(2) + " BDT"; } valueOf() { return this.c; } }
const m = new Taka(1250);   // a local class, not the shared Money
console.log(`${m}`, m + 0, String(m));
```

`12.50 BDT 1250 12.50 BDT`. Template literals and `String()` use the *string* hint (`toString` first); `+` uses the *default* hint (`valueOf` first). `Symbol.toPrimitive` overrides both.

**O5. `super` in static methods**

```ts
class Base { static id() { return "base"; } }
class Child extends Base { static id() { return "child>" + super.id(); } }
console.log(Child.id());
```

`child>base`. Static `super` resolves through `Object.getPrototypeOf(Child) === Base`.

**O6. Getter in base, field in derived**

```ts
class Base { get kind() { return "base"; } describe() { return this.kind; } }
class Derived extends Base { kind = "derived"; }
```

TypeScript compile error (TS2610: `kind` is an accessor in `Base` but redeclared as a property). If forced through, runtime prints `derived` — the own property shadows the prototype getter.

**O7. Java `equals` without `hashCode`**

```java
class Point {   // a plain class, not a record
  final int x, y;
  Point(int x, int y) { this.x = x; this.y = y; }
  @Override public boolean equals(Object o) { return o instanceof Point p && p.x == x && p.y == y; }
}
var set = new HashSet<Point>(); set.add(new Point(1, 2));
System.out.println(set.contains(new Point(1, 2)));
```

Almost always `false` (silent wrong behaviour). `HashSet` checks `hashCode` first; the default identity hash differs. Fix: override `hashCode`, or use `record Point(int x, int y)`.

### 10.2 Debugging exercises

**D1. Shared nested state in an undo snapshot**

```ts
class Canvas {
  shapes: { id: number; x: number }[] = [];
  snapshot() { return [...this.shapes]; }               // bug
  restore(s: { id: number; x: number }[]) { this.shapes = s; }
}
const c = new Canvas(); c.shapes.push({ id: 1, x: 0 });
const snap = c.snapshot();
c.shapes[0].x = 99;
c.restore(snap); console.log(c.shapes[0].x);              // 99, expected 0
```

- **Root cause:** the array is copied, but its element objects are shared.
- **Fix:** deep-copy the elements, or (better) make shapes immutable so updates replace objects.

```ts
snapshot() { return this.shapes.map(s => ({ ...s })); }   // one level deeper is enough here
// Better: type Shape = Readonly<{ id: number; x: number }>; move(id, x) replaces the object
```

- **Test:**

```ts
test("restore returns to snapshot state", () => {
  const c = new Canvas(); c.shapes.push({ id: 1, x: 0 });
  const snap = c.snapshot(); c.shapes[0].x = 99;
  c.restore(snap);
  expect(c.shapes[0].x).toBe(0);
});
```

**D2. Shared mutable value object**

```ts
class Price { constructor(public amount: number) {} }
const standard = new Price(1000);
const a = { item: "A", price: standard }, b = { item: "B", price: standard };
a.price.amount *= 0.9;          // discount A
console.log(b.price.amount);    // 900 — B got discounted too
```

- **Root cause:** aliasing a mutable object.
- **Fix:** make `Price` immutable (`readonly amount`, `discounted(p): Price` returns a new instance). Value objects should never be mutated in place.

**D3. Observer that skips listeners**

```ts
class Emitter { listeners: (() => void)[] = [];
  on(f: () => void) { this.listeners.push(f); }
  off(f: () => void) { this.listeners.splice(this.listeners.indexOf(f), 1); }
  emit() { for (const f of this.listeners) f(); } }
const e = new Emitter();
const once = () => { console.log("once"); e.off(once); };
e.on(once); e.on(() => console.log("second"));
e.emit();   // prints only "once"
```

- **Root cause:** mutating an array during `for…of` shifts the next element into the current index, so it is skipped.
- **Fix:** iterate over a copy (`for (const f of [...this.listeners])`), or use a `Set`. Also guard `off` against `indexOf === -1`, which would `splice(-1, 1)` and remove the *last* listener — a second bug.

**D4. Async work in a constructor**

```ts
class ReportService {
  config!: Config;
  constructor(private loader: ConfigLoader) { this.loader.load().then(c => (this.config = c)); }
  run() { return this.config.reportPath; }  // TypeError if called immediately
}
```

- **Root cause:** constructors cannot be `async`; the object is returned half-initialised.
- **Fix:** an async static factory, so an instance only exists once it is valid.

```ts
class ReportService {
  private constructor(private config: Config) {}
  static async create(loader: ConfigLoader) { return new ReportService(await loader.load()); }
  run() { return this.config.reportPath; }
}
```

**D5. Hard-wired dependency blocks testing**

```ts
class InvoiceDueChecker {
  isOverdue(inv: Invoice) { return inv.dueDate < new Date(); }  // depends on the real clock
}
```

- **Root cause:** hidden dependency on time; tests become date-dependent and flaky.
- **Fix:** inject a clock.

```ts
interface Clock { now(): Date }
class InvoiceDueChecker {
  constructor(private clock: Clock = { now: () => new Date() }) {}
  isOverdue(inv: Invoice) { return inv.dueDate < this.clock.now(); }
}
test("overdue after due date", () => {
  const checker = new InvoiceDueChecker({ now: () => new Date("2026-11-02") });
  expect(checker.isOverdue({ dueDate: new Date("2026-11-01") } as Invoice)).toBe(true);
});
```

**D6. Singleton state leaking between tests**

```ts
export const cart = new Cart();   // module singleton
test("adds item", () => { cart.add("A"); expect(cart.count()).toBe(1); });
test("empty by default", () => { expect(cart.count()).toBe(0); });  // fails: 1
```

- **Root cause:** module-level instance shared across tests in the same file (Jest isolates modules per *file*, not per test).
- **Fix:** create the instance per test (`beforeEach(() => cart = new Cart())`) and inject it into code under test. If a global must remain, add a reset method used only by tests — a smell worth naming.

**D7. `instanceof` fails across package copies**

```ts
if (err instanceof ValidationError) { /* never true in production */ }
```

- **Root cause:** two copies of the library are installed (different versions in `node_modules`), so there are two `ValidationError` classes. The same happens across iframes and `vm` contexts.
- **Fix:** check a stable brand (`err?.code === "VALIDATION"`, or a `Symbol.for("lib.ValidationError")` property), or dedupe the dependency.

**D8. LSP violation surfacing as a runtime error**

```ts
class FileStorage { write(path: string, data: Buffer) { /* ... */ } read(path: string) { /* ... */ } }
class ReadOnlyStorage extends FileStorage { write(): never { throw new Error("read-only"); } }
function exportReport(s: FileStorage) { s.write("report.pdf", pdf); }  // crashes with ReadOnlyStorage
```

- **Root cause:** the subtype strengthens a precondition ("you may not write").
- **Fix:** split roles — `interface Readable { read(p) }`, `interface Writable { write(p, d) }`; `exportReport` asks for `Writable`, so the type checker rejects read-only storage at compile time.

**D9. Equality in a domain set**

```ts
const selected = new Set<Money>();
selected.add(Money.of(500, "BDT"));
selected.has(Money.of(500, "BDT"));   // false
```

- **Fix options:** key a `Map` by a canonical string built from amount and currency; intern value objects through a factory cache; or, for small collections, keep an array and test with `some(m => m.equals(x))`.

## 11. Question bank by level

Fifty questions, each with the points a strong answer must hit. Deeper treatment of most topics sits in the sections cited in brackets.

### 11.1 Intermediate

1. **What is the difference between a class and an object?** Class = template + shared behaviour; object = instance with identity and state. In JS, a class is a constructor function plus a prototype object; methods are shared, fields are per instance. \[2.1\]
2. **Explain encapsulation with an example that is not getters/setters.** An `Account` with `deposit`/`withdraw` that enforce "no negative balance"; state is reachable only through rule-checking methods. \[1.1\]
3. **Abstraction vs. encapsulation?** Abstraction hides *decisions* behind a simple interface; encapsulation protects *state and invariants*. \[1.2, T12\]
4. **Overloading vs. overriding?** Overloading: same name, different signatures, chosen at compile time (TS has signatures only). Overriding: subclass replaces a base method, chosen at runtime by the receiver's type. \[1.4, T22\]
5. **What does `super` do in a constructor and in a method?** Constructor: calls the parent constructor and creates `this` (mandatory before using `this` in a derived class). Method: calls the parent's version via the method's home object. \[8.4\]
6. **Static vs. instance members?** Static lives on the class, shared, no instance state; good for factories and constants; mutable statics are global state. \[2.2\]
7. **Interface vs. abstract class in TypeScript?** Interfaces are erased, multiple, contract-only; abstract classes exist at runtime, single, can hold code and state. \[8.3\]
8. **What is composition, and why prefer it over inheritance?** Holding collaborators as fields and delegating. It allows runtime swapping, multi-axis variation, and avoids fragile base classes. \[1.3\]
9. **Shallow vs. deep copy in JS?** Spread/`Object.assign` copy one level; `structuredClone` deep-copies data but drops prototypes and methods. \[2.5\]
10. **`===` on two objects with the same fields?** `false`; compares identity. Write `equals()` for value equality. \[2.3\]
11. **What are access modifiers in TS, and are they enforced at runtime?** `public/private/protected` are compile-time only; `#private` is enforced by the engine. \[T10\]
12. **Why does `const f = obj.method; f()` fail?** `this` depends on the call site; detached, it is `undefined` in strict class code. \[T13\]

### 11.2 Advanced

13. **State the Liskov Substitution Principle in terms of contracts.** Subtypes may not strengthen preconditions, weaken postconditions, or break invariants. Give the Square/Rectangle or read-only repository example. \[3.3\]
14. **What is dynamic dispatch and how does JS implement it?** Method chosen by the runtime receiver; JS walks the prototype chain at call time. Java/C# typically use vtables. \[1.4\]
15. **Explain covariance and contravariance with function types.** Returns can narrow (covariant), parameters can widen (contravariant). TS checks method-syntax params bivariantly — unsound. \[T17, T18\]
16. **Strategy vs. State vs. Template Method?** Strategy: client picks algorithm via composition. State: object switches its own behaviour as state changes. Template Method: base fixes the skeleton, subclasses fill steps. \[6.1, 6.4, 6.5\]
17. **Decorator vs. Proxy vs. Adapter?** Same shape, different intent: add behaviour / control access / convert interface. \[5\]
18. **What is the fragile base class problem?** Subclasses depend on base internals (which methods call which), so harmless-looking base changes break them. \[1.3, T3\]
19. **Why is Singleton considered an anti-pattern by many?** Hidden global state, hard to test, couples callers to a concrete class. Prefer one instance created in the composition root and injected. \[4.1\]
20. **Dependency Injection vs. Dependency Inversion vs. IoC?** Technique vs. principle vs. broader control-flow idea. \[3.5\]
21. **How do you make a TS type nominal?** Private member or a branded type. \[8.2\]
22. **What is an anemic domain model?** Entities with data only, rules in services; invariants become unenforceable. Fine for CRUD; harmful for rule-heavy domains. \[7.6\]

### 11.3 Senior

23. **When would you choose inheritance today?** Closed, shallow hierarchies with genuine substitutability and shared invariants (framework base classes, sealed domain variants). Otherwise composition.
24. **How do you decide where to put an abstraction?** At volatility boundaries: I/O, vendors, policies that vary, module seams. Not between stable in-process classes. Rule of Three; YAGNI.
25. **Walk me through refactoring a 3,000-line `OrderService`.** Characterisation tests → identify actors/responsibilities → extract value objects and pure functions → push rules into entities → split use cases → introduce ports for I/O → strangle incrementally behind the same API. \[12, Challenge 13\]
26. **How do you design an extensible payment integration?** Domain-owned `PaymentGateway` port, adapter per provider, registry/factory by provider code, idempotency keys, a normalised result type, provider webhooks mapped to domain events. \[15.1\]
27. **Aggregates: how big?** As small as the invariants that must be consistent in one transaction. Reference other aggregates by ID. Large aggregates cause lock contention.
28. **When is CQRS worth it?** Read/write asymmetry in shape or scale, or separate teams owning reads. Not for CRUD. \[7.10\]
29. **How do you keep domain events reliable?** Transactional outbox, idempotent consumers, at-least-once delivery. \[7.8\]
30. **How do OOP and functional styles combine in a TS codebase?** Immutable values and pure functions for calculations; objects for stateful entities, boundaries, and polymorphic plug-ins. \[8.8\]
31. **How do you test code with many collaborators without brittle mocks?** Prefer fakes for ports, assert on outcomes not calls, mock only at process boundaries, test through the public API. \[13\]
32. **What makes an API (class interface) good?** Small, named in caller language, hard to misuse (types encode states), stable, returns immutable data, fails fast with clear errors.

### 11.4 Expert follow-ups

34. "Your adapter swallows provider error codes. What do you lose?" — Retry vs. permanent failure classification, support diagnostics. Map to a small domain error taxonomy, keep the raw code as metadata.

## 12. Clean code, refactoring and design quality

All of these are guidelines that trade against each other: DRY can increase coupling, small classes can scatter a concept, and YAGNI can block a needed seam. A senior answer names the tension and the context that decides it.

### 12.1 The core qualities

| Principle | One-line meaning | Overdone looks like |
| --- | --- | --- |
| High cohesion | Things that change together live together | Splitting one concept across many tiny files |
| Low coupling | Modules know little about each other | Interfaces and events everywhere; flow becomes untraceable |
| Separation of concerns | Domain, I/O, presentation kept apart | Layers that only forward calls |
| Information hiding (Parnas) | Hide the decisions likely to change | Hiding stable facts behind needless indirection |
| Law of Demeter | Talk only to direct collaborators | Dozens of forwarding methods (`getCustomerCityName()`) |
| Tell, Don't Ask | Command objects, don't interrogate them | Forcing behaviour into objects that shouldn't own it |
| Composition over inheritance | Reuse by delegation | Wrapping everything even when an `is-a` is real |
| DRY | One source of truth for each piece of *knowledge* | Merging code that only looks alike ("wrong abstraction") |
| KISS | Simplest thing that works | — |
| YAGNI | Don't build for imagined futures | Refusing a seam you already know you need |

**DRY nuance.** DRY is about duplicated *knowledge*, not duplicated *text*. Two validation rules that happen to look identical but serve different actors should stay separate — merging them couples unrelated changes.

### 12.2 Code smells and their refactorings

| Smell | Symptom | Refactoring |
| --- | --- | --- |
| God class | Knows and decides everything; many unrelated fields | Extract Class, Move Method |
| Long method | Scroll to read; comments label sections | Extract Function, Compose Method |
| Long parameter list | 5+ params, booleans | Introduce Parameter Object, Preserve Whole Object |
| Primitive obsession | `string` emails, `number` money | Replace Primitive with Value Object |
| Feature envy | Method uses another object's data more than its own | Move Method to that object |
| Data clumps | Same 3 fields travel together | Extract value object |
| Switch on type code | Same `switch` in many places | Replace Conditional with Polymorphism |
| Shotgun surgery | One change touches 10 files | Move related code together |
| Divergent change | One class changes for many reasons | Split by responsibility (SRP) |
| Refused bequest | Subclass ignores or throws for inherited methods | Replace Inheritance with Delegation |
| Message chains | `a.getB().getC().doX()` | Hide Delegate, Tell Don't Ask |
| Speculative generality | Abstract classes with one subclass | Collapse Hierarchy, Inline Class |
| Temporal coupling | Must call `init()` before `run()` | Constructor/factory that returns a ready object |
| Boolean flag argument | `render(true)` | Split into two methods or use an options object |

### 12.3 Before/after: Tell, Don't Ask + Law of Demeter

```ts
// Before: the service interrogates and decides for the object
if (order.getCustomer().getMembership().getTier() === "GOLD" && order.getTotal() > 5000) {
  order.setDiscount(order.getTotal() * 0.1);
}

// After: each object answers questions about itself
class Customer { isGold() { return this.membership.tier === "GOLD"; } }
class Order {
  applyLoyaltyDiscount() {
    if (this.customer.isGold() && this.total() > 5000) this.discount = this.total() * 0.1;
  }
}
order.applyLoyaltyDiscount();
```

Trade-off: if loyalty rules come from a marketing team and change monthly, move them out of `Order` into a `LoyaltyPolicy` strategy — still Tell, Don't Ask, but with the rule owned by its actor.

### 12.4 Before/after: primitive obsession

```ts
// Before
function register(email: string, phone: string, amountPaid: number) { /* validates everywhere */ }
register("01711-000000", "a@b.com", 500);   // swapped args compile fine

// After
class Email { private constructor(readonly value: string) {}
  static parse(s: string) { if (!/^[^@\s]+@[^@\s]+$/.test(s)) throw new Error("Invalid email"); return new Email(s.toLowerCase()); } }
class BdPhone { private constructor(readonly e164: string) {}
  static parse(s: string) { const d = s.replace(/\D/g, ""); const local = d.startsWith("880") ? d.slice(3) : d.replace(/^0/, "");
    if (!/^1[3-9]\d{8}$/.test(local)) throw new Error("Invalid BD mobile"); return new BdPhone("+880" + local); } }
function register(email: Email, phone: BdPhone, paid: Money) { /* already valid */ }
```

Validated once at construction; swapped arguments become compile errors because `Email` and `BdPhone` have private constructors and different members.

### 12.5 Before/after: replace flag arguments and temporal coupling

```ts
// Before
const exporter = new Exporter();
exporter.init(config);            // forget this → crash later
exporter.export(rows, true);      // what is true?

// After

```

### 12.6 Measuring design quality

- **Size heuristics:** functions that fit on a screen; classes whose purpose fits in one sentence without "and". These are prompts to look, not hard limits.
- **Cyclomatic / cognitive complexity:** flag methods above \~10 for review (ESLint `complexity`, SonarQube cognitive complexity).
- **Coupling metrics:** afferent/efferent coupling and instability per module; dependency-cruiser or madge for cycles in TS.
- **Change metrics:** files that always change together (from git history) reveal hidden coupling better than static metrics.

### 12.7 Technical debt — how a senior talks about it

Treat debt as a deliberate loan with interest: name the shortcut, the interest (slower changes, bugs in area X), and the trigger to repay ("before we add the third payment provider"). Refactor in small, test-protected steps alongside feature work; avoid big-bang rewrites.

## 13. Testing and quality assurance

Test objects through their public behaviour and replace only the collaborators you don't own or that are slow. If a class is hard to test, that is design feedback, not a reason to reach for more mocks.

### 13.1 Test doubles (Meszaros taxonomy)

| Double | What it does | Assert on | Example |
| --- | --- | --- | --- |
| Dummy | Fills a parameter, never used | — | `null as unknown as Logger` |
| Stub | Returns canned answers | The SUT's output | `rates.rate = async () => 110` |
| Spy | Records calls, maybe passes through | Calls made | `jest.spyOn(mailer, "send")` |
| Mock | Pre-programmed expectations on calls | Interactions | `expect(gateway.charge).toHaveBeenCalledWith(...)` |
| Fake | Working lightweight implementation | Resulting state | `InMemoryOrderRepository` |

**Mocks vs. stubs (the classic question).** Stubs feed *inputs* to the code under test; you verify its *state or return value*. Mocks verify *outgoing interactions*. Use mocks for commands to the outside world whose only observable effect is the call (send email, publish event). Use stubs and fakes for queries.

### 13.2 Testing a use case with fakes (Jest)

```ts
// Fakes for the PlaceOrder use case in 7.6 (shared types from "How to use")
class InMemoryOrders implements OrderRepository {
  #rows = new Map<string, Order>(); #seq = 0;
  nextId() { return `ord-${++this.#seq}`; }
  async byId(id: string) { return this.#rows.get(id) ?? null; }
  async save(o: Order) { this.#rows.set(o.id, o); }
  get size() { return this.#rows.size; }
}
class InMemoryStock implements StockRepository {
  reservations: unknown[] = [];
  async reserve(lines: readonly OrderLine[]) { this.reservations.push(lines); }
}
class InMemoryUnitOfWork implements UnitOfWork {
  constructor(readonly orders = new InMemoryOrders(), readonly stock = new InMemoryStock()) {}
  async run<T>(work: (r: { orders: OrderRepository; stock: StockRepository }) => Promise<T>) {
    return work({ orders: this.orders, stock: this.stock });   // no rollback: enough for use-case tests
  }
}
class FakeGateway implements PaymentGateway {
  charges: { orderId: string; amount: number }[] = [];
  constructor(private succeed = true) {}
  async charge(orderId: string, amount: Money) { this.charges.push({ orderId, amount: amount.amount }); return { ref: "pay-1", ok: this.succeed }; }
}
class RecordingEvents implements EventPublisher {
  published: DomainEvent[] = [];
  async publishAll(events: DomainEvent[]) { this.published.push(...events); }
}

describe("PlaceOrder", () => {
  const cmd: PlaceOrderCommand = { customerId: "c1", lines: [{ sku: "A", qty: 2, unitPrice: 500 }] };

  test("charges the order total, saves a paid order and publishes OrderPlaced", async () => {
    const uow = new InMemoryUnitOfWork(), pay = new FakeGateway(), events = new RecordingEvents();
    const id = await new PlaceOrder(uow, pay, events).execute(cmd);
    expect(pay.charges).toEqual([{ orderId: id, amount: 1000 }]);
    expect((await uow.orders.byId(id))?.status).toBe("paid");
    expect(events.published.map(e => e.type)).toContain("OrderPlaced");
  });

  test("does not save the order when payment fails", async () => {
    const uow = new InMemoryUnitOfWork();
    await expect(new PlaceOrder(uow, new FakeGateway(false), new RecordingEvents()).execute(cmd))
      .rejects.toThrow("Payment failed");
    expect(uow.orders.size).toBe(0);
  });
});
```

Fakes give state-based tests that survive refactoring. The test above never mentions how `PlaceOrder` calls the repository.

### 13.3 Private behaviour vs. public contracts

- Do not test private methods directly. If a private method is complex enough to want its own tests, it is usually a separate class waiting to be extracted.
- `#private` members are unreachable from tests by design; TS `private` can be reached with `as any`, which couples tests to internals.
- Test invariants through behaviour: "withdraw more than balance throws and balance is unchanged".

### 13.4 Contract tests for polymorphic implementations

One shared suite every implementation must pass — the executable form of LSP.

```ts
export function orderRepositoryContract(name: string, make: () => Promise<OrderRepository>) {
  describe(`${name} satisfies OrderRepository`, () => {
    test("returns null for unknown id", async () => {
      expect(await (await make()).byId("missing")).toBeNull();
    });
    test("round-trips a saved order", async () => {
      const repo = await make(); const o = sampleOrder(repo.nextId());
      await repo.save(o);
      expect((await repo.byId(o.id))?.total()).toEqual(o.total());
    });
  });
}
orderRepositoryContract("InMemoryOrders", async () => new InMemoryOrders());
orderRepositoryContract("PgOrders", async () => new PgOrders(await testPool()));  // integration
```

This also proves your fake behaves like the real thing, which keeps fake-based unit tests honest. Consumer-driven contract testing between services (Pact) applies the same idea across HTTP.

### 13.5 Testing inheritance hierarchies

- Run the base class's behavioural tests against every subclass (contract suite above).
- Test the template method skeleton once with a minimal test subclass; test each subclass only for its hooks.
- If subclasses need special-casing in shared tests, the hierarchy probably violates LSP.

### 13.6 Property-based and mutation testing

**Property-based testing** (fast-check) generates hundreds of inputs and checks invariants:

```ts
import fc from "fast-check";
test("money addition is commutative and keeps currency", () => {
  fc.assert(fc.property(fc.integer(), fc.integer(), (a, b) => {
    const x = Money.of(a, "BDT"), y = Money.of(b, "BDT");
    return x.add(y).equals(y.add(x)) && x.add(y).currency === "BDT";
  }));
});
```

Great for value objects, parsers, serializers (round-trip property), and state machines.

**Mutation testing** (Stryker for JS/TS, PIT for Java) changes your code (`>` → `>=`, removes a call) and checks whether tests fail. Surviving mutants show assertions that are too weak, even at 100% line coverage.

### 13.7 Avoiding brittle tests

| Brittle | Robust |
| --- | --- |
| Asserting exact call order on internal collaborators | Asserting outcomes and external effects |
| Mocking types you don't own (the SDK itself) | Wrapping the SDK in an adapter and faking your adapter; integration-test the adapter |
| Snapshotting large objects | Asserting the few fields that matter |
| Shared mutable fixtures | Fresh builders per test (`anOrder().withLines(2).build()`) |
| Real clock, randomness, network | Injected `Clock`, seeded random, fakes |

### 13.8 Testability as a design signal

Hard to construct → too many dependencies (SRP). Needs global setup → hidden singletons. Needs to mock five things to test one rule → logic is in the wrong place; move it into a pure function or entity that needs no mocks.

## 14. Object-oriented design vs. system design

The disciplines answer different questions at different zoom levels. A class model lives *inside* one deployable service; system design decides how services, data stores and networks fit together. Interviewers penalise answering one with the other.

### 14.1 The disciplines compared

| Discipline | Question it answers | Typical artefacts | Units of design | Interview round |
| --- | --- | --- | --- | --- |
| Domain modeling | What concepts and rules exist in the business? | Ubiquitous language, aggregates, events | Entities, value objects, bounded contexts | DDD / senior design |
| Object-oriented design | Which objects own which responsibilities, and how do they collaborate? | Class and sequence diagrams | Classes, interfaces | OOD |
| Low-level design (LLD) | How does one component work in code? | Class diagrams, APIs, patterns, data structures, concurrency | Classes, modules | LLD / machine coding |
| High-level design (HLD) | How does the system meet scale, availability and latency goals? | Service diagrams, data flow, capacity estimates | Services, queues, caches, DBs | System design |
| Architectural design | How is code organised so it can change safely? | Layer/dependency rules, ADRs | Layers, modules, bounded contexts | Architecture discussion |
| Database design | How is data stored, queried and kept consistent? | ERDs, schemas, indexes | Tables, keys, indexes | Data modeling |

**Key insight:** the object model and the table schema are related but not the same. An `Order` aggregate with a `Money` value object and a `List<OrderLine>` may map to two tables with `amount_minor` and `currency` columns. ORMs bridge the gap (the object–relational impedance mismatch); repositories keep it out of the domain.

### 14.2 Layered architecture

```text
Presentation (controllers, GraphQL resolvers, CLI)
      ↓
Application (use cases: PlaceOrder, RefundPayment)
      ↓
Domain (entities, value objects, domain services, events)
      ↓
Infrastructure (Postgres, Redis, bKash SDK, SMTP)
```

The weakness of naive layering: the domain depends downward on infrastructure, so database choices leak into business rules.

### 14.3 Clean / Hexagonal / Onion architecture

All three invert the bottom dependency: **source-code dependencies point inward, toward policy.** The domain defines ports (interfaces); infrastructure provides adapters.

- **Entities (core):** enterprise rules; no framework imports.
- **Use cases:** application rules; orchestrate entities; define ports like `OrderRepository`, `PaymentGateway`.
- **Interface adapters:** controllers, presenters, repository implementations, provider adapters.
- **Frameworks and drivers:** Express/NestJS, ORM, HTTP clients, message brokers.

&#91;embedded content: Clean Architecture · 4 rings, dependencies inward\]

An outer ring may import an inner one, never the reverse; the inner rings define interfaces that the outer rings implement.

```text
src/
  domain/        order.ts, money.ts, order-placed.event.ts        (imports nothing outward)
  application/   place-order.ts, ports.ts                         (imports domain)
  adapters/      http/order.controller.ts, pg/pg-order-repo.ts, bkash/bkash-gateway.ts
  main.ts        composition root: wires adapters into use cases
```

Enforce the rule with tooling (dependency-cruiser, ESLint `import/no-restricted-paths`, ArchUnit in Java), not just convention.

**When it's overkill:** a CRUD admin app with no business rules. A controller → service → ORM stack is fine there; the ceremony of ports buys nothing.

### 14.4 DDD concepts that interviewers expect

| Concept | Meaning | OOP mapping |
| --- | --- | --- |
| Ubiquitous language | Code uses the business's words | Class and method names |
| Bounded context | A boundary where a model and its language are consistent | A module or service; `Customer` in Billing ≠ `Customer` in Support |
| Entity | Identity that persists through change | Class with `id`, equality by id |
| Value object | Defined by attributes, immutable | Immutable class with `equals` |
| Aggregate | Consistency boundary with one root | Root entity that owns child entities; only the root is referenced from outside |
| Domain event | Something meaningful happened | Immutable event object |
| Repository | Collection-like access to aggregates | Interface per aggregate root |
| Anti-corruption layer | Translator protecting your model from another | Adapter + mapper |
| Context map | How bounded contexts relate | Integration contracts, events |

### 14.5 Example: from class model to backend system

Case: an e-commerce checkout in Bangladesh supporting bKash, Nagad and cards.

1. **Domain model (OOD):** `Order` aggregate (lines, status, total), `Money`, `PaymentAttempt`; events `OrderPlaced`, `PaymentCaptured`.
2. **LLD:** `PlaceOrder` use case with the simple `PaymentGateway` for cards, or `PaymentService` with the `PaymentProvider` port for wallets (15.1); `BkashProvider`, `NagadProvider`, `CardProvider` adapters selected by a `ProviderRegistry`; State pattern for order status; idempotency key per checkout.
3. **Architecture:** hexagonal layout inside an Order service; Payment as a separate bounded context communicating by events.
4. **HLD:** API gateway → Order service (Postgres) → outbox → message broker → Payment service; webhooks from providers land in Payment service; Redis for idempotency keys; read model for order history.
5. **Database:** `orders`, `order_lines`, `payment_attempts`, `outbox` tables; unique index on `idempotency_key`.

The same `PaymentProvider` interface appears at step 2 and is invisible at step 4 — that is how the levels nest.

### 14.6 How to run an LLD interview answer

1. Clarify requirements and scope (5 min): actors, use cases, non-goals.
2. Identify core entities and value objects from nouns; responsibilities from verbs.
3. Define interfaces at variation points (what will change?).
4. Sketch the class diagram; walk one use case as a sequence.
5. Write the core code: the 2–3 classes that carry the logic.
6. Discuss extensibility, concurrency, testing, and the trade-offs you made.

### 15.1 Extensible payment integrations

**Requirements.** Support bKash, Nagad and cards now; add providers without editing checkout. Handle retries without double-charging. Map async provider webhooks to order status.

**Object model**

| Class / interface | Responsibility |
| --- | --- |
| `PaymentProvider` (port) | `initiate`, `refund`, `parseWebhook` in domain terms; a richer port than the simple `PaymentGateway` because wallets redirect and confirm by webhook |
| `BkashProvider`, `NagadProvider`, `CardProvider` | Adapters: translate to each SDK/API, verify signatures, map errors |
| `ProviderRegistry` | Resolve the provider for a `PaymentMethod` |
| `Payment` (aggregate) | Status `initiated → captured / failed / refunded`; idempotency key; replay-safe transitions |
| `PaymentRepository` | Find payments by idempotency key and by provider reference |
| `PaymentService` (use case) | `start` and `handleWebhook`; persists; publishes `PaymentCaptured` |
| `PaymentError` | Small taxonomy: `Declined`, `Retryable`, `Configuration` |

```ts
type PaymentMethod = "bkash" | "nagad" | "card";

interface PaymentProvider {
  readonly method: PaymentMethod;
  initiate(p: { paymentId: string; amount: Money; idempotencyKey: string; returnUrl: string }): Promise<{ providerRef: string; redirectUrl?: string }>;
  refund(providerRef: string, amount: Money): Promise<void>;
  parseWebhook(headers: Record<string, string>, body: string): { providerRef: string; outcome: "captured" | "failed" };  // verifies the signature
}

class ProviderRegistry {
  #byMethod: Map<PaymentMethod, PaymentProvider>;
  constructor(providers: PaymentProvider[]) { this.#byMethod = new Map(providers.map(p => [p.method, p])); }
  get(m: PaymentMethod) { const p = this.#byMethod.get(m); if (!p) throw new Error(`No provider for ${m}`); return p; }
}

type PaymentStatus = "initiated" | "captured" | "failed" | "refunded";
class Payment {
  #status: PaymentStatus = "initiated";
  providerRef?: string;
  constructor(readonly id: string, readonly orderId: string, readonly amount: Money,
              readonly method: PaymentMethod, readonly idempotencyKey: string) {}
  get status() { return this.#status; }
  attach(ref: string) { this.providerRef = ref; }
  /** Returns true only when the status actually changed, so webhook replays are harmless. */
  markCaptured(): boolean {
    if (this.#status === "captured") return false;
    if (this.#status !== "initiated") throw new Error(`Cannot capture from ${this.#status}`);
    this.#status = "captured"; return true;
  }
  markFailed(): boolean { if (this.#status !== "initiated") return false; this.#status = "failed"; return true; }
}

interface PaymentRepository {
  nextId(): string;
  byIdempotencyKey(key: string): Promise<Payment | null>;
  byProviderRef(ref: string): Promise<Payment | null>;
  save(p: Payment): Promise<void>;
}

class PaymentService {
  constructor(private payments: PaymentRepository, private providers: ProviderRegistry,
              private events: EventPublisher, private clock: () => Date = () => new Date()) {}

  async start(orderId: string, amount: Money, method: PaymentMethod, idempotencyKey: string, returnUrl: string) {
    const existing = await this.payments.byIdempotencyKey(idempotencyKey);
    if (existing) return existing;                         // a retry gets the same payment, no second initiate
    const payment = new Payment(this.payments.nextId(), orderId, amount, method, idempotencyKey);
    const { providerRef } = await this.providers.get(method).initiate({ paymentId: payment.id, amount, idempotencyKey, returnUrl });
    payment.attach(providerRef);
    await this.payments.save(payment);
    return payment;
  }

  async handleWebhook(method: PaymentMethod, headers: Record<string, string>, body: string) {
    const { providerRef, outcome } = this.providers.get(method).parseWebhook(headers, body);
    const payment = await this.payments.byProviderRef(providerRef);
    if (!payment) throw new Error(`Unknown payment ${providerRef}`);
    const changed = outcome === "captured" ? payment.markCaptured() : payment.markFailed();
    await this.payments.save(payment);
    if (changed && payment.status === "captured")
      await this.events.publishAll([{ type: "PaymentCaptured", occurredAt: this.clock() }]);
  }
}
```

**Flow.** Checkout → `PaymentService.start(orderId, amount, method, idempotencyKey, returnUrl)` → a retry with the same key returns the existing payment → the registry picks the provider → `initiate` → save `providerRef` → redirect the customer → provider webhook → `handleWebhook` verifies it through `parseWebhook` → `markCaptured()` → save and publish `PaymentCaptured` (through an outbox in production) → the Order context marks the order paid.

**Principles and patterns.** Adapter (per provider), Strategy/Registry (selection), State (payment status), DIP (domain owns the port), OCP (new provider = new adapter + registration), Outbox (reliable events).

**Alternatives.** Using one generic payment aggregator SDK shrinks the adapter count but couples you to its availability and fees. A switch over `method` is acceptable for two stable providers.

**Testing.** A contract suite for every provider adapter, run against its sandbox; a fake provider for use-case tests (challenge C1); webhook signature tests with recorded payloads; idempotency and webhook-replay tests.

**Design smells to avoid.** Provider-specific fields on `Payment` (`bkashPaymentID`); `if (method === "bkash")` in the service; trusting redirect URLs instead of server-side verification.

**Senior follow-ups.** Webhook arrives before the initiate response is saved? (Upsert by `providerRef`, or store the ref before redirect.) Partial refunds? (Refund as its own entity with a sum invariant.) Provider outage? (Circuit breaker decorator, method-level fallback in UI.)

### 15.2 Notification providers

**Requirements.** Email, SMS, push; per-user channel preferences; templates; provider failover; rate limiting; no duplicate sends.

```ts
interface Channel { readonly kind: "email" | "sms" | "push"; send(to: Recipient, msg: RenderedMessage): Promise<void> }
class FailoverChannel implements Channel {          // Composite/Decorator over providers of one kind
  constructor(readonly kind: Channel["kind"], private providers: Channel[]) {}
  async send(to: Recipient, m: RenderedMessage) {
    let last: unknown;
    for (const p of this.providers) { try { return await p.send(to, m); } catch (e) { last = e; } }
    throw last;
  }
}
class Notifier {
  constructor(private channels: Map<Channel["kind"], Channel>, private prefs: PreferenceStore,
              private templates: TemplateRenderer, private sent: SentLog) {}
  async notify(userId: string, event: NotificationEvent) {
    const kinds = await this.prefs.channelsFor(userId, event.type);
    for (const kind of kinds) {
      const key = `${event.id}:${kind}`;
      if (await this.sent.has(key)) continue;                       // idempotency
      await this.channels.get(kind)!.send(await this.prefs.recipient(userId, kind), this.templates.render(event, kind));
      await this.sent.add(key);
    }
  }
}
```

Patterns: Strategy (channel), Decorator (failover, rate limit, retry), Template rendering separated (SRP), Observer (domain events trigger notifications). Production note: send asynchronously via a queue; the request path only enqueues.

### 15.3 Discount and pricing engine

**Requirements.** Percentage, fixed, buy-X-get-Y, tiered and member-only discounts; stacking rules (exclusive vs. combinable); explainable price breakdown; marketing can add rules without deploys (stretch).

```ts
interface PricingContext { lines: { sku: string; qty: number; unitPrice: number; category: string }[]; customerTier: "regular" | "gold"; coupon?: string }
interface Adjustment { ruleId: string; label: string; amount: number }   // negative = discount
interface PricingRule {
  readonly id: string; readonly priority: number; readonly exclusive: boolean;
  applies(ctx: PricingContext): boolean;
  adjust(ctx: PricingContext, runningTotal: number): Adjustment | null;
}
class PercentOffCategory implements PricingRule {
  exclusive = false;
  constructor(readonly id: string, readonly priority: number, private category: string, private pct: number) {}
  applies(c: PricingContext) { return c.lines.some(l => l.category === this.category); }
  adjust(c: PricingContext) {
    const base = c.lines.filter(l => l.category === this.category).reduce((s, l) => s + l.qty * l.unitPrice, 0);
    return { ruleId: this.id, label: `${this.pct}% off ${this.category}`, amount: -Math.round(base * this.pct / 100) };
  }
}
class PricingEngine {
  constructor(private rules: PricingRule[]) {}
  price(ctx: PricingContext) {
    const subtotal = ctx.lines.reduce((s, l) => s + l.qty * l.unitPrice, 0);
    const applicable = this.rules.filter(r => r.applies(ctx)).sort((a, b) => a.priority - b.priority);
    const exclusive = applicable.find(r => r.exclusive);
    const chosen = exclusive ? [exclusive] : applicable;
    const adjustments: Adjustment[] = []; let total = subtotal;
    for (const r of chosen) { const a = r.adjust(ctx, total); if (a) { adjustments.push(a); total = Math.max(0, total + a.amount); } }
    return { subtotal, adjustments, total };
  }
}
```

**Discussion points.** Order of application changes results (percent-then-fixed ≠ fixed-then-percent) — make it explicit via priority. Money in integer minor units. Returning `adjustments` makes the price explainable on receipts and testable. For marketer-defined rules, store rule *parameters* as data and map to a fixed set of rule classes (data-driven Strategy), or use the Specification/Interpreter approach — avoid arbitrary code.

### 15.4 Permission system (RBAC with optional ABAC)

```ts
type Action = "invoice:read" | "invoice:approve" | "salary:read";
class Role { constructor(readonly name: string, readonly grants: ReadonlySet<Action>) {} }
interface Policy { evaluate(subject: Subject, action: Action, resource: Resource): "allow" | "deny" | "abstain" }
class RolePolicy implements Policy {
  evaluate(s: Subject, a: Action) { return s.roles.some(r => r.grants.has(a)) ? "allow" : "abstain"; }
}
class OwnDepartmentOnly implements Policy {                     // attribute-based
  evaluate(s: Subject, a: Action, r: Resource) {
    return a === "salary:read" && r.departmentId !== s.departmentId ? "deny" : "abstain";
  }
}
class Authorizer {
  constructor(private policies: Policy[]) {}
  can(s: Subject, a: Action, r: Resource) {
    const votes = this.policies.map(p => p.evaluate(s, a, r));
    return !votes.includes("deny") && votes.includes("allow");   // deny overrides; default deny
  }
}
```

Patterns: Strategy/Composite (policies), Chain of Responsibility (alternative evaluation order), Proxy (authorising wrapper around services). Trap: putting `if (user.role === "admin")` checks inside domain methods — keep authorisation at the application boundary unless the rule is truly a domain rule (e.g. "approver cannot approve own expense").

### C4. Shopping cart with pricing and tax

**Requirements.** Add/remove/update quantity; per-category VAT; discounts via the pricing engine; totals in minor units; immutable line items.

```ts
type Line = Readonly<{ sku: string; name: string; unitPrice: number; qty: number; category: string }>;
interface TaxPolicy { rateFor(category: string): number }          // e.g. 0.15 VAT; 0 for exempt
class Cart {
  #lines = new Map<string, Line>();
  add(item: Omit<Line, "qty">, qty = 1) {
    if (!Number.isInteger(qty) || qty <= 0) throw new RangeError("qty must be a positive integer");
    const cur = this.#lines.get(item.sku);
    this.#lines.set(item.sku, { ...item, qty: (cur?.qty ?? 0) + qty });
  }
  setQty(sku: string, qty: number) { if (qty === 0) this.#lines.delete(sku); else { const l = this.#lines.get(sku); if (!l) throw new Error("Not in cart"); this.#lines.set(sku, { ...l, qty }); } }
  get lines(): readonly Line[] { return [...this.#lines.values()]; }
}
class CartPricer {
  constructor(private tax: TaxPolicy, private engine: PricingEngine) {}
  quote(cart: Cart, customerTier: "regular" | "gold") {
    const priced = this.engine.price({ lines: cart.lines.map(l => ({ ...l })), customerTier });
    const ratio = priced.subtotal === 0 ? 0 : priced.total / priced.subtotal;   // spread discount proportionally
    const tax = cart.lines.reduce((s, l) => s + Math.round(l.unitPrice * l.qty * ratio * this.tax.rateFor(l.category)), 0);
    return { ...priced, tax, grandTotal: priced.total + tax };
  }
}
```

**Why this model.** `Cart` owns line invariants; pricing and tax are separate policies that change for different actors (marketing vs. finance). **Discuss:** whether tax applies before or after discount is a legal question — make it a policy, not a hard-coded order.

### C7. Parking lot

**Requirements.** Multiple levels; spot sizes (motorcycle, compact, large); vehicles fit spots of their size or larger; tickets; fees by duration and vehicle type; find a free spot fast.

```ts
type Size = 1 | 2 | 3;   // motorcycle, car, bus — comparable by number
class Spot { #occupant?: string; constructor(readonly id: string, readonly size: Size) {}
  get free() { return !this.#occupant; }
  park(plate: string) { if (!this.free) throw new Error("Occupied"); this.#occupant = plate; }
  leave() { this.#occupant = undefined; } }
class Level {
  #free = new Map<Size, Spot[]>();                           // free lists per size → O(1) allocation
  constructor(readonly n: number, spots: Spot[]) { for (const s of spots) this.release(s); }
  allocate(min: Size): Spot | undefined {
    for (let s: number = min; s <= 3; s++) { const spot = this.#free.get(s as Size)?.pop(); if (spot) return spot; }
  }
  release(s: Spot) { (this.#free.get(s.size) ?? this.#free.set(s.size, []).get(s.size)!).push(s); }
}
class ParkingLot {
  #tickets = new Map<string, { spot: Spot; level: Level; plate: string; size: Size; at: Date }>();
  constructor(private levels: Level[], private fees: FeePolicy, private clock: Clock) {}
  enter(plate: string, size: Size) {
    for (const level of this.levels) { const spot = level.allocate(size); if (spot) {
      spot.park(plate); const id = crypto.randomUUID();
      this.#tickets.set(id, { spot, level, plate, size, at: this.clock.now() }); return id; } }
    throw new Error("Lot full");
  }
  exit(ticketId: string) {
    const t = this.#tickets.get(ticketId); if (!t) throw new Error("Invalid ticket");
    t.spot.leave(); t.level.release(t.spot); this.#tickets.delete(ticketId);
    return this.fees.fee(t.size, t.at, this.clock.now());
  }
}
```

Complexity: allocation O(levels × sizes), effectively O(levels). **Discuss:** concurrency (two gates allocating the same spot — use a lock per level or atomic DB update), lost tickets, EV spots (another spot attribute, matched by a `SpotMatcher` strategy).

### C8. Elevator control system

**Model.** `Elevator` (current floor, direction, stop set) with State (`Idle`, `MovingUp`, `MovingDown`, `DoorsOpen`); `Request` (floor, direction); `Dispatcher` strategy selects an elevator; `Controller` runs ticks.

```ts
class Elevator {
  floor = 0; dir: "up" | "down" | "idle" = "idle"; #stops = new Set<number>();
  addStop(f: number) { this.#stops.add(f); if (this.dir === "idle") this.dir = f > this.floor ? "up" : f < this.floor ? "down" : "idle"; }
  step(): number | null {                                   // returns a floor where doors open
    if (this.#stops.has(this.floor)) { this.#stops.delete(this.floor); this.updateDir(); return this.floor; }
    if (this.dir === "up") this.floor++; else if (this.dir === "down") this.floor--;
    return null;
  }
  private updateDir() {                                     // SCAN/LOOK: keep direction while stops remain ahead
    const ahead = [...this.#stops].some(s => (this.dir === "up" ? s > this.floor : s < this.floor));
    if (!ahead) this.dir = this.#stops.size === 0 ? "idle" : this.dir === "up" ? "down" : "up";
  }
  cost(r: { floor: number }) { return Math.abs(this.floor - r.floor) + this.#stops.size; }
}
interface Dispatcher { choose(els: Elevator[], r: { floor: number; dir: "up" | "down" }): Elevator }
const nearest: Dispatcher = { choose: (els, r) => els.reduce((a, b) => (b.cost(r) < a.cost(r) ? b : a)) };
```

### C9. Rate limiter (OOP)

```ts
interface RateLimiter { tryAcquire(key: string, now?: number): boolean }
class TokenBucket implements RateLimiter {
  #buckets = new Map<string, { tokens: number; last: number }>();
  constructor(private capacity: number, private refillPerSec: number, private clock = () => Date.now()) {}
  tryAcquire(key: string, now = this.clock()) {
    const b = this.#buckets.get(key) ?? { tokens: this.capacity, last: now };
    b.tokens = Math.min(this.capacity, b.tokens + ((now - b.last) / 1000) * this.refillPerSec);
    b.last = now;

    this.#buckets.set(key, b); return ok;
  }
}

```

### C10. Extensible logging framework

```ts
type Level = "debug" | "info" | "warn" | "error";
const order: Record<Level, number> = { debug: 10, info: 20, warn: 30, error: 40 };
interface LogRecord { level: Level; msg: string; ctx: Record<string, unknown>; at: Date }
interface Formatter { format(r: LogRecord): string }
interface Sink { write(line: string, r: LogRecord): void }
class Logger {
  constructor(private minLevel: Level, private routes: { formatter: Formatter; sink: Sink; min?: Level }[],
              private ctx: Record<string, unknown> = {}, private clock = () => new Date()) {}
  child(extra: Record<string, unknown>) { return new Logger(this.minLevel, this.routes, { ...this.ctx, ...extra }, this.clock); }
  log(level: Level, msg: string, ctx: Record<string, unknown> = {}) {
    if (order[level] < order[this.minLevel]) return;
    const r = { level, msg, ctx: { ...this.ctx, ...ctx }, at: this.clock() };
    for (const route of this.routes) if (order[level] >= order[route.min ?? "debug"]) {
      try { route.sink.write(route.formatter.format(r), r); } catch { /* a failing sink must not break the app */ }
    }
  }
  info(m: string, c?: Record<string, unknown>) { this.log("info", m, c); }
  error(m: string, c?: Record<string, unknown>) { this.log("error", m, c); }
}
```

Patterns: Strategy (formatter, sink), Composite (multiple routes), Prototype-like `child()` for contextual loggers. **Discuss:** async/batched sinks, redaction of PII, structured JSON output.

### 9.5 Inheritance and dispatch (Java and C#)

**T22. Overload is not override (Java)**

```java
class A { void m(Object o) { System.out.println("A.obj"); } }
class B extends A { void m(String s) { System.out.println("B.str"); } }
A a = new B();
a.m("hi");
```

- **Answer:** `A.obj`.
- **Why:** two-step resolution. At compile time, the static type `A` has only `m(Object)`, so that signature is chosen. At runtime, Java looks for an override of `m(Object)` in `B` — there is none, because `m(String)` is an overload. `@Override` on `B.m` would have turned this into a compile error.
- **Wrong answer:** `B.str` ("the object is a B").

**T23. Static methods are hidden, not overridden (Java)**

```java
class P { static String n() { return "P"; } }
class C extends P { static String n() { return "C"; } }
P p = new C();
System.out.println(p.n());
```

- **Answer:** `P`. Static calls bind to the declared type at compile time. (In JS/TS, `p.constructor.n()` would follow the runtime class.)

**T24. Fields are not polymorphic (Java)**

```java
class P { String name = "P"; String get() { return name; } }
class C extends P { String name = "C"; String get() { return name; } }
P p = new C();
System.out.println(p.name + " " + p.get());
```

- **Answer:** `P C`. Field access uses the static type; method calls dispatch dynamically. Never shadow fields.

**T25. `new` vs `override` (C#)**

```csharp
class A { public virtual string M() => "A"; public string N() => "A"; }
class B : A { public override string M() => "B"; public new string N() => "B"; }
A x = new B();
Console.WriteLine(x.M() + x.N());
```

- **Answer:** `BA`. C# methods are non-virtual by default; `new` hides rather than overrides, so `N` binds statically.

**T26. Diamond with default methods (Java)**

```java
interface Left { default String hi() { return "L"; } }
interface Right { default String hi() { return "R"; } }
class Both implements Left, Right { }
```

- **Answer:** compile error — class inherits unrelated defaults. Fix: override and choose, `public String hi() { return Left.super.hi(); }`. Java resolves conflicts by: class methods win over interface defaults; more specific interface wins; otherwise the class must override. C++ solves the state diamond with `virtual` inheritance; TS/JS mixins resolve by linear order.

**T27. Covariant return types**

- **Q:** Can an override return a narrower type? **Answer:** Yes in Java (since 5), C# (since 9), and TS. Narrower return types are safe (covariance); wider parameter types are safe (contravariance). Java and C# do *not* allow contravariant parameter overriding — a wider parameter creates an overload.

**T28. Circular import with `extends`**

```ts
// a.ts
import { B } from "./b"; export class A { make() { return new B(); } }
// b.ts
import { A } from "./a"; export class B extends A {}
// main.ts
import "./a";
```

- **Answer:** `ReferenceError: Cannot access 'A' before initialization` (ESM) or `TypeError: Class extends value undefined is not a constructor or null` (CommonJS).
- **Why:** `a.ts` starts loading, imports `b.ts`, which evaluates `class B extends A` before `a.ts` has defined `A`.
- **Fix:** break the cycle — move the factory out of `A`, or put shared types in a third module.

**T33. Constructor overloading across languages**

```java
// Java (and C#): real overloads, chosen at compile time
class Point {
  final int x, y;
  Point() { this(0, 0); }
  Point(int x, int y) { this.x = x; this.y = y; }
}
```

```ts
// TypeScript: several signatures, ONE implementation
class Point {
  readonly x: number; readonly y: number;
  constructor();
  constructor(x: number, y: number);
  constructor(x = 0, y = 0) { this.x = x; this.y = y; }
  static fromPolar(r: number, theta: number) { return new Point(r * Math.cos(theta), r * Math.sin(theta)); }
}
// JavaScript: a second `constructor` in one class body is a SyntaxError ("A class may only have one constructor")
```

- **Answer:** Java and C# allow several constructor bodies; TypeScript allows several signatures over one body that must branch on its runtime arguments; JavaScript allows exactly one constructor.
- **Why it matters:** two constructors with the same parameter types are impossible to overload in any of them (`fromPolar(r, θ)` vs. `(x, y)` are both two numbers). Named static factories solve that and state intent.
- **Wrong answer:** "TS supports constructor overloading like Java." The signatures exist only for the type checker.

**T34. Interface inheritance vs. implementation inheritance**

```ts
class AuditedList<T> extends Array<T> {}
const list = AuditedList.from([1, 2, 3]);
const doubled = list.map(x => x * 2);
console.log(doubled instanceof AuditedList);
```

- **Answer:** `true`.
- **Why:** `map`, `filter` and `slice` build their result through `this.constructor[Symbol.species]`, so they call `new AuditedList(length)`. If `AuditedList`'s constructor required an argument (say an audit log), every `map` would pass it a number and break.
- **Lesson:** implementation inheritance brings the base's entire behaviour, including hidden protocols like species construction. Interface inheritance (`implements Iterable<T>`, or holding an array privately) brings only the contract you choose to expose.
- **Wrong answer:** `false` ("map returns a plain array").

### 9.6 Relationships

**T29. "A `Car` has an `Engine`. Composition or aggregation?"**

- **Answer:** It depends on lifecycle ownership in *your* domain. A car-manufacturing system that builds the engine inside the car and scraps both together → composition. A fleet-repair system that swaps engines between cars → aggregation. Ask what happens to the part when the whole is deleted.

**T30. "Is a method parameter an association?"**

- **Answer:** No, it is a *dependency*. Association means the object holds a reference over time (a field). This matters because dependencies are easier to change than associations.

**T31. Bidirectional link that drifts**

```ts
class Team { members: Player[] = []; }
class Player { team?: Team; }
const t = new Team(), p = new Player();
t.members.push(p);          // p.team still undefined
```

- **Fix:** one method owns both sides: `t.add(p)` sets `p.team` and pushes; make the arrays private. Or make the link unidirectional and query the other way.

### 9.7 SOLID and design traps

| Trap statement | Correct position |
| --- | --- |
| "SRP means a class should do one thing." | One *reason to change* / one actor. A cohesive class may have many methods. |
| "OCP means never edit existing code." | It targets *anticipated* variation. Bug fixes and refactors are fine. |
| "Square is-a Rectangle, so inheritance is correct." | Only if Square honours Rectangle's behavioural contract; mutable setters break it. |
| "Every class needs an interface for DIP." | Abstractions belong at volatile boundaries; one-implementation interfaces are often noise. |
| "More small interfaces is always better (ISP)." | Segregate by client role. Hundreds of one-method interfaces hurt discoverability. |
| "Design patterns make code better." | They add indirection. Use one when its problem actually exists. |
| "Getters/setters = encapsulation." | Encapsulation means the object protects its invariants; setters often bypass them. |
| "Inheritance is for code reuse." | Inheritance is for substitutability. Reuse code with composition or functions. |
| "Anemic domain model is fine because services are testable." | It scatters invariants; any service can put an entity in an invalid state. Acceptable for CRUD apps with no real rules. |
| "God objects are about line count." | They are about knowing and deciding too much; a 300-line class can be cohesive, an 80-line one can be a God object. |

**T32. Premature abstraction**

- **Q:** "A teammate created `IUserService`, `UserServiceImpl`, `UserServiceFactory`, and `UserServiceProvider` for a CRUD endpoint. Review it."
- **Strong answer:** four types, one behaviour. Keep a `UserService` class; extract an interface only at a real seam (a second implementation, a module boundary, or an external dependency to fake). Name the cost: navigation, indirection, and false flexibility. Mention the Rule of Three before abstracting.

### 15.5 Wallet and transaction ledger

**Requirements.** Balances never go negative; every change is auditable; transfers are atomic; retries never double-post; balances reconcile.

**Model.** Double-entry: every `Transaction` has `Entries` that sum to zero. The balance is *derived* from entries (or cached with a version check), never edited directly.

```ts
class Entry { constructor(readonly accountId: string, readonly amount: bigint) {} }   // minor units; + credit, − debit
class Transaction {
  private constructor(readonly id: string, readonly idempotencyKey: string, readonly entries: readonly Entry[], readonly at: Date) {}
  static transfer(id: string, key: string, from: string, to: string, amount: bigint, at: Date) {
    if (amount <= 0n) throw new Error("Amount must be positive");
    return new Transaction(id, key, Object.freeze([new Entry(from, -amount), new Entry(to, amount)]), at);
  }
  get isBalanced() { return this.entries.reduce((s, e) => s + e.amount, 0n) === 0n; }
}
class WalletAccount {                       // aggregate guarding the non-negative invariant
  constructor(readonly id: string, private balance: bigint, readonly version: number) {}
  debit(amount: bigint) { if (amount > this.balance) throw new Error("Insufficient funds"); this.balance -= amount; }
  credit(amount: bigint) { this.balance += amount; }
}
```

**Use case.** In one DB transaction: check idempotency key (unique index), load both accounts with optimistic locking (`version`), `debit`/`credit`, insert the ledger transaction, bump versions; on version conflict, retry. Lock accounts in a consistent order (by id) if using pessimistic locks, to avoid deadlocks.

**Why `bigint` or integer minor units:** floating point cannot represent 0.1 exactly. **Event sourcing fit:** ledgers are a natural event stream; projections give balances and statements. **Follow-ups:** multi-currency (one ledger per currency, FX as a pair of transactions), reversals (new compensating transaction — never delete), reconciliation with provider statements.

### 15.6 Plugin system

**Requirements.** Third parties add file importers without changing core; plugins are discovered at startup, validated, versioned, and isolated from core internals.

```ts
export interface ImporterPlugin {
  readonly id: string;               // "csv", "xlsx"
  readonly apiVersion: 1;            // the host's plugin API version
  canHandle(file: { name: string; mime: string }): boolean;
  parse(stream: AsyncIterable<Uint8Array>, ctx: PluginContext): AsyncIterable<Record<string, unknown>>;
}
export interface PluginContext { log(msg: string): void; config: Readonly<Record<string, string>> }   // narrow capability surface

class PluginHost {
  #plugins = new Map<string, ImporterPlugin>();
  register(p: ImporterPlugin) {
    if (p.apiVersion !== 1) throw new Error(`Plugin ${p.id} targets unsupported API ${p.apiVersion}`);
    if (this.#plugins.has(p.id)) throw new Error(`Duplicate plugin ${p.id}`);
    this.#plugins.set(p.id, p);
  }
  resolve(file: { name: string; mime: string }) {
    const p = [...this.#plugins.values()].find(x => x.canHandle(file));
    if (!p) throw new Error(`No importer for ${file.name}`);
    return p;
  }
}
```

**Design points.** The plugin API is a published contract — version it and keep it tiny. Give plugins a *capability object* (`PluginContext`) instead of the whole app. Untrusted plugins need process or worker isolation, not just interfaces. Patterns: Strategy, Registry, Abstract Factory (if plugins provide families), Facade (the context).

### C11. Workflow engine

```ts
interface StepHandler<C> { run(ctx: C): Promise<void>; compensate?(ctx: C): Promise<void> }
class Workflow<C> {
  constructor(readonly name: string, private steps: { id: string; handler: StepHandler<C> }[]) {}
  async execute(ctx: C, journal: Journal) {
    const done: { id: string; handler: StepHandler<C> }[] = [];
    for (const step of this.steps) {
      if (await journal.isDone(step.id)) { done.push(step); continue; }   // resumable after crash
      try { await step.handler.run(ctx); await journal.markDone(step.id); done.push(step); }
      catch (e) {
        for (const s of done.reverse()) await s.handler.compensate?.(ctx);  // saga-style rollback
        throw e;
      }
    }
  }
}
```

**Why this model.** Steps are Commands; the workflow is a Template over them; the journal makes it resumable and idempotent. **Extend:** branching (steps return next step id → state machine), timers, human approval steps (persisted waiting state).

### C12. Inventory management

```ts
class StockItem {
  constructor(readonly sku: string, readonly warehouse: string, private onHand: number, private reserved: number, readonly version: number) {}
  get available() { return this.onHand - this.reserved; }
  reserve(qty: number) { if (qty <= 0 || qty > this.available) throw new Error(`Only ${this.available} available`); this.reserved += qty; }
  release(qty: number) { this.reserved = Math.max(0, this.reserved - qty); }
  commit(qty: number) { if (qty > this.reserved) throw new Error("Commit exceeds reservation"); this.reserved -= qty; this.onHand -= qty; }
  receive(qty: number) { if (qty <= 0) throw new Error("qty > 0"); this.onHand += qty; }
}
```

Invariant: `0 ≤ reserved ≤ onHand`. Concurrency: save with `WHERE version = ?`, retry on conflict; reservations expire via a scheduled job. Tests: cannot reserve beyond available; commit reduces both counters; release never goes negative.

### C14. Fix an LSP violation

**Broken:** `class Penguin extends Bird` where `Bird.fly()` exists and `Penguin.fly()` throws.

**Fix:** model capabilities, not taxonomy.

```ts
interface Bird { readonly species: string; eat(): void }

class Sparrow implements Bird, Flyer { species = "sparrow"; eat() {} fly(a: number) {} }
```

**Test:** a contract suite for `Flyer` run against every implementation; no implementation may throw for valid altitudes.

### C15. Replace a fragile inheritance hierarchy with composition

**Before:** `Report → PdfReport → EncryptedPdfReport → EmailedEncryptedPdfReport` (and the CSV mirror). Each new feature doubles the classes.

**After:**

```ts
interface Renderer { render(data: ReportData): Buffer }
interface Transform { apply(b: Buffer): Buffer }
interface Delivery { deliver(b: Buffer, meta: { name: string }): Promise<void> }
class ReportJob {
  constructor(private renderer: Renderer, private transforms: Transform[], private delivery: Delivery) {}
  async run(data: ReportData, name: string) {
    const out = this.transforms.reduce((b, t) => t.apply(b), this.renderer.render(data));
    await this.delivery.deliver(out, { name });
  }
}

```

Three small interfaces replace an M × N × K hierarchy with M + N + K classes, combinable at runtime.

### C17. State machine with the State pattern

Use the order example in 6.4. Also implement the table-driven version and compare:

```ts
type S = "pending" | "paid" | "shipped" | "cancelled"; type E = "pay" | "ship" | "cancel";
const transitions: Record<S, Partial<Record<E, S>>> = {
  pending: { pay: "paid", cancel: "cancelled" },
  paid: { ship: "shipped", cancel: "cancelled" },
  shipped: {}, cancelled: {},
};
function next(s: S, e: E): S { const n = transitions[s][e]; if (!n) throw new Error(`Cannot ${e} when ${s}`); return n; }
test.each([["pending", "ship"], ["shipped", "cancel"]] as const)("rejects %s → %s", (s, e) => {
  expect(() => next(s, e)).toThrow();
});
```

The table is easier to visualise, persist and test exhaustively; State classes win when each state has rich behaviour (different pricing, notifications, UI).

### C19. File import system for multiple formats

```ts
interface RowSource { rows(): AsyncIterable<Record<string, string>> }
interface FormatReader { accepts(file: { name: string; mime: string }): boolean; open(stream: Readable): RowSource }
class ImportPipeline<T> {
  constructor(private readers: FormatReader[], private map: (r: Record<string, string>) => T,
              private validate: Validator<T>, private sink: { writeBatch(items: T[]): Promise<void> }, private batchSize = 500) {}
  async run(file: { name: string; mime: string; stream: Readable }) {
    const reader = this.readers.find(r => r.accepts(file)); if (!reader) throw new Error(`Unsupported: ${file.name}`);
    const errors: { line: number; issues: string[] }[] = []; let batch: T[] = []; let line = 1;
    for await (const raw of reader.open(file.stream).rows()) {
      line++; const item = this.map(raw); const res = this.validate.validate(item);
      if (!res.ok) { errors.push({ line, issues: res.errors }); continue; }
      batch.push(item); if (batch.length >= this.batchSize) { await this.sink.writeBatch(batch); batch = []; }
    }
    if (batch.length) await this.sink.writeBatch(batch);
    return { errors };
  }
}
```

Streams keep memory flat for large files; per-row errors are collected rather than aborting. Decide (and state) whether partial imports are acceptable or the whole file must be transactional.

### C20. Pluggable validation engine

```ts
type Result = { ok: true } | { ok: false; errors: string[] };
interface Validator<T> { validate(v: T): Result }
const rule = <T>(test: (v: T) => boolean, msg: string): Validator<T> => ({ validate: v => (test(v) ? { ok: true } : { ok: false, errors: [msg] }) });
const all = <T>(...vs: Validator<T>[]): Validator<T> => ({
  validate: v => { const errors = vs.flatMap(x => { const r = x.validate(v); return r.ok ? [] : r.errors; }); return errors.length ? { ok: false, errors } : { ok: true }; },
});
const field = <T, K extends keyof T>(k: K, inner: Validator<T[K]>): Validator<T> => ({
  validate: v => { const r = inner.validate(v[k]); return r.ok ? r : { ok: false, errors: r.errors.map(e => `${String(k)}: ${e}`) }; },
});
const customer = all<{ name: string; age: number }>(
  field("name", rule(s => s.trim().length > 0, "required")),
  field("age", rule(n => n >= 18, "must be 18+")),
);
customer.validate({ name: "", age: 16 }); // { ok: false, errors: ["name: required", "age: must be 18+"] }
```

Composite + Strategy, written functionally — a good moment to say that OOP patterns and functions are not rivals. Extend with async rules (`validateAsync`), `any`/`not` combinators, and i18n message keys instead of strings.
