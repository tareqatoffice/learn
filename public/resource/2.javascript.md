# Core concepts

## §1 Fundamentals: data types, coercion, equality

### Q1.1 \[I\] What are JavaScript's data types?

There are **8 types**: 7 primitives (`undefined`, `null`, `boolean`, `number`, `bigint`, `string`, `symbol`) and `object` (which includes arrays, functions, dates, maps, etc.). Primitives are immutable and compared by value; objects are mutable and compared by reference.

```js
let a = 'hi'; let b = a; b += '!';   // a is still 'hi' — strings are immutable
const o1 = { x: 1 }; const o2 = o1; o2.x = 2; // o1.x === 2 — same reference
{ x: 1 } === { x: 1 }                // false — two different objects
```

**Follow-up:** *Is everything in JS an object?* No. Primitives get temporary wrapper objects (autoboxing) when you access a property: `'abc'.length` creates a `String` wrapper, reads `length`, discards it. That's why `'abc'.foo = 1` is silently ignored in sloppy mode and throws a `TypeError` in strict mode.

### Q1.2 \[I\] How does `typeof` behave, and what are its quirks?

| Expression | Result | Note |
| --- | --- | --- |
| `typeof null` | `'object'` | Historical bug from the first implementation; never fixed |
| `typeof []` | `'object'` | Use `Array.isArray()` |
| `typeof function(){}` | `'function'` | Functions are callable objects |
| `typeof NaN` | `'number'` | NaN is a numeric value |
| `typeof undeclaredVar` | `'undefined'` | No ReferenceError… |
| `typeof x; let x;` | ReferenceError | …except in the TDZ of `let`/`const`/`class` |
| `typeof 10n` | `'bigint'` |  |
| `typeof Symbol()` | `'symbol'` |  |

Reliable type check: `Object.prototype.toString.call(v)` → `'[object Date]'`, `'[object Null]'`, etc.

### Q1.3 \[I\] Explain `null` vs `undefined`.

`undefined` means "no value was assigned" (missing property, missing argument, uninitialised `var`, function with no `return`). `null` is an intentional "empty" set by the programmer. `null == undefined` is `true`, `null === undefined` is `false`. Default parameters and destructuring defaults trigger only on `undefined`, not `null`:

```js
function f(x = 5) { return x; }
f(undefined); // 5
f(null);      // null
```

### Q1.4 \[I+\] How does type coercion work? Explain ToPrimitive.

Operators convert operands using abstract operations: **ToPrimitive**, **ToNumber**, **ToString**, **ToBoolean**.

- `+` with any string operand (after ToPrimitive) → string concatenation; otherwise numeric addition.
- `-`, `*`, `/`, `%`, unary `+` → always ToNumber.
- ToPrimitive(obj, hint) calls `obj[Symbol.toPrimitive]` if present; otherwise for hint `"number"`/`"default"` tries `valueOf()` then `toString()`; for hint `"string"` tries `toString()` first. (Date uses `"string"` for the default hint.)

```js
[] + []        // ''            ([] → '' via toString)
[] + {}        // '[object Object]'
1 + '2'        // '12'
'5' - 2        // 3
'5' * '2'      // 10
true + 1       // 2
[1,2] + [3]    // '1,23'
+[]            // 0
+{}            // NaN
+'  42\n'      // 42 (whitespace trimmed)
null + 1       // 1  (null → 0)
undefined + 1  // NaN

const money = { [Symbol.toPrimitive](hint) { return hint === 'number' ? 42 : '$42'; } };
+money          // 42
`${money}`      // '$42'
money + ''      // '$42' (hint 'default' → returns string)
```

**Falsy values (exactly 8):** `false`, `0`, `-0`, `0n`, `''`, `null`, `undefined`, `NaN`. Everything else is truthy — including `'0'`, `'false'`, `[]`, `{}`, `new Boolean(false)`.

### Q1.5 \[I\] `==` vs `===` vs `Object.is`

- `===` (strict): no coercion. Only oddities: `NaN !== NaN`, `+0 === -0`.
- `==` (loose): coerces using the Abstract Equality algorithm. Key rules: `null == undefined` (and nothing else); number vs string → string to number; boolean → number first; object vs primitive → ToPrimitive on the object.
- `Object.is` (SameValue): like `===` but `Object.is(NaN, NaN) === true` and `Object.is(0, -0) === false`. Used by React for state comparison.
- `Array.prototype.includes`, `Map`, `Set` use **SameValueZero**: NaN equals NaN, +0 equals -0. That's why `[NaN].includes(NaN)` is `true` but `[NaN].indexOf(NaN)` is `-1`.

```js
'' == 0            // true  ('' → 0)
'0' == false       // true  (false → 0, '0' → 0)
[] == false        // true  ([] → '' → 0)
[] == ![]          // true  (![] is false → 0; [] → 0)
null == 0          // false (null only == undefined)
null >= 0          // true  (relational uses ToNumber: 0 >= 0)
NaN == NaN         // false
[0] == false       // true
```

**Production rule:** use `===` everywhere; the one accepted idiom for `==` is `x == null` to test for both `null` and `undefined`.

### Q1.6 \[I+\] Why is `0.1 + 0.2 !== 0.3`? How do you handle money?

Numbers are IEEE-754 64-bit doubles; 0.1 and 0.2 have no exact binary representation, so the sum is `0.30000000000000004`. Compare with a tolerance (`Math.abs(a - b) < Number.EPSILON`) for small values. For money, store **integer minor units** (cents/paisa), use `BigInt` for large integers, or a decimal library. `Number.MAX_SAFE_INTEGER` is 2^53 − 1; beyond it integers lose precision (`9007199254740992 === 9007199254740993` is `true`). Format with `Intl.NumberFormat`.

### Q1.7 \[I\] `NaN` and `isNaN` vs `Number.isNaN`

`isNaN('abc')` is `true` because it coerces first; `Number.isNaN('abc')` is `false` because it checks only for the actual NaN value. Prefer `Number.isNaN`, `Number.isFinite`, `Number.isInteger`, `Number.parseFloat`.

### Q1.8 \[I+\] Primitive wrapper trap

```js
const b = new Boolean(false);
if (b) console.log('runs!');    // runs — any object is truthy
typeof new String('a')          // 'object'
new String('a') === 'a'         // false
```

Never use `new` with `Boolean`, `String`, or `Number`. Calling them without `new` is a legitimate conversion: `Number('42')`, `String(x)`, `Boolean(x)`.

**Follow-ups for §1:** How does `BigInt` mix with `Number`? (It doesn't: `1n + 1` throws `TypeError`; comparisons `1n < 2` work.) What does `structuredClone` copy that `JSON` doesn't? (Dates, Maps, Sets, typed arrays, cyclic references; not functions, DOM nodes or class prototypes.)

## §2 Scope, hoisting, closures, execution context

### Q2.1 \[I+\] What is an execution context, and what happens when one is created?

An execution context is the environment in which code runs. There is one **global** context, one per **function call**, and one per `eval`/module. Each is created in two phases:

1. **Creation phase** — the engine builds the *LexicalEnvironment* (for `let`/`const`/`class`/functions) and the *VariableEnvironment* (for `var`), binds `this`, and sets the outer reference (the scope chain). Function declarations are stored fully; `var` is initialised to `undefined`; `let`/`const`/`class` are created but **uninitialised** (TDZ).
2. **Execution phase** — code runs line by line, assignments happen.

Contexts are pushed onto the **call stack**; the top one is running. When a function returns, its context pops — but its environment record survives if a closure still references it.

The stack order (who called whom) and the scope chain (where code was written) happen to line up here; they diverge as soon as a function is called from somewhere other than where it was defined — lookups always follow the scope chain.

### Q2.2 \[I\] What is hoisting? Compare `var`, `let`, `const`, functions and classes.

| Declaration | Hoisted? | Initial value | Scope | Redeclare? | Global object property? |
| --- | --- | --- | --- | --- | --- |
| `var` | Yes | `undefined` | Function | Yes | Yes (`window.x`) |
| `let` | Yes | Uninitialised (TDZ) | Block | No | No |
| `const` | Yes | Uninitialised (TDZ) | Block | No | No |
| `function` declaration | Yes | The whole function | Function (block in strict mode) | Yes | Yes (sloppy) |
| Function expression / arrow | Only the variable | Per `var`/`let` rules | — | — | — |
| `class` | Yes | Uninitialised (TDZ) | Block | No | No |

```js
console.log(a); // undefined
var a = 1;

console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 2;

foo();          // 'hi' — declaration fully hoisted
function foo() { console.log('hi'); }

bar();          // TypeError: bar is not a function (bar is undefined)
var bar = () => {};
```

### Q2.3 \[I+\] What is the Temporal Dead Zone?

The TDZ is the span from the start of a block until a `let`/`const`/`class` declaration is evaluated. Accessing the binding there throws `ReferenceError`. It proves `let` *is* hoisted — otherwise the inner access below would read the outer `x`:

```js
let x = 'outer';
{
  console.log(x); // ReferenceError, not 'outer'
  let x = 'inner';
}

function f(a = b, b = 1) {} 
f(); // ReferenceError — parameters have their own TDZ, evaluated left to right
```

### Q2.4 \[I\] Lexical scope vs dynamic scope

JS uses **lexical (static) scope**: a function's accessible variables are decided by where it is *written*, not where it is *called*. (`this` is the exception — it is dynamic, see §3.)

```js
const x = 'global';
function outer() { const x = 'outer'; return inner(); }
function inner() { return x; }
outer(); // 'global' — inner was defined at top level
```

### Q2.5 \[I\] What is a closure? Give practical uses.

A closure is a function together with references to the variables of the scope it was created in. The function keeps those variables alive after the outer function has returned.

```js
function createCounter() {
  let count = 0;                      // private state
  return {
    inc: () => ++count,
    get: () => count,
  };
}
const c = createCounter();
c.inc(); c.inc(); c.get(); // 2 — count is unreachable from outside
```

**Uses:** data privacy / module pattern, function factories, partial application and currying, memoization caches, event handlers that remember state, `debounce`/`throttle`, once-functions.

**Senior nuance:** closures capture *variables* (bindings), not values. V8 allocates only the captured variables in a heap "context" object, but all closures created in the same scope **share that context** — so one long-lived closure can retain a large object that only a sibling closure used (a classic leak; see §12).

### Q2.6 \[I\] The classic loop closure problem

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);
// 3 3 3 — one function-scoped i, read after the loop ends

for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);
// 0 1 2 — let creates a new binding per iteration (copied from the previous one)
```

Pre-ES6 fixes: an IIFE `(function(j){ setTimeout(() => console.log(j)); })(i)` or `setTimeout(console.log, 0, i)` (extra args are passed to the callback).

### Q2.7 \[I+\] What does strict mode change?

- Assigning to an undeclared variable throws instead of creating a global.
- `this` is `undefined` in plain function calls (not `globalThis`).
- Writing to read-only/non-writable properties and getter-only properties throws.
- Duplicate parameter names, `with`, and octal literals `010` are syntax errors.
- `arguments` is not linked to named parameters; `arguments.callee` throws.
- `eval` gets its own scope.

ES modules and `class` bodies are **always strict**.

### Q2.8 \[S\] Explain the scope chain lookup and its performance implications.

Identifier resolution walks environment records outward until found (or throws `ReferenceError` / creates a global in sloppy mode). Engines resolve most lookups at parse time to fixed (depth, slot) pairs, so deep nesting costs little. What defeats this: sloppy-mode direct `eval` and `with`, which can inject bindings at runtime and force dynamic lookup — and deoptimise the whole enclosing function.

**Follow-ups:** What does an IIFE give you that a block does not? (Pre-ES6 privacy; today a block plus `let`/`const` or a module does the job.) Why does `typeof undeclared` not throw while `typeof tdzVar` does?

## §3 `this`, call/apply/bind, arrow functions

### Q3.1 \[I\] How is `this` determined?

`this` is set by **how a function is called**, not where it is defined (arrows excepted). Check these rules in priority order:

1. **`new` binding** — `new Foo()` → `this` is the newly created object.
2. **Explicit binding** — `fn.call(obj)`, `fn.apply(obj)`, `fn.bind(obj)` → `this` is `obj`.
3. **Implicit binding** — `obj.method()` → `this` is the object left of the dot.
4. **Default binding** — plain `fn()` → `undefined` in strict mode, `globalThis` in sloppy mode.

**Arrow functions** skip all four: they have no own `this` and use the `this` of the enclosing lexical scope, permanently.

&#91;embedded content: how this is bound · 5 checks in order\]

Walk the checks in order at the call site; the first "yes" decides `this`. Extracting a method (`const f = obj.method`) silently drops you from row 4 to row 5.

The chart asks "arrow function?" first only because no other rule can change an arrow's `this` (arrows can't be `new`-ed and ignore `call`/`apply`/`bind`). For regular functions the priority is exactly the list above: `new` → explicit → implicit → default.

```js
const user = {
  name: 'Ana',
  regular() { return this?.name; },
  arrow: () => this?.name,          // `this` of module/global scope
  delayed() { setTimeout(() => console.log(this.name), 0); }, // arrow inherits 'Ana'
};
user.regular();             // 'Ana'   (implicit)
user.arrow();               // undefined (lexical; module scope this is undefined)
const f = user.regular; f(); // undefined — implicit binding lost
user.delayed();             // 'Ana'
```

### Q3.2 \[I\] call vs apply vs bind

| Method | Invokes immediately? | Arguments | Returns |
| --- | --- | --- | --- |
| `fn.call(thisArg, a, b)` | Yes | Listed individually | Result of fn |
| `fn.apply(thisArg, [a, b])` | Yes | Array (or array-like) | Result of fn |
| `fn.bind(thisArg, a)` | No | Pre-filled (partial application) | New bound function |

```js
function greet(greeting, punct) { return `${greeting}, ${this.name}${punct}`; }
const p = { name: 'Rafi' };
greet.call(p, 'Hi', '!');       // 'Hi, Rafi!'
greet.apply(p, ['Hello', '.']); // 'Hello, Rafi.'
const hiRafi = greet.bind(p, 'Hi');
hiRafi('?');                    // 'Hi, Rafi?'
Math.max.apply(null, [1, 5, 3]); // 5  (today: Math.max(...arr))
```

**Edge cases interviewers probe:**

- A bound function **cannot be re-bound**: `fn.bind(a).bind(b)` keeps `a`. `call`/`apply` on it can't change `this` either.
- `new` **overrides** bind's `this` (but keeps pre-filled args): `new (Foo.bind(obj, 1))()` creates a new object.
- Arrow functions ignore `call`/`apply`/`bind` for `this`.
- In sloppy mode, passing a primitive or `null` as `thisArg` boxes it / replaces it with `globalThis`; in strict mode it stays as passed.

### Q3.3 \[I+\] Implement `bind` (and `call`) from scratch

```js
Function.prototype.myCall = function (ctx, ...args) {
  ctx = ctx == null ? globalThis : Object(ctx);
  const key = Symbol('fn');          // avoid clobbering an existing prop
  ctx[key] = this;
  try { return ctx[key](...args); }
  finally { delete ctx[key]; }
};

Function.prototype.myBind = function (ctx, ...preset) {
  const target = this;
  if (typeof target !== 'function') throw new TypeError('Bind must be called on a function');
  function bound(...later) {
    // Called with `new`? Then ignore ctx and construct.
    if (new.target) return Reflect.construct(target, [...preset, ...later], new.target);
    return target.apply(ctx, [...preset, ...later]);
  }
  if (target.prototype) bound.prototype = Object.create(target.prototype);
  return bound;
};
```

Follow-up: why `Symbol` as the temporary key? (No collision with existing properties, not enumerable in `for…in` by default.)

### Q3.4 \[I\] Arrow functions vs regular functions — full list of differences

| Feature | Regular function | Arrow function |
| --- | --- | --- |
| Own `this` | Yes (dynamic) | No (lexical) |
| `arguments` object | Yes | No (use rest `...args`) |
| Usable with `new` | Yes | No — TypeError |
| `prototype` property | Yes | No |
| `super`, `new.target` | Own | Lexical |
| Can be a generator | Yes | No |
| Duplicate param names (sloppy) | Allowed | Never |

**When NOT to use arrows:** object methods that need `this`, prototype methods, constructors, DOM handlers that rely on `this === event.currentTarget`, functions that need `arguments`.

**When to prefer arrows:** callbacks inside methods (`map`, `setTimeout`, promise chains) where you want the outer `this`.

### Q3.5 \[I+\] Class methods losing `this`

```js
class Button {
  label = 'Save';
  onClickBroken() { console.log(this.label); }
  onClick = () => console.log(this.label);   // class field arrow: bound per instance
}
const b = new Button();
const h1 = b.onClickBroken; h1(); // TypeError: cannot read 'label' of undefined (class bodies are strict)
const h2 = b.onClick; h2();       // 'Save'
```

**Trade-off (senior):** class-field arrows create one function per instance (more memory, not on the prototype, can't be overridden via `super.method()` and are harder to spy on in tests). Alternatives: bind in the constructor, or bind at the call site.

### Q3.6 \[I+\] `this` in callbacks and event handlers

- `addEventListener('click', function () { this })` → the element (`event.currentTarget`).
- `addEventListener('click', () => this)` → outer `this`.
- `arr.map(function () { return this.x; }, ctx)` — many array methods take a `thisArg` as the second argument.
- `setTimeout(obj.method, 0)` loses `this`; wrap it: `setTimeout(() => obj.method(), 0)`.

**Follow-ups:** What is `this` at the top level of an ES module? (`undefined`.) In a Node CommonJS file? (`module.exports`, i.e. `{}`.) In a browser classic script? (`window`.) What is `globalThis`? (The standard name for the global object in every environment.)

## §4 Prototypes, inheritance, classes

### Q4.1 \[I\] What is the prototype chain?

Every object has an internal `[[Prototype]]` link (exposed via `Object.getPrototypeOf(obj)`, legacy `obj.__proto__`). When a property isn't found on the object, the engine follows the link, then that object's link, until it reaches `null`. **Reads** walk the chain; **writes** create an own property on the receiver (unless a setter or a non-writable property is found up the chain).

```js
const animal = { eats: true, walk() { return `${this.name} walks`; } };
const dog = Object.create(animal);
dog.name = 'Rex';
dog.walk();                  // 'Rex walks' — found on animal, this = dog
dog.hasOwnProperty('eats');  // false
'eats' in dog;               // true (in checks the chain)
Object.hasOwn(dog, 'name');  // true (ES2022, preferred)
```

### Q4.2 \[I+\] `prototype` vs `__proto__` vs `[[Prototype]]`

- `[[Prototype]]`: the internal link every object has.
- `__proto__`: a legacy accessor on `Object.prototype` that reads/writes `[[Prototype]]`. Use `Object.getPrototypeOf` / `Object.setPrototypeOf` instead.
- `Fn.prototype`: a regular property that exists on (non-arrow, non-method) functions. It becomes the `[[Prototype]]` of objects created by `new Fn()`.

```js
function Person(name) { this.name = name; }
Person.prototype.hi = function () { return 'hi ' + this.name; };
const p = new Person('Mia');
Object.getPrototypeOf(p) === Person.prototype;           // true
Person.prototype.constructor === Person;                 // true
Object.getPrototypeOf(Person.prototype) === Object.prototype; // true
Object.getPrototypeOf(Person) === Function.prototype;    // true
```

&#91;embedded content: prototype chain for new Person('Mia')\]

`Person.prototype` is an ordinary object that `new` wires in as the instance's `[[Prototype]]`; the function `Person` itself sits on a separate chain through `Function.prototype`.

### Q4.3 \[I+\] What does `new` do? Implement it.

1. Create a new object whose `[[Prototype]]` is `Fn.prototype`.
2. Call `Fn` with `this` bound to that object.
3. If `Fn` returns an **object**, use it; otherwise return the new object.

```js
function myNew(Fn, ...args) {
  const obj = Object.create(Fn.prototype);
  const result = Fn.apply(obj, args);
  return result !== null && (typeof result === 'object' || typeof result === 'function') ? result : obj;
}
```

### Q4.4 \[I\] ES6 classes — are they "real" classes?

They are mostly syntax over prototypes, with real differences:

- Class bodies are **strict mode**; class declarations are in the TDZ until evaluated.
- Calling a class without `new` throws.
- Methods are **non-enumerable** and lack `prototype` (cannot be `new`-ed).
- `extends` sets up two chains: `Child.prototype → Parent.prototype` (instances) and `Child → Parent` (static members).
- Derived constructors must call `super()` before touching `this`, because the *parent* allocates the object (that's what makes `class MyArray extends Array` work).
- Supports `#private` fields/methods, `static` blocks, and public class fields.

```js
class Shape {
  #id = crypto.randomUUID();           // truly private (hard privacy, not a naming convention)
  static count = 0;
  static { /* static init block */ }
  constructor(name) { this.name = name; Shape.count++; }
  area() { return 0; }
  get id() { return this.#id; }
  static isShape(x) { return #id in x; } // ergonomic brand check (ES2022)
}
class Circle extends Shape {
  constructor(r) { super('circle'); this.r = r; }
  area() { return Math.PI * this.r ** 2; }
  toString() { return `${super.toString()} r=${this.r}`; }
}
```

### Q4.5 \[I+\] Inheritance patterns before classes

```js
function Animal(name) { this.name = name; }
Animal.prototype.speak = function () { return `${this.name} makes a sound`; };

function Dog(name, breed) {
  Animal.call(this, name);            // inherit instance props
  this.breed = breed;
}
Dog.prototype = Object.create(Animal.prototype); // inherit methods
Dog.prototype.constructor = Dog;                 // repair constructor
```

Why not `Dog.prototype = new Animal()`? It runs the parent constructor with no args and puts instance state on the shared prototype. Why not `Dog.prototype = Animal.prototype`? Then adding a Dog method mutates Animal too.

### Q4.6 \[S\] Composition vs inheritance — when do you choose which?

Deep class hierarchies couple subclasses to parent internals (the *fragile base class* problem) and force a single taxonomy. Prefer **composition** — objects built from small capabilities — when behaviours vary independently.

```js
const canFly = (s) => ({ fly: () => `${s.name} flies` });
const canSwim = (s) => ({ swim: () => `${s.name} swims` });
const createDuck = (name) => { const s = { name }; return { ...s, ...canFly(s), ...canSwim(s) }; };
```

Use inheritance for genuine *is-a* relationships with a stable base contract (e.g. `class ValidationError extends Error`, framework base classes). Use composition, dependency injection, or mixins for *has-a* / *can-do* features.

### Q4.7 \[I+\] `instanceof` — how it works and how it fails

`a instanceof B` checks whether `B.prototype` appears anywhere in `a`'s chain (customisable via `static [Symbol.hasInstance]`). It fails across realms: an array from an iframe is not `instanceof Array` in the parent window — use `Array.isArray`. It also lies if someone reassigns `B.prototype` after creating `a`.

### Q4.8 \[S\] Why is modifying built-in prototypes (`Array.prototype.x = …`) a bad idea?

It affects every array in the realm (including third-party code), can collide with future standard methods (the *SmooshGate* incident forced the standard name `Array.prototype.flat` because MooTools had added `flatten`), shows up in `for…in` if enumerable, and changes object shapes globally. Polyfill only standard methods, only when missing, and define them non-enumerable via `Object.defineProperty`.

**Follow-ups:** What does `Object.create(null)` give you? (An object with no prototype — safe dictionary, no `toString`/`__proto__` keys; useful against prototype pollution.) How do you make a property read-only? (`Object.defineProperty(obj, 'x', { writable: false })`, or `Object.freeze`.)

### Q5.3 \[I\] Spread vs rest

## §6 Functions: higher-order functions, currying, composition

### Q6.1 \[I\] What is a higher-order function? First-class functions?

Functions are **first-class values**: they can be stored, passed and returned. A **higher-order function** takes a function as an argument or returns one (`map`, `filter`, `reduce`, `addEventListener`, `debounce`, middleware, React HOCs).

### Q6.2 \[I\] Implement `map`, `filter` and `reduce`

```js
Array.prototype.myMap = function (fn, thisArg) {
  const out = new Array(this.length);
  for (let i = 0; i < this.length; i++) {
    if (i in this) out[i] = fn.call(thisArg, this[i], i, this); // preserve holes
  }
  return out;
};

Array.prototype.myReduce = function (fn, ...init) {
  let i = 0, acc;
  if (init.length) acc = init[0];
  else {
    while (i < this.length && !(i in this)) i++;
    if (i >= this.length) throw new TypeError('Reduce of empty array with no initial value');
    acc = this[i++];
  }
  for (; i < this.length; i++) if (i in this) acc = fn(acc, this[i], i, this);
  return acc;
};
```

Why `...init` and not `init = undefined`? Because `reduce(fn, undefined)` is a valid explicit initial value and must be distinguished from "no initial value".

### Q6.3 \[I+\] Currying vs partial application — implement `curry`

**Currying** transforms `f(a, b, c)` into `f(a)(b)(c)`. **Partial application** fixes some arguments and returns a function of the rest (`bind` does this).

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...next) => curried.apply(this, [...args, ...next]);
  };
}
const add3 = curry((a, b, c) => a + b + c);
add3(1)(2)(3); add3(1, 2)(3); add3(1)(2, 3); // all 6
```

Caveat: `fn.length` ignores rest params and params after the first default, so curry needs an explicit arity for those.

**Follow-up (classic):** infinite `sum(1)(2)(3)()` →

```js
const sum = (a) => (b) => b === undefined ? a : sum(a + b);
sum(1)(2)(3)(); // 6
```

### Q6.4 \[I+\] Function composition — `compose` and `pipe`

### Q6.5 \[I+\] Memoization — implement it and name the pitfalls

```js
function memoize(fn, { key = (...a) => JSON.stringify(a), max = 1000 } = {}) {
  const cache = new Map();
  return function (...args) {
    const k = key(...args);
    if (cache.has(k)) {
      const v = cache.get(k); cache.delete(k); cache.set(k, v); // LRU refresh
      return v;
    }
    const v = fn.apply(this, args);
    cache.set(k, v);
    if (cache.size > max) cache.delete(cache.keys().next().value); // evict oldest
    return v;
  };
}
```

Pitfalls: only memoize **pure** functions; `JSON.stringify` keys fail for functions, cycles, and key order differences; unbounded caches leak memory; caching a **promise** (not the result) dedupes concurrent calls but also caches rejections unless you delete on failure; object arguments → use a `WeakMap` keyed by the object.

### Q6.6 \[I\] Debounce vs throttle

- **Debounce:** run once after calls stop for `wait` ms (search-as-you-type, resize end, autosave).
- **Throttle:** run at most once per `wait` ms during a stream (scroll, mousemove, analytics pings).

```js
function debounce(fn, wait, { leading = false } = {}) {
  let t;
  return function (...args) {
    const callNow = leading && !t;
    clearTimeout(t);
    t = setTimeout(() => { t = null; if (!leading) fn.apply(this, args); }, wait);
    if (callNow) fn.apply(this, args);
  };
}

function throttle(fn, wait) {
  let last = 0, timer = null, pending;
  return function (...args) {
    const now = Date.now();
    const remaining = wait - (now - last);
    pending = () => { last = Date.now(); timer = null; fn.apply(this, args); };
    if (remaining <= 0) { clearTimeout(timer); pending(); }
    else if (!timer) timer = setTimeout(() => pending(), remaining); // trailing call with latest args
  };
}
```

For visual updates, throttling to `requestAnimationFrame` usually beats a fixed `wait`.

### Q6.7 \[I\] Implement `once`

```js
function once(fn) {
  let done = false, result;
  return function (...args) {
    if (!done) { done = true; result = fn.apply(this, args); fn = null; } // release fn for GC
    return result;
  };
}
```

### Q6.8 \[I+\] Pure functions and side effects

A pure function returns the same output for the same input and has no observable side effects (no I/O, no mutation of arguments or outer state, no `Date.now()`/`Math.random()`). Benefits: testable, cacheable, parallelisable, safe to reorder. Production code keeps an *impure shell* (I/O, DOM, network) around a *pure core* (business logic).

## §7 Event loop, call stack, microtasks, macrotasks

### Q7.1 \[I\] JavaScript is single-threaded — so how does async work?

The **engine** (V8, SpiderMonkey, JSC) runs one call stack on one thread. The **host** (browser or Node) supplies Web APIs / libuv that do the waiting — timers, network, file I/O — on other threads or the OS, then queue callbacks. The **event loop** moves queued callbacks onto the stack only when the stack is empty.

### Q7.2 \[I+\] Microtasks vs macrotasks — what goes where, and in what order?

| Queue | Sources | When it runs |
| --- | --- | --- |
| Microtask queue | Promise reactions (`.then/.catch/.finally`), `await` continuations, `queueMicrotask`, `MutationObserver` | After the current script/task finishes and **whenever the stack empties** — drained *completely*, including microtasks added during draining |
| Task (macrotask) queues | `setTimeout`/`setInterval`, I/O callbacks, UI events, `MessageChannel`, `postMessage`, `setImmediate` (Node) | **One task per loop iteration** |
| Rendering | `requestAnimationFrame` callbacks, style, layout, paint | Browser decides, typically once per frame (\~16.7 ms at 60 Hz), after microtasks |

**One loop iteration (browser):** run one task → drain all microtasks → (maybe) run rAF callbacks, render → repeat.

&#91;embedded content: browser event loop · 4 steps per iteration\]

Because step 2 empties the microtask queue completely, a promise callback always runs before a `setTimeout` queued earlier — and a microtask that keeps queuing microtasks never lets steps 3 and 4 happen.

```js
console.log('1 sync');
setTimeout(() => console.log('5 timeout'), 0);
Promise.resolve().then(() => console.log('3 micro'));
queueMicrotask(() => console.log('4 micro'));
console.log('2 sync');
// 1 sync, 2 sync, 3 micro, 4 micro, 5 timeout
```

**Step-by-step:**

| Step | Call stack | Microtask queue | Task queue | Output |
| --- | --- | --- | --- | --- |
| 1 | main: `log('1 sync')` | — | — | 1 sync |
| 2 | main: `setTimeout` registers timer | — | (timer → cb A after 0 ms) |  |
| 3 | main: `then` queues B | B | A |  |
| 4 | main: `queueMicrotask` queues C | B, C | A |  |
| 5 | main: `log('2 sync')` | B, C | A | 2 sync |
| 6 | main ends → drain microtasks | C | A | 3 micro |
| 7 |  | — | A | 4 micro |
| 8 | next task: A | — | — | 5 timeout |

### Q7.3 \[I+\] How does `await` interact with the queue?

`await x` is roughly `Promise.resolve(x).then(continuation)`. Code **before** the first `await` in an async function runs synchronously; everything after it is a microtask.

```js
async function a() { console.log('A1'); await null; console.log('A2'); }
console.log('S1');
a();
console.log('S2');
// S1, A1, S2, A2
```

### Q7.4 \[S\] Can microtasks starve the event loop?

Yes. Because the microtask queue drains completely, a microtask that queues another microtask forever blocks rendering, input, and timers — the page freezes like an infinite loop, though no single function runs long.

```js
function loop() { Promise.resolve().then(loop); }
loop(); // tab hangs; setTimeout-based recursion would not
```

Use `setTimeout`/`MessageChannel`/`scheduler.postTask`/`scheduler.yield()` to **yield** to the browser between chunks of work.

### Q7.5 \[I+\] Why is `setTimeout(fn, 0)` not 0 ms?

It's a *minimum* delay. The callback waits for the current task and all microtasks to finish, and for its turn in the task queue. Browsers clamp nested timers (nesting depth ≥ 5) to ≥ 4 ms and throttle timers in background tabs (often to ≥ 1 s). Node clamps 0 to 1 ms.

### Q7.6 \[S\] Node.js event loop phases — how do they differ from the browser?

Node (libuv) runs phases in order: **timers** (`setTimeout`/`setInterval`) → **pending callbacks** → **idle/prepare** → **poll** (I/O; may block waiting) → **check** (`setImmediate`) → **close callbacks**. Between each callback, Node drains `process.nextTick` queue first, then the promise microtask queue.

```js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
// nextTick, promise, then timeout/immediate in NON-deterministic order from the main module
// Inside an I/O callback, setImmediate always runs before setTimeout(…, 0).
```

`process.nextTick` has higher priority than promise microtasks — and the same starvation risk.

### Q7.7 \[I+\] Where does `requestAnimationFrame` fit?

rAF callbacks run **before the next paint**, after microtasks, once per frame. Use them for visual work (reading layout then writing styles, animations). `setTimeout(16)` drifts and can run mid-frame, causing jank. `requestIdleCallback` runs when the frame has spare time — fine for non-urgent work (analytics, prefetch) but may never run on a busy page; pass a `timeout`.

### Q7.8 \[S\] How do you keep a long task from blocking the UI?

Any task > 50 ms is a *long task* and hurts Interaction to Next Paint (INP). Options:

1. **Chunk + yield:** process items in batches and yield between them.
2. **Web Workers** for CPU-heavy work (parsing, image processing, crypto, diffing) — true parallelism, communicate via `postMessage` (structured clone) or transfer `ArrayBuffer`s.
3. **Move work off the critical path:** lazy-load, `requestIdleCallback`, server-side.
4. **Algorithmic fixes** first — profiling usually finds an O(n²) loop.

```js
async function processAll(items, handle) {
  let deadline = performance.now() + 8;
  for (const item of items) {
    handle(item);
    if (performance.now() > deadline) {
      await (globalThis.scheduler?.yield?.() ?? new Promise((r) => setTimeout(r, 0)));
      deadline = performance.now() + 8;
    }
  }
}
```

**Follow-ups:** Is a `click()` called from code dispatched synchronously? (Yes — `el.click()` runs listeners synchronously, so microtasks run *after all listeners*; a real user click runs microtasks *between* listeners.) Does `MutationObserver` fire synchronously? (No, as a microtask, batched.)

## §8 Promises, async/await, error handling, concurrency

### Q8.1 \[I\] What is a Promise? States and guarantees

A Promise represents a future value. States: **pending → fulfilled** or **pending → rejected** (together, *settled*). It settles **once**; later `resolve`/`reject` calls are ignored. Handlers always run **asynchronously** (as microtasks), even if the promise is already settled — this removes the "sometimes sync, sometimes async" bug class (*Zalgo*).

`resolve(value)` where `value` is a thenable *adopts* that thenable's state, so `resolve(promiseB)` doesn't fulfil with a promise — it follows B. (`reject` never unwraps.)

### Q8.2 \[I\] How does chaining work?

Each `.then` returns a **new** promise resolved with the handler's return value (or rejected with what it throws). Returning a promise flattens it.

```js
fetchUser(id)
  .then((u) => fetchOrders(u.id))  // returns a promise → chain waits
  .then((orders) => orders.length)
  .catch((err) => { log(err); return 0; }) // recovers; chain continues fulfilled
  .finally(() => hideSpinner());          // no args; passes through value/error
```

Common bug: forgetting `return` inside `.then`, which breaks sequencing and swallows errors from the inner promise.

### Q8.3 \[I+\] Promise combinators

| Combinator | Fulfils when | Rejects when | Use for |
| --- | --- | --- | --- |
| `Promise.all` | All fulfil (array in input order) | **First** rejection (others keep running!) | Independent requests that all must succeed |
| `Promise.allSettled` | All settle (`{status, value/reason}`) | Never | Batch jobs; report partial failures |
| `Promise.race` | First to **settle** fulfils | First to settle rejects | Timeouts |
| `Promise.any` | First to **fulfil** | All reject (`AggregateError`) | Redundant mirrors / fastest replica |

```js
const withTimeout = (p, ms) => {
  let id;
  const timeout = new Promise((_, rej) => { id = setTimeout(() => rej(new Error('Timeout')), ms); });
  return Promise.race([p, timeout]).finally(() => clearTimeout(id));
};
```

Note: `race` doesn't cancel the loser. Real cancellation needs an `AbortController` (`fetch(url, { signal: AbortSignal.timeout(5000) })`).

### Q8.4 \[I+\] Implement `Promise.all` and `Promise.allSettled`

```js
function promiseAll(iterable) {
  return new Promise((resolve, reject) => {
    const items = [...iterable];
    const results = new Array(items.length);
    let remaining = items.length;
    if (remaining === 0) return resolve(results);
    items.forEach((item, i) => {
      Promise.resolve(item).then((v) => {
        results[i] = v;                 // keep input order
        if (--remaining === 0) resolve(results);
      }, reject);
    });
  });
}

const allSettled = (ps) => Promise.all([...ps].map((p) =>
  Promise.resolve(p).then((value) => ({ status: 'fulfilled', value }),
                          (reason) => ({ status: 'rejected', reason }))));
```

### Q8.5 \[I\] async/await — sequential vs parallel

```js
// Sequential: ~2s total
const a = await getA(); // 1s
const b = await getB(); // 1s

// Parallel: ~1s total
const [a2, b2] = await Promise.all([getA(), getB()]);

// Trap: await inside forEach does NOT wait
items.forEach(async (it) => { await save(it); }); // fire-and-forget, errors unhandled
for (const it of items) await save(it);            // sequential
await Promise.all(items.map(save));                // parallel (unbounded!)
```

### Q8.6 \[I+\] Error handling with async code

- `try/catch` around `await` catches rejections; it does **not** catch errors thrown inside a non-awaited callback (`setTimeout(() => { throw … })`).
- An `async` function never throws synchronously — it returns a rejected promise.
- **Unhandled rejections:** browsers fire `unhandledrejection`; Node ≥15 crashes the process by default. Always handle or `return`/`await` the promise.
- `return await p` inside `try` is necessary if you want that `try` to catch `p`'s rejection; outside a `try`, `return p` is fine.
- Preserve causes: `throw new Error('Load failed', { cause: err })`.

```js
// Go-style tuple helper — popular, but don't hide errors you can't handle
const to = (p) => p.then((d) => [null, d], (e) => [e, null]);
const [err, user] = await to(getUser());
```

### Q8.7 \[S\] Implement a concurrency limiter (promise pool)

Unbounded `Promise.all(urls.map(fetch))` with 10,000 URLs opens too many sockets, hits rate limits and spikes memory.

```js
async function mapLimit(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;
  async function run() {
    while (next < items.length) {
      const i = next++;                  // safe: single-threaded, no await between read and increment
      results[i] = await worker(items[i], i);
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, run));
  return results;
}
// await mapLimit(urls, 5, (u) => fetch(u).then((r) => r.json()));
```

**Follow-ups:** fail fast vs collect errors (wrap the worker in try/catch, use allSettled semantics); add retry with exponential backoff + jitter; support `AbortSignal` to stop launching new work.

### Q8.8 \[S\] Retry with exponential backoff

```js
async function retry(fn, { retries = 3, base = 200, max = 5000, signal } = {}) {
  for (let attempt = 0; ; attempt++) {
    try { return await fn(attempt); }
    catch (err) {
      if (attempt >= retries || signal?.aborted || !isRetryable(err)) throw err;
      const delay = Math.min(max, base * 2 ** attempt) * (0.5 + Math.random() / 2); // jitter
      await new Promise((r) => setTimeout(r, delay));
    }
  }
}
const isRetryable = (e) => e.name === 'TypeError' || [429, 502, 503, 504].includes(e.status);
```

Only retry **idempotent** operations (or use idempotency keys); jitter prevents a thundering herd.

### Q8.9 \[S\] Race conditions in UI code — stale responses

Typing "ab" fires requests for "a" and "ab"; if "a" returns last, the UI shows wrong results. Fixes: abort the previous request with `AbortController`, or ignore responses whose request id isn't the latest.

```js
let controller;
async function search(q) {
  controller?.abort();
  controller = new AbortController();
  try {
    const res = await fetch(`/api?q=${encodeURIComponent(q)}`, { signal: controller.signal });
    render(await res.json());
  } catch (e) { if (e.name !== 'AbortError') throw e; }
}
```

### Q8.10 \[I+\] `Promise.withResolvers` and deferreds

`const { promise, resolve, reject } = Promise.withResolvers();` (ES2024) replaces the old pattern of capturing `resolve` from the executor — useful for bridging event-based APIs, queues, and test helpers.

**Follow-ups:** What happens if the executor throws? (The promise rejects.) Is `fetch` rejected on HTTP 404/500? (No — only on network failure/abort; check `res.ok`.) What's the difference between `.then(f, g)` and `.then(f).catch(g)`? (The latter also catches errors thrown by `f`.)

## §9 Iterators, generators, symbols, Map/Set/WeakMap/WeakSet

### Q9.1 \[I+\] What are the iterable and iterator protocols?

An **iterable** has a `[Symbol.iterator]()` method returning an **iterator** — an object with `next()` that returns `{ value, done }`. Anything iterable works with `for…of`, spread, destructuring, `Array.from`, `Promise.all`, `new Map(iterable)`, `yield*`. Plain objects are **not** iterable.

```js
class Range {
  constructor(from, to) { this.from = from; this.to = to; }
  [Symbol.iterator]() {
    let cur = this.from; const end = this.to;
    return {
      next: () => (cur <= end ? { value: cur++, done: false } : { value: undefined, done: true }),
      return: () => { /* cleanup on early break */ return { done: true }; },
    };
  }
}
[...new Range(1, 4)]; // [1, 2, 3, 4]
```

The optional `return()` method is called when a consumer exits early (`break`, `throw`, destructuring fewer items) — use it to release resources.

### Q9.2 \[I+\] Generators — how do they work and when are they useful?

A `function*` returns a generator object (both iterator and iterable). Each `yield` pauses execution, preserving local state; `next(v)` resumes and makes the paused `yield` expression evaluate to `v`.

```js
function* idGen() { let id = 1; while (true) { const reset = yield id++; if (reset) id = 1; } }
const g = idGen();
g.next().value;      // 1
g.next().value;      // 2
g.next(true).value;  // 1 (reset)

function* take(iter, n) { for (const x of iter) { if (n-- <= 0) return; yield x; } }
[...take(idGen(), 3)]; // [1, 2, 3] — lazy evaluation over an infinite sequence
```

**Uses:** lazy/infinite sequences, custom iterables with little code, streaming pipelines, cooperative state machines, tree traversal (`yield*`), and historically async control flow (co/redux-saga — the precursor to async/await). `g.return(v)` and `g.throw(err)` let the caller end or inject errors.

### Q9.3 \[S\] Async iterators and `for await…of`

```js
async function* paginate(url) {
  while (url) {
    const res = await fetch(url);
    const { items, next } = await res.json();
    yield* items;
    url = next;
  }
}
for await (const item of paginate('/api/items')) {
  if (done(item)) break; // stops fetching further pages — backpressure for free
}
```

Node streams and `ReadableStream` (in modern runtimes) are async iterable. ES2025 **iterator helpers** add lazy `.map/.filter/.take/.drop/.flatMap/.reduce/.toArray` directly on iterators: `idGen().filter(isEven).take(5).toArray()`.

### Q9.4 \[I\] Symbols — what and why?

A `Symbol()` is a unique, immutable primitive used as a property key that won't collide with any other key. Symbol-keyed properties are skipped by `for…in`, `Object.keys` and `JSON.stringify` (still visible via `Object.getOwnPropertySymbols`, so not truly private). `Symbol.for('k')` uses a global registry (same symbol across realms).

**Well-known symbols** customise language behaviour: `Symbol.iterator`, `Symbol.asyncIterator`, `Symbol.toPrimitive`, `Symbol.toStringTag`, `Symbol.hasInstance`, `Symbol.species`, and (newer) `Symbol.dispose`/`Symbol.asyncDispose` for explicit resource management (`using` declarations, shipping in modern engines).

### Q9.5 \[I\] Map vs Object, Set vs Array

|  | `Object` | `Map` |
| --- | --- | --- |
| Key types | Strings and symbols (numbers coerced) | Any value (objects, functions, NaN) |
| Order | Integer keys first, then insertion | Pure insertion order |
| Size | `Object.keys(o).length` (O(n)) | `map.size` (O(1)) |
| Prototype keys | Inherited (`toString`, `__proto__` pitfalls) | None |
| Frequent add/delete | Slower (shape changes) | Optimised for it |
| JSON | Native | Needs conversion (`Object.fromEntries`) |

Use `Object` for fixed-shape records and JSON; use `Map` for dictionaries with dynamic keys, non-string keys, or heavy churn. Use `Set` for uniqueness and O(1) membership (`[...new Set(arr)]` dedupes); ES2025 adds `union`, `intersection`, `difference`, `symmetricDifference`, `isSubsetOf`.

### Q9.6 \[I+\] WeakMap, WeakSet, WeakRef, FinalizationRegistry

`WeakMap`/`WeakSet` hold keys **weakly**: if nothing else references the key object, it can be garbage-collected and its entry disappears. Keys must be objects (or non-registered symbols); they are **not iterable** and have no `size` (contents depend on GC timing).

```js
const meta = new WeakMap();
function track(el) { meta.set(el, { clicks: 0 }); }
// when el is removed from the DOM and dropped, its metadata is collectible too

const visited = new WeakSet(); // cycle detection in deep clone / traversal
```

**Uses:** private data per instance, caches keyed by objects, DOM-node metadata, memoizing on object arguments, cycle tracking. `WeakRef` + `FinalizationRegistry` allow caches of large objects and cleanup hooks — but GC timing is non-deterministic, so never rely on them for program correctness.

### Q9.7 \[S\] Proxy and Reflect

A `Proxy` intercepts fundamental operations (`get`, `set`, `has`, `deleteProperty`, `apply`, `construct`…). `Reflect` provides the default behaviour for each trap, so traps can forward correctly (including the `receiver`).

```js
function reactive(target, onChange) {
  return new Proxy(target, {
    set(obj, key, value, receiver) {
      const ok = Reflect.set(obj, key, value, receiver);
      if (ok) onChange(key, value);
      return ok; // returning false throws TypeError in strict mode
    },
  });
}
const state = reactive({ count: 0 }, (k, v) => console.log(k, v));
state.count++; // logs: count 1
```

Used by Vue 3 reactivity, MobX, Immer, validation layers, API clients. Costs: slower property access and harder debugging; identity differs (`proxy !== target`), and private `#fields` don't work through a proxy.

**Follow-ups:** Why can't you iterate a WeakMap? Why is `Symbol()` not constructible with `new`? How would you make an object iterable with a generator (`*[Symbol.iterator]() { yield* Object.entries(this); }`)?

## §10 Modules: ES Modules, CommonJS, module systems

### Q10.1 \[I\] ESM vs CommonJS — key differences

| Aspect | ES Modules (`import`/`export`) | CommonJS (`require`/`module.exports`) |
| --- | --- | --- |
| Loading | Static structure, parsed before execution; async-capable | Dynamic, synchronous, runs at `require` time |
| Bindings | **Live, read-only bindings** to the exporter's variables | A **copy** of `module.exports` value at require time (objects shared by reference) |
| Tree-shaking | Yes (static analysis) | Hard / limited |
| Top-level `await` | Yes | No |
| `this` at top level | `undefined` | `module.exports` |
| Strict mode | Always | Opt-in |
| `__dirname`, `require` | No (use `import.meta.url`, `import.meta.dirname` in Node ≥20.11) | Yes |
| Conditional import | `await import('./x.js')` | `if (x) require('./x')` |
| Browser support | Native (`<script type="module">`) | Needs a bundler |

### Q10.2 \[I+\] What are live bindings? Show the difference.

```js
// counter.mjs
export let count = 0;
export function inc() { count++; }
// main.mjs
import { count, inc } from './counter.mjs';
inc();
console.log(count); // 1 — live binding
count = 5;          // TypeError: Assignment to constant variable (imports are read-only)

// counter.cjs
let count = 0;
module.exports = { count, inc() { count++; } };
// main.cjs
const c = require('./counter.cjs');
c.inc();
console.log(c.count); // 0 — the value was copied into the exports object
```

### Q10.3 \[I+\] How are ES modules loaded? (Three phases)

1. **Construction** — fetch and parse every module in the graph, building module records (no code runs; `import` specifiers must be static strings).
2. **Instantiation (linking)** — allocate memory for exports and wire imports to them (live bindings). Hoisted function declarations are available.
3. **Evaluation** — run each module's top-level code once, depth-first post-order (dependencies first). Modules are **singletons** per URL — evaluated once and cached.

### Q10.4 \[S\] Circular dependencies — what happens?

In ESM, a cycle works if no module *uses* an imported binding during its own evaluation before the other module has initialised it; otherwise you get a TDZ `ReferenceError` (for `let`/`const`/`class`) — function declarations are fine because they're hoisted at linking. In CommonJS, the second module receives a **partially populated** `module.exports` (often `{}`), producing `undefined` bugs.

Fixes: extract shared code into a third module, defer access into functions (not top level), dependency inversion, or lazy `import()`. Tools like `madge` or ESLint `import/no-cycle` detect cycles.

### Q10.5 \[I+\] Default vs named exports — which do you prefer?

Named exports give consistent names across the codebase, better auto-import/refactoring, and clearer tree-shaking. Defaults allow arbitrary renaming on import (inconsistency) and interop oddities with CommonJS (`require('x').default`). Many style guides prefer named exports except where a framework requires a default (e.g. route/page files).

### Q10.6 \[S\] Tree shaking — what makes it work or fail?

Bundlers (Rollup, webpack, esbuild, Vite) remove unused exports using ESM static structure. It fails with: CommonJS modules, side effects at module top level (polyfills, prototype patches, CSS imports) unless marked via `"sideEffects"` in `package.json`, barrel files that re-export everything from modules with side effects, dynamic property access on namespaces (`ns[key]`), and transpiling ESM to CJS too early (Babel `modules: 'commonjs'`). Use `/*#__PURE__*/` annotations for side-effect-free calls.

### Q10.7 \[S\] Dynamic import and code splitting

`import()` returns a promise of the module namespace and creates a split point. Use it for routes, heavy libraries (charts, editors, PDF), feature flags, and locale data.

```js
button.addEventListener('click', async () => {
  const { renderChart } = await import('./chart.js');
  renderChart(data);
});
```

Trade-off: smaller initial bundle, but a network round-trip at use time — mitigate with `<link rel="modulepreload">`, prefetch on hover/idle, or bundling commonly co-used chunks.

### Q10.8 \[S\] Dual packages and interop in Node

Node decides module type by extension (`.mjs` ESM, `.cjs` CJS) or `"type"` in `package.json`. ESM can `import` CJS (default import = `module.exports`, named imports via static analysis when possible). CJS historically could only load ESM via `import()`; Node 22+ supports `require()` of synchronous ESM graphs (no top-level await). Library authors publish with an `"exports"` map (`import`/`require` conditions) — beware the **dual package hazard**: two copies of the same package loaded (ESM + CJS) with separate state and failing `instanceof` checks.

**Follow-ups:** What does `import.meta` contain? What's an import map? (Browser-native mapping from bare specifiers like `'lodash'` to URLs.) What are import attributes? (`import data from './x.json' with { type: 'json' }`.)

## §11 DOM, browser APIs, events, delegation

### Q11.1 \[I\] Explain event propagation: capture, target, bubble

A DOM event travels in three phases:

1. **Capture** — from `window` down through ancestors to the target's parent (listeners registered with `{ capture: true }`).
2. **Target** — listeners on the target itself.
3. **Bubble** — back up from the target to `window` (default listeners). Some events don't bubble: `focus`, `blur`, `mouseenter`, `mouseleave`, `load` (use `focusin`/`focusout` for bubbling versions).

&#91;embedded content: event propagation · capture, target, bubble\]

`stopPropagation()` anywhere on the path cuts off every ancestor after it — which is why it silently breaks delegation.

- `event.target` = the element where the event originated (deepest); `event.currentTarget` = the element whose listener is running.
- `stopPropagation()` stops further propagation; `stopImmediatePropagation()` also skips remaining listeners on the same element.
- `preventDefault()` cancels the browser's default action (link navigation, form submit) — it does not stop propagation. It is ignored in `{ passive: true }` listeners.

### Q11.2 \[I\] What is event delegation? Implement it.

Attach **one** listener to a common ancestor and handle events from many (including future) children by inspecting `event.target`.

```js
document.querySelector('#todo-list').addEventListener('click', (e) => {
  const btn = e.target.closest('button[data-action]');
  if (!btn || !e.currentTarget.contains(btn)) return;
  const id = btn.closest('li').dataset.id;
  if (btn.dataset.action === 'delete') removeTodo(id);
  if (btn.dataset.action === 'toggle') toggleTodo(id);
});
```

**Benefits:** fewer listeners (memory), works for dynamically added items, no re-binding after re-render, simpler cleanup. **Limits:** needs a bubbling event; `closest` is required because `target` may be a nested `<span>`/`<svg>`; `stopPropagation` in a child breaks it.

### Q11.3 \[I+\] `addEventListener` options and cleanup

```js
const controller = new AbortController();
window.addEventListener('scroll', onScroll, { passive: true, signal: controller.signal });
el.addEventListener('click', onClick, { once: true });
// later: removes every listener registered with this signal
controller.abort();
```

`removeEventListener` requires the **same function reference** and same `capture` flag — inline arrow listeners can't be removed. `passive: true` tells the browser you won't call `preventDefault`, so scrolling isn't blocked (Chrome defaults touch/wheel listeners on `window`/`document`/`body` to passive).

### Q11.4 \[I+\] Reflow (layout) vs repaint, and layout thrashing

Changing geometry (width, position, font, adding nodes) forces **layout**; changing only visual style (colour, visibility) forces **paint**; `transform` and `opacity` can often be handled by the **compositor** alone (cheapest). Reading layout properties (`offsetHeight`, `getBoundingClientRect`, `scrollTop`, `getComputedStyle`) after a write forces a **synchronous layout**. Alternating reads and writes in a loop = *layout thrashing*.

```js
// Bad: read/write interleaved → N forced layouts
for (const el of items) el.style.width = el.parentNode.offsetWidth / 2 + 'px';

// Good: batch reads, then writes
const widths = items.map((el) => el.parentNode.offsetWidth);
requestAnimationFrame(() => items.forEach((el, i) => { el.style.width = widths[i] / 2 + 'px'; }));
```

Also: build off-DOM with `DocumentFragment` or a single `innerHTML`/`replaceChildren`, toggle classes instead of many inline styles, use CSS `contain` / `content-visibility: auto` for large lists.

### Q11.5 \[I+\] Observers — which one when?

| API | Watches | Typical use |
| --- | --- | --- |
| `IntersectionObserver` | Element visibility vs viewport/root | Lazy-load images, infinite scroll, impression tracking |
| `ResizeObserver` | Element size changes | Responsive components, charts |
| `MutationObserver` | DOM tree/attribute changes | Third-party widget integration, editors |
| `PerformanceObserver` | Performance entries | Long tasks, LCP/INP/CLS monitoring |

These replace scroll/resize polling, which forces layout on every event.

HTML → DOM, CSS → CSSOM, combined → render tree → layout → paint → composite. CSS is render-blocking; classic `<script>` is parser-blocking.

## §12 Memory management, garbage collection, memory leaks

### Q12.1 \[I\] Stack vs heap — where do values live?

Conceptually, the **stack** holds call frames (local slots, return addresses); the **heap** holds objects, closures' captured contexts, strings and arrays. Variables hold either small immediate values (V8 "Smis" — small integers) or **pointers** to heap objects. That's why assigning an object copies the reference, not the object.

```text
STACK (frame of main)          HEAP
┌──────────────┐
│ n   = 42     │  (Smi, inline)
│ obj = 0x1a ──┼──────►  { name: 'A', tags: 0x2b ─┐ }
│ ref = 0x1a ──┼──────►  (same object)            │
└──────────────┘                                  └──► ['x', 'y']
```

### Q12.2 \[I+\] How does garbage collection work?

Modern engines use **reachability** (tracing), not reference counting. Starting from **roots** — the global object, the current call stacks, active handles/timers, DOM nodes in the document — the collector marks everything reachable; the rest is freed. Unreachable cycles are collected (reference counting couldn't do that).

&#91;embedded content: reachability · kept vs swept objects\]

The GC frees what is unreachable, not what is unused — which is why every JavaScript leak is a forgotten reference from something still alive.

V8 is **generational** (the *generational hypothesis*: most objects die young):

- **Young generation** ("nursery"/semi-space, a few MB): collected often by a fast **Scavenger** that copies survivors; objects surviving two scavenges are promoted.
- **Old generation**: collected by **Mark-Sweep-Compact**, done mostly *incrementally* and *concurrently* (Orinoco) to keep main-thread pauses short.

You cannot force GC in production (`global.gc()` exists only with `--expose-gc`), and finalization timing is unspecified.

### Q12.3 \[I+\] What causes memory leaks in JavaScript?

A leak is memory that is still **reachable** but no longer **needed**.

| Leak source | Example | Fix |
| --- | --- | --- |
| Forgotten timers/intervals | `setInterval(() => update(bigData), 1000)` never cleared | `clearInterval` on teardown |
| Event listeners not removed | Component adds `window.addEventListener('resize', h)` each mount | Remove in cleanup, or `AbortController` signal |
| Detached DOM nodes | JS array/Map still references removed elements | Drop references; use `WeakMap`/`WeakRef` |
| Closures retaining large scope | Handler closes over a 50 MB buffer it doesn't need | Null out, narrow scope, extract function |
| Unbounded caches / module-level Maps | `const cache = new Map()` keyed by request id | LRU with max size, TTL, or `WeakMap` |
| Accidental globals | `function f() { leaked = [] }` in sloppy mode | Strict mode / ESM, lint |
| Pending promises / subscriptions | Observables, WebSockets, `EventEmitter` listeners never unsubscribed | Unsubscribe; Node warns at >10 listeners |
| Console logging of objects | DevTools keeps logged objects alive | Strip logs in production |

### Q12.4 \[S\] The shared closure context leak

```js
function attach() {
  const huge = new Array(1e6).fill('*');
  const unused = () => huge.length;        // references huge
  return () => console.log('tick');         // doesn't — but shares the same context!
}
const handlers = [];
setInterval(() => handlers.push(attach()), 100); // each closure retains its `huge`
```

In V8, all closures created in one scope share one context object; if any closure captures `huge`, every closure from that scope keeps it alive. Fix: don't create the unused closure in that scope, set `huge = null` when done, or move the large data into a separate function.

### Q12.5 \[S\] How do you find a memory leak? (Process interviewers want)

1. **Reproduce** with a repeatable action (open/close a modal 20×, navigate routes).
2. **Observe** the trend: Chrome DevTools Performance panel with *Memory* checked, or Node `process.memoryUsage()` / `--inspect`. A sawtooth returning to baseline is healthy; a rising floor is a leak.
3. **Heap snapshots**: take snapshot A (baseline) → do action N times → force GC (trash-can icon) → snapshot B → view *Comparison*, sort by *# Delta* / *Retained size*.
4. **Follow retainers**: the Retainers pane shows the path from a GC root to the leaked object (e.g. `Window → listeners → closure → context → detachedDiv`). Search the snapshot for "Detached" to find detached DOM trees.
5. **Allocation instrumentation on timeline** to see which allocations survive.
6. **Fix, then re-measure.** Add a regression check (e.g. Puppeteer + `performance.memory`, or `memlab` from Meta).

In Node, also check: `--max-old-space-size`, `heapdump`/`v8.writeHeapSnapshot()`, Clinic.js, and whether the "leak" is just a cache that hasn't hit its bound.

### Q12.6 \[I+\] Shallow vs retained size

**Shallow size** = memory held by the object itself. **Retained size** = memory that would be freed if the object were collected (it plus everything reachable *only* through it). Leaks are hunted by retained size.

### Q12.7 \[S\] When should you use WeakRef / FinalizationRegistry?

Rarely: caches of expensive-to-recreate but reconstructible objects, or releasing external resources as a backstop. Never for correctness (cleanup may never run), and prefer explicit `dispose()`/`using` for resources.

**Follow-ups:** Does setting a variable to `null` free memory? (It removes one reference; memory is freed later, only if nothing else reaches the object.) Do strings leak? (Sliced strings can retain their parent string in V8; rare but real in log processing.) What is a "memory bloat" vs "leak"? (Bloat = too much memory used by design; leak = grows without bound.)

## §13 Functional programming and immutability

### Q13.1 \[I\] Core FP ideas in JavaScript

- **Pure functions** and **referential transparency** (a call can be replaced by its result).
- **Immutability** — create new values instead of changing existing ones.
- **First-class / higher-order functions**, **composition**, **currying**.
- **Declarative** data transformation (`map`/`filter`/`reduce`) over imperative loops.
- Isolating **side effects** at the edges.

### Q13.2 \[I\] Why does immutability matter in UI frameworks?

React, Redux, Angular OnPush and memoised selectors detect change by **reference equality** (`prev !== next`). Mutating in place keeps the same reference, so the change goes unnoticed (no re-render) — or worse, memoised values become stale. Immutable updates make change detection O(1), enable undo/redo and time-travel debugging, and remove shared-state bugs.

```js
// Wrong — mutation, same reference
state.todos.push(newTodo); setState(state);

// Right — structural sharing: only the changed path is copied
setState((s) => ({ ...s, todos: [...s.todos, newTodo] }));

// Nested update
const next = {
  ...state,
  users: { ...state.users, [id]: { ...state.users[id], active: true } },
};
```

### Q13.3 \[I+\] `const` vs `Object.freeze` vs deep freeze

`const` prevents **rebinding** the variable, not mutating the object. `Object.freeze` makes the object's own properties non-writable and non-configurable — **shallow**. Frozen objects silently ignore writes in sloppy mode and throw in strict mode.

```js
function deepFreeze(obj, seen = new WeakSet()) {
  if (obj === null || typeof obj !== 'object' || seen.has(obj)) return obj;
  seen.add(obj);
  for (const key of Reflect.ownKeys(obj)) deepFreeze(obj[key], seen);
  return Object.freeze(obj);
}
```

Note: freezing doesn't protect `Map`/`Set` internals or `Date` (their methods still mutate internal slots).

### Q13.4 \[S\] Trade-offs of immutability at scale

| Approach | Pros | Cons |
| --- | --- | --- |
| Manual spread | No dependency, explicit | Verbose for deep updates; easy to miss a level |
| Immer (`produce`) | Write "mutating" code on a draft; structural sharing; auto-freeze in dev | Proxy overhead; magic for newcomers |
| Persistent data structures (Immutable.js) | O(log n) updates on huge collections | Separate API, conversion cost at boundaries (`toJS`) |
| `structuredClone` per update | Simple | Copies everything — O(n) per change, breaks reference equality for unchanged parts |

Copying is O(size of changed path) with structural sharing; for hot paths on large arrays (e.g. 100k rows updated per frame), controlled local mutation inside a function that returns a fresh top-level reference is an acceptable, pragmatic choice.

### Q13.5 \[I+\] Reduce-based patterns

```js
const orders = [{ cust: 'a', total: 10 }, { cust: 'b', total: 5 }, { cust: 'a', total: 7 }];

// group & sum
const byCustomer = orders.reduce((acc, o) => {
  acc[o.cust] = (acc[o.cust] ?? 0) + o.total;   // local mutation of the accumulator is fine
  return acc;
}, {});
// { a: 17, b: 5 }

// ES2024
Object.groupBy(orders, (o) => o.cust); // { a: [..], b: [..] }
```

Anti-pattern: `reduce((acc, x) => ({ ...acc, [x.id]: x }), {})` copies the accumulator on every step → **O(n²)**. Mutating the accumulator you created is safe because nobody else holds it.

### Q13.6 \[S\] Functors, monads and `Maybe` — do you need them?

Arrays and Promises already behave like functors (`map`) and monad-like containers (`flatMap`, `then` flattens). A `Maybe`/`Result` type makes absence/failure explicit in the type:

```js
const Ok = (value) => ({ ok: true, value });
const Err = (error) => ({ ok: false, error });
function parseJSON(s) { try { return Ok(JSON.parse(s)); } catch (e) { return Err(e); } }
```

In interviews, show you can apply the idea pragmatically (explicit error values at boundaries, `?.`/`??` for absence) without forcing category theory on a team.

**Follow-ups:** What is point-free style and when does it hurt readability? Why is `arr.sort()` dangerous in a reducer (it mutates)? What does `toSorted` fix?

## §14 Performance optimization and profiling

### Q14.1 \[I+\] How do you approach a "the page is slow" ticket?

1. **Define slow** with a metric and a user journey: load (LCP, TTFB), responsiveness (INP, long tasks), visual stability (CLS), memory, or a specific interaction.
2. **Measure in the field and in the lab:** RUM data (`web-vitals` library, CrUX) for what real users see; DevTools Performance/Lighthouse with CPU and network throttling to reproduce.
3. **Find the bottleneck:** network waterfall (blocking resources, bundle size, no caching), main-thread flame chart (long tasks, forced layouts, expensive renders), memory trend.
4. **Fix the biggest cost first**, re-measure, and add a **budget** to CI (bundle size, Lighthouse CI) so it doesn't regress.

**Core Web Vitals "good" thresholds (p75):** LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1.

### Q14.2 \[I+\] Load performance techniques

| Problem | Technique |
| --- | --- |
| Large JS bundle | Code splitting by route, dynamic `import()`, tree shaking, drop unused deps (bundle analyzer), modern-only builds |
| Render-blocking resources | `defer`/`type=module`, inline critical CSS, `preload` key fonts/hero image, `fetchpriority="high"` on LCP image |
| Slow server response | CDN, caching headers (`Cache-Control: immutable` + hashed filenames), SSR/SSG/streaming, edge |
| Images | Responsive `srcset`, AVIF/WebP, explicit width/height (CLS), `loading="lazy"` below the fold |
| Third-party scripts | Audit, load async/late, facades for embeds, Partytown/web workers |
| Hydration cost | Partial/progressive hydration, islands, server components |

### Q14.3 \[I+\] Runtime performance techniques

- **Pick the right data structure:** `Set.has` O(1) vs `Array.includes` O(n) inside a loop turns O(n²) into O(n).
- **Avoid layout thrashing** (§11), animate `transform`/`opacity`, use `will-change` sparingly.
- **Virtualise long lists** (render only visible rows: react-window, TanStack Virtual).
- **Debounce/throttle** high-frequency handlers; passive listeners.
- **Memoise** expensive pure computations and avoid unnecessary re-renders (`React.memo`, `useMemo`, stable references) — but measure first; memoisation itself costs memory and comparisons.
- **Move CPU work off the main thread** (Web Workers, WASM for heavy compute).
- **Batch DOM writes**, reuse nodes, prefer `textContent`.
- **Keep objects monomorphic** (§17): same property order, avoid `delete`, avoid mixing types in arrays.

### Q14.4 \[S\] Reading a flame chart

In DevTools Performance, the x-axis is time and the y-axis is the call stack (callers above callees). Wide bars = time spent. Look for: red-flagged **long tasks** (> 50 ms), purple **Recalculate Style / Layout** blocks right after JS (forced synchronous layout warning), repeated GC events (allocation churn), and the *Bottom-Up* tab to see which functions have the highest **self time**. In Node, use `--cpu-prof`, `clinic flame`, or `0x`.

### Q14.5 \[S\] Measure correctly — micro-benchmarks lie

```js
performance.mark('start');
doWork();
performance.mark('end');
performance.measure('doWork', 'start', 'end');
console.log(performance.getEntriesByName('doWork')[0].duration);
```

Pitfalls: JIT warm-up (first runs are interpreted), dead-code elimination (the result is unused so the work is optimised away), GC pauses, CPU frequency scaling, unrealistic inputs. Use tools like `mitata`/`tinybench`, run many iterations, compare distributions (p50/p95), and benchmark the real workload, not a toy. Use `Date.now()` only for coarse timing; `performance.now()` is monotonic and sub-millisecond.

### Q14.6 \[S\] Network-level optimisation from JavaScript

- Deduplicate in-flight requests (cache the promise); cache responses (SWR — stale-while-revalidate).
- Cancel obsolete requests with `AbortController`.
- Batch/coalesce (GraphQL batching, DataLoader pattern) to solve N+1.
- Prefetch likely next routes on hover/idle; `<link rel="preconnect">` for critical origins.
- Paginate or stream (`ReadableStream`, NDJSON) large payloads instead of one huge JSON parse (which blocks the main thread).
- Service worker caching strategies: cache-first for hashed assets, network-first for HTML/API.

### Q14.7 \[I+\] String and array performance traps

- Repeated `str += x` in hot loops is fine in modern engines (ropes), but building arrays and `join` is predictable.
- `arr.shift()` is O(n); use an index pointer or a deque for queues.
- Spreading huge arrays into function args (`Math.max(...bigArray)`) can throw *Maximum call stack size exceeded*; use a loop or `reduce`.
- `JSON.parse(JSON.stringify())` for cloning is slow and lossy — use `structuredClone` or avoid cloning.
- Creating functions/objects in tight loops increases GC pressure.

**Follow-ups:** What's the difference between TTFB, FCP, LCP? Why might adding `useMemo` everywhere make an app slower? How would you set and enforce a performance budget?

## §15 Security, vulnerabilities, safe coding

### Q15.1 \[I\] What is XSS and how do you prevent it?

**Cross-Site Scripting** = an attacker gets their script to run in your origin, where it can read the DOM, call your APIs as the user, steal non-HttpOnly tokens and keylog. Types: **stored** (saved in DB, shown to others), **reflected** (from the URL/request), **DOM-based** (client JS writes untrusted data into a dangerous sink).

```js
// Vulnerable sinks
el.innerHTML = userInput;
el.outerHTML = …; document.write(…); el.insertAdjacentHTML('beforeend', …);
link.href = userUrl;                 // 'javascript:alert(1)'
eval(userInput); new Function(userInput); setTimeout(userString);

// Safe alternatives
el.textContent = userInput;
const url = new URL(userUrl, location.origin);
if (['http:', 'https:'].includes(url.protocol)) link.href = url.href;
```

**Defence in depth:** framework auto-escaping (React/Vue/Angular — but beware `dangerouslySetInnerHTML`, `v-html`, `bypassSecurityTrust*`); sanitise required HTML with **DOMPurify**; **Content Security Policy** (`script-src 'self' 'nonce-…'; object-src 'none'; base-uri 'none'`, avoid `unsafe-inline`); **Trusted Types** to make dangerous sinks reject plain strings; `HttpOnly` cookies so scripts can't read session tokens.

### Q15.2 \[I+\] CSRF — what is it and how do you defend?

**Cross-Site Request Forgery** tricks a logged-in user's browser into sending a state-changing request to your site with their cookies attached. Defences: `SameSite=Lax` or `Strict` cookies (Lax is the browser default for cookies without the attribute in Chromium), anti-CSRF tokens (synchroniser or double-submit), checking `Origin`/`Sec-Fetch-Site` headers, never changing state on `GET`, and requiring re-authentication for sensitive actions. Token-in-header APIs (Authorization: Bearer) are not CSRF-prone but are exposed to XSS if the token lives in JS-readable storage.

### Q15.3 \[S\] Prototype pollution

Unsafe deep-merge/`set(path)` utilities let an attacker write to `Object.prototype` via keys like `__proto__`, `constructor.prototype`, affecting every object in the process — leading to logic bypasses (`if (user.isAdmin)`), DoS, or RCE through gadget chains in templates/child\_process options.

```js
function unsafeMerge(target, src) {
  for (const k in src) {
    if (typeof src[k] === 'object' && src[k] !== null) target[k] = unsafeMerge(target[k] ?? {}, src[k]);
    else target[k] = src[k];
  }
  return target;
}
unsafeMerge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
({}).isAdmin; // true — every object is now "admin"
```

**Fixes:** reject `__proto__`, `constructor`, `prototype` keys; iterate `Object.keys` (own keys) not `for…in`; use `Object.create(null)` or `Map` for dictionaries; validate input with a schema (zod, ajv); `Object.freeze(Object.prototype)` in hardened environments; Node `--disable-proto=delete`; keep libraries patched.

### Q15.4 \[I+\] Where should you store auth tokens in the browser?

| Option | XSS exposure | CSRF exposure | Notes |
| --- | --- | --- | --- |
| `localStorage` / `sessionStorage` | High — any script reads it | None | Simple but a single XSS exfiltrates long-lived tokens |
| JS memory only | Medium (can't persist, still callable by XSS) | None | Lost on reload; pair with refresh cookie |
| `HttpOnly; Secure; SameSite` cookie | Not readable by scripts (XSS can still *use* the session while the page is open) | Mitigated by SameSite + tokens | Generally recommended for web apps (BFF pattern) |

No storage defeats XSS completely — prevent XSS first; use short-lived access tokens and rotating refresh tokens.

### Q15.5 \[I+\] Other common vulnerabilities

- **ReDoS:** catastrophic backtracking regex like `/^(a+)+$/` on attacker input blocks the event loop. Avoid nested quantifiers, cap input length, use linear-time engines (RE2) server-side.
- **Injection in Node:** SQL/NoSQL injection (use parameterised queries; reject objects like `{ "$gt": "" }` where strings are expected), command injection (`exec` with user input → use `execFile` with an args array).
- **Path traversal:** `fs.readFile(path.join(root, userPath))` with `../../etc/passwd` → resolve and verify the result starts with `root`.
- **Open redirects** and **SSRF** (server fetching attacker-supplied URLs → allowlist hosts, block internal IPs).
- **Clickjacking:** `frame-ancestors 'none'` in CSP / `X-Frame-Options: DENY`.
- **postMessage:** always check `event.origin` and specify `targetOrigin` instead of `'*'`.
- **Insecure randomness:** `Math.random()` is not cryptographic — use `crypto.getRandomValues` / `crypto.randomUUID`.
- **Timing attacks:** compare secrets with `crypto.timingSafeEqual`.

### Q15.6 \[S\] Supply-chain security

npm dependencies run install scripts and ship code into your bundle. Controls: lockfiles committed and `npm ci` in CI; `npm audit`/Dependabot/Snyk/Socket; pin and review major upgrades; minimise dependencies; disable install scripts where possible (`--ignore-scripts`, pnpm's allowlist); provenance/signatures (`npm audit signatures`); **Subresource Integrity** (`integrity="sha384-…"`) for CDN scripts; private registry/proxy; watch for typosquatting and compromised maintainer accounts (event-stream, ua-parser-js, the 2025 npm worm incidents).

### Q15.7 \[I\] Secure headers checklist

`Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` (needed for `SharedArrayBuffer`), and correct CORS (never reflect arbitrary `Origin` with `Access-Control-Allow-Credentials: true`).

**Follow-ups:** Does CORS protect your server? (No — it's a browser read-permission mechanism; servers must still authenticate/authorise.) Why is `eval` dangerous beyond XSS? (Defeats CSP and optimisation.) What does `rel="noopener"` prevent? (Reverse tabnabbing via `window.opener`; now default for `target="_blank"` in modern browsers.)

## §16 Testing, debugging, maintainability, design patterns

### Q16.1 \[I\] Unit vs integration vs end-to-end tests

| Level | Scope | Speed | Tools | Catches |
| --- | --- | --- | --- | --- |
| Unit | One function/module, dependencies faked | ms | Vitest, Jest, `node:test` | Logic errors, edge cases |
| Integration | Several modules together, real-ish DB/API (or MSW) | 10–500 ms | Vitest/Jest + Testing Library, Supertest | Wiring, contracts, rendering |
| End-to-end | Whole app in a real browser | seconds | Playwright, Cypress | User flows, config, deployment |

The **testing trophy** (Kent C. Dodds) argues most value comes from integration tests; static analysis (TypeScript, ESLint) is the cheap base. Test **behaviour**, not implementation details — tests that break on every refactor are a cost.

### Q16.2 \[I+\] Testing async code, timers and network

```js
import { describe, it, expect, vi } from 'vitest';

it('debounces calls', () => {
  vi.useFakeTimers();
  const fn = vi.fn();
  const d = debounce(fn, 300);
  d(); d(); d();
  vi.advanceTimersByTime(299);
  expect(fn).not.toHaveBeenCalled();
  vi.advanceTimersByTime(1);
  expect(fn).toHaveBeenCalledTimes(1);
  vi.useRealTimers();
});

it('rejects on 500', async () => {
  server.use(http.get('/api/user', () => new HttpResponse(null, { status: 500 }))); // MSW
  await expect(getUser()).rejects.toThrow(/500/);   // await the assertion!
});
```

Common bugs: missing `await`/`return` on async assertions (test passes vacuously), shared mutable state between tests, real timers making tests slow and flaky, over-mocking so the test only verifies the mock.

### Q16.3 \[I+\] Mocks vs stubs vs spies vs fakes

- **Spy** — records calls on a real function (`vi.spyOn(obj, 'method')`).
- **Stub** — replaces a function with canned responses.
- **Mock** — a stub with expectations about how it's called.
- **Fake** — a working lightweight implementation (in-memory DB, MSW handlers).

Prefer fakes at boundaries (network, time, randomness, storage) and real code inside. **Dependency injection** makes this easy: pass `fetch`, `clock`, `logger` in instead of importing singletons.

### Q16.4 \[S\] How do you debug a production-only bug?

1. **Gather evidence:** error tracking (Sentry etc.) with **source maps** uploaded privately, breadcrumbs, user agent, release version, feature flags.
2. **Reproduce** with the production build locally (minification, env vars, CDN/caching, different data volumes, slower devices).
3. **Narrow it down:** `git bisect` across releases, toggle flags, compare environments.
4. **Inspect:** conditional breakpoints and logpoints in DevTools, "Pause on caught exceptions", `debugger` statements, Node `--inspect`, async stack traces.
5. **Fix with a regression test**, then add observability (structured logs, metrics) so the next one is faster.

Common culprits: race conditions only visible with real latency, timezone/locale differences (`new Date('2026-11-01')` is UTC, `new Date('2026-11-01T00:00')` is local), floating-point, cached stale assets after deploy, minifier renaming that breaks `fn.name`/`constructor.name` checks.

### Q16.5 \[I+\] Design patterns in JavaScript — which matter?

| Pattern | JS idiom | Example |
| --- | --- | --- |
| Module | ES modules / closures | Encapsulated service with private state |
| Singleton | A module's exported instance (modules are cached) | Config, logger — beware hidden global state in tests |
| Factory | Function returning objects | `createStore(reducer)` |
| Observer / Pub-Sub | `EventTarget`, `EventEmitter`, signals | DOM events, state subscriptions |
| Strategy | Map of functions | `const pricing = { gold: (p) => p * 0.8, … }` instead of switch |
| Decorator | Higher-order functions / TC39 decorators | `withRetry(fetchUser)`, logging wrapper |
| Proxy | `Proxy` object | Validation, reactivity, lazy loading |
| Adapter | Wrapper translating interfaces | Wrapping a third-party SDK behind your own API |
| Facade | Simplified API over subsystems | `api.users.get()` hiding fetch + auth + retries |
| Middleware / Chain of responsibility | `next()` pipelines | Express/Koa, Redux middleware |
| Command | Objects describing actions | Undo/redo, Redux actions |
| Dependency injection | Pass collaborators in | Testable services |

```js
// Minimal typed-ish event emitter (Observer)
class Emitter {
  #handlers = new Map();
  on(evt, fn) {
    (this.#handlers.get(evt) ?? this.#handlers.set(evt, new Set()).get(evt)).add(fn);
    return () => this.off(evt, fn);           // return unsubscribe — prevents leaks
  }
  off(evt, fn) { this.#handlers.get(evt)?.delete(fn); }
  emit(evt, ...args) { for (const fn of [...(this.#handlers.get(evt) ?? [])]) fn(...args); } // copy: safe if handlers unsubscribe during emit
  once(evt, fn) { const off = this.on(evt, (...a) => { off(); fn(...a); }); return off; }
}
```

### Q16.6 \[S\] Maintainability — what do you enforce on a team?

- **TypeScript** in strict mode at least at module boundaries; runtime validation (zod/valibot) for external data.
- ESLint + Prettier in CI and pre-commit; no warnings allowed to accumulate.
- Small modules with one reason to change; **dependency direction** rules (UI → domain → data, never reverse).
- Explicit error handling policy (which layer catches, logs, retries, shows the user).
- Code review checklist: tests, naming, edge cases, performance, security, observability.
- ADRs (architecture decision records) for significant choices; deprecation paths for APIs.
- Avoid premature abstraction ("rule of three"); prefer duplication over the wrong abstraction.

## §17 Runtime internals and engine behaviour

### Q17.1 \[S\] How does V8 execute JavaScript?

Source → **parser** (lazy: only pre-parses inner functions until they're called) → **AST** → **Ignition** bytecode interpreter (collects type feedback) → hot functions are compiled by **Sparkplug** (fast baseline compiler) → **Maglev** (mid-tier optimising compiler) → **TurboFan** (top-tier optimising compiler using speculative type assumptions). If an assumption breaks (e.g. a function that always saw numbers now gets a string), the optimised code **deoptimises** back to bytecode.

Practical consequence: code that keeps types and shapes stable runs dramatically faster than code that is polymorphic.

### Q17.2 \[S\] What are hidden classes (shapes/maps) and inline caches?

V8 gives each object a hidden class describing its property layout. Objects created with the **same properties in the same order** share a shape, so property access compiles to a fixed memory offset. **Inline caches** at each property-access site remember the shapes seen:

- **Monomorphic** (1 shape) — fastest.
- **Polymorphic** (2–4 shapes) — slower check chain.
- **Megamorphic** (> 4) — falls back to a generic lookup.

```js
// Same shape — good
function Point(x, y) { this.x = x; this.y = y; }

// Different shapes — bad for hot code
const a = { x: 1, y: 2 };
const b = { y: 2, x: 1 };      // different order → different shape
const c = { x: 1 }; c.y = 2;  // shape transition at runtime
delete a.x;                    // often drops the object to slow "dictionary mode"
```

Guidelines: initialise all fields in the constructor (class fields help), don't `delete` properties on hot objects (set to `undefined`/use a `Map`), keep arrays homogeneous.

### Q17.3 \[S\] Array element kinds

V8 tracks element kinds: `PACKED_SMI_ELEMENTS` → `PACKED_DOUBLE_ELEMENTS` → `PACKED_ELEMENTS`, plus `HOLEY_*` variants. Transitions go only one way (more general). Creating holes (`new Array(1000)` then filling sparsely, or `arr[9999] = 1`) or mixing types makes every operation on that array slower forever.

```js
const a = [1, 2, 3];   // PACKED_SMI
a.push(4.5);           // PACKED_DOUBLE
a.push('x');           // PACKED_ELEMENTS
const h = new Array(3); // HOLEY_SMI (even after filling)
const ok = Array.from({ length: 3 }, () => 0); // PACKED
```

### Q17.4 \[S\] Engine vs runtime vs host — what belongs where?

| Layer | Provides | Examples |
| --- | --- | --- |
| ECMAScript engine | Language: syntax, built-ins (`Array`, `Promise`, `JSON`), GC, JIT, microtask *job queue* hooks | V8, SpiderMonkey, JavaScriptCore |
| Host / runtime | Event loop, timers, I/O, networking, module loading, globals | Browsers (Web APIs: DOM, `fetch`, `setTimeout`), Node.js (libuv, `fs`), Deno, Bun |

`setTimeout`, `fetch`, `console` and the DOM are **not** part of the language specification — they're host APIs (`fetch` and timers are now also in Node/Deno/Bun via WinterTC-style standardisation).

### Q17.5 \[S\] Multithreading in JavaScript

Each agent (main thread, Worker) has its own heap and event loop — no shared objects by default, so no data races on regular objects.

- **Web Workers / `worker_threads`**: parallel CPU work; communicate via `postMessage` (structured clone, O(size)) or **transfer** ownership of `ArrayBuffer`s (O(1)).
- **`SharedArrayBuffer` + `Atomics`**: true shared memory (requires cross-origin isolation in browsers); use `Atomics.wait/notify` for synchronisation. Easy to get wrong — use for well-understood hot paths (WASM threads, ring buffers).
- **Service Workers**: network proxy/offline, not for CPU work.
- Node's libuv thread pool (default 4) handles fs, DNS lookup, crypto, zlib — CPU-heavy crypto can saturate it (`UV_THREADPOOL_SIZE`).

### Q17.6 \[S\] Tail calls, recursion depth and stack size

ES2015 specified proper tail calls, but only JavaScriptCore (Safari) implements them. In V8 deep recursion throws `RangeError: Maximum call stack size exceeded` at roughly 10k frames (depends on frame size). Convert deep recursion to iteration with an explicit stack, or use trampolines.

```js
const trampoline = (f) => (...args) => { let r = f(...args); while (typeof r === 'function') r = r(); return r; };
const sumTo = trampoline(function go(n, acc = 0) { return n === 0 ? acc : () => go(n - 1, acc + n); });
sumTo(1e6); // 500000500000, no stack overflow
```

### Q17.7 \[S\] Strings, numbers and other internals worth mentioning

- Strings are UTF-16: `'😀'.length === 2`; use `[...str]` or `Intl.Segmenter` for user-perceived characters.
- Small integers (Smis, 31/32-bit) are stored inline; other numbers are boxed `HeapNumber`s unless the optimiser unboxes them.
- `JSON.parse` of a large object literal string can be faster than the equivalent JS literal (simpler grammar) — V8 recommends it for big static configs (> 10 KB).
- The engine may cache compiled code (code caching), so repeat visits parse faster; huge bundles still cost parse/compile time on low-end phones.

**Follow-ups:** What triggers deoptimisation? (Type changes, shape changes, `arguments` misuse, try/catch was once a blocker but no longer is.) How would you check if a function is optimised? (`node --allow-natives-syntax` with `%GetOptimizationStatus`, or `--trace-opt --trace-deopt` — never in production.)

## §18 Strings, regex, dates, Intl, errors and binary data

### Q18.1 \[I+\] Why is `'😀'.length` 2? How do you count characters?

Strings are sequences of UTF-16 code units. Characters outside the Basic Multilingual Plane (emoji, many CJK extensions) take two units (a *surrogate pair*), and a user-perceived character can be several code points (`'👍🏽'` = thumbs-up + skin-tone modifier; `'é'` can be one or two code points).

```js
'😀'.length;                              // 2 (code units)
[...'😀'].length;                         // 1 (code points — spread iterates by code point)
[...new Intl.Segmenter('en', { granularity: 'grapheme' }).segment('👍🏽é')].length; // 2 graphemes
'é' === 'é';                        // false (composed vs e + combining accent)
'é'.normalize() === 'é'.normalize(); // true (NFC)
```

Truncating with `slice(0, n)` can cut a surrogate pair in half — use `Intl.Segmenter` for user-visible truncation, and `normalize()` before comparing or hashing user input.

### Q18.2 \[I+\] Regex essentials interviewers test

| Feature | Example | Note |
| --- | --- | --- |
| Flags | `/x/gimsuyd` and `v` | `g` global, `i` ignore case, `m` multiline anchors, `s` dot matches newline, `u` Unicode, `y` sticky, `d` match indices, `v` Unicode sets (ES2024) |
| Named groups | `/(?<year>\d{4})-(?<mm>\d{2})/` | `match.groups.year` |
| Lookarounds | `(?=…)`, `(?!…)`, `(?<=…)`, `(?<!…)` | Assert without consuming |
| Lazy quantifier | `.*?` | Shortest match |
| Unicode classes | `/\p{L}+/u` | Letters in any script |
| `matchAll` | `[...s.matchAll(/\d+/g)]` | Requires `g`; gives every match with groups |
| `RegExp.escape` | `RegExp.escape(userText)` | ES2025: safely build regex from input |

**The `g` + `lastIndex` trap:** a global or sticky regex is *stateful*.

```js
const re = /a/g;
re.test('a'); // true  (lastIndex → 1)
re.test('a'); // false (search starts at 1, fails, lastIndex → 0)
re.test('a'); // true
```

Don't reuse a `g` regex with `test` across inputs; create it per call or drop `g`.

**ReDoS:** nested quantifiers like `/^(a+)+$/` backtrack exponentially on inputs such as `'aaaaaaaaaaaaaaaaaaaaaaaa!'`, freezing the event loop. Avoid nested/overlapping quantifiers, cap input length, and use a linear-time engine (RE2) for untrusted patterns on servers.

### Q18.3 \[I+\] Dates and timezones — what goes wrong?

- `Date` is a UTC millisecond timestamp; *display* uses the runtime's local zone.
- `new Date('2026-11-01')` (date-only ISO) parses as **UTC**; `new Date('2026-11-01T00:00')` parses as **local**. Non-ISO strings are implementation-defined.
- Months are 0-based in the constructor: `new Date(2026, 10, 1)` is 1 November.
- `Date` is mutable — `d.setDate(d.getDate() + 1)` changes `d` for everyone holding it.
- Adding 24 h is not "tomorrow" across a daylight-saving change.

```js
new Intl.DateTimeFormat('en-GB', { dateStyle: 'medium', timeStyle: 'short', timeZone: 'Asia/Dhaka' })
  .format(new Date('2026-11-01T06:30:00Z')); // '1 Nov 2026, 12:30'
```

**Production rules:** store and transmit instants as ISO 8601 with `Z` (or epoch ms); keep the user's IANA zone separately; format only at the edge with `Intl`. **Temporal** (`Temporal.Instant`, `ZonedDateTime`, `PlainDate`) fixes most of these issues with immutable, zone-aware types — it has started shipping in browsers but isn't universal yet, so check support or use the polyfill; date-fns / Luxon / Day.js remain common.

### Q18.4 \[I\] What does `Intl` give you?

```js
new Intl.NumberFormat('en-IN', { style: 'currency', currency: 'BDT' }).format(1234567.5); // 'BDT 12,34,567.50'
new Intl.NumberFormat('en', { notation: 'compact' }).format(1_250_000);                   // '1.3M'
new Intl.RelativeTimeFormat('en', { numeric: 'auto' }).format(-1, 'day');                 // 'yesterday'
new Intl.PluralRules('en').select(1);                                                      // 'one'
new Intl.ListFormat('en', { type: 'conjunction' }).format(['a', 'b', 'c']);               // 'a, b, and c'
['ä', 'a', 'z'].sort(new Intl.Collator('de').compare);                                    // locale-aware sort
```

Locale-correct formatting without libraries; reuse formatter instances in hot paths (constructing them is relatively costly). Exact output can vary slightly by runtime and ICU version, so don't hard-code it in tests.

### Q18.5 \[I+\] Error types, custom errors and `cause`

Built-ins: `Error`, `TypeError` (wrong type / calling a non-function), `ReferenceError` (unknown or TDZ binding), `RangeError` (invalid length, stack overflow), `SyntaxError` (bad `JSON.parse` input, `eval`), `URIError`, `EvalError`, `AggregateError` (`Promise.any`).

```js
class HttpError extends Error {
  constructor(status, message, options) {
    super(message, options);         // options.cause preserved (ES2022)
    this.name = 'HttpError';
    this.status = status;
  }
}

try { await loadUser(); }
catch (err) { throw new HttpError(502, 'Profile service failed', { cause: err }); }
```

Always throw `Error` instances (not strings) so you get stacks; set `name`; wrap low-level errors with `cause` instead of losing them; branch on `instanceof` or a stable `code`, never on `message` text. `Error.captureStackTrace` (V8) can hide helper frames; async stack traces in DevTools span `await` boundaries.

### Q18.6 \[S\] `ArrayBuffer`, typed arrays and `DataView`

- `ArrayBuffer` = a fixed (or, since ES2024, resizable) block of raw bytes; no direct access.
- Typed arrays (`Uint8Array`, `Float32Array`, …) = typed views over a buffer; fast, fixed element type, used by WebGL, Web Audio, `crypto.getRandomValues`, file and network bytes.
- `DataView` = mixed types and explicit endianness (`getUint32(offset, littleEndian)`) for binary protocols.
- `TextEncoder`/`TextDecoder` convert between strings and UTF-8 bytes.
- **Transferable:** `postMessage(buf, [buf])` moves ownership to a worker in O(1) — the sender's buffer becomes detached (length 0).
- `SharedArrayBuffer` + `Atomics` give shared memory between threads (requires cross-origin isolation in browsers).

```js
const bytes = new TextEncoder().encode('hi😀');   // Uint8Array(6)
const view = new DataView(bytes.buffer);
view.getUint8(0);                                  // 104 ('h')
```

**Follow-ups:** Why is `JSON.stringify` of a typed array an object of indices? How would you parse a binary file header in the browser? (`await file.arrayBuffer()` + `DataView`.)

## §19 Node.js essentials

### Q19.1 \[I+\] Streams and backpressure

Streams process data in chunks instead of loading it all into memory. Types: **Readable**, **Writable**, **Duplex**, **Transform**. **Backpressure:** when the consumer is slower than the producer, `writable.write()` returns `false` once its buffer passes `highWaterMark`; a correct producer pauses until `'drain'`. Ignoring it buffers everything in memory.

```js
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';

// Handles backpressure, errors and cleanup of every stream in the chain
await pipeline(createReadStream('big.log'), createGzip(), createWriteStream('big.log.gz'));

// Async iteration is also backpressure-aware
for await (const chunk of createReadStream('big.log')) processChunk(chunk);
```

Prefer `stream/promises` `pipeline` over chained `.pipe()`, which doesn't forward errors or destroy the other streams on failure.

### Q19.2 \[S\] worker\_threads vs cluster vs child\_process

| Option | What it is | Shares memory? | Use for |
| --- | --- | --- | --- |
| `worker_threads` | Threads in one process, each with its own V8 isolate and event loop | Only via `SharedArrayBuffer`; transferables for zero-copy | CPU-heavy work (parsing, image processing, hashing) |
| `cluster` | Multiple processes sharing a server port | No | Use every CPU core for an HTTP server (often replaced by a process manager or containers) |
| `child_process` (`spawn`, `execFile`, `fork`) | Separate OS processes | No | Running other programs, isolation, crash containment |

The event loop handles I/O concurrency well on one thread; workers are for **CPU**, not for I/O. Avoid `exec` with interpolated user input (command injection) — use `execFile`/`spawn` with an argument array.

### Q19.3 \[S\] Graceful shutdown

```js
const server = app.listen(3000);
let shuttingDown = false;

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(`${signal} received, draining`);
  server.close();                                     // stop accepting new connections
  const timer = setTimeout(() => process.exit(1), 10_000).unref(); // hard deadline
  await Promise.allSettled([db.end(), queue.close()]); // finish in-flight work, close pools
  clearTimeout(timer);
  process.exit(0);
}
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));
```

Also: fail readiness checks first so the load balancer stops routing; close idle keep-alive sockets (`server.closeIdleConnections()`); on `uncaughtException`, log and exit — the process state can't be trusted.

### Q19.4 \[S\] Request-scoped context with `AsyncLocalStorage`

```js
import { AsyncLocalStorage } from 'node:async_hooks';
const requestContext = new AsyncLocalStorage();

app.use((req, res, next) => {
  requestContext.run({ requestId: crypto.randomUUID(), userId: req.user?.id }, next);
});

function log(msg) {
  const ctx = requestContext.getStore();             // survives across await boundaries
  console.log(JSON.stringify({ msg, ...ctx }));
}
```

Fixes the "module-level current user" bug (Senior scenario S2) and powers tracing and structured logging without threading a `ctx` argument everywhere.

### Q19.5 \[I+\] EventEmitter pitfalls

- An `'error'` event with **no listener throws** and crashes the process — always handle `'error'` on streams, sockets and emitters.
- Listeners run **synchronously** in registration order; a slow listener blocks `emit`.
- `MaxListenersExceededWarning` (default 10) usually signals a leak (listeners added per request and never removed).
- `events.once(emitter, 'ready')` returns a promise; `events.on(emitter, 'data')` gives an async iterator.

### Q19.6 \[I\] Built-ins worth naming in a modern Node interview

`node:test` (built-in test runner), `--watch`, `--env-file=.env`, native `fetch`/`WebSocket` client, `node:sqlite` (newer releases), the permission model (`--permission`), type stripping for TypeScript files in recent versions, and `require()` of synchronous ES modules. Check the exact version your team runs before relying on any of these.

**Follow-ups:** Why is `fs.readFileSync` fine in a CLI but harmful in a server? What does the libuv thread pool do, and when would you raise `UV_THREADPOOL_SIZE`? How do you find what's blocking the event loop? (`monitorEventLoopDelay`, `--cpu-prof`, Clinic.js.)

## §20 Networking and real-time in the browser

### Q20.1 \[I+\] `fetch` details people miss

- `fetch` rejects only on network failure or abort — **check `res.ok`** for HTTP errors.
- The body can be read **once** (`res.json()` twice throws); use `res.clone()` if two consumers need it.
- Cookies: `credentials: 'same-origin'` is the default; cross-origin cookies need `credentials: 'include'` *and* a server response with `Access-Control-Allow-Credentials: true` and a specific (non-`*`) origin.
- Cancellation and timeouts: `signal: AbortSignal.timeout(5000)`, or `AbortSignal.any([userSignal, timeoutSignal])`.
- Streaming responses: `res.body` is a `ReadableStream` you can read incrementally.

```js
const res = await fetch('/api/export', { signal: AbortSignal.timeout(30_000) });
if (!res.ok) throw new Error(`HTTP ${res.status}`);
const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  appendChunk(value);   // render progressively instead of waiting for the whole body
}
```

### Q20.2 \[I+\] What triggers a CORS preflight?

CORS is enforced by the **browser** to decide whether page JavaScript may *read* a cross-origin response; it doesn't protect the server. A **preflight** `OPTIONS` request is sent first unless the request is "simple": method `GET`, `HEAD` or `POST`, only safelisted headers, and `Content-Type` of `text/plain`, `multipart/form-data` or `application/x-www-form-urlencoded`. So a `POST` with `Content-Type: application/json` or an `Authorization` header is preflighted. Cache preflights with `Access-Control-Max-Age` to save a round-trip.

### Q20.3 \[I+\] Polling vs long polling vs SSE vs WebSocket

|  | Direction | Transport | Auto-reconnect | Binary | Typical use |
| --- | --- | --- | --- | --- | --- |
| Short polling | Client pulls | HTTP | n/a | Yes | Low-frequency status checks |
| Long polling | Server holds request | HTTP | Manual | Yes | Legacy fallback |
| SSE (`EventSource`) | Server → client | HTTP, text | **Built in**, resumes with `Last-Event-ID` | No (text) | Notifications, feeds, progress, LLM token streaming |
| WebSocket | Both ways | Upgraded TCP | Manual | Yes | Chat, multiplayer, collaborative editing |

```js
// WebSocket with exponential backoff + jitter and heartbeat
function connect(url, onMessage, attempt = 0) {
  const ws = new WebSocket(url);
  let heartbeat;
  ws.onopen = () => { attempt = 0; heartbeat = setInterval(() => ws.send('ping'), 25_000); };
  ws.onmessage = (e) => onMessage(JSON.parse(e.data));
  ws.onclose = () => {
    clearInterval(heartbeat);
    const delay = Math.min(30_000, 500 * 2 ** attempt) * (0.5 + Math.random() / 2);
    setTimeout(() => connect(url, onMessage, attempt + 1), delay);
  };
  return ws;
}
```

Senior extras: deduplicate messages after reconnect with ids, buffer outgoing messages while offline, share one connection across tabs, and watch `bufferedAmount` for send-side backpressure.

### Q20.4 \[S\] Service workers and caching strategies

A service worker is a background script that proxies the page's network requests (HTTPS only). It runs on its own thread, has no DOM access, and its lifecycle is **install → waiting → activate**: a new version waits until all tabs using the old one close unless you call `skipWaiting()` + `clients.claim()` (which can mix old pages with new assets — handle carefully).

| Strategy | How it works | Good for |
| --- | --- | --- |
| Cache first | Serve from cache, fall back to network | Hashed static assets, fonts |
| Network first | Try network, fall back to cache | HTML, API data that must be fresh |
| Stale-while-revalidate | Serve cache immediately, update cache in background | Avatars, non-critical API data |
| Network only / cache only | One source | Analytics / precached app shell |

Common bugs: caching the HTML forever (users stuck on an old build), forgetting to delete old caches in `activate`, and caching error or opaque responses. Workbox packages these patterns.

### Q20.5 \[I\] HTTP caching headers for JavaScript apps

- Hashed assets (`app.3f9c1.js`): `Cache-Control: public, max-age=31536000, immutable`.
- HTML: `Cache-Control: no-cache` (always revalidate) so new deployments are picked up.
- Personalised API responses: `Cache-Control: private` or `no-store`; add `Vary` for headers that change the response.
- `ETag` / `If-None-Match` give cheap 304 revalidation.

**Follow-ups:** Why might a WebSocket work locally and fail behind a corporate proxy? (Upgrade blocked — SSE or long polling fallbacks.) How do you stream an LLM response to the UI? (SSE or a streamed `fetch` body, rendering tokens as they arrive.)

## §21 TypeScript for JavaScript interviews

Most JavaScript roles now expect TypeScript. These are the questions that come up even in "JavaScript" interviews.

### Q21.1 \[I\] `any` vs `unknown` vs `never`

- `any` turns type checking **off** for that value — it spreads silently through everything it touches.
- `unknown` means "could be anything; prove it before use" — you must narrow it first. Use it for `JSON.parse` results, `catch` variables, and external input.
- `never` is the type with no values: functions that always throw, and impossible branches (exhaustiveness checks).

```ts
function parse(raw: string): unknown { return JSON.parse(raw); }
const data = parse(input);
// data.id;                                     // error: 'data' is of type 'unknown'
if (typeof data === 'object' && data !== null && 'id' in data) console.log(data.id);
```

### Q21.2 \[I+\] Narrowing and discriminated unions

```ts
type Result =
  | { status: 'ok'; data: User }
  | { status: 'error'; error: string }
  | { status: 'loading' };

function render(r: Result): string {
  switch (r.status) {
    case 'ok': return r.data.name;          // narrowed: data exists
    case 'error': return r.error;
    case 'loading': return 'Loading…';
    default: {
      const exhaustive: never = r;           // compile error if a new status is added
      return exhaustive;
    }
  }
}
```

Narrowing tools: `typeof`, `instanceof`, `in`, equality, truthiness, discriminant properties, and **user-defined type guards** (`function isUser(x: unknown): x is User`) or assertion functions (`asserts x is User`).

### Q21.3 \[I+\] Generics with constraints

```ts
function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}
const names = pluck([{ id: 1, name: 'Ana' }], 'name'); // string[]
// pluck([{ id: 1 }], 'email');                        // error: '"email"' is not assignable to '"id"'
```

Rule of thumb: a type parameter should appear at least twice (relating inputs to outputs); otherwise use a concrete type or `unknown`.

### Q21.4 \[I+\] Utility and mapped types

| Utility | Does |
| --- | --- |
| `Partial<T>` / `Required<T>` | All properties optional / required |
| `Readonly<T>` | All properties `readonly` (shallow, compile-time only) |
| `Pick<T, K>` / `Omit<T, K>` | Keep / drop keys |
| `Record<K, V>` | Object with keys `K` and values `V` |
| `ReturnType<F>` / `Parameters<F>` / `Awaited<P>` | Extract from function and promise types |
| `NonNullable<T>` / `Exclude<T, U>` / `Extract<T, U>` | Filter union members |

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };            // mapped type removing readonly
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] }; // key remapping
```

### Q21.5 \[I+\] Structural typing — why does this compile?

```ts
interface Point { x: number; y: number }
const p3 = { x: 1, y: 2, z: 3 };
const p: Point = p3;           // OK — extra properties are fine for a variable
// const q: Point = { x: 1, y: 2, z: 3 }; // error: excess property check on a fresh object literal
```

TypeScript compares **shapes**, not names. Excess-property checks apply only to fresh object literals. When you need nominal behaviour (e.g. `UserId` vs `OrderId`, both strings), use **branded types**: `type UserId = string & { readonly __brand: 'UserId' }`.

### Q21.6 \[I\] `type` vs `interface`, `enum` vs union, `satisfies`

- `interface` can be **merged** (declaration merging) and extended; `type` handles unions, intersections, mapped and conditional types. Pick one convention per codebase; both work for object shapes.
- Prefer **string-literal unions** (`'sm' | 'md' | 'lg'`) or `as const` objects over `enum`: no runtime code, no reverse-mapping surprises, and they work with type-only stripping.
- `satisfies` checks a value against a type **without widening** it:

```ts
const routes = { home: '/', user: '/users/:id' } satisfies Record<string, string>;
routes.user;   // OK — the known keys are kept
// routes.usr; // error: typo caught. With `const routes: Record<string, string> = …` this would compile.

const exact = { home: '/', user: '/users/:id' } as const satisfies Record<string, string>;
exact.user;    // type is the literal '/users/:id' — add `as const` when you also want literal types
```

### Q21.7 \[S\] Types vanish at runtime — what do you do at boundaries?

TypeScript checks code, not data. An API can still return `{ id: null }` while your type says `id: number`. Validate external data at runtime and derive the static type from the schema so the two can't drift:

```ts
import { z } from 'zod';
const User = z.object({ id: z.number(), email: z.string().email() });
type User = z.infer<typeof User>;
const user: User = User.parse(await res.json());  // throws with a precise error if the shape is wrong
```

**Follow-ups:** What's the difference between `T[]` and `readonly T[]`? Why is `as` dangerous? (It's an unchecked assertion — `as unknown as X` compiles anything.) What does `strict` enable? (`strictNullChecks`, `noImplicitAny`, `strictFunctionTypes` and more; turn it on for new code.)

# Traps & output questions

Two drills in one part: **trap questions** (the tempting answer, the correct one, and why the tempting one fails) and **output questions** (predict, then check the step-by-step). Cover each answer before reading it.

## Part 2 — Trick and trap questions

### T1 \[I\] `typeof null`

- Tempting: `'null'`. **Correct: `'object'`.**
- Why the tempting answer is wrong: the first engine tagged values with type bits and `null` (the null pointer) carried the object tag `000`. The spec kept it because fixing it would break the web. Check with `x === null`.

### T2 \[I\] `[] == ![]`

- Tempting: `false` ("an array can't equal its negation"). **Correct: `true`.**
- Why: `![]` runs first; `[]` is truthy, so it's `false`. Then `[] == false`: boolean → `0`; `[]` → `''` → `0`; `0 == 0`. The tempting answer assumes `==` compares truthiness — it compares coerced primitives.

### T3 \[I\] `0.1 + 0.2 === 0.3`

- Tempting: `true`. **Correct: `false`** (the sum is `0.30000000000000004`).
- Why: IEEE-754 doubles can't represent 0.1 or 0.2 exactly; the rounding errors don't cancel. `0.5 + 0.25 === 0.75` *is* `true` because those are exact binary fractions.

### T4 \[I+\] Does `const` make values immutable?

```js
const arr = [1, 2];
arr.push(3);   // works
arr = [];      // TypeError
```

- Tempting: "`const` arrays can't change". **Correct:** `const` blocks reassignment of the *binding*, not mutation of the *value* it points to.

### T5 \[I+\] Arrow function as an object method

```js
const obj = { n: 1, get: () => this.n };
obj.get();
```

- Tempting: `1`. **Correct: depends on the enclosing `this`, never `obj`.** Browser classic script → `window.n` → `undefined`; Node CommonJS → `module.exports.n` → `undefined`; ES module → `this` is `undefined`, so `this.n` throws `TypeError`.
- Why: arrows take `this` from the scope where the object literal is written; an object literal does not create a `this` scope. Use method shorthand: `get() { return this.n; }`.

### T6 \[I+\] `parseInt` with `map`

```js
['1', '7', '11'].map(parseInt);
```

- Tempting: `[1, 7, 11]`. **Correct: `[1, NaN, 3]`.**
- Why: `map` passes `(value, index, array)`, so the calls are `parseInt('1', 0)` (radix 0 = auto → 1), `parseInt('7', 1)` (radix 1 invalid → NaN), `parseInt('11', 2)` (binary → 3). Fix: `.map(Number)` or `.map((s) => parseInt(s, 10))`.

### T7 \[I+\] Does `Promise.all` cancel the others on failure?

- Tempting: "Yes, when one rejects the rest stop". **Correct: No.**
- Why: promises are results, not tasks — `Promise.all` just stops *waiting* and rejects early; the other operations keep running and their outcomes are ignored. To stop work, share an `AbortSignal` and abort it in the `catch`.

### T8 \[I+\] `try/catch` around `setTimeout`

```js
try { setTimeout(() => { throw new Error('boom'); }, 0); }
catch (e) { console.log('caught'); }
```

- Tempting: logs `caught`. **Correct:** an uncaught error.
- Why: the callback runs later on a fresh call stack, after the `try` block has already finished. Catch inside the callback, or use promises with `await`.

### T9 \[I+\] `async` function returning a value

```js
async function f() { return 1; }
console.log(f());
```

- Tempting: `1`. **Correct:** `Promise {<fulfilled>: 1}`.
- Why: an `async` function always returns a promise, even for a plain return value or a synchronous throw.

### T10 \[I+\] `forEach` with `async`/`await`

- Tempting: `items.forEach(async (i) => await save(i))` saves one by one and the caller waits. **Correct:** all saves start at once, the caller continues immediately, and rejections are unhandled.
- Why: `forEach` ignores its callback's return value, so the promises are dropped. Use `for…of` with `await` (sequential) or `await Promise.all(items.map(save))` (parallel).

### T11 \[I\] `Array(3)` vs `Array.of(3)` vs `[3]`

- Tempting: "`Array(3)` makes `[3]`, and `new Array(3).map((_, i) => i)` gives `[0, 1, 2]`". **Correct:** `Array(3)` → `[ <3 empty items> ]`; `Array.of(3)` → `[3]`; the `map` result is still `[ <3 empty items> ]`.
- Why the tempting answer is wrong: a single numeric argument to `Array` is a *length*, not an element, and holes are not `undefined` values — `map`, `forEach`, `filter` and `reduce` skip them (while `for…of`, spread and `Array.from` treat them as `undefined`).
- Fix: `Array.from({ length: 3 }, (_, i) => i)` or `[...Array(3).keys()]`.

### T12 \[I+\] `this` inside `setTimeout` in a method

```js
const counter = { count: 0, start() { setTimeout(function () { this.count++; }, 0); } };
```

- Tempting: increments `counter.count`. **Correct:** `this` is `window` in browsers or a `Timeout` object in Node — never `counter`.
- Why: the callback is a regular function called by the timer, not by `counter`, so implicit binding doesn't apply. Use an arrow function.

### T13 \[I+\] Object keys are always strings?

```js
const o = {}; const k1 = { a: 1 }; const k2 = { b: 2 };
o[k1] = 'first'; o[k2] = 'second';
o[k1];
```

- Tempting: `'first'`. **Correct: `'second'`.**
- Why: both object keys are converted to the same string `'[object Object]'`, so the second write overwrites the first. Use a `Map` for object keys.

### T14 \[I+\] `sort()` on numbers

- Tempting: `[1, 10, 2, 21].sort()` → `[1, 2, 10, 21]`. **Correct:** `[1, 10, 2, 21]`.
- Why the tempting answer is wrong: with no comparator, `sort` converts elements to strings and compares UTF-16 code units, so `'10' < '2'`.
- Second trap: `const sorted = arr.sort(...)` **mutates** `arr` and returns the same array. Use `arr.toSorted((a, b) => a - b)` or `[...arr].sort(...)`.

### T15 \[S\] `JSON.stringify` surprises

```js
JSON.stringify({ a: undefined, b: () => 1, c: Symbol(), d: NaN, e: new Date(0), f: [undefined] });
// '{"d":null,"e":"1970-01-01T00:00:00.000Z","f":[null]}'
JSON.stringify(10n); // TypeError: Do not know how to serialize a BigInt
```

- Tempting: "it round-trips any object". **Correct:** in objects `undefined`/functions/symbols are omitted; in arrays they become `null`; `NaN`/`Infinity` → `null`; Dates become strings via `toJSON()`; cycles and BigInt throw.

### T16 \[S\] `instanceof Array` is a reliable array check?

- Tempting: yes. **Correct:** no — it fails for arrays from another realm (iframe, `vm` context) because each realm has its own `Array.prototype`. `Array.isArray` checks the internal array marker and works across realms.

### T17 \[S\] Is JavaScript pass-by-reference?

- Tempting: "objects are passed by reference". **Correct:** always **pass-by-value**; for objects the value is a reference (*call by sharing*).
- Why it matters: reassigning the parameter doesn't affect the caller (it would under true pass-by-reference); mutating the object does.

```js
function f(o) { o.x = 1; o = { x: 2 }; }
const obj = {}; f(obj); obj.x; // 1
```

### T18 \[S\] Does `await` block the thread?

- Tempting: "yes, it waits". **Correct:** it suspends only the current async function and returns control to the event loop; other code keeps running. Only synchronous work (long loops, huge `JSON.parse`, sync I/O) blocks.

### T19 \[S\] Do `Object.freeze` and `const` make state deeply immutable?

- Tempting: "`const state = Object.freeze({ user: { name: 'A' } })` is fully immutable". **Correct:** both are shallow — `state.user.name = 'B'` still succeeds.
- Why the tempting answer is wrong: `const` only stops reassigning the variable; `Object.freeze` only locks the object's *own* top-level properties. Nested objects are separate objects, and `Map`/`Set`/`Date` keep their data in internal slots that freezing doesn't touch (`Object.freeze(new Map()).set('k', 1)` works).
- Fix: `deepFreeze` in development, immutable update patterns or Immer in production.

### T20 \[S\] "Closures cause memory leaks"

- Tempting: true. **Correct:** closures retain only what's reachable through them. They leak only when the closure itself lives longer than intended (listeners, timers, caches) or shares a context with a sibling closure that captured large data. Closures are not inherently leaky.

### T21 \[I+\] `new Date('2026-11-01')` vs `new Date('2026-11-01T00:00')`

- Tempting: "same moment". **Correct:** the date-only ISO form is parsed as **UTC**; the date-time form without an offset is parsed as **local time**. In Dhaka (UTC+6) they're 6 hours apart, and `getDate()` on the first can show the previous day west of Greenwich.
- Fix: always include an offset (`Z` or `+06:00`), or use `Temporal.PlainDate` where available.

### T22 \[I+\] `'b' + 'a' + +'a' + 'a'`

- Tempting: a syntax error or `'baaa'`. **Correct: `'baNaNa'`.**
- Why: `+'a'` is unary plus → `NaN`; the rest is string concatenation.

## Part 3 — Code output questions

Cover the answer, predict, then read the explanation. O1–O13 are core; O14–O23 cover classes, promise ticks, errors and collections.

### O1 \[I\] Hoisting mix

```js
var x = 1;
function f() {
  console.log(x);
  var x = 2;
  console.log(x);
}
f();
console.log(x);
```

**Output:** `undefined`, `2`, `1`

1. Inside `f`, `var x` is hoisted to the top of `f` and initialised to `undefined`, shadowing the global.
2. First log reads the local `x` → `undefined`.
3. Assignment sets local `x = 2` → logs `2`.
4. Global `x` was never touched → `1`.

### O2 \[I+\] Function vs variable hoisting priority

```js
console.log(typeof foo);
var foo = 'bar';
function foo() {}
console.log(typeof foo);
```

**Output:** `function`, `string`

During creation, the function declaration binds `foo`; `var foo` doesn't overwrite an existing binding. At execution, `foo = 'bar'` runs, so the second log sees a string.

### O3 \[I+\] Event loop ordering

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve()
  .then(() => { console.log('C'); setTimeout(() => console.log('D'), 0); })
  .then(() => console.log('E'));
queueMicrotask(() => console.log('F'));
console.log('G');
```

**Output:** `A G C F E B D`

| Step | Runs | Microtasks after | Tasks after |
| --- | --- | --- | --- |
| Sync | logs A, schedules B (task), C-handler (micro), F (micro), logs G | C, F | B |
| Micro 1 | C: logs C, schedules D; resolving it queues E | F, E | B, D |
| Micro 2 | F | E | B, D |
| Micro 3 | E | — | B, D |
| Task 1 | B | — | D |
| Task 2 | D | — | — |

Key insight: `E` is queued only when C's handler finishes, so it lands *behind* F.

### O4 \[I+\] async/await ordering

```js
async function a1() { console.log('a1 start'); await a2(); console.log('a1 end'); }
async function a2() { console.log('a2'); }
console.log('script start');
setTimeout(() => console.log('timeout'), 0);
a1();
new Promise((res) => { console.log('p1'); res(); }).then(() => console.log('p2'));
console.log('script end');
```

**Output:** `script start`, `a1 start`, `a2`, `p1`, `script end`, `a1 end`, `p2`, `timeout`

1. `a1()` runs synchronously until `await`; `a2()` also runs synchronously and logs `a2`.
2. `await` queues the continuation (`a1 end`) as a microtask.
3. The Promise executor runs synchronously → `p1`; `.then` queues `p2` behind `a1 end`.
4. After `script end`, microtasks drain in order, then the timer task runs.

### O5 \[I+\] Closures in loops with var/let and delays

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log('var', i), i * 100);
for (let j = 0; j < 3; j++) setTimeout(() => console.log('let', j), j * 100);
```

**Output:** `var 3`, `let 0`, `var 3`, `let 1`, `var 3`, `let 2`

The delays (0, 100, 200) are evaluated immediately, but the `var` callbacks read the single `i` later → `3`. `let` gets a fresh binding per iteration. Equal delays fire in registration order, so the pairs interleave.

### O6 \[I+\] `this` lost and found


**Output (module / strict):** `obj undefined obj`, then `other`

### O7 \[I+\] Prototype shadowing

```js

A.prototype.list = [];
A.prototype.count = 0;

a.count++;
```

**Output:** `[1] 0 true false`

### O8 \[I\] Coercion round

```js

```

**Output:** `true false '24' 'null1' true`

### O9 \[S\] Promise chain with errors

### O10 \[S\] Microtask inside a microtask vs timers

### O11 \[S\] Getters and spread

### O12 \[S\] Generators: next(value), return() and finally

### O14 \[I\] Shared closure state

### O15 \[I+\] Class field initialisation order

```js
class A { x = 1; constructor() { console.log('A', this.x, this.y); } }
class B extends A { y = 2; constructor() { super(); console.log('B', this.y); } }
new B();
```

**Output:** `A 1 undefined`, `B 2`

1. `super()` runs A's field initialisers (`x = 1`), then A's constructor body — B's fields don't exist yet, so `this.y` is `undefined`.
2. After `super()` returns, B's fields initialise (`y = 2`), then the rest of B's constructor runs.

This is why a parent constructor calling an overridden method that reads a child field sees `undefined`.

### O16 \[S\] Returning a promise from `.then` costs extra ticks

```js
Promise.resolve()
  .then(() => { console.log(1); return Promise.resolve(2); })
  .then((v) => console.log(v));
Promise.resolve()
  .then(() => console.log(3))
  .then(() => console.log(4))
  .then(() => console.log(5))
  .then(() => console.log(6));
```

**Output:** `1 3 4 5 2 6`

| Tick | Chain 1 | Chain 2 |
| --- | --- | --- |
| 1 | logs 1, returns a promise → queues a *resolve-thenable* job | logs 3 |
| 2 | job calls `promise.then(...)` → queues its reaction | logs 4 |
| 3 | reaction resolves the outer promise → queues the next handler | logs 5 |
| 4 | logs 2 | logs 6 |

Returning a native promise from a handler adds two microtask hops compared with returning a plain value.

### O17 \[I+\] Property order and JSON

### O18 \[I+\] `finally` and return values


### O20 \[S\] async errors, catch and finally


### O21 \[S\] `bind` meets `new`

### O22 \[I\] Comparison grab-bag

**Output:** `true false false true true true`

### O23 \[I+\] Generator return values and spread

### S1 \[S\] Debugging: "The dashboard tab gets slower and crashes after a few hours"

**Likely causes:** a memory leak (listeners or intervals added per widget refresh, growing caches, detached DOM from re-renders, unclosed WebSocket subscriptions) or unbounded data accumulation (appending every live update to an array).

**Approach:**

1. Reproduce faster: shorten the refresh interval or script widget mount/unmount in a loop.
2. Performance monitor: JS heap, DOM node count, listener count. Rising DOM nodes point to detached trees; rising listeners to missing cleanup.
3. Heap snapshot comparison → follow retainers to the root that keeps objects alive.
4. Typical fix: an `AbortController` per widget for all subscriptions, a ring buffer for live data (last N points), `WeakMap` for per-node metadata.
5. Prevent recurrence: a memlab/Playwright test that cycles the route 50× and asserts heap growth stays under a threshold.

### S2 \[S\] Debugging: "Users occasionally see another user's data"

Treat it as a severity-1 security incident first: mitigate (disable the caching layer or feature), then debug.

**Hypotheses:** shared mutable state in a Node server (a module-level "current user" variable — requests interleave across `await`s); CDN, edge or service-worker caching of personalised responses (missing `Cache-Control: private` / `Vary`); an SSR store singleton reused between requests; a client cache not keyed by user that survives logout.

**Fix patterns:** per-request context via `AsyncLocalStorage`, a fresh store per SSR request, correct cache headers, clearing client caches on logout, and a test that runs two users' requests concurrently.

### S3 \[S\] Performance: "Typing in a search box with 20k rows lags"

- Measure: the Performance panel while typing shows long tasks from filtering plus rendering 20k rows.
- Fixes, in order of value: **virtualise** the list (render about 30 rows); **debounce** the filter (150–250 ms) or use `useDeferredValue`/`startTransition` to keep input responsive; precompute a lowercase search index once; move filtering of very large sets to a **Web Worker**; keep row components stable (keys, memoised rows).
- Trade-offs: debounce adds latency; workers add serialisation cost (transfer typed arrays or keep data resident in the worker); virtualisation complicates accessibility, find-in-page and variable row heights.

### S4 \[S\] Architecture: state management for a large SPA

Separate **server state** (cached remote data: TanStack Query, SWR, RTK Query — caching, dedupe, refetch, invalidation) from **client/UI state** (local state, context for rarely-changing globals, a store such as Zustand/Redux/signals for cross-cutting interactive state) and **URL state** (filters, pagination — shareable and back-button friendly).

| Option | Good for | Watch out |
| --- | --- | --- |
| Local state + lifting | Most UI state | Prop drilling across deep trees |
| Context | Theme, auth, locale (rarely changes) | Every consumer re-renders on change |
| Redux Toolkit | Large teams, complex workflows, devtools | Boilerplate, over-centralisation |
| Zustand / Jotai / signals | Fine-grained subscriptions, less ceremony | Fewer conventions; needs discipline |
| Server-state libraries | All remote data | Misused as a global store for UI flags |

Senior answer: most apps over-centralise. Keep state as close to its use as possible, and treat remote data as a cache, not as state.

### S5 \[S\] Architecture: monolith frontend vs micro-frontends

Micro-frontends (Module Federation, single-spa, iframes, web components) let teams deploy independently. Costs: duplicated dependencies and bigger payloads, inconsistent UX, cross-app routing and state, harder performance budgets and testing. Choose them for **organisational** scaling (many teams, independent release cadence), not technical fashion. A well-modularised monorepo (Nx/Turborepo with enforced boundaries) solves most problems with less runtime cost.

### S6 \[S\] Design: an API client used by 30 teams

Clarify first: auth refresh, retries, timeouts, cancellation, typing, observability, caching, error model.

```js
export function createClient({ baseUrl, getToken, fetchImpl = fetch, timeout = 10_000, onEvent = () => {} }) {
  async function request(path, { method = 'GET', body, signal, retries = method === 'GET' ? 2 : 0 } = {}) {
    const timeoutSignal = AbortSignal.timeout(timeout);
    const combined = signal ? AbortSignal.any([signal, timeoutSignal]) : timeoutSignal;
    return retry(async (attempt) => {
      const started = performance.now();
      const res = await fetchImpl(new URL(path, baseUrl), {
        method, signal: combined,
        headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${await getToken()}` },
        body: body === undefined ? undefined : JSON.stringify(body),
      });
      onEvent({ path, method, status: res.status, ms: performance.now() - started, attempt });
      if (!res.ok) throw Object.assign(new Error(`HTTP ${res.status}`), { status: res.status, body: await res.text() });
      return res.status === 204 ? null : res.json();
    }, { retries, signal: combined });
  }
  return { get: (p, o) => request(p, o), post: (p, body, o) => request(p, { ...o, method: 'POST', body }) };
}
```

Design points to say out loud: dependency injection for testing (`fetchImpl`, `getToken`), retries only for idempotent methods by default, typed error objects, one shared refresh-token promise for concurrent 401s (avoids a refresh stampede), a telemetry hook, and semver with deprecation warnings.

**Catch for the reviewer:** `AbortSignal.timeout(timeout)` is created once per request, so it caps the *total* time across all retries, not each attempt — a slow first attempt can leave no time to retry. For a per-attempt budget, create the timeout inside the retried function (`AbortSignal.any([signal, AbortSignal.timeout(perAttempt)])`) and keep an overall deadline as a separate signal. Say which you chose and why.

### S7 \[S\] Trade-off: SSR vs CSR vs SSG vs streaming/islands

| Strategy | TTFB | LCP | Interactivity cost | Best for |
| --- | --- | --- | --- | --- |
| CSR (SPA) | Fast (static shell) | Slow — waits for JS + data | Whole app hydrates | Authenticated dashboards |
| SSR | Slower (render per request) | Fast | Hydration of whole page | SEO + personalised pages |

### S8 \[S\] Handling errors across an application

- Classify: **operational** errors (network, validation, 404 — expected, handled) vs **programmer** errors (bugs — fail loudly, report).
- Boundaries: React error boundaries per route/widget; global `window.onerror` and `unhandledrejection` reporters; in Node, `process.on('unhandledRejection')` logs then exits so the supervisor restarts a possibly corrupt process.
- Custom error classes with `cause`, codes, and user-safe messages; never show stack traces to users.
- Graceful degradation: a failed recommendations widget must not blank the checkout page.

### S9 \[S\] Migrating a large codebase from JavaScript to TypeScript

Incremental: `allowJs` + `checkJs` with JSDoc, convert leaf modules first, `strict` per directory via project references, lint-ban new `any`, type external boundaries with runtime schemas (zod) so types match reality, and track a progress metric (share of strict files). No big-bang rewrite; keep shipping features.

### S10 \[S\] A Node.js API's p99 latency spikes every few minutes

Hypotheses: GC pauses (large heap, allocation churn), event-loop blocking (sync JSON of huge payloads, regex, crypto on the main thread), connection-pool exhaustion, a cron-like job in the same process, a slow downstream dependency. Measure: `perf_hooks.monitorEventLoopDelay()`, `--trace-gc`, APM spans, a CPU profile during a spike. Fixes: stream large responses, move CPU work to worker threads or another service, tune pool sizes, cap payload sizes, scale horizontally, and alert on event-loop lag.

### S12 \[S\] Design: a real-time notifications client

**Clarify:** one-way (server → client) or two-way? Delivery guarantees? Expected fan-out and message rate? Mobile/flaky networks?

| Option | Direction | Reconnect | Through proxies/CDN | Use when |
| --- | --- | --- | --- | --- |
| Polling | Client pulls | Trivial | Easy | Low frequency, simplest ops |
| Server-Sent Events | Server → client | Built in (`Last-Event-ID`) | HTTP, easy | Notifications, feeds, progress |

### S13 \[S\] Incident: a dependency you ship was compromised

1. **Contain:** pin to the last known-good version, rebuild from a clean lockfile, redeploy; block the bad version in your registry proxy.
2. **Assess blast radius:** did it run at install (CI secrets, developer machines) or ship in the bundle (user data, tokens)? Check CI logs and bundle diffs.
3. **Rotate** every secret the build or runtime could reach (npm tokens, cloud keys, API keys).
4. **Communicate** with security and, if user data may be exposed, follow disclosure obligations.
5. **Prevent:** lockfiles + `npm ci`, install scripts disabled or allowlisted, provenance checks, automated alerts (Socket, Dependabot), minimal dependencies, and SRI for CDN scripts.

## JavaScript utilities

### C1 \[I\] Deep clone (cycles, Dates, Maps, Sets)

```js
function deepClone(value, seen = new WeakMap()) {
  if (value === null || typeof value !== 'object') return value;
  if (seen.has(value)) return seen.get(value);
  if (value instanceof Date) return new Date(value);
  if (value instanceof RegExp) return new RegExp(value.source, value.flags);
  if (value instanceof Map) {
    const m = new Map(); seen.set(value, m);
    value.forEach((v, k) => m.set(deepClone(k, seen), deepClone(v, seen)));
    return m;
  }
  if (value instanceof Set) {
    const s = new Set(); seen.set(value, s);
    value.forEach((v) => s.add(deepClone(v, seen)));
    return s;
  }
  const out = Array.isArray(value) ? [] : Object.create(Object.getPrototypeOf(value));
  seen.set(value, out);
  for (const key of Reflect.ownKeys(value)) out[key] = deepClone(value[key], seen);
  return out;
}
```

**Complexity:** O(n) time and space over reachable nodes. **Alternative:** `structuredClone` (native, handles cycles; loses prototypes and functions). Why a `WeakMap`? Cycle detection without retaining the source after cloning.

### C2 \[I\] Flatten a nested array (with depth)

```js
const flatten = (arr, depth = Infinity) =>
  depth < 1 ? arr.slice() : arr.reduce((acc, x) => (Array.isArray(x) ? acc.push(...flatten(x, depth - 1)) : acc.push(x), acc), []);

// Iterative, full depth, no recursion limit
function flattenIter(arr) {
  const stack = [...arr], out = [];
  while (stack.length) {
    const x = stack.pop();
    if (Array.isArray(x)) stack.push(...x);
    else out.push(x);
  }
  return out.reverse();
}
```

**Complexity:** O(n) over all elements. Native: `arr.flat(Infinity)`. Caveat: `push(...x)` on a huge sub-array can exceed argument limits — use a loop for very large inputs.

### C3 \[I\] Two Sum

```js
function twoSum(nums, target) {
  const seen = new Map(); // value → index
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i);
  }
  return null;
}
```

Brute force O(n²) time, O(1) space → hash map O(n) time, O(n) space. Sorted input: two pointers, O(n) time, O(1) space.

### C4 \[I+\] Group anagrams

```js
function groupAnagrams(words) {
  const groups = new Map();
  for (const w of words) {
    const key = [...w].sort().join('');
    (groups.get(key) ?? groups.set(key, []).get(key)).push(w);

}
```

### C5 \[I+\] LRU cache with O(1) get/put

```js
class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return -1;
    const v = this.map.get(key);
    this.map.delete(key); this.map.set(key, v);   // move to most-recent
    return v;
  }
  put(key, value) {
    this.map.delete(key);
    this.map.set(key, value);
    if (this.map.size > this.capacity) this.map.delete(this.map.keys().next().value); // least recent
  }
}
```

Relies on `Map` keeping insertion order. If asked to avoid that trick: hash map + doubly linked list. O(1) per operation, O(capacity) space.

### C6 \[I+\] Event emitter with `on`, `off`, `once`, `emit`

```js
class Emitter {
  #handlers = new Map();
  on(evt, fn) {
    (this.#handlers.get(evt) ?? this.#handlers.set(evt, new Set()).get(evt)).add(fn);
    return () => this.off(evt, fn);                     // unsubscribe handle prevents leaks
  }
  off(evt, fn) { this.#handlers.get(evt)?.delete(fn); }
  emit(evt, ...args) {
    for (const fn of [...(this.#handlers.get(evt) ?? [])]) {   // copy: safe if handlers unsubscribe
      try { fn(...args); } catch (e) { queueMicrotask(() => { throw e; }); } // one bad handler can't stop the rest
    }
  }
  once(evt, fn) { const off = this.on(evt, (...a) => { off(); fn(...a); }); return off; }
}
```

Edge cases to mention: removing a handler during `emit`, a throwing handler, and `off` with the original function for a `once` handler (return the unsubscribe function instead).

### C7 \[I+\] Implement `Promise` (simplified)

```js
class MyPromise {
  #state = 'pending'; #value; #handlers = [];
  constructor(executor) {
    const settle = (state, value) => {
      if (this.#state !== 'pending') return;
      if (state === 'fulfilled' && value && typeof value.then === 'function') {
        return value.then((v) => settle('fulfilled', v), (e) => settle('rejected', e)); // adopt thenable
      }
      this.#state = state; this.#value = value;
      this.#handlers.forEach((h) => queueMicrotask(h));
      this.#handlers = [];
    };
    try { executor((v) => settle('fulfilled', v), (e) => settle('rejected', e)); }
    catch (e) { settle('rejected', e); }
  }
  then(onFul, onRej) {
    return new MyPromise((resolve, reject) => {
      const run = () => {
        const cb = this.#state === 'fulfilled' ? onFul : onRej;
        if (typeof cb !== 'function') return (this.#state === 'fulfilled' ? resolve : reject)(this.#value);
        try { resolve(cb(this.#value)); } catch (e) { reject(e); }
      };
      this.#state === 'pending' ? this.#handlers.push(run) : queueMicrotask(run);
    });
  }
  catch(onRej) { return this.then(undefined, onRej); }
  finally(fn) { return this.then((v) => { fn(); return v; }, (e) => { fn(); throw e; }); }
  static resolve(v) { return v instanceof MyPromise ? v : new MyPromise((r) => r(v)); }
}
```

Gaps vs the spec — name them, that's what seniors are graded on: no self-resolution `TypeError`, thenable adoption isn't guarded against multiple calls or a throwing `then` getter, `finally` doesn't wait for a returned promise.

### C8 \[I+\] Task queue with concurrency and priority

```js
class TaskQueue {
  constructor(concurrency = 2) { this.concurrency = concurrency; this.running = 0; this.queue = []; }
  add(task, priority = 0) {
    return new Promise((resolve, reject) => {
      this.queue.push({ task, priority, resolve, reject });
      this.queue.sort((a, b) => b.priority - a.priority); // fine for small queues; a heap for large ones
      this.#next();
    });
  }
  #next() {
    if (this.running >= this.concurrency || !this.queue.length) return;
    const { task, resolve, reject } = this.queue.shift();
    this.running++;
    Promise.resolve().then(task).then(resolve, reject).finally(() => { this.running--; this.#next(); });
    this.#next();
  }
}
```

**Complexity:** `add` is O(n log n) with the sort; a binary heap (C16) makes it O(log n).

### C9 \[I+\] Safe get/set by path

```js
const parsePath = (p) => (Array.isArray(p) ? p : p.replace(/\[(\w+)\]/g, '.$1').split('.').filter(Boolean));
const BLOCKED = new Set(['__proto__', 'constructor', 'prototype']);

function get(obj, path, fallback) {
  let cur = obj;
  for (const k of parsePath(path)) { if (cur == null) return fallback; cur = cur[k]; }
  return cur === undefined ? fallback : cur;
}

function set(obj, path, value) {
  const keys = parsePath(path);
  let cur = obj;
  keys.forEach((k, i) => {
    if (BLOCKED.has(k)) throw new Error('Unsafe key');   // prototype-pollution guard
    if (i === keys.length - 1) cur[k] = value;
    else cur = cur[k] ??= /^\d+$/.test(keys[i + 1]) ? [] : {};
  });
  return obj;
}
```

### C10 \[S\] Virtualised list windowing

```js
function visibleRange({ total, itemHeight, viewportHeight, scrollTop, overscan = 5 }) {
  const start = Math.max(0, Math.floor(scrollTop / itemHeight) - overscan);
  const end = Math.min(total - 1, Math.ceil((scrollTop + viewportHeight) / itemHeight) + overscan);
  return { start, end, offsetY: start * itemHeight, totalHeight: total * itemHeight };
}
```

Render rows `start…end` inside a container of `totalHeight`, translated by `offsetY`: O(visible) work regardless of `total`. Variable heights → measured heights + prefix sums + binary search for `start` (O(log n)).

### C11 \[S\] Topological sort with cycle detection

```js
function topoSort(graph) { // { a: ['b', 'c'], b: ['c'], c: [] } — a depends on b and c
  const state = new Map(); const order = [];
  const visit = (n, path = []) => {
    if (state.get(n) === 'done') return;
    if (state.get(n) === 'visiting') throw new Error(`Cycle: ${[...path, n].join(' → ')}`);
    state.set(n, 'visiting');
    for (const dep of graph[n] ?? []) visit(dep, [...path, n]);
    state.set(n, 'done');
    order.push(n);                       // dependencies first
  };
  Object.keys(graph).forEach((n) => visit(n));
  return order;
}
topoSort({ a: ['b', 'c'], b: ['c'], c: [] }); // ['c', 'b', 'a']
```

**Complexity:** O(V + E). Used by bundlers, build systems and task runners. Alternative: Kahn's algorithm (BFS on in-degrees), which also shows which tasks can run in parallel.

### C12 \[S\] Promise-returning debounce with `cancel`/`flush`

```js
function debounceAsync(fn, wait) {
  let timer, pending = [], lastArgs, lastThis;
  const run = async () => {
    timer = null;
    const waiters = pending; pending = [];
    try { const r = await fn.apply(lastThis, lastArgs); waiters.forEach((w) => w.resolve(r)); }
    catch (e) { waiters.forEach((w) => w.reject(e)); }
  };
  function debounced(...args) {
    lastArgs = args; lastThis = this;
    clearTimeout(timer);
    timer = setTimeout(run, wait);
    return new Promise((resolve, reject) => pending.push({ resolve, reject }));
  }
  debounced.cancel = () => { clearTimeout(timer); timer = null; pending.forEach((w) => w.reject(new Error('cancelled'))); pending = []; };
  debounced.flush = () => { if (timer) { clearTimeout(timer); return run(); } };
  return debounced;
}
```

Every caller in a burst receives the same result — useful for autosave and async validation.

### C13 \[I\] Valid parentheses

```js
function isValid(s) {
  const pairs = { ')': '(', ']': '[', '}': '{' };
  const stack = [];
  for (const ch of s) {
    if (ch === '(' || ch === '[' || ch === '{') stack.push(ch);
    else if (ch in pairs) { if (stack.pop() !== pairs[ch]) return false; }
  }
  return stack.length === 0;
}
isValid('([]{})'); // true
isValid('(]');     // false
```

Edge cases: empty string (valid), a lone closer (`pop()` returns `undefined` → false), leftover openers (non-empty stack → false).

### C14 \[I+\] Longest substring without repeating characters

```js
function lengthOfLongestSubstring(s) {
  const last = new Map();   // char → last index seen
  let start = 0, best = 0;
  for (let i = 0; i < s.length; i++) {
    const ch = s[i];
    if (last.has(ch) && last.get(ch) >= start) start = last.get(ch) + 1; // jump past the repeat
    last.set(ch, i);
    best = Math.max(best, i - start + 1);
  }
  return best;
}
lengthOfLongestSubstring('abcabcbb'); // 3 ('abc')
```

Brute force checks every substring, O(n³). The window never moves backwards, so each index is visited once: O(n) time, O(k) space for k distinct characters. Follow-up: Unicode — iterate `[...s]` so surrogate pairs count as one character.

### C15 \[I+\] Merge intervals

```js
function merge(intervals) {
  if (intervals.length < 2) return intervals.map((iv) => [...iv]);
  const sorted = intervals.toSorted((a, b) => a[0] - b[0]);
  const out = [[...sorted[0]]];
  for (const [s, e] of sorted.slice(1)) {
    const lastIv = out.at(-1);
    if (s <= lastIv[1]) lastIv[1] = Math.max(lastIv[1], e);  // overlap → extend
    else out.push([s, e]);
  }
  return out;
}
merge([[1, 3], [8, 10], [2, 6], [15, 18]]); // [[1, 6], [8, 10], [15, 18]]
```

O(n log n) for the sort, O(n) for the pass. Clarify whether touching intervals (`[1,2]` and `[2,3]`) merge — this version merges them. Uses `toSorted` so the caller's array isn't mutated.

### C16 \[I+\] Kth largest element — heap and quickselect

```js
class MinHeap {
  #a = [];
  get size() { return this.#a.length; }
  peek() { return this.#a[0]; }
  push(v) {
    const a = this.#a; a.push(v);
    let i = a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (a[p] <= a[i]) break;
      [a[p], a[i]] = [a[i], a[p]]; i = p;
    }
  }
  pop() {
    const a = this.#a, top = a[0], end = a.pop();
    if (a.length) {
      a[0] = end;
      let i = 0;
      for (;;) {
        const l = 2 * i + 1, r = l + 1;
        let m = i;
        if (l < a.length && a[l] < a[m]) m = l;
        if (r < a.length && a[r] < a[m]) m = r;
        if (m === i) break;
        [a[m], a[i]] = [a[i], a[m]]; i = m;
      }
    }
    return top;
  }
}

function kthLargest(nums, k) {
  const heap = new MinHeap();
  for (const n of nums) {
    heap.push(n);
    if (heap.size > k) heap.pop();   // keep only the k largest
  }
  return heap.peek();
}
kthLargest([3, 2, 1, 5, 6, 4], 2); // 5
```

**Heap:** O(n log k) time, O(k) space — best for streams. **Sort:** `nums.toSorted((a, b) => b - a)[k - 1]`, O(n log n) — fine in an interview if you say so. **Quickselect:** partition around a random pivot and recurse into one side: O(n) average, O(n²) worst, O(1) extra space. JavaScript has no built-in heap, so being able to write one is expected at senior level.

### C17 \[I+\] Search in a rotated sorted array

```js
function searchRotated(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (nums[mid] === target) return mid;
    if (nums[lo] <= nums[mid]) {                  // left half is sorted
      if (nums[lo] <= target && target < nums[mid]) hi = mid - 1; else lo = mid + 1;
    } else {                                      // right half is sorted
      if (nums[mid] < target && target <= nums[hi]) lo = mid + 1; else hi = mid - 1;
    }
  }
  return -1;
}
searchRotated([4, 5, 6, 7, 0, 1, 2], 0); // 4
```

O(log n) time, O(1) space. At each step one half is guaranteed sorted, so you can tell whether the target lies in it. Follow-up: with duplicates the worst case degrades to O(n) (`[1,1,1,0,1]`).

### C18 \[I+\] Deep equal

```js
function deepEqual(a, b, seen = new WeakMap()) {
  if (Object.is(a, b)) return true;
  if (typeof a !== 'object' || typeof b !== 'object' || a === null || b === null) return false;
  if (Object.getPrototypeOf(a) !== Object.getPrototypeOf(b)) return false;
  if (seen.get(a) === b) return true;            // already comparing this pair (cycle)
  seen.set(a, b);
  if (a instanceof Date) return a.getTime() === b.getTime();
  if (a instanceof Map || a instanceof Set) {
    if (a.size !== b.size) return false;
    if (a instanceof Set) return [...a].every((v) => b.has(v));   // primitive members; objects need pairing
    for (const [k, v] of a) if (!b.has(k) || !deepEqual(v, b.get(k), seen)) return false;
    return true;
  }
  const ka = Reflect.ownKeys(a), kb = Reflect.ownKeys(b);
  if (ka.length !== kb.length) return false;
  return ka.every((k) => Object.hasOwn(b, k) && deepEqual(a[k], b[k], seen));
}
deepEqual({ x: [1, { y: NaN }] }, { x: [1, { y: NaN }] }); // true
```

Decisions to state: `Object.is` (so `NaN` equals `NaN`, `0` and `-0` differ), prototypes must match, Set members compared by identity. O(n) time and space. Libraries: `node:assert`'s `deepStrictEqual`, `lodash.isEqual`.

### C19 \[I\] Spiral matrix

```js
function spiral(matrix) {
  const out = [];
  if (!matrix.length) return out;
  let rowA = 0, rowB = matrix.length - 1, colA = 0, colB = matrix[0].length - 1;
  while (rowA <= rowB && colA <= colB) {
    for (let c = colA; c <= colB; c++) out.push(matrix[rowA][c]);
    rowA++;
    for (let r = rowA; r <= rowB; r++) out.push(matrix[r][colB]);
    colB--;
    if (rowA <= rowB) { for (let c = colB; c >= colA; c--) out.push(matrix[rowB][c]); rowB--; }
    if (colA <= colB) { for (let r = rowB; r >= rowA; r--) out.push(matrix[r][colA]); colA++; }
  }
  return out;
}
spiral([[1, 2, 3], [4, 5, 6], [7, 8, 9]]); // [1, 2, 3, 6, 9, 8, 7, 4, 5]
```

O(n·m) time, O(1) extra space. The two guards stop a single remaining row or column from being read twice — the classic bug interviewers look for.

# Best practices & final checklist

## Common mistakes and what to do instead

| Mistake | Why it hurts | Do instead |
| --- | --- | --- |
| `==` comparisons | Surprising coercion | `===`; `x == null` only for null/undefined |
| `\|\|` for defaults | Replaces valid `0`, `''`, `false` | `??` / `??=` |
| Mutating props/state/arguments | Stale UI, shared-state bugs | Immutable updates, `toSorted`/`with`, spread |
| `async` callbacks in `forEach` | No awaiting, unhandled rejections | `for…of` + `await` or `Promise.all` |
| Unbounded `Promise.all` over large lists | Rate limits, memory spikes | Concurrency limit (pool) |
| Ignoring `res.ok` with `fetch` | HTTP errors treated as success | Check status, throw typed errors |
| Swallowing errors (`catch {}`) | Silent failures | Handle, rethrow with `cause`, or report |
| `return` inside `finally` | Overrides results and swallows errors | Never return from `finally` |
| Listeners/timers without cleanup | Memory leaks, duplicate handlers | `AbortController`, return unsubscribe functions |
| `innerHTML` with user data | XSS | `textContent`, a sanitiser, Trusted Types |
| Floating-point money | Rounding errors | Integer minor units / decimal library |
| `delete` on hot objects, mixed-type arrays | Deoptimisation | Stable shapes, `Map` for dynamic keys |
| Default `sort()` on numbers | Lexicographic order | Comparator `(a, b) => a - b` |
| Date-only strings and timezone-less dates | Off-by-one-day bugs | ISO 8601 with offset, `Intl`, Temporal |
| Unbounded regex on user input | ReDoS blocks the event loop | No nested quantifiers, cap input length |
| Ignoring stream backpressure in Node | Memory blow-up | `pipeline()` / respect `write()` return value |
| `any` everywhere in TypeScript | Types that lie | `unknown` + narrowing, schema validation at boundaries |
| Premature optimisation / memoising everything | Complexity, memory | Measure first, optimise hot paths |
| Deep inheritance trees | Fragile coupling | Composition, small modules |

## Production-level considerations

- **Correctness at boundaries:** validate all external input (API, forms, URL, storage) at runtime; TypeScript types vanish at runtime.
- **Observability:** structured logs, error tracking with source maps, Web Vitals RUM, tracing across services; enough context to debug without logging secrets or PII.
- **Resilience:** timeouts on every network call, retries with backoff for idempotent operations, circuit breakers, graceful degradation in the UI.
- **Performance budgets:** bundle-size limits and Lighthouse CI in the pipeline, INP/LCP alerts.
- **Security hygiene:** CSP, dependency audits, lockfiles, least-privilege tokens, no secrets in client bundles (anything in the bundle is public).
- **Accessibility and i18n:** semantic HTML, keyboard support, `Intl` for numbers, dates and plurals.
- **Compatibility:** declared browser/Node support (Browserslist, `engines`), deliberate polyfills, feature detection over UA sniffing.
- **Cleanup discipline:** every subscribe has an unsubscribe; every `setInterval` a `clearInterval`; every `AbortController` is tied to a lifecycle.

## Recommended coding patterns

1. Early returns and guard clauses over deep nesting.
2. Pure functions for business logic; side effects at the edges.
3. Dependency injection for I/O (fetch, clock, storage) → easy testing.
4. Lookup tables (object/Map of handlers) instead of long `switch`/`if` chains.
5. `const` by default, `let` when reassigning, never `var`.
6. Named exports, small modules, explicit public APIs per folder.
7. Explicit async lifecycles: `AbortController` for cancellation, `finally` for cleanup.
8. Error classes with `cause` and codes; one place per layer that decides how errors surface.
9. Readable over clever in shared code — readability is a performance feature for teams.
