## Part 1 — React Fundamentals

React is a function from state to UI: `UI = f(state)`. Every fundamental question is a variation of "what triggers f to run again, and what does React do with the result?"

### Q1.1 \[I\] What is JSX and what does it compile to?

JSX is syntax sugar for creating React elements. With the modern automatic runtime (React 17+), the compiler imports `jsx` from `react/jsx-runtime` for you.

```jsx
// You write
const el = <Button variant="primary" onClick={save}>Save</Button>;

// Compiler emits (automatic runtime)
import { jsx as _jsx } from 'react/jsx-runtime';
const el = _jsx(Button, { variant: 'primary', onClick: save, children: 'Save' });

// Which returns a plain object (simplified)
{ $$typeof: Symbol(react.transitional.element), type: Button, key: null, props: { variant: 'primary', onClick: save, children: 'Save' } }
```

**Why it matters:**

- An element is a cheap, immutable *description*. Creating one does not render anything.
- Lowercase tags (`div`) become strings; capitalised tags become component references. That is why components must start with a capital letter.
- `key` is pulled out of props — a child cannot read `props.key`.
- In React 19, `ref` is a normal prop for function components, so `forwardRef` is no longer needed.

**Follow-up \[S\]:** *Why is `$$typeof` a Symbol?* It prevents XSS via JSON injection: a server can't send a Symbol in JSON, so a forged "element" object from untrusted data will not be rendered as an element.

### Q1.2 \[I\] Components vs elements vs instances?

| Term | What it is | Who creates it |
| --- | --- | --- |
| Component | A function (or class) that returns elements | You |
| Element | A plain object describing what to render | JSX / `jsx()` on every render |
| Fiber (instance) | React's internal, long-lived record for a mounted component: state, hooks, effects | React |

State lives on the **Fiber**, not in the function. The function is called again on every render; hooks read state back from the Fiber by call order.

### Q1.3 \[I\] How do props work, and why are they read-only?

Props are the arguments a parent passes. A component must be **pure with respect to props**: same props + state + context → same output. Mutating props breaks that and breaks memoisation and concurrent rendering, which may call your component more than once.

```jsx
function Avatar({ user, size = 48 }) {   // default values via destructuring (defaultProps is removed for function components in 19)
  return <img src={user.avatarUrl} alt={user.name} width={size} height={size} />;
}
```

**Children are props too.** `<Card><Title /></Card>` passes `children`. This is the basis of composition.

### Q1.4 \[I\] What causes a component to re-render?

Exactly four triggers:

1. Its own state changes (`setState`, `dispatch`) with a value that is not `Object.is`-equal to the current one.
2. Its parent re-renders (unless the component is memoised and props are shallow-equal, or the element is referentially identical).
3. A context it reads changes value.
4. An external store it subscribes to via `useSyncExternalStore` changes snapshot.

**Common misconception:** "props changing causes a re-render." Wrong framing. A *parent re-render* causes the child to render; changed props are just what usually comes with it. A non-memoised child re-renders even if props are identical.

### Q1.5 \[I\] Conditional rendering patterns and the `0` trap

```jsx
{isLoading ? <Spinner /> : <List items={items} />}
{error && <ErrorBanner error={error} />}
{items.length > 0 && <List items={items} />}   // good
{items.length && <List items={items} />}       // BUG: renders "0" when empty
```

`false`, `null`, `undefined` and `true` render nothing. `0` and `NaN` are rendered as text. Always coerce to a boolean.

**Why position matters:** `{cond ? <A /> : <B />}` and `{cond && <A />}{!cond && <B />}` look similar but the second keeps two separate slots, which affects state preservation (see Part 3).

### Q1.6 \[I\] Why do lists need keys, and why not use the index?

Keys give each child a stable identity among its siblings so React can match old and new children during reconciliation.

```jsx
{todos.map(todo => <TodoRow key={todo.id} todo={todo} />)}
```

Index keys break when items are inserted, removed or reordered: identity follows the *position*, so state (input text, focus, checkbox) sticks to the wrong row.

Index keys are acceptable only when the list is static, never reordered or filtered, and rows have no state. Never use `Math.random()` — a new key every render remounts every row.

**Senior follow-up:** keys also work outside lists. `<Profile key={userId} />` forces a full reset when the user changes. This is the idiomatic way to reset state instead of a "sync props to state" effect.

### Q1.7 \[I\] Controlled vs uncontrolled components

|  | Controlled | Uncontrolled |
| --- | --- | --- |
| Source of truth | React state | The DOM |
| Read value | From state | From a ref, or `FormData` on submit |
| Re-render per keystroke | Yes | No |
| Good for | Live validation, dependent fields, formatting | Simple forms, large forms, file inputs, Server Actions |

```jsx
// Controlled
const [email, setEmail] = useState('');
<input value={email} onChange={e => setEmail(e.target.value)} />

// Uncontrolled + React 19 form action
function Signup() {
  async function action(formData) {
    await createUser(formData.get('email'));
  }
  return <form action={action}><input name="email" defaultValue="" /><button>Join</button></form>;
}
```

**Traps:** `value` without `onChange` makes a read-only field and logs a warning. Switching `value` from `undefined` to a string flips uncontrolled → controlled and logs a warning — initialise with `''`. `<input type="file">` is always uncontrolled.

### Q1.8 \[I\] Composition vs inheritance; what is prop drilling?

React favours composition: pass components or elements as `children` or named slot props.

```jsx
function Layout({ sidebar, children }) {
  return <div className="layout"><aside>{sidebar}</aside><main>{children}</main></div>;
}
<Layout sidebar={<Nav user={user} />}><Feed user={user} /></Layout>
```

Passing elements down (instead of data) is the first fix for prop drilling — reach for Context only after composition fails. It also helps performance: `children` created by a parent do not re-render when `Layout`'s own state changes.

### Q1.9 \[I\] Synthetic events — what changed in modern React?

- React attaches listeners at the **root container**, not `document` (since 17).
- Event pooling is gone (17+); you can read `e.target` asynchronously.
- `onChange` on inputs fires on every keystroke (like native `input`).
- `onScroll` does not bubble in React.
- Updates in any event handler, timeout or promise are batched (18+).

### Tricky follow-ups

- *Can a component return an array?* Yes, with keys, or a Fragment `<>...</>`. Fragments with keys use `<Fragment key=…>`.
- *Can a component return a string, number, or `undefined`?* Yes — since 18, returning `undefined` no longer throws.
- *Is `<Child />` inside a parent "called" by the parent?* No. The parent returns an element; React decides when and if to call `Child`. Calling `Child()` as a function breaks hooks and identity.

### Quick revision

- JSX → `jsx()` → plain element object; elements are descriptions, Fibers hold state.
- Re-render triggers: own state, parent render, context, external store.
- `{n && …}` renders `0`; coerce to boolean.
- Keys = identity among siblings; changing a key = remount; index keys break on reorder.
- Controlled = state is truth; uncontrolled = DOM is truth; React 19 form actions favour uncontrolled + `FormData`.
- Prefer composition and `children` before Context.

## Part 2 — Hooks Deep Dive

Hooks are an ordered list of slots stored on the component's Fiber. React identifies each hook only by **call order**, which is why the Rules of Hooks exist.

### Q2.1 \[I\] What are the Rules of Hooks, and why do they exist?

1. Call hooks only at the top level — not in conditions, loops, nested functions, or after an early `return`.
2. Call hooks only from components or custom hooks.

**Why:** on each render React walks a linked list of hook slots in order. If render 1 calls `useState, useEffect, useState` and render 2 skips the effect, the second `useState` reads the effect's slot. State gets corrupted, so React throws "Rendered fewer/more hooks than expected".

**Exception:** `use(promise | context)` (React 19) *can* be called conditionally and in loops. It does not occupy a stable slot the same way.

### Q2.2 \[I\] `useState` — direct value vs updater function

```jsx
const [count, setCount] = useState(0);

function addThree() {
  setCount(count + 1); // queues "replace with 0+1"
  setCount(count + 1); // queues "replace with 0+1"
  setCount(count + 1); // queues "replace with 0+1"  → result 1
}
function addThreeCorrect() {
  setCount(c => c + 1); // queues fn
  setCount(c => c + 1);
  setCount(c => c + 1); // → result 3
}
```

`count` is a constant captured by this render's closure. Setters do not mutate it; they enqueue updates processed on the **next** render. Use the updater whenever the next value depends on the previous one.

**Lazy initialiser:** `useState(() => expensiveParse(raw))` runs the function once. `useState(expensiveParse(raw))` runs it every render and discards the result.

**Bail-out:** setting the same value (`Object.is`) usually skips re-rendering children. React may still render the component itself once before bailing out.

### Q2.3 \[I\] `useEffect` — what it is for, and when it runs

Effects synchronise a component with an **external system**: network, subscriptions, timers, DOM APIs, analytics, non-React widgets.

```jsx
useEffect(() => {
  const conn = createConnection(roomId);
  conn.connect();
  return () => conn.disconnect();   // cleanup before next run and on unmount
}, [roomId]);
```

- Runs **after paint** (usually); does not block the browser.
- Cleanup runs before the next effect run with the old values, and on unmount.
- Dependencies are compared with `Object.is`. No array = every commit. `[]` = mount only (and, in Strict Mode dev, mount → cleanup → mount).

**You probably don't need an effect when:**

- Deriving data from props/state → compute during render (or `useMemo`).
- Responding to a user event → do it in the event handler.
- Resetting state when a prop changes → use a `key`.
- Notifying a parent of a change → call the parent callback in the same handler.

### Q2.4 \[I\] `useLayoutEffect` vs `useEffect`

|  | `useEffect` | `useLayoutEffect` |
| --- | --- | --- |
| Runs | After paint (async) | After DOM mutation, **before paint** (sync) |
| Blocks paint | No | Yes |
| Use for | Data, subscriptions, logging | Measuring layout, tooltip positioning, avoiding flicker |
| On server | Ignored | Ignored (no warning in 19) — measure on client |

If a state update happens inside `useLayoutEffect`, React re-renders synchronously before paint, so the user never sees the intermediate frame.

`useInsertionEffect` runs before layout effects and is only for CSS-in-JS libraries injecting styles.

On updates, an effect only re-runs when a dependency changed, and its previous cleanup always runs first.

### Q2.5 \[I\] `useRef` — when and why

`useRef` returns a stable mutable box `{ current }` that persists across renders. Changing `.current` does **not** trigger a render.

Use it for DOM nodes, timer IDs, previous values, latest-callback holders, and any instance value that the UI does not display.

```jsx
function Stopwatch() {
  const intervalRef = useRef(null);
  const [ms, setMs] = useState(0);
  const start = () => {
    clearInterval(intervalRef.current);
    intervalRef.current = setInterval(() => setMs(m => m + 10), 10);
  };
  const stop = () => clearInterval(intervalRef.current);
  return <><p>{ms}ms</p><button onClick={start}>Start</button><button onClick={stop}>Stop</button></>;
}
```

**Rule:** don't read or write `ref.current` during render (except lazy init). It makes rendering impure and breaks under concurrent rendering and the React Compiler.

**Ref callbacks (React 19):** a callback ref may return a cleanup function, called when the node detaches.

```jsx
<div ref={node => {
  const ro = new ResizeObserver(onResize);
  ro.observe(node);
  return () => ro.disconnect();
}} />
```

### Q2.6 \[I\] `useReducer` — when is it better than `useState`?

Prefer `useReducer` when the next state depends on several fields, when many event types update the same state, or when you want transitions testable as a pure function.

```jsx
function cartReducer(state, action) {
  switch (action.type) {
    case 'add': {
      const existing = state.items.find(i => i.id === action.item.id);
      const items = existing
        ? state.items.map(i => i.id === action.item.id ? { ...i, qty: i.qty + 1 } : i)
        : [...state.items, { ...action.item, qty: 1 }];
      return { ...state, items };
    }
    case 'remove':
      return { ...state, items: state.items.filter(i => i.id !== action.id) };
    default:
      throw new Error(`Unknown action ${action.type}`);
  }
}
const [cart, dispatch] = useReducer(cartReducer, { items: [] });
```

**Why seniors like it:** `dispatch` is stable, so you can pass it through Context without causing re-renders, and handlers no longer need to close over state.

### Q2.7 \[I\] `useMemo` and `useCallback`

- `useMemo(fn, deps)` caches a **value**.
- `useCallback(fn, deps)` caches a **function** (= `useMemo(() => fn, deps)`).

They help only in three cases:

1. The calculation is measurably expensive (profile first; \~1 ms+).
2. The value/function is passed to a `React.memo` child, so a stable reference lets it skip rendering.
3. The value is a dependency of another hook, and a new reference would re-run it.

They cost memory, comparison work and readability. They are a performance hint, not a semantic guarantee — React may discard the cache.

**React Compiler note:** with the React Compiler (stable 1.0) enabled, most manual `useMemo`/`useCallback`/`memo` becomes unnecessary because the compiler memoises automatically. Interviewers increasingly ask whether you know this.

### Q2.8 \[I\] `useContext`

Reads the nearest provider's value above the component. When the value changes (`Object.is`), every consumer re-renders — even if memoised parents sit in between. In React 19 you can render `<ThemeContext value={theme}>` directly instead of `<ThemeContext.Provider>`.

### Q2.9 \[I\] `useId`

Generates an ID that is stable across server and client, so it is safe for SSR hydration. Use it for `htmlFor`/`aria-describedby`. Do **not** use it for list keys.

```jsx
function Field({ label, hint }) {
  const id = useId();
  return <><label htmlFor={id}>{label}</label><input id={id} aria-describedby={`${id}-hint`} /><p id={`${id}-hint`}>{hint}</p></>;
}
```

### Q2.10 \[S\] `useEffectEvent` (stable in 19.2)

Solves the "I need the latest value inside an effect, but it must not re-run the effect" problem.

```jsx
function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showToast('Connected', theme);   // always reads latest theme
  });
  useEffect(() => {
    const conn = createConnection(roomId);
    conn.on('connected', () => onConnected());
    conn.connect();
    return () => conn.disconnect();
  }, [roomId]); // theme is NOT a dependency; changing theme does not reconnect
}
```

Rules: call Effect Events only from inside effects; never pass them to other components or list them as dependencies. Before 19.2, the workaround was a "latest ref" (`ref.current = callback` in a layout effect).

### Q2.11 \[S\] `use` (React 19)

`use(resource)` reads a **promise** or **context** during render.

- With a promise, the component suspends until it resolves; the nearest `<Suspense>` shows the fallback and the nearest error boundary catches rejections.
- Promises must be **cached/stable** (created in a Server Component, a loader, or a cache). Creating a new promise in the same component's render causes an infinite suspend loop.
- Unlike other hooks, `use` can be called inside `if` and loops.

```jsx
function Comments({ commentsPromise }) {
  const comments = use(commentsPromise);   // promise created by parent/server
  return comments.map(c => <p key={c.id}>{c.text}</p>);
}
```

### Q2.12 \[S\] Other hooks you should recognise

| Hook | Purpose |
| --- | --- |
| `useTransition` | Mark updates as non-urgent; get `isPending`. Async functions allowed in 19 (Actions). |
| `useDeferredValue` | Render with a lagging copy of a value; 19 adds an `initialValue`. |
| `useSyncExternalStore` | Subscribe to an external store tear-free under concurrent rendering. |
| `useImperativeHandle` | Expose a custom ref API from a child. |
| `useActionState` | State that updates from the result of an action (formerly `useFormState`). |
| `useFormStatus` | Read pending status of the parent `<form>` (react-dom). |
| `useOptimistic` | Show optimistic state while an action is pending. |
| `useDebugValue` | Label custom hooks in DevTools. |

### Q2.13 \[I\] Writing a custom hook — what makes a good one?

A custom hook is a function starting with `use` that calls other hooks. It shares **logic**, not state: each component that calls it gets its own state.

```jsx
function useMediaQuery(query) {
  const subscribe = useCallback(cb => {
    const mql = window.matchMedia(query);
    mql.addEventListener('change', cb);
    return () => mql.removeEventListener('change', cb);
  }, [query]);
  return useSyncExternalStore(
    subscribe,
    () => window.matchMedia(query).matches,
    () => false                       // server snapshot
  );
}
```

Good custom hooks: have a focused purpose (`useOnlineStatus`, not `useMount`), return stable references, clean up everything they start, and document SSR behaviour.

### Q2.14 \[S\] Dependencies and stale closures — the core mental model

Every render creates new functions that **capture that render's props and state**. An effect, timeout or callback created in render N sees render N's values forever. That is a stale closure when it outlives render N.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);   // count is always 0 here → stuck at 1
    }, 1000);
    return () => clearInterval(id);
  }, []);                      // lint warns: missing dep 'count'
}
```

Fixes, in order of preference:

1. Use an updater: `setCount(c => c + 1)` — removes the dependency.
2. Move the logic into a reducer and `dispatch`.
3. Use `useEffectEvent` for "read latest, don't re-run" logic.
4. Add the dependency honestly (the interval restarts each second — correct but wasteful).

**Never silence `react-hooks/exhaustive-deps`.** If a dependency is "wrong", change the code so it is no longer needed.

### Quick revision

- Hooks = ordered slots on the Fiber; order must be identical every render (`use` is the exception).
- State values are snapshots per render; setters queue updates; use updaters for derived-from-previous.
- Effects are for external systems; derive in render; handle events in handlers; reset with keys.
- Layout effect = before paint, sync; effect = after paint.
- Refs don't render; don't touch them during render.
- Memo hooks are hints; React Compiler removes most of the need.
- `useEffectEvent` (19.2) fixes "latest value without re-running".
- Stale closures: fix with updaters, reducers, effect events — never by lying about deps.

## Part 3 — Rendering & Internals

"Rendering" in React means **calling your components** to compute a new tree. It does not mean touching the DOM. The DOM is only touched in the **commit** phase, and only where something changed.

### Q3.1 \[I\] What are the render and commit phases?

&#91;embedded content: React update pipeline · 5 stages\]

Rendering can be thrown away and redone; committing cannot, which is why render must be pure.

1. **Trigger** — initial `root.render()` or a state update schedules work on a lane (priority).
2. **Render phase** — React calls components top-down from where the update happened, building a work-in-progress Fiber tree and diffing it against the current one. It must be **pure**: no DOM writes, no subscriptions. In concurrent mode it can pause, resume, restart or throw work away.
3. **Commit phase** — synchronous and uninterruptible. Sub-phases: *before mutation* (snapshot), *mutation* (DOM inserts/updates/deletes, ref detach), *layout* (attach refs, run `useLayoutEffect`).
4. **Browser paint.**
5. **Passive effects** — `useEffect` cleanups then setups, after paint (synchronously before paint if the update came from a discrete event like a click).

**Why split them?** Rendering can be expensive and is safe to interrupt because it has no side effects. Committing must be atomic so the user never sees half an update.

### Q3.2 \[I\] What is the Virtual DOM, and is it "faster than the DOM"?

The Virtual DOM is the tree of React elements (and, internally, Fibers) that describes the UI. React diffs the new description against the previous one and applies minimal DOM operations.

It is **not** inherently faster than hand-written DOM updates. Its value is a declarative programming model with *good-enough* performance, plus a layer where React can schedule, batch and prioritise work. Frameworks like Svelte and Solid show that fine-grained reactivity can skip diffing altogether — a good senior talking point about trade-offs.

### Q3.3 \[I\] How does reconciliation work?

Full tree diffing is O(n³). React uses two heuristics to get O(n):

1. **Different element types produce different trees.** If `<div>` becomes `<section>`, or `<UserCard>` becomes `<AdminCard>`, React unmounts the old subtree (destroying state) and mounts a new one.
2. **Keys identify children across renders.** Among siblings, React matches by key (or index if no key).

Same type at the same position → React keeps the Fiber and its state and updates props.

&#91;embedded content: Reconciliation · 3 cases\]

With index keys, row 3 would instead keep DOM in place and swap content, so input state would stay with the position rather than the item.

### Q3.4 \[S\] State is tied to position in the tree — preservation and reset

React keeps state as long as **the same component type is rendered at the same position** in the tree.

```jsx
// State is PRESERVED when isPlayerA flips: same type, same position
{isPlayerA ? <Counter person="Taylor" /> : <Counter person="Sarah" />}

// State is RESET: different positions (two slots)
{isPlayerA && <Counter person="Taylor" />}
{!isPlayerA && <Counter person="Sarah" />}

// State is RESET: different keys
{isPlayerA ? <Counter key="Taylor" person="Taylor" /> : <Counter key="Sarah" person="Sarah" />}
```

**Classic bug:** defining a component inside another component.

```jsx
function Parent() {
  function Child() { const [t, setT] = useState(''); return <input value={t} onChange={e => setT(e.target.value)} />; }
  return <Child />;   // new function identity every render → new type → remount → input loses focus and text
}
```

### Q3.5 \[S\] What is Fiber and why did React rewrite to it?

Fiber (React 16) is React's reconciler architecture. Each Fiber is a JS object for one component/element with: `type`, `key`, `stateNode`, `child`/`sibling`/`return` pointers, `pendingProps`, `memoizedState` (the hook list), `flags` (effects to commit), `lanes` (pending priorities) and an `alternate` (the other copy).

Why it exists:

- The old stack reconciler recursed synchronously. A big update blocked the main thread for hundreds of ms.
- Fiber turns recursion into a **loop over a linked list**, so React can stop after any unit of work, yield to the browser, and continue later.
- **Double buffering:** `current` tree is on screen; `workInProgress` tree is built off-screen. On commit, the pointers swap.
- **Lanes:** bitmask priorities (Sync, InputContinuous, Default, Transition, Retry, Idle, Offscreen). High-priority work can interrupt low-priority work.

&#91;embedded content: Lanes in action · urgent input interrupts a transition\]

This is why render must be pure: the interrupted transition work is discarded and redone without anyone seeing it.

### Q3.6 \[I\] What is automatic batching?

Since React 18 with `createRoot`, multiple state updates in the same tick are batched into **one** render — in event handlers, promises, timeouts and native listeners alike.

```jsx
function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);
  // one render, not two
}
setTimeout(() => { setA(1); setB(2); }, 0);   // also one render in 18+ (two in 17)
```

&#91;embedded content: Automatic batching · 3 updates, 1 render\]

Batching is why `console.log(state)` right after a setter shows the old value: nothing has rendered yet. React 19.3 also defers updates from `resize` events to the next frame.

Opt out (rarely needed, e.g. to read DOM between updates):

```jsx
import { flushSync } from 'react-dom';
flushSync(() => setItems(next));
listRef.current.lastChild.scrollIntoView();   // DOM is updated now
```

### Q3.7 \[S\] What is concurrent rendering?

Concurrent rendering means React can prepare multiple versions of the UI and **interrupt** a render in progress. It is not multithreading — it is cooperative scheduling on the main thread (React yields roughly every 5 ms).

You opt in per update via `startTransition`, `useTransition`, `useDeferredValue`, or Suspense. Everything else stays urgent.

**Consequences you must code for:**

- Components may render more than once before committing → keep render pure.
- Reading mutable external sources during render can "tear" → use `useSyncExternalStore`.
- Work-in-progress may be thrown away → no side effects in render.

### Q3.8 \[S\] `useTransition` vs `useDeferredValue`

```jsx
// useTransition: you own the state setter
const [isPending, startTransition] = useTransition();
function onTabClick(tab) {
  startTransition(() => setTab(tab));   // heavy tab render is interruptible
}

// useDeferredValue: you receive a value (e.g. from props)
function SearchResults({ query }) {
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;
  return <div style={{ opacity: isStale ? 0.6 : 1 }}><SlowList query={deferredQuery} /></div>;
}
```

|  | `useTransition` | `useDeferredValue` |
| --- | --- | --- |
| Wraps | The state update | The value |
| Use when | You control the setter | Value comes from props/parent |
| Pending flag | `isPending` | Compare value vs deferred |
| Text input | Never wrap the input's own state | Defer the expensive consumer instead |

**Key insight:** transitions do not make code faster. They keep the UI responsive by letting urgent updates (typing) interrupt non-urgent ones (re-rendering 10,000 rows). `SlowList` must be `memo`-ised for `useDeferredValue` to help, otherwise the urgent render renders it anyway.

In React 19, `startTransition` accepts **async functions** (Actions); `isPending` stays true until they settle.

**19.3 change worth mentioning:** transitions now render independently instead of being entangled into a single render, so one slow transition no longer holds up unrelated ones.

### Q3.9 \[I\] What does Strict Mode do?

Development-only checks, no production effect:

- **Double-invokes** component bodies, initialisers, reducers and updater functions to expose impure render logic.
- **Mount → unmount → mount** for effects, to expose missing cleanups.
- **Double-invokes ref callbacks** (19) to expose missing ref cleanups.
- Warns about deprecated APIs.

In React 19 DevTools, the second log of a double render is dimmed rather than hidden. Seeing two fetches on mount in development means your effect lacks proper cleanup or cancellation — that is the point.

### Q3.10 \[S+\] How does React schedule work, and where does `Scheduler` fit?

`react-reconciler` asks the `scheduler` package for time slices using `MessageChannel` (not `requestIdleCallback`, which fires too rarely). The work loop runs `performUnitOfWork` until `shouldYield()` is true, then gives control back to the browser. Sync-lane work (discrete events) skips yielding.

### Quick revision

- Render = call components (pure, interruptible). Commit = DOM changes + layout effects (sync). Passive effects after paint.
- Reconciliation: different type → remount; same type same position → update; keys identify siblings.
- State lives at a tree position; change type/position/key to reset.
- Fiber = linked-list units of work, double buffering, lanes for priority.
- Automatic batching everywhere since 18; `flushSync` to opt out.
- Transitions mark work non-urgent; deferred values lag behind; neither speeds up code.
- Strict Mode double-calls render and re-runs effects in dev to find bugs.

## Part 4 — Advanced React

The advanced APIs are escape hatches and composition tools. Senior candidates are judged on *when not* to use them as much as on how.

### Q4.1 \[I\] How does Context work, and what are its performance limits?

Context passes a value through the tree without props. A consumer re-renders when the nearest provider's `value` changes by `Object.is` — **regardless of `React.memo` on intermediate parents**.

&#91;embedded content: Context propagation · 7 components\]

React walks the tree to find consumers of that context and schedules them directly; memo on the parents does not stop it.

```jsx
const AuthContext = createContext(null);

function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const login = useCallback(async creds => setUser(await api.login(creds)), []);
  const logout = useCallback(() => setUser(null), []);
  const value = useMemo(() => ({ user, login, logout }), [user, login, logout]);
  return <AuthContext value={value}>{children}</AuthContext>;   // React 19 syntax
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside <AuthProvider>');
  return ctx;
}
```

**Limits and fixes:**

| Problem | Fix |
| --- | --- |
| `value={{ user, login }}` creates a new object every render → all consumers re-render | `useMemo` the value |
| One big context; a change to any field re-renders every consumer | Split contexts (state vs dispatch; theme vs auth) |
| High-frequency values (mouse position, form keystrokes) | Use a store with selectors (Zustand, Redux, `useSyncExternalStore`) |
| Consumers can't subscribe to a slice | Context has no selectors — that is the core limitation |

**Rule of thumb:** Context is dependency injection for low-frequency values (theme, locale, auth user, feature flags). It is not a state manager.

### Q4.2 \[I\] What are portals, and how do events behave in them?

`createPortal(children, domNode)` renders children into a different DOM node, typically `document.body`, to escape `overflow: hidden` or `z-index` stacking contexts (modals, tooltips, toasts).

**Trap:** events bubble through the **React tree**, not the DOM tree. A click in a portaled modal bubbles to the React parent's `onClick`, even though the DOM node lives elsewhere. Context also flows through portals.

### Q4.3 \[I\] Refs, `forwardRef` and `useImperativeHandle`

In React 19, `ref` is a regular prop on function components; `forwardRef` still works but is no longer needed.

```jsx
function VideoPlayer({ src, ref }) {
  const videoRef = useRef(null);
  useImperativeHandle(ref, () => ({
    play: () => videoRef.current.play(),
    pause: () => videoRef.current.pause(),
  }), []);
  return <video ref={videoRef} src={src} />;
}

const playerRef = useRef(null);
<VideoPlayer ref={playerRef} src="/intro.mp4" />
<button onClick={() => playerRef.current.play()}>Play</button>
```

**Why expose a narrow handle?** It keeps the child's DOM private and the API stable. Use imperative handles only for actions that are not expressible as state: focus, scroll, play, measure, open a native dialog.

### Q4.4 \[I\] Error boundaries — what do they catch and not catch?

An error boundary catches errors **during render, in lifecycle methods and in constructors** of its descendants, then renders a fallback.

They do **not** catch errors in: event handlers, async code (timeouts, promises outside render), SSR, or the boundary itself.

There is still no hook-based error boundary in React; you write a class or use `react-error-boundary`.

```jsx
class ErrorBoundary extends React.Component {
  state = { error: null };
  static getDerivedStateFromError(error) { return { error }; }
  componentDidCatch(error, info) { reportError(error, info.componentStack); }
  render() {
    if (this.state.error) return this.props.fallback({ error: this.state.error, reset: () => this.setState({ error: null }) });
    return this.props.children;
  }
}
```

React 19 adds root options `onCaughtError`, `onUncaughtError`, `onRecoverableError` on `createRoot` / `hydrateRoot` for central reporting, and no longer double-logs errors.

**Async errors:** to route an error from an event handler into a boundary, `setState(() => { throw error; })`, or use an Action (errors thrown inside Actions passed to transitions reach the nearest boundary).

### Q4.5 \[S\] How does Suspense work?

Suspense lets a component "wait" and declares the loading UI at a boundary.

&#91;embedded content: Suspense reveal · 3 frames\]

Each boundary decides what the user sees while its children wait, so placing boundaries is a UX decision.

```jsx
<Suspense fallback={<PageSkeleton />}>
  <ProfileHeader />
  <Suspense fallback={<PostsSkeleton />}>
    <Posts />
  </Suspense>
</Suspense>
```

What can suspend (stable): `lazy()` components, `use(promise)` with a cached promise, Suspense-enabled frameworks/libraries (Next.js RSC, TanStack Query `useSuspenseQuery`, Relay).

**Behaviour to know:**

- Siblings inside one boundary reveal together.
- Nested boundaries reveal outside-in as data arrives.
- If an already-visible boundary suspends during a **transition**, React keeps showing the old UI instead of the fallback (no jarring spinner).
- React 19 "pre-warms" siblings: once a component suspends, React commits the fallback immediately, then renders siblings in the background to start their data requests.

### Q4.6 \[I\] `React.lazy` and code splitting

```jsx
const Settings = lazy(() => import('./Settings'));
<Suspense fallback={<Spinner />}><Settings /></Suspense>
```

- `lazy` must be declared at module top level; declaring it inside a component re-creates it every render and resets state.
- The module must have a default export (or map: `import('./x').then(m => ({ default: m.Settings }))`).
- Split at route level first; preload on hover/intent (`const load = () => import('./Settings')`).

### Q4.7 \[S\] Compound components

Components that share implicit state through Context, giving consumers a flexible, declarative API.

```jsx
const TabsCtx = createContext(null);

function Tabs({ defaultValue, children }) {
  const [value, setValue] = useState(defaultValue);
  return <TabsCtx value={{ value, setValue }}>{children}</TabsCtx>;
}
Tabs.List = ({ children }) => <div role="tablist">{children}</div>;
Tabs.Tab = ({ value, children }) => {
  const ctx = useContext(TabsCtx);
  return <button role="tab" aria-selected={ctx.value === value} onClick={() => ctx.setValue(value)}>{children}</button>;
};
Tabs.Panel = ({ value, children }) => {
  const ctx = useContext(TabsCtx);
  return ctx.value === value ? <div role="tabpanel">{children}</div> : null;
};

<Tabs defaultValue="a">
  <Tabs.List><Tabs.Tab value="a">Account</Tabs.Tab><Tabs.Tab value="b">Billing</Tabs.Tab></Tabs.List>
  <Tabs.Panel value="a">…</Tabs.Panel>
  <Tabs.Panel value="b">…</Tabs.Panel>
</Tabs>
```

**Why:** consumers control layout and markup without a giant prop API (`tabs=[{label, content, icon, disabled…}]`). Radix and React Aria use this pattern. Part 14 builds the fully accessible version.

### Q4.8 \[I\] HOCs vs render props vs hooks

| Pattern | Example | Pros | Cons |
| --- | --- | --- | --- |
| HOC | `withAuth(Page)` | Wraps any component; good for cross-cutting concerns at boundaries | Wrapper hell, prop name collisions, opaque, ref/static forwarding |
| Render prop | `<Mouse>{pos => …}</Mouse>` | Explicit data flow | Nesting pyramids, inline functions |
| Custom hook | `const pos = useMouse()` | Composable, explicit, no extra tree nodes | Can't wrap markup; logic only |

Modern default: **hooks for logic, components for markup**. HOCs remain fine for route guards or instrumentation. Render props remain useful when a library must hand back render-time data (virtualisers, headless tables).

### Q4.9 \[S\] Controlled-or-uncontrolled component pattern

Reusable components should support both modes, like native inputs.

```jsx
function useControllableState({ value, defaultValue, onChange }) {
  const [internal, setInternal] = useState(defaultValue);
  const isControlled = value !== undefined;
  const current = isControlled ? value : internal;
  const setValue = useCallback(next => {
    const resolved = typeof next === 'function' ? next(current) : next;
    if (!isControlled) setInternal(resolved);
    onChange?.(resolved);
  }, [isControlled, current, onChange]);
  return [current, setValue];
}

function Toggle({ checked, defaultChecked = false, onCheckedChange }) {
  const [on, setOn] = useControllableState({ value: checked, defaultValue: defaultChecked, onChange: onCheckedChange });
  return <button role="switch" aria-checked={on} onClick={() => setOn(v => !v)}>{on ? 'On' : 'Off'}</button>;
}
```

Don't switch between modes during a component's lifetime — warn in development if `value` flips between defined and `undefined`.

### Q4.10 \[S\] `<Activity>` (stable in 19.2)

`<Activity mode="hidden">` hides a subtree while **preserving its state and DOM**, unmounting its effects, and rendering updates at low priority. Use it for tabs, back-navigation and pre-rendering likely-next screens.

```jsx
<Activity mode={tab === 'inbox' ? 'visible' : 'hidden'}><Inbox /></Activity>
<Activity mode={tab === 'drafts' ? 'visible' : 'hidden'}><Drafts /></Activity>
```

Compared with `{tab === 'inbox' && <Inbox />}`, scroll position and input state survive tab switches. Compared with CSS `display:none`, effects (subscriptions, timers) are cleaned up while hidden.

### Q4.11 \[S\] `<ViewTransition>` and Fragment refs (stable in 19.3)

Both graduated from experimental in React 19.3 (September 2026), so expect them in current interviews.

**`<ViewTransition>`** wraps the browser's View Transition API. It animates its children as they enter, exit or update — but **only when the change happens inside a Transition** (`startTransition`, `useDeferredValue`, or a Suspense reveal). A plain urgent `setState` does not animate.

```jsx
import { ViewTransition, startTransition, addTransitionType } from 'react';

function Details({ isOpen, onToggle }) {
  return (
    <>
      <button onClick={() => startTransition(() => { addTransitionType('open-panel'); onToggle(); })}>Toggle</button>
      {isOpen && <ViewTransition><Panel /></ViewTransition>}
    </>
  );
}
```

`addTransitionType` labels a Transition (for example "forward" vs "back" navigation) so you can apply different CSS animation classes per type. It is DOM-only.

**Fragment refs** let you attach a ref to `<Fragment>` and work with its DOM children as a group, without adding a wrapper `<div>` that breaks flex or grid layouts. `ref.current` is a `FragmentInstance` with APIs for events, focus, observers, measurement and scrolling.

```jsx
import { Fragment, useRef } from 'react';

function Toolbar({ children }) {
  const groupRef = useRef(null);   // FragmentInstance — no extra DOM node
  return <Fragment ref={groupRef}>{children}</Fragment>;
}
```

**Interview angle:** before 19.3 you'd answer "add a wrapper div" or "use a ref per child"; now you can say Fragment refs remove that workaround. For animations, the old answer was a library (Framer Motion) or manual `document.startViewTransition`; now React coordinates it with Transitions and Suspense.

### Q4.12 \[I\] Class component lifecycles (legacy, still asked)

Older codebases and some interviewers still ask for lifecycle order and hook equivalents.

**Mount:** `constructor` → `static getDerivedStateFromProps` → `render` → (DOM commit) → `componentDidMount`.

**Update:** `getDerivedStateFromProps` → `shouldComponentUpdate` → `render` → `getSnapshotBeforeUpdate` → (DOM commit) → `componentDidUpdate(prevProps, prevState, snapshot)`.

**Unmount:** `componentWillUnmount`. **Errors:** `static getDerivedStateFromError` (render a fallback), `componentDidCatch` (log).

| Class lifecycle | Hook-era equivalent | Notes |
| --- | --- | --- |
| `constructor` / `this.state` | `useState` (lazy initialiser) |  |
| `componentDidMount` | `useEffect(fn, [])` | Strict Mode runs it twice in dev |
| `componentDidUpdate` | `useEffect(fn, [deps])` | Effects synchronise; no "prevProps" needed in most cases |
| `componentWillUnmount` | Effect cleanup | Cleanup also runs before each re-run |
| `shouldComponentUpdate` / `PureComponent` | `React.memo` | Or the React Compiler |
| `getDerivedStateFromProps` | Compute during render, or reset with `key` | Rarely needed |
| `getSnapshotBeforeUpdate` | No direct hook; closest is `useLayoutEffect` plus a ref | E.g. preserving scroll position in a chat list |
| `getDerivedStateFromError` / `componentDidCatch` | **None** — error boundaries still need a class | Or `react-error-boundary` |

**Traps:** `this.setState(updater, callback)` — the callback runs after the commit, the class equivalent of an effect. `UNSAFE_componentWillMount`, `UNSAFE_componentWillReceiveProps` and `UNSAFE_componentWillUpdate` are deprecated because they run in the render phase, which concurrent rendering may repeat. Forgetting to `bind` methods (or using arrow class fields) causes `this` to be `undefined` in handlers.

### Tricky follow-ups

- *Does an error boundary catch an error from `useEffect`?* Yes — effects run as part of the commit lifecycle, so errors thrown there propagate to the boundary. Errors inside an async callback started by the effect do not.
- *Does Context skip `memo`?* Yes. A memoised component between provider and consumer does not stop the consumer re-rendering.
- *Can you lazy-load a named export?* Only by mapping it to `default`.

### Quick revision

- Context = DI for low-frequency values; memoise `value`; split contexts; no selectors.
- Portals change DOM placement, not React tree: events and context follow the React tree.
- `ref` is a prop in 19; expose narrow imperative handles.
- Error boundaries catch render/lifecycle errors, not handlers/async; root error callbacks in 19.
- Suspense: nearest boundary shows fallback; transitions keep old UI; nested boundaries reveal progressively.
- Compound components > mega-prop APIs; hooks > HOCs for logic.
- `<Activity>` hides UI but keeps state.

## Part 5 — State Management

The senior answer to "which state library?" is: first classify the state, then pick the smallest tool that fits each class. Most apps need a server-cache library and very little global client state.

### Q5.1 \[S\] How do you decide where state lives?

&#91;embedded content: Where state lives · 6 questions\]

Stop at the first yes; most state in a typical app ends in the top four answers.

| Kind of state | Example | Best home |
| --- | --- | --- |
| Local UI | Dropdown open, input text | `useState` in the component |
| Shared by siblings | Selected row + detail panel | Lift to nearest common parent |
| Shareable / bookmarkable | Filters, sort, page, tab | URL search params |
| Low-frequency app-wide | Theme, locale, current user | Context |
| High-frequency or complex client | Editor state, cart, canvas, wizard | Zustand / Redux Toolkit / Jotai |
| Server data | Users, orders, products | TanStack Query / SWR / RTK Query / framework loaders / RSC |
| Form | Field values, errors, touched | Form library or uncontrolled + actions |
| Derived | Totals, filtered lists | **Not state** — compute in render |

**State colocation:** keep state as close as possible to where it's used. Lifting too high makes everything re-render and couples unrelated components.

### Q5.2 \[I\] Why is duplicated or derived state a bug?

```jsx
// BAD: two sources of truth that drift
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
useEffect(() => setTotal(items.reduce((s, i) => s + i.price, 0)), [items]);   // extra render + stale frame

// GOOD
const total = items.reduce((s, i) => s + i.price, 0);

// BAD: storing the selected object (goes stale when items update)
const [selected, setSelected] = useState(items[0]);
// GOOD: store the id, derive the object
const [selectedId, setSelectedId] = useState(items[0]?.id);
const selected = items.find(i => i.id === selectedId);
```

### Q5.3 \[S\] Context vs a state library — when is Context not enough?

Context has no selector: every consumer re-renders when the value changes. With frequent updates or large consumer trees, that becomes the bottleneck. Stores built on `useSyncExternalStore` let each component subscribe to a **slice** and re-render only when that slice changes.

### Q5.4 \[S\] Redux Toolkit — what does it give you, and when is it worth it?

RTK is the official, modern way to write Redux: `configureStore`, `createSlice` (Immer-powered "mutating" reducers), `createAsyncThunk`, `createEntityAdapter`, and **RTK Query** for server state.

```jsx
const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    added(state, action) { state.items.push(action.payload); },        // Immer makes this immutable
    removed(state, action) { state.items = state.items.filter(i => i.id !== action.payload); },
  },
});
export const { added, removed } = cartSlice.actions;
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });

// component
const count = useSelector(s => s.cart.items.length);
const dispatch = useDispatch();
```

**Pick Redux when:** large teams need strict conventions, you want time-travel debugging and an action log, many features read and write shared client state, or middleware (undo, sync, analytics) matters.

**Selector traps:** `useSelector(s => s.cart.items.filter(...))` returns a new array each time → re-renders on every store change. Use `createSelector` (memoised) or return primitives.

### Q5.5 \[S\] Zustand — why is it popular?

A tiny store with hooks and selectors, no provider, no boilerplate.

```jsx
const useCart = create((set, get) => ({
  items: [],
  add: item => set(s => ({ items: [...s.items, item] })),
  total: () => get().items.reduce((sum, i) => sum + i.price, 0),
}));

const count = useCart(s => s.items.length);       // re-renders only when length changes
const add = useCart(s => s.add);
// Selecting several fields → use useShallow to avoid new-object re-renders
const { items, add } = useCart(useShallow(s => ({ items: s.items, add: s.add })));
```

**Trade-offs:** less structure than Redux (teams must agree conventions); global module stores need care in SSR (create a store per request and provide it via Context in Next.js).

Others to name: **Jotai** (atomic, bottom-up), **Valtio** (proxy-based mutable), **MobX** (observable, fine-grained), **XState** (explicit state machines for complex flows).

### Q5.6 \[S\] Server state vs client state — why separate them?

Server state is a **cache of data you don't own**. It can go stale, be changed by others, needs deduping, retries, background refresh, pagination and invalidation. Putting it in Redux/useState means re-implementing all of that.

```jsx
function useTodos(filter) {
  return useQuery({
    queryKey: ['todos', filter],                     // cache key; changes → new request
    queryFn: ({ signal }) => api.getTodos(filter, { signal }),   // signal enables cancellation
    staleTime: 30_000,
  });
}

const queryClient = useQueryClient();
const addTodo = useMutation({
  mutationFn: api.addTodo,
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['todos'] }),
});
```

Key concepts: **query keys** (cache identity), **staleTime** (how long data is fresh) vs **gcTime** (how long unused data stays cached), **invalidation** after mutations, **refetch on focus/reconnect**, request **deduplication**.

### Q5.7 \[S\] Optimistic updates — how, and what can go wrong?

Update the UI before the server confirms, then reconcile.

```jsx
useMutation({
  mutationFn: api.toggleTodo,
  onMutate: async ({ id }) => {
    await queryClient.cancelQueries({ queryKey: ['todos'] });       // avoid an in-flight fetch overwriting us
    const previous = queryClient.getQueryData(['todos']);
    queryClient.setQueryData(['todos'], old => old.map(t => t.id === id ? { ...t, done: !t.done } : t));
    return { previous };
  },
  onError: (_err, _vars, ctx) => queryClient.setQueryData(['todos'], ctx.previous),  // rollback
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['todos'] }),          // re-sync with truth
});
```

React 19's `useOptimistic` does the same at component level for Actions (Part 6).

**Risks:** rollback flicker, conflicting concurrent mutations, irreversible actions (payments — never optimistic), and user confusion when a rollback happens silently. Always show an error.

### Q5.8 \[S\] Immutability — why does React require it?

React detects change with `Object.is` on state and shallow compares in `memo`. Mutating an object keeps the same reference, so React sees "no change" and skips the render, and memoised children show stale data.

```jsx
// BAD
user.address.city = 'Dhaka'; setUser(user);
// GOOD
setUser(u => ({ ...u, address: { ...u.address, city: 'Dhaka' } }));
// Or with Immer
setUser(produce(draft => { draft.address.city = 'Dhaka'; }));
```

Array cheat sheet: add → `[...a, x]`; remove → `a.filter`; replace → `a.map`; insert → `[...a.slice(0, i), x, ...a.slice(i)]`; sort → `a.toSorted()` (or `[...a].sort()`).

### Quick revision

- Classify state first: local, lifted, URL, context, client store, server cache, form, derived.
- Derived values are computed, never stored. Store ids, not copies of objects.
- Context has no selectors; stores with `useSyncExternalStore` do.
- RTK for structure at scale; Zustand for lightweight global client state.
- Server state belongs in a cache library with keys, staleness and invalidation.
- Optimistic: snapshot, apply, rollback on error, re-sync on settle.
- Never mutate state; new references signal change.

## Part 6 — Forms & Data Fetching

Forms and fetching are where most production bugs live: race conditions, double submits, lost errors, and loading states that lie.

### Q6.1 \[I\] How should you manage form state and validation?

Three tiers, in order of complexity:

1. **Uncontrolled + `FormData` + native validation** (`required`, `type="email"`, `pattern`) — smallest, fastest, works with React 19 form actions and progressive enhancement.
2. **Controlled with `useState`/`useReducer`** — for live validation, dependent fields, formatting masks.
3. **A form library** — React Hook Form (uncontrolled-first, few re-renders), TanStack Form (type-safe, headless), Formik (legacy, controlled, re-renders more). Pair with a schema validator (Zod, Valibot, Yup) and share the schema with the server.

**Validation UX rules:** validate on blur or submit, not every keystroke, for most fields; re-validate on change after the first error; show errors next to fields with `aria-invalid` and `aria-describedby`; focus the first invalid field on submit; always re-validate on the server.

### Q6.2 \[S\] React 19 Actions, `useActionState` and `useFormStatus`

An **Action** is an async function run in a transition. Passing a function to `<form action>` makes React handle pending state, errors and form reset.

```jsx
async function updateName(prevState, formData) {
  const name = formData.get('name');
  if (!name) return { error: 'Name is required' };
  try {
    await api.updateName(name);
    return { error: null, saved: true };
  } catch (e) {
    return { error: e.message };
  }
}

function NameForm() {
  const [state, formAction, isPending] = useActionState(updateName, { error: null });
  return (
    <form action={formAction}>
      <input name="name" aria-invalid={!!state.error} aria-describedby="name-err" />
      <SubmitButton />
      {state.error && <p id="name-err" role="alert">{state.error}</p>}
    </form>
  );
}

function SubmitButton() {
  const { pending } = useFormStatus();          // reads the PARENT form's status
  return <button disabled={pending}>{pending ? 'Saving…' : 'Save'}</button>;
}
```

**Facts interviewers check:**

- `useFormStatus` must be called in a component **rendered inside** the `<form>`, not in the component that renders the form.
- Uncontrolled fields reset automatically after a successful form action. Use `requestFormReset` for manual control.
- With a Server Function as the action (Next.js), the form submits even before JS loads (progressive enhancement).
- Actions are queued sequentially per `useActionState`.

### Q6.3 \[S\] `useOptimistic`

```jsx
function Thread({ messages, sendMessage }) {
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (current, newText) => [...current, { id: crypto.randomUUID(), text: newText, sending: true }]
  );
  async function action(formData) {
    const text = formData.get('text');
    addOptimistic(text);              // shown immediately
    await sendMessage(text);          // when the action settles, optimistic state is discarded
  }
  return (
    <>
      {optimistic.map(m => <p key={m.id}>{m.text}{m.sending && ' (sending…)'}</p>)}
      <form action={action}><input name="text" /><button>Send</button></form>
    </>
  );
}
```

The optimistic value lives only while the Action is pending; afterwards React renders the real `messages`. If the parent did not update `messages`, the item disappears — which is your rollback.

### Q6.4 \[I\] Fetching in `useEffect` correctly — cancellation and race conditions

**The race:** user types "re", then "react". Request "re" resolves *after* "react" and overwrites the correct results.

```jsx
function useSearch(query) {
  const [state, setState] = useState({ status: 'idle', data: null, error: null });
  useEffect(() => {
    if (!query) { setState({ status: 'idle', data: null, error: null }); return; }
    const controller = new AbortController();
    setState(s => ({ ...s, status: 'loading' }));
    fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
      .then(r => { if (!r.ok) throw new Error(`HTTP ${r.status}`); return r.json(); })
      .then(data => setState({ status: 'success', data, error: null }))
      .catch(error => {
        if (error.name === 'AbortError') return;            // superseded — ignore
        setState({ status: 'error', data: null, error });
      });
    return () => controller.abort();                        // cancels the previous request
  }, [query]);
  return state;
}
```

**Why both abort and ignore?** Aborting saves bandwidth; the `AbortError` check ensures no stale write. If the API can't be aborted, use an `ignore` flag set in cleanup.

**Senior answer:** effects-based fetching has no caching, no dedupe, and creates **waterfalls** (parent fetches, renders child, child fetches). In production prefer a framework loader, Server Components, or TanStack Query/SWR.

### Q6.5 \[S\] Data fetching patterns compared

| Pattern | Where it fetches | Pros | Cons |
| --- | --- | --- | --- |
| Fetch-on-render (`useEffect`) | After component mounts | Simple | Waterfalls, races, no cache, spinner soup |
| Fetch-then-render (route loader) | Before route renders | No waterfalls; parallel | Whole route waits for slowest request |
| Render-as-you-fetch (Suspense) | Start fetch early, read with `use`/Suspense | Parallel + progressive reveal | Requires a cache/framework |
| Server Components | On the server during render | No client JS for data, close to DB, streams | Needs a framework; server/client boundary design |
| Query library | Cached client fetch | Dedupe, retries, stale-while-revalidate | Another dependency; client-side only by default |

### Q6.6 \[I\] Loading and error states that don't lie

- Model status explicitly: `idle | loading | success | error` (a discriminated union), not three booleans that can disagree.
- Distinguish **initial load** (skeleton) from **refetch** (keep data, subtle indicator).
- Empty state is not an error; error state should offer retry.
- Avoid spinner flash: delay the spinner \~150–300 ms, or rely on transitions to keep old content.
- Layout-stable skeletons prevent CLS.

### Q6.7 \[S\] Form libraries — trade-offs

| Library | Model | Strength | Weakness |
| --- | --- | --- | --- |
| React Hook Form | Uncontrolled + refs, subscriptions | Very few re-renders, small, great with Zod | Controlled third-party inputs need `Controller` |
| TanStack Form | Headless, signals-based store | Deep type safety, framework-agnostic, async validation | Newer, more verbose |
| Formik | Controlled, context | Familiar | Re-renders whole form, slower on big forms, less active |
| Native + Actions | DOM + `FormData` | Zero deps, progressive enhancement, server validation | Complex client interactions get manual |

### Quick revision

- Start uncontrolled + native validation; add control or a library only when needed.
- Validate client-side for UX and server-side for truth; share schemas.
- Actions: `<form action>`, `useActionState` (state + pending), `useFormStatus` (child of form), `useOptimistic`.
- Every effect fetch needs abort/ignore cleanup.
- Prefer loaders, RSC or a query library to effect fetching; avoid waterfalls.
- Model status as a union; keep stale data visible during refetch.

## Part 7 — Performance

Measure first, then fix the cause, then memoise only what the profiler proves is slow. Most React performance problems are **state placed too high**, **expensive work in render**, **unvirtualised long lists**, or **too much JavaScript shipped**.

### Q7.1 \[S\] How do you find out why a component re-renders?

1. React DevTools Profiler → enable "Record why each component rendered while profiling".
2. Look at the flame graph for wide (slow) and frequent (many commits) components.
3. Chrome Performance panel — React 19.2 adds **Performance Tracks** (Scheduler and Components tracks) so you see React work next to browser work.
4. Quick check: `console.count('Row render')` or `<Profiler id onRender>` in code.
5. Production: measure INP/LCP with `web-vitals` and RUM, not just dev profiles.

### Q7.2 \[I\] `React.memo` — how it works and when it fails

`memo(Component)` skips re-rendering when props are shallow-equal (`Object.is` per prop).

It silently fails when a parent passes:

- Inline objects/arrays: `style={{ color: 'red' }}`, `items={list.filter(...)}`
- Inline functions: `onClick={() => select(id)}`
- `children` JSX (a new element object every render)

```jsx
const Row = memo(function Row({ item, onSelect }) { /* … */ });

function List({ items }) {
  const [selected, setSelected] = useState(null);
  const onSelect = useCallback(id => setSelected(id), []);  // stable
  return items.map(item => <Row key={item.id} item={item} onSelect={onSelect} />);
}
```

Custom comparator: `memo(Row, (prev, next) => prev.item.id === next.item.id && prev.item.version === next.item.version)` — risky, because forgetting a prop causes stale UI.

### Q7.3 \[S\] Cheaper fixes before memoisation

**Move state down** — isolate fast-changing state into a small component.

```jsx
// BEFORE: typing re-renders <ExpensiveChart />
function Page() {
  const [text, setText] = useState('');
  return <><input value={text} onChange={e => setText(e.target.value)} /><ExpensiveChart /></>;
}
// AFTER
function SearchBox() { const [text, setText] = useState(''); return <input value={text} onChange={e => setText(e.target.value)} />; }
function Page() { return <><SearchBox /><ExpensiveChart /></>; }
```

**Lift content up** — pass slow subtrees as `children`; they were created by the parent and keep the same element reference.

```jsx
function ScrollTracker({ children }) {
  const [y, setY] = useState(0);
  useEffect(() => { const h = () => setY(scrollY); addEventListener('scroll', h); return () => removeEventListener('scroll', h); }, []);
  return <div><ProgressBar y={y} />{children}</div>;   // children don't re-render on scroll
}
```

### Q7.4 \[S\] What does the React Compiler change?

The React Compiler (stable 1.0, build-time Babel/SWC plugin, works with React 17+ via a runtime package, best with 19) analyses components and hooks and **auto-memoises** values, callbacks and JSX at a finer grain than you would by hand — even after early returns.

- Requires code that follows the Rules of React (pure render, no mutation of props/state, no reading refs in render). Violations make it skip that component.
- `eslint-plugin-react-hooks` includes compiler-powered rules that flag these violations.
- You can opt a component out with `"use no memo"`.
- Existing `useMemo`/`useCallback` are fine to keep; new code needs far fewer.

**Interview framing:** the compiler removes *re-render* cost, not *render* cost. A genuinely slow component (10k rows, heavy calculations) still needs virtualisation, better algorithms or moving work to the server.

### Q7.5 \[S\] Virtualisation for large lists

Rendering 10,000 DOM rows costs memory, layout and paint. Virtualisation renders only visible rows plus overscan, using spacer padding for the rest.

```jsx
import { useVirtualizer } from '@tanstack/react-virtual';

function BigList({ rows }) {
  const parentRef = useRef(null);
  const v = useVirtualizer({ count: rows.length, getScrollElement: () => parentRef.current, estimateSize: () => 36, overscan: 8 });
  return (
    <div ref={parentRef} style={{ height: 480, overflow: 'auto' }}>
      <div style={{ height: v.getTotalSize(), position: 'relative' }}>
        {v.getVirtualItems().map(item => (
          <div key={rows[item.index].id} style={{ position: 'absolute', top: 0, transform: `translateY(${item.start}px)`, height: item.size, width: '100%' }}>
            {rows[item.index].name}
          </div>
        ))}
      </div>
    </div>
  );
}
```

**Trade-offs:** Ctrl+F can't find off-screen rows; screen readers see a partial list (use `aria-rowcount`/`aria-rowindex`); dynamic heights need measurement; sticky headers and keyboard focus need care. Alternatives: pagination, "load more", CSS `content-visibility: auto`.

### Q7.6 \[S\] Bundle size and code splitting

- Analyse with `rollup-plugin-visualizer`, `@next/bundle-analyzer`, or `source-map-explorer`.
- Split by route first, then by heavy, rarely-used widgets (editors, charts, maps).
- Prefer ESM, tree-shakeable libraries; import narrowly (`lodash-es/debounce`, `date-fns` functions).
- Move non-interactive UI to Server Components — zero client JS.
- Preload on intent; prefetch likely next routes.
- Set a performance budget in CI (bundle size check).

### Q7.7 \[S\] Avoiding unnecessary effects (a performance and correctness issue)

Every "effect that sets state" causes an extra render pass and a frame of stale UI.

```jsx
// BAD: effect chain
useEffect(() => setFiltered(items.filter(i => i.match(q))), [items, q]);
// GOOD: derive (memoise if expensive)
const filtered = useMemo(() => items.filter(i => i.match(q)), [items, q]);
```

### Q7.8 \[S\] Keeping interactions responsive (INP)

- Wrap expensive non-urgent updates in `startTransition`.
- `useDeferredValue` + `memo` for expensive consumers of fast input.
- Break long tasks; move heavy computation to a Web Worker.
- Debounce/throttle high-frequency events (scroll, resize, input → network).
- Avoid layout thrashing: batch DOM reads before writes in layout effects.

### Quick revision

- Profile first (DevTools Profiler, Performance Tracks, RUM).
- Move state down / lift content up before reaching for memo.
- `memo` fails with inline objects, functions and children.
- React Compiler auto-memoises; it doesn't make slow renders fast.
- Virtualise long lists; mind a11y and find-in-page.
- Split by route, analyse bundles, push static UI to the server.
- Derived state in render, not effects.

## Part 8 — Modern React & Frameworks

The Server Components *model* is part of React; using it requires a framework or bundler integration (Next.js App Router is the most common; React Router and others also integrate). Always say which context you mean.

### Q8.1 \[I\] CSR vs SSR vs SSG vs ISR vs streaming

| Strategy | When HTML is produced | Good for | Cost |
| --- | --- | --- | --- |
| CSR | In the browser after JS loads | Dashboards behind login | Slow first paint, weak SEO |
| SSR | On each request | Personalised, SEO, fresh data | Server cost, TTFB depends on slowest data |
| SSG / static | At build time | Docs, marketing, blogs | Stale until rebuild |
| ISR / revalidation | Static, regenerated on interval or on demand | Catalogues, CMS pages | Briefly stale; framework-specific |
| Streaming SSR | On request, sent in chunks as data resolves | Mixed fast/slow data | Needs Suspense boundaries |
| Partial pre-rendering | Static shell at build + dynamic holes streamed per request | Mostly static pages with personalised islands | Newer; framework-specific |

### Q8.2 \[S\] What is hydration, and what is selective hydration?

Hydration attaches React to server-rendered HTML: React renders the same tree on the client, walks the existing DOM, attaches event listeners and state, but does not recreate nodes.

&#91;embedded content: Streaming SSR and selective hydration · server and browser\]

The user sees content after the first chunk, but can only interact with a boundary once it has hydrated.

**With streaming (`renderToPipeableStream` / `renderToReadableStream`):**

1. Server sends the HTML shell immediately with Suspense fallbacks.
2. As each boundary's data resolves, the server streams its HTML plus a tiny inline script that swaps it into place — before any React JS has loaded.
3. Client JS loads; `hydrateRoot` hydrates boundaries **independently**.
4. **Selective hydration:** if the user clicks inside a not-yet-hydrated boundary, React prioritises hydrating that one first and replays the event.

### Q8.3 \[S\] What causes hydration mismatches, and how do you fix them?

The client's first render must produce the same output as the server.

Common causes: `Date.now()`/`new Date().toLocaleString()` (timezone/locale), `Math.random()`, `typeof window !== 'undefined'` branches, reading `localStorage` during render, browser extensions injecting DOM, invalid HTML nesting (`<div>` inside `<p>`, `<a>` in `<a>`), and different data on server vs client.

```jsx
// Fix: render the client-only value after hydration
function LocalTime({ iso }) {
  const [text, setText] = useState(null);
  useEffect(() => setText(new Date(iso).toLocaleTimeString()), [iso]);
  return <time dateTime={iso}>{text ?? '—'}</time>;
}

// Or a hook that tells you if you're hydrated
const useIsClient = () => useSyncExternalStore(() => () => {}, () => true, () => false);
```

- For unavoidable text differences (a timestamp), `suppressHydrationWarning` on that one element (one level deep only).
- React 19 shows a single diff-style error for mismatches, and tolerates unexpected tags injected by third-party scripts/extensions in `<head>` and `<body>`.

**React 19.3 option — `browser()`:** react-dom now exports `browser()`. Calling `use(browser())` inside a `<Suspense>` boundary marks that subtree as browser-only: the server renders the fallback, and the client renders the subtree, without reporting a recoverable hydration error. Servers can observe these bail-outs with the `onBrowserBailout` option.

```jsx
import { use, Suspense } from 'react';
import { browser } from 'react-dom';

function LocalTime({ iso }) {
  use(browser());                                   // server: suspends → fallback; browser: continues
  return <time dateTime={iso}>{new Date(iso).toLocaleTimeString()}</time>;
}

<Suspense fallback={<time dateTime={iso}>—</time>}><LocalTime iso={iso} /></Suspense>
```

Use it for genuinely browser-only UI (locale/timezone formatting, `window` measurements, third-party widgets). Overusing it gives up the SEO and first-paint benefits of SSR.

### Q8.4 \[S\] What are React Server Components?

Server Components run **only on the server** (at build time or per request). Their code never ships to the browser. They can be `async`, read databases and files directly, and pass rendered output plus serialisable props to Client Components.

&#91;embedded content: Server and Client Components · one product page\]

Tabs is a client component, yet Reviews stays a server component because Page renders it and passes it in as children.

```jsx
// app/products/[id]/page.jsx — Server Component (default in Next.js App Router)
import { db } from '@/lib/db';
import AddToCart from './AddToCart';

export default async function ProductPage({ params }) {
  const { id } = await params;
  const product = await db.product.findUnique({ where: { id } });
  return (
    <article>
      <h1>{product.name}</h1>
      <Markdown source={product.description} />    {/* heavy lib stays on server */}
      <AddToCart productId={product.id} price={product.price} />
    </article>
  );
}

// AddToCart.jsx — Client Component
'use client';
export default function AddToCart({ productId, price }) {
  const [qty, setQty] = useState(1);
  return <button onClick={() => addToCart(productId, qty)}>Add · {price * qty}</button>;
}
```

|  | Server Component | Client Component |
| --- | --- | --- |
| Runs | Server only | Server (SSR) **and** client |
| State, effects, event handlers | No | Yes |
| Browser APIs | No | Yes |
| Direct DB / secrets | Yes | Never |
| Async component | Yes | No (use `use` / a library) |
| Ships JS | No | Yes |

**Rules interviewers probe:**

- `'use client'` marks a **module boundary**: that file and everything it imports become client code. It does not mean "client-only rendering" — client components are still SSR'd.
- A Client Component cannot import a Server Component, but it can **receive one as `children` or a prop** (composition is the escape hatch).
- Props crossing server → client must be serialisable: primitives, plain objects/arrays, Dates, Maps/Sets, promises, JSX, and Server Functions. **Not** class instances or ordinary functions.
- Push `'use client'` to the leaves to minimise client JS.
- Use the `server-only` package to make accidental client imports of secret-handling modules fail at build.

### Q8.5 \[S\] RSC vs SSR — aren't they the same?

No. **SSR** turns components into HTML for the first load; the components still ship and hydrate. **RSC** produces a serialised component tree (the RSC payload) whose server parts never ship as JS and are never hydrated. Next.js uses both: RSC payload → SSR to HTML → hydrate only Client Components. On client navigations, only the RSC payload is fetched, preserving client state.

### Q8.6 \[S\] Server Functions / Server Actions

A function marked `'use server'` runs on the server but can be called from the client (React turns it into a reference + network call). Used as a form action, it is a Server Action.

```jsx
// app/actions.js
'use server';
import { z } from 'zod';
import { revalidatePath } from 'next/cache';

const Schema = z.object({ title: z.string().min(1).max(200) });

export async function createPost(prevState, formData) {
  const session = await auth();                         // ALWAYS authenticate inside
  if (!session) return { error: 'Unauthorized' };
  const parsed = Schema.safeParse({ title: formData.get('title') });  // ALWAYS validate
  if (!parsed.success) return { error: parsed.error.issues[0].message };
  await db.post.create({ data: { ...parsed.data, authorId: session.userId } });
  revalidatePath('/posts');
  return { error: null };
}
```

**Security point (senior must-know):** every Server Function is a **public HTTP endpoint**. Never trust arguments; check auth and authorisation inside each one; never close over secrets you don't intend to expose. Keep React and the framework patched — RSC-related vulnerabilities have been disclosed and patched across React 19.x releases.

### Q8.7 \[S\] Next.js App Router rendering and caching strategies

Versions and defaults change between Next.js majors — state the version you used and verify against current docs.

- **Layouts** persist across navigations; **pages** re-render. `loading.js` creates a Suspense boundary; `error.js` an error boundary.
- **Static vs dynamic:** a route becomes dynamic when it reads request data (`cookies()`, `headers()`, search params) or opts out of caching.
- **Caching/revalidation:** time-based (`revalidate`) or on-demand (`revalidatePath`, `revalidateTag`); newer versions add explicit cache directives (`'use cache'`).
- **Parallel data fetching:** start promises together, `await Promise.all`, or pass promises down and read them with `use` inside Suspense.
- **Streaming:** wrap slow sections in `<Suspense>` so the shell is not blocked.
- **Middleware/proxy:** edge redirects and auth gating — but never as the only auth check.

### Q8.8 \[S\] When *not* to use Server Components / SSR?

- Highly interactive apps behind login (editors, design tools) gain little; a SPA with good code splitting may be simpler.
- Teams without server operations capacity.
- Offline-first apps.
- When latency to the server is the bottleneck and data is already on the client.

### Quick revision

- SSR = HTML first, still hydrates; RSC = server-only components, zero JS; usually combined.
- Streaming + Suspense = shell first, chunks later; selective hydration prioritises user input.
- Hydration mismatch = different first render; fix with post-mount effects, `useSyncExternalStore`, valid HTML.
- `'use client'` is a module boundary; pass server components to client ones via children.
- Server Functions are public endpoints: authenticate, authorise, validate inside.
- Framework caching is version-specific — say which version.

## Part 9 — Testing & Quality

Test behaviour the user can observe, not implementation details. The more your tests resemble how the software is used, the more confidence they give.

### Q9.1 \[S\] What is your testing strategy for a React app?

The "testing trophy" weighting:

| Layer | Tool | What it covers | Share of effort |
| --- | --- | --- | --- |
| Static | TypeScript, ESLint (hooks + jsx-a11y + compiler rules) | Typos, wrong props, hook rules | Always on |
| Unit | Vitest / Jest | Pure functions, reducers, hooks with logic | Small |
| Integration | React Testing Library + MSW | A feature through its UI with mocked network | **Largest** |
| End-to-end | Playwright / Cypress | Critical journeys in a real browser against a real backend | Few, high-value |
| Visual / a11y | Storybook + Chromatic, axe | Regressions in design system | Targeted |

### Q9.2 \[I\] React Testing Library — principles and an example

Query the way users find things: `getByRole` > `getByLabelText` > `getByText` > `getByTestId` (last resort). Use `user-event` for realistic interactions. Use `findBy*` for async appearance.

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('shows an error when email is invalid', async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();
  render(<SignupForm onSubmit={onSubmit} />);

  await user.type(screen.getByLabelText(/email/i), 'not-an-email');
  await user.click(screen.getByRole('button', { name: /sign up/i }));

  expect(await screen.findByRole('alert')).toHaveTextContent(/valid email/i);
  expect(onSubmit).not.toHaveBeenCalled();
});
```

**Anti-patterns:** asserting on state values or component instances, snapshotting whole trees, `container.querySelector`, wrapping everything in `act()` manually (RTL already does), arbitrary `waitFor` with side effects inside.

### Q9.3 \[S\] Mocking APIs with MSW

Mock at the **network layer** so the component, the fetch code and the cache library all run for real.

```js
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

export const server = setupServer(
  http.get('/api/users/:id', ({ params }) => HttpResponse.json({ id: params.id, name: 'Ada' }))
);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

// Per-test override for the error path
server.use(http.get('/api/users/:id', () => new HttpResponse(null, { status: 500 })));
```

The same handlers can power Storybook and local development.

### Q9.4 \[S\] Testing custom hooks, async and timers

```jsx
import { renderHook, act } from '@testing-library/react';

test('useDebounce', () => {
  vi.useFakeTimers();
  const { result, rerender } = renderHook(({ v }) => useDebounce(v, 300), { initialProps: { v: 'a' } });
  rerender({ v: 'ab' });
  expect(result.current).toBe('a');

  expect(result.current).toBe('ab');

```

### Q9.5 \[S\] Testing Server Components and Server Functions

Async Server Components are not yet well supported by RTL/jsdom. Practical split: unit-test the data and Server Function logic as plain async functions (auth, validation, DB calls mocked), test Client Components with RTL, and cover the full RSC flow with Playwright.

### Q9.6 \[S\] Accessibility testing

- Lint: `eslint-plugin-jsx-a11y`.
- Automated: `jest-axe`/`vitest-axe` in component tests, `@axe-core/playwright` in e2e. Catches roughly a third of issues.
- Manual: keyboard-only pass (Tab, Shift+Tab, Enter, Space, Esc, arrows), screen reader smoke test (VoiceOver/NVDA), zoom to 200%, reduced motion.
- Querying by role in RTL is itself an a11y test: if `getByRole('button', { name })` fails, so does a screen reader.

### Q9.7 \[I\] Debugging tools

React DevTools (components, props, hooks, "highlight updates", Profiler, owner stack), browser Performance panel with React tracks, `console.log` with Strict Mode dimming, network panel, Redux/TanStack Query DevTools, source maps in production, and React 19 **owner stacks** in error messages (which component *rendered* the faulty one).

### Quick revision

- Mostly integration tests with RTL + MSW; few, critical e2e tests.
- Query by role/label; `user-event`; `findBy` for async.
- Mock the network, not your modules.

- Automated a11y catches some issues; keyboard and screen reader checks catch the rest.

## Part 10 — Security & Production

React escapes text by default, which removes most XSS — but not all. Production readiness is about what happens when things go wrong.

### Q10.1 \[I\] How does React prevent XSS, and where can it still happen?

React escapes strings rendered as children and attribute values. XSS still happens through:

| Vector | Example | Defence |
| --- | --- | --- |
| `dangerouslySetInnerHTML` | Rendering user-written HTML | Sanitise with DOMPurify, ideally server-side; prefer Markdown → safe AST renderer |
| `javascript:` URLs | `<a href={userUrl}>` | Allow-list `http:`/`https:`/`mailto:`; React 19 blocks `javascript:` URLs and warns |
| Spreading untrusted props | `<div {...userProps}>` | Never spread user-controlled objects |
| Third-party scripts / SSR injection | Inline JSON with `</script>` | Serialise with escaping (`serialize-javascript`), CSP |
| DOM APIs in refs | `ref.current.innerHTML = x` | Avoid, or sanitise |

```jsx
import DOMPurify from 'dompurify';
function RichText({ html }) {
  return <div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />;
}
```

Add a **Content Security Policy** with nonces as defence in depth.

### Q10.2 \[S\] Authentication and authorisation patterns in React apps

- **Token storage:** prefer `HttpOnly`, `Secure`, `SameSite` cookies (set by the server, unreadable by JS) over `localStorage` tokens, which any XSS can steal. Add CSRF protection for cookie-based mutations (SameSite + CSRF token or origin checks).
- **Client guards are UX only.** Hiding a button or redirecting from a route does not protect data; the API/Server Function must authorise every request.
- **Pattern:** an `AuthProvider` exposing `user` and `status: 'loading' | 'authenticated' | 'anonymous'`; route guards render nothing (or a skeleton) while loading to avoid flashing protected UI.
- **Authorisation:** check permissions (`can(user, 'invoice:approve')`), not roles scattered through components. Centralise in a policy module shared with the server.
- **Token refresh:** single in-flight refresh promise; queue requests during refresh; logout on refresh failure; sync logout across tabs with `BroadcastChannel` or the `storage` event.

```jsx
function RequirePermission({ permission, children, fallback = null }) {
  const { user, status } = useAuth();
  if (status === 'loading') return <Skeleton />;
  return can(user, permission) ? children : fallback;
}
```

### Q10.3 \[S\] Secure API interactions

- Never ship secrets in client bundles — anything in `NEXT_PUBLIC_*`/`VITE_*` is public.
- Validate inputs on the server (Zod) even if the client validated.
- Use the `server-only` package and Server Components for secret-touching code.
- Rate-limit and authorise Server Functions like any endpoint.
- Don't leak internal error messages to the client; log them server-side and return a safe message.
- Keep dependencies patched; run `npm audit`/Dependabot/Renovate. Patch React promptly when security releases ship.

### Q10.4 \[S\] Error monitoring and logging in production

- Error boundaries at app, route and widget level with **useful fallbacks** (retry, report, navigate home).
- Report via `onUncaughtError`/`onCaughtError` root options (19) and `window.onerror`/`unhandledrejection` to Sentry/Datadog/etc.

## Part 11 — Tricky & Trap Questions

Each trap follows the same format: code → *What happens?* → answer → step-by-step flow → why the tempting answers are wrong. Assume React 19 with `createRoot` unless stated.

### T1 \[I\] Three setters and a log (state snapshot)

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    console.log(count);
  }
  return <button onClick={handleClick}>{count}</button>;
}
```

**What is logged, and what does the button show after one click?**

**Answer:** logs `0`; button shows `1`.

1. Render 1: `count` is the constant `0` in this closure.
2. Each `setCount(0 + 1)` enqueues "replace with 1". The queue is `[1, 1, 1]`.
3. `console.log(count)` reads the closure's `0` — setters never mutate the local variable.
4. After the handler, React batches and renders once: applying the queue gives `1`.

**Why not 3?** That needs updater functions (`c => c + 1`), each receiving the previous queued result. **Why not log 1 or 3?** `count` is a `const` captured at render time; state is a per-render snapshot.

### T2 \[I\] Mixing values and updaters

```jsx
setCount(c => c + 1);
setCount(5);
setCount(c => c + 1);
```

**Starting from 0, what is the result?** **6.** Queue processing: `0 → 1` (updater) → `5` (replace) → `6` (updater). Updates are applied in order; a plain value discards everything queued before it.

### T3 \[I\] Mutating state in place

```jsx
const [user, setUser] = useState({ name: 'Ada', tags: [] });
function addTag() {
  user.tags.push('admin');
  setUser(user);
}
```

**Does the UI update?** **No** (usually not).

1. `setUser(user)` passes the same reference.
2. React compares with `Object.is(old, new)` → `true` → bail out.
3. The mutation happened, but nothing re-renders. If something else later re-renders the component, the tag suddenly "appears", which makes the bug intermittent.

**Why "React deep-compares" is wrong:** React never deep-compares state. **Fix:** `setUser(u => ({ ...u, tags: [...u.tags, 'admin'] }))`.

### T4 \[I\] The stale alert (closures over time)

```jsx
function Inbox() {
  const [count, setCount] = useState(0);
  function showLater() {
    setTimeout(() => alert(`Count: ${count}`), 3000);
  }
  return <><button onClick={() => setCount(count + 1)}>+1</button><button onClick={showLater}>Show</button></>;
}
```

**Click Show, then +1 three times within 3 s. What does the alert say?** **"Count: 0".**

The timeout callback closed over the render where `count` was 0. Later renders create new closures, but the old timer holds the old one.

**Is this a bug?** Not necessarily — it is often the *correct* behaviour ("the count when I clicked"). If you need the latest value, read it from a ref updated in an effect, or use `useEffectEvent` inside an effect-driven timer.

### T5 \[S\] The stuck interval

```jsx
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);
```

**What does the counter display over 5 seconds?** **1, then it stays at 1.** The effect ran once with `count = 0`; every tick sets `0 + 1`. After the first tick React bails out because the value is already 1.

**Fix:** `setCount(c => c + 1)` (no dependency needed). Adding `[count]` also "works" but tears down and recreates the interval every second.

### T6 \[I\] The infinite effect loop — three versions

```jsx
// A: no dependency array
useEffect(() => { setCount(count + 1); });

// B: object dependency created during render
const filters = { status, page };
useEffect(() => { fetchItems(filters).then(setItems); }, [filters]);

// C: function dependency
const load = () => fetchItems({ status }).then(setItems);
useEffect(() => { load(); }, [load]);
```

**Which loop forever?** **All three.**

- **A:** runs after every commit → sets new state → commit → runs again.
- **B:** `filters` is a new object each render → `Object.is` fails → effect runs → `setItems` with a new array → render → new `filters` → repeat. (It is a network loop, not just a render loop.)
- **C:** same as B, with a new function each render.

**Fixes:** depend on primitives (`[status, page]`) and build the object inside the effect; move the function inside the effect; or `useMemo`/`useCallback` as a last resort. Better still, use a query library.

**Why "`setItems` with the same data won't render" is wrong:** each `json()` result is a new array, so `Object.is` is false.

### T7 \[S\] `memo` that never memoises

```jsx
const Child = memo(function Child({ onClick, style }) {
  console.log('Child render');
  return <button style={style} onClick={onClick}>Child</button>;
});

function Parent() {
  const [n, setN] = useState(0);
  return <><button onClick={() => setN(n + 1)}>{n}</button><Child onClick={() => {}} style={{ color: 'red' }} /></>;
}
```

**Does `Child` re-render when `n` changes?** **Yes, every time.** Both `onClick` and `style` are new references each render, so the shallow comparison fails. `memo` added cost and saved nothing.

**Fix:** `useCallback` for the handler and hoist the constant style outside the component (or `useMemo`) — or enable the React Compiler. Same trap with `children`: `<Child><span/></Child>` passes a new element each time.

### T8 \[S\] `useMemo` with an unstable dependency

```jsx
const ids = items.map(i => i.id);
const sorted = useMemo(() => expensiveSort(items), [ids]);
```

**Is the sort cached?** **No.** `ids` is a new array each render; the memo recomputes every time. Depend on `items` (if it's stable) or on a primitive key like `ids.join(',')`.

### T9 \[I\] Index keys and stateful rows

```jsx
function List() {
  const [items, setItems] = useState(['B', 'C']);
  return <>
    <button onClick={() => setItems(['A', ...items])}>Prepend A</button>
    {items.map((item, i) => <label key={i}>{item} <input /></label>)}
  </>;
}
```

**Type "hello" in B's input, then click Prepend. Where is "hello"?** **Next to "A".**

1. Before: key 0 → B (input DOM node holds "hello"), key 1 → C.
2. After: key 0 → A, key 1 → B, key 2 → C (new).
3. React matches by key: key 0's Fiber and DOM input are reused with new text "A". The uncontrolled input keeps its DOM value "hello".
4. Key 2 is new → a fresh, empty input is mounted at the end.

**Why "React re-creates all rows" is wrong:** React reuses nodes whose key matched. **Fix:** `key={item.id}`.

### T10 \[S\] Resetting state from props

```jsx
function EditProfile({ user }) {
  const [name, setName] = useState(user.name);
  return <input value={name} onChange={e => setName(e.target.value)} />;
}
// parent: <EditProfile user={selectedUser} />
```

**Switch `selectedUser` from Ada to Grace. What does the input show?** **"Ada".** The initial value is used only on mount; the component is the same type at the same position, so state persists.

**Fix:** `<EditProfile key={selectedUser.id} user={selectedUser} />`. **Why not `useEffect(() => setName(user.name), [user])`?** It renders a stale frame first, overwrites in-progress edits on refetch, and adds a render.

### T11 \[S\] Context and `memo`

```jsx
const ThemeCtx = createContext({ theme: 'light' });

const Middle = memo(function Middle() { return <Leaf />; });

function Leaf() {
  const { theme } = useContext(ThemeCtx);
  console.log('Leaf render');
  return <p>{theme}</p>;
}

function App() {
  const [theme, setTheme] = useState('light');
  const [clicks, setClicks] = useState(0);
  return (
    <ThemeCtx value={{ theme }}>
      <button onClick={() => setClicks(c => c + 1)}>{clicks}</button>
      <Middle />
    </ThemeCtx>
  );
}
```

**When `clicks` changes, does `Leaf` re-render?** **Yes** — "Leaf render" logs on every click, although `theme` never changed.

1. `setClicks` re-renders `App`.
2. `value={{ theme }}` builds a new object, so `Object.is(oldValue, newValue)` is false and the context value has "changed".
3. `Middle` is memoised with no props, so React skips rendering it.
4. React still finds every component that reads `ThemeCtx` below the provider and schedules it directly — so `Leaf` renders.

**Why "memo on Middle protects Leaf" is wrong:** `memo` only compares props; context updates bypass it. **Fix:** `const value = useMemo(() => ({ theme }), [theme])`, or pass the primitive (`value={theme}`) and read it as a string.

**Fix:** `useMemo(() => ({ theme }), [theme])`, or pass the primitive `value={theme}`.

### T12 \[I\] Controlled input traps

```jsx
<input value={name} />                                  // A
<input value={user?.name} onChange={handle} />          // B, user loads async
```

- **A:** the field is read-only — typing does nothing; React warns to add `onChange` or use `defaultValue`/`readOnly`.
- **B:** first render `value={undefined}` → uncontrolled; after load it becomes controlled → warning "changing an uncontrolled input to be controlled". **Fix:** `value={user?.name ?? ''}`.

### T13 \[I\] Strict Mode double effects

```jsx
useEffect(() => {
  console.log('subscribe', roomId);
  return () => console.log('unsubscribe', roomId);
}, [roomId]);
```

**In development with Strict Mode, what logs on mount?** `subscribe` → `unsubscribe` → `subscribe`.

React mounts, simulates an unmount (running cleanup), then remounts to prove the effect is resilient. **Production:** only `subscribe`. **Why "it's a React bug, remove StrictMode" is wrong:** the double run reveals effects that would break on real remounts (Fast Refresh, `<Activity>`, back-navigation). Fix the cleanup, don't remove the check. **Trap within the trap:** a `useRef` flag to "run once" hides real bugs.

### T14 \[S\] Mutating props during render

```jsx
function App() {
  const [players, setPlayers] = useState(initialPlayers);   // stored in join order
  const [tick, setTick] = useState(0);
  return <>
    <button onClick={() => setTick(t => t + 1)}>Refresh</button>
    <JoinOrderList players={players} />
    <Leaderboard players={players} />
  </>;
}

function Leaderboard({ players }) {
  const top3 = players.sort((a, b) => b.score - a.score).slice(0, 3);
  return <ol>{top3.map(p => <li key={p.id}>{p.name}</li>)}</ol>;
}
```

**What does `JoinOrderList` show after you click Refresh?** **Players in score order** — the join order is gone.

1. First render: `JoinOrderList` renders first and shows join order. Then `Leaderboard` calls `players.sort(...)`, which **sorts the parent's state array in place**.
2. Nothing re-renders, because no state was set. The bug is invisible.
3. Click Refresh: `App` re-renders and passes the same, now-sorted array. `JoinOrderList` displays score order.

**Why "Strict Mode would catch it" is wrong:** the double render just sorts twice, with the same result. **Why "React freezes props" is wrong:** in development React freezes the props object itself, not the arrays and objects it points to. **Fix:** `players.toSorted(...)` or `[...players].sort(...)`, wrapped in `useMemo` if the list is large. Rule: render must not mutate anything that existed before the render started.

### T15 \[S\] Hydration mismatch

```jsx
export default function Footer() {
  return <p>Rendered at {new Date().toLocaleTimeString()}</p>;
}
```

**What happens with SSR?** The server renders its time; the client renders a different time on hydration → React reports a hydration mismatch and, for the mismatched boundary, falls back to client rendering (discarding server HTML up to the nearest Suspense boundary or root). Cost: lost SSR benefit, layout shift, and in some cases event handlers attached to wrong nodes in older versions.

**Fix:** render the time after mount (effect), use `suppressHydrationWarning` on that text node if the difference is acceptable, or format on the server with a fixed timezone and pass the string as a prop.

### T16 \[S\] Fetch race on fast prop changes

```jsx
function Profile({ userId }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetchUser(userId).then(setUser);
  }, [userId]);
  return <h1>{user?.name}</h1>;
}
```

**`userId` changes 1 → 2 quickly; request 1 takes 800 ms, request 2 takes 100 ms. What is shown at the end?** **User 1** — the wrong one.

1. Effect(1) starts request 1. 2. `userId` → 2: cleanup is empty, effect(2) starts request 2. 3. Request 2 resolves → `setUser(user2)`. 4. Request 1 resolves later → `setUser(user1)` overwrites it.

**Fix:** an `ignore` flag or `AbortController` in cleanup (Part 6). **Why "React cancels the old effect" is wrong:** React runs your cleanup; it cannot cancel promises you started.

### T17 \[I\] Component defined inside a component

```jsx
function Form() {
  const [v, setV] = useState('');
  const Input = () => <input value={v} onChange={e => setV(e.target.value)} />;
  return <Input />;
}
```

**What happens when you type?** The input **loses focus after every keystroke**. Each render creates a new `Input` function → a new component type → React unmounts the old input and mounts a new one. **Fix:** declare components at module level and pass props.

### T18 \[I\] Refs don't render

```jsx
function Clicks() {
  const count = useRef(0);
  return <button onClick={() => { count.current++; }}>{count.current}</button>;
}
```

**After 3 clicks, what does the button show?** **0.** The ref changes, but nothing schedules a render. It will jump to the latest value whenever something else re-renders the component. Use state for anything displayed.

### T19 \[S\] `useCallback` with empty deps

```jsx
const [items, setItems] = useState([]);
const add = useCallback(item => setItems([...items, item]), []);
```

**Add three items. How many are in the list?** **One** (the last). `items` is frozen at `[]`; each call sets `[item]`. **Fix:** `setItems(prev => [...prev, item])`.

### T20 \[S\] `useLayoutEffect` vs `useEffect` flicker

```jsx
function Tooltip({ anchorRect }) {
  const ref = useRef(null);
  const [top, setTop] = useState(0);
  useEffect(() => {
    const h = ref.current.getBoundingClientRect().height;
    setTop(anchorRect.top - h);
  }, [anchorRect]);
  return <div ref={ref} style={{ position: 'absolute', top }}>Tip</div>;
}
```

**What does the user see?** A visible jump: the tooltip paints at `top: 0`, then moves after the effect re-renders. **Fix:** `useLayoutEffect` — measurement and the re-render both happen before paint.

### Common misconceptions — rapid fire

| Claim | Reality |
| --- | --- |
| "setState is async" | It's *deferred*: the update is queued and applied on the next render. There is no promise and no callback (use an effect or compute the next value yourself). |
| "Re-render means DOM update" | Re-render = calling the function. DOM changes only where output differs. |
| "Changing props triggers a re-render" | A parent render does; props just come with it. |
| "`useEffect` with `[]` is `componentDidMount`" | Similar timing, different model: it is a sync with no reactive inputs, and Strict Mode re-runs it. |
| "`useMemo` guarantees the value is cached" | It's an optimisation hint; React may discard caches. |
| "Keys only matter in `.map`" | Keys work on any element to force a remount. |
| "Context is a state manager" | It's transport; it has no selectors. |
| "Server Components are SSR" | RSC never hydrate or ship JS; SSR does. |
| "`'use client'` means rendered only on the client" | Client Components are still server-rendered to HTML. |

### Quick revision

- State is a snapshot per render; setters queue; updaters chain.
- Same reference = no render; mutation is invisible.
- Closures capture their render; timers and callbacks can be stale.
- Effects loop on objects/functions created in render.
- Inline props defeat `memo`; Context bypasses `memo`.
- Index keys move DOM state to the wrong row; keys reset state.
- Strict Mode double-calls to reveal impurity and missing cleanup.
- Server/client first-render differences cause hydration errors.
- Clean up async work in effects or the slowest response wins.

## Part 12 — Code Output & Debugging Questions

### O1 \[I\] Render and effect order in a tree

```jsx
function Child({ name }) {
  console.log(`render ${name}`);
  useLayoutEffect(() => { console.log(`layout ${name}`); return () => console.log(`layout cleanup ${name}`); });
  useEffect(() => { console.log(`effect ${name}`); return () => console.log(`cleanup ${name}`); });
  return null;
}
function Parent() {
  console.log('render Parent');
  useLayoutEffect(() => console.log('layout Parent'));
  useEffect(() => console.log('effect Parent'));
  return <><Child name="A" /><Child name="B" /></>;
}
```

**Output on mount:**

```text
render Parent
render A
render B
layout A
layout B
layout Parent
effect A
effect B
effect Parent
```

**Why:** render goes **top-down** (parents call into children). Effects run **bottom-up** (children before parents) because a parent's effect may depend on children's DOM/refs being ready. All layout effects run before any passive effect.

**On re-render of Parent:** renders top-down again; then `layout cleanup A`, `layout cleanup B`, `layout A`, `layout B`, `layout Parent`; then after paint `cleanup A`, `cleanup B`, `effect A`, `effect B`, `effect Parent`. All cleanups of a phase run before that phase's setups.

### O2 \[I\] Updater queue with logs

```jsx
function App() {
  const [n, setN] = useState(0);
  console.log('render', n);
  return <button onClick={() => {
    setN(x => x + 1);
    setN(x => x + 1);
    console.log('handler end', n);
  }}>{n}</button>;
}
```

**Output after one click:**

```text
render 0        (mount)
handler end 0   (click)
render 2
```

The handler logs its own render's snapshot (`0`). Both updaters are queued, the handler finishes, and React renders **once**, applying `0 → 1 → 2`. The button shows `2`.

**Follow-up \[S+\]:** *When exactly do updater functions run?* Normally while React processes the queue in the next render. As an optimisation React may compute the first update early, while the handler is still running. That is why updaters must be pure — Strict Mode calls them twice in development to expose side effects.

### O3 \[S\] Layout effect vs effect vs microtask

```jsx
function Demo() {
  useEffect(() => console.log('effect'));
  useLayoutEffect(() => console.log('layout'));
  console.log('render');
  Promise.resolve().then(() => console.log('microtask'));
  return null;
}
// root.render(<Demo />)   — initial mount, no Strict Mode
```

**Output:** `render` → `layout` → `microtask` → `effect`.

1. `root.render` schedules default-priority work. In that task React renders (`render` logs and the microtask is queued), commits, and runs layout effects (`layout`).
2. The task ends, so the microtask queue drains (`microtask`).
3. For a default-priority update, passive effects are scheduled as a separate task after paint (`effect`).

**Follow-up \[S+\]:** *What changes if the same component re-renders because of a click?* Updates from discrete events (click, keydown) run at sync priority, and React flushes their passive effects synchronously at the end of the commit. The order becomes `render` → `layout` → `effect` → `microtask`. This is why "`useEffect` always runs after paint" is not strictly true.

### O4 \[I\] `useRef` vs `useState` in an event

```jsx
function App() {
  const [count, setCount] = useState(0);
  const ref = useRef(0);
  function click() {
    ref.current += 1;
    setCount(count + 1);
    console.log(ref.current, count);
  }
  return <button onClick={click}>{count}</button>;

```

**After two clicks, the second log is:** `2 1`. The ref is mutated synchronously and shared across renders; `count` is the snapshot from the render the handler belongs to (1 on the second click).

### O5 \[S\] `useMemo` and `useCallback` identity

```jsx
function App() {

  const [other, setOther] = useState(0);

  const fn = useCallback(() => n, [n]);
  const prev = useRef({ obj, fn });

    console.log(prev.current.obj === obj, prev.current.fn === fn);
```

- Mount: `true true` (same render's values).

### O6 \[S\] Context and custom hook

### O9 \[S\] Async state update after unmount / out of order

```jsx
function Search({ q }) {
  const [res, setRes] = useState('');
  useEffect(() => {
    let active = true;
```

### O10 \[S\] Batching across `await`

```jsx
async function handleClick() {
  setA(1);
  setB(1);              // batched with setA → 1 render
  await save();
  setC(1);
  setD(1);              // batched together → 1 more render
}
```

**How many renders?** **Two.** Updates in the same synchronous slice are batched; the `await` ends the slice. Inside `startTransition(async () => …)` (React 19), updates after `await` need their own `startTransition` wrapper to stay marked as transitions — a current React limitation.

### O11 \[S\] Debugging: "my effect runs twice and fetches twice"

Checklist an interviewer wants to hear:

3. Is the component remounting (key changing, parent type changing, component defined inline)? Add a mount/unmount log.
4. Are there two instances rendered (layout + page both mount it)?

### O12 \[S\] Debugging: "the list shows stale data after an update"

1. Was state mutated in place (same reference)?
2. Is a `memo` comparator or memo dependency missing a field?

5. Is an index key reusing DOM from another row?

### Quick revision

- Render top-down; effects bottom-up; all layout effects before passive ones; cleanups before setups.
- Updaters run during the next render; handlers see their render's snapshot.
- Memo hooks keep identity while deps are equal.

- Each synchronous slice batches; `await` starts a new batch.

Senior questions have no single right answer. Interviewers score how you **clarify requirements, name trade-offs, choose, and say what would make you change your mind**. A useful structure for every answer: *Context → Options → Decision → Risks → How I'd measure it*.

### S1 \[S\] Design a scalable React application for a 30-engineer, multi-team product

&#91;embedded content: Feature-based architecture · 4 layers\]

Arrows show the only allowed import direction; a feature reaching into another feature's internals is a review blocker.

**Feature-based structure** (colocate by domain, not by file type):

```text
src/
  app/                 # routes, layouts, providers, app shell
  features/
    billing/
      api/             # queries, mutations, server functions
      components/
      hooks/
      model/           # types, schemas, pure logic
      index.ts         # public API — other features import ONLY from here
    orders/
  shared/
    ui/                # design-system primitives (or a package)
    lib/               # http client, date utils, analytics
    config/
```

**Rules that keep it scalable:**

- Dependencies point inwards/down: `app → features → shared`. Features don't import each other's internals; enforce with ESLint boundaries (`eslint-plugin-boundaries`, Nx module boundaries).
- Each feature has one owning team (CODEOWNERS).
- Shared code earns its place: promote to `shared/` only after a second real consumer.
- TypeScript strict mode, path aliases, consistent error/loading primitives.

### S2 \[S\] Design a reusable component library / design system

- **Layers:** design tokens (colour, spacing, type, radius, motion) → headless behaviour primitives (Radix, React Aria, or your own) → styled components → product patterns.
- **API principles:** composition over configuration (compound components, `asChild`/slot patterns); controlled-or-uncontrolled support; forward `ref` and `...rest` props to the root element; polymorphic `as` only where it's safe for a11y; consistent naming (`variant`, `size`, `onOpenChange`).
- **Accessibility built in:** keyboard support, focus management, ARIA, tested with axe and screen readers.
- **Distribution:** versioned package (Changesets, semver), tree-shakeable ESM, CSS strategy that works with RSC (CSS Modules, Tailwind, or zero-runtime CSS-in-JS — runtime CSS-in-JS conflicts with Server Components and streaming).
- **Docs and tests:** Storybook as the catalogue, visual regression, interaction tests.
- **Governance:** contribution model, deprecation policy with codemods, adoption metrics.

### S3 \[S\] How do you choose a state-management approach for a new app?

Answer with Part 5's classification, then: "I'd start with server-cache library + URL state + local state, add Context for auth/theme, and introduce Zustand or RTK only when a real cross-feature client state appears — e.g. a multi-step editor. I'd revisit if profiling shows Context churn or teams need shared conventions."

### S4 \[S\] A page is slow. Walk me through diagnosing it.

1. **Define slow:** load (LCP/TTFB) vs interaction (INP) vs memory. Get RUM data per route and device class.
2. **Load:** check bundle size and waterfalls (network tab), render-blocking resources, server time, missing SSR/streaming, unoptimised images/fonts.
3. **Interaction:** Performance panel + React Profiler during the slow interaction; find long tasks, frequent commits, wide components.
4. **Fix by cause:** state too high → move down; expensive render → memo/compiler or algorithm; huge list → virtualise; heavy compute → worker/server; too much JS → split, RSC; slow API → cache, prefetch, parallelise.
5. **Verify** with the same measurement, add a budget/regression check.

### S5 \[S\] Large lists: 50,000 rows with sort, filter and inline edit

- Server-side pagination/filtering if the data is large or changes often; client-side only if the dataset fits in memory comfortably.
- Virtualise rows (and columns if wide); stable row keys by id; memoised row components; selection stored as a `Set` of ids.
- Filter/sort in a `useMemo` or a Web Worker; `useDeferredValue` on the query so typing stays responsive.
- Inline edit: edit state lives in the edited row only; commit on blur/Enter with optimistic update.
- A11y: grid role with `aria-rowcount`/`aria-rowindex`, keyboard navigation.

### S6 \[S\] Complex forms: 40-field multi-step onboarding with conditional sections

- React Hook Form or TanStack Form with a Zod schema per step + a combined schema for final submit; share schemas with the server.
- Step state in the URL (`?step=3`) for back/refresh; draft persisted (server or `localStorage`) with versioning.
- Conditional fields: derive visibility from values; unregister hidden fields or strip on submit.
- Async validation (e.g. company name unique) debounced with abort.
- Error summary at top on submit, focus first invalid field, `aria-describedby` for messages.
- Test: unit-test schemas; integration-test each step; one e2e for the happy path.

### S7 \[S\] API integration, caching and synchronisation across tabs and devices

- Typed API client (OpenAPI/tRPC/GraphQL codegen); query keys factory per feature.
- Stale-while-revalidate; invalidate by key after mutations; optimistic updates where reversible.
- Real-time: WebSocket/SSE events → `queryClient.setQueryData` or invalidate.
- Cross-tab: `BroadcastChannel` to sync auth/logout and cache invalidation.
- Offline: persist cache, queue mutations, conflict strategy (last-write-wins vs server merge).

### S8 \[S\] Error boundaries and fault isolation

- Boundaries at **app** (full-page fallback), **route** (keep nav working), and **widget** (one broken chart doesn't take down the dashboard).
- Reset boundaries on navigation (`resetKeys` / `key={pathname}`).
- Distinguish expected errors (404, validation — handled in UI state) from unexpected ones (boundary + report).
- Report with release, route, user id (hashed), and component stack.

### S9 \[S\] Authentication and authorisation at scale

Session cookie (HttpOnly) issued by a BFF or the framework server; Server Components read the session; middleware redirects anonymous users (UX), and every data access path authorises again (security). Permissions modelled as capabilities from the server, used by a `<Can>` component and by Server Functions. Multi-tenant apps include tenant id in every query key and every server check.

### S10 \[S\] Accessibility and UX considerations you enforce as a lead

Semantic HTML; design-system components accessible by default; lint + axe in CI; keyboard and screen-reader acceptance criteria in tickets; focus management on route change and modals; reduced-motion support; skeletons sized to content (no CLS); optimistic UI with clear failure messages; error copy that tells users what to do.

### S11 \[S\] Testing strategy for a large codebase

Trophy shape (Part 9). Contract tests between frontend and API (schema), MSW handlers shared across tests/Storybook/dev, Playwright for top 10 journeys running on every PR against preview deployments, flaky-test quarantine with ownership, coverage as a signal, not a target.

### S12 \[S\] Code splitting and lazy loading strategy

Route-level splitting by default (frameworks do it); lazy-load heavy, below-the-fold or rarely used widgets; prefetch on hover/viewport; avoid splitting tiny components (more requests, more Suspense boundaries); place Suspense boundaries where a loading state is acceptable to users; move static content to RSC.

### S13 \[S\] SSR, streaming, hydration and RSC — when would you adopt them?

Adopt when: public/SEO pages, slow devices or networks, data close to the server, heavy dependencies that can stay server-side. Plan: migrate route by route; mark leaves `'use client'`; identify data waterfalls and turn them into parallel fetches with Suspense; set caching policy per route; train the team on the server/client boundary and Server Function security.

### S14 \[S\] Production debugging and monitoring

"A customer reports a blank screen in production only." Check error monitoring for the session (release, browser), reproduce with production build + source maps, look for hydration errors, chunk-load failures after deploy (stale `index.html` referencing deleted chunks — fix with long-lived asset retention and a reload-on-ChunkLoadError handler), CSP blocks, or feature flag differences. Add the missing boundary/alert afterwards.

### S15 \[S\] Monorepos

Pros: atomic cross-package changes, shared tooling, one version of React. Cons: tooling complexity, CI time. Make it work with Turborepo or Nx (task graph + remote caching), pnpm workspaces, "affected" builds/tests, CODEOWNERS per package, and a single React version enforced across packages (duplicate React = "invalid hook call").

### S16 \[S\] Micro-frontends — when are they worth it?

| Worth it | Not worth it |
| --- | --- |
| Many autonomous teams needing independent deploys | One or two teams |
| Legacy migration (strangler pattern) | Performance-critical consumer apps |
| Different release cadences/compliance boundaries | Desire for "clean separation" alone |

Costs: duplicated dependencies (or fragile shared singletons via Module Federation), inconsistent UX, cross-app routing/state/auth, harder testing and observability. Prefer a modular monolith with enforced boundaries first.

### S17 \[S\] Dependency management

Evaluate libraries on maintenance, bundle size, SSR/RSC compatibility, a11y, licence and types. Wrap third-party UI behind your own component API so you can swap it. Automated update PRs with grouped minor updates; scheduled major upgrades with codemods; lockfile review for supply-chain risk.

### S18 \[S\] Technical leadership and code review scenarios

- *A PR adds `useEffect` to sync props into state.* Ask what problem it solves; suggest derivation or a `key`; explain the extra render and stale frame; approve once fixed or accept with a follow-up if it is urgent.
- *A teammate memoises everything.* Share profiling data; explain cost; point to the React Compiler; agree on a team guideline ("memo when the profiler or a stable-identity requirement justifies it").
- *Two teams want different state libraries.* Write an ADR with criteria (team skills, devtools, SSR, bundle, data shape); prototype both on one real feature; decide and document the escape hatch.
- *Production incident from a hydration bug.* Blameless postmortem, add a test or lint rule, add monitoring for recoverable errors.

**Good code review comments** are specific, explain *why*, separate blocking from non-blocking ("nit:"), and suggest a concrete alternative.

## Part 14 — Hands-on Coding Questions

### H1 \[I→S\] Build a reusable, accessible modal

**Requirements:** open/close controlled by parent; closes on Esc and backdrop click; traps focus; returns focus to the trigger; locks background scroll; labelled for screen readers; renders above everything.

**Edge cases:** nested modals, content taller than viewport, close during an animation, SSR (no `document`).

**Solution — native `<dialog>`** (modern browsers give you focus trapping, Esc, top layer and inert background for free with `showModal()`):

```jsx
import { useEffect, useRef, useId } from 'react';

export function Modal({ open, onClose, title, children, closeOnBackdrop = true }) {
  const ref = useRef(null);
  const titleId = useId();

  useEffect(() => {
    const dialog = ref.current;
    if (!dialog) return;
    if (open && !dialog.open) dialog.showModal();     // focus moves inside; background becomes inert
    if (!open && dialog.open) dialog.close();         // focus returns to the previously focused element
  }, [open]);

  useEffect(() => {
    if (!open) return;
    const prev = document.body.style.overflow;
    document.body.style.overflow = 'hidden';
    return () => { document.body.style.overflow = prev; };
  }, [open]);

  return (
    <dialog
      ref={ref}
      aria-labelledby={titleId}
      onCancel={e => { e.preventDefault(); onClose(); }}        // Esc → let parent decide
      onClick={e => { if (closeOnBackdrop && e.target === ref.current) onClose(); }}   // click on ::backdrop hits the dialog itself
      className="modal"
    >
      <div className="modal__content">
        <h2 id={titleId}>{title}</h2>
        {children}
        <button type="button" onClick={onClose} aria-label="Close">×</button>
      </div>
    </dialog>
  );
}

// Usage
function DeleteButton() {
  const [open, setOpen] = useState(false);
  return <>
    <button onClick={() => setOpen(true)}>Delete</button>
    <Modal open={open} onClose={() => setOpen(false)} title="Delete project?">
      <p>This cannot be undone.</p>
      <button onClick={() => { deleteProject(); setOpen(false); }}>Delete</button>
    </Modal>
  </>;
}
```

**Why `<dialog>`:** the browser handles the hardest a11y parts. The inner `.modal__content` wrapper (with padding) ensures clicks inside content never target the dialog element itself.

**Alternative (custom portal):** `createPortal` into `document.body`, `role="dialog" aria-modal="true"`, a focus trap (cycle Tab between first/last focusable), `inert` on the app root, Esc listener, and restore focus to `document.activeElement` captured on open. Mention libraries (Radix Dialog, React Aria) for production.

**Tests:** opens and focuses inside; Esc calls `onClose`; Tab stays inside; focus returns to trigger; `getByRole('dialog', { name: 'Delete project?' })` works.

```jsx
// jsdom does not implement showModal/close — stub them in test setup

});
```

### H2 \[I\] Debounced search with cancellation

**Requirements:** search as the user types; wait 300 ms after the last keystroke; never show results for an outdated query; show loading/error/empty; cancel in-flight requests.

```jsx
function useDebouncedValue(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);        // each keystroke resets the timer
  }, [value, delay]);
  return debounced;
}

function SearchUsers() {
  const [query, setQuery] = useState('');
  const debounced = useDebouncedValue(query.trim(), 300);
  const [state, setState] = useState({ status: 'idle', results: [], error: null });

  useEffect(() => {
    if (!debounced) { setState({ status: 'idle', results: [], error: null }); return; }
    const controller = new AbortController();
    setState(s => ({ ...s, status: 'loading' }));
    fetch(`/api/users?q=${encodeURIComponent(debounced)}`, { signal: controller.signal })
      .then(r => { if (!r.ok) throw new Error(`HTTP ${r.status}`); return r.json(); })
      .then(results => setState({ status: 'success', results, error: null }))
      .catch(err => { if (err.name !== 'AbortError') setState({ status: 'error', results: [], error: err }); });
    return () => controller.abort();
  }, [debounced]);

  return (
    <div>
      <label htmlFor="user-search">Search users</label>
      <input id="user-search" type="search" value={query} onChange={e => setQuery(e.target.value)} />
      <div aria-live="polite">
        {state.status === 'loading' && <p>Searching…</p>}
        {state.status === 'error' && <p role="alert">Something went wrong. Try again.</p>}
        {state.status === 'success' && state.results.length === 0 && <p>No users match “{debounced}”.</p>}
      </div>
      <ul>{state.results.map(u => <li key={u.id}>{u.name}</li>)}</ul>
    </div>
  );
}
```

**Edge cases handled:** whitespace-only query, out-of-order responses (abort), unmount mid-request, non-2xx responses.

**Improvements to mention:** cache results per query (TanStack Query with `queryKey: ['users', debounced]` and `placeholderData: keepPreviousData`); `useDeferredValue` for client-side filtering instead of debounce; minimum query length; highlight matches.

**Debounce vs throttle:** debounce waits for silence (search, autosave); throttle limits rate (scroll, resize, drag).

**Test:** fake timers; type "re" then "react"; advance 300 ms; assert one request for "react" (MSW) and its results shown.


### H3 \[I\] Create a custom hook: `useLocalStorage` that syncs across tabs

**Requirements:** `[value, setValue]` like `useState`; persists JSON; survives refresh; syncs between tabs and between components using the same key; SSR-safe; handles bad JSON and quota errors.

```jsx
const listeners = new Set();
function notify() { listeners.forEach(l => l()); }

function subscribe(callback) {
  listeners.add(callback);
  window.addEventListener('storage', callback);           // other tabs
  return () => { listeners.delete(callback); window.removeEventListener('storage', callback); };
}

export function useLocalStorage(key, initialValue) {
  const getSnapshot = () => localStorage.getItem(key);     // string | null — stable primitive, safe for comparison
  const raw = useSyncExternalStore(subscribe, getSnapshot, () => null);

  const value = useMemo(() => {
    if (raw === null) return initialValue;
    try { return JSON.parse(raw); } catch { return initialValue; }
  }, [raw, initialValue]);

  const setValue = useCallback(next => {
    const current = (() => { try { const r = localStorage.getItem(key); return r === null ? initialValue : JSON.parse(r); } catch { return initialValue; } })();
    const resolved = typeof next === 'function' ? next(current) : next;
    try {
      if (resolved === undefined) localStorage.removeItem(key);
      else localStorage.setItem(key, JSON.stringify(resolved));
    } catch (e) {
      console.warn('useLocalStorage write failed', e);    // quota exceeded / private mode
    }
    notify();                                             // same-tab subscribers
  }, [key, initialValue]);

  return [value, setValue];
}
```

**Why `useSyncExternalStore`:** localStorage is an external mutable store; this hook prevents tearing under concurrent rendering and provides a server snapshot for SSR. Returning the raw **string** as the snapshot keeps it referentially stable (parsing in `getSnapshot` would return a new object every call → infinite re-render).

**Caveat:** `initialValue` should be a primitive or memoised by the caller, or the `useMemo` recomputes each render. Server and first client render return `initialValue`, so a stored value appears after hydration — mention it.

```jsx
test('persists and syncs between components using the same key', () => {
  localStorage.clear();
  const a = renderHook(() => useLocalStorage('theme', 'light'));
  const b = renderHook(() => useLocalStorage('theme', 'light'));
  act(() => a.result.current[1]('dark'));
  expect(localStorage.getItem('theme')).toBe('"dark"');
  expect(b.result.current[0]).toBe('dark');
});

test('falls back to the initial value when stored JSON is corrupt', () => {
  localStorage.setItem('theme', '{oops');
  const { result } = renderHook(() => useLocalStorage('theme', 'light'));
  expect(result.current[0]).toBe('light');
});
```

**Complexity:** reading is O(size of the stored string), and parsing runs only when that string changes (memoised on the raw value). Writing is O(size) for `JSON.stringify`, plus notifying each subscriber — O(number of mounted hook instances).

### H4 \[S\] Manage complex form state (dynamic list + validation) with `useReducer`

**Problem:** an invoice form with customer fields and a dynamic list of line items (add/remove/edit), computed totals, field-level validation on blur, and submit.

```jsx
const emptyItem = () => ({ id: crypto.randomUUID(), description: '', qty: 1, price: 0 });
const initial = { customer: { name: '', email: '' }, items: [emptyItem()], touched: {}, submitting: false, serverError: null };

function reducer(state, action) {
  switch (action.type) {
    case 'customer':
      return { ...state, customer: { ...state.customer, [action.field]: action.value } };
    case 'item':
      return { ...state, items: state.items.map(i => i.id === action.id ? { ...i, [action.field]: action.value } : i) };
    case 'addItem':
      return { ...state, items: [...state.items, emptyItem()] };
    case 'removeItem':
      return state.items.length === 1 ? state : { ...state, items: state.items.filter(i => i.id !== action.id) };
    case 'touch':
      return { ...state, touched: { ...state.touched, [action.path]: true } };
    case 'touchAll':
      return { ...state, touched: Object.fromEntries(Object.keys(validate(state)).map(k => [k, true])) };
    case 'submit': return { ...state, submitting: true, serverError: null };
    case 'submitError': return { ...state, submitting: false, serverError: action.error };
    case 'submitted': return initial;
    default: throw new Error(action.type);
  }
}

function validate({ customer, items }) {          // pure → derived, never stored
  const e = {};
  if (!customer.name.trim()) e['customer.name'] = 'Name is required';
  if (!/^\S+@\S+\.\S+$/.test(customer.email)) e['customer.email'] = 'Enter a valid email';
  items.forEach(i => {
    if (!i.description.trim()) e[`items.${i.id}.description`] = 'Description is required';
    if (!(i.qty >= 1)) e[`items.${i.id}.qty`] = 'Quantity must be at least 1';
    if (!(i.price >= 0)) e[`items.${i.id}.price`] = 'Price cannot be negative';
  });
  return e;
}

export function InvoiceForm({ onSubmit }) {
  const [state, dispatch] = useReducer(reducer, initial);
  const errors = validate(state);
  const total = state.items.reduce((s, i) => s + i.qty * i.price, 0);
  const show = path => state.touched[path] && errors[path];

  async function handleSubmit(e) {
    e.preventDefault();
    if (Object.keys(errors).length) {
      flushSync(() => dispatch({ type: 'touchAll' }));   // from react-dom: render the errors now so aria-invalid exists before we query it
      e.currentTarget.querySelector('[aria-invalid="true"]')?.focus();
      return;
    }
    dispatch({ type: 'submit' });
    try { await onSubmit({ customer: state.customer, items: state.items }); dispatch({ type: 'submitted' }); }
    catch (err) { dispatch({ type: 'submitError', error: err.message }); }
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      <Field label="Customer name" error={show('customer.name')}
        value={state.customer.name}
        onChange={v => dispatch({ type: 'customer', field: 'name', value: v })}
        onBlur={() => dispatch({ type: 'touch', path: 'customer.name' })} />
      <Field label="Email" type="email" error={show('customer.email')}
        value={state.customer.email}
        onChange={v => dispatch({ type: 'customer', field: 'email', value: v })}
        onBlur={() => dispatch({ type: 'touch', path: 'customer.email' })} />
      <fieldset>
        <legend>Line items</legend>
        {state.items.map(item => (
          <div key={item.id} className="row">
            <Field label="Description" value={item.description} error={show(`items.${item.id}.description`)}
              onChange={v => dispatch({ type: 'item', id: item.id, field: 'description', value: v })}
              onBlur={() => dispatch({ type: 'touch', path: `items.${item.id}.description` })} />
            <Field label="Qty" type="number" value={item.qty} error={show(`items.${item.id}.qty`)}
              onChange={v => dispatch({ type: 'item', id: item.id, field: 'qty', value: v === '' ? '' : Number(v) })}
              onBlur={() => dispatch({ type: 'touch', path: `items.${item.id}.qty` })} />
            <Field label="Price" type="number" value={item.price} error={show(`items.${item.id}.price`)}
              onChange={v => dispatch({ type: 'item', id: item.id, field: 'price', value: v === '' ? '' : Number(v) })}
              onBlur={() => dispatch({ type: 'touch', path: `items.${item.id}.price` })} />
            <button type="button" onClick={() => dispatch({ type: 'removeItem', id: item.id })} disabled={state.items.length === 1}>Remove</button>
          </div>
        ))}
        <button type="button" onClick={() => dispatch({ type: 'addItem' })}>Add item</button>
      </fieldset>
      <p>Total: {total.toFixed(2)}</p>
      {state.serverError && <p role="alert">{state.serverError}</p>}
      <button disabled={state.submitting}>{state.submitting ? 'Saving…' : 'Save invoice'}</button>
    </form>
  );
}

function Field({ label, error, onChange, ...props }) {
  const id = useId();
  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} {...props} onChange={e => onChange(e.target.value)}
        aria-invalid={!!error} aria-describedby={error ? `${id}-err` : undefined} />
      {error && <span id={`${id}-err`}>{error}</span>}
    </div>
  );
}
```

**Design points to say out loud:** errors and totals are **derived** (no sync bugs); items keyed by stable `id` (not index); reducer is unit-testable; validation on blur, all fields on submit; focus first invalid. **Scaling:** at 40+ fields or with performance issues, move to React Hook Form + Zod (fewer re-renders, schema shared with server).

**Why `flushSync` in `handleSubmit`?** Without it, `touchAll` is only queued, so `aria-invalid="true"` isn't in the DOM yet and the focus query finds nothing. This is one of the few legitimate uses of `flushSync`: you need the DOM updated before the next line runs.

**Tests** — the reducer and validator are pure, so test them without rendering, then add one integration test for submit:

### H5 \[S\] Infinite scrolling

**Requirements:** load the next page when the user nears the bottom; no duplicate requests; stop at the end; handle errors with retry; keep it accessible.

```jsx
function useInfiniteList(fetchPage) {
  const [pages, setPages] = useState([]);
  const [cursor, setCursor] = useState(null);
  const [status, setStatus] = useState('idle');          // idle | loading | error | done
  const loadingRef = useRef(false);                      // guards double-trigger before state updates

  const loadMore = useCallback(async () => {
    if (loadingRef.current || status === 'done') return;
    loadingRef.current = true;
    setStatus('loading');
    try {
      const { items, nextCursor } = await fetchPage(cursor);
      setPages(p => [...p, items]);
      setCursor(nextCursor);
      setStatus(nextCursor ? 'idle' : 'done');
    } catch {
      setStatus('error');
    } finally {
      loadingRef.current = false;
    }
  }, [cursor, status, fetchPage]);

  return { items: pages.flat(), status, loadMore };
}

function Feed() {
  const { items, status, loadMore } = useInfiniteList(fetchPosts);
  const sentinelRef = useRef(null);

  useEffect(() => {
    const node = sentinelRef.current;
    if (!node || status !== 'idle') return;
    const observer = new IntersectionObserver(
      entries => { if (entries[0].isIntersecting) loadMore(); },
      { rootMargin: '400px' }                              // prefetch before reaching the end
    );
    observer.observe(node);
    return () => observer.disconnect();
  }, [status, loadMore]);

  return (
    <section aria-busy={status === 'loading'}>
      <ul>{items.map(post => <li key={post.id}><PostCard post={post} /></li>)}</ul>
      <div ref={sentinelRef} />
      {status === 'loading' && <p>Loading more…</p>}
      {status === 'error' && <button onClick={loadMore}>Couldn't load more. Retry</button>}
      {status === 'done' && <p>You're all caught up.</p>}
      {status === 'idle' && <button onClick={loadMore}>Load more</button>}  {/* keyboard / AT fallback */}
    </section>
  );
}
```

**Why a ref guard?** Two intersection callbacks can fire before `status` re-renders; the ref blocks the second synchronously.

**Edge cases:** first page shorter than the viewport (sentinel visible immediately — the effect re-runs after each load and fetches again until the screen fills or `done`); duplicates across pages if data shifts (use cursor pagination, dedupe by id); thousands of items (combine with virtualisation); back navigation (cache pages, restore scroll — TanStack Query `useInfiniteQuery`).

**Complexity:** O(n) rendering in total items unless virtualised; memory grows with pages.

**Test** — test the hook's paging logic directly; leave IntersectionObserver wiring to a Playwright scroll test (jsdom has no layout):


### H6 \[I\] Server-side pagination with URL state

**Requirements:** page through results; page and page size in the URL (shareable, back button works); keep the previous page visible while loading the next; disable buttons at the edges; clamp invalid pages.

```jsx
function usePageParam(defaultSize = 20) {
  const [params, setParams] = useSearchParams();          // React Router / Next.js equivalent
  const page = Math.max(1, Number(params.get('page')) || 1);
  const size = Number(params.get('size')) || defaultSize;
  const setPage = p => setParams(prev => { const n = new URLSearchParams(prev); n.set('page', String(p)); return n; });
  return { page, size, setPage };
}

function OrdersPage() {
  const { page, size, setPage } = usePageParam();
  const { data, isPending, isFetching, isError, refetch } = useQuery({
    queryKey: ['orders', { page, size }],
    queryFn: ({ signal }) => api.getOrders({ page, size }, { signal }),
    placeholderData: keepPreviousData,                     // show old page while new loads
  });

  const totalPages = data ? Math.max(1, Math.ceil(data.total / size)) : 1;
  useEffect(() => { if (data && page > totalPages) setPage(totalPages); }, [data, page, totalPages]);   // clamp

  if (isPending) return <TableSkeleton rows={size} />;
  if (isError) return <ErrorState onRetry={refetch} />;

  return (
    <>
      <OrdersTable rows={data.items} style={{ opacity: isFetching ? 0.6 : 1 }} />
      <nav aria-label="Pagination">
        <button onClick={() => setPage(page - 1)} disabled={page <= 1}>Previous</button>
        <span aria-current="page">Page {page} of {totalPages}</span>
        <button onClick={() => setPage(page + 1)} disabled={page >= totalPages}>Next</button>
      </nav>
    </>
  );
}
```

**Offset vs cursor pagination:** offset (`page`, `size`) supports jumping to page N but skips/duplicates rows when data changes between requests; cursor is stable and fast for infinite feeds but can't jump. **Prefetch** the next page (`queryClient.prefetchQuery`) for instant navigation. **Pure client pagination** (all data loaded): `items.slice((page-1)*size, page*size)`, O(size) per render.

### H7 \[S\] Optimise a slow component

**Given:**

```jsx
function Dashboard({ transactions }) {          // 20,000 items

```

**Problems, found by profiling:**

1. Filter + sort of 20,000 items on every render, including theme toggles. Sort mutates? No (filter returns a new array) — but it's O(n log n) each render.
2. `toLowerCase` of the query repeated per item.
3. 20,000 `<li>` DOM nodes.
4. Index keys — sorting changes positions, so React updates every row.
5. New `onOpen` closure per row defeats any `memo`.
6. Typing blocks while the list re-renders.

**Optimised:**

```jsx
const TransactionRow = memo(function TransactionRow({ t, onOpen }) {
  return <li><button onClick={() => onOpen(t.id)}>{t.description} — {t.amount}</button></li>;
});

function Dashboard({ transactions }) {
  const [query, setQuery] = useState('');
  const [theme, setTheme] = useState('light');
  const deferredQuery = useDeferredValue(query);               // typing stays responsive

  const sorted = useMemo(() => [...transactions].sort((a, b) => b.date - a.date), [transactions]);   // sort once per data change
  const filtered = useMemo(() => {
    const q = deferredQuery.trim().toLowerCase();
    return q ? sorted.filter(t => t.searchText.includes(q)) : sorted;   // searchText precomputed lowercase on fetch
  }, [sorted, deferredQuery]);

  const onOpen = useCallback(id => open(id), []);

  return (
    <div className={theme}>
      <button onClick={() => setTheme(t => (t === 'light' ? 'dark' : 'light'))}>Theme</button>
      <input value={query} onChange={e => setQuery(e.target.value)} aria-label="Filter transactions" />

    </div>
  );
}
```

**Results to state:** sort O(n log n) only when data changes; filter O(n) only when the deferred query changes; theme toggles do no list work; DOM limited to \~visible rows; typing never blocked. Also consider moving filtering to the server or a worker for 100k+ rows. With the React Compiler, the `useMemo`/`useCallback`/`memo` lines become optional, but `useDeferredValue` and virtualisation do not.

**How to verify (measurements, not unit tests):** record the same interaction — typing "rent", then toggling the theme — in the React DevTools Profiler before and after. ### H8 \[S\] Handle API race conditions generically

**Problem:** build a `useAsync` hook that runs an async function when its inputs change and guarantees only the **latest** call can update state, supports cancellation, and exposes status.

```jsx
export function useAsync(asyncFn, deps) {
  const [state, setState] = useState({ status: 'idle', data: undefined, error: undefined });
  const requestIdRef = useRef(0);

  const run = useCallback(() => {
    const id = ++requestIdRef.current;
    const controller = new AbortController();
    setState(s => ({ ...s, status: 'loading' }));
    asyncFn(controller.signal).then(
      data => { if (id === requestIdRef.current) setState({ status: 'success', data, error: undefined }); },
      error => {
        if (error?.name === 'AbortError' || id !== requestIdRef.current) return;
        setState(s => ({ status: 'error', data: s.data, error }));
      }
    );
    return () => controller.abort();
    // eslint-disable-next-line react-hooks/exhaustive-deps -- deps are supplied by the caller
  }, deps);

  useEffect(() => run(), [run]);
  return { ...state, retry: run };
}

// usage
const { status, data, error, retry } = useAsync(signal => api.getUser(userId, { signal }), [userId]);
```

**Two layers of protection:** the request id makes stale responses harmless even when the API ignores `AbortSignal`; abort saves network and server work. Note that `retry` is a manual run and its abort cleanup is not tracked — mention it as a follow-up improvement (store the latest controller in a ref and abort it before each run).

**Other race shapes to mention:** double-submit (disable button or use an Action, which queues), out-of-order mutations (sequence them or use server versions/ETags), optimistic update overwritten by a slower refetch (cancel queries in `onMutate`).

**Test** — control resolution order with hand-made deferred promises:

```jsx
function deferred() {
  let resolve;
  const promise = new Promise(r => { resolve = r; });
  return { promise, resolve };
}

test('a slow, stale response never overwrites a newer one', async () => {
  const calls = {};
  const fetchUser = id => { calls[id] = deferred(); return calls[id].promise; };
  const { result, rerender } = renderHook(({ id }) => useAsync(() => fetchUser(id), [id]), { initialProps: { id: 1 } });

  rerender({ id: 2 });
  await act(async () => { calls[2].resolve({ name: 'Grace' }); });   // newer request finishes first
  await act(async () => { calls[1].resolve({ name: 'Ada' }); });     // older request finishes late

  expect(result.current.data).toEqual({ name: 'Grace' });
  expect(result.current.status).toBe('success');
});
```

**Complexity:** O(1) per request; correctness comes from comparing the request id.

### H9 \[S\] Accessible tabs and accordion

**Tabs requirements (WAI-ARIA Authoring Practices):** `tablist`/`tab`/`tabpanel` roles; `aria-selected`; `aria-controls`/`aria-labelledby`; **roving tabindex** (only the active tab is in the Tab order); Left/Right arrows move between tabs (wrapping), Home/End jump; panel is focusable.

```jsx
export function Tabs({ tabs, defaultIndex = 0, label }) {
  const [active, setActive] = useState(defaultIndex);
  const tabRefs = useRef([]);
  const baseId = useId();

  function onKeyDown(e) {
    const last = tabs.length - 1;
    const next = { ArrowRight: active === last ? 0 : active + 1, ArrowLeft: active === 0 ? last : active - 1, Home: 0, End: last }[e.key];
    if (next === undefined) return;
    e.preventDefault();
    setActive(next);                   // automatic activation; for heavy panels use manual (Enter/Space)
    tabRefs.current[next]?.focus();
  }

  return (
    <div>
      <div role="tablist" aria-label={label} onKeyDown={onKeyDown}>
        {tabs.map((tab, i) => (
          <button
            key={tab.id}
            ref={el => { tabRefs.current[i] = el; }}
            role="tab"
            id={`${baseId}-tab-${tab.id}`}
            aria-selected={i === active}
            aria-controls={`${baseId}-panel-${tab.id}`}
            tabIndex={i === active ? 0 : -1}
            onClick={() => setActive(i)}
          >
            {tab.label}
          </button>
        ))}
      </div>
      {tabs.map((tab, i) => (
        <div key={tab.id} role="tabpanel" id={`${baseId}-panel-${tab.id}`} aria-labelledby={`${baseId}-tab-${tab.id}`} tabIndex={0} hidden={i !== active}>
          {tab.content}
        </div>
      ))}
    </div>
  );
}
```

**Accordion requirements:** each header is a `<button>` inside a heading, with `aria-expanded` and `aria-controls`; panel `role="region"` labelled by the button; support single or multiple open sections.

```jsx
export function Accordion({ items, allowMultiple = false }) {
  const [open, setOpen] = useState(() => new Set());
  const baseId = useId();
  const toggle = id => setOpen(prev => {
    const next = new Set(allowMultiple ? prev : []);
    prev.has(id) ? next.delete(id) : next.add(id);
    return next;
  });
  return items.map(item => {
    const expanded = open.has(item.id);
    const btnId = `${baseId}-btn-${item.id}`, panelId = `${baseId}-panel-${item.id}`;
    return (
      <div key={item.id}>
        <h3>
          <button id={btnId} aria-expanded={expanded} aria-controls={panelId} onClick={() => toggle(item.id)}>{item.title}</button>
        </h3>
        <div id={panelId} role="region" aria-labelledby={btnId} hidden={!expanded}>{item.content}</div>
      </div>
    );
  });
}
```

**Discussion points:** native `<details>/<summary>` is a zero-JS accordion (and `name` attribute gives exclusive groups in modern browsers); `hidden` panels are removed from the a11y tree — if panel state must survive, keep them mounted (as here) or use `<Activity>`; tests should drive the keyboard (`user.keyboard('{ArrowRight}')`) and assert focus and `aria-selected`.

### H10 \[S\] Design a reusable data table

**Requirements:** column definitions with custom cell renderers; client-side sort (click header, toggles asc/desc/none); text filter; pagination; row selection with "select all on page"; empty and loading states; accessible headers.

```jsx
export function DataTable({ columns, rows, getRowId = r => r.id, pageSize = 10, loading = false, onSelectionChange }) {
  const [sort, setSort] = useState(null);                 // { key, dir: 'asc' | 'desc' } | null
  const [filter, setFilter] = useState('');
  const [page, setPage] = useState(0);
  const [selected, setSelected] = useState(() => new Set());
  const deferredFilter = useDeferredValue(filter);

  const processed = useMemo(() => {
    const q = deferredFilter.trim().toLowerCase();
    let out = q
      ? rows.filter(r => columns.some(c => c.filterable !== false && String(c.accessor(r) ?? '').toLowerCase().includes(q)))
      : rows;
    if (sort) {
      const col = columns.find(c => c.key === sort.key);
      const factor = sort.dir === 'asc' ? 1 : -1;
      const cmp = col.compare ?? ((a, b) => (a > b) - (a < b));
      out = [...out].sort((a, b) => factor * cmp(col.accessor(a), col.accessor(b)));
    }
    return out;
  }, [rows, columns, deferredFilter, sort]);

  const pageCount = Math.max(1, Math.ceil(processed.length / pageSize));
  const safePage = Math.min(page, pageCount - 1);          // derived clamp, no effect
  const pageRows = processed.slice(safePage * pageSize, safePage * pageSize + pageSize);
  const pageIds = pageRows.map(getRowId);
  const allOnPageSelected = pageIds.length > 0 && pageIds.every(id => selected.has(id));
  const someOnPageSelected = pageIds.some(id => selected.has(id));

  const updateSelection = next => { setSelected(next); onSelectionChange?.(next); };
  const toggleRow = id => { const n = new Set(selected); n.has(id) ? n.delete(id) : n.add(id); updateSelection(n); };
  const togglePage = () => { const n = new Set(selected); pageIds.forEach(id => (allOnPageSelected ? n.delete(id) : n.add(id))); updateSelection(n); };
  const cycleSort = key => {
    setSort(s => (!s || s.key !== key ? { key, dir: 'asc' } : s.dir === 'asc' ? { key, dir: 'desc' } : null));
    setPage(0);
  };

  return (
    <div>
      <input type="search" aria-label="Filter rows" value={filter} onChange={e => { setFilter(e.target.value); setPage(0); }} />
      <table aria-busy={loading}>
        <thead>
          <tr>
            <th scope="col">
              <input type="checkbox" aria-label="Select all rows on this page" checked={allOnPageSelected}
                ref={el => { if (el) el.indeterminate = !allOnPageSelected && someOnPageSelected; }} onChange={togglePage} />
            </th>
            {columns.map(col => {
              const dir = sort?.key === col.key ? sort.dir : null;
              return (
                <th key={col.key} scope="col" aria-sort={dir === 'asc' ? 'ascending' : dir === 'desc' ? 'descending' : 'none'}>
                  {col.sortable === false ? col.header : <button onClick={() => cycleSort(col.key)}>{col.header}{dir === 'asc' ? ' ▲' : dir === 'desc' ? ' ▼' : ''}</button>}
                </th>
              );
            })}
          </tr>
        </thead>
        <tbody>
          {loading ? (
            <tr><td colSpan={columns.length + 1}>Loading…</td></tr>
          ) : pageRows.length === 0 ? (
            <tr><td colSpan={columns.length + 1}>{filter ? 'No rows match your filter.' : 'No data yet.'}</td></tr>
          ) : pageRows.map(row => {
            const id = getRowId(row);
            return (
              <tr key={id} data-selected={selected.has(id) || undefined}>
                <td><input type="checkbox" aria-label={`Select row ${id}`} checked={selected.has(id)} onChange={() => toggleRow(id)} /></td>
                {columns.map(col => <td key={col.key}>{col.cell ? col.cell(row) : col.accessor(row)}</td>)}
              </tr>
            );
          })}
        </tbody>
      </table>
      <nav aria-label="Table pagination">
        <button onClick={() => setPage(safePage - 1)} disabled={safePage === 0}>Previous</button>
        <span>Page {safePage + 1} of {pageCount}</span>
        <button onClick={() => setPage(safePage + 1)} disabled={safePage >= pageCount - 1}>Next</button>
      </nav>
    </div>
  );
}

// usage — define columns outside render or memoise them
const columns = [
  { key: 'name', header: 'Name', accessor: r => r.name },
  { key: 'amount', header: 'Amount', accessor: r => r.amount, cell: r => formatCurrency(r.amount) },
  { key: 'date', header: 'Date', accessor: r => r.date, compare: (a, b) => new Date(a) - new Date(b) },
];
```

**Complexity:** filter O(n·c), sort O(n log n), page slice O(pageSize); recomputed only when inputs change. Selection uses a `Set` for O(1) lookup and persists across pages and sorts because it is keyed by row id.

**Design discussion:** this is a "headless + default UI" boundary question. For production, a headless engine (TanStack Table) handles sorting/filtering/grouping/column state while you own markup and styling; switch to server-side processing when data is large (send `sort`, `filter`, `page` to the API); add virtualisation for long pages; expose controlled props (`sort`, `onSortChange`) so parents can sync state to the URL.

**Why `data-selected` and not `aria-selected` on the row?** `aria-selected` is only valid on rows when the table has `role="grid"` (an interactive grid with full keyboard navigation). In a plain table, the labelled checkbox already tells assistive technology which rows are selected; `data-selected` is just a styling hook.

- Complex forms: reducer + derived validation; stable ids for dynamic rows.
- Infinite scroll: IntersectionObserver + ref guard + manual fallback.
- Pagination: URL state, keep previous data, clamp pages.
- Optimise: profile, memoise expensive derivations, defer, virtualise, stable keys.
- Races: request ids + abort.
- Tabs: roving tabindex + arrow keys; accordion: `aria-expanded` buttons in headings.
- Data table: derive everything, key selection by id, accessible sort headers.

## Part 15 — Best Practices & Common Mistakes

Good React code is boring: pure components, minimal state, effects only at the edges, and explicit loading/error paths.

### Recommended patterns vs anti-patterns

| Area | Do | Avoid | Why |
| --- | --- | --- | --- |
| Component design | Small, single-purpose components; composition via `children`/slots | 500-line components; boolean-prop explosions (`isPrimary isLarge isCompact`) | Readability, reuse, testability |
| Component definition | Declare components at module level | Components defined inside components | Remounts on every render |
| State shape | Minimal, normalised; store ids | Duplicated or derived state; nested deep objects | Sync bugs, stale copies |
| State location | Colocate; lift only as far as needed | Global store for everything | Unneeded re-renders, coupling |
| Updates | Immutable updates; updater functions for previous-based updates | Mutating state/props | React can't detect change |
| Effects | Sync with external systems; always clean up | Derived state, event logic, prop→state sync in effects | Extra renders, races, stale frames |
| Dependencies | Honest deps; restructure code to remove deps | Disabling `exhaustive-deps` | Stale closures |
| Reset | `key` to reset state | Effects that reset state on prop change | Stale intermediate frame |
| Memoisation | Profile first; React Compiler; memo where identity matters | Memoising everything by default | Cost without benefit, noise |
| Keys | Stable ids from data | Index (dynamic lists), random keys | Wrong state reuse, remounts |
| Data fetching | Framework loaders, RSC, query libraries | Unguarded effect fetches | Waterfalls, races, no cache |
| Context | Low-frequency values; split; memoise value | High-frequency state in one big context | Re-render storms |
| Refs | DOM access, instance values | Reading/writing refs during render | Impure render, compiler bail-outs |
| Errors | Layered error boundaries + reporting | One root boundary; swallowed errors | Whole-app crashes, blind spots |
| Accessibility | Semantic elements, labels, focus management | `div onClick`, placeholder-as-label | Excludes users, legal risk |
| Types | TypeScript strict, discriminated unions for status | `any`, three booleans for status | Impossible states become possible |

### Effects decision checklist

Before writing `useEffect`, ask in order:

1. Can I compute this during render? → compute (memoise if expensive).
2. Is it caused by a specific user action? → put it in the event handler.
3. Do I need to reset state when a prop changes? → `key`.
4. Am I subscribing to an external store? → `useSyncExternalStore`.
5. Am I fetching data? → framework/query library; otherwise effect with abort.
6. Am I syncing with a non-React system (DOM API, widget, socket)? → **this is what effects are for** — with cleanup.

### Production-ready loading and error states

```jsx
function OrdersPanel() {
  const { data, status, error, isFetching, refetch } = useOrders();
  if (status === 'pending') return <OrdersSkeleton />;                       // layout-stable
  if (status === 'error') return <ErrorState title="Couldn't load orders" detail={toUserMessage(error)} onRetry={refetch} />;
  if (data.length === 0) return <EmptyState action={<NewOrderButton />} />;  // empty ≠ error
  return <><RefreshingIndicator active={isFetching} /><OrdersTable rows={data} /></>;
}
```

- Every async UI has four states: loading, error, empty, success — design all four.
- Keep stale data visible during background refresh.
- Error messages tell users what happened and what to do; log technical details separately.
- Disable or debounce actions while pending; use Actions to get pending state for free.

### Performance without premature memoisation

1. Structure first: colocate state, lift content up, split components on update boundaries.
2. Measure: Profiler + Performance Tracks + RUM.
3. Fix the dominant cause (algorithm, list size, bundle, network).
4. Memoise where identity or cost is proven — or let the React Compiler do it.

### Maintainability habits seniors look for

- Consistent folder structure and public module APIs.
- Naming: components as nouns (`InvoiceTable`), hooks as `use` + noun/verb (`useInvoices`), handlers as `handleX` internally and `onX` as props.
- Props: small, explicit, typed; forward `...rest` and `ref` on design-system components.
- No magic: avoid clever HOC chains and implicit globals.
- Document decisions in ADRs; codemods for breaking changes; lint rules for team conventions.

### Top 15 mistakes interviewers listen for

1. Storing derived data in state.
2. Fetching in effects without cleanup.
3. Disabling the hooks lint rule.
4. Index keys on dynamic lists.
5. Mutating state.
6. Defining components inside components.
7. One giant context for all app state.
8. Memoising everything (or nothing, then blaming React).
9. Using effects to respond to events.
10. Treating client-side route guards as security.
11. `dangerouslySetInnerHTML` without sanitising.
12. Ignoring hydration warnings.
13. No error boundaries around risky widgets.
14. Inaccessible custom controls (`div` buttons, no focus management).
15. Shipping everything as client JS when it could render on the server.

## Part 16 — Rapid Revision Cheat Sheet

Read this the night before. Each line is an answer you should be able to expand into two minutes of explanation.

**Core model**

- `UI = f(state)`; render = call components; commit = touch DOM; effects after.
- Re-render triggers: own state, parent render, context change, external store.
- State is a per-render snapshot; setters queue; updaters chain; same reference bails out.
- Keys = identity; new key = new instance; index keys break reorder.

**Hooks**

- Order must be stable (except `use`).
- `useEffect` after paint; `useLayoutEffect` before paint; cleanup before re-run and on unmount.
- `useRef` persists without rendering; don't touch in render.
- `useMemo`/`useCallback` are hints; React Compiler auto-memoises.
- `useEffectEvent` (19.2): latest values without re-running effects.
- `use` reads cached promises/context; can be conditional.
- `useSyncExternalStore` for external stores; stable snapshots.

**Internals**

- Fiber: units of work, linked list, double buffering, lanes.
- Reconciliation: type + position + key decide keep vs remount.
- Batching everywhere since 18; `flushSync` to opt out.
- Transitions = interruptible, non-urgent; deferred values lag; neither speeds up code.
- Strict Mode: double render, effect re-run, ref callback re-run (dev only).

**Advanced**

- Context bypasses `memo`; memoise value; split; no selectors.
- Portals: DOM moves, React tree (events, context) doesn't.
- Error boundaries: render/lifecycle errors, not handlers/async.
- Suspense: nearest boundary fallback; transitions keep old UI; nested boundaries stream.
- `<Activity>`: hide but keep state.
- `ref` is a prop in 19; `forwardRef` legacy.

**State and data**

- Classify: local, lifted, URL, context, client store, server cache, form, derived.
- Server state → query library or RSC; keys, staleTime, invalidation.
- Optimistic: snapshot → apply → rollback → re-sync. `useOptimistic` for Actions.
- Forms: uncontrolled + Actions first; `useActionState`, `useFormStatus` (in a child of form).
- Abort or ignore stale responses in every effect fetch.

**Performance**

- Profile → cause → fix → verify.
- Move state down, lift content up, then memo.
- Virtualise long lists; split bundles by route; push static UI to the server.
- INP: transitions, deferred values, workers.

**Server rendering**

- SSR = HTML + hydrate; RSC = server-only components, zero JS; Next.js combines both.
- Streaming + selective hydration; avoid client/server first-render differences.
- `'use client'` = module boundary; pass server components as children.
- Server Functions = public endpoints: auth + validate inside.

**Testing, security, production**

- RTL by role + `user-event` + MSW; few Playwright journeys; axe + manual a11y.
- XSS via `dangerouslySetInnerHTML`, URLs, prop spreading; sanitise, CSP.
- HttpOnly cookies; authorise on the server; no secrets in bundles.
- Layered boundaries, root error callbacks, source maps, RUM, feature flags.

**Senior framing**

- Context → options → decision → risks → measurement.
- Feature folders with enforced boundaries; design system on headless primitives.
- Modular monolith before micro-frontends; monorepo with one React version.
- Code review: explain why, separate blocking from nits, offer an alternative.

**Version notes to say confidently:** React 19 is the stable line, at 19.3 (19.3.1 is the latest patch as of November 2026). 19.0 brought Actions, `use`, `useActionState`, `useOptimistic`, ref as a prop and metadata hoisting. 19.2 added `<Activity>`, `useEffectEvent` and Performance Tracks. 19.3 made `<ViewTransition>` and Fragment refs stable, added react-dom `browser()` and Trusted Types support, and renders transitions independently. React Compiler 1.0 is a separate, stable build plugin. Server Components need a framework.
